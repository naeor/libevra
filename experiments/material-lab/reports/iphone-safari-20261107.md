# LMPP 0.3.2：iPhone Safari 真机性能测试报告

## 结论与适用范围

本次真机自动测试中，Native 没有暴露明显的帧时间问题；当前 Precomputed、Uniform 和 Tiled 的 JavaScript 模糊实现存在严重的画面生成延迟。产品选型可以优先考虑浏览器原生材质，自研实现继续留在 Lab，不应因为已有研发投入而接入正式产品。

结论针对这一版实现、这一台设备和这一组负载。不能推出所有 SSPR 算法都比原生差，也不能推出原生在 GPU、功耗或发热上全面优胜——本报告没有这些测量。

## 2. 测试环境与负载

浏览器 UA 报告 iPhone、iPhone OS 18_7、Safari Version/27.0.1；这里照录 UA，不据此推断具体机型。实际 DPR 为 3，结束时视口 393 × 695，实验场景宽 365 CSS px。原生滤镜可用；Event Timing 可用，LoAF、JS Heap 不可用。局域网 HTTP，非安全上下文。

空闲 rAF 采样 90 个间隔：平均 16.63 ms，中位数 17 ms，P95 17 ms，P99 20 ms。页面使用 17 ms 作为对照预算，约 58.8 次/秒只是量化后的回调节奏，不是实测屏幕呈现帧率。

使用固定种子模拟数据，80 / 240 笔列表，单色 1×1 字形代理，模糊半径 12 CSS px，浅色主题，关闭折射。后台预算 3 ms。每轮执行构建或更新、滚动、反向滚动、打开面板、拖动、关闭面板、单笔修改、连续五笔修改、约 5 秒稳定性负载。即每轮包含七次构建/更新。

冷缓存是应用缓存清空，不是浏览器、字体或驱动的冷启动；每组事先预热。热缓存测试修改了数据，不是读取完全相同的旧画面。自动滚动和拖动不是真实触摸。

## 4. 结果解释

### 4.1 帧节奏稳定，不代表结果及时

分批计算让主线程不断有机会处理帧回调，因此平均帧间隔约 16.7 ms；但一个新结果仍可能要等四五十秒。第一轮 Precomputed 冷缓存测试约 310 秒，其中首次构建约 42.3 秒，单笔修改约 48.3 秒，连续五笔约 212.7 秒。此前“第三轮一直不动”的感受有明确数据依据，不只是进度文案问题。

当前构建过程中会暂用静态材质。因而漫长计算阶段中的平稳 rAF，也不能当作实时玻璃始终流畅的证明。整轮帧统计还会被大量计算等待期稀释，应优先结合具体滚动、拖动子阶段观察。

### 4.2 主要瓶颈在模糊与调度，不在字形代理

Uniform 每轮代理计时中位数仅约 140–296 ms，而模糊计时累计约 107–113 秒。Precomputed 与 Uniform 都使用当前 JavaScript 盒式模糊核心，二者结果接近不能证明代理思想没有价值，只能说明现有模糊实现掩盖了其余差异。

旧核心每像素重复执行索引函数与边界运算；调度器每约 3 ms 使用 setTimeout 让出执行权，单次构建可达五千多次。数据证明计算本身和调度等待都值得优化，但尚无 Safari profile，不能把全部差值归因于某一个浏览器机制。

### 4.3 缓存统计必须按层理解

Uniform 的总体命中率约 99% 以上，主要是字形复用。第一组热缓存测试中，80 与 240 笔完整纹理缓存均为 0 次命中、8 次未命中：新内容意味着新整图，仍会重新模糊。该测试不是“缓存坏了”，而是整图缓存难以覆盖编辑后的增量更新。

Tiled 热更新比 Uniform 快很多，说明局部更新有效；但首次构建所有区块仍很慢，Halo 增加边缘工作量。本次数据不支持“Tiled 冷启动也优于 Uniform”。

### 4.4 长列表并非同画质比较

为避免整页 Canvas 过大，80 笔有效画布 DPR 约 1.242，代理比例约 0.311；240 笔分别约 0.725、0.181。两者参考画布均接近四百万像素预算，代理像素量也因此接近。长列表降低了精度、代理模糊半径和修改所影响的像素面积。

因此 240 笔 Tiled 热更新更快，不是“数据越多越快”，也不能证明长列表画质不变。后续应增加视口区域渲染或固定画质对照，不能靠扩大整页 Canvas 得出扩展性结论。

### 4.5 保护机制遗漏结果等待

旧保护关注 P95 帧间隔和输入延迟，整个会话没有触发。单次构建最大约 55 秒，没有超过 60 秒硬取消阈值，所以整轮等待数分钟仍可正常完成。结果生成等待需要独立保护，不能靠 FPS 判断。

## 5. 报告保存缺陷

用户导出的完整报告为 124,370,035 字节，紧凑 JSON 约 37.90 MiB。电脑接收端限制 16 MiB，实际只保存到 18 轮、修订 19（约 15.97 MB）。之后即使测试继续，完整检查点也会被拒绝。

同一帧数据同时出现在整轮和子阶段数组中，并使用大量重复字段；每轮重新发送所有历史数据，造成网络、序列化和存储放大。此前短测试验证不足，没有覆盖三小时级完整报告，是 Lab 的实现问题，而非用户保存操作错误。

## 6. 局限与不能下的结论

1. 单设备、单次长会话、每组仅三次重复。构建 P95/P99 在三个样本中实际落到最大值，不是稳定的总体高分位估计。
2. 测试接近三小时。虽轮换算法顺序，仍不能排除设备状态、温升和系统负载影响；未测温度或功耗。
3. 原生 GPU 成本不可直接读取；rAF 不是每帧真实呈现测量。没有证据支持“原生全面更省电”。
4. 没有手动触摸测试；40 ms 页面级 INP 不可用作四算法输入体验比较。
5. 无画质评分、截图对照或真机字形损失验收，不能声称视觉效果等价。
6. 5 轮帧样本截断；大报告、重复序列化和保存也可能影响设备状态。轮次外保存避免直接计入计时，并不等于完全无干扰。

## 7. 决策建议与下一步

- 产品方向：优先验证原生 backdrop-filter 在实际页面和目标设备上的使用边界，保留不透明材质回退。该实验支持继续使用原生，不授权直接修改正式产品。
- 自研方向：保留 Tiled 增量思路，优先优化 CPU 模糊和调度；不把研究目标设为必须打败原生。
- Lab 工程：增量回传、去重帧数据；加入可观察的结果等待保护；将降级轮次明确排除出同画质性能结论。
- 下一次真机验证先做短场景：单次冷构建、几次单笔更新、滚动和真实点击。确认数量级改善后再决定是否跑完整压力测试。

## 8. 本轮实现与验证记录（0.3.3）

报告上传改为逐轮增量请求，电脑合并为同会话 JSON；浏览器恢复文件和导出采用紧凑结构，子阶段帧使用 `[start, at, ms]`，整轮不再重复保存原始帧。统计值与既有报告保持可比较，原有 truncated 标记保留。

新增默认 2 秒、可调 0.5–10 秒的结果等待保护（仅实验参数）。启用自适应时，自研材质准备超过阈值直接取消昂贵计算并使用静态材质，之后沿用稳定窗口恢复；关闭自适应时保留原有 60 秒硬取消。

模糊核心把逐像素闭包索引改为预计算步长与直接索引，保留原有三次盒式核、Float32 中间数据和 Halo 语义。浏览器分批让出改用 MessageChannel，保持原有时间预算、用户忙碌暂停、取消和隐藏页保护。这是实现优化，不是更换测试负载或降低精度。
