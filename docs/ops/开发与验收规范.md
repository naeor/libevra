# 开发与验收规范

> 最后修改：2026-11-08 23:47（UTC+08:00）

本文定义开发检查、风险分级与交付证据；授权边界仍在 [AGENTS](../../AGENTS.md)。检查范围由实际影响决定，不以“简单改一下”的措辞降级。纯文档任务不升级产品版本、不执行业务构建或数据库迁移。

## 开发规则

- 用户可见功能、行为或样式变更：更新 `packages/shared/src/version.ts`、对应系列 changelog 和 STATUS 的相关行；产品版本规则见[版本与兼容规范](../specs/product/内部构建编号、产品版本与多端兼容规则.md)。
- 修复实现错误而既定规则正确时，保留正确规格；改变有效契约时直接更新其权威正文。
- Web 源码有改动，提交前必须 `pnpm check:build`；它包含 Web typecheck，避免重复。
- 不用 shell 字符串替换 UTF-8 源码；使用可靠的补丁或结构化编辑。完成后核对差异与实际接线。
- 金额、权限、迁移、离线、导入导出和兼容性按下表执行专项；数据库改动前备份并验证可恢复。

## 小版本更新与 changelog

**每完成一个小版本更新，必须在提交和交付前把该版本写入 `docs/changelog/` 对应系列文件；缺少条目不算该版本交付完成。** 例如 `1.19.44` 记入 `1.19.md`；进入新系列时按版本规则维护相应入口。仅本机、内部测试、尚未 push 或尚未部署的版本同样要记录，不等阶段结束或正式发布时再集中回忆补写。

- 条目以准确版本号和实际日期标识，简述改了什么、主要修复及原因、实际验证结果与未验证项，并明确“仅本机 / 内部测试 / 已部署”等真实状态。涉及数据库、协议或兼容性变化时同时说明影响和迁移要求，必要时链接对应证据。
- 同一小版本的补充及时更新该条目；下一个小版本单独新增条目，不能用一个笼统阶段总结替代多个版本记录。历史事实保留，后续修复写入对应的新版本。
- 提交前对照 `packages/shared/src/version.ts` 核对版本条目、实际改动和 STATUS 是否一致；Git 提交信息、聊天回复、STATUS 或用户可见公告都不能代替技术 changelog。
- 未执行的测试不写成通过，未部署不写成已上线。技术记录与用户公告分开维护，不要求每个 commit 都生成公告；纯文档任务不升产品版本，也不为此虚构一个小版本条目。

## Diagnostic Mode：专项 Bug 诊断模式

**可选的工作方式，不是额外验收等级。** 适用于反复修复失败、根因不明、跨页面出现相似症状，或涉及浏览器、设备与平台差异的问题。Agent 可根据现象主动采用：优先理解问题、收集运行证据，提出并验证根因假设，再选择修复方案。原因明确的常见小 Bug 可以直接处理；不要求每次执行完整流程或生成调查报告，既有风险分级与授权边界仍然适用。

### 按问题选择排查方法

以下是可组合、可跳过、可回到前一步的方法，不是逐项打勾的固定流水线。已有可靠证据可以复用；新证据推翻假设时及时调整方向，不连续叠加未经验证的补丁。

- **复现与现象拆分**：明确预期和实际行为、触发路径、发生频率及影响范围；记录与问题有关的版本、浏览器、设备、构建模式和页面状态。把“卡顿”“闪一下”等描述拆成可观察的事件，比较首次与再次进入、正向与返回、正常与失败样本。
- **代码与接入调查**：沿实际业务入口追踪事件、状态、数据和组件生命周期，检查共享依赖与近期变更。跨页面相似症状可优先调查共同路径，但不能仅凭外观相似认定根因相同；同时核实修复代码是否真的被正式页面调用。
- **运行证据与性能测量**：按需使用日志、时间戳、浏览器性能记录、逐帧画面或设备测量，区分调度等待、脚本执行、布局、绘制和合成等可能来源。说明测量环境、采样方式和工具限制；诊断代码本身也可能改变时序，避免用单次测量或桌面模拟代替目标设备结论。
- **根因假设与最小实验**：提出少量可证伪的解释，并说明各自预期看到的证据；一次尽量改变一个因素，用对照缩小范围。最小实验可验证机制，仍需回到真实数据、布局与导航接入中确认；症状暂时消失不等于因果关系已经证实。
- **针对性查阅资料**：遇到不熟悉的 API、浏览器特定行为或无法解释的现象，主动查阅最新官方文档、标准、浏览器厂商说明及相关问题记录，必要时参考可信研究。记录关键出处与适用版本，区分文档明确说明、运行中观测到的事实和自己的推测；版本未知或资料与实测不符时保留不确定性并验证，不把单一帖子或旧资料当作通用结论。
- **修复与正式业务验收**：根据证据选择能解释问题的修复，或明确说明临时缓解方案的代价与后续验证需求。复测原失败路径及实际受影响的邻近场景；按风险选择自动测试、真实页面操作和目标平台验证，不机械扩大为全量检查。

### 时序、渲染与内容交接的通用原则

以下原则吸收 S19 首帧计时、正式页面接入、渲染停顿和 Object Expand 内容交接的经验；[相关版本记录](../changelog/1.19.md)保留当时的方案与验证边界。具体时长、进度阈值、时钟实现或浏览器归因不能直接升级为所有功能的默认规则。

- **区分不同的时间点**：交互触发、状态提交、动画计时起点、回调执行与用户实际看到第一帧可能不一致。排查跳帧或起始姿态丢失时，关注这条时间线；回调执行或样式值正确本身不能证明相应画面已经显示，必要时结合性能记录与逐帧画面核对。
- **把运动连续性与渲染成本分别验证**：时钟或调度调整可能改善可见运动，重渲染、布局测量、快照或滤镜造成的停顿仍可能存在。分别检查起始等待、帧间隔、总耗时和交互响应；降级与超时收尾要能释放临时状态，不能把缓解措施写成已经消除性能根因。
- **以正式接入为验收对象**：Demo 成功只证明其环境下的行为。接入后需要核对真实页面挂载、滚动、导航、内容规模及材质等条件是否改变了机制；在实际入口上验证，而不只检查工具函数或独立实验。
- **明确内容交接与状态归属**：涉及旧页、过渡层和目标内容时，先说明谁承载可见内容、何时提交状态、何时交接以及中断后谁清理。结合内容就绪、几何和遮挡关系选择交接时机，不照搬固定百分比；按影响检查展开、收回、快速反向、返回或视口变化后的内容连续性、可操作性与残留状态。

### 诊断交付

在通常的交付回复中简要说明：**已证实的原因及关键证据、采用的方案、实际验证结果、仍不确定或未覆盖的部分**。若只找到相关因素、暂时缓解或尚未复现，应如实说明，不强行宣称找到根因。需要时附最小复现或资料链接；有长期价值的理由按既有文档维护规范记录，不为每次排查另建完整报告。

## 检查分级：按改动范围选一级，每条命令跑一次

| 级别 | 什么时候 | 跑什么 |
|---|---|---|
| **日常检查**（Level 1，默认） | 普通开发任务、普通低风险任务 | 改动包的 typecheck（`pnpm --filter @libellum/<web\|api\|shared> typecheck`）+ 受影响测试（`pnpm --filter @libellum/web exec vitest run <文件或目录>`）；web 有改动跑 `pnpm check:build`（含 web typecheck，不要再跑一遍）；改了文档跑 `pnpm check:docs`；改了版本号 / 迁移 / STATUS 跑 `pnpm check:status`；影响交互时在 `localhost:5173` 走一遍相关路径 |
| **交付检查**（Level 2） | 准备把一个完整版本交给所有者验收；高风险任务 | `pnpm check:delivery`（shared + api typecheck、真实构建、文档、状态、i18n）+ 改动包**全量**测试；动 API / 数据库另跑 API 测试（需测试库）与 `pnpm check:db`；改配置 schema 跑对应的兼容 / 迁移测试 |
| **验收检查**（Level 3） | 阶段收尾、生产发布前；阶段或生产任务 | `pnpm -r test`（含 API + Postgres）、`pnpm build`、`pnpm check:delivery`、`pnpm check:db`；迁移：备份 + 隔离库恢复演练 + 行数比对；权限 / 越权；历史兼容；浏览器 320 / 390 / 1280 与真机（iOS Safari / PWA）清单；**一份**阶段验收总结或发布记录 |

**不能降级的范围**：只要改动碰到 **财务金额计算、数据丢失风险、账号与账本权限、数据库迁移、离线队列与同步冲突、导入导出、安全与隐私、配置 schema 兼容** 之一，至少做交付检查，并跑该模块的全量测试与对应专项（金额 → 独立复算 / 边界样本；迁移 → 备份恢复演练；权限 → 越权测试；同步 → 离线与并发冲突用例）。用户说"简单改一下"也不例外。

**不要重复**：

- 同一条命令通过后不要为了"再确认"重跑；只有改了代码或失败修复后才重跑**失败的那一项**。
- 不因为改了一个文件去跑与它无关的模块测试，不全量扫描历史版本，不在 `archive/` 里核对旧数字。
- 截图只在视觉改动需要所有者确认、或所有者要求时做；不逐页截图。
- CI（`.github/workflows/ci.yml`）在 push / PR 时会跑全套；本地不需要为了"模拟 CI"把全套再跑一遍，除非是验收检查。

```powershell
pnpm check:build      # 真实生产构建（含 web typecheck）← web 有改动不能省
pnpm check:docs       # 相对链接 + 文档值一致性（只报问题；--verbose 看明细：node tools/doc-audit.mjs --verbose）
pnpm check:status     # STATUS 与代码 / 迁移数一致，且没有变回历史日志
pnpm check:delivery   # 交付检查的固定组合
pnpm check:db         # 开发库 / 测试库迁移一致
```

## 交付说明

说明实际修改、版本是否变化、检查结果、未验证项与剩余风险。区分代码完成、自动检查通过、所有者验收和生产发布。没有真实设备记录就不宣称 Safari 真机通过；未执行的测试不写成通过。

有小版本更新时，交付前确认对应 changelog 已写入且反映最终改动；简短交付回复注明记录位置，便于所有者追溯。

文档与工具修改运行 `pnpm check:docs`；目录清单变更先 `pnpm docs:index`；已有阅读版按[文档维护规范](文档维护规范.md)同步与验证。只修改文档工具时验证受影响工具，不为了形式执行全量业务测试。
