# 文档体系与持续维护规范

> 最后修改：2026-11-08 22:52（UTC+08:00）

本文是文档组织、同步更新、目录导航和阅读版生成的权威规则。Agent 的授权与安全边界仍在 [AGENTS](../../AGENTS.md)，检查等级见[开发与验收规范](开发与验收规范.md)。

## 1. 三类信息

| 类型 | 负责什么 | 位置与维护方式 |
|---|---|---|
| 现行规则 | 当前有效产品、技术、设计、开发、运维契约；未来方案须标明规划中/待确认 | `specs/`、`ops/` 和核心正文；直接替换被修改的规则 |
| 历史记录 | 原方案、否决理由、试验、重要讨论、发布/验收证据 | `archive/`、版本日志、ADR/经验案例；按当时语境阅读 |
| 导航索引 | 文件职责、直属内容、任务到权威来源的路由 | 各层 README 管目录；`00-索引.md` 管任务，不复制完整目录树 |

STATUS 是唯一当前状态表，不写维护流水。`01-规划` 是现行规划入口与候选池，长期路线图定义阶段；`02-技术方案` 解释现行架构和代码入口。规则与历史必须分开；确需同文件保留时，现行规则在前，历史在明确标记的最后区域。

## 2. 规则直接替换

正式决定由 A 改为 B 后，权威正文直接写完整的 B，不留下 A/B 并列，也不追加日期更正让读者推理。Git 保存字节历史；重要理由、所有者决定、否决背景和实验依据保存到历史或 ADR 并从正文链接。

不把“规划中”“推荐”“待确认”改成既成政策，不凭阶段完成自动关闭所有未决问题。旧任务 ID、历史发布状态和原始验收记录保留意义，不重写成今天的状态。不为减少篇幅删除独有决定。

### 最后修改时间

每次新增或修改 Markdown 文档（包括 AGENTS、README、索引、规范和版本记录），在一级标题下、正文前保留一行 `> 最后修改：YYYY-MM-DD HH:mm（UTC+08:00）`。完成本轮编辑时读取实际系统时间，按北京时间更新，精确到分钟；覆盖原值，不追加时间流水。正文、引用和目录清单的修改都适用，批量编辑可在内容定稿后统一补齐，再生成阅读版。

“最后修改”只表示本文件最近一次编辑；“最后核对”表示整份文档实际核验，不能因局部修改顺手更新。历史事件、发布、验收日期保留原义；确需修正历史文件的链接时，新增或更新独立的修改时间，不改写历史日期。未触及的文档不批量补造修改时间，待下次编辑时加入。

只读检查、内容未变的目录生成或单独重新生成 PDF 不更新 Markdown 的修改时间。PDF 沿用源文档中的时间，生成与校验时间仍由阅读版清单分别记录；更新时间标记后，也须按阅读版规则同步已有 PDF。

## 3. 目录 README

每个长期维护目录应有 README，说明职责、优先入口、直属文件和子目录；根 README 继续介绍产品。源码目录尽量列出模块、组件、脚本和测试用途，细节以实现和专题规范为准。

`pnpm docs:index` 更新 README 的 `directory-index` 自动区块，不覆盖人工职责说明。`pnpm check:docs` 检查清单是否过期。自动区块从 Git 跟踪文件和未忽略的新文件生成，不读取私密配置；Markdown 标题、模块导出与文件名只用于定位，不替代产品定义。发现用途描述不准确时修改 README 的人工说明。

合理排除：依赖、缓存、生成客户端、构建产物、阅读版、私人资料和 vendored 代码；数据库迁移单元、冻结截图和纯素材叶目录由父 README 列出，不在每个自动/证据单元重复 README。具体排除集中在目录工具中，不用人工维护第二份文件列表。源码仍依赖的实验和历史协议不得按目录名清理。

## 4. 开发中的同步维护

| 改动 | 完成时维护 |
|---|---|
| UI 行为、材质、布局规则改变 | 对应现行设计规范；用户可见时版本记录与 STATUS |
| 新增、删除、移动文件 | 受影响目录 README、引用与必要任务索引 |
| API、协议、schema、导入/导出格式或兼容性改变 | 对应技术契约、兼容影响、迁移及验证说明 |
| 实现错误修复，既定规则仍正确 | 必要技术变更记录，不重写正确规则 |
| 正式版本或部署变化 | 对应系列 changelog、STATUS；发布执行单独留证据 |
| 重要设计选择或失败经验 | 原有 ADR/专题历史/经验记录，避免另建重复报告 |
| 已有阅读版的 Markdown 正文改变 | 重新生成对应 PDF，并验证源哈希、产物及版面 |

开始时：目录 README → 任务索引 → 权威规则 → 必要历史。结束时逐项判断表中哪些受影响；无关文档不顺手改。当前规则的准确性由维护该功能的 Agent 一并负责，不等所有者另行提醒。

## 5. 阅读版 PDF

Markdown 是唯一内容源，PDF 是方便所有者阅读的衍生物。沿用 `tools/build-docs.mjs` 调用 `tools/md2pdf.py`，中文字体、目录、标题层级、表格和分页由转换器负责。输出仍镜像到 `docs/阅读版/`，不进 Git；不恢复 Word 双份维护。`docs/恢复码.docx` 等私人材料不扫描、不转换、不清理。

运行环境需要 Python、fpdf2、PyMuPDF 及可用中文字体；可用 `PYTHON` 指向已有解释器。工具优先使用本机隔离环境，不改业务依赖。缺少环境时明确报错，不把空白或不完整产物覆盖旧阅读版。

### 日常与批量命令

```text
pnpm docs:sync                         # 更新已改 Markdown 的已有阅读版，以及已登记但过时的阅读版
pnpm docs:sync --since=<基线提交或分支> # 批量整理后检查与基线相比修改的正文
pnpm docs:sync docs/ops/文档维护规范.md # 显式为重要新文档生成阅读版
pnpm docs:check-pdf                    # 只验证受影响/已登记阅读版，不生成
pnpm docs:build                        # 按原有入口批量生成仓库 docs 下的 Markdown
```

先完成一批 Markdown，再一次生成，避免逐行重复。默认同步不为普通目录 README 自动建立阅读版；新增长期权威规则、重要阶段规划或所有者主要阅读材料时可显式生成。已有 PDF 即进入同步范围，不因文件篇幅小而忽略。

工具登记源文件、源 SHA-256、转换器 SHA-256、PDF SHA-256、页数和验证时间到阅读版目录的本机清单。检查对照内容哈希，不用“运行过命令”或修改时间冒充同步。没有清单的旧 PDF 只在被本次修改影响或显式选中时重建和登记，不能宣称其他旧 PDF 已验证。

### 生成与验证

1. 使用现有字体与转换器生成临时 PDF；成功后检查能重新打开、页数、中文文本、标题、正文片段与文本边界，再替换同一路径的阅读版。代码围栏未闭合或表格列数不一致时拒绝生成。
2. 检查源与产物哈希一致性；不得仅凭进程退出成功确认更新。
3. 批量生成抽查每份变化文档的代表页，长表、代码、最长标题及末页重点检查；转换器变化时覆盖中文、长表、跨页和目录样例。自动检查不能替代视觉核对。
4. 生成失败保留 Markdown 和旧 PDF，输出失败文件与原因；旧 PDF 不标为最新。修复后只重跑失败或再次变化的文件。
5. 源文件移动时重新生成到镜像新路径；旧 PDF 仅报告为孤立，不自动删除。任何实际清理需符合授权与恢复要求，不产生无意义的“最新版”副本。

## 6. 检查与恢复

完成时执行目录更新、`pnpm check:docs`，修改 STATUS/版本/迁移时运行 `pnpm check:status`；涉及已有阅读版再执行同步与验证。链接检查覆盖文件目标，章节引用由额外锚点检查核对；外部地址可用性和产品事实仍需适当人工判断。

重要重整前留 Git 恢复点，过程中按可审查范围提交。本次历史原文的基线与 SHA-256 记录于 [20261108 历史清单](../archive/documentation/20261108/manifest.json)。归档保留原文含义并重定位相对链接；不携带凭据或本地真实数据。PDF 不入 Git，可从相应提交的 Markdown 重新生成。
