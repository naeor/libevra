> **S0 备注：本地数据库怎么选（本机实测结果）**
>
> 我在这台机器上实际查过：**Docker 未安装，WSL2 也未安装**（`wsl --status` 提示需要先 `wsl --install` 并重启一次），好消息是 BIOS 虚拟化与 Hyper-V 都已开启。
>
> | 路线 | 命令 | 优点 | 缺点 |
> |---|---|---|---|
> | **① 原生 PostgreSQL 17（推荐）** | `winget install --id PostgreSQL.PostgreSQL.17 -e` | 一条命令、**不用装 WSL、不用重启**、装完即用 | 与生产用的 Docker 容器略有环境差异（SQL 层完全一致） |
> | ② Docker Desktop | 先 `wsl --install`（**需重启**），再 `winget install --id Docker.DockerDesktop -e` | 本地与生产环境完全一致 | 多两步、要重启、占内存，可能还需要开 BIOS 虚拟化 |
> | ③ 免费云数据库（Neon / Supabase） | 注册后拿连接串 | 零安装 | 依赖网络；连接串要管好，绝不能进仓库 |
>
> **结论：走 ①。** 生产环境照样用 Docker（装在服务器上），本地用原生 Postgres，**数据库迁移脚本与 SQL 写法完全一致**，不影响简历成色，还省掉 WSL 这个坑。
>
> 你只需要复制粘贴这几条（我会在你确认后逐步给）：
>
> ```powershell
> winget install --id PostgreSQL.PostgreSQL.17 -e     # 本地开发库
> winget install --id GitHub.cli -e                   # 可选，建仓库/发 Release 更方便
> git config --global user.name  "你的名字"
> git config --global user.email "你的邮箱"
> corepack enable pnpm                                # 本机 corepack 0.35.0 已就绪
> ```

> **S0 详细步骤 A：git 与 GitHub 怎么配（本机实测现状）**
>
> 我在这台机器上查过：git 2.55 已装，但 **`~/.gitconfig` 根本不存在**（所以 `user.name` / `user.email` 全空）；**Git Credential Manager 已经装好**（`credential.helper=manager`），所以推送时浏览器授权一次即可，**不需要手抄 Personal Access Token**；SSH 密钥目录是空的——用 GCM 就不必再配 SSH。
>
> | 步骤 | 命令 | 为什么 |
> |---|---|---|
> | 1. 身份 | `git config --global user.name "你的名字"`<br>`git config --global user.email "你的 GitHub 邮箱"` | 提交记录里的作者信息。**推荐用 GitHub 的 noreply 邮箱**（形如 `12345678+用户名@users.noreply.github.com`）：提交里不暴露真实邮箱，GitHub 仍能把提交算到你账号上 |
> | 2. 默认分支 | `git config --global init.defaultBranch main` | 新仓库默认 main，避免 master/main 两套叫法 |
> | 3. 推送免配 | `git config --global push.autoSetupRemote true` | 第一次 `git push` 不用再写 `-u origin main` |
> | 4. **换行符（Windows 最容易踩的坑）** | `git config --global core.autocrlf false` | 关掉自动 CRLF 转换，改由仓库里的 `.gitattributes`（`* text=auto eol=lf`）统一管理。否则 Windows 的 CRLF 混进仓库，Mac/Linux 贡献者会看到"整个文件都被改了" |
> | 5. 身份验证 | 无需配置 | 已装 Git Credential Manager，第一次 push 弹浏览器授权即可 |
> | 6. 建仓库 | `gh auth login`，然后 `gh repo create <名字> --public --source . --push` | 用 GitHub CLI 一条命令建公开仓库并推送 |
> | 7. 仓库初始文件 | `.gitignore`、`.gitattributes`、`.env.example`、`LICENSE`、`README.md` | **`.env` 从第一次提交起就必须被忽略**——这是开源项目最常见的翻车点 |
>
> 提交规范：用 Conventional Commits（`feat:` / `fix:` / `docs:` / `chore:`），历史干净、以后能自动生成 changelog，面试时也是加分细节。
>
> **S0 详细步骤 B：PostgreSQL 本地怎么装**
>
> 1. `winget install --id PostgreSQL.PostgreSQL.17 -e`（17.11，本机已确认可装）
> 2. 安装向导里设置 `postgres` 超级用户密码（**别用你常用的密码**，它只服务本地开发）
> 3. 端口保持 5432；装完确认服务在跑：`Get-Service postgresql*`
> 4. 建开发库与专用角色（用 SQL 建，权限比直接用 superuser 干净）
> 5. 连接串写进项目根目录 `.env`（**不进 Git**）：`DATABASE_URL="postgresql://ledger:密码@localhost:5432/ledger_dev"`
> 6. 生产用 Docker 跑 `postgres:17`，**版本与本地一致**，所以不会出现"本地能跑、线上报错"
>
> 想和线上完全一致也可以装 Docker Desktop，但必须先 `wsl --install` 并重启一次——我建议先跳过这一步。

### S5 · 截图识别记账（**已重新定义**，原估 0.5 天 → **2–3 天**）

> **2026-10-09 重大修正**：项目所有者更正了场景——**不是"小票拍照"，而是"付款截图识别"**
> （微信付款截图、支付宝收款截图、银行转账截图）。这个区别极大，见下。

#### 为什么"截图"比"小票拍照"容易得多

| | 拍照小票 | **付款截图** |
|---|---|---|
| 几何形变 | 有透视畸变、纸张卷曲 | **完全没有，像素完全对齐** |
| 光照 | 阴影、反光、色偏 | **无，屏幕自发光** |
| 对比度 | 依赖拍摄条件 | **极高，通常是黑字白底** |
| 版式 | 各家不同、随时改版 | **字段固定、措辞固定** |
| OCR 难度 | 高 | **低** |

> 项目所有者对 OCR 持怀疑态度（此前的自动化测试项目里 OCR 表现很差）。
> **那个经验很可能来自"拍照 / 复杂界面"，而付款截图恰好是 OCR 最擅长的一类输入。**

#### 实测数据（2026-10-09，本机 CPU，未做任何图像预处理）

用 `RapidOCR`（PaddleOCR 模型的 ONNX 轻量版，`pip install rapidocr-onnxruntime`）对三张仿真付款截图实测：

| 截图类型 | 识别行数 | 平均置信度 | 耗时 | 金额 | 类型 | 渠道 | 日期 | 时间 | 对方 | 单号 |
|---|---|---|---|---|---|---|---|---|---|---|
| 微信支付 | 19 | 0.975 | 1.12s | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 支付宝收款 | 17 | 0.997 | 0.50s | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 银行转账 | 17 | 0.996 | 1.01s | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

**平均 0.88 秒/张（不含模型加载），三张全部字段正确。**

> **过程中的关键教训（这条最有价值）**：
> 第一版提取规则**只有 1/3 能取到金额**——因为它要求 `¥` **紧挨着**数字，
> 而识别器把 `¥` 单独成行，在一张里甚至认成了「夫」（置信度 0.966）。
> **问题不在识别，在提取规则。** 改用"**金额是屏幕上最大的数字**"（用识别返回的文字框**高度**判断）后立刻变成 3/3。
> 随后又发现"对方"取错了方向（支出取到了付款方自己的账号），修正后完全正确。
>
> **结论：OCR 只负责"把像素变成文字"，"把文字变成结构化数据"是我们自己的活——而那一层可以调到对为止。**

#### 产品流程

```
记账页点相机图标
   ↓
选图（最多 5 张）+ 选模式
   ├─ 单笔消费，多张凭证  → 金额相加 → 一个弹窗
   └─ 多笔消费，批量上传  → 每张一个弹窗
   ↓
上传 → 服务端 OCR → 字段提取 → 返回结构化数据
   ↓
【图片在此刻被丢弃，从未写入磁盘】
   ↓

   ↓

```

#### 已定方案

| 项 | 决定 | 理由 |
|---|---|---|
| **图片不落盘** | 内存中处理完即丢弃 | 比"存了再删"更彻底：**没有可泄露的副本，也没有要清理的垃圾** |

| 试运行期**样本保存开关** | 默认关，调试时可开 | 所有者要肉眼核对识别效果 |
| 数量上限 | **5 张** | |
| 单笔多凭证 | 暂**限同一币种**，金额相加 | 不同币种一次上传 → 已记入待办 |
| 入口 | **记账页**的相机图标 | |
| 弹窗 | **一屏以内、可编辑** | 目标是"核对"而不是"重填" |
| 识别不准时 | 字段留空 + 明确提示，**不猜** | **猜错比留空更糟**——留空用户会填，猜错用户可能直接确认 |

**三层划分（本阶段定下的原则，后续新入口都按它归位）**

| 层 | 装什么 | 现在的情况 |
|---|---|---|
| **用户级** | 个人资料、密码、恢复码、账号级邀请码额度、下载管理、软件更新、**默认币种** | 默认币种确实在 `users` 上，但**分类管理被错放在"我的"页** |
| **账本级** | **分类 / 标签 / 支付方式**、导出 / 导入、成员、分享、留言、编辑历史、账本信息 | 分类三项在账户页；导出/导入在设置页；成员/分享在账本齿轮面板 |
| **应用级** | 系统管理（管理员）、版本公告、关于、法律条款 | 基本正确 |

> **原则一句话：分类、标签、支付账户属于账本；账号属于人；平台属于应用。**
> **入口的父级必须与数据的父级一致**——否则用户会以为"换账号才换分类"，
> 而实际是"换账本就换分类"，两类误解的代价完全不一样。

> | 4 | **云端协作**：邀请链接 / **二维码 / 短时配对码**加入共享账本 | ③ 方案 B（只做可行性） |
> | 5 | **游客不参与全站搜索** | ③ 方案 B（**硬约束**） |
> | 6 | **注册后迁移**：防重复、防串账、失败不删本地、可重试 | ② 游客本地 |
> | 7 | **动态公开注册名额**（分批 + 原子扣减 + 异常收紧） | ④ 名额 |
> | 8 | **邀请额度新规**（7 天成熟 / 每月 1 日 / 累计上限 2 / 被邀请者同样成熟） | ⑤ 邀请码 |
> | 9 | **异常注册告警**（汇总、去重、限频、不读账本内容、不自动封禁） | ⑥ 告警 |
> | 10 | **不改 S13 的邀请码管理与生产规则** | 全阶段边界 |

1. **统一登录 / 注册 / 游客入口**
   - 四条路径：**账号登录、公开注册、邀请码注册、游客模式**。
   - **公开注册名额耗尽时，其余三条路径必须仍然可用**——名额只约束"公开注册"这一条，不能把整个入口关掉。
   - **复用现有登录 / 注册页的视觉与组件**，**不造第二套认证系统**；不新增一套账号模型。
   - ⚠️ 具体入口怎么摆、文案怎么写，**S14 设计阶段再定，本轮不设计 UI**。

2. **游客本地记账**
   - **免账号**；**多本地账本**；基础记账 / 分类 / 账户 / 分析 / 导出。
   - 评估现有 **IndexedDB、离线队列（印记）、同步体系**：哪些可复用、哪些**绑定账号**。
   - **数据默认只留本机、不上传**；**必须明确提示**：清缓存、换设备、设备损坏会丢数据。
   - 转正式账号时做**安全迁移**：**防重复记账、防归属错误、迁移失败不删本地**；迁移要可重试。
   - ⚠️ 游客能不能有"账户 / 分类 / 导出"的完整能力，取决于 2 里的可行性结论，**不是先承诺再补**。

3. **受限云端游客协作（方案 B，先可行性分析，不实施）**
   - 用户**明确同意**后获得**受限游客身份**；通过**邀请链接 / 二维码 / 短时配对码**
     **加入或创建共享账本**；**服务端保存与同步，不要求创建者在线**。
   - **游客不参与全站搜索**、权限受限（具体权限待定）。
   - 需设计：**设备丢失处理、滥用限制、配额、共享权限、升级迁移**。
   - **⚠️ 本轮只做可行性分析，不实施、不建表、不改权限判断。**

4. **动态公开注册名额**
   - **每日有限名额**（例如首日 20，视需求与风险逐步增加）；**分批释放 + 随机偏移**。
   - 当天未用可**有限累计**，**不可无限结转**；服务端**原子扣减**，**防并发超额**。
   - **不能仅凭名额耗尽判断需求**——要排除机器人抢注；异常时**自动收紧**。
   - **⚠️ 额度 / 算法 / 上限未拍板：本轮只记录需求，不硬编码。**

5. **新版邀请码制度**
   - **注册未满 7 天无生成额度**；**满 7 天得 1 次**；**满 14 天后每月 1 日再得 1 次**；
     **未用额度最多累计 2 次**；**已生成的邀请码仍 7 天有效**；
     **被邀请用户同样适用成熟规则，不再永久禁邀**。
   - **必须区分「生成额度」与「已生成邀请码」**——前者是"还能发几次"，后者是"已经发出去的码"。
   - 月度发放时区、首次边界、消耗顺序、重复生成保护、邀请链滥用**留待 S14 细化**。
   - **⚠️ 本轮不改生产规则、不影响 S13 的邀请码管理**：S13 管的是管理员发出的注册邀请码，
     这里说的是账号级邀请码（次级码），**不是同一件事**。

6. **异常注册检测与邮件告警**
   - 监测：**异常注册、配额快速消耗、异常兑换、无正常使用行为的批量账号**。
   - **优先用注册时间 / 邀请关系 / 速率 / 汇总指标**，**不读私人账本内容**。
   - 可疑情况**优先人工审核，不自动封禁**。
   - **复用已有 Resend 告警通道**，但必须**去重、汇总、限频**，**防止邮件轰炸**。

**可行性判断（先看结论，证据见设计要点 §2）**

| 判断 | 内容 |
|---|---|
| **可以复用** | 本地键值存储与 `ledger-months` / `ledger-marks` 的键设计；本地统计与筛选；本地导出所需的 CSV 工具（`shared/spreadsheet`）；持久化查询缓存；`storage.persist()`；邀请码"一次性原子占用"的模式 |
| **不能直接复用** | 按 `账号:账本` 划分的离线作用域（游客没有账号）；账本 / 分类 / 支付方式 / 标签的服务端元数据；**同步、写入队列、冲突处理**（都要求登录态）；下载管理；**导出接口**（在服务端，XLSX 生成器也在 api 侧）；分享链接加入（`requireAuth`）；全站搜索；通知配额 |
| **开工前必须先解决** | 游客身份的本地表示；多本地账本的元数据从哪来；本地分类 / 支付方式 / 标签的默认值；**本地导出**（CSV 可先做，XLSX 需评估把生成器移到 `shared` 或只做 CSV）；云端游客的服务端身份；名额与邀请额度的数据模型；异常检测的数据模型与保留期 |
