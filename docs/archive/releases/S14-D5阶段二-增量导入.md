## 1. 产品行为

本轮在 D5 阶段一的分批任务上增加**增量导入**，但不是重新设计一套流程：仍复用 D1 的选择 → 预览 → 核对 → 确认，并复用 D3 的重复组和 A 软删除核对。

| 来源记录情况 | 默认行为 | 用户明确动作 |
|---|---|---|
| 之前已导入且内容未变化 | 跳过，不重复创建 | 无需动作 |
| 新增记录 | 按普通导入处理 | 与现有重复组核对共用 |
| 之前已导入，来源内容变化 | **保留目标**（不静默覆盖） | 可逐条选择“用来源更新目标”；目标版本变化时禁止覆盖 |
| 之前明确跳过 / keep-a | 保持跳过 | 可逐条选择“本次导入” |
| keep-both | 视为已导入，未变化时跳过 | 不重复提示 |
| 目标账目已被删除 | 保持跳过，不自动复活 | 不自动删除/恢复目标 |
| 来源后来删除了该账目 | 目标保留 | 不自动删除目标 |
| 旧版本没有状态行的已导入记录 | 以 `sourceRef`/内容推断；不静默覆盖 | 逐条确认 |

`keep-both`、跳过的决定会写入持久状态；再次导入不会因为重复操作自动改变之前的结果。

## 2. 身份与状态模型

新增 `ledger_import_source_states`（migration `20261019110000_s14d_import_source_states`）：

- `(targetBookId, sourceBookKey, sourceTransactionId)` 唯一；
- 游客来源 `sourceBookKey = "guest"`，正式来源为来源 bookId；
- 保存来源内容指纹、决策（`imported|skipped|kept_target|target_deleted`）、目标交易 id/version、最近任务 id；
- **只保存状态与指纹，不复制整份来源快照**。

身份关联优先使用目标账目已有的 `sourceRef`；`transactions(book_id, source_ref)` 的唯一约束仍是并发重复写入的最终防线。

### 服务端状态推断

新增 `POST /api/v1/ledger-imports/incremental-preview`（只读、owner 权限）：

```json
{ "targetBookId": "...", "sourceBookId": "..." }
```

或游客快照：

```json
{ "targetBookId": "...", "source": { "name": "...", "transactions": [] } }
```

返回每条来源记录的状态：`new / unchanged / modified / target_changed / target_deleted / previously_skipped / previously_skipped_modified / needs_review`，以及 `targetVersion`、`targetChanged`、`previousDecision`、前后指纹。

服务端在真正的导入事务/批次中重新计算并校验这些状态，不接受客户端伪造“这是新增/未变化”。

## 3. 执行与并发

### 单事务路径

D2–D4 的小导入仍走原有单事务；本轮在事务内为所有来源记录写入初始状态（imported/skipped），供后续增量使用。

### 分批任务

增量导入（只要存在非 new 的历史状态）**始终使用服务端持久化分批任务**，即使记录数低于 200：

- 任务 payload 保存每个来源记录的 `create / update / skip` 操作；
- skip 也写状态，记录用户已作出的决定；
- update 在批次事务内校验目标 `version`，失败即暂停，不覆盖；
- 新增和更新都在同一批次原子提交；逐批提交仍**不宣称整个任务单事务原子性**；
- 已完成任务清空 payload 中的游客来源快照（数据最小化）。

### 并发与旧任务

- 同一来源/目标已有 `queued/running/paused/finalizing` 任务时，新任务创建返回旧任务，不并行启动重复导入；
- `transactions(book_id, source_ref)` 唯一约束 + 目标 version 校验是并发最终防线；
- 暂停后继续只处理剩余批次，已提交 B 不重复。

## 5. 本轮验证

### API 自动化

- `ledgerImportIncremental.test.ts`：
  - 未变化/新增/修改识别；
  - 明确选择 update 才更新目标；
  - 来源移除不删除目标；
  - 此前跳过保持跳过，明确选择后导入；
  - keep-both 视为已导入，不再重复提示；
  - 同一来源/目标的重复创建返回旧任务；
  - 完成任务 payload 来源快照被清空。
- D5 任务测试新增：部分批次后目标变化暂停，恢复后不重复已提交批次。

### 真实浏览器

隔离栈 390 宽度：

1. 首次导入 2 笔；
2. 修改 1 笔、新增 1 笔；
3. 预览/核对显示「未变化 1 / 新增 1 / 修改 1」；
4. 选择「用来源更新目标」；
5. 完成后目标 3 笔，金额 `[1500, 2000, 3000]`，游客来源仍为 3 笔。

### 真实 SIGKILL / restart

隔离库 + 独立 API 进程：

- 3000 笔正式来源任务，每批 200；
- 在 **`nextBatch=2 / imported=400`**（已有两批提交）时真实 `SIGKILL`；
- 新 API 进程恢复扫描；
- 最终 `completed nextBatch=15 imported=3000`；
- 目标 3000、回执 3000、重复 `sourceRef=0`。

这一轮同时覆盖了“已提交若干批次后崩溃”和“重启后继续”的场景。

## 6. 游客来源快照：数据最小化、访问与清理方案

### 现状（已实现）

1. **只在本机/本地服务端处理**：游客快照仅在上传请求、当前任务 payload 和导入结果需要时存在；事务/任务完成后不写入业务表。
2. **完成即清空**：任务完成后在同一最终事务中把 `payload.source` 置空，保留计数、批次回执与结果；测试断言完成任务的 payload 无 source。
3. **访问控制**：任务查询/恢复路由要求当前登录 owner；没有跨用户列表；不返回 payload；错误消息不含来源备注。
4. **持久状态最小化**：`ledger_import_source_states` 只存来源 id、内容指纹、目标 id/version、决策，不复制备注/分类/标签内容。
5. **不写日志**：任务错误只记录 code 和截断后的消息，不记录来源快照。

### 仍保留快照的情况

- 任务运行中/暂停/失败等待用户继续时，payload 必须保留来源快照，否则无法恢复；
- 这是有意的短期保留，不是永久存档。

### 阶段三建议

1. 增加任务取消/放弃接口：取消后立即清空 payload；
2. 对超过 TTL（例如 7 天）的暂停/失败任务做后台清理，只保留最小错误信息；
3. 若未来需要更强的静态保护，可在服务端对 payload 加密，密钥与数据库分离；这不替代访问控制；
4. 任务创建/恢复接口继续只允许 owner，且只返回状态/结果，不返回 payload；
5. 来源清理本身必须走 S13 生命周期（弃置/恢复/墓碑/人工恢复），不得直接 SQL 删除来源账本；清理前必须验证服务端最终回执和完整对账；
6. 游客本机快照清理必须由用户独立确认，并在服务端成功回执可验证后才允许；不能把“导入完成”与“清理”绑定成一个默认动作。

## 7. 剩余风险

1. 正式来源清理未实现；当前来源 B 永远保留。
2. 游客任务在暂停/失败期间仍保留快照；TTL/取消清理待阶段三。
3. 旧 D2/D3/D4 导入没有逐条状态行；本轮只能依据 `sourceRef`、目标内容和回执推断，首次增量预览中可能出现“旧导入记录需确认”。
4. 历史备份恢复仍可能复活 A 中已软删除的账目；这是 S13-I 既有边界，未在本轮改变。
5. 大量 modify/update 的最终一致性已按批次校验，但尚未做真实极端并发（数百个任务同时修改同一目标）的压测。
6. 页面关闭后任务继续由服务端执行；浏览器真实断网自动重试仍需在最终 D5 验收中补端到端测试。
