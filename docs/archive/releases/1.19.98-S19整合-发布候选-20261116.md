## 兼容、权限与回滚审查（1.19.56 → 1.19.98）

由独立子代理只读审查 1.19.56 与候选之间的全部差异（不读 `.env`，不改文件），结论：**没有阻断发布的问题**。逐项如下。

**旧客户端兼容（部署后仍缓存着 1.19.56 网页的用户）**——可接受。

- 请求 schema 只放宽没收紧：分类决定 400 → 500、增量决定 5000 → 2 万；来源改为“快照 / 暂存 / 正式账本 id 三选一”，旧客户端总是只给快照或账本 id 之一，照常通过。
- 没有删除或改名的接口，只多 4 条。
- `account/close` 多返回 `closedAccountId`，旧客户端不做严格解析。
- 增量预览的条数上限放到 2 万；旧客户端只有在来源是超过 5000 笔的正式账本时才会碰到，那种情况旧服务器本来也失败，不是回归。
- 账单导入解析器挪进 shared 后，服务器仍用未改的严格 schema 校验响应。

**敏感权限（AGENTS §5）**

- **服务器端：权限代码零改动**。`auth/`、`admin/`、`ledger/access.ts`、`requireBook*`、成员 / 邀请 / 分享都不在差异里。新增的检查都是新增：分段上传沿用 `requireAuth`，并按用户核对归属；导入目标的权限核对未动。
- **网页端改动有两类，都有记录**：
  - 同意门禁的显示判断（1.19.81），有所有者批准记录。
  - 游客模式补齐（1.19.94–1.19.96），所有者 2026-11-15 要求：22 条路由从 `RequireAuth` 改为 `RequireSession`，批量操作、重复检查、账本新建与切换等对游客放开。
- 守卫组件本身的定义没动；服务器照旧把关，游客拿不到服务器数据。
- `auth/AuthProvider.tsx` 的改动是退出 / 登录失效时清本机数据（BUG-007，所有者要求立即修；1.19.84 改为凭注销回执清理），不是访问控制。

**新增的公开接口**——可接受，记录在案。

- `GET /api/v1/fx/public-rates` 不读用户数据，输入有界，按 IP 每分钟 60 次（IP 来自 Caddy，生产 Caddy 版本待核实）。
- 两个小风险，作为后续改进，不阻断：
  - 1999-01-01～03 这几天上游没有报价，每次查询都会再请求一次上游；
  - 响应里的 `cached` / `checkedAt` 会透露某天有没有人查过。

**审查发现、本候选已修**

- **分段上传没有累计上限**：任意登录用户可往一份暂存里塞远超声明的数据，写满磁盘或在“完成”时撑爆内存。现在收段时拒绝“已收笔数 + 本段笔数 > 声明笔数”（错误码 `source_upload_too_many`），测试覆盖。
- `App.tsx` 一处过时注释（附件页“仍只给正式账号”）已更正。

**回滚预案（部署后若要退回 1.19.56）**

1. **只回滚应用、不回滚数据库**：用 1.19.56 记录里的 `up -d --no-deps api web` 方式，**不要用旧镜像运行 `migrate`**。数据库多出一条旧版不认识的已执行迁移，旧镜像的 `prisma migrate deploy` 是否通过未验证。
2. **保留服务器 `.env` 里的 `SESSION_SECRET`**，直到回滚窗口关闭。新版 compose 不再要求它，但 1.19.56 的 compose 要求，删了回滚会起不来。
3. **游客数据**：1.19.95 起游客数据改为每本账一份，旧位置迁完即删。1.19.56 的网页只读旧位置，会给游客显示一本空账。数据仍在浏览器里，再升级回来会恢复（回滚期间记的账另存为「（恢复的副本）」）；只有用户在旧版里点“清除游客数据”才会真丢。按优先顺序：
   - 能只回滚 API 就保留新网页；
   - 必须回滚网页时，在公告里提醒游客不要清除数据。
4. 两张暂存表旧版不认识也不清理；回滚后手工删一次到期行。
5. 服务器没有写入任何旧版不认识的枚举值；导入任务记录旧版读取时不重新校验，不受影响。
