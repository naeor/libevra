# S14 1.14.20 Whisper 语音识别性能研究

> 状态：**研究记录，不修改生产模型/配置**。生产仍使用 `pywhispercpp` + multilingual small；本报告不授权替换模型、增加线程或升级服务器。
> 所有测试音频均为本地 TTS 合成、噪声或静音样本，不含真实用户财务/录音数据。

## 1. 当前生产环境与已知现象

- 服务器：2 vCPU、约 7.5 GiB RAM、Intel Xeon E5-26xx v4、无 GPU。
- 当前代码：`apps/voice/service.py`
  - 模型：`LIBELLUM_WHISPER_MODEL=small`
  - 模型文件：`/data/.local/share/pywhispercpp/models/ggml-small.bin`，487,601,967 字节
  - 代码默认 `LIBELLUM_WHISPER_THREADS=4`
  - 进程：`/repo/apps/voice/service.py`，常驻；先前检查 RSS 约 858 MiB、3 个 OS 线程；模型只加载一次。
- 生产请求耗时：
  - 一条实际请求约 27 秒；
  - 用户观察到部分请求约十几秒；
  - 不含真实财务内容的合成静音请求约 50–57 秒。
- 主机无 OOM；内存/磁盘充足；问题不是资源耗尽。

> ⚠️ 生产实际 `n_threads` 未能再次从 `.env` 读取：本轮重启后 SSH 私钥需要口令解锁。代码默认 4；进程只有 3 个 OS 线程，可能意味着实际配置为 2+主线程。发布前必须通过 `printenv LIBELLUM_WHISPER_THREADS` 与容器内进程确认，不能把 Python 进程总线程数误认为模型 `n_threads`。

## 2. 测试环境与方法

### 2.1 本地测试硬件

- CPU：AMD Ryzen 9 8940HX，16 核 / 32 线程
- RAM：约 16 GiB
- OS：Windows
- Python 3.12；`pywhispercpp`、`av`、`numpy`、`psutil`
- 模型：本地下载的 whisper.cpp GGML 模型
- 所有推理都在本地执行，不使用生产服务器；结果不能直接等同于 2 vCPU 生产机。

### 2.2 合成音频

用 Windows Huihui 中文 TTS 生成 16 kHz 单声道 WAV：

| 样本 | 时长 | 内容 |
|---|---:|---|
| `short.wav` | 4.70s | “昨天午餐花了三十五元，用微信支付。” |
| `short-noise.wav` | 4.70s | 上述语音 + 低幅白噪声 |
| `natural10.wav` | 9.91s | “十月八号下午三点，我在超市买了牛奶和水果，一共支出四十二元五角，用支付宝付款。” |
| `instruction.wav` | 7.16s | “记一笔，九月二十一号，餐饮支出人民币八十八元，微信支付。” |
| `silence5.wav` | 5.00s | 5 秒数字静音 |

### 2.3 参数

- `language="zh"`
- 与生产相同的记账 `initial_prompt`
- `no_context=True`
- 基准线程数：`n_threads=2`
- 额外线程扩展测试：1 / 2 / 4 / 8（仅 small，本地 32 线程机器）
- 每个模型只加载一次；记录模型加载时间、推理时间、进程 RSS、文字输出；未包含 HTTP 上传和浏览器录音时间。

## 3. 本地实测结果

### 3.1 模型对比（`n_threads=2`）

| 模型 | 文件大小 | 模型加载 | 常驻 RSS | short (4.7s) | natural10 (9.9s) | instruction (7.2s) | 关键字段表现 |
|---|---:|---:|---:|---:|---:|---:|---|
| **small**（当前生产） | 487.6 MB | 0.64s | 705 MiB | 4.43s | 5.20s | 4.91s | 金额/日期/渠道正确；“牛奶和水果”误为“喝”，指令开头“记一笔”误为“记亦比” |
| **small-q5_1** | 190.1 MB | 0.21s | 418 MiB | 6.46s | 7.75s | 7.59s | 关键字段正确；本地推理反而更慢 |
| **base** | 147.9 MB | 0.23s | 311 MiB | 1.74s | 1.89s | 1.73s | 金额/日期/渠道正确；natural 更准确；instruction 部分汉字误写但不影响金额/渠道 |

补充：

- small + 5s 静音：5.11s，输出明显幻觉文本；
- base + 5s 静音：9.28s，同样幻觉；
- small-q5_1 + 静音：8.08s，幻觉；
- 结论：**没有 VAD 时，静音也会被 Whisper 当作内容处理，既浪费时间又可能产生虚假文字。**

### 3.2 small 线程扩展（本地 32 线程机器）

| `n_threads` | short | natural10 |
|---:|---:|---:|
| 1 | 8.58s | 9.66s |
| 2 | 5.74s | 6.42s |
| 4 | 5.93s | 5.97s |
| 8 | 6.46s | 7.72s |

本地 2 线程已接近最佳；4/8 没有明显改善。该结果不能直接外推到 2 vCPU 生产机。

### 3.3 关键字段准确率（本地合成样本）

- **小额/日期/渠道**：small、base、q5 都能从三条语音中识别金额（35 / 42.5 / 88）、日期（昨天 / 10月8号 / 9月21号）和渠道（微信 / 支付宝 / 微信）。
- 文字层面仍有小错误：
  - small：`牛奶喝水果`（应为“和”）、`记亦比`（应为“记一笔”）；
  - q5：`记亿笔`；
  - base：`記憶比...人民幣`。
- 对记账最关键的金额、日期、渠道、收支方向没有观察到模型级失败；真实用户口音/网络音频仍需生产样本验证。

## 4. 为什么生产 small 这么慢

本地 2 线程 small 约 4–5 秒，生产同类请求约 27–57 秒，差异接近一个数量级。已知事实：

- 生产进程只有 2 vCPU，CPU 为较老的 Xeon E5 v4；
- 本地为 16 核 Ryzen 9，单核性能和调度条件明显更强；
- 模型只加载一次，生产 RSS 858 MiB，不是重复加载；
- 没有 OOM、内存不足或模型缺失；
- 生产 `n_threads` 尚未通过环境变量确认；代码默认是 4，而 2 vCPU 上 4 线程可能造成线程竞争，不能假定更多线程会更快；
- Whisper 通常按约 30 秒窗口处理，短语音也会承担固定解码成本；
- 没有 VAD，静音/无语音也进入完整识别，耗时和幻觉都会增加。

**当前结论：主因是 CPU-only Whisper small 在低核心/较老 CPU 上的推理成本，而不是模型文件错误或明显的代码 bug。** 但生产 `n_threads`、完整 HTTP/音频转换耗时仍需一次受控 profiling 才能最终确认。

## 5. 全链路耗时构成（代码路径）

当前路径：

1. 浏览器录音（WebM/Opus 或 MP4/AAC）；
2. Caddy/API 接收上传；
3. Fastify 将音频传给 Node voice client；
4. Python 子进程用 PyAV 解码、重采样为 16 kHz mono float32；
5. `whisper.cpp` 推理；
6. 返回文字；
7. Node/前端提取金额、日期、渠道等字段。

本轮测量了**模型加载 + 实际推理**；尚未单独测量生产上传、PyAV 解码/重采样、Node IPC 和字段提取。代码显示这些步骤通常远小于模型推理，但不能在没有生产 instrumentation 时断言其占比。

## 6. 优化方向与判断

### 6.1 短期（研究/验证，不直接改生产）

- 先确认生产实际 `LIBELLUM_WHISPER_THREADS`，用受控合成音频做一次分段计时；
- 加入/研究 VAD：静音或纯噪声直接返回“没有听到语音”，避免完整解码和幻觉；
- 记录模型加载、解码、推理、字段提取各自耗时；
- 在隔离的 2 vCPU/相近老 CPU 环境比较 `small` 与 `base`，同时评估中文准确率。

### 6.2 模型选择

- **base**：本地比 small 快约 2.5 倍、内存约一半，关键金额/渠道/日期仍正确；但所有者此前选择 small 是因为 base 在中文上有误听（午饭/五份）。是否值得切换必须用同一批真实口音测试集验证，不能只看本地速度。
- **small-q5_1**：本地反而更慢，仅内存更小；不建议用它改善延迟。
- **medium**：文件约 1.5 GB，计算量显著更高；本轮未下载/未测试。以当前 2 vCPU 生产机判断，**不建议作为默认模型**，需要独立隔离环境验证准确率、内存和延迟后才能讨论。
- 不盲目增加线程；2 vCPU 上线程超过核心数可能变差，应以实际 profiling 为准。

### 6.3 更大范围

- 增加 CPU 核心/更高单核性能可能改善，但本轮不授权升级服务器，也不应先换硬件而不解决 VAD/解码浪费/线程配置。
- 未来原生 App 或家庭服务器可在设备本地承担语音识别，但移动端后台/发热/电量/模型大小限制需要单独研究；不是当前承诺。

## 7. 结论

1. **small 慢的主因是 CPU-only 推理 + 2 vCPU 老 Xeon + 30 秒窗口固定成本；不是模型缺失、OOM 或重复加载。** 生产实际推理线程数仍需确认。
2. **没有发现明确代码 bug**，但有明显优化点：VAD/静音短路、线程配置确认、解码/HTTP 分段计时。
3. **base 值得在隔离环境做准确率+延迟 A/B**，但不能在没有真实中文样本验证前直接替换。
4. **small 量化版在本轮本地测试中更慢**，不建议为延迟切换。
5. **medium 当前 2 vCPU 服务器不具备已被证明的实用价值**，本轮未测，不建议直接部署。
6. **不建议现在增加 CPU 核心**；先把线程、VAD 和完整耗时链路测清楚。
7. 原生客户端/家庭服务器本地语音是未来研究方向；需另行评估设备资源、后台限制和隐私边界。

## 8. 测试数据与限制

- 合成 TTS 语音不是真实用户口音/环境，不能作为最终准确率结论；
- 本地 Ryzen 16 核与生产 2 vCPU 不同，绝对耗时不通用；
- medium 未完成下载/未运行；
- 未修改生产模型、线程、API 或前端；
- 未输出任何真实用户财务/录音数据。
