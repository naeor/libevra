# S13-G 状态流转与绕过验证报告

> 2026-10-18。本地隔离测试栈：API `http://127.0.0.1:3100`、Web `http://127.0.0.1:5175`、版本 `1.13.11`。
> 使用独立测试数据库和独立无头浏览器会话；**未接触生产、未 push、未部署**。
> 本轮只验证，不修改业务代码。

## 1. 三个概念

| 术语 | 含义 | 本次验证方式 |
|---|---|---|
| **刷新** | 浏览器重新加载当前页面（F5 / address bar 回车 / 重新打开同一 URL），不是点击应用内导航 | 直接访问 `/settings` 后再次加载同一 URL |
| **深链** | 不经过应用内正常入口，直接把受保护页面 URL 输入地址栏，例如 `/ledger`、`/export` | 逐页直接打开 6 个业务路由 |
| **API 直连** | 不经过 React 页面，用已登录的 session cookie 直接请求服务端接口，例如 `GET /api/v1/books` | 直接请求 16 个 GET + 11 个 POST 受保护接口，以及允许接口 |

## 2. 测试对象

- **协议拒绝账号** `verify_protocol`：注册后删除协议接受记录，模拟“已有账号、尚未同意当前协议”；账号会话仍有效。
- **重大公告账号** `verify_major`：已接受协议，账号创建时间置于本地测试重大公告发布之前；创建三个独立登录会话（设备 A、设备 B、第三会话）。
- 使用本地测试协议/重大公告，均为 `testOnly`；生产策略不受影响。

## 3. 同一账号两台设备的重大公告流转

结果：**通过，服务端状态不重复。**

1. 设备 A 和设备 B 各自使用独立浏览器 profile + 独立登录会话；两台都先显示「重要更新测试公告」。
2. 在设备 A 点击「知道了」。
3. 立即查询两台设备会话：
   - A：`majorAnnouncement = null`
   - B：`majorAnnouncement = null`
4. 设备 B 刷新后：不再出现公告弹窗。
5. 第三台新登录会话：`majorAnnouncement = null`。
6. 数据库 `major_announcement_acknowledgements`：该账号恰好 **1 条**记录，动作 `acknowledged`。
7. 另一个在公告发布后创建的新账号：接受协议后 `majorAnnouncement = null`，不补看历史公告。

**已知表现（不是绕过）**：设备 B 在 A 确认之前已经打开并渲染了弹窗时，A 的确认不会实时把 B 已打开的弹窗关闭；B 刷新/重新进入后不再弹。服务端状态是统一的，客户端没有实时推送/轮询，这是本轮验证到的交互边界。

## 4. 协议拒绝后的刷新 / 深链 / API 绕过

### 4.1 刷新

- 直接打开 `/settings`，门禁出现，标题「本地测试协议」。
- 再次加载同一 URL：门禁仍在，业务页面没有解锁。
- 接受协议后再次加载 `/settings`：门禁消失，设置页正常渲染。

截图：[刷新后仍被门禁](../screenshots/2026-10-18-S13-G-状态流转验证/protocol-refresh-settings.png)

### 4.2 深链

以下路由全部直接访问成功进入页面，但都被协议门禁覆盖，服务端对应 API 均为 `403 agreement_required`：

`/`、`/ledger`、`/settings`、`/export`、`/downloads`、`/about`

截图：

- [深链 `/settings`](../screenshots/2026-10-18-S13-G-状态流转验证/protocol-deep-link-settings.png)
- [深链 `/export`](../screenshots/2026-10-18-S13-G-状态流转验证/protocol-deep-link-export.png)

**唯一有意的公开例外**：`/legal/local-test-terms` 不需要登录即可阅读完整文件，这是协议确认的必要条件，不是绕过业务限制。

### 4.3 API 直连

使用未接受协议账号的**有效 session cookie**，直接请求：

- **受保护 GET（16 个）**：`/api/v1/books`、`/ledger`、`/ledger/history`、`/ledger/operations`、`/transactions`、`/summary`、`/stats`、`/export`、`/export-log`、`/notifications`、`/share/links`、`/directory/lookup`、`/books/members`、`/books/messages`、`/conflicts`、`/admin/overview`
- **受保护 POST（11 个）**：`/transactions`、`/books`、`/categories`、`/payment-methods`、`/tags`、`/export`、`/notifications/read-all`、`/share/links`、`/books/invite`、`/referral-codes`、`/admin/invites`

结果：**27 个全部返回 `403 agreement_required`**；没有任何一个业务接口返回数据或执行写入。

允许接口（按设计保留）：

| 接口 | 结果 |
|---|---|
| `GET /api/v1/account/consent` | 200（受限状态可读） |
| `GET /api/v1/account/export` | 200（受限状态可导出） |
| `GET /api/v1/legal/documents` | 200（公开） |
| `GET /api/v1/legal/documents/local-test-terms` | 200（公开完整文件） |
| `GET /api/v1/auth/me` | 200 |
| `GET /api/v1/health` | 200 |
| 无 cookie 请求 `/api/v1/books` | 401 |

接受协议后：
- `GET /api/v1/books` 从 403 恢复为 **200**；
- 接受证据表出现 1 条记录，包含 `documentId`、`documentVersion`、SHA-256 `contentHash`、`action=accept`、`acceptedAt`。

截图：[接受后 `/settings` 正常](../screenshots/2026-10-18-S13-G-状态流转验证/protocol-after-accept-settings.png)

## 5. 结论

- 未发现通过刷新、深链或直接 API 绕过协议限制的路径。
- 同一账号在两台设备上的重大公告确认由服务端账号级记录统一；确认后新会话/刷新不重复弹窗。
- 受限状态只开放了必要的状态、导出、协议阅读和退出通道，符合设计。
- 本轮未覆盖：全部 API 路由的穷举（只覆盖上述 27 个代表性接口）、真实 iPhone Safari 真机、实时跨设备弹窗自动关闭（当前依靠刷新/重新进入拿最新状态）。
- 本地测试数据仅存在于隔离测试库；生产仍为 `1.13.09`。
