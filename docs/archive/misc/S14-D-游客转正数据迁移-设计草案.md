# S14-D · 游客账本转正式账号 · 设计草案

> **状态：设计草案，尚未实现。** 本文只定义 S14-D 的数据映射、接口、幂等与失败恢复方案；没有迁移代码、没有新增迁移接口。
> 所有者确认方向后再拆实施任务。实现前必须重新读 `版本记录（1.14）.md` §1 与 `交接.md`，确认 S14-A/B/C 的冻结范围没有被改动。
>
> 制定时间：2026-10-18。适用版本：S14-C（`1.14.05`，本地分支 `s14-a`，未部署）。

## 1. 目标与边界

**目标**：让同一台设备上已经存在的游客本地账本，可以在用户明确确认后，安全、可预览、可中断恢复地复制到一个正式账号的账本里；**复制不是移动，游客本地数据在用户明确清理前始终保留**。

**必须满足（所有者已定）**：

1. 必须由用户主动发起并确认；**不自动上传、不自动合并**。
2. 迁移前可预览：将迁移多少条、哪些分类/支付方式/标签会新建、跳过什么、迁到哪个账号与账本。
3. **幂等、可重试**：同一批数据重复执行不产生重复交易。
4. **失败不丢本地**：失败时游客数据原样保留，可继续重试或放弃。
5. **绝不覆盖正式账号已有数据**；目标账本的选择必须明确（不能默认“当前账本”）。
6. 游客数据只有通过正式账号会话、用户确认后才离开本机；游客 id 不是 userId。
7. 迁移完成后也不自动删除游客数据；清理是独立动作。

**明确不做（S14-D 首版）**：

- 不做服务器端“游客账号”、不做游客数据上云/跨设备同步。
- 不做自动迁移、静默合并、覆盖/改写正式账本已有交易。
- 不迁移本地已删除（墓碑）的游客交易；不迁移游客身份、欢迎状态、本地 UI 状态。
- 不迁移附件/图片（游客记账当前没有附件）。
- 不支持迁移到他人管理、或非本人所有的账本；共享账本默认拒绝（见 §7）。
- 迁移完成后游客继续记账的“双向同步”不在首版：只做一次性增量迁移，见 §10 开放问题。

## 2. 现状（S14-C 的事实，迁移必须基于它）

### 2.1 游客数据

- 身份：`localStorage["libellum-guest-identity"]`，schema v1；`id` 为 UUID，仅本机使用。
- 数据：独立 IndexedDB `libellum-guest`，store `kv`，键 `guest:<guestId>:data`；schema v1。
- 数据块字段：
  - `book`：`GuestLedger { id: "guest-book-…", name, currency, createdAt, updatedAt }`；
  - `categories: Category[]`、`paymentMethods: PaymentMethod[]`、`tags: Tag[]`；
  - `transactions: Transaction[]`（客户端形状，含 `id`（UUID）、`seq`（本地序号）、`amountCents`、`currency`、`kind`、`categoryId/categoryName`、`paymentMethodId/Name`、`tags`、`occurredAt`、`occurredLocalDate`、`occurredTz`、`note`、`version`）；
  - `deleted: Transaction[]`（软删除墓碑）、`nextSeq`。
- 游客写入只落本地；不写正式库 `libellum`、不写正式查询缓存/同步队列（S14-C 已验证）。
- 游客交易 `id` 由 `crypto.randomUUID()` 生成，是合法 UUID；`seq` 只是本地显示序号，**不是服务器编号**。

### 2.2 正式账号写入接口（已存在，S14-D 可直接复用）

- `POST /api/v1/books`：`{ name?: string }`，服务器创建账本并返回 `bookId`；不能指定账本 id。
- `POST /api/v1/categories`：`{ name, kind, sortOrder? }`；同账本 `(bookId, kind, name)` 唯一。
- `POST /api/v1/payment-methods`：`{ name, sortOrder? }`；同账本 `(bookId, name)` 唯一。
- `POST /api/v1/tags`：`{ name, color }`；同账本 `(bookId, name)` 唯一。
- `POST /api/v1/transactions`：要求客户端提供 `id`（UUID）和 `idempotencyKey`（UUID）；其他字段
  `kind, amountCents, currency, categoryId, paymentMethodId?, occurredAt, occurredLocalDate, occurredTz, note?, tagIds[]`。
  - 服务器先按 `idempotencyKey` 查找：已存在且同账本 → 返回 200 + 已有行（**这就是重试不重复的机制**）；不同账本 → `idempotency_conflict`。
  - 服务器分配 `seq`，客户端不能传；`idempotencyKey` 全表唯一。
- 分类/支付方式/标签**没有**客户端 idempotency key，靠名称唯一约束 + “先查后建”实现幂等。
- 所有写接口都要求正式会话与账本权限；游客没有会话，不能调用。

### 2.3 约束

- 正式账号已有数据不能改；迁移是**只新增**。
- 游客 id 不是账号身份；迁移日志里的 `guestId` 只是本机来源标记，不能作为服务端权限依据。
- 游客本地一个数据块只有一本账；目标可以选择现有账本或新建账本。

## 3. 数据映射

| 游客来源 | 正式目标 | 规则 |
|---|---|---|
| `GuestIdentity` | **不迁移** | 只在本机迁移日志里保存来源 mark（如 `guestId`）；不上传、不创建账号。 |
| `book`（`guest-book-…`） | 目标 `Book` | 首选**新建账本**（名称默认取游客账本名，服务器上限 40 字）；或用户明确选择一个**本人管理且为空**的已有账本。游客账本 id 不能作为服务器 bookId。 |
| `book.currency` | 不单独映射 | 正式账本本身不存单一币种；交易各自带 `currency`；新建账本时用户默认币种由账号设置决定，不覆盖。 |
| `categories[]`（系统 暂无分类） | 目标账本系统分类 | 通过 `isSystem` 识别；映射到目标账本的 `暂无分类`，不新建。 |
| `categories[]`（自定义） | `Category` | 按 `(kind, 规范化名称)` 匹配已有；不存在则 `POST /categories`；归档的自定义分类可先建后 PATCH 归档（若首版不保留归档，预览要明示“归档分类将迁为普通分类”）。描述/图标不迁移（游客无描述/图标）。 |
| `paymentMethods[]` | `PaymentMethod` | 按名称匹配；不存在则新建；归档状态同分类策略。 |
| `tags[]` | `Tag` | 按名称匹配；不存在则新建（带游客颜色）；已存在同名标签**不覆盖目标颜色**；颜色不同在预览中列出但不阻塞。 |
| `transactions[]`（live） | `Transaction` | 新 id（建议直接复用游客交易 UUID 作为 `id`）；`idempotencyKey = 游客交易 id`；字段逐项映射，见下表。 |
| `transactions[]`（`deleted`） | **跳过** | 墓碑不迁移；预览显示“本地已删除 N 条，不迁移”。 |
| `nextSeq` | **不迁移** | 服务器按目标账本分配 `seq`；游客序号不进入正式账本。 |
| `version` | 不迁移 | 服务器新行 `version = 1`。 |

**单笔交易字段映射**：

| 正式请求字段 | 来源 | 说明 |
|---|---|---|
| `id` | 游客交易 `id` | 合法 UUID；同一笔交易在所有尝试中保持同 id。 |
| `idempotencyKey` | 游客交易 `id` | 与 `id` 相同即可；重试命中服务器已有行，绝不重复插入。 |
| `kind`, `amountCents`, `currency` | 原样 | 金额已是 minor units；精度按币种校验，游客端已保证合法。 |
| `categoryId` | 映射后的目标分类 | 若映射缺失（目标分类被删）→ 该笔标记 fatal，不可静默丢进“暂无分类”；用户可选择跳过或修复。 |
| `paymentMethodId` | 映射后的目标支付方式或 null | 游客无支付方式时传 null。 |
| `tagIds` | 映射后的目标标签 | 顺序保持；缺失标签必须先建。 |
| `occurredAt` | 原样 ISO 字符串 | 保留原始时区偏移。 |
| `occurredLocalDate` | 原样 | 必须与 occurredAt 一致；服务器会校验。 |
| `occurredTz` | 原样 | 例如 `Asia/Shanghai`。 |
| `note` | 原样（可空） | 不截断；服务器上限校验失败则该笔 fatal。 |
| `seq` / `version` | **不发送** | 服务器分配。 |

## 4. 目标选择与预览

### 4.1 入口

- 游客「我的」页保留入口：「迁移到正式账号」→ 如果未登录，先走现有登录/注册（不新建设计）。
- 登录后如果同时存在游客数据，显示“本机还有一份游客账本”的入口；**不自动弹窗、不强制迁移**。
- 已存在完成的迁移日志时，入口改为“查看迁移记录/迁移新增账目”，避免重复全量迁移。

### 4.2 预览（只读，不上传）

本地计算并展示：

- 交易数、时间范围、按币种/收支的合计（让用户核对“是不是这笔账”）。
- 将新建/匹配的分类、支付方式、标签数量；归档分类/支付方式的处理提示；同名标签颜色差异。
- 本地已删除、将跳过的条数。
- 目标账号（用户名/账号编号）与目标账本（新建或已有）；已有账本必须显示是否为空、是否有其他成员。
- 明确一句：**迁移只是复制；本机游客数据会保留到你另行清理。**

服务端只读校验：

- 目标账本是当前用户可管理的账本；共享账本默认拒绝（见 §7）。
- 已有账本非空：默认拒绝；如所有者未来要求允许，必须增加单独确认，明确“不会覆盖，只追加”，且先做重复检测。
- 账号会话有效；账号没有处于受限/注销流程。

### 4.3 目标账本创建

- 默认推荐新建；名称取游客账本名，加“（来自本机）”前后缀前检查 40 字上限。
- 创建成功后立即把 `targetBookId` 写入迁移日志；**在写入日志前崩溃**，重试时先按名称 + 账号查最近的空账本并让用户确认，绝不自动再建第二个同名账本。
- 用户明确选择已有空账本时，不创建；日志记录同一 `targetBookId`。

## 5. 迁移接口设计

### 5.1 推荐首版：复用现有正式接口，不新增服务器写接口

理由：现有 `POST /transactions` 已经具备客户端 id + 幂等键，分类/支付方式/标签有名称唯一约束；S14-D 首版用客户端编排 + 本地日志即可，风险最小、无需数据库迁移、无需新权限面。

建议客户端调用顺序：

1. （可选）`GET /books`、`GET /books/:bookId/categories|payment-methods|tags`：预览/匹配。
2. `POST /books`（仅新建时）。
3. 对缺失分类/支付方式/标签逐个创建；每个成功后写映射日志。
4. 按批次（建议 20 笔）逐笔 `POST /transactions`；每笔成功写完成标记；全部交易完成前不清理任何本地数据。
5. 最终对账（GET 目标账本交易，按 id 集合/数量/币种求和核对）。

**迁移“接口”在首版就是这些既有接口的受控调用**；不引入“游客迁移专用”服务器路由。

### 5.2 可选第二版：服务器批量迁移接口（仅当首版出现性能/可靠性问题）

如果实测逐笔调用导致慢或中断恢复困难，再考虑专用接口（**本次不实现**）：

```http
POST /api/v1/guest-migrations/preflight
{
  "targetBookId": "uuid",
  "expected": { "transactions": 128, "categories": 6, "paymentMethods": 3, "tags": 2 }
}
→ 200 { "ok": true, "bookEmpty": true, "warnings": [] }
```

```http
POST /api/v1/guest-migrations/batches
{
  "migrationId": "uuid",        // 客户端生成，幂等主键
  "batchIndex": 0,
  "targetBookId": "uuid",
  "taxonomy": { "categories": [...], "paymentMethods": [...], "tags": [...] },
  "transactions": [ ... ]
}
→ 200 {
  "batchIndex": 0,
  "results": [{ "guestTransactionId": "uuid", "status": "created|already_exists|failed", "transactionId": "uuid", "error": null }],
  "done": false
}
```

- 服务器端 `migrationId + batchIndex` 唯一，重复请求返回同一结果（operation receipt 机制可复用现有 `CriticalOperation.idempotencyKeyHash` 或新增迁移表；**若新增表，必须重新评估是否值得**）。
- 这种接口的代价是新的服务端一致性面；首版不推荐。

### 5.3 错误语义

沿用现有错误码；客户端至少要区分：

- `401/403`：会话失效、目标账本无权限 → 暂停并保留日志，要求重新登录/换账本。
- `idempotency_conflict`：幂等键已属于其他账本 → **fatal**，不得继续，保留本地数据。
- `409` 分类/支付方式/标签同名：视为“已存在”，查询后映射，不重复创建。
- `400/422` 单笔校验失败：该笔 `fatal`，记录原因，允许用户明确跳过后继续；**不静默跳过**。
- `429/5xx/网络错误`：可重试，指数退避，日志保持 `pending`，绝不删本地。

## 6. 客户端迁移日志

在游客自己的 IndexedDB 中新增键（与业务数据同库、**不得写入正式库**）：

`guest:<guestId>:migration`，schema v1：

```ts
interface GuestMigrationJournal {
  schemaVersion: 1;
  migrationId: string;              // UUID，一次迁移一个
  guestId: string;                  // 本机来源，仅用于校验；不发给服务端
  targetUserId: string;             // 正式账号 id（用于识别账号切换）
  targetBookId: string | null;      // 创建成功后立即写
  targetBookName: string;
  createdAt: string;
  updatedAt: string;
  status: "preview" | "running" | "paused" | "complete" | "failed";
  counts: { transactions: number; skippedDeleted: number; categories: number; paymentMethods: number; tags: number };
  mappings: {
    categories: Record<string, string>;      // guest category id -> target category id
    paymentMethods: Record<string, string>;
    tags: Record<string, string>;
  };
  items: Record<string, "pending" | "sending" | "done" | "skipped" | "fatal">;
  // 或者存数组；键为游客交易 id。sending 崩溃后复位 pending（幂等安全）。
  failures: { guestTransactionId: string; code: string; message: string; at: string }[];
  lastError: string | null;
  attempts: number;
}
```

- 迁移日志与游客业务数据分开键；清理游客数据时**连日志一起删**，但“清除游客数据”在迁移 `running/paused/complete 未确认` 时给出额外警告（见 §9）。
- 迁移日志不进入正式库、不发服务器；不参与正式同步队列。

## 7. 幂等机制（三层）

1. **交易层（最强）**：服务器 `idempotencyKey` 唯一。客户端固定 `idempotencyKey = guestTransaction.id`，并用同一 `id`；重试/断网/崩溃后重复提交返回同一行。
2. **实体层**：分类/支付方式/标签使用 `(bookId, kind, name)` / `(bookId, name)` 唯一约束；先查后建，遇到 409 再查一次并写入映射；绝不重命名或覆盖目标已有实体。
3. **编排层**：
   - 一次迁移固定 `migrationId` 与本地日志；`targetBookId` 一旦确定不更换。
   - Web Locks API 锁 `guest-migration:<guestId>`，防止两个标签页同时迁移；锁不可用（旧浏览器）时至少用日志 `status` 做第二次检查。
   - 每次启动迁移页/进入游客应用时检查日志：有 `running/paused` 则恢复；有 `complete` 则阻止重复全量迁移，只提供增量。
   - `sending` 状态的条目在重新开始前一律视为 `pending`，因为交易接口幂等，重复发送无害。

## 8. 失败恢复方案

### 8.1 状态机

```
preview
  → running
      ├─ 全部条目 done/skipped + 对账通过 → complete
      ├─ 网络/会话/限流 → paused（保留日志）
      ├─ 目标丢失/权限错误/幂等冲突 → failed（保留日志）
      └─ 用户主动取消 → paused（不删任何已写数据）
  → complete（终态；可清理游客数据或做增量）
```

### 8.2 具体场景

| 场景 | 行为 |
|---|---|
| 断网 / 请求超时 | 当前批次停在 `pending`，状态 `paused`；恢复网络后用户点“继续”或下次进入自动提示；不删本地。 |
| 浏览器刷新/崩溃/关闭 | 日志在 IndexedDB；重新打开后按日志恢复；`sending` → `pending`，利用交易幂等重发。 |
| 账号退出/切换 | 迁移要求 `targetUserId` 一致；不一致 → 不自动继续，要求重新登录原账号或明确放弃本次迁移（已写入目标账本的数据保留，不自动删除）。 |
| 401/403，目标账本被删除/失去权限 | `failed`：本地保留，提示“目标账本不可用，请重新选择”；已写入的数据不自动回滚。 |
| 单笔 4xx 校验失败 | 该笔 `fatal`；迁移可继续其他条目；结果页逐条显示原因，允许“重试失败项”“跳过后完成”（跳过必须用户点选）。 |
| 分类/标签映射失败 | 不发送该笔交易，记录 fatal；用户可重试或跳过。 |
| 429/5xx | 退避重试 1s/2s/4s（上限 3 次）后暂停；继续后从待发项恢复。 |
| 重复打开两个标签页 | Web Lock 独占；第二个提示“另一个页面正在迁移”。 |
| 迁移中用户清理游客数据 | 拒绝或强提示：先暂停/确认，至少不能静默删源；`running` 时禁用“清除游客数据”，完成后单独确认。 |
| 完成后再次迁移 | 只迁移 `items` 中不存在的**新增**交易（按游客交易 id 过滤）；已迁移条目不再发送；不更新服务器上已迁移的数据。 |
| 游客在迁移后继续编辑已迁移条目 | **首版不反向同步**；结果页明确提示“已迁移的旧记录不会随游客端修改而更新”；需要编辑请在正式账号里操作。 |

### 8.3 永不自动做的事

- 不自动删除游客数据、游客身份、迁移日志。
- 不自动删除/回滚目标账本或已写入交易；失败只保留并报告。
- 不自动重试 `idempotency_conflict`、目标权限错误等 fatal。
- 不在失败时把部分成功伪装成“迁移完成”。

## 9. 完成判定与本地清理

**完成条件**（全部满足）：

1. 所有未跳过交易 `status = done`；跳过项由用户明确确认；
2. 分类/支付方式/标签映射全部完成或明确跳过；
3. 对账通过：按游客交易 id 集合查询/比对目标账本科目数量、按币种/收支求和与本地一致（只读校验）；
4. 迁移日志写 `complete`，记录完成时间与统计；
5. 结果页展示“已迁移 N 笔到账本 B；本机游客数据仍保留”。

**清理**：迁移完成不自动清理；游客「我的」页的“清除游客数据”仍按现有两条确认逻辑，并额外提示“迁移已完成，删除的是本机副本”。目标账本上的数据属于正式账号，不因清理游客数据而删除。

## 10. 安全、权限与隐私

- 迁移所有写操作都在**正式账号会话**下调用现有接口；服务器权限/账本成员校验不绕过。
- 游客数据只在用户点击“确认迁移”后离开本机；预览阶段只读取本地 + 正式账号的只读接口。
- 不把 `guestId` 当作 userId/权限；服务器不持久化 guestId 作为身份（如需要审计，只保存在客户端日志）。
- 共享账本默认拒绝迁移（可能被其他成员看到/影响）；只允许本人管理且**无其他成员**的账本，或新建账本。
- 迁移目标若含其他成员，必须先由所有者明确未来是否允许；首版不做。
- 日志/诊断只记录错误码与匿名 id，不把金额/备注写进服务器日志；本地诊断也不额外复制交易正文。
- CSRF/会话规则沿用现有；迁移不做额外“长期令牌”。

## 11. UI 与交互（S14-D 首版）

- 入口：游客「我的」→「迁移到正式账号」；先登录/注册，再进入迁移向导。未登录时只显示说明，不自动跳转。
- 三步向导：**预览 → 选择目标 → 确认迁移**；进度页显示已迁移/总数、当前批次、失败数；失败页显示原因与“重试/跳过失败项/放弃（本地保留）”。
- 完成页显示结果与“清除本机游客数据”的**独立**入口（不默认勾选）。
- 不新增独立品牌/首页；复用现有 `TabPage`/按钮/对话框与语义颜色。
- 迁移过程中导航离开：允许，但显示“迁移已暂停，可回来继续”；不在页面卸载时静默发请求。

## 12. 测试计划（实现时）

**单元**：

- 映射纯函数：同名校验、系统分类、归档分类、标签颜色、金额/币种、时间/时区、墓碑跳过。
- 日志状态机：pending/sending/done/skipped/fatal，崩溃恢复，幂等键稳定性，增量过滤。
- 预览统计与对账求和。

**集成/API**：

- 相同 idempotencyKey 重复提交只产生一行且同账本返回 200；不同账本冲突。
- 分类/支付方式/标签重复创建返回 409 后可查询映射。
- 目标非空/无权限/共享账本被拒绝。
- 正式账号原有数据在迁移前后完全不变（数量、金额、修改时间）。
- 迁移日志不进入正式库/缓存/队列。

**真实浏览器（320/390/桌面）**：

- 正常迁移：N 笔/多币种/分类/支付方式/标签，完成页统计与正式账本一致。
- 断网/刷新/重启浏览器/关闭标签页后恢复；重复点击“继续”不重复。
- 单笔失败注入（如超长 note/被删分类）→ 失败列表、跳过、重试。
- 两个标签页并发只允许一个。
- 迁移中切账号/退出/清理游客数据被阻止/警告。
- 迁移完成后游客数据仍在；清理游客数据不影响正式账本。
- 正式账号原有账本/交易无变化；游客数据在 `libellum-guest`，正式库无 guest 键。

## 14. 开放问题（需所有者拍板）

1. 目标首选**新建账本**，是否允许迁移进已有空账本？建议允许但只限本人管理的空账本；共享账本首版禁止。
2. 归档分类/支付方式：保留归档状态（多一次 PATCH），还是首版统一迁为普通项并明确提示？建议首版保留状态。
3. 迁移完成后游客数据：保留多久、是否提供一键“确认迁移完成并清除本机游客副本”？建议不自动清除，完成页给独立按钮 + 二次确认。
4. 迁移后游客继续记账的增量迁移：只迁新增、不更新旧记录，是否足够？若要“游客编辑后再同步”则超出 S14-D 首版，需重新设计冲突规则。
5. 是否需要服务端迁移审计记录（谁在何时迁移多少条）？首版客户端日志已足够；如需要，再加只读审计。
6. 单账号多次迁移（换设备/换游客身份）是否允许？建议允许但每次都要求预览确认，并按游客交易 id 幂等；不能依赖 guestId 作为身份。

## 15. 验收标准（草案）

- 迁移由用户主动发起、可预览、可选择目标；未登录/未确认不会上传。
- 迁移重复执行不产生重复交易；中断后可以继续；失败不丢本地。
- 正式账号原有数据不改变；不覆盖、不合并已有交易。
- 完成对账：数量与金额按币种/收支一致；本地游客数据仍存在。
- 清理游客数据后，正式账号数据不受影响；正式账号清理本地数据不影响游客数据（S14-C 已验证，迁移实现不得破坏）。
- 所有真实浏览器回归（S14-A/B/C 既有套件 + 本设计测试）通过。
