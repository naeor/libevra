## 3. 顶部三按钮与更多菜单

- 顺序与语义：`刷新`（原行为：`syncNow` → `syncMonth` → `readLocalTransactions`）／`批量操作`（进入当前列表的多选模式）／`更多`。
- 导出不再是顶部按钮，进入 `/export` 的入口改为「明细 · 更多 → 导出账目」。导出页面本身未改。
- 顶部布局、海浪、汇总区域未动：`DetailTools` 仍在原 `.detail-tools` 行内，按钮尺寸 `size-9`、图标 `18px` 与刷新一致。
- guest：仍只显示刷新，与原有 `guest ? null : (导出/更多)` 的隐藏规则一致；理由见 §6。
- 更多页分区：
  - **这台设备**：本机存放统计（原样保留）。
  - **导出账目**：按钮进入 `/export`。
  - **筛选与查找**：回到明细页使用现有筛选（月份箭头 / 收支 / 分类 chip），页面明确写「目前还没有按文字搜索账目」。
    未新增搜索系统（按任务要求属"需先报告"的范围）。
  - **数据维护**：清空「待同步」印记（逻辑与原文案逐字保留：不发请求、不删任何账目）；新增「重新加载应用」。
- 重新加载应用：确认后执行**普通** `window.location.reload()`；确认框写明「未保存的表单内容会丢失」「正在进行的导入可能中断」
  「不会清除本机账目，也不会删除服务器上的任何数据」。与下载管理的「清除并重新加载」（会清本机副本）明确区分，未改动后者。

## 4. 批量选择模式

| 行为 | 实现 |
|---|---|
| 进入 | 顶部「批量操作」；不跳路由，列表原地变多选 |
| 顶部 | 工具栏换成「取消」；收支分段下方出现「选择账目 / 已选 N 条 / 全选已加载的 N 条」 |
| 行 | 左侧复选框；点击卡片=切换选择，不再进入详情（含冲突行） |
| 全选 | 只作用于 `ordered`（当前筛选下已加载的记录），文案写明「不会扩大到整本账」；再点变「取消全选」 |
| 筛选变化 | 月份 / 收支 / 分类任一变化即清空选择，并显示「筛选条件变了，已清空选择。」 |
| 底部 | 批量栏**取代** `BottomNav`（含中央记账按钮、账本说明、卡片预留高度），自带 `pb-[env(safe-area-inset-bottom)]`；未选中或不可写时两按钮禁用并显示原因 |
| 退出 | 恢复原列表、筛选、滚动位置（未重置 scrollTop）、账本上下文；选择状态清空 |

批量模式下会先折叠记账卡片菜单（`menu.close()`），避免同时开两种模式。

## 5. 批量编辑 / 删除的字段范围

| 字段 | 是否可批量 | 说明 |
|---|---|---|
| 分类 | ✅ | 必选一本账内、未归档、与该笔 `kind` 一致；混合收支时禁用该字段并说明 |
| 标签 | ✅ | 按「添加」或「移除」两种模式，结果按每笔现有标签计算；超过每笔上限（10）则该笔失败并说明 |
| 支付方式 | ✅ | 必选一本账内、未归档 |
| 金额 / 收支方向 / 币种 / 日期 / 时区 / 备注 | ❌ | 补丁构造里根本没有这些字段的写入分支（不是"检查后跳过"），测试逐一断言保持原值 |

- **补丁式更新**：`buildBatchEdit` 只把勾选字段写进 `apply()`；本地副本其余字段原样带过，服务端请求体由
  `lib/offline/sync.ts` 从本地副本 + 变更链生成，未勾选字段不会被整对象覆盖。
- **逐条执行**：每笔调用既有 `updateEntry`（离线队列 / 幂等 / 版本与冲突链均复用）；删除调用既有 `deleteEntry`（软删除）。
  没有新增批量 API，也没有改同步协议。
- **混合收支**：选择"禁用并说明"——列出「所选的账目收支方向不同，不能统一改分类」；不在同一请求里按 kind 分组（两种结果更难解释）。
- **冲突中的账目**：选中后逐条判失败「这笔还在等你在冲突页面里选一版，先处理冲突。」，不制造无法投递的改动。
- **删除确认**：标题带数量（`删除选中的 N 笔账目？`），后果三条：不可自行恢复、本月总额会重算、离线时先本机排队。
- **结果汇总**：`成功 N / 不变 N / 失败 M（原因，最多列 2 条 + …）`；全部失败时不说成功；离线时用
  「已在本机修改 N 笔，还没有投递到云端；联网后会自动投递」。**没有静默部分成功**。
- 执行后仅保留失败项为选中，便于重试。

## 6. 权限与离线处理

| 情形 | 处理 |
|---|---|
| 个人账本 | 允许（单成员即所有者，不额外查询角色） |
| 共享账本 + 离线 | 沿用既有 `useSharedLedgerOfflineReadOnly()`（`writePolicy.ts`）→ 禁用并说明；与写入层 `assertWriteAllowedNow` 同一判断 |
| 共享账本 + 查看者 | **新增**一次性角色查询（`useBookMembers` 的 `myRole`），仅批量模式且仅共享账本挂载；`viewer` → 禁用并说明 |
| 角色查询失败 | 禁用并说明「没能确认你在这本账的权限…联网后重试」（宁可不可点，不给服务端必拒的写入） |
| 角色未返回 | 禁用并说明「正在确认你在这本账的权限…」 |
| guest | 批量按钮隐藏，与导出/更多一致；理由：现有 `guest ? null` 规则不拆开实现，单笔修改/删除仍可在记账详情页完成 |

- 离线写入：`updateEntry` 在离线时返回 `pending: true`，汇总按「本机排队」表述；`deleteEntry` 后读 `readMarks()`
  判断该笔是否仍 `pending`，**不**把排队说成已删除到云端。
- 共享账本离线只读的判断未复制，直接复用既有 hook 与写入层守卫（项目规则：既有权限判断不许改动，只许新增；
  本轮只新增了角色查询这一条客户端判断，服务端仍是权威）。

## 7. 刷新反馈

- 行为未重写：仍是 `syncNow()` → `syncMonth(month)` → `readLocalTransactions()`；`refreshing` 防并发与图标旋转保留。
- 新增一句话结果（`refreshFeedback.ts`，8 秒后自动消失，`role="status"`）：
  - 投递 + 拉取：`已向云端投递 X 条，并更新了当前月（Y 条来自云端）。`
  - 仅投递 / 仅拉取 / 都没有：分别给出准确说法；**零投递不写成"已同步"**。
  - 离线（按下时的合并离线信号）：`当前离线，没能连上云端；已经重新读取了本机账目。`
  - 抛错：`同步没有完成：<原因>。已经重新读取了本机账目。`（不再只是"转圈停了"）
- `syncMonth` 请求失败会返回 0（无法区分"没有数据"和"没连上"），因此文案从不据 0 宣称云端已被更新。
- 未改成 reload，不碰 IndexedDB、未同步账目、冲突解决与幂等路径。

## 10. 残余风险

1. **真机视觉未验收**：批量栏取代导航后的底部留白、选择栏挤占列表高度（小屏约剩 200–250px）只能靠代码推断，需手机确认。
2. **共享账本角色查询**会让批量模式多一次 `GET /books/members`（仅共享账本、仅进入批量时）；失败时按钮禁用，方向安全但会挡住本可写的用户。
3. **批量删除的"服务器是否已收到"**：与单笔删除一致——服务器拒绝时该笔仍带 `pending` 印记，汇总按"还在本机排队"表述，不会说成已删除；
   但用户需要到「数据维护 → 清空待同步印记」或下次刷新才能看清残留。
4. **冲突中的账目不能批量处理**：会逐条失败，错误文案已说明原因；批量场景下没有直达冲突页的入口。
5. **逐条串行**：30 笔即 30 次写入/同步，弱网下耗时明显（`updateEntry` 在线时每次都会尝试投递）。
6. **只存在于查询缓存的账目无法批量编辑**：`updateEntry` 找不到本机存储的副本时返回 `null`，该笔被判失败
   「本机没有这笔账目，无法修改。」（例如该月未下载、记录只来自服务端查询）。单笔编辑在同情况下会回退到服务端 PATCH；
   批量为了统一走离线队列，没有做这条回退。删除不受影响（`deleteEntry` 先入队再投递，不要求本机有副本）。
7. **`applyBatchEdit` 的 `input` 为兼容游客写入路径而携带了未勾选字段的当前值**；账号路径不使用该对象（请求体由本地副本推导），若将来有人改成直接发送 `input`，需重新核对。
8. **更多页「筛选与查找」是入口而非功能**，可能被理解为"搜索已实现"，文案已尽量直白，仍需所有者确认口径。
