## 0. 结论摘要

1. **现有重复检测是三套独立实现加一个专用接口，共四种判定口径**，没有共享的规则模块：
   - Python `apps/ocr/dedupe.py`（图内 / 跨图 / **与账本已有记录**三类）；
   - 前端 `apps/web/src/lib/ocr/duplicates.ts`（只有图内 / 跨图，**没有"与账本历史比较"**）；
   - 账本导入 `apps/web/src/lib/ledgerImport/duplicates.ts`（跨来源 A/B 六条规则）；
   - 接口 `POST /api/v1/transactions/duplicates`（精确到分钟的全等匹配，供拍照单笔用）。

2. **"60 秒口径"不是唯一的**：三处 60 秒（`dedupe.py:45`、`duplicates.ts:18`、`ledgerImport/duplicates.ts:26`），
   一处**精确到 HH:mm 的全等**（`apps/api/src/routes/transactions.ts:441-445`），一处**完全不看时间**
   （游客模式的本地判重，`apps/web/src/lib/queries.ts:1748-1755`）。同一笔交易在不同入口会得到不同结论。

3. **"是否查历史"按入口分裂**：只有账本导入真的拿目标账本**全量历史**做候选
   （`apps/api/src/ledger/importTarget.ts:86-102`，无时间窗、无分页）；拍照单笔查的是**同一天 + 同金额 + 同币种 +
   同方向 + 同一分钟**（索引可用，且有 `take: 20`、返回前 5 条）；
   **OCR 批量导入完全不查历史**；CSV 导入**只按身份**去重，不做内容判重。

4. **§6.2"已有记录不得因未勾选而删除"这条产品硬边界，在账本导入里已经实现**，而且是逐条选择：
   来源默认"导入"、目标默认"保留"，只有用户逐条点"移除"才进软删除清单
   （`apps/web/src/lib/ledgerImport/decisions.ts:25-35`、`:63-65`、`:93-114`；服务端二次校验 `ledgerImport.ts:762-787`），
   提交前还有一次列出具体记录的二次确认（`LedgerImportPage.tsx:1129-1166`）。**这是 E4/E5 可以直接沿用的语义。**

5. **"未勾选即跳过"存在于 OCR 批量导入**：`buildImportPlan` 遍历全部候选，只跳过用户显式标记无效的项
   （`apps/web/src/lib/ocr/import.ts:191-238`），疑似重复项**默认全部导入**，确认框只做整体提示
   （`OcrOverviewPage.tsx:442`）。该逻辑**不能**用于删除已有正式交易——它与账本导入的目标侧语义正好相反。

6. **完全没有的**：不重复关系记录、全账本主动审查入口/接口、按金额或来源 ID 的跨历史候选检索、
   任何"用户已确认不重复"的抑制机制、任何服务端的重复候选计算接口。

7. **不需要重写账本导入**：其检测 + 逐组/逐条决定 + 指纹并发保护 + 软删除 + 撤销链路完整可用，
   缺口只在（a）候选范围仅限"本次导入的来源 vs 目标全量"，（b）检测在浏览器算、服务端只校验结构。

8. **S15 发布安全性：未发现阻断发布的重复检测缺陷。** 细节与判定依据见 §11。

### 2.3 60 秒口径落在哪里 / 能不能参数化

| 位置 | 常量 | 可否调参 |
|---|---|---|
| `apps/ocr/dedupe.py:45` | `DUPLICATE_TIME_TOLERANCE_SECONDS = 60` | **可**：`DuplicateOptions(time_tolerance_seconds=…)`（`:69-72`），但**没有**从 env/配置读取的入口，只有测试与 `overview.py` 会传 |
| `apps/web/src/lib/ocr/duplicates.ts:18` | `DUPLICATE_TIME_TOLERANCE_SECONDS = 60` | **不可**：模块常量，`timesClose` 直接闭包引用（`:91-96`） |
| `apps/web/src/lib/ledgerImport/duplicates.ts:26` | `DUPLICATE_TIME_WINDOW_MS = 60_000` | **不可**：`withinWindow` 直接引用（`:167-172`） |
| `apps/api/src/routes/transactions.ts:441-445` | 无窗口，全等 | **不可**（语义不同，不是窗口） |

结论：**60 秒目前是三处硬编码 + 一处全等匹配，不是一套可配置规则**。E2 若要求"按来源/时间精度分档"，
必须先把窗口提取成带来源参数的输入，并给四套实现一个共同的规则模块（或明确只保留一套）。

### 2.4 两条写入通道（六个入口的落地方式不同，E4 接入前必须先分清）

| 入口 | 写入通道 | 离线可用 |
|---|---|---|
| 手动记账 `/add` | `offline/write.ts:290-336` `createEntry`（本地先写 + 印记 + 排队） | **是** |
| 语音记账 `/voice/review` | `useCreateTransaction` → `POST /transactions`（直连） | **否** |
| OCR 单图 `/scan` | `useCreateTransaction` + `useDeleteTransaction`/`useRestoreTransaction`（直连） | **否** |
| OCR 批量 `/ocr/overview` | `offline/write.ts` `createEntry` 逐条（`OcrOverviewPage.tsx:57`） | **是** |
| CSV `/import` | 服务端 `POST /api/v1/import` | 否 |
| 账本导入 `/import-ledger` | 服务端 `POST /api/v1/ledger-imports*` | 否 |

证据：`queries.ts:1666-1682`（`useCreateTransaction` 只调 `apiFetch`）、`ScanPage.tsx:64-67`、
`VoiceReviewPage.tsx:52`/`:280-296`、`OcrOverviewPage.tsx:57`。

> ⚠️ 这条差异直接影响 E4：**同一个"新增时提醒"组件不能假定写入一定会成功落地**。
> 直连通道在离线时会直接失败（`apiFetch` 在离线时立即拒绝），所以提醒出现后失败的情形必须能解释清楚。

### 3.3 已有交易与新增候选的保存语义对照（回答"为什么不能照搬"）

| 维度 | 新增候选（OCR 批次） | 已有正式交易 |
|---|---|---|
| 数据本体 | sessionStorage 里的**草稿**，不是账目（`lib/ocr/types.ts:1-13`、`lib/ocr/batchStore.ts`） | 数据库行，带 `seq`/`version`/`deletedAt`（`schema.prisma:971-1091`） |
| "不处理"意味着 | 标记 `invalid` → 确认时不计入 → **什么都不发生** | 什么都不做 = **保留** |
| 默认状态 | 有效（未勾选 = 导入） | 有效（未勾选 = 保留） |
| 决定粒度 | 整批一次确认，没有逐组表态 | 逐条 + 二次确认 |
| 删除实现 | 没有删除这回事 | `DELETE /transactions/:id` → 软删除 + `TransactionEvent` |
| 失败后果 | 几笔没写进去，批次还在，可重试 | 账目真的少了一笔 |

"未勾选即跳过"的两处实现（**都只对候选成立**）：
- OCR 批量：`import.ts:195-196` 跳过 `invalid`，其余进入 `ready`；
- 账本导入：`decisions.ts:67-79` 的 `skippedSourceIds` 只统计**来源 B** 的 `skip`。

**为什么不能照搬**：`buildImportPlan` 的语义是"有效项默认写入"；把它套到已有记录上，
等于把"用户没看见/没勾选"翻译成"删除"。这与规划 P6、S14-D §6.3（"组是核对单位，不是删除单位"）
直接冲突。反过来，账本导入的**目标侧默认 `keep`**（`decisions.ts:63-65`）才是可以照搬的那一半。

## 4. 已知缺陷与缺失能力

### 4.1 真实缺陷（有证据、有明确影响）

**D1 · "与账本历史比较"在 OCR 路径上只存在于 Python，没有接到产品路径。**
`dedupe.find_against_existing`（`apps/ocr/dedupe.py:391-428`）与 `build_overview(existing_entries=…)`
（`apps/ocr/overview.py:87-109`）都有实现与测试（`tests/test_dedupe.py:155-227`、`tests/test_overview.py:110-125`），
但：
- `apps/ocr/service.py:159-166` 的响应里没有任何重复字段，`recognise()` 也不接收已有记录；
- 唯一调用 `build_overview` 的产品外工具 `apps/ocr/multi_preview.py:71-73` **不传** `existing_entries`；
- 前端 `apps/web/src/lib/ocr/duplicates.ts` 没有对应函数，`OcrOverviewPage.tsx:163` 只调 `findSuspectedDuplicates`。

影响：S15-B 设计方向 §11 "三类范围（图内/跨图/跨来源）"实际只落地两类；批量导入同一笔已记账的交易不会提示。
（`apps/api/src/ocr/client.ts:103-104, 477-478` 已经能透传 `duplicate_suspected`，只是没人填。）

**D2 · 四套判定口径不一致，同一笔交易在不同入口得到不同结论。**
证据见 §2.2。最尖锐的是：账本导入要求"分类映射后相等 + 标签集合相等"，而单笔判重和 OCR 都不看分类/标签；
同一笔交易若在两个渠道被归入不同分类，导入会说"不重复"、OCR 会说"重复"。
影响：**提示不一致**，不损坏数据；但会让用户不信任提示。修复属规则统一（E2），不属热修。

**D3 · OCR 批量导入不要求对每组疑似重复表态，默认全部写入。**
`countImportableItems`（`import.ts:173-182`）把"未标记无效且字段齐全"都算可导入；`buildImportPlan`
（`:191-238`）不含任何重复判断；确认框文案只是整体提示（`OcrOverviewPage.tsx:442`）。
影响：与 E4 §6.1 的"分别选择保留 A / 保留 B / 都保留"不一致；用户若没点开"疑似重复"筛选，会一次性写入两笔。
**不构成数据丢失**（重复行可删），但它是"未经逐组确认就写入重复"的唯一路径。

**D4 · 账本导入的重复组由浏览器主张，服务端只校验结构。**
`detectDuplicateGroups` 在前端跑（`ledgerImport/preview.ts:50-66`），提交时服务端 `buildDecisionPlan`
（`ledgerImport.ts:700-801`）只校验：来源/目标 id 是否存在、是否跨组重复、`sourceActions/targetActions`
是否覆盖整组、一对多/多对多禁止组级删除。
影响：**不是漏洞**（等价于用户直接调删除接口，仍需写权限、仍需逐条显式勾选，且有二次确认），
但 E1 必须记下：**"重复组正确"这件事没有服务端保证**，所以 E5 不能以"服务端已确认过重复"为前提。

**D5 · `loadTargetSnapshot` 无时间窗、无分页，一次读全账本。**
`apps/api/src/ledger/importTarget.ts:86-102`。当前只允许"本人拥有的单人账本"作为目标
（`:145-186`，`book_not_solo`），因此规模有限；但它同时是"大账本"风险的现成前例：
E5 若照抄这个读取形状，会在几千笔以上把整本账塞进一次响应和浏览器内存。

**D6 · 单笔判重的失败被静默吞掉。**
`ScanPage.tsx:371-386`：`catch { /* 故意静默 */ }`，检查不到就照常写入。
这是**有意的取舍**（宁可不提醒，也不能因为提醒失败而丢账），文档里也写明（`shared/src/ledger.ts:585-589`）。
列入清单只为避免 E4 把它当 bug 修掉。

### 4.2 设计范围外 / 不是缺陷（避免夸大）

| 现象 | 为什么不是缺陷 |
|---|---|
| CSV 导入不做内容判重 | 文案已明说"没有这几列的外部文件也能导入，但那时无法判重"（`ImportPage.tsx:215-218`）；服务端注释解释了"去重按账本范围、而不是按标识符全局"（`import.ts:32-35`） |
| OCR 重复只标记不阻塞 | 规划 P4 + S15-B §3 的硬边界 |
| 没有"不重复"关系表 | 规划 §5/E3 未开始 |
| 没有全账本审查入口 | 规划 §7/E5 未开始 |
| 手动/语音不查重 | 规划 §6 尚未接入；且 `ScanPage` 已有可复用接口 |
| 账本导入要求分类/标签相等 | 是 S14-D §6.1 的所有者定义（2026-10-19），不是实现偏差 |
| 游客判重只看金额+方向+日期 | `queries.ts:1743-1755` 注释写明"故意保守"，避免游客问到账户账目 |
| 检测结果没写进 `TransactionEvent` | 目前没有"判定"这一事实需要持久化；E3 才需要 |

## 6. "不重复"关系表的数据设计可行性与风险（建议，不是定案）

### 6.1 建议字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid PK | |
| `bookId` | uuid | **冗余但必要**：所有查询都先按账本收窄；也是"不跨账本"的硬保证 |
| `transactionAId` | uuid | 规范化为"字典序较小者"，保证 `(A,B)` 与 `(B,A)` 只存一行 |
| `transactionBId` | uuid | 同上；写入前断言 `A < B` |
| `relationship` | varchar(16) | 首版只需 `not_duplicate`（保留 `duplicate_confirmed` 之类的扩展位，或直接不加） |
| `decidedBy` | uuid | 确认人（多人账本里要能答"谁说的"） |
| `decidedAt` | timestamptz | |
| `decisionSource` | varchar(24) | `import_group` / `audit_group` / `manual` —— 便于按来源统计与撤销 |
| `basis` | jsonb | 判定当时的依据快照（金额/币种/方向/日期/时间/分类/标签的**值**，不是引用） |
| `basisVersion` | jsonb 或 int[] | 两条交易当时的 `version`（失效判据，见 §6.4） |
| `revokedAt` / `revokedBy` | timestamptz / uuid | 撤销用**软撤销**，不物理删除 |
| `createdAt` | timestamptz | |

推荐约束与索引：
- `UNIQUE (bookId, transactionAId, transactionBId)`（配合 A<B 规范化，等价于无序唯一）；
- `INDEX (bookId, transactionAId)`、`INDEX (bookId, transactionBId)`（双向查"这对是否已判过"）；
- 可选 `INDEX (bookId, revokedAt)`（列"当前生效的关系"）。

### 6.2 与现有结构的三种参照，以及为什么不能直接套

| 现有结构 | 为什么不照搬 |
|---|---|
| `Tag` / `TransactionTag`（`schema.prisma:944-956`、`1166-1176`） | 标签是**分类学**：一个标签可挂任意多笔，语义是"同类"；而"不重复"是**具体两笔之间**的关系，且**不具备传递性**（规划 §5.3）。用标签表达会让人误以为可以批量套用 |
| `TransactionEvent`（`:515-560`） | 它是**单笔的时间线**（`transactionId` 单侧），无法表达"两笔之间"，也无撤销语义 |
| `LedgerImportSourceState`（`:1355-1376`） | 结构相近（账本 scope + 唯一键 + 无外键 + 决策字符串），是**最好的先例**：说明本项目能接受"回执/关系表刻意不加外键"；但它是"来源记录 × 目标账本"，不是"交易 × 交易" |

### 6.3 外键与级联（两种方案，需所有者选）

**方案 A：加外键（`bookId → books.id onDelete: Cascade`，交易侧不加外键）**
- 账本被永久删除（S13-H 生命周期/墓碑清理）时关系随之消失，符合"不留无使用者的行"；
- 交易侧不加外键 → 交易被生命周期清理后关系行仍可解释（与 `ledger_imports` 的理由一致）。

**方案 B：完全不加外键**
- 与 `LedgerImport*` 三张表一致（`:1237-1240`、`:1264-1265`、`:1352`），回执/历史类数据的既有风格；
- 代价：账本删除后需要清理任务，否则会留孤儿行（`apps/api/src/scripts/purge-archived.ts` 一类脚本要跟进）。

**关键事实：软删除不会触发任何级联。** `Transaction.deletedAt` 只是标记（`schema.prisma:1067`），
所以"删掉一笔被记录为不重复的交易"不会让关系行消失——这正是需要的（撤销删除后关系仍应有效）。

### 6.4 失效规则（规划 §5.4 的技术含义）

必须能被判定的四种变化，都可以用"`basis` 里的值 + 当时的 `version`"回答：

| 变化 | 建议判定 |
|---|---|
| 金额 / 币种 / 方向 改变 | **立即失效**（不再抑制），并让该对重新进入候选 |
| 时间改变（跨出窗口） | 失效 |
| 分类 / 标签 / 商户 / 备注改变 | 规划 §4.5 说这些**不是必要条件**，因此建议**不失效**（只更新 `basis` 或忽略） |
| 删除 / 恢复 | **不失效**（保留抑制）。理由：用户确认的是"这两笔不是同一笔钱"，删除不改变这个判断 |
| 跨账本迁移 | 关系**不迁移**（bookId 不同）；迁移本质是导入，导入应重新判定 |
| 数据导入时 | 不迁移关系（同上） |

> ⚠️ 若采用"`version` 不一致即失效"，则任何编辑都会让关系失效——对用户来说表现为"我确认过，怎么又问一遍"。
> 建议：**只对影响判定依据的字段做值比较**，`version` 仅作为"这条记录后来被动过"的提示信息，不单独触发失效。

### 6.5 撤销与审计

- 撤销 = `revokedAt/revokedBy` 置位（不是删除），撤销后该对回到候选池；
- 重新确认 = 新增一行（或清空 `revokedAt` 并把旧行记为历史）——**建议新增一行**，因为"撤销过再确认"是一个有意义的序列；
- UI 入口：规划 §7.5 建议放在"重复交易检查"页面的次级区域，不需要新主页面。

### 6.6 与多设备同步的关系（风险最高的部分）

现状：离线写使用"印记即队列"（`offline/write.ts:290-336`、`:463-486`），同步按 id 逐个投递
（`offline/sync.ts`），冲突以"服务器权威 + 每字段冲突记录"处理（`S8 冲突设计决定`）。

对关系表的三种可能，需要所有者选（规划 §10.10）：
1. **服务器权威、不参与离线队列**（推荐首版）：离线时"不重复"判断不可写，只能读缓存；联网后写；
2. 复用离线队列：会引入"关系也要冲突解决"的复杂度（两台设备同时给同一对相反判断）；
3. 完全不在离线展示：最简单，但用户离线看审查结果时看不到"已忽略"的组。

另有一条硬约束：**关系判定不能替代幂等**。即使用户把两笔判为"不重复"，重复提交同一次请求仍必须被
`idempotencyKey` 挡住（规划 §6.4 已写，现状 `import.ts:207`、`transactions.ts:292-306` 已满足）。

### 6.7 风险清单

| 风险 | 说明 | 缓解 |
|---|---|---|
| 用户误点导致永久静默 | "不重复"一旦记录，后续不再提示 | 必须有可见的"已忽略"列表 + 撤销（规划 §5.5 已要求） |
| 传递性误用 | A–B、B–C 不重复 ≠ A–C 不重复 | 只存显式确认的对；不实现推导（规划 §5.3 已写明） |
| 关系数量膨胀 | 一个 5 笔的组确认"都独立"会产生 C(5,2)=10 行 | 可接受（量级小）；但要在 E6 说明"每组确认会产生两两组合" |
| 迁移后无回滚 | 本项目"应用回滚不回滚数据库"（`AGENTS.md` §8） | migration 必须自带 `DOWN` 说明 + 备份演练 |
| 与导入锁交互 | 账本被 `ledger_write_locks` 锁住时（触发器 `assert_ledger_write`，`ledgerLocks.ts:5-12`）关系写入会被拒 | E3/E5 必须识别锁状态并给出可读提示，不能静默失败 |

## 7. 全账本主动审查：候选筛选与性能限制

### 7.1 可行的候选筛选（不新增索引的前提下）

1. **账本 + 未删除**：所有查询的硬前置；
2. **时间分桶**：用现有 `(bookId, deletedAt, occurredLocalDate)` 按月/周取桶，桶内再做两两比较——
   桶内规模通常是"一天几笔到几十笔"，可把 O(n²) 降到可控；
3. **金额 + 币种 + 方向**：桶内用内存 Map 分桶（`${kind}|${amountCents}|${currency}`）——
   这正是账本导入 `candidateKey` 的做法（`ledgerImport/duplicates.ts:163-165`），只是那里还多了分类键；
4. **来源交易 ID**：`unique(bookId, sourceNamespace, sourceRef)` 可做"同一来源记录被导入两次"的精确检测，
   这是**最可靠的一类**（规划 §4.6 "有可靠唯一交易标识支持的重复候选"）；
5. **已确认关系过滤**：E3 生效后作为最后一道排除。

> ⚠️ 时间分桶有一个真实陷阱：**"只有日期没有时分秒"的记录**（CSV 导入把时间缺省为 12:00，
> `apps/api/src/routes/import.ts:409-412`；OCR 导入同样，`apps/web/src/lib/ocr/import.ts:215`）会在同一桶里
> 大量互相碰撞，产生大量误报。这类记录必须降级为"仅金额+日期"的弱证据，不能按 60 秒窗口判定。

### 7.2 现在做不到的三件事

| 需要 | 现状 | 影响 |
|---|---|---|
| 按金额跨月检索 | 无接口、无索引 | 只能时间分桶后再内存筛 |
| 服务端计算候选并返回 | 无（只有前端算） | 几千笔以上会把比较放到浏览器 |
| 后台任务 + 进度 + 取消 | 账本导入有同类能力（`LedgerImportJob`），但**没有通用扫描任务** | E5 若要做后台执行，需要新表或复用 job 形状 |

### 7.3 量级参考（用于判断"要不要任务化"）

- 列表分页默认 50 / 上限 100（`transactions.ts:35-36`）；
- 账本导入单批默认 200 / 上限 500，超过 200 笔才分批（`packages/shared/src/ledgerImport.ts:27-30`）；
  增量导入则**一律**走服务端任务（S14-D §13E）；
- CSV 导入单文件上限 20 000 行（`packages/shared/src/export.ts:134`）；
- 真机实测记录：所有者设备曾出现"60 个月 / 138 条"与"磁盘 115 644 字节 → 138 条"
  （`localLedger.ts:190-198`、`:216-226` 的注释）。**即当前真实账本在"百条"量级**，不是万条。

结论（推断）：**首版按"同步分批 + 真实进度"实现，规模门槛设在几百到一两千笔**是合理的；
真正的风险不是算法，而是"把整本账一次塞进一次响应/一次内存"（D5）。

### 7.4 执行方式的两个现成模板

| 模板 | 位置 | 优点 | 代价 |
|---|---|---|---|
| 同步分批（客户端循环 + 取消） | OCR 批量导入（`apps/web/src/lib/ocr/importExecution.ts:31-70`） | 无需新表，进度诚实（逐条 awaited） | 关页面即中断；数千笔会久 |
| 后台任务（服务端逐批 + 断点恢复） | `LedgerImportJob`（`importJob.ts:260-311`、分批/undo journal/超时自动撤销） | 关页面不影响、有真实进度、可撤销 | 新表 + 生命周期 + 复杂度，且要过 `AGENTS.md` §6 的迁移批准 |

规划 §7.3 要求"进度必须来自真实执行状态，不能用固定动画假装扫描完成"。现有的两个模板都满足；
**不能**用 `setInterval` 递增百分比。

### 7.5 浏览器内存与离线检查边界

- `readLocalTransactions` 会**全量合并**已下载月份 + 查询缓存 + 内存（`localLedger.ts:168-317`），
  这是现有明细页已经在付的成本；
- 设备只持有**已下载的月份**，所以离线审查的候选集天然是子集——**不能据此声称整本账没有重复**
  （规划 P10 已写）；
- 因此 UI 文案必须区分"本机已知范围内未发现"与"账本内未发现"。

## 8. 离线 / 同步 / 软删除 / 编辑 / 撤销的影响

| 机制 | 现状（证据） | 对 S15-E 的具体影响 |
|---|---|---|
| **离线写入** | 本地先写 + 印记即队列（`offline/write.ts:290-336`）；共享账本离线只读（`:48-74`） | E4 的"新增时提醒"在离线时**只能查本机**；共享账本离线不可写，因此也不该提示"可以保留两笔" |
| **同步投递** | 按 mark 逐条投递，创建用 `idempotencyKey = id`（`sync.ts:475-495`） | 检测结果**不得**改变投递行为；"两笔都保留"只是两条独立 create |
| **冲突** | 服务器权威 + 每字段冲突记录（`S8`、`transactions.ts` 冲突路由） | 与重复检测是**两件事**：冲突是"同一笔被改出两个值"，重复是"两笔可能是一笔"。E4 文案不能混称 |
| **软删除** | `DELETE /transactions/:id` 只写 `deletedAt` + `version+1` + 事件（`transactions.ts:990-1030`）；列表过滤墓碑（`ledgerView.ts:9-30`） | E5 删除**必须**走这个接口（而不是新写 UPDATE），否则撤销/恢复/历史全部失效 |
| **恢复** | `POST /transactions/:id/restore`（`transactions.ts:1042-1084`），恢复原 id、原编号 | 撤销"删除"和撤销"不重复判断"是两条独立路径，UI 不要合并成一个"撤销" |
| **撤销条** | `UndoProvider`（`components/UndoProvider.tsx:24-52`）+ 删除后 `showUndo`（`EntryDetailPage.tsx:47`） | 秒级撤销适合单笔删除；批量删除（E5）不适合塞进 UndoBar，应走导入式的"任务可撤销"或"逐条恢复入口" |
| **导入锁** | `ledger_write_locks` + DB 触发器 `assert_ledger_write`（`ledgerLocks.ts:5-12`，migration `20261019150000_s14d_phase4_undo_locks`） | 账本被导入锁住时，**任何写入（含软删除）都会被触发器拒绝**。E5 执行前必须判锁并给出可读提示 |
| **编辑** | `updateEntry` 本地 + 服务端 version 乐观锁（`offline/write.ts:346-430`） | E3 关系失效判定要读"当前值"，不能用"用户确认时的值" |
| **归档 / 永久删除生命周期** | `requireBook` 对归档/删除中返回 403/410（`access.ts:105-111`） | 关系表的外键/清理必须考虑账本被 purge 的情况（§6.3） |

### 10.2 E1 新发现、需要所有者额外决定的问题

1. **"分类相等"要不要从必要条件降为加权项？**（C 口径 vs 规划 §4.5）
   降级会让账本导入**新增**一批重复组，属于可见行为变化，需要所有者认可。
2. **OCR 批量导入是否必须逐组表态才能确认？**（D3）
   这会明显增加一次批量导入的操作步数；替代方案是"确认框默认勾选'我已知晓 N 笔疑似重复'"。
3. **是否接受"服务端只校验结构、不重算重复组"？**（D4）
   若要求服务端重算，E5 必须同时提供"服务端候选计算"接口，工作量与 D5 的规模问题合并。
4. **"不重复"关系是否允许在共享账本里由 editor 创建、由另一名 editor 撤销？**
   多人账本里的"谁说不是重复"需要一条明确的权限规则（现有 `access.ts` 只区分 viewer/可写）。
5. **`Transaction.seq`（用户可见编号）是否要出现在重复对照的 UI 里？**
   账本导入的删除清单已列 `seq`（`decisions.ts:104`），但 `RecordFacts` 不显示编号；S15-E 的核对页需要统一。
6. **历史日期精度不足的记录（CSV 12:00 缺省）如何处理？**
   这是最可能产生大量误报的一类，规划没有覆盖；建议"仅金额+日期，且标注时间精度"。
7. **导入锁存在时，全账本审查是"阻断"还是"只读预览"？**
   触发器会拒绝写入（§8），UI 需要明确是"先完成导入"还是"允许只看不删"。
8. **是否允许 viewer 触发审查（只读）？**
   `POST /transactions/duplicates` 现在挂 `requireRead`（viewer 可用），沿用与否需要确认。

## 11. 与 S15 发布的关系

### 11.1 明确不阻断发布的事实

- 重复检测全部是"只提示"的纯函数，**没有任何一处自动删除/合并/覆盖**（`dedupe.py:13-22`、
  `ocr/duplicates.ts:12`、`ledgerImport/duplicates.ts:14`）；
- 账本导入的删除路径已经是：逐条勾选 → 二次确认 → 软删除 → 事件审计 → 可撤销；一对多/多对多
  组级删除被服务端硬拒（`ledgerImport.ts:780-785`）；
- 幂等与检测完全独立（`import.ts:207`、`transactions.ts:292-306`）；
- 权限边界不依赖客户端（`access.ts:116-122` 的注释与 `app.ts` 装配）。

### 11.2 D1–D6 为什么不构成发布阻断

| 编号 | 为什么不是阻断项 |
|---|---|
| D1（OCR 批量不查历史） | 是"少提示"，不是"错误写入"；单笔 OCR 与账本导入仍提供历史判重 |
| D2（四套口径不一致） | 影响提示一致性，不产生错误数据；不会导致丢账 |
| D3（批量默认写入重复） | 用户被明确告知"可能包含 N 笔疑似重复…是否都保留由你决定"（`OcrOverviewPage.tsx:442`）；重复行可用现有删除/撤销清理 |
| D4（服务端不重算重复组） | 等价于用户直接调删除接口，仍需写权限 + 逐条显式 + 二次确认 |
| D5（目标快照无分页） | 仅限"本人单人账本"，规模受账号约束；超出会成为性能问题而非数据安全问题 |
| D6（判重失败静默） | 有意的取舍，方向是"宁可少提醒也不丢账" |

### 11.3 结论

> **未发现阻断发布的重复检测缺陷。**
>
> 现有实现满足 S15 发布所需的四条底线：只提示不自动处理、删除必须显式确认、检测不替代幂等、
> 不跨账本。D1–D6 应作为 S15-E2/E3/E5 的输入，而不是发布前的返工项。
