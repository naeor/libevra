# Libevra 文档整合与瘦身方案（2026-10-20）

> 对象：`Desktop\工作\记账程序\记账程序v1`（下称 **A**）与 `Documents\deepseek-harness\default-workspace\libevra-s14a`（下称 **B**）。
> 本文只是诊断与方案，**尚未修改任何项目文件**。所有结论都有文件+行号或 git 命令证据。

## 0. 一句话结论

不是"文档太多"，是三件事叠在一起：

1. **同一仓库的两个 worktree 各自维护了一整套互相矛盾的"当前状态"**，两边都自称权威，而判断新旧的方法（版本号 / mtime）都不可靠。
2. **唯一自动注入的规则文件 `AGENTS.md` 自己落后约 6 周**：它还在讲"S13-I 与 S14 并行""本轮 S12-B 部署"，而生产已经是 1.14.20。Agent 每天开工先读到的是过期指令。
3. **`doc-audit` 这个"核查工具"本身审错了分支**（写死 A 的路径），在 B 里跑会把 "1.13.15" 当"代码现状"打印，并且退出码仍是 0。它既产生假阳性，也产生假通过。

三者共同导致一个闭环：**文档不可信 → 每次开工重查 → 重查依据本身是错的 → 结论又写回文档 → 下次更不可信。**

```
文档只写"怎么查"  ──►  必须自己重建状态
        ▲                          │
```

## 4. 目标态

### 4.1 四条原则（写进 AGENTS.md）

1. **一个事实只出现在一处**：规则 / 状态 / 规格 / 历史，四个容器互不越界。
2. **状态可被机器验证**：唯一状态文件带 `commit + 版本 + 迁移数 + 最后核对时间`，脚本校验，不需要人肉重建。
3. **历史只读**：完成即进 `archive/`，不再回写"当前"。
4. **同一时刻只有一个活动工作区**。

### 4.2 目录结构（目标）

```

docs/
├── STATUS.md             ← 唯一"当前状态"（≤ 100 行，机器校验）
```

## 5. 执行方案

### 5.0 第一步：定"唯一活动工作区"

**推荐：只保留 B 作为唯一开发目录，A 退役。**

理由：B 已含 A 全部代码且是生产版本；A 独有 = 1 个文档提交 + `恢复码.docx` + `_backups/` 12 个 dump；两套现状的物理根源就是两个 worktree。

**A 退役前必须搬走**：
1. `docs/恢复码.docx` → B 的 `docs/`
2. `_backups/*.dump`（12 个，约 1.1 MB）→ B 的 `_backups/`
3. A 的 `4980266` 内容 → **不合并**，作为"1.13.15 时点参考"保留（`git show 4980266:docs/...`），但**其中 S13 状态修正要逐条拣回 B**（见 2.1 末）。

> 备选：若确实要两个 Agent 并行，必须改成"**只有一个 Agent 写共享文档**"（另一个只写代码 + 自己 feature 分支），文档由整合者在合并时统一写。以本项目规模，单工作区更省事。

### 第 0 步 · 止血（不动内容，30–60 分钟，零风险）
