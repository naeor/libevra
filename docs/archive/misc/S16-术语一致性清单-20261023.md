# S16 术语一致性清单（2026-10-23）

> 配套文件：[全站文案清单 CSV](S16-用户文案清单-20261023.csv) · [用户文案审查报告](S16-用户文案审查报告-20261023.md) · [Codex 文案任务清单](S16-Codex文案任务清单-20261023.md)
>
> **本轮只整理，不决定全站术语的最终替换。** 尤其涉及账务对象、删除/恢复、重复检测、恢复凭证的词，必须由产品所有者与 Codex 确认后再改。静态命中数是清单行的出现次数，不是唯一句数。

## 0. 先分清四类东西

1. **业务对象**：账本、账目、交易、记录、明细、账单。它们不是同义词，不能为了统一全部替换。
2. **用户数据**：交易备注、账本名、用户名、分类/标签名、用户留言、OCR 原文、语音转写、历史正文。**这些不在文案修改范围。**
3. **产品文案**：字段标签、按钮、说明、状态、错误、确认句。这是本清单的对象。
4. **法律/历史公告**：已发布公告、隐私与条款文本单独分类。可以指出问题，但不能自行改写实质内容或历史公告。

## 1. 高优先级术语簇

### 1.1 账本 / 账目 / 交易 / 记录 / 明细 / 账单

| 术语 | 当前实际含义（代码/产品事实） | 当前出现场景 | 冲突 |
|---|---|---|---|
| **账本** | 一个记账空间（book）；成员、币种、分类、支付方式都归属账本 | 全站 1,190 条静态命中 | 总体稳定；偶与“账目/账单”混用 |
| **账目** | 一笔已保存或待处理的账务条目（entry）；重复检测、历史、详情常用 | 147 条 | 与“交易/记录”大量互换，是主要冲突词 |
| **交易** | 外部或抽象的收支事件；导入/重复检测中常与“账目”混用 | 110 条 | 导入文案里“交易”既指账目又指外部事实 |
| **记录** | 泛称一条账目或一条历史；也用于“历史记录” | 181 条 | 范围过宽；有时指历史事件、有时指账目 |
| **明细** | 列表/账目明细页、明细条目；不是业务对象本名 | 48 条 | 作为导航名可保留，但不宜与“交易”混用 |
| **账单** | 导入的文件/账单（bill）；不是账本 | 22 条 | “账单/账本”字形近，低频但需防混用 |

**建议方向**：由产品确认“账本（空间）—账目（业务条目）—交易（导入/外部事实）—记录（历史/泛称）—明细（视图名）”是否作为稳定层级。若保留“交易”作为对外主词，也必须明确“账本里的交易”和“银行交易”的区别。当前**不要自动全局替换**。

### 1.2 删除 / 移除 / 清理 / 弃置 / 永久删除 / 注销 / 归档 / 恢复 / 撤销

| 术语 | 真实含义 | 冲突点 |
|---|---|---|
| **删除** | 将账目从账本移除；可能可恢复，也可能不可恢复（取决于当前页面/操作） | 509 条；同一动作在不同页面用“删除/移除/清理/弃置”，且可恢复性说法矛盾 |
| **移除** | 从列表/批次/成员中移除，或清除本地副本；不一定是业务数据删除 | 39 条；与“删除”混用 |
| **清理** | 清除缓存/本地副本/过期项 | 48 条；用户可能理解为删除账本数据 |
| **弃置** | 丢弃未保存草稿/批量候选 | 4 条；低频，但语义与删除不同 |
| **永久删除** | 不可恢复的数据清除；生命周期的最后阶段 | 5 条；与“删除”并列出现时，用户需要明确差别 |
| **注销** | 终止账号，不可登录 | 50 条；与“删除服务器数据”是不同动作，不能合并 |
| **归档** | 账本生命周期状态；可限期恢复，不等于删除 | 50 条；与“删除/注销”并列时必须说明可恢复性 |
| **恢复** | 把删除/归档内容还原；或恢复账号访问 | 201 条；与“撤销”不同 |
| **撤销** | 撤回一次操作（如导入、批量操作），不是恢复历史数据 | 42 条；不能与“恢复”互换 |

**建议方向**：保留“删除”“永久删除”“注销”“归档”“恢复”“撤销”的业务区别；只统一**同一能力**在同一流程中的叫法。删除/恢复是 P1 安全问题，先确认真实能力，再改词。

### 1.3 保存 / 提交 / 确认 / 写入 / 入账 / 记账

| 术语 | 真实含义 | 冲突点 |
|---|---|---|
| **保存** | 写入数据库/草稿；可能只是保存备注/账单解析结果 | 369 条；有时用户以为“保存=已记账” |
| **提交** | 提交表单/批次/确认动作 | 79 条；与“确认”边界不清 |
| **确认** | 用户对关键决定的最终确认（重复、删除、导入） | 120 条；被用作普通保存按钮的同义词 |
| **写入** | 技术/内部视角：写数据库/写账本 | 38 条；不应直接给普通用户 |
| **入账** | 真正进入账本成为账目 | 198 条；与“保存”混用会误导 |
| **记账** | 用户的业务动作（手动/语音/粘贴/拍照） | 292 条；应作为动作主词，不替代状态词 |

**建议方向**：区分“保存输入/草稿”和“确认入账”；在用户可见处避免“写入”；“提交”只用于批次/表单动作。**不能为了统一把“保存”全部改成“入账”。**

### 1.4 重复交易 / 疑似重复 / 重复账目 / 重复检测 / 重复提醒

| 术语 | 真实含义 | 冲突点 |
|---|---|---|
| **重复交易** | 入口/设置中常用功能名 | 4 条；与“重复账目”互相替代 |
| **疑似重复** | 尚未确认的重复候选；不是结论 | 118 条；当前最准确的候选状态词 |
| **重复账目** | 审查页标题/群组泛称 | 6 条；与“重复交易”混用 |
| **重复检测** | 全账本扫描动作 | 3 条；与“重复检查”混用 |
| **重复提醒** | 记账时的轻提示，不是全账本审查 | 与“检测”明显不同，不能合并 |

**建议方向**：功能名统一一个（如“重复检测”），候选状态保留“疑似重复”；“重复提醒”作为独立功能保留。**由产品所有者确认。**

### 1.5 支付方式 / 渠道 / 付款方式

| 术语 | 真实含义 | 冲突点 |
|---|---|---|
| **支付方式** | 账本内可管理的支付方式对象（微信、支付宝、银行卡……） | 77 条；主词 |
| **渠道** | 外部平台/来源渠道，不是账本支付方式 | 1 条；低频技术词，容易误导 |
| **付款方式** | 与“支付方式”同义但出现在个别文案 | 应统一到“支付方式” |

**建议方向**：统一为“支付方式”；“渠道”只在确指外部平台时使用。

### 1.6 分类 / 标签

分类是账本的收支分类；标签是用户自定义的横向标记。两者可同时存在，不是同义词。当前大部分文案区分正确，需避免“分类标签”混写和把标签当分类。

### 1.7 成员 / 协作者 / 邀请 / 分享链接 / 加入

| 术语 | 真实含义 | 冲突点 |
|---|---|---|
| **成员** | 账本内的人；含角色/状态 | 331 条；主词 |
| **协作者** | 与成员同义，但在少数说明中使用 | 2 条；低频，建议统一到“成员” |
| **邀请** | 邀请成员进入账本/邀请注册 | 217 条；“邀请码”可能是注册邀请码，不是账本分享 |
| **分享链接** | 账本邀请链接（可能一次性/有期限） | 71 条；与“邀请码/恢复链接”不同 |
| **加入** | 通过分享链接成为成员 | 与“登录/注册”不同 |

**建议方向**：账本内统一“成员/邀请/分享链接/加入”；注册邀请码另行命名并明确区别。**不要把所有“邀请”合并成同一能力。**

### 1.8 恢复码 / 恢复凭证

| 术语 | 真实含义 | 不可合并的原因 |
|---|---|---|
| **恢复码** | 账号密码恢复/账号安全用的一次性码（也可用于恢复账号访问） | 22 条 | 与账号安全绑定 |
| **恢复凭证** | 注销/归档账本时生成的一次性凭证，只用于恢复符合条件的归档账本 | 9 条 | **不能恢复账号**；合并会误导用户 |

**建议方向**：保留两个词；在同时出现的页面加一句“恢复码用于账号，恢复凭证只用于归档账本”。这是安全语义，不能为了简洁合并。

### 1.9 备注 / 说明 / 商品说明

- **备注**：用户填写的交易备注（198 条），属于用户数据，不改写。
- **说明**：页面/字段解释（产品文案），可以改。
- **商品说明**：OCR/账单里的原始商品描述（用户/外部数据），不改写。
- 需要在字段标签上统一，但不能把用户备注当文案重写。

### 1.10 币种 / 货币 / 金额单位

- **币种**（49 条）是账本/账目维度（CNY/USD）；
- **货币**（23 条）多出现在“多币种”相关说明；
- **金额单位/最小单位/分**是技术/边界说明，普通用户文案应避免“最小单位”而用“金额格式/小数位”。
- 建议：产品对象统一“币种”；“货币”只在解释概念时使用，不强制全站替换。

### 1.11 同步 / 离线 / 已保存 / 待确认 / 已入账

| 术语 | 真实含义 | 冲突 |
|---|---|---|
| **同步** | 与服务端交换数据；不是导入 | 常与“导入”混用 |
| **离线** | 本地可继续查看/操作，联网后同步 | 文案需说明“哪些操作会排队、哪些不可用” |
| **已保存** | 数据已写入（可能只是草稿/本地） | 与“已入账”不同 |
| **待确认** | 尚未最终入账/需要用户确认 | 与“已保存”不同 |
| **已入账** | 已成为正式账目 | 与“已保存”混用会误导财务结果 |

**建议方向**：状态词必须区分“本地已保存/待同步/已入账”；涉及离线时保留队列、失败、重启后不丢数据的说明。

### 1.12 历史 / 动态 / 事件 / 变更记录 / 操作记录

- **历史**：账本历史页/生命周期。
- **动态**：成员活动摘要（谁改了什么）。
- **事件**：内部历史记录类型（成员加入、交易修改等）。
- 用户可见处建议统一“历史/变更记录”；“事件”只在需要区分具体类型时使用。不要改历史正文与事实。

### 1.13 账号 / 用户 / 用户名 / 昵称 / 账号编号

- **账号**：登录与数据归属主体；**用户**是泛称。
- **用户名**：登录名（可能不可改）；**昵称**：显示名（可改）；**账号编号**：对外可读编号；**用户 ID**：内部标识，不应直接展示给普通用户。
- 现有“个人资料”中同时出现这些字段，建议保留字段本身，删除“昵称是什么/用户名有什么作用”的常识解释。

### 1.14 公告 / 更新 / 通知 / 提醒 / 消息

- **公告**：软件更新公告/重大公告；历史公告不改写。
- **更新**：版本升级/软件更新。
- **通知**：系统推送的类别（如重复提醒、预算提醒）。
- **提醒**：功能性提示（重复提醒等）。
- **消息**：留言板/站内消息。
- 建议保留区分；“软件更新”是产品页名，不应与“更新日志”混用。

### 1.15 OCR / 识别 / 转写 / 核对 / 草稿 / 候选

- **识别/OCR**：从图片/文件中提取文字。
- **转写**：语音→文字。
- **解析**：文字→字段（用户不必看到这个词）。
- **核对/草稿/候选**：尚未入账的状态。
- 用户可见处避免“解析/字段/类型枚举/关键字段/批次”等技术词，除非在诊断页。

## 2. 需要统一但可低风险处理的词

| 现状 | 建议 | 风险 |
|---|---|---|
| 储存 / 存储 | 统一“存储” | 低 |
| 付款方式 / 支付方式 | 统一“支付方式” | 低 |
| 协作者 / 成员 | 账本内统一“成员” | 低（若“协作者”是品牌用语则保留） |
| 重复账目 / 重复交易 | 功能名统一，候选状态用“疑似重复” | 中，需产品确认 |
| 历史页“变更了成员 这本账” | 改成自然句 | 低，但要覆盖四类成员事件 |
| 历史未知 key 英文（如 joined） | 补中文标签，未知 key 不上屏 | 中，需 API 测试 |
| “导出账目与数据维护” | 拆成两个入口名 | 低，但涉及 UI 结构 |

## 3. 不能为了统一而合并的词（明确保护）

1. **删除 ≠ 永久删除 ≠ 注销 ≠ 归档**：生命周期不同，可恢复性不同。
2. **恢复 ≠ 撤销**：恢复是还原数据/访问，撤销是撤回操作。
3. **恢复码 ≠ 恢复凭证**：账号恢复 vs 归档账本恢复。
4. **账本 ≠ 账单**：记账空间 vs 导入文件。
5. **重复提醒 ≠ 重复检测**：记账时轻提示 vs 全账本扫描。
6. **已保存 ≠ 已入账**：持久化 vs 正式进入账务。
7. **同步 ≠ 导入**：数据交换 vs 文件导入。
8. **用户名 ≠ 昵称 ≠ 账号编号 ≠ 用户 ID**。
9. **分类 ≠ 标签**。
10. **交易备注/分类名/用户名/OCR 原文/语音转写 ≠ 产品文案**，不进入自动改写。

## 4. 留给产品所有者/Codex 的决定

- “账目/交易/记录/明细”哪一个是用户主词；是否按页面角色分层使用。
- “重复交易/重复检测/疑似重复/重复账目”的最终功能名与候选状态名。
- 删除/恢复能力的真实边界，以及删除确认句的最终说法。
- “恢复码/恢复凭证”是否改名（不建议合并）。
- “协作者”是否为品牌用语；“付款方式”是否全量替换。
- “the free, open ledger”是否为品牌标语。
- 历史页是否保留“动态”叫法，还是统一“变更记录”。

## 5. 使用方式

Codex 修改前应：

1. 在 CSV 中按“术语命中”定位所有同词出现处；
2. 先判断它属于哪个业务对象/状态，再决定是否替换；
3. 对安全/财务词，逐条对照审查报告第 8 节；
4. 修改后全局搜索旧词，避免只改标题；
5. 更新本清单中“仍有冲突”的条目标记，不删历史记录。

## 6. 二次确认结论（2026-10-23）

本轮在真实代码与用户路径上再次确认，以下判断不变：

- **账本/账目/记录/交易/明细**：按业务对象区分，不合并；历史页和导入页优先用“账目”指一笔可恢复的记录。
- **删除/移除/清理/弃置/永久删除/注销**：后果不同，不能统一成“删除”；尤其是账号注销、账本归档、导入目标删除、游客本机清理。
- **保存/提交/确认/写入**：按用户动作阶段区分；“保存”是本地或表单动作，“入账/写入账本”是服务器确认后的结果。
- **重复交易/疑似重复/重复账目**：重复检测页保留“疑似、非结论”的含义，不改成“重复交易已确认”。
- **支付方式/渠道**：用户界面以“支付方式”为主，账单原文中的“渠道”只在引用原文时保留。
- **恢复码/恢复凭证**：恢复码用于找回账号，恢复凭证只用于恢复符合条件的归档账本；**不可合并**。
- **内部词处理**：高风险路径不再使用墓碑、UTC、回执、幂等、账本锁、A/B；诊断/高级页面可以有技术说明，但不能混入普通用户路径。
