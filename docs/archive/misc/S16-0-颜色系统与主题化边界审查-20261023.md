# S16-0 · 颜色系统与主题化边界审查（2026-10-23）

> **这是一次独立的只读审查，不是 S16-A 视觉重构，也不是主题功能开工。**
> 基线：`s15-complete` / `32e6be8`（2026-10-23，工作区 clean）；当前生产 `1.15.05 / 35ff89f`。
> 本轮没有修改任何 UI、CSS、设计令牌、图表颜色或运行时代码；只新增本报告并更新文档索引。
> 报告中的 **【事实】** 来自当前代码/静态计算；**【建议】** 是技术建议；**【待定】** 是必须由所有者或视觉设计决定的产品选择。

## 0. 一句话结论

**【事实】** Libevra 已经有一套可靠、克制、可继续复用的语义底色：19 个 `--color-*` 令牌把画布、卡片、正文、次要文字、边框、品牌强调、危险/警告、遮罩和投影分开了；绝大多数页面确实通过 Tailwind 语义类使用它们，而不是到处写 HEX。这是 S16 主题化最重要的资产。

**【建议】** 但**现在的代码还不能直接乘以“浅色/深色 × 预设色盘”**。真正的阻塞点不是令牌数量，而是四类“语义还没有被单独建模”的地方：

1. **前景色没有令牌**：`text-white` 被当作“品牌色上的文字”使用（静态扫描 103 处），一旦品牌色变成黄/橙/浅紫，白字会不可读。主题系统必须新增 `on-brand` 一类的前景角色。
2. **数据颜色把“身份”借给了排序**：环形图的分类颜色按当前金额排名取 `categoricalColor(index)`，同一分类换个月份可能换颜色；主题化之前必须先修“分类 → 颜色”的稳定映射。
3. **用户数据和品牌数据混在一起**：标签颜色既是 `#RRGGBB` 用户数据，又被 `CATEGORICAL_COLORS` 当作可选色板；标签色不能随主题重染，但当前选中标签的白色文字在 8 个色板中有 5 个达不到 4.5:1。
4. **动态特殊视觉没有独立层**：海浪 4 层色、明细页白色玻璃、热力图色阶、图表 SVG 都是硬编码在 JS/CSS 里的值，不能自动跟随 CSS 变量。

**【建议】** 最小改造方向是“**三层令牌 + 两组覆盖 + 数据/特殊视觉单独映射**”，而不是在组件里加 `dark:` 分支，也不是现在先定死 7 套色值。推荐：多分类图表用**方案 A（固定分类色，按模式校正明度）**，热力图/单指标用**方案 C（主题色系）**；方案 B 只作为所有者的可选产品实验，不作为默认。

### 2.2 仍然成立的结论

- `ink` / `muted` / `line` / `surface` / `canvas` 的职责成立，不应为了主题化重命名；用户明确要求避免与这些名字职责重叠的新命名。
- `category-ink`、`accent-ink`、`chart-rule` 虽然都是灰绿/绿系，但职责不同：分类图标、图表文字、图表线条。**不能合并成一个 token。**
- 状态色（danger / warn）必须保持独立语义，不能整体变成品牌色。
- 图表分类色和用户标签色都属于“数据身份”，不是品牌色。

### 2.3 已经过期的结论

- **“warn 令牌未使用”已过期**：当前 `warn-dark` 29 次、`warn-soft` 12 次；冲突/提醒界面已实际使用。
- **旧使用量全部过期**：旧文档 `muted 295`、`ink 170`、`brand 56`、`danger-soft 19`；当前分别是 718、392、161、27。
- **旧文档把 `accent-ink` 的 2.67:1 当作当前问题已过期**：当前 `#5f7268` 在 surface 上约 5.13:1，已修复；但历史问题应保留记录，不能冒充当前缺陷。
- **旧文档把“图表 8 色永远独立”当作不可讨论的结论**：这是 1.10 的实现事实，不是产品所有者今天的最终决定；S16 正在重新考虑方案 A/B/C。报告只比较方案，不修改。
- **旧文档的 `docs/开发过程记录/颜色清单.md` 路径已不存在**：`index.css` 与 `theme.ts` 的注释仍指向旧路径，属于维护性技术债，S16-A 可顺手改注释，但本轮不改。

## 3. 当前颜色按语义分类【事实 + 建议】

### 3.1 分类总表

| 大类 | 令牌/值 | 是否随模式 | 是否随色盘 | 是否必须独立语义 | 建议 |
|---|---|---|---|---|---|
| 基础中性 | `canvas` / `surface` / `ink` / `muted` / `line` | ✅ 必须 | ❌ 不应 | ✅ | 只换明暗色阶，不染色 |
| 品牌强调 | `brand` / `brand-dark` / `brand-soft` / `on-brand`（待新增） | ✅ 必须 | ✅ 必须 | ✅ | 色盘的核心映射 |
| 图表界面 | `accent-ink` / `chart-rule` | ✅ 必须 | ⚠️ 建议不随色盘 | ✅ | **建议降为“图表中性界面色”**，避免换主题后图表文字/网格变彩 |
| 分类标识 | `category-ink` | ✅ 必须 | ⚠️ 建议由色盘派生但必须保证对比度 | ✅ | 与品牌同族，但独立 token |
| 状态 | `danger*` / `warn*` | ✅ 明度可调 | ❌ 不应 | ✅ | 红/琥珀语义固定；深色只调明度/软底 |
| 交互效果 | `overlay*` / 阴影 | ✅ 必须 | ❌ 不应 | ✅ | 深色需独立投影/遮罩策略 |
| 数据分类 | `CATEGORICAL_COLORS` 8 色 | ✅ 明度校正 | ⚠️ 方案 A/B/C 待定 | ✅ | 多分类建议独立固定 |
| 数据强度 | `HEAT_COLORS` 5 档 | ✅ 必须 | ⚠️ 可做主题色系 | ✅ | 建议方案 C，但必须保证每档前景对比 |
| 用户标签 | 用户 `#RRGGBB` | ❌ 不改存储色 | ❌ | ✅ | 只处理显示前景/描边，不重染 |
| 海浪 | 4 层色 | ✅ | ✅ | ✅ 特殊 | 色可换，几何/动画不可换 |
| 明细页玻璃 | `rgb(255 255 255 / .14)` | ✅ | ❌ | ✅ 效果 | 改为模式相关效果 token，不做色盘映射 |
| QR | 纯黑/白 | ❌ | ❌ | ✅ | 绝对保持黑白 |
| 品牌字标/白字 | `text-white` / `color:white` | ⚠️ 语义上应改 | ✅ 由前景色决定 | ✅ | 必须有 `on-brand` 等前景角色 |

### 3.2 必须新增的前景角色【建议】

这是当前主题化最大的“隐藏硬编码”：`text-white` 103 次。它不是错误；在绿色 `#55997a` 上白字视觉也成立。但主题化后它不再可靠：

- 黄色/橙色色盘上白字对比度很低；浅色品牌填充需要深色文字；
- 危险/警告填充也需要明确前景；
- 深色模式下“品牌填充”可能变亮或变暗，不能固定白色。

**建议新增（不是现在实现）**：

| 角色 | 用途 | 为什么不能复用现有 token |
|---|---|---|
| `on-brand` | 品牌填充上的文字/图标 | `brand` 是背景，`ink` 是页面正文；`on-brand` 是随色盘/模式变化的前景 |
| `on-danger` / `on-warn` | 状态填充上的文字（如需要） | 状态色明度在深色模式可能变化，白字不一定合格 |
| `on-inverse` | 深色/高对比浮层上的文字 | 避免在组件里写 `text-white` |

**不建议**为了这些新增而重命名 `brand`、`ink`、`muted`；也不要创建 `primary`、`secondary` 之类与既有 `brand`/`muted` 职责重叠的名字。新增名字只表达**现有体系没有表达的角色**。

## 4. 明暗模式影响矩阵【技术建议】

| 颜色组 | 浅色模式 | 深色模式 | 说明 |
|---|---|---|---|
| `canvas` / `surface` | 近白 / 纯白 | 两档深灰/墨色 | 不能简单反相；画布与卡片必须保持层级 |
| `ink` / `muted` / `line` | 深墨/中灰/浅线 | 浅文字/中浅灰/深线 | 文字对比度目标按 WCAG AA；线需兼顾非文本 3:1 |
| `brand` / `brand-dark` / `brand-soft` / `on-brand` | 色盘浅色变体 | 色盘深色变体 | 同一色盘的“模式”不是把 HEX 调暗；需专门设计 |
| `accent-ink` / `chart-rule` | 中性深灰绿/浅灰绿 | 中性浅灰/深灰 | 建议不随色盘；否则图表文字会随之变色 |
| `danger*` / `warn*` | 语义红/琥珀 | 提高明度或换深软底 | 色相不变，只调明度/透明度 |
| `CATEGORICAL_COLORS` | 8 个中间明度色 | 8 个更适合深底的颜色 | 方案 A 下也**必须**做深色版；不能直接复用浅色 HEX |
| `HEAT_COLORS` | 浅→深 | 深→浅或低亮→高亮 | 热力图色阶必须保持单调、每档可区分 |
| 用户标签 | 任意用户色 | 任意用户色 | 不重染；只调整文字/描边/底色透明度 |
| 海浪 4 层 | 品牌绿色阶 | 深色/低亮度色阶 | 形状/波动/速度不变，只换 4 个层色 |
| `overlay*` / 阴影 | 墨色透明度 | 深黑透明度 | 白底阴影与深底阴影不是同一套 |
| QR | 黑/白 | 黑/白 | 绝不随主题 |
| 明细页玻璃 | 白色 14% | 视设计换成深色/亮色玻璃 | 保留“玻璃”效果，不直接把白 alpha 改主题色 |
| 浏览器控件/滚动条 | `color-scheme: light` | `color-scheme: dark` | 必须显式设置，否则原生控件不协调 |

**必须同时验证“深色 × 每套色盘”**，而不是只测默认绿色深色。尤其是按钮、危险/警告按钮、标签选中态、图表文字、热力图前景、输入框占位符和焦点环。

## 5. 色盘切换影响矩阵【技术建议】

| 颜色组 | 换色盘是否变化 | 备注 |
|---|---|---|
| 基础中性（canvas/surface/ink/muted/line） | ❌ | 色盘不应改变页面骨架 |
| `brand` / `brand-dark` / `brand-soft` / `on-brand` | ✅ | 这是色盘的核心 |
| `category-ink` | ⚠️ 建议变化但需检查对比度 | 分类圆标可以跟品牌同族 |
| `accent-ink` / `chart-rule` | ⚠️ 建议不变 | 图表文字/网格保持中性，避免数据阅读被氛围干扰 |
| `danger*` / `warn*` | ❌ | 语义色固定；深色模式只调明暗 |
| 分类 8 色 | ⚠️ 按方案 | A：不变；B：每色盘一套；C：部分变化 |
| 热力 5 档 | ⚠️ 按方案 | 建议 C：每色盘一套连续色阶 |
| 用户标签色 | ❌ | 用户数据，不重染 |
| 海浪 4 层 | ✅ | 每色盘一套，仅颜色 |
| QR | ❌ | 绝对 |
| 遮罩/阴影 | ❌ | 中性效果，只随模式 |
| 焦点环 | ✅（建议） | 随强调色但必须有足够对比度；不能只靠 `brand-soft` |

**每套色盘的最低验收**：`brand`/`on-brand` 至少满足 4.5:1（小字）；`brand-dark` 在 `surface` 上至少 4.5:1（文字链接）；状态填充前景至少 4.5:1；焦点环与相邻底色至少 3:1；并且要通过色觉差异模拟，不能只测普通视力。

## 6. 绝对不应直接主题化的颜色【建议】

1. **QR 黑色/白色**：扫码可靠性优先。`QrCodeView.tsx` 的黑色模块/白色底不应跟随色盘或深色模式。
2. **用户标签存储色**：`#RRGGBB` 是用户数据；API 已允许任意合法 HEX（`packages/shared/src/ledger.ts:207-209`）。不得把用户红色标签“主题化成紫色”。
3. **分类数据身份的色相关系**：即使采用方案 C，也不能把 8 个分类直接按主题批量旋转色相；多分类图表的可区分性属于数据语义，不属于品牌氛围。
4. **danger / warn 的语义色相**：危险不能变品牌绿、警告不能变紫；可以调明度/软底，不可改语义。
5. **支出/收入的数据语义**：当前图表用分类色第 4 位（红）与第 1 位（绿）表示支出/收入。这个语义不能被色盘改写成“主题色”。是否保留红/绿、是否改用其他 CVD 安全组合，是所有者决策。
6. **海浪几何、波形、动画速度、交互**：颜色可映射，形状/动画不可随主题变化。
7. **阴影用墨色**：这是“同一束光”的视觉逻辑，不应随色盘染色；深色模式单独设计投影。
8. **明细页玻璃高光**：这是透明效果，不是品牌色；应做成效果角色，而不是把白色直接替换成主题色。

## 7. 海浪与动态视觉【事实 + 建议】

### 7.1 事实

- `components/OceanBackdrop.tsx` 定义 `OCEAN_COLORS = ["#3f7059", "#4f8a6d", "#6aa78a", "#96c4ac"]`；四层 SVG path 由 `oceanPath(layer, p, elapsed)` 生成。颜色和几何/动画代码在同一个组件里，但**颜色只是四个 fill 值**。
- `apps/web/src/detail-motion.css` 的“头部动态”使用 CSS 变量 `--p` 做布局/透明度/位置插值；`background: rgb(255 255 255 / .14)` 是玻璃效果；**没有发现运行时颜色插值**。
- `DetailPage` / `TabPageHeader` 的头部底色是静态 `bg-brand`，文字是 `text-white`；没有逐帧计算颜色。
- 热力图格子颜色来自 `heatColor(level)` 的 inline `backgroundColor`；图表 SVG 使用 `categoricalColor()` 常量；标签使用数据库中的 `tag.color` 作为 inline 背景。
- `QrCodeView` 的黑色/白色是模块常量。
- 没有发现 canvas 绘制的主题色；动态颜色主要集中在 SVG fill、CSS 背景和 inline style。

### 7.2 建议：颜色与几何彻底解耦

**【建议】** 把海浪 4 层色提升为特殊视觉令牌：

```css
/* 示意，不包含最终色值 */
:root {
  --ocean-layer-1: …;
  --ocean-layer-2: …;
  --ocean-layer-3: …;
  --ocean-layer-4: …;
  --ocean-ink: …; /* 海浪区域内文字，若未来需要 */
}
```

- `OceanBackdrop` 只把 `fill` 改为 `var(--ocean-layer-N)`；`oceanPath`、层数、相位、速度、CSS 动画全部不动。
- 色盘/模式只覆盖这 4 个变量；不在组件里 `if (theme === ...)`。
- 若文字会落在海浪上，必须验证每层/每模式的前景对比度；当前四层上的白字约为 **5.72 / 4.05 / 2.80 / 1.95**，只有第一层稳定过 AA，因此**不要把正文放到第 2–4 层**。
- 明细页玻璃建议改成 `--glass-highlight` 之类的效果角色（可随模式调透明度），不参与色盘映射；几何插值仍只读 `--p`。
- 给海浪加一个“几何快照测试”：只改 4 个 fill 色时，path 的 `d` 必须逐字不变；防止未来主题化误改形状。

## 8. 图表三方案对比【建议 + 待定】

### 8.1 先修正一个独立于主题的数据颜色问题【事实】

`CategoryDonut.buildSlices()` 在 `components/charts/CategoryDonut.tsx:168-192` 用当前 `positive` 数组的下标取色；而 `apps/api/src/routes/stats.ts:227-236` 按金额降序返回分类。结果是：

> **同一个分类，金额排名变化时颜色会变化；不同月份/不同范围下，用户记忆中的“餐饮是红色”会失效。**

这不是主题系统造成的，但会直接影响 A/B/C 三方案的可解释性。无论选哪种方案，都应先改为**按稳定的 categoryId（或分类的固定排序/名称）映射颜色**；`其它` 使用单独的固定色；颜色和形状同时绑定稳定身份。

### 8.2 三种方案对比

| 维度 | A. 完全独立 | B. 主题协调 | C. 部分主题化 |
|---|---|---|---|
| 8 分类可区分性 | 高（现有 8 色专为分类设计） | 中低（受同一色盘约束，容易变得相近） | 取决于哪部分主题化；多分类仍用独立色 |
| 浅色/深色 | 需维护两套明度 | 需维护 7×2 套 | A 的部分两套 + C 的部分每色盘两套 |
| 对比度 / 色觉差异 | 可独立验证，风险可控 | 每套都要重新验证，工作量最大 | 热力/单指标风险可控；分类部分同 A |
| 同一分类跨页面一致性 | 最高（固定映射） | 中（同一主题内固定，但主题间变化） | 高（分类仍固定） |
| 品牌氛围 | 弱（图表可能显得“外来的”） | 强 | 中等 |
| 实现/维护成本 | 低 | 高 | 中 |
| 用户学习成本 | 最低 | 高（换主题换色义） | 低 |
| 对当前代码侵入 | 小（只加 mode 变量） | 大（每色盘一套 8 色 + 校验） | 中（热力/单系列走色盘） |
| 建议 | ✅ 多分类默认 | ⚠️ 可选实验 | ✅ 热力/单指标/强调数据 |

### 8.3 具体组件建议

| 组件/场景 | 当前实现 | 建议 |
|---|---|---|
| `CategoryDonut` 环形图（8 分类） | 8 色按金额排名取色，形状 4 种 | **方案 A**；先修 categoryId 稳定映射；`其它` 固定色；保留形状/直接标签 |
| `Legend` 图例 | 颜色+形状 | 与环形图同一映射；不要另算一套 |
| `TrendChart` 趋势图（支出/收入） | `categoricalColor(3)` 红 / `categoricalColor(0)` 绿 | **独立语义数据色**（支出/收入），不要借用分类色；若单系列再允许方案 C 的品牌强调 |
| `SummaryPanel` 汇总条 | 同上红/绿 | 与趋势图共用语义数据色 |
| `CalendarHeatmap` 热力图 | 5 档固定色阶，`level>=3` 白字 | **方案 C**：色盘派生 5 档，必须每档检查前景；或方案 A 固定色阶但深色重做 |
| 单指标进度/强调数据 | 品牌色/分类色 | **方案 C**：品牌强调色系；但只用于无分类含义的场景 |
| 用户标签 | 复用 `CATEGORICAL_COLORS` 作为可选项 | 与图表解耦；标签色不随主题；选中态前景按对比度计算 |
| 图表文字/网格 | `accent-ink` / `chart-rule` | 中性、随模式；**建议不随色盘** |
| 分类标签（tag）在明细页 | 用户色背景 + 白字 | 白字在 8 个标签色中 5 个不达 4.5:1；需要自动前景或描边/底色方案 |

**结论【建议】**：

- **多分类图表用 A**，保证数据身份和可访问性；
- **热力图、单指标进度、单系列趋势用 C**，让品牌氛围体现在“强调数据”而不是“类别身份”；
- **B 不作为默认**。如果所有者坚持要“每套色盘都有自己的 8 色图表”，那应作为单独的产品实验，先做 7 套 × 2 模式的色觉/对比度验收，并接受跨主题颜色学习成本。
- 无论 A/B/C，都先修“按排名取色”的现有问题；否则主题化会把一个已有数据可读性问题放大。

## 11. 推荐的最小实现架构【建议】

### 11.1 总体模型

```text
外观偏好（light / dark / system） ──► 解析后的 mode
预设色盘（green / …） ─────────────► palette
        mode × palette ──► 一组 CSS 自定义属性
                              ├─ 基础中性（mode）
                              ├─ 品牌强调（palette × mode）
                              ├─ 状态（mode，色相固定）
                              ├─ 交互效果（mode）
                              ├─ 图表界面/数据（mode；数据策略另定）
                              └─ 海浪/特殊视觉（palette × mode 或固定）
```

**原则**：组件继续写 `bg-surface` / `text-ink` / `border-line` 这类语义类；不在组件里判断 `theme === "purple"`，也不使用大量 `dark:` 变体。

### 11.2 CSS 组织（示意，不含最终色值）

```css
/* 1. 默认：绿色 + 浅色，继续作为编译期默认值 */
@theme {
  --color-canvas: #fafcfb;
  --color-surface: #ffffff;
  /* … 现有 token 不变 … */
  --color-brand: #55997a;
  --color-on-brand: #ffffff; /* 新增：前景角色 */
}

/* 2. 模式覆盖：只改变量值，不改工具类 */
:root { color-scheme: light; }
:root[data-mode="dark"] {
  color-scheme: dark;
  --color-canvas: …;
  --color-surface: …;
  --color-ink: …;
  --color-muted: …;
  --color-line: …;
  --color-danger-soft: …;
  --color-overlay: …;
}

/* 3. 色盘覆盖：只覆盖强调组和特殊视觉 */
:root[data-palette="purple"] {
  --color-brand: …;
  --color-brand-dark: …;
  --color-brand-soft: …;
  --color-on-brand: …;
  --ocean-layer-1: …;
  --ocean-layer-2: …;
  --ocean-layer-3: …;
  --ocean-layer-4: …;
}

/* 4. 色盘 × 深色：只写真正需要不同的组合 */
:root[data-palette="purple"][data-mode="dark"] {
  --color-brand: …;
  --color-on-brand: …;
  --ocean-layer-1: …;
}
```

**注意**：

- 这些覆盖应放在 `@layer base`/无层叠层，确保高于 `@theme` 默认层；具体层序由 S16-A 实测确定。
- 不建议给每个组件加 `dark:` 前缀；`data-*` 属性放在 `<html>`，CSS 变量自动级联到所有 Tailwind 工具类。
- 不建议为 7 套色盘复制整份 19 token；只覆盖强调组、ocean、必要时状态软底/图表色阶。基础中性按模式只需一套。
- 新增色盘只增加一个 CSS 块 + 一个元数据项；组件不需要改。

### 11.3 新增 token 的最小集合（优先级）

| 优先级 | token | 原因 | 是否必须现在决定 |
|---|---|---|---|
| P0 | `on-brand` | 103 处白字 + 黄/橙/浅紫主题的必要前景 | 是（架构必需） |
| P0 | `on-danger` / `on-warn`（如填写按钮需要） | 状态填充前景不一定白 | 视设计 |
| P1 | `chart-1…8` 或图表 CSS 变量 | SVG 可跟随主题；替代 JS 硬编码 | 图表方案确定后 |
| P1 | `heat-0…4` | 热力图色阶/模式/色盘 | 热力图方案确定后 |
| P1 | `ocean-1…4` + `on-ocean` | 海浪颜色与文字 | 是（海浪品牌视觉） |
| P1 | `focus-ring` | 当前品牌软色焦点环 1.08:1，不可用 | 是（无障碍） |
| P2 | `line-strong` | 输入框边界 1.20:1，非文本对比不足 | 视组件规范 |
| P2 | `data-expense` / `data-income` | 移除支出/收入借分类色 | 是（数据语义） |
| 不建议现在加 | `surface-raised`、`surface-muted` 等 | 深色是否需要多级表面尚未设计；先别把 token 数量膨胀 | 等视觉设计 |

**不要**新增 `primary`、`secondary`、`accent` 等与 `brand`/`ink` 竞争的名字；也不要重命名现有 `ink`/`muted`。新增名字只填“现有语义没覆盖的角色”。

### 11.4 运行时切换与无闪烁

**【建议】**：

1. 存两个偏好：`appearance = "light" | "dark" | "system"`、`palette = "green" | …`；**存偏好，不存解析后的 mode**。
2. 在 `index.html` 的 `<head>` 中、应用 CSS/JS 之前放一个最小内联脚本：读取 localStorage → 解析 `system` 的 `matchMedia("(prefers-color-scheme: dark)")` → 设置 `<html data-mode="light|dark" data-palette="…">` + `style.colorScheme`。这样第一帧就是正确颜色。
3. React ThemeProvider 只负责：读取偏好、写入 `<html>` 属性、监听系统变化、持久化；不需要把颜色值传进组件。
4. 监听 `matchMedia` 仅在 `appearance === "system"` 时生效；用户选 light/dark 后忽略系统变化。
5. 可选：监听 `storage` 事件同步其他标签页；不必引入状态管理库。
6. 若有未来 SSR/预渲染，改为 cookie/首屏内联变量；当前 SPA 可先用内联脚本。

**避免闪烁的验收**：冷启动、刷新、切换模式、切换色盘、系统主题变化、从设置页返回首页，均不能出现错误颜色的首帧。

### 11.5 JS / SVG / 动态颜色

| 场景 | 建议 |
|---|---|
| 图表 SVG | `fill={var(--chart-1)}`、`stroke={var(--chart-rule)}`；不要在模块顶层冻结 HEX |
| 热力图 | `style={{ backgroundColor: "var(--heat-3)" }}`；或使用 CSS class；不要在 JS 里按主题选色 |
| 标签 | 保留用户 HEX；用 `tagInk(hex)` 计算前景（WCAG 相对亮度），或统一使用“浅底/描边 + ink 文字”的标签样式 |
| 海浪 | `fill="var(--ocean-N)"`；不改 path/动画 |
| 明细玻璃 | `background: var(--glass-highlight)`；只随模式 |
| QR | 固定黑/白，不读取主题 |
| 需要真实色值（导出、canvas、第三方） | 通过 `getComputedStyle(document.documentElement).getPropertyValue("--color-…")` 读取；在模式变化后重算；当前没有 canvas 主题色需求 |

### 11.6 新色盘接入清单

**【建议】** 每新增一套色盘，需要：

1. 一个 `[data-palette="…"]` 块：`brand`、`brand-dark`、`brand-soft`、`on-brand`、`category-ink`（如需要）、`ocean-1…4`；
2. 一个深色块（或 `[data-mode="dark"]` 组合）：对应深色值；
3. 图表策略所需的 8 色/5 档（若采用 B/C）；
4. 自动对比度测试：`on-brand` vs `brand`、`brand-dark` vs `surface`、`text` vs `soft`、focus ring vs canvas、每个 chart/heat 前景；
5. 真实浏览器抽查 320/390/1440 的首页、记账、分析、标签、设置、弹层、海浪；
6. 更新色盘清单文档和截图，但**不需要改组件**。

## 13. S16-B 增量审查（2026-10-24）

> 本节是 S16-0 报告的增量更新，不替代 §1–§12 的原始证据。原报告的“当前”以 2026-10-23 为准；本节核对的是 1.16.03 生产代码（HEAD `26e40a8`，工作区 clean）中与 S16-B 直接相关的事实，并把实现前的技术准备单独整理为《S16-B 主题系统实施准备清单》。

### 13.1 一句话结论

**当前系统是“单一浅色外观 + 单一品牌绿色”的语义 token 体系，不是一个主题系统。**
19 个 `--color-*` token 已经让大多数页面不再散落色值，但 token 只有“浅色一套值”，没有明暗变体、没有前景色角色、没有主题持久化/预渲染，也没有图表、海浪、PWA 的主题数据源。S16-B 的正确做法不是给现有组件加 `dark:` 分支，而是先把“基准 / 强调 / 状态 / 数据 / 特殊”五类角色补齐，再在 `html[data-mode]` × `html[data-palette]` 两个独立轴上赋值。

### 13.3 完整语义分类（A–F）

| 类别 | 现有角色/来源 | 是否随色盘变 | 是否需要明暗变体 | 结论 |
|---|---|---|---|---|
| **A. 品牌与交互** | `brand`、`brand-dark`、`brand-soft`、`category-ink`、`text-brand`、`bg-brand`、链接、选中态、focus | 是（强调轴） | 是 | 需要成对的 `on-brand`/`on-brand-muted`；主按钮/页头白字必须由 token 决定，不能固定白 |
| **B. 基础界面** | `canvas`、`surface`、`ink`、`muted`、`line`、`overlay-soft`、`overlay`、shadow | 否（基准轴） | 是 | 深色不是反相；surface/line/shadow 需独立层级，hover/selected/disabled 需补 |

### 13.4 角色缺口与冲突（S16-B 前置问题）

| 优先级 | 角色 | 当前问题 | 建议 |
|---|---|---|---|
| **P0** | `on-brand` / `on-brand-muted` | 主按钮/页头使用固定白字；品牌绿 `#55997a` 上白字约 3.37:1，不达 AA 小字 | 由色盘/模式定义前景；必要时改用 `brand-dark` 作填充或调整品牌填充 |
| **P0** | `focus-ring` | 当前聚焦环常用 `brand-soft`，对 canvas 对比度约 1.08:1，几乎不可见 | 独立焦点环 token，至少 3:1；键盘/读屏可感知 |
| **P0** | `line-strong` | 输入框默认 `line` 对 surface 约 1.2:1，非文本边界不足 | 增加强边框 token；表单控件必须有可感知边界 |
| **P0** | `success*` / `info*` | 成功/信息借 brand，主题色一变语义就变；无 token | 增加状态色与前景，语义稳定，只随明暗微调 |
| **P0** | 图表数据色 | `EXPENSE_COLOR = categoricalColor(3)`、`INCOME_COLOR = categoricalColor(0)` 把财务语义绑在分类槽位上 | 抽 `data-expense`/`data-income`/`data-transfer`；分类色按数据项索引，不绑定业务 |
| **P0** | 热力图前景 | `text-white` 在部分热力档对比不足 | `heat-0…4` + 自动前景或分档前景 token |
| **P1** | `chart-grid` / `chart-axis` | 现用 `chart-rule`/`accent-ink`，缺少明确命名；网格过亮/深色下可能刺眼 | 拆成 chrome token，明暗各自定义；非文本线不强制 3:1 但需可辨 |
| **P1** | 标签前景 | 选中标签 `tag.color` 背景 + 固定白字，任意用户色可能不达 AA | 保留用户色；用相对亮度选黑/白前景，或统一“浅底+描边+色点” |
| **P1** | `ocean-1…4` / `on-ocean` | 4 个 hex 写死在组件；文案白色落在第一层绿上 | token 化；每套色盘/模式给 4 层与前景；几何 path 完全不动 |
| **P1** | PWA 主题色 | `index.html` 无 `theme-color`；无 manifest/浏览器 UI 主题 | 动态设置 `<meta name="theme-color">`；PWA manifest 属 S17-E |
| **P2** | 深浅色切换动画 | 无主题切换机制；将来直接切 CSS 变量会闪白 | 过渡只在 `prefers-reduced-motion: no-preference` 时启用；颜色过渡简洁 |
| **P2** | 禁用/hover/selected | 多数靠 opacity 或 brand-soft，缺少独立语义 | 先设计 role，不要每个组件各写一套灰 |

### 13.5 双维度主题模型（明暗 × 色盘）

S16-B 必须把两个维度正交：

```
外观 appearance: light | dark | system   （决定明暗基准轴）
色盘 palette:    green | red | orange | yellow | cyan | blue | purple
```

矩阵行为：

| token 组 | light + green | dark + green | light + red | dark + red |
|---|---|---|---|---|
| 基准（canvas/surface/ink/muted/line/shadow） | 只由 light 决定 | 只由 dark 决定 | 与 green 相同 | 与 green 相同 |
| 强调（brand* / on-brand / category-ink） | green 浅色值 | green 深色值 | red 浅色值 | red 深色值 |
| 状态（danger/warn/success/info） | 固定语义浅色值 | 固定语义深色值 | 不随 red 变 | 不随 red 变 |
| 数据（分类/支出/收入/热力） | 独立数据斜坡 | 独立深色斜坡 | 可保持独立（最多轻微协调） | 同左 |
| 海浪（ocean-1…4） | green 浅色层 | green 深色层 | red 浅色层 | red 深色层 |
| QR | 固定黑白 | 固定黑白 | 固定黑白 | 固定黑白 |
| 用户标签 | 用户原色 + 自动前景 | 同左 | 同左 | 同左 |

**默认保留 `#55997a` 品牌绿**，但默认绿色是否使用精确原值、还是为深色另调一档，由 Codex 设计后给所有者确认；本报告不决定最终色值。

CSS 组织建议（示意，不含最终值）：

```css
:root { /* light + green：现有 19 token 的向后兼容默认值 */ }

html[data-mode="dark"] { /* 基准、状态、数据、玻璃、阴影的 dark 值 */ }
html[data-palette="red"] { /* 强调 + 海浪的 red light 值 */ }
html[data-mode="dark"][data-palette="red"] { /* red dark 值 */ }
```

规则：
- 不再新增 `primary`、`secondary`、`accent` 等与 `brand`/`ink` 竞争的名字；新名字只补“现有语义没覆盖的角色”。
- 组件不写 `theme === "dark"` 分支，只消费 token；`data-mode`/`data-palette` 只出现在 `html`。
- 旧 19 个 token 名称保留；新增 `on-*`、`success*`、`info*`、`focus-ring`、`line-strong`、`data-*`、`heat-*`、`ocean-*`、`glass-highlight` 等角色。
- 默认值应让 1.16.03 的浅色绿外观视觉不变；主题系统的第一步是“可切换但默认零变化”。

### 13.6 运行时、持久化与无闪烁

**建议**（与 §11.4 一致，补充 S16-B 边界）：
1. 存储两个原始偏好：`appearance`、`palette`；不存解析后的 mode。
2. 在 `index.html` 的 `<head>` 内、应用 CSS 之前放最小内联脚本：读 localStorage → 解析 `system` 的 `matchMedia` → 设置 `<html>` 的 `data-mode`、`data-palette`、`style.colorScheme`、`meta[name=theme-color]`。
3. React 只负责设置页交互、监听系统变化（仅 `system` 时）、写偏好；颜色值不进入组件 props。
4. 刷新、重新登录、游客/登录切换、清除站点数据后都要恢复；账号级同步归 S16-E 决策，S16-B 先做设备级存储。
5. 验收必须包含首屏无错误主题闪烁、系统模式实时切换、减少动画偏好；不能只看截图。

### 13.7 图表与海浪专项（对 §7、§8 的增量）

- 图表仍应保持“颜色不是唯一信号”：现有 marker 形状机制应保留；深色模式要重新做明度顺序，不能把浅色 HSL 直接减亮。
- 当前支出/收入借用分类色，是一个**独立于主题的数据语义问题**；S16-B 应先把 `data-expense`/`data-income` 从 8 分类色中解耦，再讨论图表是否随色盘轻微协调。
- 分类图建议继续方案 A（固定可辨识分类色，chart chrome 随明暗）；热力/单指标建议 C；具体最终方案仍需产品/设计决定（原报告 §8/§12）。
- 海浪四层是“品牌视觉”而不是数据色：应随色盘和明暗改变，但必须保持四层顺序、对比和文字前景；路径函数、速度、层数、动画不改。当前 `OCEAN_COLORS` 写死在组件内，是 S16-B 前必须抽出的硬编码。
- 明细页玻璃白、QR、用户标签分别属于“只随明暗”“永不主题化”“用户数据”三种边界，不能统一当成品牌色。
