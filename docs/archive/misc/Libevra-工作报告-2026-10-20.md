### 1.1 两个文件夹，其实是同一个仓库的两个 worktree

| | A（桌面） | B（Documents） |
|---|---|---|
| 分支 | `s13-g` | `s14-integration` |
| 版本 | 1.13.15 | **1.14.20（=生产）** |
| 领先 `origin/main` | 57 提交 | 95 提交 |
| 关系 | `s13-g` = 共同祖先 + 1 个**纯文档**提交 | 包含 A 的全部代码 |

**关键判断**：`s14-integration` 已经把 `s13-g` 的代码全部包含，唯一的差别是 A 多一个文档提交。也就是说：

- 两个 Agent 不是"各开发一小部分"，而是**同一份代码在两个检出目录里，各自维护了一套'当前状态'**；
- 有一个约 10 万行代码的第三事实源（生产服务器）也参与其中。

### 1.2 证据：两套互相矛盾的"当前状态"

- 两份 `交接.md` 都写着"📌 当前状态（以此为准）"：A 说 1.13.15，B 说 1.14.20。
- 两份 `开发计划.md` **都叫 v3.4**，但 S15/S16/S17 定义互斥（A：S15=阅读与列表、S17=开源发布；B：S15=核心记账与识别、S17=正式公开发布）。版本号相同、内容相反——按版本号判断不出谁新。
- "当前状态的唯一出处"被声明了 **4 次**，指向 3 个不同文件；其中一处指向**已冻结**的 `版本记录（1.10-1.13）`。
- `开发过程记录/` 里 65 份文档有 **38 份 mtime 完全相同**（批量拷贝造成），连"看修改时间判断新旧"都失效。

### 1.3 一条真正会误导人的工具 bug

`tools/doc-audit.mjs` 第 35 行把路径写死成 **A 目录**。于是在 B 目录（1.14.20）执行 `pnpm check:docs` 时：

```
代码现状（ground truth）
  版本号：1.13.15          ← 实际是 1.14.20
  ⚠️ 版本记录（1.14）写 1.14.05，实际 1.13.15   ← 假阳性
```

而命令退出码是 **0**。它同时具备"假阳性"和"假通过"：Agent 每次"验证文档"，得到的都是另一个分支的现状，然后去"修正"，越改越乱。

### 1.4 `AGENTS.md` 本身过期约 6 周

它是唯一被自动注入的文件，却还在写：

- "本轮（S12-B 部署）"——S12-B 早已完成；
- "S13-I 与 S14 在不同 Worktree 并行"——S14 早已发布；
- 待办项编号指向的章节已改名。

同时它要求"首次接手"读 7 份文档 = **878 KB / 13,146 行 / 约 26.8 万 token**，是它自己写的 65,536 字节预算的 **13.7 倍**。读不完 → 复核 → 把结论写回文档 → 又多一份"当前状态" → 下次更不可信。**这就是"效率在变低、时间都花在核查上"的机制根源。**

### 1.5 生产源码不在 GitHub

`git ls-remote` 实测：GitHub 上只有 `main`（`e1b43cc`，2026-10-17）和几个旧 release 分支。**65 个 S13 提交 + 95 个 S14 提交只在本机**。服务器之所以是 1.14.20，是因为发布路径是"本机 `git archive` → 服务器"，**从不经过 GitHub**。

### 3.1 决策

保留 **桌面目录**（`记账程序v1`），删除另外两个 worktree。理由：

1. 真正的 `.git` 在那里（另两个只是 worktree）；

### 3.2 执行

1. `git bundle create --all` → **15.2 MB / 43 个 ref**（回滚保险）；
2. 删除 Codex 遗留 worktree 与 B worktree；
3. 在保留目录 `git checkout s14-integration`（**切分支，不是合并**）；
4. 验证：`APP_VERSION=1.14.20`、89 份 md、51 个迁移、dev 库 `migrate status = up to date`、依赖无变化（免重装）、Prisma 客户端重新生成；

### 3.3 两个过程中的意外（如实记录）

- **Windows 长路径**：`git worktree remove` 删目录时报 `Filename too long`（node_modules 深路径），注册已注销但目录残留。用 `\\?\` 长路径方式补删干净，数据无损失。
- **我自己的一次失误**：给 `.gitignore` 加 `!docs/恢复码.docx` 反而让这个**明文恢复码**被 `git add` 进仓库。发现后立即 `git rm --cached`、恢复忽略规则、**重写该提交**（当时尚未推送），并验证 `git ls-files` 与 `git log --all` 均无此文件、磁盘文件还在。这是当天唯一一次接近"不可逆风险"的操作，已闭环。

### 6.3 所以它能做到什么、不能做到什么

- ✅ **能**：区分"单笔详情 / 交易列表 / 未知"，因为这是**文本结构特征**（金额行、时间列、多行同构、关键词）；能给出可扩展的版式注册结构；能把单笔详情字段标准化；能在合成单笔样本上端到端跑通。
- ❌ **不能**：声称能准确识别你的真实微信/支付宝**交易列表**、BOA、银行流水。这些版式**没有真实样本**，Agent 在代码注释、fixture 命名和交接报告里都标了 `未验证`。

**这正是"没有截图也能做出东西"的原因：做的是框架 + 可解释特征 + 明确未验证标注，而不是编造识别率。** 报告里没有出现任何"识别准确率 xx%"的漂亮数字——因为没有真实样本就不该有。
