## 0. 一句话

概览页从“六个大数字 + 全展开筛选 + 六行卡片 + 页面底部确认区”压成“一行数字 + 一行短说明 + 四个状态 chip + 两层卡片 + 固定底部确认条”；分类联想复用语音的 `matchCategory`，只从**批次所属账本**的已有分类里匹配交易对象/备注，标「系统建议」并区分来源；「可导入」改用真实字段校验计数，不再把“未标记无效”当“写得进去”。

## 1. 六块分别怎么做的

### A. 顶部压缩（改了哪里、压到什么程度）

改动前（自上而下）：`InnerPage` 标题 + 一行半说明 → 六格统计卡（`本次识别 / 待核对 / 可直接导入 / 可能重复 / 已标记无效 / 可导入`，2 列 3 行）+ 一段说明 → 批次提示 → 全部筛选项 → 卡片列表。

改动后：

1. `InnerPage` 的 subtitle 只有一句：**「只核对有疑问的；确认前不写账本。」**（安全提示保留，不再另起一段）。
2. 统计卡第一行只放四个重点数字：**本次识别 / 待核对 / 疑似重复 / 可导入**（`dl` 一行，窄屏最多两行）。
3. 其余数字（未标记无效、已确认、已标记无效、你已核对过）与**统计口径说明**、批次存储说明一起收进同一张卡里的 `<details>详情与统计口径</details>`；收起时整块高度约一行数字 + 一行「详情」。「已确认」在详情里明确定义为“字段齐全、不需要逐笔核对”，并单独写清它不是「你已核对过」（保存过详情），也不是已导入。
4. 批次级提示（属于另一本账本、有截图没切出候选）独立成一行警告，**不因压缩而隐藏**。
5. 数字全部来自真实函数：`countBatchItems(items)` 与 `countImportableItems(items)`，与筛选、卡片同一套判断（`itemStatus` / `isItemQuestionable` / `validationBlocker`），没有手写常量。

### B. 筛选区

- 常驻主状态 chip：**全部 / 待核对 / 疑似重复 / 已确认**（保留原有“已确认”能力，四个都带真实计数）。
- 来源平台、收支方向收进「筛选」按钮展开的折叠面板（页面持有展开状态，移动端就是页面内展开，不用弹层）。面板关闭但次级筛选生效时，显示「已筛选：来源 微信 · 只看支出」一行摘要 + 「清除」；展开时也有「清除来源/方向筛选」。
- 未删除任何筛选能力；筛选只改变列表，不改变汇总数字（详情里明确写了一句）。
- 空列表有两种说明：批次本身 0 笔 → “这次识别没有切分出任何交易…”；筛选后为空 → “当前筛选下没有交易。” + “当前筛选：待核对 · 来源 微信。” + 「显示全部交易」（同时重置状态/来源/方向）。

### C. 卡片信息层级

每张卡片三层，无异常时只有三行左右：

1. **第一层**：状态标记（已识别/待核对/疑似重复/无效）+ 退款/转账/已核对标记；右侧 **日期（含时间，缺失写“日期待确认”）· 来源平台**。
2. **第二层**：**金额（大号）+ 币种 + 收支方向**；下一行是交易对象/商户（缺失写“对象/商户待确认”）。
3. **第三层**：`分类：… · 支付方式：…`，有标签才加 `· 标签：…`，有账户才加 `· 账户：…`；右侧「查看详情」。
4. 备注只在非空时以单行出现（过长截断，详情可看全文）。
5. 警告只为**真有疑问**的记录出现：疑似重复分组、`deriveIssues` 的逐条原因；另外新增一条“已识别但写不进账”的提醒（例如币种账本不支持），避免出现“状态已识别、按钮却被禁用”的静默不一致。
6. 点击卡片上的「查看详情」仍进原详情页；返回后概览重新读取批次（现有 batch store 链路，无改动）。
7. **未改排序**：仍按批次识别顺序展示（原因见 §6）。

### D. OCR 分类联想（复用语音已有逻辑）

新增纯函数模块 `apps/web/src/lib/ocr/category.ts`：

- `usableCategories(categories, kind)`：只留 kind 一致、未归档、非系统、名字非空；`matchCategory` 自己会过滤 kind/归档/空名，`isSystem` 只能在本地过滤。
- `inferCategory(item, categories)`：输入候选 + 账本分类，输出 `{ categoryId, matched }` 或 `null`。
- `applyCategorySuggestions(items, categories)`：把建议写进候选（`categoryId` + `categorySource: "inferred"`），返回新数组；**没有可改的项时返回 `null`**，调用方据此避免无谓的状态/存储写入（幂等）。

优先级与守卫（按顺序）：

| 情况 | 行为 |
|---|---|
| 候选已有 `categoryId`（扫描/平台默认、转账预设、用户已选） | **不动**，不联想 |
| `categorySource === "user"`（含用户清空分类） | 不联想 |
| `invalid`（用户已排除） | 不联想 |
| `isTransfer` / `isRefund` | 不联想（理由见下） |
| 方向不是 expense/income | 不联想（分类带 kind，猜错方向更糟） |
| 本账本没有可用分类 | 不联想 |
| 交易对象、备注分别 `matchCategory` 后指向**不同**分类 | 视为歧义，**不填** |
| 只有一边命中 / 两边一致 | 采纳；写 `categorySource="inferred"` |
| 都匹配不到 | 返回 `null`，保持“未分类”待用户选 |

- **区分原始值与推断值**：`OcrBatchCandidate` 新增**可选** `categorySource?: "ocr" | "inferred" | "user"`；旧 sessionStorage 批次没有该字段，`categorySourceOf` 把“有分类、无来源”解释为 `ocr`（平台默认/旧版用户选择），因此旧数据不会报错、也不会被冒标成“系统建议”。只有 `inferred` 会在界面显示「系统建议」。
- 概览卡片第三层显示 `分类：餐饮（系统建议）`；详情页分类下拉框下方显示 `系统建议：餐饮（可改；按交易对象/备注的文字匹配本账本已有分类，不是已确认）`，只在分类还不是用户自己定时出现。用户改选/清空后 `categorySourceAfterSave` 返回 `user`，概览不会再推断覆盖。
- **不动其它字段**：只写 `categoryId` / `categorySource`；金额、币种、日期、方向、支付方式、标签、备注均不触碰；也不因分类被推断出来而消除其它待核对状态（完整性判断里没有分类）。
- 不自动创建分类、不跨账本：分类列表来自**批次所属账本** `useLedgerMeta(batch.bookId)`，跨账本时不回退当前账本的分类（宁可不显示，也不串账）。

### E. 待核对状态一致性

- 沿用并核对现有判断：`deriveIssues`（按字段过滤已解决/仍成立的识别问题）→ `isItemComplete` → `isItemQuestionable` → `itemStatus` → `countBatchItems`；导入侧 `validationBlocker` / `findImportBlockers` 一行未改语义。
- 新增 `countBatchItems.reviewed`（未标记无效且 `reviewed === true`），只为把“用户已核对”作为**第四种信息**单独呈现，不参与 `itemStatus`。
- 新增 `countImportableItems`：未标记无效 + `validationBlocker === null`；**不要求已有幂等 id**（id 只在确认那一刻生成）。概览的「可导入」、底部条的数量、确认按钮文字、确认弹窗标题全部用这个数。
- 卡片新增“已识别但写不进去”的提醒（仅当状态是“已识别”而 `validationBlocker` 非空），覆盖“看起来完整、实际币种不支持/金额格式不对/备注超长”等静默阻塞。
- 没有升级任何既有规则：缺时间但其余完整的记录仍可导入（`occurredAt` 用 12:00，沿用原逻辑）；缺商户仍只提示、不阻塞导入（备注里会写商户）。**待核对与可导入不是互斥集合**，见 §2。
- 数据结构里确实**没有字段级置信度/来源标记**（本分支不伪造数值），所以“不确定性”只通过现有 `issues`、缺失字段、疑似重复、`validationBlocker` 表达。

## 2. 计数与状态口径（唯一口径）

| 名称 | 定义（`lib/ocr/types.ts` / `import.ts`） |
|---|---|
| 本次识别 `total` | 批次全部候选，**含已标记无效** |
| 未标记无效 `valid` | `!invalid`（用户没排除它） |
| 待核对 `pending` | `!invalid && isItemQuestionable`：缺关键字段（金额/币种/方向/日期/商户）或有 `BLOCKING_ISSUES` 或疑似重复 |
| 疑似重复 `duplicates` | `!invalid && duplicateSuspected`（**含在待核对里**，是子集） |
| 已确认（无需核对） `confirmed` | `!invalid && itemStatus === "recognized"`：字段齐全、无阻塞问题、非重复；筛选 chip 仍叫「已确认」，详情里写明它不是已核对、也不是已导入 |
| 已标记无效 `invalid` | `invalid === true` |
| 你已核对过 `reviewed` | `!invalid && reviewed`（进过详情并保存过，**不代表已入账**） |
| 可导入 `importable` | `!invalid && validationBlocker === null`：金额存在且可解析为正数、币种账本支持、方向明确、日期合法、时间格式合法（可空）、备注不超长 |

四种状态的关系（界面上分得开）：

- **识别成功（recognized）**：卡片徽标“已识别”，只表示字段齐全且无阻塞问题；
- **可导入（importable）**：通过导入字段校验，是底部按钮与数字的口径；可能包含少量“待核对”项（如缺商户、版式未验证——现有规则不阻塞）；
- **存在疑问（review / duplicate）**：徽标“待核对/疑似重复” + 具体警告；**仍可能可导入**，这是既有业务语义，没有擅自升级；
- **用户已核对（reviewed）**：徽标“已核对” + 详情里的计数；与 `itemStatus` 正交（可能仍是待核对，也可能仍是已识别）。

一致性由同一组纯函数保证，并有测试覆盖：缺币种的候选计入“待核对”、从“可导入”里排除；`reviewed` 不会把“待核对”变“已识别”；筛选“待核对/疑似重复/已确认”的人数与汇总数字一致。

## 3. 分类联想的规则与局限

- **不做/不填的情况**：见 §1D 表格；退款与转账明确不联想。理由：账本没有 transfer 类型，转账的默认分类由 `batch.ts` 按识别标记映射到账本已有的「转账」分类；退款的方向与“算不算支出”在现有模型里本身需要人确认，硬套普通分类等于用猜的填平业务语义。
- **歧义处理**：`matchCategory` 没有置信度分数，所以**不伪造 confidence**；能用的信号只有“交易对象文本”和“备注文本”两段证据——两边指向不同分类时不填，同一段文字内部并列时仍会按 `matchCategory` 自己的规则选一个（这一点看不见，是已知局限）。
- **词表局限**：`matchCategory` 的词表是语音记账那套（餐饮/交通/购物/居住/通讯/医疗/娱乐/教育/人情/宠物 + 收入）；商家名（如“肯德基/星巴克/中国石化”）大多不在词表里，会返回 `null`；宁可“未分类”也不乱猜。
- **不使用 `rawText`**：只按需求里的“交易对象 + 备注”匹配，避免把整屏 OCR 噪声当证据。
- **命中词**：`inferCategory` 返回 `matched`（命中的词），目前界面只用“系统建议”四个字，没有展示命中词；保留字段是为了以后能说明“为什么是它”。
- **落值位置与时机**：概览页在分类列表就绪后应用一次（effect），best-effort 写回 sessionStorage 草稿（**不是账本**）；写存储失败只影响“详情页能否看到同一条建议”，详情页会用同一纯函数现算。导入时该 `categoryId` 会随既有 `buildImportPlan` 写进账目（与既有的“转账预设类别”一样，属于系统填的默认值，但这里明确标 `inferred` 并显示「系统建议」）。
- **旧数据兼容**：`categorySource` 可选；`normalizeBatch` 未改，缺字段照常读；`categorySourceOf` 把“有分类、无来源”视为 `ocr`。

## 6. 未做与原因

1. **排序（默认待核对优先 + 恢复原始顺序）未做。** 现有列表顺序 = 批次识别顺序 = 导入顺序；没有选择/索引逻辑依赖显示顺序，风险低。但加排序切换会新增一块 UI（入口、状态、空态说明）与测试面，所有者要求“先报告风险再决定做不做”，因此本轮不动。若要做，建议加一个受控的“待核对优先/原始顺序”开关，不改 `items` 顺序、只在渲染前排序。
2. **没有逐笔勾选（selection）**。现有导入语义是“所有未标记无效且通过校验的项一起写”，`OcrBatchCandidate`/`import.ts` 没有选择字段；加选择要么改 `buildImportPlan`（新增参数/过滤）要么把未选项标 `invalid`，两者都会改变既有写入语义，超出“局部优化”。底部条因此显示“可导入 N 笔”而不是“已选 N 笔”。
3. **分类联想没有展示命中词**（只标「系统建议」）；也没有对“歧义”给提示（静默保持未分类）。如需提示“有歧义，请手动选”，要在 `inferCategory` 返回值里加原因码。
4. **没有新增字段级置信度/来源**（后端/共享类型都没有），也没有把不确定性升级为逐笔确认；只沿用现有 `issues` 口径。

1. **推断值会落进 `categoryId` 并随导入写入账目**（这是“联想”在语音那边的同样语义：建议即预选，可改）。如果所有者希望“只提示、不预选”，只需在概览页 effect 里不调用 `applyCategorySuggestions`（详情页仍可显示建议），或改成导入时再决定——请确认。

3. **底部固定条为 `fixed`**：展开“查看 M 笔不能导入的原因”时会临时盖住列表底部一小块（收起即恢复）；真机上与安全区/键盘的实际表现未目视验证。
4. **分类候选按批次账本读取**会让概览多一次 `useLedgerMeta` 请求（`staleTime: 0`）；离线时同账本回退 `useLedger` 缓存，跨账本离线时分类名会显示“未分类”（页面已有“属于另一本账本、不能导入”的警告）。如认为这一请求不必要，可只在批次账本 ≠ 当前账本时才查。
5. **旧批次无 `categorySource`**：有分类按 `ocr` 处理（不标「系统建议」、不会被推断覆盖）；如果旧批次里存的是旧版用户手动选的分类，界面不会区分——只影响“系统建议”标签，不影响值。
6. **详情页改了收支方向、原推断分类失效时**：`changeKind` 会清掉不兼容的分类，保存后来源记为 `user`（视为用户在这次保存里做了决定），概览不会自动换一个方向重新联想；用户可再进详情手动选。若要“改方向后自动重推”，需要把来源区分成“用户改方向”与“用户否决分类”两种，属于后续细化。
