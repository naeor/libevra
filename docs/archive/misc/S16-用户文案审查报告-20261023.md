## 0. 结论摘要

- 共收集 **3,700 条**候选用户可见文案，覆盖 332 个源文件；其中前端 2,823、服务端用户可见响应 537、共享规则 186、历史公告 129、法律文本 25。
- 当前最严重的问题不是“文字不好看”，而是**少数文案与真实产品状态/能力不一致**：
  1. **P0 财务误导**：历史记录把金额按原始最小单位显示（如 `3500` 而不是 `35.00`）。
  2. **P0 状态误导**：法律页仍称“项目尚未上线”，但生产环境已在运行。
  3. **P1 数据安全事实冲突**：删除确认称“无法在应用里自行恢复”，而已删除记录详情页提供“恢复这笔记账”；不同入口说法不一致。
- 第二类问题是**技术实现直接进入普通用户界面**：本地 `pnpm dev` 启动指令、服务端业务锁、回执、幂等、UTC、来源 A/B 等，集中在导入/账本导入/OCR/账号与数据流程。
- 第三类问题是**解释性文字过量和重复**：标题下再解释标题、设置项解释显而易见的选项、安全说明与操作说明混在一起。不能简单全删，安全/财务/不可逆操作的含义必须保留。
- 第四类问题是**术语体系未统一**：账本/账目/记录/交易/明细、删除/移除/清理/永久删除/注销、保存/提交/确认/写入、重复交易/疑似重复/重复账目等。部分词确实代表不同业务含义，**不能为了统一而合并**。
- 已有大量写得好的文案：删除影响范围、重复检测不会自动删除/合并、导入可撤销与事务回滚、分享链接一次性、恢复码一次性、账号注销对每本账的影响等，均比普通产品说明更清楚；本轮明确保留其安全含义，不为了“简洁”删短。

## 4. P0/P1 高风险问题

### 4.1 P0-1 历史记录金额按原始最小单位显示

- **位置**：`apps/api/src/ledger/history.ts:145-149`（`renderValue()` 故意返回原始 `amountCents` 字符串）；`apps/web/src/components/HistoryList.tsx:129-133` 直接渲染 `{change.from} → {change.to}`。
- **现状**：修改金额 35.00 → 38.00，历史页显示 `3500 → 3800`；API 测试 `apps/api/test/historyApi.test.ts:198` 也把 `"3500"`/`"3800"` 当作预期。
- **问题**：这是财务结果误导，不是措辞问题。用户会以为金额被改成 3,500 元或无法判断实际变化。
- **动作**：保留 API 返回原始最小单位（与其他金额契约一致），在客户端用共享 `formatMoney` 格式化；或让 API 明确返回格式化后的展示值。**不要只在测试里改期望**。需补前端测试，覆盖人民币/美元/0 位小数币种。
- **风险**：财务；P0。必须由负责金额格式化的同一规则处理，不能新增第二套金额格式化。

### 4.2 P0-2 法律页仍称“项目尚未上线”，但生产已在提供服务

- **位置**：`apps/web/src/pages/LegalPage.tsx:86-88`（ID `S16-COPY-2421`）。
- **问题**：生产已上线并积累真实账号；页面文字仍说“项目尚未上线/正式提供对外服务之前补齐”。这是事实状态错误，可能让用户误以为没有正式条款/没有运营主体，也会影响隐私与合规判断。
- **动作**：由所有者与法律文本负责人处理；本轮不修改法律实质。UI 在条款补齐前应显示准确状态（例如“条款仍在确认”），不能继续声称“尚未上线”。法律文本整体单独维护，不纳入普通文案批量改写。
- **风险**：合规/信任；P0，但属于“单独分类”，不是普通 UX Writing 任务。

### 4.3 P1-1 删除确认与已删除详情互相矛盾

- **位置**：`apps/web/src/pages/EntryDetailPage.tsx:761`（确认删除：“删除后，你无法在应用里自行恢复这笔记录”，ID `S16-COPY-1791`）；同文件 `:196` 已删除详情提供“恢复这笔记账”（ID `S16-COPY-1741`）；批量删除 `apps/web/src/components/ledger/batch.ts:402` 也有同类提示（ID `S16-COPY-0385`）。
- **问题**：同一个删除动作，一处说不可自行恢复，另一处提供恢复按钮。用户无法判断删除是否可逆，也无法据此做安全决策。
- **动作**：先由产品确认“单笔删除是否始终可恢复、批量删除是否不同”。文案与按钮必须一起调整：要么允许恢复并改写后果说明，要么移除恢复入口并说明条件；不能只改一句文案掩盖能力差异。
- **风险**：数据安全/不可逆操作；P1（若确认可恢复，则升级为 P0 事实错误）。

### 4.4 P1-2 文件导入错误把本地开发命令暴露给普通用户

- **位置**：`apps/web/src/pages/ImportPage.tsx:300-303`（ID `S16-COPY-1872`）。
- **现状**：“…请先启动本地 API（项目根目录运行 pnpm dev），刷新页面后重试。（…）”。
- **问题**：普通用户没有项目目录、不会运行 `pnpm dev`；括号里还拼接内部异常。错误提示没有可执行的用户动作。
- **动作**：改写为“服务暂时不可用，请稍后重试；如果持续失败，请联系管理员”，技术细节只进日志/诊断页。保留“文件本身不一定有问题”的安全含义但缩短。
- **风险**：技术暴露/误导；P1。

### 4.5 P1-3 账本导入把内部并发/回滚机制当作页面说明

- **位置**：`apps/web/src/pages/LedgerImportPage.tsx:1348`（ID `S16-COPY-1999`）等。
- **现状**：“服务端业务锁”“撤销会恢复本次已提交的业务变化，而不是只停止后续批次”等。
- **问题**：这是实现语义，不是用户能操作的说明；真正需要告诉用户的是“确认前其他人不能修改这本账”“撤销会撤回这次导入已写入的数据，不只是停止后续”。
- **动作**：保留关键后果，替换内部术语；必要时放到“导入说明”折叠区。
- **风险**：技术暴露/功能边界；P1。

### 4.6 P1-4 历史成员事件句法错误

- **位置**：`apps/api/src/ledger/history.ts:44`（`member_changed: "变更了成员"`）、`:101-108`（成员事件 subject 为“这本账”）、`:119`（`${who} ${verb} ${subject}`）。
- **现状**：生成“张三 变更了成员 这本账”。
- **动作**：把动词或句式改成能带“这本账”的完整谓词（如“变更了这本账的成员”），不要在 assembler 里为单个事件加特例。
- **风险**：历史可读性；P1。属于服务端动态文案，必须先改 API 句子生成与测试。

### 4.7 P1-5 历史变更字段回退到内部英文 key

- **位置**：`apps/api/src/collab/share.ts:326,350` 写入 `changes: { joined: ... }`；`apps/api/src/ledger/events.ts:95-121` 的 `TRACKED_FIELDS` 没有 `joined`；`apps/api/src/ledger/history.ts:126` 回退为 `key`。
- **现状**：历史页可能显示 `joined：曾经退出 → 通过分享链接重新加入`。
- **动作**：补中文标签或在事件层使用稳定字段名；同时补历史 API 测试，确保“tracked 未命名”不会穿到界面。
- **风险**：历史可读性；P1。

### 4.8 P1-6 重复检测术语三套并存

- **位置**：`apps/web/src/pages/DuplicateReviewPage.tsx:97`（“重复账目检测”，ID `S16-COPY-1699`）、`apps/web/src/pages/BookSettingsPage.tsx:329`（“重复账目检测”，ID `S16-COPY-1478`）、`apps/web/src/pages/EntryDetailPage.tsx:679`（同题，ID `S16-COPY-1778`）；正文同时使用“疑似重复”“重复交易”“重复账目”。
- **问题**：标题叫“重复账目检测”，按钮/说明叫“重复交易”，同一屏还有“疑似重复”。用户无法判断“重复交易”是不是一个独立功能。
- **动作**：由产品确认统一层级：功能名与候选状态名分开（例如功能统一“重复账目检测”，候选状态统一“疑似重复”），不要为了统一把“交易”这个业务词整体替换。详见术语清单。
- **风险**：术语/理解；P1。

## 7. 可直接删除或缩短的冗余说明（候选）

- 页面标题下重复标题含义的副标题/说明（设置、我的、个人资料等）。

## 11. 术语现状摘要

详见 [术语一致性清单](S16-术语一致性清单-20261023.md)。本报告只强调三点：

- **账本/账目/记录/交易/明细**不是同义词：账本是容器，账目是一笔记录，历史记录是事件流，交易更适合导入/重复检测语境；“明细”既有账目列表也有导出统计语境。
- **删除/移除/清理/弃置/永久删除/注销**对应不同生命周期，不能统一成一个“删除”。
- **恢复码**（账号密码恢复）与**恢复凭证**（归档账本恢复）是完全不同的安全物，必须保留区分。

## 13. 方法与限制再声明

本报告是**调查记录**，不是最终产品文案。Codex 修改时应：

1. 以 CSV 的 `ID + 源文件 + 行号 + 原文` 定位，不只看行号（Codex S16-A 改动会移动行）。
2. 先确认调用路径和状态，再决定删/改；动态文案必须保留参数来源与条件分支。
3. 对 P0/P1 先与产品所有者确认事实（尤其删除恢复、法律状态、备份期限），不能只改措辞。
4. 每批修改补对应测试或快照；用户可见文案变更按 AGENTS.md 记录 changelog，但本轮不提交、不 push、不部署。
