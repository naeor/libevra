## 1. 结论

**删除请求已经成功（服务器 204），但客户端把「重试时服务器说这行不存在」（404 `transaction_missing`）当成
了永久失败**，于是删除印记永远停在 `{ pending: true, deleted: true }` —— 这就是红行的来源；
「点了刷新也不消失」是因为 `syncController` 注释里承诺的「手动刷新先清掉放弃标记」**从来没有实现**。

修了两处：

| # | 改什么 | 位置 |
|---|---|---|
| 1 | `deliver()`：`op === "delete"` + `404` + `transaction_missing` → 视为投递成功（与 204 完全同一条路径） | `sync.ts` L339–371 |
| 2 | 导出 `retryAbandonedWrites()`，只由手动刷新在 `syncNow()` 之前调用 | `sync.ts` L55–78、`syncController.ts` L23–38、`DetailPage.tsx` L363–374（调用在 L371） |

**没有动**：API、Prisma schema、软删除语义、导入/撤销、冲突解决主流程、幂等键生成、自动同步触发逻辑。

## 2. 根因（代码 + 日志证据）

### 2.1 服务端是对的

API 访问日志（Lead 提供）：

- `DELETE /api/v1/transactions/01a129f8-…` → **204**（删除成功）
- `DELETE /api/v1/transactions/01a159b5-…` → **404 `transaction_missing`**

404 的语义是「这行已经不在了」，而**这正是删除想要的结果**：同一 id 之前已经删成功过，重试当然拿不到。

### 2.2 客户端把 404 记成了永久失败

`sync.ts`（基线）`deliver()` 的 `catch`：

- 通用失败分支给每个失败写入 `failures`，`permanent` 的判定是**所有 4xx**（只有 `agreement_required` 例外）。
  基线 L324–328，现 L383–387：

  ```ts
  permanent:
    status >= 400 &&
    status < 500 &&
    !(error instanceof ApiRequestError && error.code === "agreement_required"),
  ```

- 404 落在 400–499，于是 `permanent: true`。
- `runSync()` 对 `permanent` 的条目**整段会话内直接跳过**（基线 L163–166，现 L187–191：`refused += 1; continue;`），
  到 `MAX_ATTEMPTS`（5）也一样（基线 L168–171，现 L193–196）。
- `failures` 是**模块级内存 Map**（L50），只有 `deliver()` 成功才会 `failures.delete()`；页面刷新才清空。
- 于是：标记一直停在 `{ pending: true, deleted: true }`（`sync.ts` L252 的成功分支根本走不到），
  屏幕按 `deleted` 渲染淡红删除线（`LedgerEntryRow.tsx` L50–56，`DetailPage.tsx` L1104）。

### 2.3 为什么「删除第一次其实成功了」

本机 API 以 `--watch` 运行，最近合并代码时反复重启；请求在重启窗口里丢了响应 → `deliver()` 走 `catch`
（`status === 0`，`permanent: false`，`attempts: 1`）→ 重试 → 收到 404 → 被记成永久失败。
**两个不同 id 的 204 / 404 正好对上这条时间线**：204 的那次服务端已经删了，404 的那次是重试。

### 2.4 为什么「点刷新也救不回来」

`syncController.ts` 顶部注释写着「A person pressing this button is asking us to try again, so the "give up"
marks are cleared first」，但**代码里没有任何清除**。刷新只是重跑 `syncAll()`，而 `permanent` 判定还在内存
Map 里，条目继续被 `continue` 跳过 —— 用户按多少次都一样，只有整页刷新（换掉进程）才重来一次，
而整页刷新后的第一次重试仍然是 404 → 又变红。

### 2.5 一条佐证：这个修复曾经存在，后来丢了

`write.ts` L460–461 的注释（基线代码，未改）已经写着：

> **If the server has already deleted it, the delete is a 404 — and a 404 on a delete means the job is
> done**, which `syncOne` now treats as success rather than a permanent failure to retry for ever.

即：**代码注释早于代码**描述了这条规则（`syncOne` 是队列时代的函数名，改成「印记即队列」之后这条规则没跟过来）。
所以本次不是新语义，是**把注释承诺的语义补上**。

## 3. 改了什么

### 3.1 `apps/web/src/lib/offline/sync.ts`（+59 行）

**修复 1：`deliver()` 里新增「删除的 404 就是删掉了」分支**（L339–371），位置在 409 冲突处理之后、
通用失败记账之前，因此**4xx 的通用判定对 delete 404 不再生效**：

```ts
if (op === "delete" && status === 404 && error instanceof ApiRequestError &&
    error.code === "transaction_missing") {
  if (JSON.stringify((await readMarks())[entry.id]) === JSON.stringify(intent.mark)) {
    await setMark(entry.id, { deleted: true, pending: false, synced: true });
    await republishLedger();
  }
  failures.delete(entry.id);
  await logOffline("DIAGNOSTIC:sync-already-gone", …);
  return true;
}
```

- **与 204 成功路径逐字同形**（L252 的同一条 `setMark` + `republishLedger`），所以「删除已确认」的后续行为
  （印记保留为已确认墓碑、不再产生 intent、不再发请求）完全复用既有逻辑，没有第二套语义。
- **in-flight 保护照抄成功分支**：只有当前印记仍等于本次意图的 `intent.mark` 才写，请求期间用户又改过就
  不覆盖。
- **`return true`** → `runSync()` 计入 `delivered`（L198），不计 `refused`。
- **没有扩大**：只认 `op === "delete"`、只认 `404`、只认服务器自己的 `transaction_missing`。
  `update`/`create` 的 404 语义不动（注释里写明了原因：那是「设备以为存在的行服务器没有」，是真的分歧，
  必须保持可见、不能被确认掉）。

**修复 2 的实体：`retryAbandonedWrites()`**（L52–80，导出）：清空 `failures`，返回清掉的条数，并写一条
`DIAGNOSTIC:sync-retry`。**只清内存记账**：不动队列、不动印记、不动账目数据；下一次 `runSync()` 会把每条
待投递印记重新判一遍，4xx 仍然是 4xx，只是「重新判一次」。

### 3.2 `apps/web/src/lib/offline/syncController.ts`（+7 行）

`export { retryAbandonedWrites } from "./sync.js";`，并把顶部那段「手按刷新就应当重试」的注释**指向实现
位置**（原来是一句没有实现的承诺）。

### 3.3 `apps/web/src/pages/DetailPage.tsx`（+10 行）

`refresh()` 在 `syncNow()` **之前** `await retryAbandonedWrites();`（带注释说明：只清会话内的放弃记录、
不动数据、自动触发不调用）。手动刷新路径仅此一处（`syncNow` 也只有这一处调用者）。

## 5. 修复 3：拉取对账为什么没把行清掉（**只诊断，未改**）

基线 `sync.ts` L584–592（现 L588–592）的对账分支：

```ts
for (const entry of stored[month] ?? []) {
  if (marks[entry.id]?.deleted === true && marks[entry.id]?.pending === true && !serverIds.has(entry.id)) {
    await setMark(entry.id, { deleted: true, pending: false, synced: true });
  }
}
```

事实与结论：

1. **这条分支本身是对的，也确实会执行**（`conflictFlow.test.ts` L134–144 已经钉住它：只有当月被完整
   拉取后才确认，且保留墓碑）。所以不是「没覆盖到分页」——拉取是 `do/while` 走完所有 cursor 的。
2. **但它清不掉颜色**：它写出的也是 `{ deleted: true, pending: false, synced: true }`，而
   `deleted === true` 仍然让这条 id 留在 `publishDeleted` 的集合里（`localLedger.ts` L635–641、L770–776），
   于是只要这一行还在被合并的列表里，就仍然画成淡红删除线。**「已确认的墓碑」与「还没同步的删除」在同
   一条渲染规则下，屏幕无法区分。**
3. **「行还在」来自合并路径，不来自印记**：`readLocalTransactions()`（`localLedger.ts` L201–292）把自己
   存储的账目（已过滤 deleted）与**持久化查询缓存 + 内存查询缓存**合并，后两者没按印记过滤；
   页面再用 `mergeLedgerEntries(local, remote, pending, filters)`（`ledgerView.ts` L6–15）合并一次，
   **这个函数只筛月份/收支/分类/币种，不筛 deleted**。所以「刷新后已删除的行还出现」只能用这条路径解释：
   服务器已经不返回它了，是本地查询缓存把它又交回来了。
4. 因此**只改对账分支是没用的**（它已经按设计工作），要真正让已确认的删除从屏幕消失，得改合并/渲染
   语义（例如「已确认墓碑不进列表，待删除才画红」）。这会让「已删除行是否还显示」的既有设计改变，属于
   **本次不改**的范围，需要所有者先决定：确认删除后，那行应当立刻消失，还是保留红色直到列表重新拉取。
5. 所有者描述的「**刷新后颜色正常、再点一次才变红**」这一条，我用代码**没有找到能确定解释的路径**：
   正常颜色要求这条 id 完全没有印记，而删除路径（`write.ts` L475）是无条件写印记的。
   可能的解释是「那批行是别的设备/更早的会话删掉的，本机只是从查询缓存里又看到它们」，但这需要
   `DIAGNOSTIC:ledger-marks` 行才能确认。**这一条本次不修，也不猜着改。**

## 6. 风险 / 未验证

1. **红行是否「立刻」消失，只能在真实浏览器复核。** 本次让 404 与 204 走**同一条**成功路径，因此
   「404 之后的行」行为与「一次正常成功的删除」**完全一致**；但如上 §5.3 所述，行的可见性还取决于本地
   查询缓存与页面合并，**不保证刷新点击后同一帧就消失**。请所有者在 `localhost:5173` 复核：
   删除 → 点刷新 → 是否不再红、是否从列表消失；必要时整页刷新再确认。
2. **没有真实网络往返的验证**：测试里 `apiFetch` 是 mock，未在本机起 dev server、未对真实 API 发请求
   （按要求）。
3. **`retryAbandonedWrites()` 只在「明细页手动刷新」被调用**：账本more页「清空全部待同步印记」
   （`clearAllMarks`）是另一条已有的逃生门，本次未动。
4. **没有升版本号、没有加 `changelog/` 条目**：本次是 worktree 分支上的最小修复，合并到 localhost 主
   分支时由 Lead 决定版本与公告。
5. 自动同步触发（`online` / 回到前台 / 启动）行为**未改**：它们仍然尊重「放弃」判定，这是刻意的。

## 补充（Lead 复核后追加，2026-10-20 23:55）

复核时发现**还有一层根因**必须一起修，否则"删了还在"只解决一半：

- `mergeLedgerEntries`（`lib/ledgerView.ts`）把本地副本与查询结果合并后**没有过滤删除墓碑**，而 `LedgerEntryRow` 的注释写着"已删除的行实际不会渲染"——**注释与代码不一致**。于是无论删除是"排队中"还是"已确认"，被删条目都会继续出现在明细里（已确认时还会以正常颜色显示，正是所有者看到的"删了还在、颜色正常"）。
- 修复：`mergeLedgerEntries` 新增 `deleted` 参数，合并后按墓碑 id 过滤；`DetailPage` 传入设备上的 deleted 集合（含 pending 与已确认）。已删除条目现在**从列表消失**，不再依赖查询缓存刷新。
- 新增测试：排队中删除（本地副本 + 服务端旧行都在）、已确认删除（只有本地副本）都必须不渲染，未删除的行不受影响。
- 合并后复核：web **706 tests**（76 文件）全过、typecheck ✅、build ✅、`check:docs` ✅、`check:status` ✅（路由 69）。

**现在三处修复共同保证**：服务端删除已成功时，重试 404 会被视为成功并清掉标记；本地墓碑不再进列表；手动刷新可重试被放弃的条目。
