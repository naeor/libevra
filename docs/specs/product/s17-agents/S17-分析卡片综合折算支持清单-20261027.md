## 2. 数据流（一条路径，所有卡片共用）

```
useFxRange(from, to)                         apps/web/src/lib/fxView.ts
  └─ aggregateFxDetailedAsync(…, { includeEntries: true, maxEntries: FX_MAX_DETAIL_ENTRIES })   ← 显式传参（§4.8-8）
       ├─ 成功：detail.entries（逐笔折算结果）+ failures（日期 / 币种 / 原因）+ 读取覆盖 sourceComplete
       └─ 超 50,000 笔：fx_detail_limit → 回退为聚合（aggregateFxAsync），状态 entryLimitExceeded = true
projectFx(view)                              apps/web/src/statsWorkbench/fxProjection.ts
  └─ 校验（守恒 / 孤儿 / 缺明细 / 金额超安全整数 / 币种）→ 把逐笔折算结果「投回」原账目：
       同一 id、日期、方向、分类、支付方式不变；金额 = 折算后目标币种最小单位；币种 = 目标币种
       → converted（可计算）/ all（计数口径用）/ missing 清单（日期 · 币种 · 原因 · 账目入口）
fxPolicy.ts（按卡片口径分类）→ 现有 A 目录 assemble / B 时间引擎 / 上期比较，原样复用
```

关键规则（与 S16-D 一致、已被测试逐条覆盖）：

- **不改原账、不二次折算**：每一笔只按其发生日期的历史汇率折算一次（半入取整，`minor-half-away-v1`），汇总的是折算后的整数最小单位；不是先汇总再折算。
- **不用 JS Number 做金额中间量**：金额以 BigInt / 整数字符串流转；折算结果超过安全整数时该笔判为 `amount-unsafe`，投影整体 `invalid`，不静默失真。
- **缺汇率永远不当 0**，也永远不宣称完整：每种卡片有自己的降级（§3）。
- **条数上限不截断**：超过 50,000 笔必须显式失败，不得取前 5 万笔冒充完整，也不得提高上限（§5.1）。
- **能找到未折算的账目**：缺汇率清单（日期、币种、原因、账目入口）在顶部「统计不完整」入口列出，沿用既有页面。

## 3. 口径类别与缺汇率时的呈现

| 类别 | 含义 | 缺汇率（相关方向）时 | 理由 |
|---|---|---|---|
| **sum** 合计 | 总额 / 差额 | 只给「**已成功折算部分的小计**」，并写明另有几笔缺汇率未计入、不是总额 | 小计是真实的下界信息；写成总额会误导 |
| **count** 计数 | 笔数、天数、分类数、记账频次 | **照常计数**，缺汇率账目计入，结果恒完整，不提示不完整 | 计数与金额无关；排除缺汇率账目反而会少算 |
| **partial** 可部分计算 | 日均支出 | 只用已折算部分算，并标明「另有 N 笔缺汇率未计入」 | 分母（天数）完整，分子是下界 |
| **undetermined** 无法确定 | 笔均、中位数、支出收入比、结余率 | **不给数字**，只写「有 N 笔缺汇率，这个数字无法确定」 | 缺一笔就可能改变均值 / 中位数 / 比率，给任何数都是编造 |
| **extreme** 极值 | 最大 / 最小单笔、最多的一天 / 分类 | 只在已折算账目里比较，并声明「不一定是全局结果 / 缺汇率的账目可能改变它」 | 缺的那几笔可能才是真正的极值 |
| **composition** 构成 | 分类 / 支付方式占比 | 给分项小计，**不显示百分比**（分母不完整），图形退化为排行并说明 | 占比的分母是总额，总额未知 |
| **ranking** 排行 | 分类排行 | 只含已折算账目，注明「排名可能变化」，不给占比 | 缺的账目可能改变名次 |
| **series** 序列 | 趋势 / 热力 / 累计 / 多分类 | 含缺汇率日期的时间桶标为 **unknown**（金额与笔数为空，不是 0），合计与其后的累计不给出；热力图未知日与「真实为零」的日子区分显示 | 与 B 引擎五态 `complete/in-progress/future/unknown/unavailable` 一致（§4.8-2：任一 unknown ⇒ total = null） |
| **比较** 上期比较（A01） | 本期对上期的增减 | 本期或上期任一**缺汇率 / 读取失败 / 覆盖不全**：不显示增减，不编造增长率；本期数字仍显示（缺汇率时标为小计） | 拿残缺的一期去比完整的一期没有意义 |

「相关方向」：缺的是支出账目时，只有支出相关卡片降级；收入合计、收入构成、收入趋势等不受影响（反之亦然）。同时涉及收支的卡片（差额、支出收入比、结余率、收支趋势、上期比较）任一方向缺汇率即降级。

## 5. 限制与已知情况（需要读者知道，不是待办承诺）

1. **逐笔条数上限 50,000（不提高）**：这是冻结协议的默认保护值，逐笔明细视图显式传参。超限只影响需要逐笔数据的 31 张卡片，且是显式状态；缩短时间范围即可。
2. **固定窗口卡片读自己的数据**：AN-I09 / AN-I10（近 12 个月）、AN-A01（上一周期）以及用户创建的「固定时间范围」自定义卡片，各自按自己的窗口读取并折算（`useFxRange(窗口)`），不拿顶部筛选的范围冒充；同一工作台里不同窗口的卡片互不串数据（浏览器验收已覆盖「跟随筛选的卡片」与「固定窗口卡片」并存且数字互不影响）。窗口的跨度由既有的范围校验限制（自定义卡片「范围不能超过读取上限」，S16-D 的 `FX_MAX_RANGE_MONTHS` = 36 个月），本次未改动；某张固定窗口卡片的窗口还没读到时，显示「该范围的折算结果还没有读取到，不显示全局金额」，不借用别的范围的数字。
3. **安全整数守卫 + A01 的 Number 口径**：折算后每笔金额必须是不超过 `Number.MAX_SAFE_INTEGER` 的非负整数最小单位，否则投影整体判为 `invalid（amount-unsafe）`，卡片显示「折算明细与账目对不上，为避免给出错误数字，这张卡片暂不显示；可重试」，不静默失真。在守卫之内，沿用既有的统计函数（含 A01 的 `computeStats`，用 JS Number 求和）是精确的；改为 BigInt 全程需要改既有统计函数，不在本次范围。
4. **本机历史镜像每月最多取回约 4,000 笔（既有行为，与折算无关）**：`lib/offline/fill.ts` 的 `FILL_PAGE_SIZE × MAX_FILL_PAGES = 100 × 40`。某个月超过该数量时，本机只镜像一部分；原币与综合折算两种模式读取的是同一份本机镜像，因此表现一致，且「B 类卡片不提示镜像不全」同样是既有行为（两种模式相同）。个人记账几乎不会触发，但它意味着「逐笔超限 5 万笔」在真实浏览器里无法通过正常同步复现：超限路径改用「测试浏览器内把条数常量改写为 10」验证（见验收报告）；5 万笔的边界本身由 `fxProjection.test.ts`、`fxCards.test.tsx`（7 张聚合卡片不变、其余 31 张显式状态）与共享层 `aggregateFxDetailedAsync` 的上限测试覆盖。是否调整该镜像上限属于既有离线同步的另一件事，需所有者另行决定。
