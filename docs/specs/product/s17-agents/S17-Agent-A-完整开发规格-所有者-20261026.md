# 0. 本次任务的根本目标

Agent A 需要为 Libevra 开发一套可靠、可复用、可扩展的基础财务分析系统。

它既负责从真实账目中计算分析数据，也负责将这些数据绘制成对应图表。

但计算函数和绘图函数必须是两个独立的技术模块。

整个数据流必须满足：

```text
原始账目 / 授权后的查询结果
              ↓
       财务计算与分组
              ↓
       标准化分析结果
              ↓
       图表兼容性与适配
              ↓
       独立图表组件
              ↓
        工作台卡片展示
              ↓
       完整分析详情页
```

**任何箭头不得反向影响原始账务数据。**

具体目标：

1. 实现 B01–B20 共 20 项基础分析。
2. 实现 I01–I05、I17 共 6 项分类与构成分析。
3. 建立可供其他分析 Agent 复用的基础计算原语。
4. 建立统一分析结果协议的第一版实现。
5. 开发相应的图表家族，而不是每个指标单独复制一个图表组件。
6. 允许一种分析对应多种合适的图表。
7. 支持小、中、大不同卡片尺寸。
8. 为未来完整分析详情页提供标准化数据。
9. 支持原币与综合汇率统计。
10. 严格保留账本权限、金额精度与来源追溯。
11. 为全部 26 项建立针对性的计算测试。
12. 将所有实现决策、开发进度和遗漏事项持续写入 Agent A 的永久文档。

用户应当能够选择：

**分析什么 → 使用什么图表 → 在什么尺寸的卡片里展示。**

这三种配置是独立的。

# 2. 首先核查真实数据模型

开始编码前，需要对现有账务系统做一次**针对性的数据合同核查**。

这里只要求核查与本任务有关的模型和函数，不需要对整个项目做全面代码审计。

至少确认：

1. 账目主键和账本关联关系。
2. 收入、支出是如何区分的。
3. 金额在数据库和前端分别如何表示。
4. 原始币种如何记录。
5. 分类和分类 ID 如何存储。
6. 分类是否存在父子结构。
7. 支付方式是否为结构化字段。
8. 交易日期如何存储及解释。
9. 交易实际日期与创建时间是否不同。
10. 编辑、删除、恢复后的账目如何过滤。
11. 账目可见性和共享权限如何判断。
12. 原币统计已有的计算路径。
13. 汇率综合统计已有的计算路径。
14. 历史汇率与逐笔舍入规则。
15. 离线数据覆盖范围如何判断。
16. 当前统计查询和明细下钻的接口。
17. 既有 P0 修复是否已合入当前开发基线。
18. 哪些统计能力已经存在，可直接复用。

要求生成一份简洁的字段映射表：

```text
分析概念 → 实际字段或现有函数 → 使用限制
```

不要凭字段名称猜测业务含义。

例如，支付方式字段不等同于真实资金账户；创建时间也不一定代表消费发生时间。

如果某个功能所需字段缺失，应明确登记，不得创造看似正确的替代数据。

# 3. 全部分析必须遵守的财务合同

## 3.1 数据来源

只能使用当前用户有权限查看的账目。

所有计算应复用已经验证的账目查询、权限检查和原有账务语义。

布局配置、图表配置和分析页面的个人偏好不得修改原始账目。

## 3.2 收入、支出与收支差额

基础统计应保留系统现有对收入、支出、退款、冲销、恢复以及其他交易类型的正式定义。

在标准的正金额收入/支出模型下：

```text
收入总额 = 所有符合条件收入记录的金额之和

支出总额 = 所有符合条件支出记录的金额之和

账目收支差额 = 收入总额 - 支出总额
```

但具体实现不得直接假设数据库里所有金额都是正数，或者简单使用 `abs(amount)`。

需要根据真实交易模型确定其语义。

对退款、冲销、负金额和历史兼容记录，必须与既有账务合同一致。

## 3.3 金额精度

金额计算不得使用普通浮点数作为权威累加方式。

继续沿用现有的：

- BigInt 或等效精确金额表示。
- 原始币种最小单位。
- 历史汇率有理数计算。
- 逐笔舍入。
- 逐笔折算后累加。
- 不同币种正确处理。
- 金额格式化规则。

严禁：

```ts
const total = transactions.reduce(
  (sum, tx) => sum + Number(tx.amount),
  0
);
```

如果这种写法会损失权威金额精度。

对于绘图，需要将金额转换成视觉坐标时，可以使用经过验证的、归一化的绘图数值。

**视觉坐标允许使用浮点数；账务计算结果不能因此失去精度。**

若金额超过 JavaScript 安全整数范围，也不得让显示金额、排序或统计结果出现错误。

## 3.4 原币与综合汇率

所有金额分析必须有明确币种口径。

原币分析：

- 仅处理被选中的特定币种。
- 不得直接累加 USD 与 CNY 等不同币种。
- 必须显示统计币种。

综合分析：

- 通过现有权威 FX 引擎逐笔折算。
- 保留原始交易当地日期。
- 保留现有历史汇率回退策略。
- 保留现有舍入规则。
- 不允许 Agent A 自创另一套汇率算法。
- 缺汇率或来源不完整时必须正确反映完整性。

例如，不能把一部分可以折算的交易相加之后，直接称为“完整总支出”。

## 3.5 日期语义

所有日期统计使用明确的业务交易日期。

不得混淆：

- 交易发生日期。
- 记录创建时间。
- 最近编辑时间。
- 服务器 UTC 时间。
- 浏览器显示日期。

建议内部采用明确的日期区间合同，例如半开区间 `[start, endExclusive)`，但应与现有项目日期语义保持一致。

用户看到的“本月”“本周”“近 30 天”等概念必须通过统一日期范围解析器解释。

自然周从星期一开始，这是所有者已确认的规则。

## 3.6 数据完整性

分析结果必须能够区分：

- 完整。
- 无交易。
- 数据部分缺失。
- 汇率部分缺失。
- 离线数据覆盖不足。
- 加载中。
- 请求失败。
- 无权限。
- 当前分析不适用。

这里建议采用结构化完整性状态，而不是只返回一个布尔值。

对于“支出为零”和“无法确定支出是否为零”，必须有明确区别。

## 3.7 来源追溯

每个金额类分析都应提供足够的来源信息，使用户能够查看形成结果的具体账目。

允许通过：

- 精确筛选条件。
- 分组键。
- 分析定义。
- 必要的权限校验。
- 账目查询参数。

重新获取来源记录。

不要求所有计算结果都永久携带所有交易对象。

但来源筛选必须与计算口径一致，不能出现汇总三个月而详情只显示一个月的错误。

# 4. 统一分析输入和输出协议

Agent A 应当提出一套供 Agent B、C、Codex 和详情页共同使用的协议。

以下是**建议的语义结构**，不是强制要求逐字使用这些 TypeScript 名称。

## 4.1 分析定义

建议至少包含：

```ts
interface AnalysisDefinition {
  id: string;
  type: string;

  metric: string;
  aggregation?: string;
  groupBy?: string[];

  filters: {
    kind?: "income" | "expense" | "both";
    categoryIds?: string[];
    paymentMethodIds?: string[];
  };

  time: {
    mode: "inherit" | "fixed" | "relative";
    // 具体区间由共享日期合同表达
  };

  currency: {
    mode: "inherit";
    // 首版不允许卡片独立覆盖工作台币种模式
  };

  parameters?: Record<string, unknown>;
}
```

注意：

- 这只是概念示意。
- 类型需要尽量严格。
- 不建议正式实现中到处使用无校验的 `Record<string, unknown>`。
- 用户配置与实际请求权限必须分离。
- 不能允许用户通过传入账本 ID 绕过授权。
- 账本授权上下文应由查询层提供。

## 4.2 统一金额类型

建议采用类似：

```ts
interface MoneyValue {
  amountMinor: string;
  currency: string;
  scale: number;
}
```

其中 `amountMinor` 是精确最小单位的十进制字符串，避免跨 JSON 边界传输 BigInt 导致问题。

不过，必须优先复用项目现有金额类型和编码约定。

不能为了符合示例而破坏已有协议。

对于平均值、中位数和比例，需要允许比最小货币单位更高的中间精度。

建议内部使用精确有理数或等效表示，并制定明确的显示舍入规则。

不得通过提前舍入每个中间结果使总额发生偏差。

## 4.3 标准分析结果

所有 Agent 的计算结果应包含统一元信息。

例如：

```text
AnalysisResult
├── analysisId
├── analysisType
├── metric
├── resolvedFilters
├── resolvedPeriod
├── resolvedCurrency
├── completeness
├── summary
├── groups / series / records
├── sourceDescriptor
├── computationMetadata
└── error / unavailableReason
```

其中：

**resolvedFilters** 表示实际生效的筛选条件。

**resolvedPeriod** 表示最终统计的真实日期区间。

**resolvedCurrency** 表示币种及折算口径。

**completeness** 表示数据完整性。

**sourceDescriptor** 负责为详情页提供安全、准确的下钻依据。

**computationMetadata** 可说明平均数分母、有效交易数量、舍入方式等必要统计依据。

不能把账本敏感数据放进布局导出和分享模板。

## 4.4 结果形状

建议复用少数标准结果形状：

### Scalar

单一指标：

```text
value
unit
comparison?
source
completeness
```

适合总金额、交易笔数、最大值。

### RankedGroups

分组排行：

```text
groups[]
  id
  label
  exactValue
  count
  share?
  source
```

适合分类排行和支付方式构成。

### Composition

构成分析：

```text
total
parts[]
  groupId
  amount
  share
  count
```

适合环形图和比例条。

### RecordExtreme

记录极值：

```text
extremeValue
matchingRecords / sourceFilter
tieCount
```

适合最大单笔、最高单日等分析。

这里还需要额外设计：

- 分组顺序。
- 缺少分类的归属。
- 同值排序。
- 金额格式化。
- 统计状态。
- 分析来源。

Agent A 提出的共享协议必须允许 B、C 扩展时间序列、分布、矩阵等类型，而不需要重新设计整个结构。

# 5. 基础计算原语

26 项分析不应该各自重新遍历所有账目。

建议建立以下可复用能力。

## 5.1 聚合

支持：

- 精确求和。
- 计数。
- 最大。
- 最小。
- 平均。
- 中位数。
- 极值对应来源。

## 5.2 分组

支持：

- 收入/支出。
- 分类。
- 支付方式。
- 交易日期。
- 其他经过授权的基础字段。

注意缺失分组键的统一处理。

## 5.3 排序

支持：

- 按精确金额排序。
- 按交易数量排序。
- 按名称或稳定 ID 排序。
- 同值确定性排序。

不可把格式化后的金额字符串作为排序依据。

## 5.4 比例

支持：

- 部分 / 总额。
- 支出 / 收入。
- 收支差额 / 收入。
- 百分比格式化。

需要处理：

- 分母为零。
- 负分母。
- 负结果。
- 超过 100%。
- 数据不完整。
- 中间精度。

## 5.5 日期分组

支持：

- 每个业务日期的收入总额。
- 每个业务日期的支出总额。
- 每个业务日期的交易笔数。
- 有交易日期的集合。
- 有支出交易日期的集合。

本模块只实现 B 类需要的基础日期聚合。

完整时间序列和趋势分析由 Agent B 负责。

不得在两个 Agent 中重复建立互不兼容的日期分组规则。

## 5.6 计算缓存与复用

同一个账本、区间、币种和过滤条件可能被多个卡片使用。

例如：

- 总支出。
- 支出分类占比。
- 最大支出分类。
- 分类排行。

可以复用同一份授权后的基础统计结果。

避免每张卡片都单独发起完整账目查询。

但是缓存键必须包含真正影响结果的条件，包括：

- 授权上下文。
- 账本。
- 数据版本。
- 时间。
- 收支类型。
- 币种模式。
- 目标币种。
- 分类筛选。
- 其他实际过滤条件。

禁止跨用户泄漏缓存内容。

# 6. B01–B05：基础收支金额与笔数

## B01 · 总支出

**定义：** 统计指定账本、时间范围、币种模式及其他筛选条件下的支出总额。

计算：

```text
TotalExpense = Σ EligibleExpenseAmount
```

输出：

- 精确支出金额。
- 统计币种。
- 有效交易笔数。
- 时间区间。
- 完整性。
- 来源筛选。

图表：

- 大数字卡。
- 迷你进度/摘要卡。
- 中等尺寸可附加简要来源信息。
- 大尺寸可附加 Agent B 提供的趋势结果，但不能自行创造独立趋势算法。

金额为零时显示真实零值；数据不完整时必须有相应说明。

## B02 · 总收入

与 B01 使用同一聚合核心，仅收支过滤条件不同。

计算：

```text
TotalIncome = Σ EligibleIncomeAmount
```

支持：

- 数字卡。
- 收入摘要卡。
- 扩展尺寸下的收入构成概览。

不得将收入与支出的退款语义简单混淆。

## B03 · 账目收支差额

计算：

```text
Net = TotalIncome - TotalExpense
```

输出：

- 精确净差额。
- 正/负/零状态。
- 收入和支出两个组成值。
- 完整性。
- 来源范围。

图表：

- 正负数字卡。
- 以零为基线的水平数值条。
- 大尺寸下显示收入与支出对照。

**名称应明确为账目收支差额，不等于真实账户余额。**

当收入或支出一侧数据不完整时，不得把结果标为完整净差额。

## B04 · 支出交易笔数

计算：

```text
ExpenseCount = Count(EligibleExpenseTransactions)
```

输出整数。

不得用分类组数量代替交易数量。

同一交易不可因多个展示维度被重复计数。

## B05 · 收入交易笔数

与 B04 共享计数实现。

仅过滤收入记录。

### B01–B05 推荐图表

- KPI 数字卡。
- 收入/支出对照卡。
- 简化正负条。
- 交易笔数卡。
- 中等卡片的迷你构成图。

### 必测边界

- 空账本。
- 只有收入。
- 只有支出。
- 多币种。
- 历史汇率缺失。
- 极大金额。
- 删除及恢复交易。
- 跨月筛选。
- 用户没有对应权限。

# 7. B06–B08：平均值与中位数

## B06 · 日均支出

推荐基础定义：

```text
DailyAverageExpense =
  TotalExpense / CalendarDaysInSelectedPeriod
```

分母应是选定区间内实际日历天数，而不是有交易的天数。

例如：

用户选择连续 10 天，总支出 500 元。

结果为：

```text
500 / 10 = 50 元/天
```

即使其中只有两天存在交易，日均支出仍然是 50 元/天。

注意：

- 今天尚未结束时，区间是否包含今天，取决于实际已解析的统计日期范围。
- 不得把“最近 30 天”与“当前自然月”混淆。
- 自定义时间范围必须明确边界。
- 零天或非法区间应返回不可计算。
- 数据覆盖不完整时不能声称准确日均。

输出：

- 日均金额。
- 总金额。
- 分母日数。
- 统计区间。
- 舍入依据。

图表：

- 数字卡。
- 对应日均水平的参考线或辅助摘要。
- 大尺寸下可使用 Agent B 的时间序列，但不重复实现。

## B07 · 单笔平均支出

计算：

```text
AverageExpensePerTransaction =
  TotalExpense / ExpenseTransactionCount
```

当支出笔数为零时，不存在平均单笔金额。

不要简单显示零元并暗示平均值为零。

对于不整除的金额，内部应保留足够精度，再根据显示规则输出。

输出：

- 单笔平均金额。
- 支出总额。
- 支出笔数。
- 计算状态。

图表：

- 数字卡。
- 简短的金额与笔数说明。
- 大型卡片可以增加分布相关入口。

## B08 · 单笔支出中位数

定义：

先取得符合条件的每笔支出金额，按精确金额排序。

如果样本数为奇数：

```text
Median = MiddleValue
```

如果样本数为偶数：

```text
Median = (MiddleLeft + MiddleRight) / 2
```

例如：

```text
10, 20, 30 → 20

10, 20, 30, 40 → 25
```

需要注意：

- 中位数计算以交易为样本，而不是按日聚合。
- 原币分析只使用对应币种的交易。
- 综合模式必须先采用统一、正确的逐笔折算金额。
- 不得使用浮点金额排序。
- 偶数样本的中位数可能落在半个最小货币单位上；内部应保留精确结果，显示时明确采用统一格式与舍入规则。
- 样本数为零时为不可计算。

图表：

- 中位数指标卡。
- 在支持分布图的详情页中作为参考统计线。
- 相关分布图由 Agent C 负责。

# 8. B09–B12：交易与日期极值

## B09 · 最大单笔支出

选择符合条件的支出交易中金额最大的一笔。

输出：

- 最大金额。
- 对应交易来源。
- 业务日期。
- 分类。
- 交易名称或可安全展示的摘要。
- 同值最大记录数量。

若多笔金额完全相同，应采用确定性的排序或显示并列记录数量。

不能随机选择其中一笔，导致刷新页面后显示不同来源。

图表：

- 最大单笔指标卡。
- 简洁交易摘要。
- 大尺寸可展示来源入口。

## B10 · 最小单笔支出

从符合条件的支出交易中找到最小金额。

默认语义应当是**有效支出交易的最小金额**。

需要核查项目中退款、冲销、零金额和负数支出的业务定义。

不得为了拿到一个正数擅自过滤所有非正记录。

如果既有合同允许这些记录参与，则应明确其统计语义；必要时把“最小正向支出”作为独立候选，而不是偷偷改变 B10。

输出与 B09 类似。

## B11 · 最高单日支出

先按业务日期汇总支出，再取金额最高的日期。

```text
DailyExpense(d) = Σ ExpenseAmountOnDate(d)

PeakExpenseDay = argmax DailyExpense(d)
```

注意：

- 这里比较的是单日支出总额。
- 不是最大单笔支出所在的日期。
- 必须使用业务交易日期。
- 多币种仍遵守原币或综合规则。
- 同值最高日期应有确定性处理。

输出：

- 日期。
- 当日总支出。
- 当日交易笔数。
- 并列最高日期数量。
- 对应日期的来源筛选。

图表：

- 数字日期摘要。
- 当日金额卡。
- 小型柱状强调图。
- 完整时间图由 Agent B 负责。

## B12 · 最高单日收入

与 B11 共享日期聚合和极值逻辑。

仅过滤收入。

# 9. B13–B14：有记录与无记录天数

## B13 · 有支出记录的天数

定义：

在选定日期范围内，存在至少一笔符合筛选条件支出交易的日期数量。

```text
ActiveExpenseDays =
  Count(Distinct BusinessDateOfExpense)
```

例如连续七天中只有周一、周三和周五存在支出记录，则结果为 3 天。

注意：

- 同一天有十笔支出，也只计算一天。
- 不因不同币种而重复计数同一天。
- 用户切换币种时，必须明确这是对应筛选范围内的支出记录天数。
- 如涉及缺失汇率，应区分“原始记录存在”和“可成功折算的记录”；不能静默丢弃原始记录。
- 如果分析结果基于离线部分数据，应明确覆盖不足。

图表：

- 数字卡。
- 有记录天数 / 观察天数比例条。
- 大尺寸下可与日历图结合。

## B14 · 无支出记录的天数

定义：

```text
DaysWithoutExpenseRecords =
  CalendarDaysInPeriod - ActiveExpenseDays
```

但只有在统计区间及交易数据覆盖完整的情况下，才能给出可信结果。

**必须将其称为“无支出记录天数”，而不是“没有花钱的天数”。**

因为：

没有记账，并不等于现实中没有消费。

例如某个日期没有录入账目，我们只能证明系统没有相应记录，不能证明用户真的没有花钱。

图表：

- 数字卡。
- 有记录/无记录比例条。
- 简化日历摘要。

如果离线数据没有覆盖完整区间，必须显示不完整状态。

# 11. B18–B19：基础比例分析

## B18 · 收支比

定义：

```text
ExpenseIncomeRatio =
  TotalExpense / TotalIncome
```

可显示为百分比。

例如：

```text
收入 5000
支出 3000

收支比 = 3000 / 5000 = 60%
```

必须注意：

- 分母为零时不能计算。
- 收入可能为负或出现特殊调整记录，需根据既有业务语义判断比例是否有意义。
- 支出超过收入时，结果可以超过 100%。
- 不得为了好看将结果强行截断为 100%。
- 综合折算不完整时不能显示完整比率。
- 不得将它称为“预算使用率”，因为没有预算分母。

图表：

- 百分比数字卡。
- 水平比例条。
- 在超过 100% 时支持明确的超出状态。
- 大尺寸显示收入和支出组成金额。

## B19 · 账面结余比例

定义：

```text
LedgerSurplusRatio =
  (TotalIncome - TotalExpense) / TotalIncome
```

例如：

```text
收入 5000
支出 3000

账面结余比例 = 40%
```

此结果可以为负。

它不应无条件命名为“储蓄率”。

原因是 Libevra 目前没有完整的账户、真实转账和资产负债模型。

**账面结余比例不等于实际资金储蓄率。**

与 B18 一样，需要处理零分母、负收入和不完整数据。

图表：

- 正负比例卡。
- 以零为基线的比例条。
- 对应收入、支出、差额的解释。

# 13. I01–I02：分类构成分析

## I01 · 支出分类构成

这是 Agent A 最重要的图表之一。

计算流程：

1. 获取当前条件下符合要求的支出账目。
2. 按分类 ID 分组。
3. 计算每类的精确金额。
4. 计算总支出。
5. 计算各分类所占比例。
6. 根据金额或用户指定规则排序。
7. 返回分类信息、金额、笔数、比例和来源。

计算：

```text
CategoryExpense(c) =
  Σ ExpenseAmountInCategory(c)

TotalExpense =
  Σ CategoryExpense(c)

Share(c) =
  CategoryExpense(c) / TotalExpense
```

需要保证分类金额合计与总支出一致。

不能因为“其他”分组而丢失部分金额。

### 图表形式

至少支持：

1. 环形图。
2. 分类横向条形图。
3. 分类排行列表。
4. 百分比构成条。

未来还可以与 Treemap、旭日图兼容，但复杂图表由 Agent C 实现。

### 交互

环图应支持：

- 选择分类。
- 选中部分高亮。
- 中心金额和名称更新。
- 图例联动。
- 查看对应分类金额。
- 查看分类占比。
- 打开来源账目。
- 处理未分类与其他分组。

不可只通过颜色区分分类。

### “其他”分类规则

如果分类很多，可以将低占比类别折叠为“其他”。

但：

- “其他”必须代表真实分类的合计。
- 应返回其包含的具体分类 ID。
- 必须支持展开。
- 不能将它当作一个真实数据库分类。
- 点击“其他”后可以继续查看其组成。
- 来源追溯要包含其所有组成分类。
- 不能将金额较大的类别不合理地隐藏在不可展开的其他分组中。

### 数据准确性

- 所有分类金额精确求和。
- 占比使用高精度分数计算。
- 百分比显示允许四舍五入。
- 如果显示百分比相加不是恰好 100%，需要采用一致的显示策略，不能因此修改金额。
- 环图角度应基于统一的可靠归一化结果。
- 缺汇率导致不完整时，不能把部分金额伪装成完整构成。

## I02 · 收入分类构成

与 I01 使用同一计算和图表核心。

只是改为收入类型。

需要正确处理：

- 没有收入分类。
- 所有收入都在一个分类。
- 分类数量很多。
- 收入来源记录缺少分类。
- 原币与综合模式切换。

不允许复制出一套完全不同的环图实现。

# 14. I03–I04：分类金额排行

## I03 · 支出分类排行

计算：

按分类汇总支出金额，然后按金额降序排列。

输出：

- 分类名称。
- 精确金额。
- 排名。
- 交易笔数。
- 占总支出比例。
- 来源筛选。

排序必须确定。

若金额相同，应采用稳定、可解释的次级排序规则。

建议使用：

- 主要排序：金额降序。
- 次级排序：稳定分类 ID 或现有明确的分类顺序。

不要使用会因语言变化而不稳定的随机排序。

### 图表

至少支持：

- 横向条形图。
- 排行列表。
- 带数值标签的分类榜单。
- 简化 Top N 卡片。

### 重要规则

- 条形长度应与金额成比例。
- 应明确零基线。
- 不得使用不恰当的非零截断坐标夸大差距。
- 非常小的金额不能被错误放大成与最大分类相近的长度。
- 数值标签必须展示真实金额。
- 排行数量应可配置，例如 Top 3、Top 5、Top 10。
- Top N 之外的分类不能消失于权威总额之外。
- 点击某类可进入对应来源。

# 16. I17：支付方式构成

## I17 · 支付方式分析

在真实数据模型支持可靠支付方式字段的前提下，按支付方式汇总交易。

默认以支出金额构成为主。

可以允许切换：

- 支出金额。
- 收入金额。
- 交易笔数。

但这应作为受支持的分析参数，不得将三者混为同一指标。

### 计算

```text
PaymentMethodExpense(m) =
  Σ ExpenseAmountUsingPaymentMethod(m)
```

并计算：

- 支付方式金额。
- 交易笔数。
- 占比。
- 排名。
- 未指定支付方式金额。
- 来源交易。

### 图表

- 环形图。
- 横向条形图。
- 百分比堆叠条。
- 支付方式排行。

### 特殊限制

支付方式是交易的描述性维度。

不得根据支付方式名称推导：

- 真实银行余额。
- 信用卡债务。
- 账户之间的资金流向。
- 转账排除。
- 实际持有资产。

如果现有数据库没有可靠的结构化支付方式字段，则必须标记为“等待数据能力确认”，不得通过备注文字猜测支付方式并冒充正式统计。

# 18. 卡片尺寸自适应

Agent A 需要支持真实容器尺寸，而不是单纯按屏幕型号判断。

原因：

Libevra 未来允许：

- 两列和三列网格。
- 不同占格尺寸。
- 自由分割容器。
- 滑动抽屉。
- 平板和桌面布局。

因此同一张卡可能出现在不同宽高比的区域。

## 18.1 不强制固定像素门槛

1×1、1×2、2×2 是占格预设。

真实展示密度应根据容器的实际可用宽度和高度决定。

可以研究：

- Compact。
- Medium。
- Expanded。

这些是内容密度模式，不等同于固定的格数。

## 18.2 紧凑卡片

优先：

- 核心数值。
- 简短标题。
- 必要单位。
- 数据状态。
- 可进入详情的明确交互。

不能在极小卡片里强制展示完整环图图例或十项排行。

## 18.3 中型卡片

可以显示：

- 图表主体。
- 主要数据标签。
- 简短说明。
- 部分分类/交易信息。

## 18.4 大型卡片

可以显示：

- 完整图表。
- 多个数据标签。
- 详细图例。
- 选择状态。
- 解释。
- 来源入口。

## 18.5 最小可读性

需要测试：

- 很长的金额。
- 负金额。
- 小数币种。
- 零小数币种。
- 长分类名称。
- 英文语言。
- 大字体。
- 七主题。
- 浅色和深色。
- 很窄但较高的容器。
- 很宽但较矮的容器。

不要通过无限缩小字号维持布局。

当区域不适合完整图表时，切换成内容更少的摘要形态。

# 19. 图表视觉与交互标准

## 19.1 整体视觉

沿用 Libevra：

- 品牌绿色 `#55997a`。
- 克制的色彩。
- 清楚的数字层级。
- 自然留白。
- 柔和动画。
- 七主题兼容。
- 中文和英文兼容。

不要大量加入不符合整体应用风格的默认图表库颜色。

具体视觉规范应服从 Codex 提供的共享设计系统。

## 19.2 动画

建议：

- 轻量淡入。
- 柔和数值/形状过渡。
- 选中状态变化。
- 图例联动。

但：

- 不允许动画制造虚假的财务金额。
- 不应在异步加载期间先展示错误金额。
- 不完整数据不能通过动画伪装成完整。
- 尊重 reduced-motion。
- 大量卡片同时显示时不能让所有图表持续高频动画。

## 19.3 交互优先级

工作台卡片主要用于快速阅读和进入详情。

允许轻量交互，例如分类高亮。

复杂的：

- 全部分类展开。
- 来源明细。
- 精细图表探索。
- 多项比较。

可以由完整详情页负责。

不能为了功能丰富，让一张小卡片塞满按钮。

## 19.4 图例

分类图例应包含：

- 分类颜色或符号。
- 分类名称。
- 金额或笔数。
- 必要时的占比。

不可只显示颜色和名称，却把真实金额隐藏在需要精确悬停才能看到的位置。

## 19.5 可访问性

必须支持：

- 键盘访问。
- 屏幕阅读器可用的文本。
- 足够的点击或触摸区域。
- 颜色以外的区别信息。
- 数字和表格替代视图。
- 减少动态效果。

这里不要求每张图表单独开发一套完整表格系统。

应设计可复用的数据表或语义摘要组件。

# 20. 图表的数学与视觉正确性

## 20.1 权威计算与绘图区分

例如分类金额分别为：

```text
餐饮 1200
交通 600
娱乐 200

总计 2000
```

分类占比：

```text
餐饮 60%
交通 30%
娱乐 10%
```

环图角度：

```text
216°
108°
36°
```

绘图可以使用浮点角度。

但用户看到的金额与来源，必须来自精确计算结果。

## 20.2 缺失数据

如果某些交易缺少汇率：

不能简单将可折算部分重新归一化为 100%，然后称其为全部支出分类占比。

必须使用明示的部分覆盖语义，或在不满足完整构成条件时禁用完整占比图。

## 20.3 零数据

如果没有支出：

不要画一个看似“100% 未分类”的完整环。

应展示明确的无数据状态。

## 20.4 分类名称与身份

分类显示名称可能被用户更改。

计算时应使用稳定分类身份，而不是仅按当前名称分组。

如果同名分类实际是不同 ID，应根据正式业务语义处理，不得擅自合并。

## 20.5 删除分类与历史数据

历史账目可能引用已删除分类。

需要根据现有数据模型和业务合同处理。

不能直接丢弃相关账目金额。

## 20.6 排序和颜色

分类排序可以随金额变化。

但颜色应尽可能保持稳定。

否则用户本月看到绿色代表餐饮，下个月同一绿色又代表交通，会造成误解。

# 21. 逐项测试要求

本任务的财务计算属于高风险部分，应进行严格测试。

但不需要让每一种简单图表都重新执行全项目安全审计。

## 21.1 基础测试样本

至少建立以下测试数据：

### 样本 A：空账本

没有任何交易。

验证：

- 总额为零。
- 交易笔数为零。
- 平均值和中位数不可计算。
- 极值无结果。
- 环图为空状态。

### 样本 B：只有收入

三笔收入，无支出。

验证：

- 收入合计正确。
- 支出总额为零。
- 净差额正确。
- 支出平均值不可计算。
- 支出分类构成为空。

### 样本 C：只有支出

多分类、多笔支出。

验证金额、分类汇总、排行和比例。

### 样本 D：金额相同

多个分类或交易金额完全相同。

验证确定性排序。

### 样本 E：一个分类

全部支出属于同一分类。

环图应正确展示单一完整扇区。

### 样本 F：大量分类

至少几十个分类。

验证“其他”、排行、图例和小扇区处理。

### 样本 G：大整数金额

包含超过 `Number.MAX_SAFE_INTEGER` 的最小单位金额。

验证求和、排序、平均、中位数和格式化。

### 样本 H：跨月份

例如九月末到十月初。

验证实际生效日期范围与来源一致。

### 样本 I：多币种

USD、CNY、EUR 同时存在。

验证原币隔离与历史折算。

### 样本 J：汇率缺失

部分记录缺少可用汇率。

验证完整性与构成分析行为。

### 样本 K：多人共享

只读成员与有编辑权限成员。

验证只读查询不扩大权限。

### 样本 L：离线数据不足

本地只保存部分日期的交易。

验证“无支出记录天数”与其他依赖完整覆盖的指标不会给出虚假完整结果。

### 样本 M：删除及恢复

交易经历编辑、删除、恢复。

验证统计与来源查询一致。

### 样本 N：特殊小数精度

测试：

- 金额不能整除平均值分母。
- 偶数样本中位数产生半个最小货币单位。
- 百分比结果需要舍入。
- 极小分类金额在图表中接近零。

### 样本 O：不同过滤条件

分别设置：

- 不同时间。
- 不同收支类型。
- 不同分类。
- 不同币种。
- 不同账本。

验证缓存隔离和分析结果变化。

## 21.2 每个分析必须具备的测试

对于 B01–B20、I01–I05、I17：

至少测试：

1. 正常结果。
2. 空数据。
3. 一个相关边界条件。
4. 币种/精度适用性。
5. 来源追溯或可解释性。

相近的分析允许共用底层测试夹具。

但不能因为两个功能共享函数，就完全不验证其中一个分析定义。

## 21.3 图表测试

重点检查：

- 数值是否对应计算结果。
- 图表标签是否正确。
- 颜色是否稳定。
- 图例是否完整。
- 小尺寸是否溢出。
- 空状态。
- 负数。
- 大金额。
- 单分类。
- 大量分类。
- 主题和语言。

纯视觉微调只需有针对性的组件或截图检查，不必重复数据库级回归。

## 21.4 来源一致性

至少为金额类分析建立一致性用例：

```text
分析显示的金额
    ==
同一分析条件下来源账目的权威汇总
```

对于平均值：

```text
平均值的精确计算依据
    ==
来源总额 / 正确分母
```

对于分类构成：

```text
所有互斥且完整的分类金额之和
    ==
对应支出或收入总额
```

不允许图表自己生成一套与来源不一致的统计。

# 22. 性能目标与缓存

因为未来用户可能添加几十张分析卡片，需要避免重复计算。

请研究：

- 相同查询的去重。
- 共享聚合结果。
- 分组结果复用。
- 缓存的账号和账本隔离。
- 数据编辑后的失效。
- 离线同步后的失效。
- 切换时间或币种后的失效。
- 图表不可见时的按需渲染。
- 多个卡片同时请求时的优先级。
- 大账本下的性能基线。

尽量使用一次聚合产生多个基础指标，例如一次遍历得到：

```text
收入总额
支出总额
收入笔数
支出笔数
最大单笔
最小单笔
分类分组
日期分组
```

但不要为了节省循环次数，将业务语义不同、错误处理不同的统计强行耦合在一起。

需要对不同数据量进行测试，并记录实际性能。

不要未经测量承诺某个固定耗时。

Agent A 交付的不只是 26 种统计功能。
