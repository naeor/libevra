## Q1. 分布图的直方图分箱算法

- **问题**：分布分析（AN-C 系列）把金额分成若干箱。两种常用算法会产生不同箱数与箱宽，用户看到的分布图形状会不同。
- **选项**：A. `nice-bin-width`（当前 C 已实现，箱宽取整齐数值）；B. `Sturges`（按样本量算箱数）；C. 两者都支持、结果里标注算法（会增加一个用户可见选项）。
- **A 建议**：选 **A（nice-bin-width）**，结果里固定标注 `method="histogram-nice-bin-width"`。
- **理由**：C 已实现并有测试；箱宽整齐、图例易读；Sturges 在小样本下箱数偏多、且与 C 现有实现不一致。
- **暂不决定的影响**：分布图无法冻结算法口径，A/C 图表验收会卡在这一项。

## Q2. 分位数必须提供哪几个点

- **问题**：分布分析要展示分位点（P25/P50/P75 等），决定表格与箱线图显示哪些数字。
- **选项**：A. 只要求 **P25 / P50 / P75 + IQR**；B. A + 显式可选 P10/P90（需分析定义显式开启）；C. 任意 p 都由用户配置。
- **A 建议**：选 **B**（必填 P25/P50/P75+IQR，P10/P90 作为显式可选参数）。
- **理由**：B 覆盖大多数读图需求，又不在默认界面堆指标；任意 p 会让协议与校验复杂化。
- **暂不决定的影响**：distribution 结果字段无法定稿，箱线图和分位表无法验收。

## Q3. P13 四指标交叉表归到哪个形状

- **问题**：C 的 P13（分类 × 时间的金额/笔数/日均/占比四指标表）目前同时被 `matrix`（P01–P04）与 `pivot` 覆盖，定义重复。
- **选项**：A. 归 **pivot**（matrix 只保留 P01–P04）；B. 归 matrix（pivot 只留其他透视项）；C. 两处都登记（不推荐，会双份实现）。
- **A 建议**：选 **A**。
- **理由**：pivot 本身就是「多指标交叉表」；matrix 定位是固定分析矩阵，混入四指标会让两个形状语义重叠。
- **暂不决定的影响**：P13 可能被两套代码各实现一次，产生口径不一致。

## Q4. C 的「部分完整」状态如何映射到统一完整性

- **问题**：C 的部分结果使用三/四态（complete / partial / unavailable），S-01 v2 用九态完整性。需要确定 `partial` 对应哪个统一状态。
- **选项**：A. `partial → fx-incomplete`（另用 `unavailableReason` 说明具体原因）；B. 新增一个统一 `partial` 状态（改动更大）；C. 由各形状自定义、不映射。
- **A 建议**：选 **A**（附映射表：C complete→complete、partial→fx-incomplete、unavailable→按原因归入 fx-incomplete/request-failed/no-permission）。
- **理由**：不扩枚举、与 A/B 的缺失语义一致；`unavailableReason` 保留具体原因。
- **暂不决定的影响**：C 与 A/B 的部分完整状态无法互认，跨形状比较会出现「同样缺 10% 却显示不同状态」。

## Q5. P16（币种构成）的完整性用几态

- **问题**：P16 只统计「已成功折算」的部分，C 实现用三态（完整/部分/不可用），统一协议写的是九态。语义上 P16 不能笼统说「部分」。
- **选项**：A. 保持 C 三态（完整/部分/不可用）+ 原因字段；B. 统一为九态（需 C 改实现）；C. 不标状态、只标缺失笔数。
- **A 建议**：选 **A**，并强制附 `unavailableReason`（缺汇率/无交易/权限）。
- **理由**：不逼 C 重写；同时要求原因字段，避免「部分」二字丢失信息。
- **暂不决定的影响**：币种构成卡片的空/缺/权限状态展示不一致。

## Q6. P20（汇率回退）的「无折算需求」标记放在哪一层

- **问题**：P20 中「本区间没有需要折算的金额」与「不可用」不同，需要标记 `available`。C 把它放在 web 适配层，协议层没有对应字段。
- **选项**：A. 放**适配层**（web 内部派生，协议不动）；B. 放**结果层**（P20 结果显式字段，所有消费方都能读到）；C. 不标记，用空结果表达。
- **A 建议**：选 **B**（结果层加一个可选标记，与 completeness 并列）。
- **理由**：A 的话同一结果换渲染端可能丢标记；B 让来源追溯/导出/无障碍文本都能用同一事实。
- **暂不决定的影响**：「无需折算」可能被渲染成「无法计算」，用户误解。

## Q7. B 与 C 的日历/多桶图归属

- **问题**：B 的日历热力图与 C 的 `calendar` 分析指向同一份数据；small-multiples（小多图）的桶轴也没有统一来源。
- **选项**：A. **只冻结 B 的 `calendar-heatmap`**，C 的 `calendar` 作为纯投影、small-multiples 复用 B 的 `TimeAxisHint`；B. C 也保留独立形状（两份日历实现）；C. 暂不规定，W3 再定。
- **A 建议**：选 **A**（C 已同意）。
- **理由**：避免两套日历口径；B 已实现周一起始、ISO 周、五态与分位强度；C 只做展示投影最省成本。
- **暂不决定的影响**：日历与多小图可能出现两种强度/周界算法，互相矛盾。

## Q8. 冻结常量按什么规则分类（F/C/O/P）

- **问题**：协议登记了 40+ 个数值常量（如分析区间上限、明细上限、箱线图最小样本、TopN、桑基连线上限）。需要您确认分类规则，而不是逐个讨论几十个数字。
- **选项**：A. 按 **F=冻结（协议不变量）/ C=可配置（产品可调）/ O=需所有者确认 / P=占位（W3 视觉定稿前）** 四类，由 A 先归类、您只审 O 类；B. 全部冻结；C. 全部可配置。
- **A 建议**：选 **A**；并请您重点确认 6 个 O 项：明细上限 50,000 笔、月键上限 36 个月、箱线图最小可靠样本 5、小多图 TopN 24、交叉表组合上限 5,000、桑基连线上限 4,000。
- **理由**：分类规则一次定清，后续常量增补不必反复打扰您；O 类才真正影响业务可解释性。
- **暂不决定的影响**：协议无法宣称「常量已确认」，冻结检查清单 G-33 卡住。

## Q9. 枚举与白名单是否冻结为协议枚举

- **问题**：透视指标（金额/笔数/日均/占比）、高级维度、排名策略等是 C 的能力边界，是否写进协议当正式枚举。
- **选项**：A. **冻结为协议枚举**（新增能力必须升协议版本）；B. 允许各 Agent 自行扩展、结果里标 `domain`；C. 先不定，W3 再说。
- **A 建议**：选 **A**（按 C 已实现列表冻结，新增走协议版本）。
- **理由**：保护兼容性；否则 B/C 扩展时消费方无法判断支持范围。
- **暂不决定的影响**：跨 Agent 传输出现「字段存在但对方不认识」的静默忽略。
