## 3. 逐项落实

### 3.1 OQ-LM-03（垂直紧凑与投影组合）

**原始问题（布局规格 §14.4、§20.2）**：垂直紧凑已在 2026-10-27 确认“默认采用”且保护 Spacer/容器结构/明确保存位置；但 **(a) 紧凑是否应用于投影**（推荐应用、仍待决）、**(b) “明确保存的位置”指什么**、以及 Spacer 锚定留下的空行如何处理，仍未裁定。D-3 实现为可切换开关 `ProjectOptions.verticalCompact`，默认 `false`。

**所有者方向**：支持紧凑，但不得裁切真实内容；卡片可按空间改变展示密度、图表可精简刻度/图例/摘要；空间不足须保留明确展开或详情入口，不得溢出。

**逐点对照**：
- “支持紧凑” ↔ (a) 的组合方向：方向支持“支持”，但未说明是否默认应用于投影、以及投影与紧凑的先后关系 → **未闭合**。
- “不得裁切真实内容 / 密度自适应 / 图表精简” ↔ 布局层职责：布局层（E 层）只做位置与尺寸，不裁切、不改金额口径；密度与图表精简属卡片/图表层（C/B 层）按真实尺寸决定 → **一致，可落实为跨层约束**。
- “保留展开/详情入口、不得溢出” ↔ 既有 C-1…C-10、compat 1×1、`minSize`/`sizeLadder` → **一致**。
- “Spacer 空行/明确保存位置” ↔ 原 (b)：方向未提及 → **未闭合**。

**落实（正式决定）**：
- **D-OQ-03a**：垂直紧凑是受支持的产品行为（与既有 Q-09 默认方向一致）；紧凑**只改变对象在网格中的位置**，不得裁切、隐藏或以遮挡代替内容；不得因紧凑改变金额口径。
- **D-OQ-03b**：空间不足时，卡片/容器的密度与图表精简由卡片/图表层按真实内容盒决定；布局层必须保留明确的展开或详情入口，不得让内容溢出格子。
- **D-OQ-03c**：Spacer 不得因紧凑被当作普通空洞消除（与既有确认一致）。

**未闭合（给 Lead/所有者）**：见 §4 DIFF-01（(a) 默认启用与组合顺序、(b)“明确保存的位置”定义、Spacer 空行；以及 D-3 当前默认 `false` 与方向之间的实现待调整关系）。

### 3.2 OQ-LM-04（Spacer 窄屏降级）

**原始问题（布局规格 §16.6、§20.2）**：候选 a 夹宽（夹具默认）/b 夹宽限高/c 临时折叠/d 不处理；无论选哪个，**未经所有者确认不得自动删除 Spacer**；区分用户删除 vs 系统临时降级只写派生标记（`shrunk`/`suppressed`）永不写回。

**所有者方向**：Spacer 保持真正布局对象身份；窄屏迁移可调整展示尺寸与位置，但不得删除、不得改权威主布局；派生布局必须可重复计算，不得因反复切换宽度漂移。

**逐点对照**：
- “窄屏可调整尺寸与位置” ↔ 候选 a（夹宽）+ 投影重排 → **一致**；b（限高）当前场景不需要，c（临时折叠）与“保持真实对象身份”不冲突但非必需。
- “不得删除 / 不得改权威主布局 / 派生可重复计算、无漂移” ↔ 既有规则（投影纯函数、不写回、INV-6 幂等/无漂移）→ **一致**。

**落实（正式决定）**：
- **D-OQ-04**：Spacer 窄屏降级采用**夹宽（`min(colSpan, 目标列数) × rowSpan`）+ 投影重排**；可调整显示尺寸与位置，但**不删除、不写回权威主布局**；派生结果必须可重复计算、反复切换宽度不漂移；任何临时降级只写派生标记，不产生删除记录。

**差异**：无实质差异；b/c 候选暂无必要，若后续出现高度不足的真实场景再评审。

### 3.3 OQ-LM-05（容器入口与完整查看）

**原始问题（布局规格 §17.4、§17.7、§20.2）**：①收缩容器 1×1 入口的具体 UI（推荐图标+短名+N 张卡片+打开）；②完整查看用 A 独立详情页 / B 全屏面板 / C 自适应容器。

**所有者方向**：区分浏览态/编辑态；浏览态 Carousel 容器内横滑；无法完整展示的容器可提供展开入口（覆盖层/详情视图，不破坏外部网格位置）；编辑态可进容器内部编辑子卡片；必须处理“容器内滑动 vs 工作台拖动”手势冲突。

**逐点对照**：
- “浏览态/编辑态区分” ↔ 既有普通/编辑模式严格分离 → **一致，可落实**。
- “浏览态 Carousel 横滑” ↔ 既有 Q-13 手势原则（普通/编辑分离、不抢纵向滚动）→ **一致，可落实**。
- “展开入口：覆盖层/详情视图，不破坏外部网格位置” ↔ 候选 B/C（非 A 独享）→ **部分落实**；最终形态未定。
- “编辑态可进容器内部编辑子卡片” ↔ 原规格未定义的新增能力（首版深度 1 不变）→ **可落实为能力方向，交互细节待原型**。
- “1×1 入口具体 UI” ↔ 原问题核心之一：方向未说明 → **未闭合**。

**落实（正式决定）**：
- **D-OQ-05a**：浏览态与编辑态行为严格分离；浏览态容器内横滑切页，编辑态容器停止浏览手势、按编辑命令处理。
- **D-OQ-05b**：无法完整展示的容器必须提供展开入口；入口形态限定为**覆盖层或详情视图**，打开与关闭不改变容器外层网格位置与尺寸。
- **D-OQ-05c**：编辑态允许进入容器内部编辑子卡片（新增能力；首版容器深度仍为 1，容器内不放容器/Spacer）。
- **D-OQ-05d**：必须显式定义“容器内横滑 / 工作台拖动 / 页面纵滚 / 图表读数 / 卡片点击”的手势优先级；不能由同一手势同时触发两类操作。

**未闭合**：1×1 入口的具体 UI、完整查看 A/B/C 最终选型、容器详情与卡片详情的关系、容器内部编辑的清单/槽位交互（与 Codex OQ-UI-12 同源）。

### 3.4 OQ-LM-06（自动收缩与用户主动收缩）

**原始问题（布局规格 §17.6、§20.2）**：自动收缩与用户主动收缩的区别：字段、编辑模式表现、在窄布局里如何编辑被自动收缩的容器；推荐 `presentation`=full|collapsed（用户意图）、`expandedSize`（完整尺寸）、派生 `form` 永不写回。

**所有者方向**：不默认全部缩 1×1；新容器使用能表达用途的合理默认尺寸；所有要求支持 1×1 的容器必须保留 1×1 与恢复入口；收缩只改展示形态，不删除内部卡片与配置。

**逐点对照**：
- “不默认全缩 1×1” ↔ §17.3 只在完整宽度不足且无合法紧凑档、或内部最小可读不满足时收缩 → **一致**。
- “新容器合理默认尺寸” ↔ 新能力方向（默认尺寸数值未定，由模板/家族另行定义）→ **可落实为规则，数值待定**。
- “保留 1×1 与恢复入口” ↔ C-1…C-10 → **一致**。
- “收缩只改展示形态，不删内部卡片与配置” ↔ §17.2 三样分开存、派生永不写回 → **一致**。

**落实（正式决定）**：
- **D-OQ-06**：容器不得默认缩为 1×1；仅在目标列数/宽度不足且无合法紧凑档、或内部最小可读不满足时收缩（§17.3 不变）。新容器创建时使用能表达用途的合理默认尺寸（具体数值由模板/卡片家族在后续批次定义，本决定不发明数值）。所有支持 1×1 的容器保留 1×1 与恢复入口。收缩仅改变展示形态，不删除内部卡片、配置、顺序或比例；`presentation`=用户意图、`expandedSize`=完整尺寸、派生 `form` 永不写回，保持不变。

**未闭合**：编辑模式中“被自动收缩的容器”的界面表现与窄布局提示细节（属 D-2 UI / Codex 视觉范围），不阻塞字段语义。

### 3.5 OQ-LM-07（统一模式跨列编辑写回）

**原始问题（布局规格 §18.3、§20.2）**：在非基准列数的设备上编辑并保存后，主布局如何落点：M1 以编辑后排列为新主布局（baseCols=2 并提示，推荐起点）/ M2 只并回相对改动 / M3 仅基准列数设备可编辑。

**所有者方向**：拖放预览 + 合法位置高亮；非法位置不得静默丢内容；手机端除长按拖动外需触控友好替代（如点击添加后选位置）；编辑支持撤销；明确保存/取消/未保存行为。

**逐点对照**：所有者方向全部属于**编辑交互质量要求**（D-2 UI 范围），**没有回答**“主布局写回落点 M1/M2/M3”这一原问题。

**处理**：**不裁定 OQ-LM-07**，原问题保持待所有者；方向另登记为交互设计决定（见 [S17-Agent-D-布局与交互设计稿-v1.md](./S17-Agent-D-布局与交互设计稿-v1.md) §4）。请 Lead 向所有者重新明确：跨列编辑保存后主布局的落点规则。

### 3.6 OQ-CF-01（配置合并粒度）

**原始问题（配置草案 §4.5、§10）**：同步合并粒度：内容文档逐对象合并 vs 整体替换；首版推荐“内容逐对象、布局整体替换 + 保留被覆盖方为上一个布局”；必须不丢对象 ID/容器结构/Spacer、冲突可见可恢复。

**所有者方向**：用稳定对象 ID + 明确配置版本，避免整份覆盖；互不冲突的独立卡片配置尽量安全合并；容器内部结构操作保持原子性；真实冲突不得静默丢配置；对照已有同步架构给最小可行实现。

**逐点对照**：
- “稳定 ID + 明确版本” ↔ 既有 `objectId`/schemaVersion/version → **一致**。
- “独立卡片配置安全合并” ↔ 内容文档逐 objectId 合并（§4.5 推荐）→ **一致，可正式确认**。
- “容器内部结构原子” ↔ 容器树整体取舍（§4.5 推荐）→ **一致**。
- “冲突不得静默” ↔ §4.5 强制项 → **一致**。
- “避免整份覆盖” ↔ 现行布局文档“整体替换” → **冲突**（布局文档是整份几何，若逐对象合并需新的几何冲突规则）。
- “对照已有同步架构” ↔ 当前 W6 服务端同步**尚未实现**（D-4 只有接口占位），无既有架构可对照 → 只能给契约级最小可行实现。

**落实（正式决定）**：
- **D-OQ-CF-01a**：内容文档按 `objectId` 逐对象合并；新增并集、单侧删除可判、双方都改不静默覆盖（保留可见副本）。
- **D-OQ-CF-01b**：容器内部结构（children 顺序、GridSplit 比例、Carousel 页）作为**原子单元**合并，不拆散、不部分写入。
- **D-OQ-CF-01c**：真实冲突必须可见、可恢复，不得静默丢失配置。

**未闭合**：布局文档的合并粒度（继续整体替换 + `previousMain`，还是改为逐对象合并）需所有者/Lead 明确；服务端最小可行实现待 W6 批准与迁移评审。

### 3.7 OQ-CF-05（预置分类稳定键）

**原始问题（配置草案 §6.5、§10）**：系统预置分类只有中文 `name`/`description` 与 `isSystem`，没有独立稳定键；分享导入映射：以预置原名为键，或新增 key 字段（属数据模型变更）；在此之前所有分类引用一律“待绑定占位”。

**所有者方向**：用稳定内部能力 ID/分类标识，不用随语言变化的中文显示名作持久化身份；不同账本分类可能不同，切换账本不得把同名分类当相同业务分类；缺失时提示重选或显示不适用，不得伪造匹配。

**逐点对照**：与原始推荐一致 → **一致（原则层面）**；具体键形态（新增字段 vs 预置原名键）仍是原 OQ 待决部分，且涉及数据模型变更。

**落实（正式决定）**：
- **D-OQ-CF-05**：卡片/模板中的分类引用只允许**稳定内部键（能力 ID / 分类标识）**，禁止以显示名（含中文名、翻译名）作为持久化身份；切换账本时不按同名自动绑定；缺失引用显示“待绑定/不适用”，不得伪造匹配。

**阻塞**：稳定键的具体形态与数据模型变更需所有者批准（原 OQ-CF-05 选项，W6/数据模型变更流程）。

### 3.8 OQ-CF-07（分享内容治理）

**原始问题（配置草案 §6.4、§10）**：分享内容审核：模板名称/描述的字符集、违禁词、举报与下架流程（G-03），与 S19 法律关口的关系；候选“限长度与字符集 + 举报入口；是否允许自定义文本由所有者定”。

**所有者方向**：卡片/布局/分享模板须有明确允许字段与校验；分享模板可含布局结构、支持的分析能力 ID、展示类型与安全配置；禁止含真实账单/财务结果/余额/真实账本标识/敏感信息；禁止脚本执行；限制非法嵌套、循环引用、异常对象数量与超大配置。

**逐点对照**：

- 审核流程（字符集/违禁词/举报下架/法律关口）↔ 原 OQ 核心：方向未回答 → **未闭合**。

**落实（正式决定）**：

**未闭合**：模板名/描述字符集与违禁词、举报与下架流程、与 S19 法律关口的衔接（原 OQ-CF-07 核心）仍需所有者决定。
