## 1. 传输与部署

- **✅｜全站 HTTPS，证书自动续期**｜Caddy 以站点块域名自动申请 Let's Encrypt 证书；仓库里没有手写证书或自签证书；`email` 行由 entrypoint 条件渲染。｜证据：`deploy/Caddyfile:63`、`deploy/Caddyfile:27-49`。｜建议措辞：「全站 HTTPS，证书自动签发与续期」。

- **✅｜只有一个服务有公网端口：80 / 443（含 443/udp 的 HTTP/3）**｜生产 compose 里 `web` 是唯一带 `ports:` 的服务。｜证据：`deploy/docker-compose.prod.yml:131-137`。｜建议措辞：「公网只开放 80 和 443 两个端口」。

- **✅｜数据库与 API 不暴露公网**｜`db` 与 `api` 都没有 `ports:`，只挂在 `internal` 网络上；PostgreSQL 跑在容器里，宿主机不装。｜证据：`deploy/docker-compose.prod.yml:37,58,93,180`；`deploy/README.md:34,126`。｜建议措辞：「数据库与接口都在内网，公网连不上」。

- **✅｜防火墙只放行 SSH 与 80/443（有运维手册步骤）**｜`deploy/README.md` 给出 `ufw allow 80/tcp` / `443/tcp` 的启用步骤。｜证据：`deploy/README.md:112-119`。｜建议措辞：「服务器防火墙只放行 SSH 与 Web 端口」。**限定**：这是文档步骤，具体机器的 `ufw status` 未在本仓库留证（见 §15）。

- **✅｜安全响应头成套配置**｜HSTS、`nosniff`、`Referrer-Policy`、`Permissions-Policy`、`X-Frame-Options: DENY`、`-Server`（去掉 Server 头）。｜证据：`deploy/Caddyfile:74,80,81,85,89,112`。｜建议措辞：「一整套浏览器安全响应头」。

- **🟡｜HSTS 只有 1 天，且无 preload / includeSubDomains**｜Caddyfile 注释写明「短 max-age、无 preload 是有意的，等站点稳定后再加」。｜证据：`deploy/Caddyfile:70-74`。｜建议措辞：「已启用 HSTS（当前为渐进式短周期）」。**不要说**「强制 HTTPS 两年 / 已加入 preload 列表」。

- **✅｜CSP 严格：脚本无 inline、无 eval**｜`script-src 'self'`；`style-src` 的 `unsafe-inline` 只用于 React 行内样式动画，注释解释了原因。｜证据：`deploy/Caddyfile:91-110`（策略全文在 :110）。｜建议措辞：「内容安全策略禁止外部脚本与内联脚本」。**限定**：样式仍允许 inline（`:96-100`），别说「零 inline」。

- **✅｜Caddy 管理接口关闭**｜`admin off`，本机无法通过 2019 端口改配置。｜证据：`deploy/Caddyfile:25`。｜建议措辞：「反向代理的管理接口默认关闭」。

- **✅｜裸 IP 访问不会得到有效 TLS**｜没有 catch-all 站点块，证书只对配置域名签发。｜证据：`deploy/Caddyfile:148-165`。｜建议措辞：「只对正式域名提供服务」。

- **🟡｜反代信任 `X-Real-IP` 且 API `trustProxy: true`**｜限流按 IP 依赖这一跳；若前面再加一层未受控代理，IP 可被伪造。｜证据：`deploy/Caddyfile:118-126`、`apps/api/src/app.ts:110`。｜建议措辞：「限流与审计按真实来源 IP 记录」。**限定**：以 Caddy 为唯一入口为前提。

- **⛔｜「服务器上什么都能加密」**｜只有传输层加密；容器内文件系统、数据库卷（`pgdata`）无静态加密配置。｜证据：`deploy/docker-compose.prod.yml:49`（命名卷，无加密选项）。｜禁止措辞：「静态数据全加密」「磁盘加密」。

## 2. 认证与会话

- **✅｜密码用 Argon2id（`@node-rs/argon2`），参数写死在代码里**｜`memoryCost: 19_456`（19 MiB）、`timeCost: 2`、`parallelism: 1`，注释标注为 OWASP 交互式登录推荐档位；校验异常按「密码错误」处理，不泄漏细节。｜证据：`apps/api/src/auth/password.ts:12-16,22-29`。｜建议措辞：「密码用 Argon2id 慢哈希保存，服务器不存明文密码」。

- **✅｜会话 token 是 256 bit 随机值，库里只存 SHA-256**｜`randomBytes(32).toString("base64url")`；`hashSessionToken` = SHA-256 hex；Schema 注释写「只存 token 哈希，库泄露无法重放」。｜证据：`apps/api/src/auth/session.ts:15-21`、`prisma/schema.prisma:350-370`（`tokenHash @unique`）。｜建议措辞：「登录凭证在服务器只存哈希，数据库泄露也无法冒充登录」。

- **✅｜cookie 属性齐全：HttpOnly + SameSite=Lax + Secure + 30 天**｜`setSessionCookie` 显式设置四项；`secure` 来自 `env.cookieSecure`，生产环境恒为 `true`。｜证据：`apps/api/src/routes/auth.ts:106-114`、`apps/api/src/env.ts:96`。｜建议措辞：「登录 cookie 禁止脚本读取、禁止跨站携带，生产环境只走 HTTPS」。

- **✅｜会话 30 天有效，且服务端可判定过期/吊销/停用/注销**｜`expiresAt` 校验；`revokedAt`、`closedAt`、`disabledAt` 分别返回不同错误码；停用时直接删掉该行。｜证据：`apps/api/src/auth/session.ts:6`、`apps/api/src/auth/guard.ts:19-33,40-52,70-73`。｜建议措辞：「会话有明确有效期，账号停用或注销后立即失效」。

- **✅｜改密码会清空所有设备会话，并轮换当前会话**｜事务内更新哈希 + `session.deleteMany({ userId })` + 审计事件，之后重新签发。｜证据：`apps/api/src/routes/auth.ts:615-638`。｜建议措辞：「改密码后，其它设备上的登录立即失效」。

- **✅｜忘记密码走一次性恢复码，不走邮件**｜16 字符 Crockford base32（去掉易混的 I/L/O/U），格式 `XXXX-XXXX-XXXX-XXXX`；用后**换发新码**，并清空全部会话。｜证据：`apps/api/src/auth/recovery-code.ts:7-25`、`apps/api/src/routes/auth.ts:647-698,703-736`。｜建议措辞：「忘记密码用纸质恢复码重置，不依赖邮箱」。

- **🟡｜恢复码注释称「128 bit」，实际约 80 bit**｜实现是 16 个字符、每字符取 `randomBytes[i] % 32`（5 bit/字符）= 80 bit，与注释 `recovery-code.ts:22` 的「128 bits」不符。｜证据：`apps/api/src/auth/recovery-code.ts:7-25`。｜建议措辞：「恢复码是一次性随机码，服务端只存哈希」。**不要说**具体位数。

- **✅｜登录限流：用户名 + IP 双键，指数退避**｜默认 5 次失败 / 15 分钟窗口，锁 60 秒起、每次翻倍最多 5 次（最长约 32 分钟）。｜证据：`apps/api/src/auth/login-throttle.ts:16,56-59`、`apps/api/src/app.ts:95-99`、`apps/api/src/env.ts:97-99`。｜建议措辞：「连续登录失败会被逐步拉长冷却时间」。

- **🟡｜限流在内存里，重启即清零**｜代码注释明说这是单实例部署可接受的折中，不是持久审计记录。｜证据：`apps/api/src/auth/login-throttle.ts:21-24`。｜建议措辞：「有限流」。**不要**说「暴力破解会被永久记录/全局封禁」。

- **✅｜登录失败不区分「用户不存在」与「密码错」，且未知用户也计算一次哈希以保持等时**｜`getDummyHash()` 与统一 `invalid_credentials`；停用/注销判定放在密码校验之后，同样为了等时。｜证据：`apps/api/src/routes/auth.ts:496-525`、`apps/api/src/auth/password.ts:31-43`。｜建议措辞：「登录失败提示不透露账号是否存在」。

- **✅｜默认邀请制，邀请码由服务端判定并原子抢占**｜`registrationMode` 仅接受 `invite|open`，默认 `invite`；`updateMany where usedAt:null, revokedAt:null` 防并发重复使用。｜证据：`apps/api/src/env.ts:55-62,100`、`apps/api/src/routes/auth.ts:265-283,391-398`。｜建议措辞：「默认邀请制注册」。

- **✅｜注册写死 `isAdmin: false`，邀请码不再授予管理员**｜注释解释了历史漏洞与修复。｜证据：`apps/api/src/routes/auth.ts:329-349`。｜建议措辞：「注册不会自动获得管理权限」。

- **✅｜CSRF 双保险：Origin/Host 校验 + SameSite=Lax**｜`onRequest` 对非 GET/HEAD/OPTIONS 校验 `new URL(origin).host === request.headers.host`，否则 403 `origin_not_allowed`。｜证据：`apps/api/src/app.ts:143-191`。｜建议措辞：「写操作会校验请求来源，跨站伪造被拒绝」。

- **✅｜全局速率限制 100 请求/分钟**｜`@fastify/rate-limit`。｜证据：`apps/api/src/app.ts:131-134`。｜建议措辞：「接口有整体请求频率上限」。

- **🌐 补充事实｜没有邮箱验证、没有短信、没有第三方登录**｜全仓库无 SMTP/邮件服务商/短信/OAuth 依赖（见 §5）；注册不要邮箱。｜证据：依赖扫描；`apps/api/src/routes/auth.ts` 只有密码 + 恢复码两条路径。｜建议措辞：「不需要手机号，也不需要邮箱就能用」。

- **⛔｜「双因素认证 / 2FA / 硬件密钥」**｜没有 TOTP/WebAuthn 实现，恢复码不是第二因素。｜证据：全仓库无 `totp|webauthn|otplib|u2f` 相关实现。｜禁止措辞：「两步验证」「双因素登录」。

## 3. 权限与管理员

- **✅｜账本权限唯一来源是成员表，读与写分成两档**｜`requireBookRead` / `requireBookWrite`；写入要求角色在 `editor|owner`，`viewer` 只能读；非成员直接拒绝；无 header 时回退到最早成员并记日志。｜证据：`apps/api/src/ledger/access.ts:8-15,17-33,59-64,123-135,166-180`、`apps/api/src/app.ts:308-364,326-327`。｜建议措辞：「能不能看、能不能改，由账本成员身份和服务端逐请求校验决定」。

- **✅｜「离开了」与「还在」是两种状态（`leftAt`）**｜退出后行保留、权限立即失效，历史不丢。｜证据：`apps/api/src/ledger/access.ts:48-51,94`、`prisma/schema.prisma:892`。｜建议措辞：「退出共享账本后，权限立即收回」。

- **✅｜已删除/归档/正在清理的账本在读取层就被拦下**｜分别返回 410 `book_deleted`、`book_deleting`、`book_archived`。｜证据：`apps/api/src/ledger/access.ts:95-111`。｜建议措辞：「已删除的账本连读取都会被拒绝」。

- **✅｜管理员资格 = 5 项同时成立，缺一即拒**｜有效会话 + `admin_grants` 活行 + `admin_allowlist` 活行（**两张不同的表**，一个判断读两遍不算双锁）+ 账号号在 `10000000–10000099` + 非 demo 账号；每次请求都重读、不缓存；两个 kill switch 任一关闭即全拒；所有拒绝统一 403。｜证据：`apps/api/src/admin/guard.ts:22-51,53-59,133-196,241-250,272-306`；设计说明 `docs/specs/product/管理员与权限边界-设计决定.md:194-213,297`。｜建议措辞：「管理员权限要同时满足多项条件，且每次操作都重新核对，不缓存」。

- **✅｜管理员操作不提供任何数据访问能力**｜`decideAdmin` 只回答「能不能做管理员操作」，不返回账本内容；三套权限相互独立。｜证据：`docs/specs/product/管理员与权限边界-设计决定.md:369-394`。｜建议措辞：「管理员能做的是账号与生命周期操作，看不到别人账本里的账目」。

- **🟡｜「看不到」的产品边界 vs 服务器权力**｜这是单台自托管服务器；拥有 root 的人可以直接读 PostgreSQL。产品界面与 API 层面确实拿不到账本正文。｜证据：同上 `:369-394`；`deploy/docker-compose.prod.yml:37-58`（库与 API 同机）。｜建议措辞：「管理员在产品里看不到你的账目；数据在你自己的服务器上」。**不要**说「任何人（包括服务器主人）都看不到」。

- **✅｜敏感管理员操作要再输一次当前密码**｜`createReauthVerifier` 用请求体里的当前密码做 `verifyPassword`，失败写审计 `recordRefusal`，且有独立限流（3 次 / 5 分钟锁 / 15 分钟窗口）。｜证据：`apps/api/src/admin/reauth.ts:22-26,39-77`、`apps/api/src/routes/admin.ts:96,121-143`。｜建议措辞：「停用账号、发放邀请码这类操作，要再输一次管理员自己的密码」。

- **✅｜停用账号会在同一事务里删掉该用户全部会话**｜并写 `disabledAt/disabledBy`；禁止停用自己、禁止停用现任管理员；恢复只清标记、不重建会话。｜证据：`apps/api/src/admin/accounts.ts:75-111,96-101,114-140`。｜建议措辞：「停用一个账号，它所有设备上的登录同时失效」。

- **✅｜管理员动作有审计与幂等包装**｜`runP0Operation` + `recordAudit` + `recordCriticalEvent`；审计可分页查询（50 条/页）；审计模型 `AdminAuditLog`。｜证据：`apps/api/src/routes/admin.ts:452-586,591-603`、`prisma/schema.prisma:1638`。｜建议措辞：「管理员的关键动作会留下审计记录」。

- **✅｜邀请码发放有每小时上限**｜`INVITES_PER_HOUR` 限制。｜证据：`apps/api/src/routes/admin.ts:98-113`。｜建议措辞：「邀请码发放有频率上限」。

- **✅｜站内通知有发送配额，靠 `UPDATE … WHERE used < limit` 原子占用**｜单收件人 5 条/天、总量 20 条/天，超限 429。｜证据：`apps/api/src/collab/quota.ts:28-29,114-128,165-180`。｜建议措辞：「分享与邀请类通知有每日上限，防止骚扰式刷屏」。

- **✅｜分享链接：256 bit token、库中只存哈希、1–7 天、可撤销**｜`randomBytes(32)`；有效期**每次按 `createdAt + days` 现算**，没有第二份存储的截止时间；撤销写 `revokedAt` 并记事件。｜证据：`apps/api/src/collab/share.ts:29-30,66,89-108`、`apps/api/src/routes/share.ts:165-204`、`prisma/schema.prisma:464-481`。｜建议措辞：「分享链接有短期有效期（最长 7 天），随时可撤销，服务端只存链接的哈希」。**限定**：拿到链接的人在这段时间内能看到该账本的内容——这是「用户主动分享」，不是「数据不外流」。

- **⛔｜「账本内有管理员角色，能改别人的设置」**｜`BookRole` 枚举虽保留 `owner`，但代码已弃用 owner 角色，只写 `editor/viewer`；账本内没有「超级权限」。｜证据：`prisma/schema.prisma:842-857,874`。｜禁止措辞：「账本管理员可以管理成员权限」。**正确说法**：`editor` 可写账目并可管理成员（见 `routes/books.ts` 的写守卫），但没有独立于成员关系的「账本管理员」。

## 4. 数据存储与加密

- **⛔｜「端到端加密」**｜仓库里没有任何 E2E 密钥体系：没有客户端加密后再上传的路径，没有用于业务数据的 KDF，服务端持有明文业务表。｜证据：`prisma/schema.prisma` 全文无加密字段；`apps/` 内 `createCipheriv|createDecipheriv` 仅出现在 `apps/api/src/critical/remote.ts:218,260`（关键事件信封）。｜禁止措辞：「端到端加密」「零知识」「服务器无法解密」。

- **⛔｜「数据库加密 / 字段级加密」**｜业务数据以明文存进 PostgreSQL：金额、备注、账本名、成员名都是普通列；没有 `pgcrypto`、没有列级加密、没有应用层加密。｜证据：`prisma/schema.prisma:1060-1094`（交易列定义）、`:724-840`（账本列）；`apps/api/src` 无 `pgcrypto`/列加密调用。｜禁止措辞：「数据库加密存储」「敏感字段密文保存」。

- **✅｜备份是加密的（gpg 对称，显式 AES256）**｜本地备份 + 演练通过后，用 `deploy/.backup.key` 做 `gpg --symmetric --cipher-algo AES256`，密文小于 1024 字节视为异常；上传对象是 `*.dump.gpg`。｜证据：`deploy/backup-all.sh:283-302`（`--cipher-algo AES256` 在 :292）。｜建议措辞：「备份用 AES-256 加密后才离开服务器」。**限定**：密钥文件也在同一台服务器上（`deploy/.backup.key`）——防的是「存储桶泄露」，不是「服务器被完全控制」。

- **✅｜关键事件对象在服务端加密（AES-256-GCM，带 key ring 轮换）**｜`createCipheriv("aes-256-gcm", ring.activeKey, iv)`，支持多把钥匙轮换；对象键含序号与事件 id；manifest 里带哈希链头。｜证据：`apps/api/src/critical/remote.ts:131,166-232,260,298-300`。｜建议措辞：「关键操作日志单独加密后上传，存储桶里看到的只是密文」。

- **🟡｜「本地数据加密」不成立**｜桌面/浏览器本地副本是**明文 IndexedDB**：`DATABASE="libellum"`、`STORE="kv"`、`VERSION=1`；文件里没有任何 crypto 调用，只有 `indexedDB.open` / `deleteDatabase`。｜证据：`apps/web/src/lib/offline/storage.ts:36-42,149,493`；文档说明见 `docs/specs/product/离线与同步-设计决定.md:48-101`。｜建议措辞：「账本在你设备上有一份可以离线阅读的副本」。**不要说**「本地数据加密」「没有密码打不开本地文件」。

- **🟡｜本地缓存「不会自动过期」**｜查询缓存 `gcTime` 为 `Infinity`，注释解释：过期会让离线用户看不到自己的账本，宁可保留。｜证据：`apps/web/src/lib/offline/cache.ts:29-52`。｜建议措辞：「离线副本会一直保留，直到你退出登录或手动清除」。**不要说**「本地缓存会自动清理」。

- **✅｜默认退出登录会清掉整份离线缓存**｜缓存注释写明「最多只存一个用户的数据，所以退出即抹掉」；`logout()` 默认 `await clearQueryCache()`。｜证据：`apps/web/src/lib/offline/cache.ts:17-19`、`apps/web/src/auth/AuthProvider.tsx:133-142,317`。｜**🟡 限定**：`logout({ preserveOfflineData: true })` 会保留缓存，目前唯一调用点是同意门槛页（`apps/web/src/components/ConsentGate.tsx:157`）——即「登出一定清缓存」不是绝对命题，但常规登出会清。｜建议措辞：「退出登录会清除这台设备上的离线账本副本」。

- **✅｜「清除这台设备全部数据」是独立动作，需要两次确认**｜`clearAllDeviceData()` 处理两套身份、两个数据库、`localStorage` 里所有 `libellum*` 键，**故意不动服务器**、也不注销会话（注释解释这是另一种同意）。｜证据：`apps/web/src/lib/guest/cleanup.ts:45-101`。｜建议措辞：「设备上留了什么，你可以一键全部清掉（服务器上的数据不受影响）」。

- **🟡｜本地存储的具体位置**｜浏览器/WebView 的 IndexedDB + `localStorage`，位于浏览器用户数据目录；项目没有原生 App 外壳（`apps/web` 下无 Tauri/Capacitor 配置，`src-tauri` 不存在）。｜证据：`apps/web/src/lib/offline/storage.ts:36-42`。｜建议措辞：「数据存在你浏览器的本地数据库里」。**限定**：设备磁盘是否加密取决于操作系统，产品不做承诺。

- **✅｜离线优先是真的离线：Service Worker 只缓存外壳，`/api` 响应一律不在这里缓存**｜注释解释第二个副本「会活过登出、还会和查询缓存互相矛盾」。｜证据：`apps/web/public/sw.js:1-33`。｜建议措辞：「断网也能打开并记账」。

## 5. 第三方与数据出口

- **✅｜OCR 在本机服务器的子进程里跑，不开端口**｜`spawn()` 常驻 Python 子进程，JSON 逐行经 **stdin/stdout 管道**；voice 客户端注释明写「用管道而不是 HTTP，因为管道没有地址需要保护」。｜证据：`apps/api/src/ocr/client.ts:219-241,351`、`apps/api/src/voice/client.ts:6-11,306-331,473`；`deploy/README.md:42-44`。｜建议措辞：「截图识别与语音识别都在你自己的服务器上完成，不发给任何云服务」。

- **✅｜模型与 Python 侧无外网请求**｜grep `huggingface|requests\.|urllib|urlopen|http://` 在 `apps/` 的 Python 代码里只命中 OOXML 命名空间字符串；无模型下载逻辑。｜证据：见 §15 检索结论。｜建议措辞：「识别模型随应用一起部署，运行时不联网」。

- **✅｜应用本身没有统计、广告、分析 SDK**｜三个 `package.json` 里 `posthog|sentry|mixpanel|amplitude|google-analytics|umami|plausible|algolia` 等零命中。｜证据：见 §15。｜建议措辞：「没有埋点、没有广告 SDK、没有第三方统计」。

- **✅｜前端只请求同源 `/api`**｜`fetch(` 全部走 `buildUrl(path)`；无 `sendBeacon`；无第三方域名。｜证据：`apps/web/src/lib/api.ts:216,295`、`apps/web/src/lib/consent.ts:54`。｜建议措辞：「页面不会向第三方域名发请求」。

- **✅｜没有第三方 cookie**｜服务端只设置一个会话 cookie（`libellum_session`），无广告/追踪 cookie，无第三方脚本。｜证据：`apps/api/src/auth/session.ts:3`、`apps/api/src/routes/auth.ts:106-114`、`deploy/Caddyfile:104`（`connect-src 'self'`）。｜建议措辞：「只有一个登录用的 cookie，没有追踪 cookie」。

- **🟡｜确实存在的外部服务（运维面，不是业务面）**｜① 腾讯 COS：存加密备份与加密关键事件对象；② Resend（`api.resend.com`）：只发运维告警邮件；③ healthchecks.io 类心跳（`HEARTBEAT_URL`）。三者都**不接触账本正文**。｜证据：`deploy/backup-all.sh:307-346`、`deploy/alert-mail.sh:230-232`、`deploy/heartbeat.sh:22,72`、`apps/api/src/critical/remote-cos.ts:27`。｜建议措辞：「业务数据不会发给第三方；服务器运维用到的对象存储与告警通道，接收的是加密备份和运维文本」。**不要说**「完全没有第三方」。

- **🟡｜告警邮件会让收件方看到什么**｜Resend 发信，正文是运维告警文本（备份失败/心跳异常），不含账本数据；`MAIL_FROM`/`MAIL_TO` 由运维配置。｜证据：`deploy/alert-mail.sh:23-25,230-232`。｜建议措辞：「运维告警邮件里没有你的账目」。

- **✅｜账号导出只返回本人有权访问的数据，且记录导出日志**｜三个导出端点都挂 `requireAuth`；导出记录可查（`/export-log`），模型 `ExportLog`。｜证据：`apps/api/src/routes/export.ts:169,291,325`、`prisma/schema.prisma:1290`。｜**🟡 限定**：导出**不要求再输密码**（对比注销/删数据要密码），所以「导出必须二次验证」不能宣传。｜建议措辞：「你可以随时导出自己的数据，导出行为有记录」。

- **⛔｜「数据绝对不会离开这台设备」**｜离线副本 + 自有服务器同步 + 可选分享链接 + 异地加密备份，四者都会让数据「离开当前设备」。｜证据：§4、§5 上述条目。｜禁止措辞：「数据只存在本设备」「永不上传」。

## 6. OCR 与导入的临时文件

- **✅｜上传的图片只在内存里处理，从不落盘**｜`await part.toBuffer()` 读进内存后立刻交给识别进程；注释写明「流从不落到文件，所以截图没有存在于磁盘的窗口」。｜证据：`apps/api/src/routes/recognize.ts:83-85`。｜建议措辞：「截图只在你服务器的内存里过一遍，不写磁盘」。**限定**：进程被 dump/被 root 抓内存属于操作系统层面，不在承诺范围。

- **✅｜识别结果不保存**｜文件头注释明说该端点「不保存任何结果」；返回后不写库、不写文件。｜证据：`apps/api/src/routes/recognize.ts:18-27,139`。｜建议措辞：「识别完就把结果交给你确认，服务器不保存这张图，也不保存识别结果」。

- **✅｜上传有大小与数量上限，且校验真实文件类型**｜multipart 限制 `fileSize` 与 `files`；服务端嗅探 magic bytes，伪造扩展名会被拒；HEIC 明确拒绝并说明原因。｜证据：`apps/api/src/app.ts:125-130`、`apps/api/src/routes/recognize.ts:36-63,76-96,100-111`。｜建议措辞：「不是图片的文件会被直接拒绝」。

- **✅｜失败不会留下残留**｜失败路径直接返回错误，没有临时文件可残留（从未写盘）；文案明确「你的图片没有被保存」。｜证据：`apps/api/src/routes/recognize.ts:139`。｜建议措辞：「识别失败也不会留下文件」。

- **✅｜导入（支付宝/微信/银行 CSV）的预览缓存在进程内存里，不落盘**｜`import/cache.ts` 是进程内 `Map`：TTL + 最多 25 条 + 按 `userId`/`bookId` 隔离；注释说明重启丢失是设计允许的。｜证据：`apps/api/src/import/cache.ts`（文件头注释与容量常量）。｜建议措辞：「导入预览只暂存在内存里，几分钟后自动消失」。

- **🟡｜`UPLOAD_DIR` 是一个「预留但没人用」的配置**｜compose 给 api 挂了 `UPLOAD_DIR=/data/uploads` 与 `api-data` 卷，但代码里**零引用**——即当前没有任何业务上传会写这个目录。｜证据：`deploy/docker-compose.prod.yml:108-112`；`apps/api/src` 内无 `UPLOAD_DIR` 读取。｜建议措辞：「没有把用户图片存到磁盘的功能」。**注意**：这是一个「看起来支持上传存储、实际不写」的配置，未来若接入上传必须重审本清单。

- **⛔｜「所有上传文件都会在 N 分钟后自动删除」**｜不存在「上传文件」这个对象，因此也不存在「自动删除策略」；说这句话会给用户一个不存在的机制。｜证据：同上。｜禁止措辞：「临时文件会定时清理」。

## 7. 备份与恢复

- **✅｜每天 03:00（Asia/Hong_Kong）自动备份，带 `Persistent=true`**｜systemd timer 触发 `backup-all.sh`，服务以 `ubuntu` 用户运行。｜证据：`deploy/systemd/libevra-backup.timer:11-12`、`deploy/systemd/libevra-backup.service:15,21`。｜建议措辞：「每天凌晨自动备份一次」。

- **✅｜备份 = `pg_dump -Fc` + SHA-256 + 归档目录校验**｜生成 dump 后算 `sha256sum` 写进 manifest/状态 JSON，并用 `pg_restore --list` 数 TOC 条目确认归档完整。｜证据：`deploy/backup.sh:139,158,166,108`。｜建议措辞：「每份备份都有校验和，并检查归档结构完整」。

- **✅｜备份默认做「隔离恢复演练」：重建临时库 → 恢复 → 逐表对行数**｜`RESTORE_DRILL=1` 是默认值；脚本注释强调最忌讳的是「漏了权限表也报通过」的假成功。｜证据：`deploy/backup.sh:47,183-199,210`。｜建议措辞：「备份完不是看一眼文件大小，而是真的恢复到临时库里对一遍行数」。

- **✅｜跳过演练会被明确标注「这份备份还没有被证明能恢复」**｜`--no-restore-drill` 时打印该行。｜证据：`deploy/backup.sh:175-177`。｜建议措辞：「没做恢复验证的备份，脚本自己会标出来」。

- **✅｜保留策略：最近 7 天 + 永远保留最新 3 份**｜`KEEP_DAYS=7`、`KEEP_NEWEST=3`。｜证据：`deploy/backup.sh:46,49,261-273`。｜建议措辞：「本地保留最近一周，并始终保留最近三份」。

- **✅｜异地副本上腾讯 COS，gpg 加密，上传后比对远端大小**｜`daily/YYYY/MM/…` 每日、`monthly/` 每月一份（保留 365 天）；`rclone lsjson --stat` 校验大小一致。｜证据：`deploy/backup-all.sh:307-346,351-377`。｜建议措辞：「加密后同步一份到异地对象存储，并回读校验大小」。

- **✅｜上传身份最小权限：只有 PutObject/HeadObject，没有读和删**｜代码注释与设计一致；恢复用的身份 `COS_RESTORE_*` 不常驻服务器。｜证据：`deploy/backup-all.sh:22-24,37`、`apps/api/src/critical/remote-cos.ts:17-18`。｜建议措辞：「服务器上的上传钥匙只能写、不能读，拿不到历史备份」。

- **✅｜异地未配置时整体记为失败，而不是「成功但没异地」**｜避免「以为有异地备份」的假象。｜证据：`deploy/backup-all.sh:262-268`。｜建议措辞：「异地备份没配好，这次备份就算失败」。

- **✅｜恢复脚本不删现有库：先做安全副本，再建新库恢复**｜`pg_restore --list` 校验 → `pg_dump` 出一份 safety 副本 → `createdb` → `pg_restore --exit-on-error`。｜证据：`deploy/restore.sh:72,84,98,110`；`deploy/verify-dump.sh:63-73`。｜建议措辞：「恢复过程会先给现有数据再做一份快照，不会直接覆盖」。

- **✅｜有一次可查的真实演练记录（隔离集群）**｜45 migrations / 4 users / 5 books / 7 members / 164 transactions 全部恢复成功，结论「满足『生产备份副本可恢复、可升级、关键数据不受损』的验收目标」。｜证据：`docs/archive/releases/S14-D5生产备份隔离升级演练.md:166-174,225`。｜建议措辞：「做过完整的恢复演练，逐表核对行数一致」。

- **🟡｜但演练有明确剩余风险**｜只在一次性隔离集群验证；**未在生产 Docker 的 `restore.sh` 环境实跑**；演练时未 push/未部署。｜证据：`docs/archive/releases/S14-D5生产备份隔离升级演练.md:217-218,228`。｜建议措辞：「备份可恢复经过演练验证」。**不要说**「已在生产环境验证过一键恢复」。

- **🟡｜RPO 约 24 小时；没有流复制/热备**｜备份是每日全量 dump；`db` 是单容器单卷。｜证据：`deploy/docker-compose.prod.yml:37-58`、`deploy/systemd/libevra-backup.timer:11`。｜建议措辞：「最坏情况下会丢失一天内的数据」。**不要说**「零丢失」「实时同步」。

- **🟡｜备份文件权限靠 `umask 077` / `chmod 600` 的脚本约定**｜本机备份目录权限未在 compose 里声明，取决于脚本与宿主 umask。｜证据：`deploy/backup-all.sh:308,321`。｜建议措辞：「备份文件只对运行用户可读」。**限定**：这是脚本行为，不是文件系统级强制。

- **⛔｜「备份和数据库分离」作为完整承诺**｜备份默认与数据库在**同一台服务器**上（`deploy/backups`），异地只靠 `backup-all.sh`；异地未配置时脚本会把本次记为失败，但本机副本仍在。｜证据：`deploy/backup.sh:283`（脚本自己提示「同一台服务器上的备份会和服务器一起消失」）。｜禁止措辞：「备份和服务器分离，服务器没了也不怕」——除非明确看到异地已启用。

## 8. 删除与生命周期

- **✅｜「删除账本」有两级缓冲：60 天自助恢复，之后归档 365 天，再清理**｜常量写死 `SELF_RESTORE_DAYS=60`、`ARCHIVE_RETENTION_DAYS=365`；清理「到期后 24 小时内」。｜证据：`apps/api/src/lifecycle/constants.ts:7-12,24-29`。｜建议措辞：「删掉的账本有 60 天反悔期，之后归档一年再清除」。

- **✅｜清理是独立任务，每天 03:30 跑，带 advisory lock，不靠 Web 请求**｜systemd timer 执行 `pnpm --filter @libellum/api lifecycle:purge`；`SELECT … FOR UPDATE` 按固定顺序锁账本防并发。｜证据：`deploy/systemd/libevra-lifecycle.timer:7-12`、`apps/api/src/lifecycle/account.ts:92,495-496`、`docs/specs/features/S13-H-…-设计决定.md:58-60`。｜建议措辞：「到期清理是每天定时跑的独立任务，不是你打开页面才执行」。

- **✅｜清理是单事务，先写墓碑再删数据，失败回滚并记原因**｜顺序：写 `bookTombstone` → 删 transactions（因为 `transactions.category_id` 是 `ON DELETE RESTRICT`）→ 删冲突 → 删 book → 写生命周期事件 → 写关键事件；失败时 `purgeAttempts+1` 并记 `purgeLastError`。｜证据：`apps/api/src/lifecycle/book.ts:750-836,944-996`。｜建议措辞：「清理要么整本删干净，要么整单回滚，不会删一半」。

- **✅｜墓碑只留「发生过删除」这个事实，不留账本内容**｜墓碑含 bookNumber、创建者、`purgedAt`、`deletionMethod`（`self_delete|account_closure|auto_purge|admin_purge`）、成员数、交易数——**不含**交易正文、备注、附件、账本名。｜证据：`apps/api/src/lifecycle/book.ts:769-793`、`docs/specs/features/S13-H-…-设计决定.md:93`。｜建议措辞：「删掉之后只在系统里留一条『这本账已被删除』的记录，账目内容不保留」。

- **✅｜注销账号不物理删 users 行，而是匿名化 + 墓碑**｜`username` 改成 `closed_<userId>`、`displayName` 改成「已注销账号」、写 `closedAt`、`disabledBy="self_close"`，另写 `accountTombstone`。设计文档解释原因：`books.created_by` / `transactions.user_id` 是 `ON DELETE CASCADE`，物理删会连别人的共享账本一起销毁——「这是有意的安全边界，不是假注销」。｜证据：`apps/api/src/lifecycle/account.ts:717-745`、`docs/specs/features/S13-H-…-设计决定.md:10-28`。｜建议措辞：「注销会把账号匿名化，并确保你参与过的共享账本不会被连带毁掉」。**限定**：因此「账号数据被彻底删除」不成立——留下的是匿名壳 + 墓碑。

- **✅｜注销前必须先处理每本账本；处理不了就整单不执行**｜共享账本缺可接手编辑者时 `book_needs_successor`；「还有账本没有安全的管理者或正在清理」→ `account_close_blocked`。｜证据：`apps/api/src/lifecycle/account.ts:466,560-561,578`。｜建议措辞：「注销时如果有账本没人接手，会要求你先安排好，而不是悄悄把别人的账本弄坏」。

- **✅｜注销 / 删数据都要输密码 + 手打确认短语**｜注销要输入指定短语，删除服务器数据要输入「删除服务器数据」，两者都走 `verifyOwnPassword`（带限流）。｜证据：`apps/api/src/routes/lifecycle.ts:98-110,241-252,293-302`。｜建议措辞：「删数据这种事，要输密码再打一遍确认语」。

- **✅｜「只删服务器数据」与「注销账号」是两条独立路径**｜`CloseMethod = "close_account" | "delete_data"`；`deleteAccountData` 注释明确它**不删会话、不改密码/恢复码、不写账号墓碑**。｜证据：`apps/api/src/lifecycle/account.ts:22,261-264`。｜建议措辞：「可以只清服务器数据、保留账号，也可以整个注销」。

- **✅｜归档结束前允许人工恢复申请，管理员核验**｜60 天内自助恢复；超期可提交申请（7 天窗口，且不超过 `scheduledPurgeAt`）；已注销账号用一次性恢复凭证（只存 SHA-256）。｜证据：`apps/api/src/lifecycle/book.ts:420-451,490-512`、`apps/api/src/lifecycle/account.ts:797-864`、`docs/specs/features/S13-H-…-设计决定.md:65-69`。｜建议措辞：「误删了可以自己恢复；过期了还能申请人工找回，但要管理员核验」。

- **🟡｜删除「彻底性」的真实边界**｜① 归档期 365 天内数据仍在库里；② 备份 `daily/` 70 天、`monthly/` 365 天；③ 灾难恢复会把旧备份里的已删账本「复活」，需要 `lifecycle:replay-tombstones` 再补删；设计文档明确「**不能对外宣称『删除后 365 天后任何副本都不存在』**」。｜证据：`docs/specs/features/S13-H-…-设计决定.md:103-108`、`deploy/backup-all.sh:351-377`。｜建议措辞：「删除会在系统里按期限清理，备份里的历史副本会按备份保留期自然淘汰」。**不要说**「永久删除」「不可恢复」。

- **🟡｜「所有设备」这个词要小心**｜S13-H §4 明确「不声称所有设备已即时物理清除」。｜证据：`docs/specs/features/S13-H-…-设计决定.md:87`。｜建议措辞：「服务器上的数据按期限清除；你设备上的离线副本，可以在设置里一键清掉」。

- **⛔｜「注销即彻底消失」**｜用户行保留为匿名壳，`accountTombstone` 永久保留删除事实，备份保留期内仍有旧副本。｜证据：`apps/api/src/lifecycle/account.ts:717-745`。｜禁止措辞：「注销后数据彻底消失」。

## 9. 同步与冲突

- **✅｜冲突判定不用版本号、不用时间，只比「值」**｜设计文档给出四条判定规则：目标值相同 → 不算冲突；本机值在服务器历史里 → 直接覆盖成服务器当前值；其余 → 冲突。｜证据：`docs/specs/product/S8-冲突-设计决定.md:12,23-26,30-68,71-96`。｜建议措辞：「冲突判断只看值本身，不靠设备时钟，也不靠版本号猜测」。

- **✅｜判不出胜者就 409 且**不写库**，两份都留着**｜服务端返回 409 并记下双方声明；客户端日志写「两份都留住了，等用户决定」。｜证据：`docs/specs/product/S8-冲突-设计决定.md:105-109`、`apps/web/src/lib/offline/sync.ts:315-334`、`prisma/schema.prisma:1120-1132`。｜建议措辞：「两边改了同一个字段，系统不会替你选一个，而是停下来问你」。

- **✅｜冲突记录在服务器，一次确认全设备生效**｜`GET /api/v1/conflicts` 返回 `serverValue/claims/history`；`POST /api/v1/conflicts/resolve-with-server` 一键采用服务器版本；冲突解决后设备不再重复提问。｜证据：`docs/specs/product/S8-冲突-设计决定.md:146-176,311`。｜建议措辞：「在任意一台设备上确认一次，其它设备就都不会再问」。

- **✅｜值历史只保留最近 20 个，用来回答「这个值是不是我改过的」**｜超出即淘汰，防止无界增长。｜证据：`docs/specs/product/S8-冲突-设计决定.md:131-133`。｜建议措辞：「系统记得最近若干次改动，用来判断是不是同一个人的改动」。

- **✅｜冲突界面只问服务器点名的字段，其余字段静默合并**｜`conflictQuestions()` 从 `fields[].claims` 生成候选项，去重后不足 2 个就不提问；`occurredAt` 不参与。｜证据：`docs/specs/product/S8-冲突-设计决定.md:296-302`、`apps/web/src/lib/offline/conflictChoices.ts:24,33,40-43`。｜建议措辞：「只问真正打架的那个字段，别的字段不会拿一堆问题烦你」。

- **🟡｜「静默合并」存在，且是设计选择**｜除冲突字段外，服务器会直接合并；这不是 bug，但和「任何改动都不会被覆盖」并不等价——被合并的是**不冲突**的字段。｜证据：同上 `:296-302`。｜建议措辞：「不冲突的改动自动合并；真正冲突的不会静默覆盖」。**不要说**「任何情况下都不会覆盖你的改动」。

- **✅｜「在线设备永远不该冲突」作为实现约束**｜设计文档写明：在线设备发生冲突即视为实现错误。｜证据：`docs/specs/product/S8-冲突-设计决定.md:23-26`。｜建议措辞：「同一台设备在线时的连续修改不会被当成冲突」。

- **🟡｜删除不做冲突判定（一台删、一台改）**｜设计文档「明确不做」清单里列了删除冲突，且没有 WebSocket 推送（靠设备下次动作自己问）。｜证据：`docs/specs/product/S8-冲突-设计决定.md:321-322`。｜建议措辞：「多端改同一笔会被拦住问你」。**不要说**「删除也有冲突保护」「实时推送同步」。

- **✅｜网络失败与业务拒绝分开处理：409 不重试，5xx/断网重试**｜`sync.ts` 区分 `ledger_locked`（临时拒绝，保留待同步标记）与内容冲突（记录冲突、等用户决定）。｜证据：`apps/web/src/lib/offline/sync.ts:185-193,295-334`。｜建议措辞：「断网时的操作会排队重试，不会被当成冲突丢掉」。

## 10. 重大事项及时同步（critical events）

- **✅｜关键事件 = 40 种类型，分 P0/P1 两组**｜覆盖账号生命周期、账本生命周期、成员与权限、认证与会话、邀请/分享/管理、同意与保留策略六组；P0 含 `account.closed`、`book.deleted`、`member.removed`、`auth.password_changed`、`auth.sessions_revoked`、`admin.granted` 等。｜证据：`apps/api/src/critical/types.ts:4-50,54-79`。｜建议措辞：「账号注销、删账本、移除成员、改密码、权限变更这类事，都会单独记一条关键事件」。

- **✅｜关键事件在业务事务里同步落库，带哈希链**｜同事务写 `critical_events` 行，`prevHash` + `canonicalJson` 求 SHA-256 形成链，`critical_chain` 记录 `lastSeq/lastHash`；用 advisory lock 串行化。模型 `CriticalEvent` 在 `prisma/schema.prisma:1819`。｜证据：`apps/api/src/critical/store.ts:18,38-51,59,77,125,142-143`。｜建议措辞：「每条关键事件都和上一条串成哈希链，中间少一条或改一条都对不上」。

- **✅｜`pg_notify` 唤醒 relay，异步重试**｜`SELECT pg_notify('critical_events_new', $1)`；`pg_notify` 是事务性的，回滚不会留下假通知。｜证据：`apps/api/src/critical/store.ts:129-135`。｜建议措辞：「写完立刻叫醒上传进程，失败会自动重试」。

- **✅｜relay 是独立容器、无端口、无 HTTP 监听、共享数据库**｜`command: pnpm --filter @libellum/api critical:relay`；`networks: [internal]`；注释「这个进程不可从网络访问」；健康检查关闭，真实健康靠心跳表。｜证据：`deploy/critical-events-relay.compose.yml:6-38`、`docs/03-运维手册.md:70-79`。｜建议措辞：「上传由单独的无端口进程负责，Web 服务本身拿不到对象存储钥匙」。

- **✅｜上传对象加密且不可变（putIfAbsent 语义）**｜AES-256-GCM 信封 + key ring；对象键含序号与事件 id，manifest 带链头；同键 PUT 会覆盖，所以上传路径用 putIfAbsent 语义。｜证据：`apps/api/src/critical/remote.ts:131,166-232,298-300`、`apps/api/src/critical/remote-cos.ts:78`。｜建议措辞：「上传的是密文，对象名带序号，重传不会覆盖已有记录」。

- **🟡｜业务成功**不**依赖远端确认**｜`confirmP0` 已被标记 `@deprecated` 且是空函数，注释明写「业务成功故意不与远端账本耦合……relay 独立重试……绝不因为 relay 不可用返回 503 或等 ack」。｜证据：`apps/api/src/critical/confirm.ts:3-13`。｜建议措辞：「关键事件会补传，不会因为它没传上去就让你存不了账」。**不要说**「每条操作都实时上链确认后才生效」「实时异地存证」。

- **🟡｜「不可篡改」只能说到「可发现」**｜哈希链 + 只写身份 + 不可变对象，使篡改在链上留下断点；但数据库所有者仍可整体重写链（本地链自洽），且这**不是公开链/时间戳服务**。｜证据：`apps/api/src/critical/store.ts:38-143`、`apps/api/src/critical/remote-cos.ts:17-18`。｜建议措辞：「改动会被哈希链发现」。**不要说**「无法篡改」「区块链存证」「司法级存证」。

- **⛔｜「所有人可见的公开账本 / 第三方可验证」**｜对象存在私有 COS 桶里，服务器持有写入密钥，外部无法独立验证。｜证据：`apps/api/src/critical/remote-cos.ts:17-27`。｜禁止措辞：「公开可验证」「第三方可审计」。

## 11. 一致性与读取校验

- **✅｜金额是整数最小单位（分），绝不用浮点**｜`amountCents BigInt`，Schema 注释「整数分，绝不用浮点」；共享包 `money.ts` 是唯一换算入口，并处理 JPY 无小数位等差异，解析非法金额直接抛错。｜证据：`prisma/schema.prisma:1060-1062`、`packages/shared/src/money.ts:1-30`。｜建议措辞：「金额按『分』存整数，不会出现 0.1+0.2≠0.3 这种账目误差」。

- **✅｜写入有幂等键，重复提交不会记两笔**｜`Transaction.idempotencyKey @unique`；服务端先按 key 查、命中即返回已有结果。｜证据：`prisma/schema.prisma:1078`、`apps/api/src/routes/transactions.ts:306,336,387`。｜建议措辞：「同一个请求重复发送（比如网络抖动重试）不会变成两笔账」。

- **✅｜外部来源账目有唯一约束，重复导入被数据库挡住**｜`@@unique([bookId, sourceNamespace, sourceRef])`。｜证据：`prisma/schema.prisma:1114`。｜建议措辞：「同一份账单重复导入，不会产生重复账目」。

- **✅｜冲突与版本字段持久化在服务器，不由客户端决定**｜`version`、`valueHistory`、`TransactionConflict` 都在服务端表里。｜证据：`prisma/schema.prisma:1077,1080-1090,1120-1132`。｜建议措辞：「谁改了什么，以服务器记录为准」。

- **🟡｜「服务端权威时间」只对系统字段成立**｜`createdAt/updatedAt` 由服务端写入；但账目发生时间 `occurredAt` 是业务字段，且明确**不参与冲突判定**。没有 `serverTime` 接口给客户端校时。｜证据：`prisma/schema.prisma:1073`、`docs/specs/product/S8-冲突-设计决定.md:182-185`。｜建议措辞：「系统记录的时间以服务器为准」。**不要说**「客户端无法伪造时间」——`occurredAt` 是用户填的业务时间。

- **✅｜写入冲突有业务锁，返回 409 而不是 500**｜写锁冲突返回 409 `ledger_locked`，客户端知道这是「暂时被拒、可以重试」；锁表 `LedgerWriteLock`。｜证据：`apps/api/src/lib/errors.ts:104-132`、`apps/web/src/lib/offline/sync.ts:305-313`、`prisma/schema.prisma:1405`。｜建议措辞：「并发写入时不会互相踩，冲突的一方会被告知稍后重试」。

- **⛔｜「账目绝对不会重复」**｜幂等键与唯一约束覆盖了「同一请求重试」「同一来源重复导入」，但用户手动记两笔一样的账是允许的。｜证据：`prisma/schema.prisma:1078,1114`。｜禁止措辞：「系统自动去重所有重复账目」——应说「重复导入会拦住，手写的重复由你决定」。

## 13. 运维隔离与 CI

- **✅｜生产/测试数据库隔离**｜CI 用独立的 `ledger_test` 库；仓库另有 `docker-compose.s13i-test.yml` 与 `.s13i-test.*.env.example` 用于隔离环境；演练记录用 55432 端口的隔离库，明确「未读取/打印生产用户数据」。｜证据：`.github/workflows/ci.yml:19-35`、`deploy/docker-compose.s13i-test.yml`、`docs/archive/releases/S14-D5生产备份隔离升级演练.md:47,145-156`。｜建议措辞：「测试和演练都在隔离库上做，不碰生产数据」。

- **✅｜发布脚本不碰数据卷，回滚只回滚应用**｜`deploy.sh` 头部注释：「它一行都不会碰数据卷——没有 `down -v`，没有 `prune --volumes`，没有 `migrate reset`；数据库迁移是只向前的，回滚应用不会撤销 schema」；必须显式 `--version`，流程含健康检查与失败退回，并建议发布前先 `./deploy/backup.sh`。｜证据：`deploy/deploy.sh:1-30`、`docs/03-运维手册.md:99-156`。｜建议措辞：「升级只换应用，不动数据库；出问题可以退回上一版」。

- **✅｜迁移由独立的一次性服务执行**｜compose 里 `migrate` 服务跑 `pnpm db:deploy`，注释禁止 `migrate dev`/`reset`；api 等 `db healthy` + `migrate completed` 才启动。｜证据：`deploy/docker-compose.prod.yml:64-79,113-120`。｜建议措辞：「数据库结构变更由单独的迁移步骤完成，不会在 API 启动时偷偷改表」。

- **🟡｜「环境变量里的密钥」是运维面事实**｜`POSTGRES_PASSWORD`、`SESSION_SECRET` 等以 `.env` 形式存在服务器上（仓库只放 example）。｜证据：`deploy/.env.production.example:17,20,25`、`docs/03-运维手册.md:205`。｜建议措辞：「密钥只在服务器上，不入仓库」。**限定**：服务器被完全控制时密钥同样暴露。

- **✅｜单服务器 + 单实例，架构简单可解释**｜`db` 单容器、`api` 单实例、限流与登录节流都是进程内状态（因此也天然单实例）。｜证据：`deploy/docker-compose.prod.yml:37-120`、`login-throttle.ts:21-24`。｜建议措辞：「整套系统跑在一台你自己的服务器上，没有隐藏的云依赖」。

- **⛔｜「高可用 / 多副本容灾」**｜没有多副本、没有流复制、没有负载均衡；单点故障即停机（数据靠备份恢复）。｜证据：`deploy/docker-compose.prod.yml`。｜禁止措辞：「高可用」「多活」「自动故障转移」。
