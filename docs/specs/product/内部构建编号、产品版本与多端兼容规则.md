## 1. 产品版本与身份之间的关系

### 1.1 现行：S 系列开发版本

- `1.AB.CD`：`AB` 对应 S 开发阶段，`CD` 表示该阶段内部迭代；例如 S19 使用 `1.19.x`。这不是已经采用 SemVer 的承诺。
- 运行产品版本的源码源头仍是 `packages/shared/src/version.ts` 的 `APP_VERSION`；用户可见功能变更按 [AGENTS §6](../../../AGENTS.md) 升版并记录。纯文档规划不升产品版本。
- 原始版本按整数段保存与比较；既有界面补零只是展示（如原始 `1.19.1` 显示 `1.19.01`），不能用显示字符串做排序，也不把补零形式直接当成未来 SemVer。
- Git 提交标识源码，不证明构建成功、验收通过或实际发布。现有产品版本也不能独自证明某个二进制、环境或数据库状态完全相同。

### 1.2 待确认：公开发布后的 SemVer

建议在 S26 正式公开发布时切换 SemVer，并考虑 `2.0.0` 为起点；**切换关口、起始号及是否各平台同时切换均未批准**。确认前继续 §1.1，不提前改成 `2.x`。

切换后 Minor 不再绑定 S 阶段；需要先声明产品稳定契约的范围，包括公开接口、同步/备份格式及承诺的升级路径，再约定 Major 表示不兼容变化、Minor 表示兼容功能增加、Patch 表示兼容修复。协议和数据版本仍独立判断兼容，产品 Major 相同也不能免除检查。预发布标识可表达候选阶段；`+build` 元数据不参与 SemVer 优先级，不能用它承担平台升级排序。[SemVer 规范](https://semver.org/)

同一待发布产品版本可以多次重构建；已公开发布的版本内容不可被偷偷替换。已发布后的功能/修复变更应升适当产品版本；同源码重签或渠道包装如获批准，也必须登记不同构建/产物身份，不能覆盖旧文件。不能把“`2.1.0` 内部候选修复后重建”误读成“公开的 `2.1.0` 可以任意换包”。

### 1.3 规划中：身份模型

| 身份 | 回答的问题 | 关系与边界 |
|---|---|---|
| Product Version | 用户在用哪一代产品？ | 一版可以包含多个平台、多个候选构建，不说明所有平台已发布 |
| Git Commit | 从哪个源码快照构建？ | 保存完整 commit；一个 commit 可以产生多个构建，依赖与工具链也需固定 |
| Global Build ID | 哪一次受控构建尝试？ | 项目官方命名空间内唯一、递增，不随产品版本/S 阶段归零 |
| Platform Build Number | 该平台如何识别与排序安装包？ | 平台独立规则；与 Global Build ID 映射而非强制相等 |
| Artifact Identity | 到底是哪份字节内容？ | 文件 SHA-256、镜像 digest、目标架构、签名身份；一个构建可有多个配套产物 |
| Release Identity | 哪次获批准的发布活动？ | 引用已验收产物，可分平台/分批进行；审批与撤回单独留证 |
| Platform Release Identity | 哪个平台/渠道何时实际可用？ | 记录商店/下载渠道标识、受众、状态与产物；提交审核不等于可下载 |
| Deployment Identity | 哪个实例何时实际运行什么？ | 每次部署独立记录实例、镜像/资源、配置摘要及迁移状态；同包可多次部署 |

示例（**虚构，非当前支持或发布事实**）：

| 产品版本 | 构建 | 源码/目标 | 结果 |
|---|---|---|---|
| `2.1.0` 候选 | `1842` | 提交 A / Android | 内部测试发现问题，未正式发布 |
| `2.1.0` 候选 | `1843` | 修复提交 B / Android | 验收通过，平台构建号另行登记 |
| `2.1.0` 候选 | `1844` | 提交 B / Web（含 PWA 外壳） | 验收通过 |
| `2.1.0` 候选 | `1845` | 提交 B / iOS | 失败；号码保留，不能填补 |
| `2.1.1` | `1846` | 后续修复提交 C / Android | 新产品补丁候选，尚未发布 |

发布活动 `R-A` 可以先批准 Web 构建 `1844`，后批准 Android `1843`；iOS 仍未发布。Web 同一资源包可部署为实例记录 `D-A`、`D-B`，不会因此消耗新 Build ID。服务器若另有镜像构建，部署记录同时引用它自己的 Build ID 与 digest。构建完成先后、编号大小与实际发布时间不要求同序。

## 2. 规划中：Global Build ID 分配与追溯

### 2.1 分配单位与消耗边界

建议采用**一个明确目标和输入配方的一次受控产物构建尝试，一个全局编号**。Android、iOS、Web、服务器镜像独立构建各领一个号；一次 CI 矩阵运行有自己的关联 ID，不能把运行 ID 当成所有子任务的 Build ID。

| 行为 | 是否消耗正式 Build ID |
|---|---|
| 热更新、本地试编译、单测、文档检查、只检查代码的 PR CI | 否；使用本地/验证标识 |
| 输入已固定、准备用于可追溯内部交付/候选/正式发行的受控构建 | 是；检查输入后、开始产物构建前原子领号 |
| 已领号后失败、取消、超时、构建机丢失 | 已消耗；保留终态与原因，允许空缺，永不回收 |
| 失败后重新执行完整产物构建；同源码换工具链、依赖、编译参数或重新签名 | 新号，并关联先前尝试 |
| CI 内纯测试重试或重新下载同一份已封存产物 | 不新领号；记录测试/传输尝试 |
| 同一份字节从内部渠道晋级正式渠道、重新部署、镜像增加别名 | 不新领号；新增发布/部署事件 |

一个受控构建可同时生成同配方的安装包、符号文件、校验文件等配套产物，逐一登记摘要。Web 与 PWA 若共用同一资源包，则共用该构建；服务器多架构子镜像若独立执行构建则各有编号，汇总索引引用各子产物；改变或重新组装发行产物的任务另行登记，不能在旧记录下追加替换内容。

### 2.2 单一登记系统与并发

建议由一个逻辑上唯一的构建登记系统分配编号，可部署为持久服务或受控 CI 基础设施；**实现、存储位置、起始值、启用阶段待确认，本轮不建设服务**。

- 使用持久原子序列/事务和唯一约束，禁止“读取最大值再加一”、Git 提交数量、时间戳或多个工作流各自的运行计数充当全局分配器。
- 一次领号请求携带唯一请求键和不可变输入摘要；超时重发相同请求返回原编号，输入不一致则拒绝。只有唯一执行者可认领该尝试；任务恢复与重试需有租约/失效隔离，防止失联旧任务回写覆盖新产物。
- 分配顺序严格递增，完成顺序不保证递增；号码不是数量、时间或兼容程度。
- 登记服务不可用时不私自离线预分配“正式号”；可以继续本地开发，恢复后固定源码重新走受控构建。
- 登记库备份、恢复及单写者切换必须保护已发号高水位；恢复旧备份后先核对已分配记录与产物账册，不能从较小数值继续发号。
- 官方命名空间由项目维护。家庭自构建/第三方 fork 使用独立发行者命名空间，不得冒用官方编号；复用官方未改动镜像则保留其官方身份。安装兼容与可信签名另行判断。

本地标识建议为 `local.<随机会话标识>.<序号>.<短commit>`，另记 `dirty` 与本地输入摘要；`globalBuildId = null`，不能伪装成正式数字。正式构建只接受已固定、干净的源码与受控输入；不能把一个脏工作区临时包事后只补个编号就当作 CI 产物。

### 2.3 准确源码与产物证据

每个编号至少关联：完整 commit、源码归档摘要、锁文件与依赖输入摘要、构建配方/工作流修订、平台/架构、工具链/SDK/基础镜像 digest、非秘密编译配置摘要、分配/开始/结束 UTC 时间、CI 任务与尝试标识、终态、产物摘要及签名指纹。运行环境配置与编译环境分别记录；不将口令、私钥、真实账目写入公开清单。

安装包内嵌可读取的产品/构建/源码身份；外部产物登记将最终字节摘要与这些身份绑定。**只有 commit 不足以证明二进制准确来源**，源码之外的生成输入也必须可追溯。可追溯不等于已实现逐字节可重现构建；后者需要独立证明。文件 hash 用于完整性和查找，不能替代可信签名或权限审批。

## 3. 规划中：平台字段与独立升级顺序

| 平台 | 字段/身份 | 拟采用映射与限制 |
|---|---|---|
| Android | `versionName` / `versionCode` | 前者表达产品版本；后者在安装身份/发行渠道实际约束下递增。Google Play 的 `versionCode` 为正整数，最大 `2100000000`，已使用的上传编号不可重用；不能直接拼接无限位全局编号。[Android 官方规则](https://developer.android.com/studio/publish/versioning) |
| iOS | `CFBundleShortVersionString` / `CFBundleVersion` | 前者为三段数字产品版本，后者为一至三段数字构建字符串；不要把 `-rc` 或 `+build` 直接塞入这些字段。应用、产品版本和构建字段共同参与平台识别。具体上传递增范围、格式上限与分发工具约束在 S24 接入时复核并测试，不照抄历史限位规则。[版本字段](https://developer.apple.com/help/glossary/version-number/)、[构建字段](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleversion)、[上传关联](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds/) |
| Web / PWA | 产品标识、资源内容 hash、资源清单、Service Worker 资源代次 | 页面内可读 Build ID；资源按内容寻址。同一运行外壳不能混装不同构建的脚本，缓存代次不是业务数据库版本；不能用清理缓存顺便清除账本或待同步数据 |
| 自部署服务器 | 镜像标签、OCI 镜像/索引 digest、运行部署 ID | 标签如 `2.1.0-build.1847` 便于识别，精确运行证据以 digest 为准；多架构记录索引与实际架构子镜像，禁止只凭 `latest` 判断兼容或回滚 |

建议由同一登记体系维护**独立平台计数器及映射表**，并记录映射规则版本。是否在某平台满足范围时直接使用 Global Build ID，是待评估简化方案，不作为跨平台保证。不得截断、取模、归零或超限后换算法而没有迁移设计。

发行者、Android application ID、iOS bundle ID、签名及渠道共同影响升级路径。测试/正式渠道若共用安装身份，必须协调平台编号，不能各自计数后碰撞；独立安装身份也需验证数据迁移与恢复。各平台可停留在不同产品版本，不为凑齐版本号重发没有变化的包。

内部候选可共享产品版本；商店已经发布后的修复遵循 §1.2。应用商店通常不能靠上传较小平台构建号“降级回滚”：需撤回/停止分发，或构建带更高合法平台编号的修复包，并先验证其读取现有数据的能力；不是把旧源码重新包装就一定安全。

## 4. 规划中：客户端—服务器兼容契约

### 4.1 独立版本轴

| 轴 | 语义 |
|---|---|
| API contract | 请求/响应与错误结构契约；现有 `/api/v1` 路径不能单独证明所有请求语义兼容 |
| Sync protocol | 推送、拉取、游标、冲突、墓碑、确认与重试语义 |
| Data format | 业务对象/备份/操作载荷的可解释格式；与数据库结构版本分开 |
| Local schema | 各本地存储适配器的结构版本与读写能力范围 |
| Server migration set | 服务器实际应用的有序迁移 ID 与校验值；不是只数迁移数量 |
| Capabilities | 可选功能及契约修订，如 `attachments.read@1`（示意）；区分实现、启用、可用和当前身份获准 |

服务器声明支持的 API/同步协议集合、能力及强制要求；客户端声明自己支持的集合、每项操作要求的最低服务端能力。选择双方有交集且已验证的组合，不能把“最高产品版本”当作最佳协议。具体协议编号、接口路径、错误码和版本字段仍需实现评审，本轮不宣称已有握手接口。

### 4.2 协商与写入门禁

1. 连接目标服务器时确认目标身份和认证边界，取得最小兼容描述；只公开必要信息，不泄露数据库内部详情或秘密配置。
2. 求协议交集、校验必需能力、确定可以读/写/同步的功能集合。兼容描述要有修订标识；换服务器、重连及服务端状态变更后重新检查。
3. 所有业务写入由服务端在实际执行前重新校验协议、操作版本、能力与权限，拒绝不能理解的请求；前端隐藏按钮和此前握手都不能替代此检查。兼容不等于授权。
4. 拒绝返回可理解原因、目标实例、当前/要求的协议或能力、建议升级哪一端、数据是否仍在本机及恢复步骤。拒绝发生在业务事务提交之前，不得部分入账后才报版本不兼容。
5. 老服务端/客户端没有兼容描述时，只允许按明确登记、已测试的旧协议适配路径接入；没有证据即标记未知，停止远端写入/同步，不根据产品版本猜测兼容。

### 4.3 降级行为

| 场景 | 拟采用行为 |
|---|---|
| 旧客户端 + 新服务器 | 保留已承诺的旧协议适配；仅显示可理解内容，隐藏不可用新操作。不能把未知字段读丢后整对象覆盖回去 |
| 新客户端 + 旧家庭服务器 | 协商旧协议和能力子集；停用缺失的联网功能，说明需要升级家庭服务器，不能强制改连官方云 |
| 只有可选模块缺失/不可用 | 只影响对应功能；例如 OCR 不可用不阻断手工记账 |
| 无可用写协议、队列格式不兼容 | 暂停受影响远端写入和同步，保留原始操作；能安全读取才展示远端数据，否则提示无法解释 |
| 离线或远端兼容未知，但本地结构/操作格式可安全写入 | 继续本地核心记账，清楚标注未同步；不能承诺一定可上传，不能把远端故障扩散成本地停用 |
| 本地格式自身不可安全读写、迁移未完成、当前编辑会破坏未知字段 | 限制受影响数据的写入；提供受控备份/升级/恢复入口，不能伪装“保存成功” |

协议层兼容也不代表每个操作都兼容。可选功能分别协商；未知但可无损保留的字段留在原始数据中，无法无损回写的对象只能只读或拒绝编辑。先扩展读取与服务端接收能力，再开放新写入；删除旧协议要有使用证据、公告、迁移路径和所有者批准的支持期限。

## 5. 规划中：本地数据库、缓存与降级保护

现有 IndexedDB 数据和印记队列沿用原设计；未来 S22 本地核心、S23/S24 原生数据库要分别声明以下契约，不能假称现有数据库已具备完整的格式阻断机制。

- 各适配器分别定义结构版本（IndexedDB 数据库版本、SQLite 等适配器版本）、业务数据格式版本，以及客户端可读/可写范围。它们不能共用一个模糊的 `schemaVersion` 数字。
- 迁移图记录起点、终点、迁移 ID、校验值、前置条件、是否可逆，以及失败恢复路径。迁移数量相同不等于同一 schema。
- 升级前固定一致的数据点，包含唯一的本地账目、待同步操作及附件引用；先验证备份可恢复、容量足够，再在事务或受控副本中迁移。浏览器备份还在同一可被清理的存储内时，不宣称已形成独立灾备。
- 迁移成功并校验记录数、金额/关系不变量和队列状态后才切换版本标记。失败保留原数据与诊断；可回滚事务就回滚，无法原子回退时保留迁移检查点并阻止普通写入，恢复流程须可重入。
- 删除字段、压缩语义、合并无法分解的值或不可还原编码必须显式标为不可逆；有备份不等于允许自动整库覆盖，恢复会损失备份点之后的更改，必须评估并授权。
- 旧客户端启动前读取格式元信息，超出已验证范围时拒绝写入；不能“打开失败→删除数据库→重建”。已发布且没有这种保护的旧客户端不能靠新文档获得保护：升级前需验证其实际行为，必要时隔离新库、保留旧库只读并阻止旧写入路径，方案单独验收。
- 可再生成查询缓存可按格式失效；账本持久数据、未同步队列、附件不能按缓存清理。`cacheVersion`、外壳资源代次和本地业务 schema 分别管理。
- PWA 更新保留完整资源清单；旧标签页与新 Service Worker 并存时协调数据库连接和迁移锁。升级被旧连接阻塞时提示关闭/重载，不强制激活造成新旧代码同时写不同格式；离线更新不删除唯一可用外壳与未同步数据。

降级应用前必须先验证新数据对旧客户端的可读/可写兼容；仅恢复一个旧安装包或旧网页资源，不能成为数据回退方案。只读查看、无损备份、前向修复与经授权的备份恢复是不同操作，提示要说清影响范围。

## 6. 规划中：离线操作与同步升级

现行“印记就是队列”与 [S8 冲突判据](S8-冲突-设计决定.md)保持不变；下表是未来队列/印记封装契约的要求，不意味着已新增独立队列表。产品版本、构建编号、时间戳和数据库迁移序号都不能替代逐字段冲突判断。

| 项目 | 兼容要求 |
|---|---|
| 队列格式 | 单独记录 envelope/操作类型/载荷格式版本，保留对象 ID、base、wanted、目标服务器/账本身份及操作依赖；本地存储结构版本不能代替队列语义版本 |
| 幂等 | 每个逻辑变更的稳定操作 ID，在重试、重连、格式迁移后保持身份。服务端按服务器/租户或账本等明确作用域去重，并以事务绑定入账结果；相同键不同有效载荷拒绝，不能当成重试吞掉 |
| 确认丢失 | 服务端已入账、客户端未收到响应时，用同一身份重试并取得相同逻辑结果，收到持久确认后才清除待投递状态；不得生成新键再次记账 |
| 操作改写 | 已投递但未确认的操作保持不可变；后续编辑作为有依赖的新逻辑操作。迁移/拆分操作必须有确定的身份映射与重复提交证明，不能随意重编号 |
| 未知字段/操作 | 可无损保留的未知内容原样存储；不认识的必需语义拒绝或隔离，保留原始载荷和原因。禁止静默丢字段、跳过后标成功或直接删队列 |
| 顺序与故障 | 先阻断受影响对象/依赖链；只有证明独立的其他操作才继续。批次部分成功需逐项回执，不能把整个批次统一标已同步 |
| 游标/墓碑 | 版本化游标和删除语义。游标失效时安全重新拉取并合并，保留未提交的 base/wanted；不得覆盖本地队列、复活删除对象或丢失冲突证据 |

离线期间服务器升级后的恢复顺序：冻结待投递快照 → 重新协商目标服务器 → 校验游标/操作格式 → 必要时备份并迁移队列 → 按依赖重放 → 逐项确认。若协商或迁移失败，保留队列并说明阻断原因；网络恢复不是直接盲目重放的许可。

去重记录、变更历史和墓碑保存期限必须与支持的最长离线窗口一起设计，**具体期限待确认**。超出可证明去重窗口时先查询操作结果或进入对账流程，不能自动重新作为新操作提交。不可处理的格式暂停对应同步；本地能安全保存的新记账仍按 §4.3 工作，只有本地数据也不安全时才限制相应本地写入。

## 7. 规划中：家庭自部署兼容与升级

家庭服务器有独立实例身份、认证和维护节奏，不要求与官方云同日升级，也不强制依赖官方账号或在线编号服务。客户端按契约连接，不根据服务器品牌或产品版本相同假定兼容。

每个服务端发行产物需提供：镜像 digest/平台架构、构建身份、必需数据库版本/迁移图、API 与同步支持集合、可选模块契约、模块依赖和最低资源边界。运行实例另报实际启用与可用能力；“镜像包含 OCR”不代表实例已配置可用，更不代表当前用户获准调用。

兼容矩阵的最小记录单元为“客户端构建/平台 × 服务端构建/协议 × 数据格式 × 可选模块配置”，每格分别写读取、写入、同步、升级/恢复结果及证据：**通过／失败／未验证／不适用**。支持矩阵由测试产生，不从版本号推算。

示意判定（不是 Libevra 已验证范围）：客户端支持协议 `{P1,P2}`，家庭服务器支持 `{P1}`，只有 P1 对应操作及所需能力已验证时才允许使用；客户端只支持 `{P2}` 则停止该连接的远端写入，继续安全本地功能；服务器没有附件能力则禁用对应联网附件操作，不能阻断整个账本。

升级步骤的未来验收要求：读迁移路径与磁盘前置条件 → 备份数据库/附件/配置并隔离恢复演练 → 固定镜像 digest 与配置 → 进入适当维护窗口 → 执行已评审迁移 → 健康与账目/同步验证 → 记录部署结果。运行时秘密配置只记录受控引用/摘要，不放进公开镜像或版本清单。

应用回滚不回滚数据库。仅当旧服务端对当前 schema、关键状态与队列语义兼容且验证通过时才切回旧镜像；否则考虑前向修复或经授权恢复备份。恢复前保存故障现场、核对恢复点后写入和远端未确认操作；客户端不能因服务器数据回到旧时间点而自动清空待同步状态。是否提供长期支持线、允许跨几版升级、维护/安全补丁期限均待所有者决定。

## 8. 规划中：机器可读清单与单一可信来源

### 8.1 输入、构建快照与事件记录

建议未来用一个仓库内的**版本契约描述文件**作为人工维护源头（具体路径/格式待实施确认），自动生成 `version.ts`、Gradle/Info.plist 参数及运行时版本说明。启用前仍只维护现有 `APP_VERSION`；本轮不创建第二份可执行版本配置。

构建时，将该描述文件、源码/配方和登记系统分配值解析为**不可变构建清单**。平台字段与兼容报告都从它生成，禁止人工修改各平台副本。构建登记系统是 Build ID 与平台映射的唯一分配权威，仓库不能再手工维护另一个 `nextBuildId`。

发布/部署是构建完成后的事实，保存在追加式事件记录中并引用清单，不回写已签名安装包里的 channel/status。构建意图的 channel 与后续实际发布渠道分别记录；同一验收字节晋级不需要为改渠道标签而重新编译。并发登记的事件需要唯一身份与幂等写入。

### 8.2 字段草案

| 字段组 | 语义与约束 |
|---|---|
| `manifestSchemaVersion` | 清单自身结构版本；不是产品/业务数据库版本 |
| `issuer`, `productVersion`, `versionScheme` | 发行者、用户版本与 `stage` / `semver` 规则 |
| `globalBuildId`, `localBuildId`, `buildIntentChannel` | 正式号用十进制字符串避免整数精度丢失；本地构建正式号为 null；意图渠道如 internal/candidate/stable，不证明已发布 |
| `source.commit`, `source.archiveSha256`, `source.dirty` | 完整 commit、实际源码归档摘要、是否含未提交输入；正式记录 dirty 必须为 false |
| `target`, `platformBuild`, `mappingRevision` | 平台、架构、安装身份、平台编号/产品显示字段及映射规则版本 |
| `build.recipe`, `environment`, `timestamps`, `attempt` | 构建配方、工具链/依赖/非秘密配置摘要、UTC 时间、任务身份与结果 |
| `contracts.api`, `contracts.sync`, `contracts.dataFormats` | 命名的协议与格式支持集合；不把所有契约压成同一个整数 |
| `storageAdapters`, `queueFormat` | 各适配器 schema 及可读/可写集合、队列封装版本；不存在的适配器标不适用 |
| `capabilities`, `requires`, `compatibilityPolicyRevision` | 提供能力、按操作要求的服务端能力、协议范围及支持策略修订；运行权限另查 |
| `requiredMigrations` | 分别列本地/服务端/队列迁移的 ID、校验值、起止格式、前置条件、可逆性；不是只有迁移总数 |
| `evidenceRefs` | 测试、兼容矩阵、迁移演练和验收记录引用；无证据不能写通过 |
| 外部 `artifactAttestation` | 引用清单及最终安装包/镜像摘要、签名/来源证据；最终产物摘要放外部，避免内嵌清单与包摘要循环依赖 |
| 外部 `releaseEvents` / `deploymentEvents` | 审批、实际渠道、受众、时间、实例、当前产物、配置与迁移事实、撤回/回滚记录 |

清单校验要拒绝缺字段、未知必需语义、平台号碰撞、产品版本副本漂移、无来源产物及虚构证据。清单声明能力只说明构建所含实现，运行时仍核对模块启用、数据状态、认证与权限。当前实现不存在的字段保持“规划中”，不能用默认值冒充已检测结果。

## 9. 规划中：记录、验收与自动化门禁

### 9.1 一份技术事实，多种呈现

- 每个正式编号保留登记记录；失败/取消记录说明原因且没有可发行产物。每个成功交付记录源码、变更/主要修复、数据库与协议变化、兼容影响、测试结果、限制与证据；“无变化”也明确声明。
- 构建技术记录自动关联现有 `docs/changelog/` 产品条目和测试/迁移证据，不要求每次构建再写独立 Markdown 报告。未来注册系统未启用前，仍使用现行 changelog、Git、部署记录，不补造历史 Build ID。
- 发布状态按平台/渠道查询发布事件：未发布、内部测试、候选、已提交审核、分批可用、已发布、已撤回等需要各自证据。内部测试不是公众发行，构建的 `stable` 意图也不是已上线事实。
- 现有生产发布仍按 [AGENTS §7](../../../AGENTS.md) 一次发布一份记录，准备、执行、恢复入口放同一份；未来发布活动的多平台回执引用同一活动，不复制公告正文或重复维护事实。
- 用户公告只写实际可见、已核实的产品变化和必要升级提醒，按平台说明可用范围；不是每个 commit、Build ID、内部测试或重复部署都要发布公告。技术记录可含未发布修复，公告不能据此声称已上线。

### 9.2 拟议自动化门禁（本轮不实现）

| 关口 | 检查与失败处理 |
|---|---|
| 构建登记前 | 干净源码、锁定输入、产品版本合法、契约清单完整；不通过不发正式号 |
| 编号与平台映射 | 原子分配、请求幂等、唯一执行者、平台上限及升级顺序；失败留号，不能回收 |
| 构建封存 | 内嵌身份、产物摘要、签名身份和配方一致；任意产物变化不能覆盖原记录 |
| 兼容检查 | 新旧客户端/服务端双向组合、缺能力、无握手、握手后服务器变化、旧客户端未知字段写回；不兼容写入应在事务前拒绝 |
| 迁移检查 | 支持起点逐一升级、异常中断、空间不足、多标签页/进程锁、恢复演练、不可逆提示、旧版重开；无恢复证据不放行 |
| 同步检查 | 长时间离线后重连、超时重试、重复/乱序操作、同键不同载荷、未知操作、丢回执、失效游标、迁移与墓碑；核对金额与冲突结果 |
| 验收证据 | 必需测试实际通过，平台真机范围明确；缺测、跳过、不适用分别记录，不用绿色总状态遮盖缺口 |
| 发布审批 | 绑定准确构建/摘要、目标平台、受众、兼容影响与回滚方式；由所有者当次批准，CI 成功不自动上线 |
| 实际发布后 | 校验商店/下载产物与部署运行身份、实际迁移状态、健康与核心流程；失败停止推广并记录，按已评审恢复方案处理 |

既有检查分级仍由 [AGENTS §6.1](../../../AGENTS.md)决定。未来实现涉及财务数据、同步、迁移、权限时按相应高风险检查执行；本轮只是文档，不运行构建/迁移，也不声称上述门禁已自动执行。
