## 1. 背景与目标定义更新

### 1.1 为什么重写 S18-B 的定义

S18-B 最初被描述为“不同分辨率、屏幕比例与设备的 UI 适配”，重点在“让页面在不同屏幕上显示得下”。经过 2026-10-27 第三轮讨论，所有者确认这一描述**过窄**：字体、断点和缩放在技术上能解决“显示”，但解决不了“在更大的空间里，信息应该如何组织、操作应该如何变化”。

### 1.2 正式定位【已确认 2026-10-27】

**S18-B：跨设备自适应布局与交互体系（Adaptive Layout & Interaction）**

它不只解决 UI 在不同屏幕上的显示问题，还要解决：

1. 不同**窗口大小**下，信息如何重新组织；
2. 不同**宽高比例**下，导航和外围控件如何让位；
3. 不同**设备输入方式**下，交互逻辑如何变化；
4. **手机、平板、电脑**如何共享统一功能和品牌语言，同时具有各自适合的操作体验；
5. 如何避免简单地把手机 UI 按比例放大到平板或电脑；
6. 如何让复杂分析、记账、账本管理等功能**充分利用大屏幕空间**。

**这是一套面向整个 Libevra 的 UI 体系，而不仅仅是几个 CSS 断点。** 以上是开发目标与设计原则，**不代表任何具体布局已经确定**。

> 历史称呼：原“跨分辨率、跨设备形态与自适应布局”保留为 2026-10-27 次轮的历史描述，不再作为正式阶段名；阶段编号、任务编号（`S18-01…08`）与两阶段结构不变。

### 1.3 版本结构不变【已确认 2026-10-27】

- **继续保留现有 S18-A / S18-B 规划**：不拆分 S18-B，不新建 S19 来承接这些内容；
- 本次讨论发现的新增需求，**全部作为 S18-B 原有范围的扩展**；
- 不因工作量增长而自行修改版本结构、里程碑编号或开发优先级；
- S18-A 的既定范围（统一动画、转场、绿色顶部收缩、卡片动画、组件动效与 UI 细化）不因本轮讨论改变。

## 2. 核心设计原则

> 本章原则的状态均为【已确认】——所有者已明确表达。原则之下的一切具体做法仍是候选（§10 清单）。

### 2.1 P-01 屏幕变大，不代表 UI 应同比例放大【已确认】

这是所有者明确提出的重要原则。

- 假设某个按钮在手机上的视觉尺寸约为直径 1 厘米；到了平板上，它应继续维持接近合理的视觉尺寸，**而不是仅因为设备屏幕更大，就自动放大到直径 2 厘米**；
- 允许根据设备观看距离、输入方式、可访问性等因素进行**适度**调整，但**不能直接按屏幕宽度对所有组件进行同比例缩放**；
- 屏幕变大后，应优先：
  - 增加信息容量；
  - 增加内容列数；
  - 并排展示原本需要跳转才能查看的内容；
  - 提供辅助面板；
  - 改善留白和信息层级；
  - 提高连续工作的效率；
- **不要用大量无意义放大的按钮、卡片和空白填满屏幕。**

### 2.2 P-02 使用逻辑尺寸，而不是直接依赖物理分辨率【已确认】

Libevra 是 Web / PWA，应主要使用 **CSS px、rem、响应式设计 token、视口尺寸与容器尺寸**等机制判断布局。需要区分：

- 设备物理像素；
- 浏览器 CSS 视口宽高；
- 组件容器可用宽高；
- 设备像素密度；
- 系统和浏览器缩放；
- 触屏与鼠标命中区域。

**不要根据具体手机的硬件分辨率简单判断应该使用哪套 UI**；也不要求 CSS 尺寸严格对应现实中的固定厘米数（“1 厘米”在 §2.1 中只是直观说明）。

### 2.3 P-03 核心内容空间优先【已确认】

这是所有者提出的另一项核心原则。界面在概念上分为：

- **核心内容区域（Content Canvas）**：账目、图表、分析卡片、记账表单、账户资料等真正重要的信息；
- **外围控制区域（Adaptive Chrome）**：主导航、快捷操作、工具栏、部分状态提示与辅助按钮。

在屏幕空间不足时，应**优先考虑重新组织外围控件，而不是无限压缩核心内容区域**。

例如，在宽而矮的手机上，可以研究将原本占据顶部和底部的部分控件移动到侧面，以保留更充足的内容高度。但**不能因此隐藏重要财务警告或造成关键操作不可达**。

### 2.4 P-04 不强制锁定固定的内容长宽比【已确认】

所有者此前提出，希望在不同长宽比的手机上，尽量为中央内容提供一个比例协调的展示区域；讨论中曾以 16:9 的横向比例、对应竖屏约 9:16 的比例作直观参考。

**这只是设计理念，不是硬性比例约束。**

不要求全部设备维持固定 16:9 或 9:16，也不要求内容区必须是固定长方形。不同页面需要的空间本身不同：

- 交易列表通常更需要**高度**；
- 趋势图可能需要**宽度**；
- 表单需要合理的**行宽**和按钮尺寸；
- 数据表格需要较大的**横向空间**。

最终原则：**优先保证核心内容区域拥有适当空间，允许外围控件自适应排列；不强制锁定固定长宽比。**

### 2.5 P-05 电脑版不能只是放大的平板版【已确认】

电脑端需要重点考虑**鼠标和键盘**。除了布局变化，可能还需要：

- 键盘快捷键；
- 右键菜单；
- 鼠标悬停反馈；
- 表格与更高的信息密度；
- 批量选择和批量编辑；
- 行内编辑；
- 固定或可展开的详情面板；
- 连续录入、多任务操作；
- 更方便的筛选、排序与搜索。

移动端则继续考虑手指触控、明显的主要操作入口和合理的触摸命中区域。

### 2.6 P-06 输入能力与窗口大小是两个独立维度【已确认】

平板可能连接键鼠，电脑也可能支持触屏。**不能简单地认为宽屏一定只有鼠标操作、窄屏一定只有触摸操作**：窗口尺寸和输入能力必须分别判断、组合判断（详见 §3）。

### 2.7 P-07 统一功能与品牌语言，各自的适合体验【已确认】

手机、平板、电脑共享同一套功能语义和品牌语言，但操作体验应适合各自设备；**不允许为每一种具体设备型号分别建立完全独立的 UI**。

### 2.8 P-08 宽屏导航以左侧竖向为总体方向【已确认方向；细节待所有者草图】

- 常规手机竖屏保留底部导航；
- 在空间足够的宽屏布局中，优先研究将主导航改为竖向排列；
- 常规宽屏的竖向导航**以左侧为首选方向**；
- 特殊低高度设备可研究侧边控制区的其他排列方式。

注意：左侧竖向导航是宽屏设计的**总体方向**，具体栏宽、位置、按钮分布与细节**尚未确定**（§10 O 清单）。

### 2.9 P-09 绿色加号是 Libevra 的视觉语言【已确认】

绿色加号（点击展开五种记账方式）最初是因为手机屏幕空间有限。但经过长期使用，所有者认为它**已经逐渐形成 Libevra 的视觉语言，具有独特的识别价值**：用户看到加号，通常自然理解为“添加 / 创建”。

因此即使到了平板和桌面，**也不应简单地因为空间充足，就默认废弃现有加号设计**。具体方向见 §5.3。

同时所有者特别强调：**绿色记账按钮应有足够的视觉突出程度**；浅色主题下周围尽量使用白色或低干扰背景，让品牌绿色自然突出；深色主题使用对应的中性背景与合理对比；并为五种记账方式的展开**保留空间，避免菜单被屏幕、侧栏或容器裁切**。

### 2.10 P-10 与 S17 布局系统一致：派生布局不得写回权威【已确认】

S18-B 复用 S17 建立的布局引擎、配置与持久化机制。不同屏幕宽度可以有**派生布局**，但必须遵守既有的权威布局、迁移规则和**不累计漂移**原则；**不能因为用户切换屏幕宽度或设备旋转，就静默破坏保存的卡片配置和原始布局**（详见 §7.1 与[新路线图 §4.3.2](../product/S17-S18-新路线图.md)）。

## 3. 适配维度：宽度、高度、输入方式与特殊屏幕空间

### 3.1 不能只依据单一信号

不能只依据 `orientation: landscape` 或单一宽度断点选择布局。后续需要**至少同时判断**宽度、高度、输入能力与特殊屏幕空间四类信息。

### 3.2 宽度

决定：

- 导航位置（底部 / 左侧 / 顶部 / 侧边控制区）；
- 内容列数；
- 辅助面板是否存在、以何种形态存在；
- 主从布局是否可以并排。

### 3.3 高度

决定：

- 顶部区域的最大合理高度；
- 工具栏压缩策略；
- 可用内容空间；
- 是否进入**低高度模式**。

例如手机横屏可能**非常宽，却只有很有限的高度**，因此不能仅凭宽度将其当作普通平板横屏。

### 3.4 输入能力

分别处理 **touch、mouse、hover、keyboard** 等能力；允许混合设备（触屏笔记本、接键盘的平板）同时命中多类能力；**不得由窗口宽度反推输入方式**（P-06）。

### 3.5 特殊屏幕空间

需要考虑：

- 折叠屏铰链与分段区域；
- 刘海和系统安全区域；
- 虚拟键盘；
- 浏览器工具栏；
- 系统和浏览器缩放；
- 设备分屏；
- 动态窗口尺寸变化。

### 3.6 逻辑尺寸与判断手段的候选【待技术验证】

以下只是**候选技术方向**，具体断点、阈值与实现机制**暂时不冻结**：

- CSS px / rem / 响应式 token 作为布局尺寸基准（P-02）；
- 视口单位（含动态视口高度类单位）与容器查询作为候选判断手段；
- `hover` / `pointer` 等能力媒体查询与运行时可用的指针能力检测；
- `env(safe-area-inset-*)` 一类安全区处理；
- 虚拟键盘与可视区域变化的运行时观测；
- 折叠屏分段区域相关的可用平台能力；
- 元素尺寸 / 容器变化的运行时观测（如 `ResizeObserver`）。

上述手段是否采用、如何组合、在哪些组件上生效，**必须在阶段四工程规格（§9）中用原型与真机验证后再定**。

### 3.7 不按设备型号分支【已确认】

**按实际容器尺寸与窗口状态适配，不按设备型号分支**；不要求为某款具体折叠屏、平板或手机写死规则。

### 4.2 三种候选布局体系（设计候选，未批准）

| 代号 | 名称 | 主要参考场景 | 可能采用的结构（讨论稿） | 状态 |
|---|---|---|---|---|
| A | 紧凑布局 Compact | 现有手机竖屏 | 现有底部 Tab、单列核心内容、手机端记账入口、适合触摸的表单和操作；现有手机端设计基本保留 | 【设计候选】 |
| B | 自适应宽屏布局 Adaptive Wide / Touch | 平板、折叠屏、较宽手机以及部分横屏窗口 | 侧边竖向导航、随窗口高度变化的紧凑工具栏、根据可用宽度决定单列或多列、适合触摸操作的控件间距、对非常矮的横屏设备进行特殊空间优化 | 【设计候选】 |
| C | 桌面工作台布局 Desktop Workspace | 拥有充足空间的键鼠工作环境 | 可展开侧栏、高密度列表或表格、多栏信息展示、详情与属性检查器、键盘快捷键、连续编辑和批量操作 | 【设计候选】 |

### 4.3 重要声明：A / B / C 不是已批准的 UI 架构

- **A / B / C 是讨论中的候选分类方法，而不是已经批准的最终 UI 架构**；
- 具体需要几种布局、是否增设中间状态、各布局在哪个宽高区间切换，**都尚未确定**；
- **禁止未经所有者确认就将这些分类冻结为最终工程方案**；
- 本文**故意不给出宽高区间或阈值示例**，避免任何数字被误读为已定断点；
- 也不应该为每一种具体设备型号分别建立完全独立的 UI（P-07）。

### 4.4 “手机 / 平板 / 电脑”三个词的用法

它们是**使用场景标签**，便于讨论；真正的适配输入是**窗口 / 容器尺寸 + 输入能力 + 特殊屏幕空间**，而不是设备名称本身。

## 5. 导航、Logo 与绿色记账入口（讨论记录）

### 5.1 导航栏

目前比较明确的总体方向【已确认方向；细节待所有者草图】：

- 常规手机竖屏保留底部导航；
- 在空间足够的宽屏布局中，优先研究将主导航改为竖向排列；
- 常规宽屏的竖向导航以左侧为首选方向；
- 特殊低高度设备可研究侧边控制区的其他排列方式。

注意：

- **左侧竖向导航是宽屏设计的总体方向，但具体栏宽、位置、按钮分布与细节尚未确定**；
- 对于非常宽而矮的手机，曾讨论将部分顶部或底部控件移向右侧，以给核心内容保留空间；但**哪些按钮适合放到右侧、是否需要双侧控制区，都仍属待讨论方案**；
- 不允许直接按照某一款具体折叠屏设备写死规则。

### 5.2 Logo

所有者提出，希望考虑将 **Libevra Logo 放在宽屏导航区域左上角**。参考常见桌面网站设计，Logo 通常可作为品牌识别与返回默认页面的入口。

目前尚未确定【待所有者草图】：

- Logo 的具体尺寸；
- 是否展示文字；
- 点击后回到哪个页面；
- Logo 与其他操作之间的留白；
- 侧栏展开与收起时的表现。

**不得自行决定。**

### 5.3 绿色记账加号（重点记录）

现状：Libevra 目前采用**绿色加号**，点击后展开**五种记账方式**。

- 这种交互最初主要是因为手机屏幕空间有限，无法方便地让五种入口全部常驻；
- 但经过长期使用，所有者认为**绿色加号已经逐渐形成 Libevra 的视觉语言，具有独特的识别价值**（P-09）；
- 因此即使到了平板和桌面，也不应简单地因为空间充足，就默认废弃现有加号设计。

目前**可讨论的方向**（均未定案，【设计候选】）：

1. 继续保留加号作为统一记账入口；
2. 根据设备改变五种操作的展开方向；
3. 宽屏中保留加号，同时提供部分高频记账快捷入口；
4. 桌面端增加键盘快捷键或快速记账面板；
5. 空间非常充裕时，研究五种记账方式是否适合部分或全部常驻。

**视觉突出要求【已确认】**：

- 绿色记账按钮应有足够的视觉突出程度；
- **浅色主题**下，周围尽量使用白色或低干扰背景，让品牌绿色自然突出；
- **深色主题**则使用对应的中性背景与合理对比；
- 需要为五种记账方式的展开保留空间，**避免菜单被屏幕、侧栏或容器裁切**；
- 颜色与 token 的使用必须与[颜色语义与配色规范](颜色语义与配色规范.md)、[颜色主题系统实现规范](颜色主题系统实现规范.md)保持一致；**不得为未确认的布局自行新增颜色 token 或绕过主题系统**。

**尚待所有者确认**：主按钮的确切位置、造型、尺寸及展开方式（**必须等待所有者提供草图或进一步意见**，见 §8 与 §10）。

### 5.4 其他外围控件

快捷操作、工具栏、状态提示与辅助按钮属于“外围控制区域（Adaptive Chrome）”。在空间不足时优先重组它们（P-03），但**不得隐藏重要财务警告或造成关键操作不可达**。

## 6. 各主要页面的适配方向（讨论参考）

> **以下仅为讨论参考，不能作为已经批准的布局规格。** 所有页面布局均需所有者进一步设计和确认（§8 门禁、§10 O 清单）。

| 页面 | 手机（现有） | 宽屏探索方向【设计候选】 | 电脑探索方向【设计候选】 |
|---|---|---|---|
| 明细 | 单列账目展示 | 列表与详情并排 | 高密度表格、批量操作、排序、搜索、右侧详情 |
| 分析 | 保留已有卡片工作台的主要体验 | 利用更大的内容区域展示更多卡片 | 常驻筛选区、属性面板、更高密度的工作台布局 |
| 记账 | 保留现有加号展开方式 | 适合触屏的弹层、侧边面板或其他形式 | 快速录入、快捷键、连续编辑 |
| 账本与协作 | 现有列表与详情跳转 | 列表与账本详情、成员权限等信息并排显示 | 同左，并考虑批量管理 |
| 「我的」 | 保留已有个人资料区域 | 横向组织个人信息和设置内容 | 同左，并考虑多栏设置 |

### 6.1 分析页面的硬约束【已确认】

**必须复用 S17 Agent D 的正式布局引擎、持久化及响应式投影规则**；设备旋转或窗口改变**不能静默破坏用户保存的卡片布局**（§7.1）。分析页的宽屏布局探索**不得**另建一套布局数据模型。

### 6.2 记账语义一致【已确认】

五种记账方式在手机、平板、电脑上的**功能语义应保持一致**；允许形态、位置、触发方式不同，但不允许某个设备缺失某种记账方式。

### 6.3 与 S18-A 兼容

「我的」页的宽屏排布需要与 S18-A 已规划的绿色顶部收缩及头像变化动画保持兼容（§7.2）。

## 7. 与 S17 布局系统、S18-A 动画体系的关系

### 7.1 复用 S17 / D 布局系统

- 继续沿用现有 S17 / D 的布局系统：不同屏幕宽度可以有**派生布局**，但必须遵守既有的权威布局、迁移规则和**不累计漂移**原则（[布局规格 §13–§19](S17-工作台布局与格式模板规格.md)）；
- **不能因为用户切换屏幕宽度，就静默破坏保存的卡片配置和原始布局**；派生结果不得写回权威布局（除非用户显式保存）；
- **S18-B 无新增财务计算、无新增持久化数据**（[新路线图 §8](../product/S17-S18-新路线图.md)）；纯前端呈现、交互与布局派生；
- 如果未来允许用户保存特定宽度的独立布局档案，必须明确权威关系与同步策略（路线图 §4.6 S18-OQ-06，与 Q-08、OQ-LM-07 / OQ-LM-08 联动）；在此之前，跨宽度只做确定性派生。

### 7.2 与 S18-A 的关系：兼容，不推翻

S18-A 已确定负责：

- 统一动画体系（时长分级、缓动 / spring 原则、`prefers-reduced-motion`）；
- 页面转场；
- 顶部绿色区域收缩；
- 分析工作台卡片拖放动画；
- 组件动效与 UI 细化。

其中一个明确的设计要求是：**绿色顶栏收缩之后始终紧贴屏幕最上方**。

S18-B 的宽屏设计需要与这些机制兼容；但不同设备的顶部布局可能不完全相同，具体如何收缩仍需结合后续草图决定（【待所有者草图】）。**不得因本次文档更新擅自推翻 S18-A 的既定规划。**

### 7.3 共享设计系统

- 响应式 token、组件多设备适配层属于**统一设计系统**的一部分，不得在每个页面各自发明一套；
- S18-B 发现的通用组件问题，应回馈统一设计系统（token 与组件库），而不是在各页面逐个打补丁（[新路线图 §4.4](../product/S17-S18-新路线图.md)）；
- S18-A / S18-B 共享视觉规范与组件系统，但验收标准分开定义。

## 8. 设计决策权限与草图确认门禁（强制）

> **本章对后续所有参与 S18-B 的 Agent 具有强制约束力，包括 Claude、DeepSeek、Codex 或其他开发助手，以及未来的任何会话。**
> 本章回答一个问题：**讨论出来的东西，什么时候可以变成“要实现的页面”？** 答案是：**只有所有者明确确认之后。**

### 8.1 本轮讨论只确认理念，不确认具体视觉稿

当前已经提出了设计原则和候选布局分类，但**绝大多数具体 UI 仍未定案**。

**任何 Agent 不得将讨论中的示例直接认定为正式设计。** 本文出现的所有页面示意、布局描述、组件排布，只能作为讨论材料引用，不能当作实现依据。

### 8.2 具体布局必须先征询所有者

以下事项在实施前必须取得所有者**明确意见**：

- 手机横屏的具体页面布局；
- 平板横屏与竖屏的导航结构；
- 折叠屏展开后的布局结构；
- 桌面工作台的具体页面结构；
- Logo、绿色加号及五种记账入口的排布；
- 双侧控制区的具体使用方式；
- 各个页面的主内容、辅助面板与工具栏安排；
- 其他影响整体视觉和交互方式的重要布局方案。

**Agent 必须先请所有者提供草图、参考图、明确文字描述或具体设计意见。** 草图可以非常简单，只需要表达结构关系，不要求专业美术质量。

### 8.3 禁止自行生成最终布局方案

未经所有者明确要求：

- 不得自行生成 UI 草图；
- 不得自行生成 UI 效果图；
- 不得自行生成完整视觉原型；
- 不得擅自设计并冻结布局；
- 不得把 AI 提出的候选方案写成所有者批准的决定；
- 不得直接把未经确认的方案实现为正式页面。

Agent **可以**做：

- 分析现有界面、整理约束；
- 研究技术可行性；
- 记录其他成熟软件的设计案例；
- 在所有者要求时提供不同设计方案供讨论。

但**最终选择权和具体布局定义权属于所有者**。

### 8.4 没有草图时应如何处理

如果开发推进到了需要决定具体布局的阶段，而所有者尚未给出草图或意见：

1. 标记为「**待所有者设计确认**」；
2. 说明当前缺少哪一项设计决定；
3. **保留原有 UI**，避免自行创造替代布局；
4. 继续处理**不依赖**该设计决定的工程准备工作；
5. 等所有者主动恢复讨论或提供材料后再推进该部分。

**不得为了完成任务而绕过确认门禁。**

### 8.5 违规的后果与记录方式

- 未经所有者确认的布局方案，一律视为**未批准草稿**：不得合入正式页面，不得写入规格文档，也不得以“已实现”或“设计已定”表述；
- 如果 Agent 已经误做，应在文档与提交说明中标注“未获所有者确认、待返工”，而不是把结果留下当作方案；
- 门禁的例外只有一种：**所有者当次明确授权**（例如“这次按你提的方案先做出来看看”），且必须记录授权范围。

### 8.6 与决策状态标识的配合

本文与相关文档中的每一条设计结论都必须带状态标识（§10）。读文档的 Agent 必须：

- 只把【已确认】当作约束；
- 把【设计候选】当作可讨论方向；
- 把【待所有者草图】当作**不可实施**；
- 把【待技术验证】当作**工程准备项**；
- **不得把候选想法误认为实施指令。**
