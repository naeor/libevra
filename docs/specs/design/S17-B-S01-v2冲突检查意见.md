## 2. 🔴 需 A 修订/裁定项

### B-V2-01 `total` 口径矛盾：§3.2 表 vs §4.2
- **位置**：v2 §3.2 `time-series` 行「`total` 只对 complete 桶求和」；§4.2「`total` 口径：`unknown`/`future` 不计入；`in-progress` 可计入但 `complete=false` 明示；存在 `unknown` 时 `total=null`」。
- **冲突**：两处对 `in-progress` 是否进入 `total` 相反。B 实现（`timeSeries.ts` 已提交 `934680c`）口径为：**`total = Σ(state ∈ {complete, in-progress})`，任一 `unknown` → `total = null`，`future` 不计入**；`complete = (unknown==0 && future==0 && inProgress==0)`。这与 §4.2 一致、与 §3.2 表相反。
- **建议**：冻结稿删除 §3.2 表「只对 complete 桶求和」表述，统一为 §4.2 口径并补一句「`in-progress` 计入 `total` 但 `complete=false`；`unknown` 存在时 `total=null` 且必须给出 `unavailableReason`」。B 不需改实现。

### B-V2-02 §3.2 括注把 I12 标成「支出分类构成」
- **位置**：v2 §3.2 `calendar-heatmap` 行括注「（**I12 为「支出分类构成」，非日历**）」。
- **事实**：所有者规格 **I12 = 每日支出波动（对应 A12）**；「支出分类构成」是 **I14**；日历热力对应 **I19/I13（B08）**。
- **建议**：改为「I12 为每日支出波动（A12），非日历；日历热力见 I19/B08」。

### B-V2-03 §3.4 `calendar` 行仍要求对齐「B I12 日历」
- **位置**：v2 §3.4 C 的 `calendar`（P15）行「**须与 B I12 日历同结果、不另立日历系统**」。
- **冲突**：C 的日历应对齐 B 的 **`calendarHeatmap.ts`（B08/I19）**，不是 I12；若按错编号实现，C 侧会拿「每日支出波动」当日历口径，冻结后产生跨 Agent 口径分裂。
- **建议**：改为「须与 B 的日历热力（B08/I19，`calendarHeatmap.ts`）同结果、同五态、周一起始；强度分位以 B 实现为权威」。与 B-17 唯一实现归属一致。

### B-V2-04 五态→9 态映射在桶级丢失信息
- **位置**：v2 §4.10 映射表；`in-progress` → `no-transactions` 或 `complete`，靠「结果层 `complete=false` 明示」兜底。
- **问题**：卡片/图例需要逐桶状态（B 的 `TimeBucket.state` 是五态）。仅映射到 9 态后，桶级消费者无法区分 `in-progress`/`unknown` 与「已知空桶」；`unavailable` 还要按 `fx-incomplete`/`request-failed`/`no-permission` 细分。
- **建议**：v2 明确「**桶对象保留五态原值 `state`（B 已实现），9 态仅用于 `result.completeness`**；逐桶若需细分原因，附 `unavailableReason?`（枚举见 B §3.7）」，映射表保留作 envelope 层规则。

### B-V2-05 `metric` 是否允许 `count`
- **位置**：v2 §2「`analysisId`/`analysisType`/`metric` 沿用」；s01-draft 的 `metric` 未固定枚举（原 `AggregationKind` 为 `sum|count|average|...`，`RecordExtremeResult.metric` 只有 `"expense"|"income"|"net"`）。
- **问题**：I19 每日交易频率要求 `metric = "count"`（B 实现 `TimeSeriesMetric = "expense"|"income"|"count"`）；若冻结时把 metric 收窄为金额枚举，B 的 count 序列无法表达。
- **建议**：v2 §2 明确 `metric` 为开放字符串（推荐 `<domain>.metric` 命名）或显式加入 `"count"`；同时 §3.2 `time-series` 行注明「`count` 序列的 `value` 为整数计数、`MoneyValue` 不适用」。

### B-V2-06 `SourceDescriptor.query.kind` 收窄后的映射缺失
- **位置**：v2 §2「`SourceDescriptor.query.kind` 增 `"analysis-records"`、`"fx"`」；§7 G-02 待裁定。
- **问题**：B 现有信封草案用 `kind: "stats" | "transactions"`（与现网 `/stats`、`/transactions` 对应）。若冻结后 kind 只允许新增两值，B 七形状来源无法直写；若允许保留旧值，需在 v2 明确「`stats`/`transactions` 仍有效（1.16.23 已实现路径）」及三者的语义边界。
- **建议**：v2 §4.4 增加 kind 映射表（`stats`=服务端聚合、`transactions`=逐笔读取、`analysis-records`=A 的 T2 只读投影、`fx`=FX 只读投影），并允许 `kind: string` + `params` 扩展；B 七形状在 W1 只用 `transactions`/`stats`（原币路径）。

### B-V2-07 桶 `span` 的裁剪语义未明确
- **位置**：v2 §4.1/§4.4 只说桶半开 `[start,end)` + `bucketToInclusive`；未说 `span` 是「自然桶」还是「被分析区间裁剪后的桶」。
- **问题**：点桶取来源（`bucket.from/to`）时，若 `span` 未裁剪，会取到分析区间外的交易（或漏掉末端）；B 实现同时有 `span`（裁剪后）与 `naturalSpan`（自然桶）+ `clippedStart/clippedEnd`。
- **建议**：明确「`bucket.span` 为**裁剪到分析区间后**的半开区间；自然桶起点/终点另存 `naturalSpan`，`clippedStart/clippedEnd` 标记；`bucket.from/to` 用 `bucketToInclusive(bucket.span)`」。B 不需改实现。

### B-V2-08 `dataVersion` 在客户端计算路径的取值
- **位置**：v2 §2「`dataVersion` 书级数据版本令牌，由计算入口提供、A 只透传；缓存键必须包含」；§7 G-10 待 Lead/离线模块定。
- **问题**：W1 原币路径（B 的 S0 决策）是 web 端基于交易页计算（与 `localStats.ts` 同模式），**没有服务端计算入口**，`dataVersion` 无直接来源；若冻结稿要求非空 string，B 的 24 项原币分析无法满足。
- **建议**：G-10 明确原币路径的取值规则（例如取当前账本最新 `updatedAt`/事件游标，作为 query key 的失效因子），或允许 `dataVersion: string | null`（null=不用于服务端缓存，仅前端 key 用本地版本）；B 在 S0 实现可切换的 `analysisKeys`。
