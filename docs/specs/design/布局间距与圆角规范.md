# Libevra · 布局间距与圆角规范

> 最后修改：2026-11-08 23:28（UTC+08:00）

现行规则：间距、圆角、二级页面骨架和 S19 组合模式。保留 §15–§17 编号供现有引用定位；旧审计、试验与实测记录见文末历史依据。具体材质与转场见 [S19 设计系统](S19-材质组件与动效设计系统.md)。

## 15. 现行几何与组件边界

底部贴边面板上圆角使用 `rounded-t-sheet`（24px），下圆角为 0；安全区由既有容器负责。不要为视觉重整改变手势、导航或权限行为。

### 15.3 页面与间距边界

个人资料的只读 `dl` 不机械改为可点击设置菜单。导出页的分段按钮 `px-4` 是控件内边距，与列表行 `px-5` 不同。行高由内容行数与触控目标决定，不全局统一垂直内边距。协作留言、编辑历史、账本列表按各自内容结构使用共享积木。

容器是否保留由职责决定：滚动边界、定位参照、动画裁切、软键盘避让和语义分组都可以需要嵌套。不能为减少层数删除这些容器；只清理没有独立职责的重复视觉包装。海浪/动态标题的进度插值、图表坐标与徽标光学校正不是普通间距 Token，不参与机械归一。长文与多行控件允许高度增长，窄屏不靠固定高度裁掉内容；安全区、键盘和触控目标按 §16、§17 的对应规则验证。

### 15.4 为什么底部面板的圆角与卡片**分开**

所有者裁决：*"底部面板属于大型浮起式交互容器，与普通卡片不是同一种组件……
未来修改底部面板圆角时，不应该连普通信息卡片的圆角一起改变."*

**⚠️ 关键不在那 4px，而在"改一个不会连带改另一个"。**
`--radius-card` 同时画着**所有信息卡片**，所以如果把面板绑在它上面，
**"让面板更圆"和"让卡片更圆"就会永远变成同一次编辑**。

**⚠️ 另一个具体理由**：`.rounded-t-card` 的定义是 `border-top-*-radius: var(--radius-card)`，
**改 `--radius-card` 会同时改卡片和它的消费者**——面板与卡片从此无法分别演进。

### 15.5 Bottom Sheet 的判定标准（避免以后误判）

**已确认的贴底面板组件认定为 Bottom Sheet**，判定依据是**「从视口底边升起、覆盖在内容之上的浮层」**：

| 是 Bottom Sheet ✅ | 不是 ❌ |
|---|---|
| `BookManageSheet`（`fixed inset-x-0 bottom-0`） | 普通 `Dialog`（居中，四角都圆） |
| `MonthPicker`（底部升起的选择面板） | 弹出菜单（锚定在触发元素旁） |
| | 卡片（在文档流里，四角都圆） |

**⚠️ 判据不是"圆角大不大"，而是"它是不是从底边长出来的"。**
**⚠️ 因此 `rounded-t-sheet` 只设上两角；普通 Dialog 与卡片继续用 `rounded-card`（四角）。**

### 15.6 共享间距来源

不新增全局 `--spacing-*` 变量，不另建间距配置体系；共享组件本身可以是规则的唯一来源。页面横向基准 24px 由 `Section` / `SectionFrame` / `TabPageHeader` 的 `px-6` 保证，控件内边距与列表行另按其角色定义。否决全局间距变量的原因和原始测量保存在文末历史依据，不作为待实施方案。

### 15.7 最终圆角语义等级

| 角色 | 实现 | 值 | 用在哪 |
|---|---|---|---|
| 小型控件 / 图表格 | Tailwind `rounded-sm` | **4px** | 图表日历格 |
| **控件 / 列表行 / 输入框** | **`--radius-field`** | **14px** | 按钮、输入框、列表行、chip |
| **普通信息卡片** | **`--radius-card`** | **20px** | 所有卡片、Dialog、分段容器 |
| **底部面板（仅上两角）** | **`--radius-sheet`** | **24px** | `BookManageSheet`、`MonthPicker` |
| 圆形 | `rounded-full` | 50% | 头像、分类圆标、徽标 |

**⚠️ 只有 4 个圆角值 + 圆形。不要新增第五个，除非有和中控面板同级的独立职责。**

### 15.8 修改验证

检查实际面板上/下圆角、卡片与控件角色、列表内边距、触控目标及横向溢出。共享 CSS 改动还需验证编译结果与受影响页面。历史测试数量和当轮视觉变化见历史依据，不作为新改动的验收结果。

## 16. ✅ 二级/三级页面的骨架与内容积木（S16-A，2026-10-23）

> **起因（所有者原话）**：*"许多二级、三级页面过度依赖「返回按钮 → 页面标题 → 一段灰色说明 → 数张圆角白色卡片」……
> 统一的应该是：文字层级和排版规则、页面边距/间距及对齐、操作反馈和导航习惯、卡片/列表/表单的设计原则、
> 整体视觉气质。不应该强制统一的是：每个页面必须有副标题、每个区域必须有卡片、每段说明必须单独成框……"*
>
> **所以本节规定的是"规则与积木"，不是页面模板。** 数值仍是 §15 的那几个（页面边距 24、行内边距 20、
> 圆角 4/14/20/24），本节**没有新增任何 token、颜色或字号**。

### 16.1 页面骨架：`InnerPage`

| 部分 | 规则 |
|---|---|
| **顶部导航条** | `sticky top-0`，高 48px + `safe-area-inset-top`；左侧「‹ 返回」（`data-back-control`，44px 触控高度，箭头落在内容 24px 边线上），右侧是页面自己的操作槽（`actions`） |
| **大标题** | `text-page-title`，紧跟在导航条下面；**滚出导航条之后**，导航条中间出现同一标题的小号版本，并在条下沿出现一条细线（`IntersectionObserver`，不监听滚动） |
| **副标题** | **可选**。只写"这一页是关于哪一个"（账本名、版本号）这类上下文，一到两行；**说明这一页怎么用的话不放这里**，放到它解释的东西旁边（§16.4） |
| **离线横幅** | `SyncBanner` 在导航条的同一个吸顶组里（不会被导航条盖住）；下载提示 `OfflineStatus` 在其上方随页面滚走 |
| **返回** | 仍然是 `useGoBack(backTo, backMode)`：默认按历史返回，`backTo` 只是深链兜底；账本设置仍是 `parent` |

**例外（有明确原因，不套这个骨架）**：

| 页面 | 原因 |
|---|---|
| 五个一级页（明细、分析、记账、账本/协作、我的） | 绿色页头 + 底部导航，是一级页的身份 |
| 账本空间 `/start` | 海浪动画页（海浪规格保护） |
| 全屏留言 `/ledger/messages` | 键盘弹出时输入框必须贴底：`h-dvh` 三段式框架；**顶栏外观与 `InnerPage` 一致**，返回同样走 `useGoBack` |
| 导入完成页（拍照识别后） | 流程终点，只给"返回明细 / 再识别一批"两个明确出口，没有返回键（有测试约束） |
| 登录 / 注册 / 恢复 | `AuthLayout` 独立版式（排版规范 §8.8） |

### 16.2 内容积木（`components/ui/List.tsx`、`components/ui/RecordList.tsx`）

**由内容的职责决定用哪一个，而不是由"页面上都是卡片"决定：**

| 内容是什么 | 用什么 | 视觉语义 |
|---|---|---|
| 去往下一页的入口 | `ListRow`（`to`） | 整行可点，行尾统一的 `›` 图标（`ChevronIcon direction="right"`） |
| 设置项 | `ListRow` 的 `value` / `trailing` | 名称在左、**当前值在右**、行尾是 `›` 或开关 |
| 就地执行的操作 | `ListRow tone="action"` | 名称用 `brand-dark`、**没有 `›`**——箭头只属于"去往某处" |
| 不可逆操作 | `ListRow tone="danger"` | 名称用 `danger` |
| 只读资料 | `FactRow`（放在 `ListGroup as="dl"` 里） | 标签左、值右，**没有箭头、没有按下态**；解释写在这一项下面（`hint`） |
| 一组同类条目 | `ListGroup` | 手机 / 平板保留外框与贯通分隔线，组名与行内文字左对齐（`px-5`）；电脑端按下述轻分区规则。组名采用现有 14px/500 深色，文字角色见文字语义规范 §13.8 |
| 按时间排列的记录 | `RecordList` / `RecordGroup` / `RecordRow` | **不加外框**，条间是左右缩进到内容边的细线；主行单行省略、时间右对齐；分组标题吸顶在导航条下沿 |
| 以阅读为主的说明 | `ProseSection` | 小标题 + 正文，**不装进卡片**，靠留白分节 |
| 页面内的反馈 | `InlineMessage` | 默认最多两行，可「展开全文」、可关闭；全文始终在 DOM 里 |
| 摘要对象（例如选中的账号） | 按内容选择卡片或直接排版 | 卡片只留给"一个完整的对象"，不再用来给每段文字加框；软件更新首页按所有者后续决定使用无背景外框的固定高度预览 |

**电脑端轻分区（所有者 2026-11-01 批准）：**

- 普通设置、资料和对象列表去掉重复的白底圆角外框；用组标题、留白和必要的细分隔线建立层级。设置主内容靠近分类导航，最大宽度 1120px；内容容器足够宽时用左组名 / 右内容，空间不足时标题回到上方，依据容器宽度而非整个窗口。
- 账本列表在空间足够时对齐名称、编号、类型、成员数与管理入口；窄时仍用名称 + 说明。动作名称可以展示在行尾，仍由原行链接 / 按钮负责点击和禁用，不嵌套第二个按钮。只读资料值靠近标签排列；成员姓名与角色对齐。
- 控件、说明靠近对应设置，重复检测的简单规则可两列排列，带说明和复杂控件占整行；窄容器回到单列。鼠标操作行最小 44px，独立小操作最小 32px；粗指针时交互目标至少 44px。字号不因信息密度降低。
- 独立任务（改密码、恢复码、邀请码等）、主题预览、Dashboard / 分析卡片和浮层保留边界。独立设置表单最大宽度 680px，避免控件横跨整页。普通列表悬停区域使用已有 4px 小圆角；表单、任务卡片仍使用各自既有圆角 token。
- 实现通过 `ListGroup` / `ListRow` / `SettingsToggle` 与 `lv-settings-*` 语义类统一覆盖，样式限定在 `.lv-desktop` 内；不全局覆盖 `rounded-card`。手机 / 平板外壳沿用原布局，权限表达式和操作确认不变。

### 16.3 记录的排版（编辑记录、更新公告、导入批次）

- **一条 = 一句主行 + 若干补充行**。主行单行，超出省略号；补充行（"备注：A → B"）也各占一行。
  **所以长备注不会让一条记录变成三行、把下一条推下去**——同一种记录高度一致。
- **完整内容的去处是点开**：编辑记录点开即账目详情；公告点开即全文；桌面端悬停看 `title`。
- **层级**：内容（主行，ink）> 操作人（主行开头，500）> 时间（右对齐，12px muted，等宽数字）> 编号（可复制的小胶囊）。
- **预览文字最多两行**（`line-clamp-2`），长短不同的预览不会让列表忽高忽低。
- **服务器的句子不改写**：编辑记录只把句首的操作人、动词与句中的编号分开排版；句子形状不符合预期时原样显示。

### 16.4 说明文字放在哪里

| 说明的对象 | 位置 |
|---|---|
| 整组列表的规则（"归档后不再出现在记账选项中……"） | 该组下方的脚注（`ListGroup footer` 或列表后一行 `text-helper-relaxed`） |
| 某一项的作用（"用户名：登录时使用"） | 这一项下面（`FactRow hint` / `ListRow detail`） |
| 一个按钮的后果（"导出的文件会带一个编号"） | 按钮下方 |
| 步骤的前提规则（账本导入的来源限制） | 步骤的操作下方，**不压在操作上面** |
| 页面在讲哪一本账 / 哪个版本 | 副标题 |

**同一句话不出现两次**：七个开关各带同一句说明 → 合成开关下方的一句；单笔粘贴识别不再在卡片里重复已在输入框中的原文。

### 16.5 按钮的层级

| 场景 | 变体 |
|---|---|
| 页面的主操作 | `primary` |
| 次要操作 | `secondary` |
| **次要的破坏性操作**（"标记为无效"、"删除全部已下载数据"、"清除本应用的全部本地数据"） | **`danger-quiet`**：红字 + 细红边，无红色填充。红色填充只留给"这一页的主操作本身就是删除"的情形 |
| 两个并列的流程出口（导入完成页） | 同一行左右并排，主操作在右 |

### 16.6 本节不改变的东西

- §15 的所有数值与圆角等级；字号 token；颜色 token（S16-0 的主题化建议不在本轮）。
- 一级页面、海浪、明细页动态头部、分析页图表、底部导航。
- 任何权限判断（"是否显示/可点"）——只改了它们外面的版式，条件表达式原样保留。

### 16.7 应用控件与系统界面的边界

所有者 2026-11-01 确认：应用内可控制的 UI 尽量采用站内组件，统一视觉与交互。普通选择、排序、筛选、展开入口和日期选择不直接展示浏览器默认菜单或装饰；沿用既有主题色、字号、圆角与焦点样式。触屏和键鼠的容器可以不同，选项含义与当前状态保持一致。

- 系统文件选择器、相机 / 麦克风授权、输入法、软键盘、系统分享和下载等必要能力保留；不为了外观仿制安全提示或系统权限流程。
- 输入与按钮继续采用语义化 HTML，保留标签、键盘输入、读屏、焦点返回、禁用状态；不以普通 `div` 代替原生交互语义。
- 优先复用既有弹层与底部面板。桌面排序在入口旁展开；手机与平板按所在工作区使用底部 / 居中面板。筛选条件分组展示，容量输入就近标注单位，应用后显示条件摘要，并提供清除操作。
- 新增或修改控件时按此规则实施；现有页面逐项迁移并做操作验证，不使用全局 CSS 强行遮盖所有原生控件。本轮落地范围为明细排序及附件 / 空间筛选，未将其他页面记为已完成迁移。

## 17. S19 常用布局组合（Layout Patterns）

本节是推荐组合，不是强制页面模板。沿用 §15–§16 的尺寸、组件与 Tailwind 间距 scale，**不增加全局 spacing token 或新布局框架**。组件与材质的 API 见 [S19 设计系统](S19-材质组件与动效设计系统.md)。

入口：[Gallery · 布局模式](http://localhost:5173/component-gallery.html#layouts)。五组示例位于 `apps/web/src/s19/component-gallery/LayoutExamples.tsx`，只调用正式共享组件和 Grid/Flex 工具类；Gallery 的完整代码从该文件提取，参数受同一份类型检查。复制到 `src/pages/` 后可按业务取用，不需要引入实验模块。普通内页的实际返回与折叠标题继续由 `InnerPage` 管理，示例里的按钮不会操作历史。

### 17.1 共同基线

| 项目 | 使用现有规则 |
|---|---|
| 页面水平留白 | 普通内页由 InnerPage 的 `px-6` 提供（24px）；示例组合只加一层 px-6，放进 InnerPage 时去掉这一层，避免双重留白 |
| 内容宽度 | 手机沿用 `frameWidthClass` 的 `max-w-md`（现有 Tailwind 默认 28rem）；宽工作区使用 reading/content/full。桌面设置与独立任务仍按 §16.2，不以 Gallery 宽度覆盖工作区 |
| 紧密关联 / 区块内部 / 字段卡片 / 分组 | `gap-2`（8）、`gap-3`（12）、`gap-4`（16）、`gap-6`（24）；标题与上下文 `mt-1`；不按风格另设间距 |
| 标题与说明 | 页面标题 text-page-title；组名/卡片标题 text-card-title；上下文 text-body-relaxed；字段说明 text-helper-relaxed。说明紧贴解释对象，不重复堆在顶部 |
| 多按钮 | 次要左、主要右；`grid grid-cols-2 gap-3 items-stretch`，或工具 `flex flex-wrap items-center gap-2`。长操作名允许换行；不压小字号、点击区或强制 nowrap |
| 长文字与窄屏 | 可收缩项 `min-w-0`，正文 `break-words`；摘要可 truncate，但必须有完整内容去处。完整标题自然换行，导航栏缩略标题由 PageNavBar 截断。右上优先一个更多入口，避免塞多个长文本按钮 |

### 17.2 五类模式

| 模式 | 推荐结构与适用范围 | 避免 |
|---|---|---|
| 页面头部 | 普通二三级页用 InnerPage(title/subtitle/actions)。PageNavBar 提供 48px 导航行、44px 返回目标与顶部安全区；大标题在正文中。Gallery HeaderPattern 显示相同组件的两种标题状态 | 再手写返回逻辑；在单行里同时塞完整长标题、返回和长动作组 |
| 工具栏与筛选 | 图标/FilterChip 放可换行工具行；SegmentedControl 可单占下一行。组件内部点击目标保持，行间 gap-3 | 缩小图标点击区；每个业务页复制一份分段指示器；覆盖分析工具栏或明细搜索 |
| 卡片列表与分组 | 完整对象用 Card；整块点击用 ActionCard；同类条目用 ListGroup/ListRow；普通说明用 ProseSection。卡片 gap-4、组间 gap-6，组本身不再加 p-6 | 卡片套卡片来包每一段文字；ActionCard 内嵌按钮；给 ListGroup 再加一层 px-5 |
| 表单编辑 | 字段组 gap-4、说明/错误随 TextField；末尾主次操作 gap-3。简单表单可直接组合，不必整页再包 Card。使用原生 form/onSubmit，取消 type=button | 为排版改金额/权限/提交逻辑；输入低于 16px；按每次输入或挂载自动报错 |
| 底部固定操作 | 有限高度的 flex 列：头部 shrink-0 → 内容 min-h-0 flex-1 overflow-y-auto → 操作区 shrink-0。操作区固定在框架底部且参与占位，最后一项可完整滚动到其上方 | 无预留空间直接 fixed bottom-0；估算按钮高度写死 padding；让内容和操作区各自再套满屏滚动 |

### 17.3 底栏、安全区与键盘

- 固定在视觉底部不等于必须使用 CSS fixed。推荐同级占位模式，操作区高度随按钮换行自然增长；共享 Button 决定材质，外层只负责布局。真实全屏框架用 h-dvh，内嵌示例的 h-96 仅是展示窗口高度。
- 底部操作区使用 `pb-[calc(1rem+env(safe-area-inset-bottom,0px))]`，顶部按既有 PageNavBar 或框架单次加入 safe-area-inset-top。安全区由最靠近视口的容器负责，不在外框、操作栏和按钮上重复累计。
- 示例独立入口 `?layout=bottom` 使用既有 `useKeyboardInset` 对 visualViewport 进行避让；参照对象是固定高度外框，内边距变化不会改变外框底边。输入仍交给原生浏览器滚动和键盘，不锁 focus、不改变输入字号。缺少 visualViewport 时沿用原 hook 的 0 降级；缩放与清理规则不另写一套。
- Gallery 内嵌框不启用键盘偏移：框架处于页面下方不能被误判为键盘遮挡。键盘验收请打开“满屏底部操作区示例”，只在该独立文档内运行；不修改业务路由。
- 已有 sticky/fixed 操作栏若经过业务验收，保持原实现和真实留位逻辑。TabPage 的底栏、加号与分析抽屉有自己的额外避让量，不套用这里的普通表单规则。
- 极窄或短视口下让内容区滚动，底部按钮保持可见；宽屏演示仍限制手机阅读列。正式 Pad/桌面按原工作区宽度与样式处理，不能直接拿手机示例当桌面布局。

### 17.4 状态与稳定性

加载、错误、空状态使用同一内容区域，不每次替换整个页面容器或更换 key。短反馈可用 `min-h-24` 预留槽；加载到长列表后内容自然增长，不为保持假高度截断内容。错误提示靠近字段，允许合理增加一行；禁止额外入场位移导致抖动。完成提示复用 StatusMessage 的显式 completion，重复渲染不重播。需要重试时在当前结果区组合 Button，不重建导航头部。

### 17.5 不标准化的特殊布局与 Coverage 交接

明细收缩/搜索、账本空间四层海浪、分析工作台与卡片抽屉、手动记账金额键盘/保存条、底部 Tab 与加号菜单、登录/注册 AuthLayout、全屏留言、导入完成流程、桌面多工作区，均保留原骨架、交互与动画。使用本节组合不构成改动这些页面的授权。

Coverage 在普通业务页先选现有 InnerPage/TabPage 与内容积木，再从 Gallery 取对应组合，删除示例外层重复的 px-6，替换示例数据/回调并保留业务权限条件。只有多个真实页面出现同一缺口且简单组合难以表达时，才请求补共享布局能力。本轮没有新增通用布局 React 抽象；完成后不继续主动扩展设计系统。


## 18. 原始目标与已完成的布局成果

原始目标是让同一职责的布局稳定、对齐清楚，同时保留真正需要的几何和容器层级；不是把所有间距、圆角和嵌套数量都改成相同值。

| 时间 / 成果 | 决定与理由 |
|---|---|
| 2026-10-14 圆角与间距收口 | 底部贴边面板与普通卡片拥有独立圆角职责，避免“调面板就连带改卡片”；只为职责建立语义，不按数值相近合并。原实施只改必要位置，未进行无差别全站替换。 |
| 不新增全局 spacing Token 的决定 | 当时实际构建验证 `--spacing-*` 会影响 Tailwind 间距体系；已存在的页面共享组件与控件自身间距更适合承担职责。故否决另建全局 spacing scale，并非忘记实施原提案。 |
| 2026-10-23 页面骨架与内容积木 | S16-A 形成 `InnerPage`、列表/记录/说明/按钮层级，统一普通二三级页并保留海浪、明细、全屏留言等特殊骨架。 |
| S19 常用布局组合 | 在已有积木上建立五类布局示例、安全区与键盘处理、状态和 Coverage 交接；成果是可复用组合，不是另一套与业务争夺职责的 React 布局框架。 |

详细测量、候选方案与失败原因保留在历史原文，正文中的 §15–§17 直接给出有效规则。历史视口的通过结果不能替代新改动的实际验证。
