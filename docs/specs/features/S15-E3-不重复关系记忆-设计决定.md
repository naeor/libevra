## 0. 一句话与范围

用户明确确认「A 与 B 不是同一笔」之后，把这一对**按规范化后的交易 ID 对**记在账本里；
后续重复提示可以按这一对抑制，用户也可以在账本设置里**查看与撤销**。
关系是**账本级共享状态、服务器权威**；个人检测偏好仍然只存 `localStorage`。

**本轮做**：关系表 + migration、创建/查询/撤销 API、关键字段变化的失效规则、
账本设置里的管理区、拍照记账的显式确认入口、E2 适配层的抑制挂点、测试与文档。

**本轮不做**：E4 各新增入口的提醒、E5 全账本主动审查、离线写队列、关系冲突解决、
自动删除/合并、任何生产迁移或部署。

## 1. 数据模型

### 1.1 表 `transaction_not_duplicate_relations`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `uuid` PK | |
| `book_id` | `uuid` NOT NULL | **冗余但必要**：所有查询先按账本收窄，也是"绝不跨账本"的硬保证 |
| `transaction_a_id` | `uuid` NOT NULL | 字典序**较小**的一方 |
| `transaction_b_id` | `uuid` NOT NULL | 字典序**较大**的一方 |
| `relationship` | `varchar(24)` | 首版只有 `not_duplicate`；`CHECK` 限定取值 |
| `decision_source` | `varchar(24)` | `manual` / `review_group` / `import_review` |
| `decided_by` | `uuid` NULL | 确认人；**刻意不加 `users` 外键**（账号注销后这条判断仍要可解释） |
| `decided_by_name` | `varchar(64)` NULL | 确认时的昵称快照（同 `TransactionEvent.actorName`） |
| `decided_at` | `timestamptz` | 确认时间；重激活时会被这次确认覆盖 |
| `basis` | `jsonb` | 判定当时两笔交易关键字段的**值快照**（见 §1.2） |
| `revoked_at` | `timestamptz` NULL | 软撤销；非空 = 不再抑制 |
| `revoked_by` / `revoked_by_name` | `uuid` / `varchar(64)` | 撤销人与其昵称快照 |
| `revocation_reason` | `varchar(48)` | `user_revoked` / `key_fields_changed` / `basis_stale` / `book_cleanup` |
| `created_at` / `updated_at` | `timestamptz` | |

### 1.2 `basis` 的形状

```json
{
  "version": 1,
  "capturedAt": "2026-10-21T03:00:00.000Z",
  "a": {
    "transactionId": "…", "seq": 12, "version": 1,
    "amountCents": "1234", "currency": "CNY", "kind": "expense",
    "occurredAt": "2026-10-21T02:03:00.000Z",
    "occurredLocalDate": "2026-10-21", "occurredTz": "Asia/Shanghai",
    "categoryId": "…", "paymentMethodId": "…"
  },
  "b": { "…": "同上" }
}
```

- **金额是字符串**：JSON 与 `BigInt` 之间不经 `Number`，避免精度问题。
- **`version` 只作说明**：不因"后来被编辑过"就失效（E1 §6.4 明确不建议用版本号一刀切）。
- **分类/支付方式只留快照**：它们不参与失效判断（按 E2 规则不是必要条件）。
- `basis` 读不出来（损坏/未来格式）→ **按失效处理**：宁可多问一次，也不让一条无法核对的旧判断永久压住新的疑似重复。

### 1.3 规范化、唯一约束与索引

- 写入前断言 `transaction_a_id < transaction_b_id`（字符串字典序；UUID 规范小写形式与
  PostgreSQL 的 `uuid` 比较结果一致）。数据库再加 `CHECK (a < b)` 兜底。
- **唯一**：`UNIQUE (book_id, transaction_a_id, transaction_b_id)` —— 配合规范化，等价于"无序唯一"，
  同一对 `(A,B)` / `(B,A)` 只能落一行。
- 索引：
  - `(book_id, transaction_a_id)`、`(book_id, transaction_b_id)`：双向查"这一对是否已经判过"；
  - `(book_id, revoked_at)`：列"当前生效的关系"；
  - `(book_id, decided_at)`：管理页按确认时间倒序分页。
- `CHECK relationship IN ('not_duplicate')`：首版只有一种关系，新增取值必须先改约束，避免静默写入。

### 1.4 外键选择（E1 §6.3 两方案，本轮选方案 A）

| 方案 | 内容 | 取舍 |
|---|---|---|
| **A（本轮采用）** | `book_id → books.id ON DELETE CASCADE`；交易侧**不加外键** | 账本永久清理时关系随账本消失、不留孤儿；交易行真正消失时仍保留"曾经确认过"的事实；读取端容忍对端缺失 |
| B | 完全不加外键 | 与 `LedgerImport*` 一致，但账本删除后要另写清理任务 |

关键事实：**软删除不触发任何级联**（只写 `deleted_at`），所以"删掉一笔被记录为不重复的交易"
不会让关系行消失——这正是需要的（恢复后关系仍然有效）。**交易侧不加外键**还有一个直接好处：
关系表不会和 `transactions` 的清理路径互相阻塞；读取端把缺失的一侧返回 `null`，
管理页显示"交易已不存在"。

### 1.5 为什么不用标签系统

标签是分类学（一个标签挂任意多笔，语义是"同类"），而不重复关系是**具体两笔之间**的判断，
且**不具备传递性**：A–B 与 B–C 不能推出 A–C。用标签表达会让人以为可以批量套用（规划 §5.3）。

## 2. API

所有路由挂在 `/api/v1/books/:bookId/not-duplicate-relations`。
**账本在路径里，权限在请求头里**：与 `PATCH /books/:bookId` 相同，路径账本必须与
`x-libellum-book` 一致，否则 `400 book_mismatch`、什么都不做。

### 2.1 `GET`（读权限，viewer 可用）

| 参数 | 说明 |
|---|---|
| `includeRevoked` | `true`/`1` 时连已撤销一起返回；默认只返回**当前生效**的关系 |
| `transactionId` | 只返回"和这一笔有关"的对（E4/E5 的查询形状） |
| `limit` / `cursor` | 默认 20、上限 100；游标按 `(decided_at, id)` 倒序 |

返回每条关系：规范化 id 对、确认人/时间/来源、撤销人/时间/原因、`stale`/`staleFields`、
`effective`，以及**两侧交易摘要**（seq/日期/金额/方向/币种/分类/支付方式名/是否已删除；
交易被永久清理时为 `null`）。

**默认列表的"生效"定义**：未撤销、快照未过期（`basis` 与当前值一致）、两侧交易都还在。
软删除的交易仍算"在"——关系保留，只是它不再被用来比较（候选只对 live 交易生效）。

### 2.2 `POST`（写权限）

请求体二选一或并用：

```json
{ "pairs": [{ "transactionIdA": "…", "transactionIdB": "…" }] }
{ "transactionIds": ["A", "B", "C"], "decisionSource": "review_group" }
```

- `pairs`：逐对确认；
- `transactionIds`：用户明确把一组标为"都不是同一笔"时，服务端展开 **C(n,2)** 个显式对
  （A、B、C → A–B、A–C、B–C）。**这不是传递性推导**：每一对都来自用户点名的那一组；
  A–B、B–C 永远不会自动推出 A–C。
- 校验：两笔都在同一账本（`transaction_not_in_book` 403）、不能是同一笔（`same_transaction` 400）、
  逐对规范化、请求内去重、单请求上限 200 对（组上限 20 笔）。
- 幂等：
  - 已生效且快照仍一致 → 原样返回（200，`unchanged`）；
  - 已撤销 → **原地重激活**（200，`reactivated`），不插新行；
  - 不存在 → 新建（201，`created`）；
  - 同一请求重放不会写第二行（唯一约束）。
- `basis` 由服务端从交易当前值生成；**客户端不能提供/覆盖 basis**。
- **导入锁**：锁生效时返回 `409 book_locked`（可读中文说明）；数据库触发器是第二层兜底。

### 2.3 `DELETE /:relationId`（写权限）

软撤销：置 `revoked_at/revoked_by/revoked_by_name`、`revocation_reason = user_revoked`，**行保留**。
撤销后该对重新进入候选。重复撤销幂等（200，`unchanged: 1`，不改时间）。
找不到或跨账本 → `404 not_duplicate_relation_missing`。

### 2.4 留给 E4/E5 的接口

- `GET ?transactionId=` 已经支持"新增交易前问：这笔和我确认过不重复的哪些记录有关"。
- 尚未实现、也不在本轮授权内：`POST .../filter`（批量问"这些对里哪些已确认"）。
  若 E4/E5 需要，建议在现有 GET 上加 `transactionIds[]` 批量参数，而不是新建一套形状。

## 3. 失效规则（核心）

### 3.1 关键字段变化 → 失效

**金额 `amountCents`、币种 `currency`、方向 `kind`、时间 `occurredAt`** 任一变化
→ 关系失效，该对重新进入候选。

- **写入时确定性撤销**：`PATCH /transactions/:id` 在**同一 DB 事务**内比较 before/after，
  有变化就 `UPDATE … SET revoked_at …` 涉及该交易的全部生效关系（`revocation_reason = key_fields_changed`，
  `revoked_by` 记为执行编辑的人，便于回答"为什么失效"）。
  **不改这个路由的响应/权限/版本语义**：编辑照旧成功；撤销与编辑同事务，失败一起回滚。
- **读取时兜底**：`GET` 拿 `basis` 与当前值比较，发现 stale 就**不视为生效**（`stale: true`、
  `staleFields`），覆盖导入、清理、历史数据等绕过 PATCH 的写入。**读取只判定、不写库**——
  GET 仍是只读操作；真正持久化的失效发生在下一次 PATCH 或显式撤销。
- 时间按**真实时刻**比较（`Date.parse`），同一时刻的不同写法（`+08:00` vs `Z`）不算变化。
- 币种比较前 `trim().toUpperCase()`；金额按字符串比较。

### 3.2 非关键字段变化 → 不失效

分类、支付方式、标签、商户、备注变化**不失效**。理由：按 E2 统一规则，这些字段不是
"疑似重复"的必要条件；若因它们失效，用户体验会退化成"我确认过，怎么又问一遍"（E1 §6.4）。

### 3.3 软删除 / 恢复 / 永久清理

| 事件 | 关系 | 说明 |
|---|---|---|
| 软删除一笔 | **保留、仍生效** | 删除不改变"这两笔不是同一笔钱"的判断；候选只比较 live 交易，所以它自然不再参与比较 |
| 恢复 | **保留、继续生效** | 恢复同一行、同一 id；`base` 快照未变即继续抑制 |
| 交易被永久清理 | 关系行保留，对端摘要 `null`、`effective = false` | 读取端容忍缺失；不再抑制 |
| 账本永久清理（purge） | 随 `book_id` 外键 **Cascade 删除** | 不留孤儿行 |

### 3.4 交易身份字段

`sourceRef` / `sourceNamespace` / `seq` **不可编辑**（没有请求 schema 暴露它们），
因此不存在"身份字段被改"的失效路径；`seq` 只作为展示与日志线索写入 `basis`。

### 3.5 导入锁

关系写入与交易写入一样受 `ledger_write_locks` 保护。本轮**新增**一个只针对本表的触发器
（复用既有 `trg_guard_book_id()`，不修改任何既有触发器）：

- 应用层先查锁 → `409 book_locked`，带具体说明；
- 数据库触发器兜底 → 既有全局错误处理翻译成同一个可读错误。

## 4. 权限矩阵

| 动作 | viewer | editor | 已离开账本 | 归档/删除中账本 | 导入锁生效 |
|---|---|---|---|---|---|
| 查看列表 | ✅ | ✅ | ❌ 403 | ❌ 403/410 | ✅（只读不受锁影响） |
| 创建关系 | ❌ 403 `book_read_only` | ✅ | ❌ | ❌ | ❌ 409 `book_locked` |
| 撤销关系 | ❌ 403 | ✅ | ❌ | ❌ | ❌ 409 |

- 权限**只复用** `access.ts` 的既有包装器（`requireBookRead` / `requireBookForWrite`），
  **没有新增或修改任何权限判断**；`book_members` 仍是唯一来源。
- 关系是账本级共享状态：所有当前成员可见；`decided_by` 记录"谁说的"；
  成员离开账本后关系保留（仍对留下的成员生效）。
- viewer 的撤销按钮在界面上禁用并写明原因；即使绕过界面，服务器也会拒绝。

## 5. 离线与同步

**关系是服务器权威，首版不进入离线写队列。**

- 离线时：创建/撤销**禁用**并给出说明（"离线时不能修改「不重复」判断…联网后可撤销"）；
  已加载的关系仍可查看（React Query 缓存），联网后重新取。
- 不引入"关系冲突解决"：两台设备对同一对给出相反判断的情况，本轮没有自动合并语义；
  服务器按到达顺序记录，最后一次写入生效（与幂等重放一致）。
- **关系判定不替代幂等**：即使两笔被判为不重复，重复提交仍由 `idempotencyKey` / 唯一约束保护；
  关系也不参与离线队列的投递与冲突记录。
- 个人检测偏好（开关、窗口、分类/支付方式匹配）**继续只存 `localStorage`**，与账本级关系分开存储；
  换设备/清缓存会回到默认偏好，但**不会丢失**账本级关系。

## 6. UI 接入

### 6.1 管理 / 撤销入口（已接入）

**账本设置 → 数据管理 → 已忽略的重复交易**（`BookSettingsPage` 内嵌
`NotDuplicateRelationsSection`，不新增路由）：

- 显示两笔交易的编号/日期/金额/方向/分类、确认人/时间/来源；
- 「生效中 / 含已撤销」筛选；空态区分两种视图；
- 撤销按钮；viewer 只读、离线禁用、撤销中禁用；
- 已撤销行显示撤销人与时间；失效行显示"判定依据已变化（金额、时间）…重新参与提示"；
- 交易已永久清理时显示"交易已不存在"。

### 6.2 确认入口（已接入一处）

**拍照记账（`/scan`）的重复对话框**新增独立选项「确认不是同一笔」：

- 只有点击这个选项才记录关系；**「仍然保存」故意不记录任何关系**——
  保留两笔相似账目是合法操作，不能翻译成"用户说这不是同一笔"。
- 用户确认后，先写账目，再用**新账的最终 id** 与对话框中列出的每一笔配对提交；
  只配对新账与旧记录，不把旧记录彼此配对。
- 关系提交失败**不回滚账目**，也不静默：完成页显示"账目已保存，但「不是同一笔」没有记住：…"。

### 6.3 E2 适配层过滤（挂点已接入，生产调用暂为空集合）

- `apps/web/src/lib/ocr/duplicates.ts`：`OcrDuplicateOptions.suppressedPairKeys`；
- `apps/web/src/lib/ledgerImport/duplicates.ts`：`detectDuplicateGroups(..., suppressedPairKeys)`；
- 两者都按 `notDuplicatePairKey` **精确跳过那一对**，不推导传递关系，不改 E2 核心规则与用户设置语义。

**为什么生产路径暂时传空集合**：当前产品里唯一"同一账本内两笔已存在交易"的对照场景还没有
（单笔拍照的新交易在确认时还不存在；账本导入是跨账本；OCR 批次候选项在导入前不是正式交易）。
这两个挂点是为 **E4（新增后再问）/E5（全账本审查）** 准备的唯一抑制点，
届时由调用方传入服务器返回的生效关系。本轮用固定样本测试证明抑制机制本身正确。

### 6.4 未接入、留给 E4/E5

- 手动记账 / 语音记账的提醒；OCR 批量导入的逐组表态；
- 全账本主动审查页面与"已忽略"次级区域（E5 可直接复用本组件）；
- 新增交易前的"这笔和已确认不重复的记录有关吗"查询（接口形状已预留）。

## 7. 迁移与回滚

### 7.1 迁移内容

文件名：`prisma/migrations/20261021031459_s15e3_not_duplicate_relations/migration.sql`

1. `CREATE TABLE transaction_not_duplicate_relations`（§1.1 全部字段）；
2. `UNIQUE (book_id, transaction_a_id, transaction_b_id)`；
3. 四个索引：`(book_id, transaction_a_id)`、`(book_id, transaction_b_id)`、
   `(book_id, revoked_at)`、`(book_id, decided_at)`；
4. `CHECK (transaction_a_id < transaction_b_id)`、`CHECK (relationship IN ('not_duplicate'))`；
5. `FOREIGN KEY (book_id) REFERENCES books(id) ON DELETE CASCADE`；
6. `DROP/CREATE TRIGGER trg_guard_transaction_not_duplicate_relations`（复用 `trg_guard_book_id()`）；
7. 文末注释形式的 `DOWN` 语句。

### 7.2 本机执行情况（只有开发/测试库）

| 环境 | 情况 |
|---|---|
| 开发库 `ledger_dev`（`DATABASE_URL`） | 已应用（52 个 migration，`migrate status` up to date） |
| 测试库 `ledger_test`（`TEST_DATABASE_URL`） | 已应用（`prisma migrate deploy`，测试前校对 up to date） |
| 生产库 | **未连接、未迁移、未写入** |

⚠️ 应用前发现**开发库既有漂移**：`books_disposed_at_idx` 存在于迁移历史与测试库，但开发库缺失。
按规矩**没有 `migrate reset`**；用迁移历史里的 `CREATE INDEX IF NOT EXISTS` 把开发库补齐（不改任何数据），
再用 `migrate deploy` 应用本迁移。这是**开发库**的修复，与生产无关。

### 7.3 回滚方案

**应用回滚**：关系表是**纯新增**，旧代码不认识它也能照常运行（交易、导入、离线、权限均不受影响）；
回退到 E3 之前的 commit 即可，数据库不需要回滚。

**数据库回滚（forward-only 项目不自动执行）**：

```sql
DROP TRIGGER IF EXISTS "trg_guard_transaction_not_duplicate_relations"
  ON "transaction_not_duplicate_relations";
DROP TABLE IF EXISTS "transaction_not_duplicate_relations";
```

或从备份恢复。**生产执行前必须先备份**（`./backup.sh`），并按发布流程单独批准；
本轮**没有**执行任何生产迁移。

## 9. E4 / E5 边界与待决

1. **E4**：新增交易（手动/语音/OCR 批量/CSV）在写入前或写入后询问"是否与已确认不重复的记录有关"。
   接口用本轮的 `GET ?transactionId=`；抑制用适配层的 `suppressedPairKeys`。
   **本轮没有**接入任何新增入口的提醒。
2. **E5**：全账本主动审查页面、候选检索、进度与取消；"已忽略关系管理"可以直接复用
   `NotDuplicateRelationsSection`（规划 §7.5 允许放在审查页面的次级区域）。
3. **待所有者决定**：
   - 是否需要在 E4 里把"同一对再次确认"的撤销历史保留下来（当前每对只有一行，
     重激活会覆盖上一次的 `decided_at/decided_by`；要完整历史需另加审计表）；
   - 关系数量上限/清理策略（C(n,2) 在 20 笔以内可控，超大组是否需要拆分确认）；
   - 是否允许 `decision_source` 增加新取值（需要同时改数据库 CHECK）；
   - 生产迁移的时间点与备份演练（需再次批准）。
