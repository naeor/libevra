## 0. 旧草案必须改掉的内容

| 旧草案 | 2026-10-19 的新决定 | 影响 |
|---|---|---|
| 只做"游客账本 → 正式账号" | 扩大为**账本导入**：来源可以是本机游客账本，也可以是同一账号下另一本单人正式账本 | 来源模型、权限、UI 全部要统一 |
| 目标账本必须是新建或空账本 | **允许导入已有账目的正式账本 A**（只要 A 是本人拥有、无其他协作者的单人账本） | 必须做重复检测与冲突处理 |

| 首版尽量复用现有逐笔接口、不新增服务端接口 | D1 只读预览仍不新增；**D2/D3 需要最小事务型导入接口**，否则无法保证"删除 A + 写入 B"原子性 | 需要新表/新路由/迁移测试 |
| 没有跨来源重复检测 | 新增 60 秒时间窗、跨 A/B 的重复组检测；绝不比较 A-A 或 B-B | 模型与冲突 UI 的核心 |
| 游客必须新注册账号 | 可导入**新注册或已有正式账号** | 入口/登录流程调整 |
| 导入后不能删除来源 | 完成后用户独立选择是否保留来源 B；游客数据永不自动清除 | D5 来源保留/删除 |
| "迁移"名称 | 统一叫**导入**，不区分"导入/合并" | 全部文案 |

## 1. 产品定义与术语

- **A**：目标账本，接收数据。
- **B**：来源账本，提供数据。
- **导入**：把 B 中的内容复制到 A；完成后用户可以选择是否保留 B。
- **两种来源**：
  1. 本机游客账本（只存在于当前浏览器，未经用户确认不上传）；
  2. 同一账号下另一本**本人拥有、没有其他协作者**的正式单人账本。
- 首版不涉及多人账本之间的导入；共享账本不参与（新建的单人账本可以）。
- 目标 A 可以是已有的正式单人账本（即使已有账目），也可以是新建的正式账本。
- 来源 B 与目标 A 必须是不同的账本。

## 2. 不变量（任何实现都不得违反）

1. **目标 A 已有账目的编号不变**；导入的每笔账由 A 的服务器编号机制分配新编号，不复用 B 的旧编号。
2. **失败不丢来源**；导入完成并通过核对前不自动删除 B；游客数据永不自动清除。
3. **不静默覆盖/修改 A 的已有分类、支付方式、标签或账目**。属性冲突必须显式处理。
4. **重复检测只跨来源 B 与目标 A**；A-A、B-B 永远不算本次导入的冲突。
5. **A 原有记录的移除必须由用户逐组选择并最终明确确认**；默认不删。
6. 写入必须可重试且不产生重复记录；服务器成功但客户端丢状态后，恢复能识别已提交结果。
7. 账号/目标权限变化时停止，不向错误账号或错误账本续写。
8. 游客身份 id 不是 userId；游客数据只在用户明确确认后才上传。
9. 不改变 S13-I 的关键事件语义；正式账本删除继续走现有生命周期机制。

## 3. 现状能力审查（代码/数据库事实）

### 3.1 已具备

- `GET /api/v1/books` 返回每本账的 `role / isCreator / memberCount / bookNumber`，可识别"本人拥有且只有一位成员"的单人账本；服务端 `book_members` 仍是权限唯一来源。
- `GET /api/v1/ledger`（可带 `x-libellum-book`）返回目标账本的分类、支付方式、标签和元数据；`GET /api/v1/transactions` 支持逐页读取。
- `POST /api/v1/transactions` 要求客户端提供 `id` 与 `idempotencyKey`；服务器按 `idempotencyKey` 查重、在事务内分配 `seq`，所以"重试不重复 + 新编号"已有基础。
- 交易是软删除（`deletedAt` + `version` + `TransactionEvent`），可用现有 `DELETE /transactions/:id` 撤销；不是物理删除。
- 分类/支付方式/标签有 `(bookId, kind, name)` 或 `(bookId, name)` 唯一约束；同名对象的复用/冲突可以由名称和属性判断。
- 现有 CSV 导入在一个 `prisma.$transaction` 内逐行创建交易、逐笔分配编号、写 `ImportLog`，证明"一次事务写一批记录"在本项目中可行。
- 游客数据在独立 IndexedDB `libellum-guest`，正式账号数据在 `libellum`；S14-C 已验证两者隔离。

### 3.2 缺口（D1 不需解决，D2/D3 必须解决）

1. **没有导入批次/来源映射表**：`sourceRef` 只能在交易行上存一个值且每本账唯一，无法完整回答"这条来源记录被导入到哪本 A 的哪个 UUID、当时做了什么决定"。
2. **没有事务型导入接口**：逐笔 `POST /transactions` + 逐笔 `DELETE /transactions/:id` 不能保证"A 旧记录删除与 B 新记录写入"同时成功或同时回滚；中途失败会产生缺失/重复。
3. **没有导入状态/回执**：浏览器在服务器提交成功后、保存本地状态前崩溃时，无法只靠本地状态判断服务器是否已有这次导入。
4. **没有正式账本来源的一致性快照**：预览/提交期间 B 可能变化；D4 需要服务端在提交时校验来源版本或重新读取。
5. **游客快照需要用户授权的上传通道**：预览可以本地做，但真正提交必须由用户确认后发送；服务端需要校验结构和权限，不能信任客户端映射结果。

**结论**：D1 可以完全只读、无需服务端改动；D2/D3 必须先补最小事务型导入接口，不能为了少改代码而采用两段式逐笔删除/写入。

## 4. 统一导入模型（D1 已实现）

D1 的代码在 `apps/web/src/lib/ledgerImport/`：

- `types.ts`：来源/目标快照、映射计划、冲突、重复组、预览。
- `sources.ts`：读取正式账本（现有 API）与本机游客账本（IndexedDB），只读。
- `mapping.ts`：分类/支付方式/标签映射、同名冲突、唯一新建名称。
- `duplicates.ts`：60 秒窗口 + 跨来源图连通分量。
- `preview.ts`：汇总、警告、日期范围、重复组。
- `LedgerImportPage.tsx`：D1 只读预览页（`/import-ledger?target=<A>`），从账本设置进入。

### 4.1 来源/目标快照

两种来源最终都归一为同一结构（账本识别信息 + 分类 + 支付方式 + 标签 + 可导入交易 + 游客墓碑计数）。正式来源每次预览通过 API 读取；游客来源直接读本机 IndexedDB。

### 4.2 读取权限

D1 只允许用户选择 `/books` 返回的 `isCreator && memberCount === 1` 单人账本；来源与目标不能相同。这只是界面过滤，**服务端权限才是最终边界**，D3 的提交接口会重新校验。

## 5. 分类 / 支付方式 / 标签映射

### 5.1 基本规则

- **逻辑映射先于重复检测**：按 `(kind, 规范化名称)`、支付方式名称、标签名称匹配；不比较两个账本的内部 id。
- 名称规范化：NFKC、去首尾空白、连续空白压缩；保留大小写与中文语义。
- 目标已有且属性兼容 → 复用目标对象。
- 目标不存在 → 在目标新建；分类保留归档状态，标签保留颜色。
- 系统分类按目标账本 `isSystem` 分类匹配（名称不是语义身份）。
- 同名但：
  - 分类归档状态不同；
  - 自定义分类与目标系统分类同名；
  - 支付方式归档状态不同；
  - 标签颜色不同；
  → 产出显式冲突，**不得静默覆盖或丢失属性**。

### 5.2 冲突处理（D3 实现）

每个冲突由用户选择：
1. 复用目标对象（可能丢失来源属性）；
2. 在目标新建一个保留来源属性的对象（同名时用安全后缀生成唯一名称）；
3. 预览中明确说明所选方案的影响。

分类名称长度上限 20；`uniqueName` 生成后缀并在目标已有名称集合内保证唯一。来源新建的对象在真正提交前不写库。

**D1 的状态**：预览展示冲突和暂定方案（暂按"复用目标对象"估算重复项）；没有让用户逐项选择，也没有写库。D3 必须在执行前收集选择并重新计算映射与重复组。

## 6. 重复检测与冲突组

### 6.1 判定条件（全部满足）

1. 一条来自来源 B，一条来自目标 A；
2. 发生时间绝对差 ≤ **60 秒**；
3. 收支类型相同；
4. 金额（minor units）与币种完全一致；
5. 分类相同——比较**映射后的目标分类键**；
6. 标签集合完全相同，顺序无关（比较映射后的目标标签键集合）。

支付方式与备注只展示，不作为必须相同条件。A-A、B-B 永不进入候选。

### 6.2 多候选 → 冲突组

把满足条件的 B-A 边连成图，取**连通分量**作为冲突组。一个组可以是一对一、一对多、多对一、多对多；同一记录只会属于一个组，因此组级决定不会互相矛盾。

D1 的输出：
- `duplicateGroups[]`（来源记录在前、目标记录在后，时间与 id 排序稳定）；
- 每组来源/目标条数；
- 默认待导入数 = 全部来源交易 − 参与重复组的来源交易；
- 未命中重复的来源记录默认进入待导入列表，但不执行。

### 6.3 冲突处理（D3；组只用于检测，不作为批量删除单位）

**组是检测和核对单位，不是删除单位。** 多对多组不得用一个组级选择默认删掉整组 A；用户必须看到具体会移除哪些记录。

建议的决定模型：

- **来源 B**：每条来源记录默认「导入」，用户可逐条改为「跳过」；
- **目标 A**：每条目标记录默认「保留」，只有用户**逐条明确选择**「移除」才会软删除；
- 界面在组内同时展示来源和目标记录；对多条 A 的组，要求逐条勾选确认要移除的 A 记录；
- 一对一冲突可以保留四个快捷意图（只保留 A / 只保留 B / 两笔都保留 / 两笔都不保留）作为预设，
  但预设只勾选对应记录，**最终仍需展示并确认逐条结果**；
- 最终摘要逐条列出目标 A 将被移除的记录（编号/金额/日期/分类），没有明确勾选的 A 绝不删除；
- 组与组之间互不重叠，因此逐条决定的最终结果不会在多个组之间互相矛盾。

D1 只展示候选，不提供选择/写入；重复检测是提醒，不是自动删除依据。

## 7. 目标/来源选择与预览

### 7.1 入口

- D1 从账本设置进入：目标 A 由账本设置页带入地址（`/import-ledger?target=<A>`），页面明确展示目标名称、编号、所属账号。
- 以后可从游客「我的」进入游客导入；未登录时先走现有登录/注册，不新建账号。

### 7.2 预览内容

- 来源/目标名称、编号、所属账号；
- 来源交易数、目标已有数、日期范围；
- 按币种/收支的金额汇总；
- 分类/支付方式/标签的复用/新建/需确认数量；
- 可能重复组数与每组记录细节；
- 将跳过的游客墓碑数量；
- 明确说明：预览不写入；来源 B 不会被自动删除。

### 7.3 目标选择规则

- 允许创建新账本 A（D2 起）或选择已有单人账本 A；
- 不默认选择任何一本现有账本；从设置页带入的目标也必须在页面上清楚显示；
- 目标 A 与来源 B 不能相同；
- 多人账本首版不允许作为 A 或 B。

## 8. 可靠提交（D2/D3 服务端设计）

### 8.1 为什么需要新的最小接口

现有逐笔 API 的原子性单位是单笔。若先删除 A 的旧记录再逐笔写入 B，出现网络中断会得到"A 已删、B 未写"的最坏状态。必须在**一个服务器事务**内完成：
- 新建缺失的分类/支付方式/标签；
- 按用户逐条明确选择的 A 记录软删除并写事件；
- 写入 B 的记录（服务器分配新编号）；
- 写导入批次记录/来源映射；
- 返回可重放的导入回执。

### 8.2 建议的最小服务端改动

新增 `LedgerImport` 与 `LedgerImportItem`（名称可在实施时调整）：

```
LedgerImport
  id uuid PK
  targetBookId uuid
  targetUserId uuid
  sourceKind   varchar(8)   // "guest" | "book"
  sourceBookId uuid?        // 正式来源
  sourceGuestHash varchar(64)? // 游客来源的本地匿名哈希，不是身份凭证
  status       varchar(16)  // running | complete | failed
  sourceFingerprint varchar(64)
  counts       json
  createdAt / completedAt
  @@unique([targetBookId, id]) // 实际使用 importId 客户端生成
```

```
LedgerImportItem
  importId uuid
  sourceKey varchar(80)     // 来源交易/对象稳定键
  sourceTransactionId uuid?
  targetTransactionId uuid?
  removedTargetTransactionId uuid?
  decision varchar(24)      // imported | skipped | kept_target | removed_target | both
  status varchar(16)
  errorCode varchar(64)?
  @@unique([importId, sourceKey])
```

新路由（首版统一为同步单事务，客户端分批只用于传输前的组装，不拆事务）：

```http
POST /api/v1/ledger-imports
{
  "importId": "uuid",
  "targetBookId": "uuid",
  "source": { "kind": "guest", "snapshot": {...} }
             | { "kind": "book", "bookId": "uuid", "expectedFingerprint": "..." },
  "taxonomy": [ { "sourceId": "...", "action": "reuse|create", "targetId": "...", "createName": "..." } ],
  "sourceActions": [ { "sourceTransactionId": "uuid", "action": "import|skip" } ],
  "targetActions": [ { "targetTransactionId": "uuid", "action": "keep|remove" } ],
  "idempotencyKey": "uuid"
}
→ 200 {
  "importId": "...",
  "status": "complete",
  "importedCount": 12,
  "removedTargetCount": 2,
  "skippedCount": 3,
  "countsByCurrency": [...],
  "warnings": [...]
}
```

- 对正式来源，服务器应**自己读取 B**，并校验 B 属于同一用户、无其他成员、B≠A；客户端只提供决定和映射，不提供 B 的任意改写。预览应带回来源指纹/版本；提交时校验 `expectedFingerprint`，来源在预览后发生变化必须返回 `source_changed`，**不写入**，要求重新读取、重新核对和确认，不能静默导入用户没看过的新数据。
- 对游客来源，服务器接收客户端上传的快照，必须严格校验 schema/数量/币种/时间，并重新计算重复组或校验客户端给出的组与摘要；不能把客户端传来的"任意 transaction"直接无校验写入。
- 整个写入在一个 `prisma.$transaction` 中；分类/标签/支付的创建、交易插入（`allocateTransactionSeq`）、明确选择的 A 记录软删除 + 事件、批次记录全部同事务。
- 源记录与目标记录关联写入 `LedgerImportItem`；之后增量导入和结果核对依赖它，而不是目标新 UUID 猜测。
- 重试同一个 `importId`：先查 `LedgerImport` 的回执，已完成直接返回；未完成由服务器状态决定恢复/重试，防止重复插入。
- **500 笔只作为初期限流，不是最终产品永久上限**。最终实现必须支持分批导入与断点恢复（同一 importId、批状态、逐批回执与最终对账），不能因为账本较大就简单拒绝；分批不得改变跨批次冲突检测的一致性。D2/D3 实施时确认批次边界。
- 不修改现有 `book_members` / S13-I 关键事件判断；新路由只调用现有 `requireAuth`/`requireBook` 等 guard。

### 8.3 目标 A 的删除

- 只使用软删除（`deletedAt`、`version+1`、`TransactionEvent`），可被现有恢复路径恢复。
- 删除仅针对用户在组内**逐条明确选择**的 A 记录；组外 A 记录、未勾选的 A 记录都不动。
- 删除与 B 写入在同一事务；任一步失败整体回滚，不能出现"A 已删、B 未写"。
- 结果摘要逐条列出目标 A 被移除的记录，并再次要求明确确认（D3）。
- 被移除的 A 记录应沿用现有账目软删除/恢复机制；恢复入口如何与现有删除机制统一，D3/D5 再定，不在 D1 实现。

## 9. 中断恢复、幂等与并发

### 9.1 客户端日志

D2 起在**游客库**或 IndexedDB 本地日志保存导入任务：`importId`、来源/目标、`targetUserId`、组决定、分类映射、每项状态、服务器回执。正式来源导入也需要本地日志以应对刷新/崩溃。日志不写入正式业务表；D1 不创建日志。

### 9.2 状态机

```
preview → confirmed → submitting → complete
                         ├─ paused（网络/会话/限流）
                         └─ failed（权限/校验/冲突）
```

- 提交前不删除任何 A/B 记录；
- 服务器完成即写回执，客户端刷新后能读取；
- 客户端本地日志丢失也不能导致重复插入：以服务器 `importId`/回执和 `LedgerImportItem` 为准；
- 账号切换：本地日志记录 `targetUserId`，不一致时暂停，要求重新登录目标账号；
- **正式来源在预览后发生变化**：提交携带预览指纹；不一致返回 `source_changed`，不写入，要求重新预览和重新核对，绝不静默导入用户没确认过的新数据；
- 多标签页：`navigator.locks` 锁 `ledger-import:<targetUserId>:<targetBookId>`；日志/服务器状态二次校验；
- 浏览器崩溃/关闭：重新打开导入页时按 `importId` 查询已有导入状态；已提交则显示结果，不重发；
- 对账：按来源交易 id 集合、导入条数、按币种/收支求和核对；未通过不标记完成。

### 9.3 服务器成功、浏览器未保存状态

必须按下面的顺序回答：
1. 客户端发起提交时已持久化 `importId`；
2. 服务器在事务中写业务数据 + `LedgerImport` 回执；
3. 客户端收到响应后保存结果；
4. 若第 3 步失败/崩溃，客户端重开时用 `importId` 查询服务器；找到 `complete` 回执直接展示已导入结果，不重新提交；
5. 服务器没有回执则说明事务没有成功，客户端可安全重试（同 importId）。
这是 D3 的硬性验收条件。

## 10. 来源保留 / 删除与增量导入

### 10.1 游客来源

- 默认保留本机游客账本与身份；
- 导入完成后清理游客数据仍是游客「我的」页的独立操作（现有二次确认）；
- 不自动清除游客身份、本地数据或导入日志。

### 10.2 正式来源 B

- 默认保留 B；
- 用户明确选择"不保留"后，走现有安全的账本删除/归档流程（S13-I 关键事件语义不变）；
- 只有 A 导入完成且对账成功才允许发起删除 B；
- 删除 B 失败不影响已完成的 A 导入：界面明确说"导入已完成，但来源账本未删除"，不伪装成导入失败，不自动回滚；
- B 删除后历史事件/来源映射保留（`LedgerImportItem` 的来源标识不依赖 B 是否还在）。

### 10.3 增量导入

- `LedgerImportItem` 保存 `(sourceKind, sourceBookId/guestId, sourceTransactionId)`；
- 下次导入同一来源时，预览标出**已导入**记录并默认跳过；只导入新出现的来源记录；
- 已导入记录的游客端编辑**不会自动更新** A 中的对应交易（首版明确说明两者不是持续同步）；
- 若来源交易内容变化，按源 ID 判定为已导入并提示"不会更新"，不能静默覆盖；
- 同一来源导入到另一目标 A 是新的导入任务；`importId` 与目标维度隔离，不复用目标 UUID 做来源关联。

## 13D. D5 阶段一实际交付：分批任务与断点恢复（已实现；当轮未发布，后随 `1.14.18` 上线）

**D5 阶段一、二、三、四均已实现；阶段四见 `S14-D5阶段四-可撤销导入与账本锁.md`。**

1. **持久化任务**：新增 `ledger_import_jobs`（无外键，独立回执表）。任务保存完整来源快照、taxonomy、用户逐条决定、计划导入顺序、批次回执、目标基线与预期指纹。
2. **分批执行**：超过 200 笔的导入由服务端后台逐批执行（默认 200，可调）；每批一个独立事务，稳定 `importId`；每批成功后在同一事务更新任务进度、目标指纹和已提交计数。逐批提交**不是**整体单事务原子性，已提交批次不会因后续批次失败而回滚。
3. **短锁**：每批读取/写入前锁成员/邀请/分享表、两本账本行和目标/来源现有交易行；锁只在当前批次事务内持有，不把 D4 的宽锁覆盖整个长任务。正式来源每批重新校验单人/邀请/分享资格与来源指纹。
4. **断点恢复**：服务端启动和定期扫描 `queued/running/finalizing` 任务；页面关闭/刷新不影响；页面通过 `job id` 查询服务端真实已提交进度，不需要保持打开。
5. **删除 A 延后**：所有 B 批次完成后才进入最终阶段；最终事务重新校验目标指纹/数量、逐条 A 身份/version、来源资格，再统一软删除；失败则任务停在 `paused/failed`，已导入批次保留、A 不删除，不能显示整体成功。

## 13E. D5 阶段二实际交付：增量导入（已实现；当轮未发布，后随 `1.14.18` 上线）

**身份与状态**

- 新增 `ledger_import_source_states`（migration `20261019110000_s14d_import_source_states`），唯一键为 `(targetBookId, sourceBookKey, sourceTransactionId)`；
- 目标已有 `sourceRef` 与状态表共同识别来源记录；状态表保存来源内容指纹、决策、目标 id/version，不保存完整游客快照；
- 完成任务的 payload 会清空游客 source 快照（数据最小化）。

**状态与动作**

- 状态：`new / unchanged / modified / target_changed / target_deleted / previously_skipped / previously_skipped_modified / needs_review`；
- 动作：`keep_target / update_target / import / skip`；
- 未变化默认跳过；变化默认保留目标；只有显式 `update_target` 且目标 version 未变化时才更新；目标变化时禁止覆盖；此前跳过/keep-a 不自动改变；keep-both 视为已导入；来源删除不删除目标。

**分批与并发**

- 增量导入统一走服务端任务（即使低于 200 笔）；任务 payload 保存逐条 create/update/skip 操作，skip 也写状态；
- 同一来源/目标已有暂停/运行任务时返回旧任务，不并行新建；
- 目标 `sourceRef` 唯一约束 + version 校验是并发最终防线；
- 暂停后恢复只处理剩余操作，不重复已提交批次。

**验证**

- `ledgerImportIncremental.test.ts` 5 条；
- 真实浏览器：未变化/新增/修改、显式更新目标、来源保留；
- 真实 SIGKILL：已有 400 笔提交后杀 API，重启后完成 3000 笔，重复 sourceRef=0；
- 详见 [`S14-D5阶段二-增量导入`](../../archive/releases/S14-D5阶段二-增量导入.md)。

**来源清理仍不做**：阶段三必须默认保留、独立确认、走 S13 生命周期，不得直接 SQL 删除来源账本。

### 14.1 D4 / D5 产品决定（所有者 2026-10-19 确认）

**D4：正式账本 B → A**

- 正式账本 B 在预览后发生变化时，**拒绝提交并要求重新预览、重新核对**；不静默接受变化。
- 服务端仍需重新校验来源权限/成员、来源指纹、目标权限与目标指纹。
- 可以暂存用户已选草稿，但只有在重新验证来源/目标记录身份、taxonomy 映射关系和重复冲突组完全兼容后才允许恢复这些选择；任何一项不兼容就必须重新选择。
- **D4 实现采用比最小要求更严格的安全边界**：B/A 都必须是当前账号创建的单人账本；有效成员只有本人；不存在待接受邀请或可用分享链接；账本不得归档、弃置或进入永久删除。历史上已退出的成员不算当前成员。
- 草稿恢复按组签名逐组进行：没有变化的组恢复，变化的组清空并高亮；涉及 A 软删除的决定不会套用到其他 A 记录。
- 来源 B 在导入后完整保留；D4 不删除、不清空、不关闭来源 B。

**D5：大账本导入**

- 用户只做**一次最终确认**，之后由服务端后台分批执行；
- 初始可按每批约 **200 笔**设计，但通过测试调整，不把它写成永久上限；
- **完整重复检测必须在全局预览阶段完成**，不能因为分批而漏掉跨批次重复关系；
- 每批需要独立幂等回执与断点续传，界面显示总体进度；**只有整体对账通过才显示导入完成**；
- 涉及 A 删除时，优先研究「完成 B 的全部写入与对账后，再统一软删除 A」；必须评估部分批次成功时的用户可见性、并发修改、最终事务失败与恢复方式；
- 分批机制明确区别于 D2/D3 当前的单事务原子性，**不能宣称整个分批过程具有单事务原子性**；
- 批次未全部完成、或最终 A 删除未完成时，不能显示整体导入成功；
- 本轮 D4 不扩展分批范围。

**发布策略**

- **D2 不单独发布**；
- 完整 D3、D4、D5 完成，并安全整合 S13-I 最终版本、通过完整回归后，才发布 S14。
