# S15-B · OCR 多笔交易与「概览页面」设计方向

> 状态：**正式产品设计方向，未开发**。本文锁定的是产品原则与交互边界，不是实现规格，也不代表 OCR 技术路线、数据库结构或数量阈值已经确定。
> 归属：`开发计划.md`（ROADMAP）v3.4 的 **S15-B**。
> 关联：现有 S5 单笔 OCR、S6 CSV 导入、S14-D 账本导入/任务锁/撤销机制。**不得绕过既有安全机制。**

## 0. 一句话结论

**一张图片不等于一笔交易。** OCR 必须先判断页面类型、再切分交易，最后把结果放进统一的「概览页面」让用户批量核对；用户只重点处理有问题的条目，但最终必须由用户确认后才会写入账本。

## 1. 产品目标

当前 OCR 面向微信/支付宝的单笔交易详情，流程是“一张截图 → 一笔交易 → 核对弹窗”。S15-B 要支持：

- 单笔详情；
- 交易列表/账单概览/银行流水等**一图多笔**；
- 多张图片分别识别，并把所有独立交易合并成一个待核对集合；
- 多张凭证属于同一笔交易时的现有合并逻辑继续保留；
- 跨图片/滚动截图重叠部分的疑似重复提示；
- 不确定时由用户选择处理方式，不擅自认定交易数量。

### 1.1 非目标

- 不承诺“支持所有银行”；
- 不因为 OCR 置信度高就直接入账；
- 不默认把真实截图发到第三方云 OCR/AI；
- 不把用户截图、语音、日志或测试样本提交进仓库；
- 不把 S14 的导入锁、撤销、确认机制替换成 OCR 自己的保存逻辑。

## 2. 输入分类与处理路径

用户上传单张图片时：

| 判断结果 | 处理 |
|---|---|
| 单笔付款/收款/转账详情 | 识别一笔，走已有单笔核对体验 |
| 交易列表/账单概览/银行流水 | 识别多笔，进入批量概览 |
| 无法可靠判断 | 让用户选择“按单笔处理 / 按多笔处理 / 取消”，不擅自决定 |
| 部分截图、金额不完整、日期缺失 | 保留交易草稿并标注待确认项，不编造字段 |

用户上传多张图片时，保留现有两种选择：

1. **多张凭证属于同一笔交易**：按现有规则合并；
2. **多张图片分别识别**：提取各自包含的独立交易；**一张图片仍可以包含多笔**。

示例：

- 一张详情截图 → 一笔；
- 一张微信交易列表截图 → 多笔；
- 三张详情截图 → 三笔；
- 三张交易列表截图 → 合并成统一待核对集合。

跨图片重复出现的交易应被标记为“可能重复”，而不是直接删除或直接合并。

## 3. 「概览页面」正式设计方向

> 这是本轮确定的核心 UI 概念。以后涉及批量账目选择、核对、处理的功能，应优先复用**统一概览页面**的视觉、列表、选择与核对体验；但不同业务动作必须保留各自独立的权限、冲突、撤销与保存逻辑。

### 3.1 定位

**让用户先看到系统准备处理的全部账目，只对有问题的具体账目进行编辑，最后统一确认。**

它不是逐笔编辑表单，也不是要求用户点二十次确认的连续弹窗。

### 3.2 页面结构

页面顶部显示汇总：

- 待处理总数；
- 可直接确认的数量；
- 有疑问的数量；
- 可能重复的数量；
- 当前选中数量。

交易按清晰顺序排列，每笔一个横向独立小卡片/条目。卡片尽可能显示：

- 金额；
- 币种；
- 收入/支出方向；
- 日期及必要时间；
- 商户 / 交易对象 / 交易说明（必须区分来源平台、支付方式、账户与商户，不混为一个字段）；
- 分类；
- 标签；
- 支付方式或来源账户；
- 必要的识别状态、重复提示与异常标识。

没有识别出的字段必须显示“未填写/待确认”，不允许伪造默认值制造“完整”的假象。信息应按主次层级、换行、标签样式呈现，不能为了展示全部字段而让移动端卡片过度拥挤。

### 3.3 交互

- 概览页负责**展示、选择、核对**，不直接编辑字段；
- 点击某笔进入该交易的详细核对/编辑界面；
- 修改金额、日期、币种、分类、标签、支付方式、备注等后返回，概览卡片同步最新结果；
- 用户可以保留或排除某些交易；
- 无问题记录不要求逐笔点击；
- 信息缺失、字段冲突、疑似重复、方向不明确等给出明显提示；
- 用户只重点核对有问题的具体交易；
- 最后提供一次统一确认/批量保存流程。

示例：OCR 提取 20 笔，16 笔完整、4 笔有疑问。系统允许用户直接保留或批量选中 16 笔，只进入 4 笔详细界面核对，而不是打开 20 次弹窗。

**“无疑问”必须经过字段完整性检查和重复检测，不等于“OCR 置信度高”。** 即使系统自动预选某些记录，最终写入也必须由用户执行确认。

### 3.4 与现有流程的关系

- 现有单笔核对体验保留；
- 现有“多张凭证同一笔”合并逻辑保留；
- 概览页只复用视觉组件、交易列表、选择交互与核对体验；
- **不**把 OCR 批量保存、CSV 导入、S14-D 账本导入强行塞进同一套保存逻辑；
- S14 已有的账本导入任务、业务锁、10 分钟确认、撤销、最终确认等机制不得改变或绕过。

## 4. 技术分层

建议把处理拆成可独立测试的层，避免“一个模型直接决定交易数量”：

1. **图像/页面 OCR**：只负责文字和位置；
2. **页面/版式类型判断**：单笔详情、交易列表、账单概览、银行流水、未知；
3. **交易切分**：把页面中的多笔交易边界识别出来；
4. **字段提取**：每笔的金额、方向、日期、币种、商户、账户、状态等；
5. **标准化交易数据**：统一不同平台的字段含义与日期/金额格式；
6. **疑似重复检测**：图片内、跨图片、跨来源；
7. **人工核对**：单笔详情/编辑 + 批量概览；
8. **最终保存**：用户确认后才调用既有安全保存流程。

技术边界要求：

- 优先在现有 RapidOCR 基础上扩展；
- 不未经评估引入大型云端 AI 模型；
- 不把“识别准确率”押在单一模型上；
- 各层输出可被测试样本固定、可单独回归；
- 失败时能降级到人工录入/单笔核对，不假装成功。

## 5. 近期版式范围

### 5.1 优先研究并支持

- 微信支付单笔详情；
- 支付宝单笔详情；
- 微信交易记录列表；
- 支付宝交易记录列表；
- Bank of America（BOA）交易活动列表；
- BOA 单笔交易详情或可获得的版式。

### 5.2 长期扩展（不作为 S15-B 完成条件）

- 中国国内银行 App；
- 美国其他银行；
- 其他国家和地区银行；
- 更多支付工具；
- 不同语言、日期格式、币种格式。

**“支持所有银行”不是 S15-B 必须完成的条件。** 目标是建立可以继续增加版式、提取规则和测试样本的架构。

## 6. 必须处理的边界情况

- Pending 与 Posted 状态；
- 转账（不是普通收支）；
- 退款（方向与分类）；
- 重复交易；
- 同一笔交易在多张/滚动截图中重复出现；
- 不同币种；
- 缺失年份的日期；
- 金额正负号；
- 不同银行的商户名称格式；
- 截图不完整、分辨率不足、混合版式；
- 图片内多笔与多图片多笔的组合。

## 7. 与 CSV 导入的配合

对支持正式导出交易数据的银行，优先考虑 CSV 等结构化导入。BOA 可同时研究 CSV 与截图 OCR，但两者最终应尽量使用**一致的交易核对与概览体验**。

不得假定额外假定截图 OCR 的准确率天然高于结构化文件导入。

## 8. 隐私与安全

- 默认不把真实付款截图发送到第三方云 OCR/AI；
- 不为了训练或调试默认保存用户截图；
- 用户真实截图不得加入仓库、日志或测试样本集；
- 自动化测试只用合成/脱敏样本；
- 图片处理继续遵循现有“不落盘”原则，除非所有者明确批准新的隐私边界；
- OCR 结果在用户确认前只是草稿，不得直接写入正式账本；
- 不得因识别不确定而猜测金额或自动补齐关键财务字段。

## 9. 验收标准（草案，待所有者确认）

### 9.1 分类与切分

- 单笔详情只产生一笔；
- 列表/流水能产生多笔；
- 未知类型不擅自决定数量，必须让用户选择；
- 部分截图不编造缺失字段。

### 9.2 概览页面

- 顶部汇总数量与实际列表一致；
- 完整/有疑问/疑似重复/选中数量可辨认；
- 卡片字段层级清晰，移动端不拥挤；
- 缺失字段明确显示“未填写/待确认”；
- 点击进入详情编辑，返回后同步最新值；
- 可保留/排除；无问题记录无需逐笔确认；
- 最终确认前没有任何账本写入。

### 9.3 重复与多图

- 跨图片重复被提示/标记；
- 多张同一笔凭证按现有规则合并；
- 多张分别识别时一张图片的多笔也进入统一集合；
- 重复处理由用户可见、可核对。

### 9.4 既有安全机制

- S14 导入任务/锁/确认/撤销机制未被绕过；
- 批量保存与单笔保存的权限、错误、撤销边界清楚；
- 失败时不会部分静默写入或丢失用户选择。

### 9.5 测试

- 每个已知版式有合成/脱敏固定样本；
- 覆盖单笔、列表、不完整截图、重复、多图、噪声和低分辨率；
- 不使用真实用户截图；
- 性能以及准确率阈值（包括关键字段容错）**由所有者确认后写入正式验收**；在确认前不得宣称“生产准确率已达标”。

## 10. 待所有者决定

1. S15-B 首发的版式优先级是否就是本文 §5.1，是否先只做其中一部分；
2. 单张图/一次上传的图片数量限制是否沿用现有 OCR 限制；
3. Pending/Posted、退款、转账的默认处理规则；
4. 重复检测的判定口径（哪些自动提示、哪些必须用户选择、哪些可自动排除）；
5. 批量确认后的保存动作是否沿用现有交易接口，还是新增专用批量接口；
6. 是否需要数据库结构变更；如需要，必须单独设计迁移与回滚；
7. 哪些情况需要用户明确选择“按单笔/按多笔处理”；
8. 真实截图/真实用户数据的授权、保存期限与测试样本治理规则；
9. 准确率、切分率、重复率、性能的验收阈值；
10. CSV 导入与 OCR 是否在第一版共用同一个概览页面。

## 11. 交付拆分（建议）

- **S15-B1**：页面类型判断 + 单笔/多笔切分接口与固定样本；
- **S15-B2**：概览页面视觉/交互 + 单笔详情编辑回流；
- **S15-B3**：多图合并、跨图/滚动截图重复提示；
- **S15-B4**：BOA/CSV 等版式扩展与准确率验收；
- **S15-B5**：与既有安全保存流程集成、真机验收。

各子项均需所有者验收后才进入下一项；不得把 B1 的识别能力直接当成 B5 的可发布状态。

## 12. 未来扩展

- 更多银行/支付工具/语言/币种；
- 自定义版式规则/模板；
- 更强的智能整理与主动分析；
- CSV/银行结构化数据优先；
- 自托管/本地 OCR；
- 原生客户端。

这些均不属于 S15-B 的完成条件，也不阻塞 Web/PWA 正式发布。
