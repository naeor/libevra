## 1. 一句话结论

所有记账入口（手动、语音、单图拍照、OCR 批量、CSV 导入、账本导入、明细页即时检查、全账本主动检查）
共用**一份**判定函数 `duplicateDetection.ts`、**一份**用户设置、**一套**提示文案；疑似重复只提示，
写入、删除、合并始终由用户显式决定。

## 2. 唯一核心与唯一设置

| 关注点 | 位置 | 说明 |
|---|---|---|
| 判定 | `packages/shared/src/duplicateDetection.ts` | `evaluateDuplicatePair` / `evaluateDuplicateCandidates`；顺序 book→kind→amount→currency→time→category→paymentMethod→merchant→note→tags |
| 批量分组 | `packages/shared/src/duplicateReview.ts` | `groupDuplicatePairs` 只做排版（并查集），**不是结论** |
| 文案 | 同上 | `describeDuplicateMatch(pair)`：所有入口的提示一律用它 |
| 设置 | `packages/shared/src/duplicateDetection.ts` + `apps/web/src/lib/duplicateSettings.ts` | 11 个键；localStorage 按用户隔离、版本化、坏数据恢复 |
| 设置界面 | `apps/web/src/components/DuplicateDetectionSettings.tsx` | 主开关 + 金额/币种/方向/时间/分类/支付方式/商户/备注/标签 + 时间窗 |

开关语义（E2 已定，E4 全部入口遵守）：

- **缺失 ≠ 不同**：一方没值 → 该规则记 `missing`，不排除；
- 默认开启：金额、币种、方向、时间、分类、支付方式；默认关闭：商户、备注、标签；
  时间窗默认 60 秒；总开关关闭 → 所有入口都不提示，但幂等键、来源单号去重、导入锁照旧生效；
- 时间只比较**带偏移的真实时间戳**：跨分钟、跨午夜、跨时区都按绝对时刻算；
  只有日期（`occurredAtPrecision === "day"`）的记录记 `missing` 并用“同本地日期”作弱依据，
  **不补 12:00**；日期不同则排除；
- `evidence` 只分 strong/weak/none，**不是概率**。

## 4. 新增时的两部分检查

- **本批之间**：`evaluateDuplicateCandidates` 先按 `(bookId, kind, amountCents, currency)` 分桶再逐对，
  不产生 O(n²) 的全量比较。
- **本批对账本历史**：`POST /api/v1/transactions/duplicates/candidates`，每个候选一次 `findMany` 粗筛
  （`duplicateWhere`：账本 + 未删除 + 开启的维度 + 时间窗），最多 501 行；命中后仍由
  `evaluateDuplicatePair` 复判。**不重扫全账本**，也不为每笔拉全量历史。
- 上限与截断：单次请求 ≤100 个候选、≤500 对、≤500 条历史；超出时 `truncated: true`，
  界面必须说明“结果不完整”，不能装作没发现。
- 离线/游客：`checkNewCandidates` 落到本地分支，逐对比较本机已知账目（游客读 `libellum-guest`，
  登录用户读离线库，两套存储必须分叉），并返回 `scope: "local"`。

## 5. 关系记忆（复用 E3）

- 表与接口不动：`transaction_not_duplicate_relations`、`/api/v1/books/:bookId/not-duplicate-relations`。
- **只有**“确认不是同一笔”写关系（`decisionSource`：`manual` / `review_group` / `import_review`）；
  “仍然保存 / 仍然全部导入”**不写**。
- 判定端过滤：`suppressConfirmed`（服务端 candidates/review/import-review 三个接口）/
  `notDuplicatePairKey` 集合（前端：账本导入预览由 `fetchNotDuplicatePairKeys` 读目标账本的生效关系）按对精确抑制，
  不推导传递关系（A–B、B–C ≠ A–C）。
- 失效：`PATCH /transactions/:id` 改金额/币种/方向/时间时，同事务撤销关系（E3 已有）；
  分类/支付方式/标签/商户/备注变化不失效。
- 可查看/撤销：账本设置 → 数据管理 →“已忽略的重复交易”（E3 页面保留）。
- 游客与离线：关系在服务器，游客不提供“确认不是同一笔”（按钮禁用并解释原因），
  不让用户以为本地按下了就等于记住了。

## 6. 全账本主动检查（E5）

- 入口只放在**账本设置 → 数据管理**，不占明细页顶部。
- 流程：`POST /transactions/duplicates/review` 分块（每块 50 行，每行只与 `seq` 更大的行比较），
  客户端回传 `afterSeq`，进度按 `processed / total` 显示真实数字并可随时取消；
  取消只是停止请求，**不写任何数据**。
- `truncated`（达到 500 对上限）时提示“本次结果不完整”；失败可“从断点重试”。
- 分组只用于阅读顺序；组内逐对展示 `describeDuplicateMatch` 的依据。
- 处理方式：跳过（只是关掉这条提示）、保留、标记“不是同一笔”。**没有**自动删除/自动合并；
  要删历史账目仍走明细页软删除（回收站/撤销/权限一套不变）。
- 规模边界：单账本 ≤2000 笔量级可用（E1 实测百条量级）；超过时靠分块与截断保持可响应，
  但没有专门的索引（`Transaction` 无 `(bookId, amountCents)` 索引），仍是“时间/明细扫描 + 内存分桶”。

## 7. 旧口径清理

| 旧实现 | 处理 |
|---|---|
| `POST /api/v1/transactions/duplicates`（按 `occurredLocalDate` + `HH:mm` 全等） | 内部改为统一核心 + 关系抑制；响应结构 `{duplicates}` 保留以兼容旧客户端，`useCheckDuplicates` 已换成候选接口 |
| 游客本地判重（金额 + 方向 + 本地日期） | 改为 `checkNewCandidates` 的 local 分支（同一核心、同一设置） |
| Python `apps/ocr/dedupe.py`（图内/跨图/对历史） | **删除**（含 `tests/test_dedupe.py`）；`overview.py` 只做字段完整性，不再有第二套判重 |
| OCR 前端 0.85 商户相似度前置 | 删除：商户改为核心的 `matchMerchant` 开关，按 `trim` 后原文严格比较；不再有不受设置控制的隐藏规则 |
| CSV 导入只按 `sourceRef` 身份去重（无内容判重） | 保留身份去重；内容判重改为导入后按 `importRef` 检查这一批（§3）。无时间的行由导入补 `12:00`，落库后无法区分（§10 第 9 条） |
| 各入口手写提示（“金额、币种、方向、日期、时间都相同”等） | 统一由 `describeDuplicateMatch` 生成；缺失字段不再被说成“相同” |

## 8. 权限、离线与安全

- 检测接口用 `requireRead`（viewer 可检测），写关系用 `requireBookWrite`（viewer 403 `book_read_only`）。
- 敏感权限判断**只复用未改动**：`auth/guard.ts`、`ledger/access.ts`、`admin/*` 均未修改。
- 幂等与来源去重不受总开关影响：`idempotencyKey`、`UNIQUE(bookId, sourceNamespace, sourceRef)`、
  `importRef`、导入锁（`ledger_write_locks` 409 `book_locked`）照旧。
- 离线：手动记账仍可写本地队列；检测只能说明“检查了本机已知数据”，不会宣称服务器账本无重复；
  关系的创建/撤销在离线与游客下禁用（服务器权威）。
- 不新增数据库迁移；仍 52 个（E3 的表只在本机开发库/测试库）。
- 没有上传任何截图/文字到外部服务；OCR 判重全在浏览器/本地。

## 10. 已知限制 / 未完成

1. **API 集成测试未在本机跑通**（环境缺数据库凭据），只做过类型检查；首次在有测试库的机器上跑必须确认 8 个用例全绿。
2. **CSV 导入没有逐行预览**：服务端整批写入，浏览器拿不到行数据，因此内容判重发生在写入**之后**
   （按 `importRef`）。这不是“写入前拦截”；若要拦截，需要把解析结果回传前端（会引入第二套解析口径）。
3. **OCR 批量的历史检测只在“确认导入”时做**，单笔核对页只有批次内分组；这是刻意的（避免每改一格都请求）。
4. **商户/备注/标签匹配依赖数据存在**：`Transaction` 没有商户字段，所以商户匹配实际只对 OCR 候选生效；
   备注/标签匹配对正式账目生效，但对 OCR/导入候选通常缺失（按“缺失不排除”处理）。
5. **全账本检查没有新增索引**，大账本（>2000 笔）会慢；靠分块与 500 对截断保持可取消。
6. **设置仍只在 localStorage**（按用户隔离），**不跨设备同步**——本轮明确不做。
7. **关系与候选的并发**：检查期间账本被改（编辑/删除/切换账本）时，页面只保证不把旧结果写进新账本，
   没有乐观锁；关系创建前服务端会再判一次 `effective`。
8. E6（18 个验收场景 + 安全清单）**未做**；真机体验、取消/失败反馈的手感未验。
9. **“只有日期”的识别结果与“已经写进账本的只有日期”不是一回事**：OCR/导入预览的候选带
   `occurredAtPrecision: "day"`，核心按“同本地日期”的弱依据处理（§2）；但 `Transaction` 表
   **没有 precision 字段**，`apps/api/src/routes/import.ts:409-412` 对缺时间的 CSV 行会补
   `12:00:00`，落库后无法再区分“真有 12:00”与“不知道几点”。因此 CSV 导入的无时间行在后续
   检查里会被当作 12:00 参与 ±60 秒比较——这是既有导入行为，本轮按“不改导入代码”保持原样。
   要彻底解决需要给交易加 precision 列（新迁移），不在本轮范围。
10. **消费日期与入账日期的差异没有落地**：账本模型只有 `occurredLocalDate`/`occurredAt`，
    银行账单里“消费日”与“入账日”两列没有对应字段，CSV 导入也只取消费日。用户要求里的这一条
    属于**未完成**，需要先扩数据模型再谈核对（会引入新迁移，需单独批准）。
