# 离线历史读取容量上限与长期优化（2026-10-28）

> 最后核对: `s17/integration-claude @ 84e716b` / 2026-10-28（1.17.6 离线读取上限修复）。性质：功能规格与长期优化说明；执行状态只写 [STATUS](../../STATUS.md)。

## 1. 一句话

离线历史镜像现在每月最多读取 **约 50,000 笔**（500 页 × 100 条），**这是临时保护边界，不是永久规格**；`50,000` 与逐笔综合折算的 `50,000`、分析范围的 `100,000` 是三个不同的容量，不得混为一谈。

## 2. 现状：三个不同的容量阈值

| 名称 | 值 | 位置 | 语义 | 超限行为 |
|---|---|---|---|---|
| 离线历史读取 · 单月 | 50,000 笔/月（本次由 4,000 提高） | `apps/web/src/lib/offline/fillCoverage.ts` `FILL_MONTH_ENTRY_LIMIT` | 本机把某个月取回本地账本的能力上限 | 该月**不写入**本地账本；记录「未完整」状态（已取回条数 / 上限 / 时间）；下载管理与离线提示显式说明；下次联网或手动「下载全部」重试 |
| 分析范围读取 | 100,000 条/范围 | `apps/web/src/lib/analysisRange.ts` `remote.size > 100_000` | S17 工作台一次分析范围从服务器补齐原件的容量守卫 | 抛 `fx_range_capacity`，界面显示容量超限而不是部分结果 |
| 逐笔综合折算投影 | 50,000 笔/次 | `packages/shared/src/fx.ts` `FX_MAX_DETAIL_ENTRIES` | 一次把逐笔汇率投影给分析引擎的条数上限 | 抛 `fx_detail_limit`；逐笔准确卡片显式提示、回退聚合口径；7 张「聚合即精确」卡片不受影响 |

**为什么必须区分**：分析范围可以跨月。即使每个月都能完整取回，一个 12 个月的范围仍可能超过逐笔折算的 50,000，届时是综合折算显式降级（不是离线读取失败）。修改任何一个阈值都要单独评估，不能宣称「支持任意数量」。

## 3. 临时上限：是什么、为什么、用户会看到什么

### 3.1 旧行为（1.17.5 及以前，已修复）

- 每月最多 40 页 × 100 条 = 4,000 笔；达到上限时循环退出与「取完」不可区分。
- 代码随后**无条件**把已取页面写入本地账本，并计为完成 → 超过 4,000 笔的月份被静默截断；下次启动仍会重新拉同样 40 页，永远补不齐。
- 界面显示「已下载」/「全部月份都已下载」，离线明细与统计少算且不可发现。

### 3.2 现在的行为（1.17.6）

- 每页仍 100 条（服务端单页上限），最多 500 页；只有最后一页 `nextCursor === null` 才算**取完**。
- **取完**：写入本地账本（`storeMonth`），与以前一致。
- **没取完**：不写本地账本；在 `offline-fill-partial-months`（按账本作用域）记录 `{ entries, limit, at }`；下载管理该月显示「未完整 · N 笔（单月上限 L 条）」；单月下载页显示「未完整下载」并给出原因；离线提示补充「有 N 个月的本地记录没有取完，离线统计不包含这些月份」。
- 自动填充遇到已触顶的月份会跳过重试（避免每次启动重复烧流量）；用户手动「下载全部」或单月「下载」会强制重试，直到成功或再次触顶。
- S17 分析工作台的来源完整性不受影响：没有完整写入本地账本的月份不会产生覆盖回执，离线分析继续显示「数据不完整」，不会把部分数据当成整月。

### 3.3 为什么现在仍是临时边界

- 500 页意味着一次完整回填最多 60 个月 × 500 次请求；手机上耗时、耗流量、耗内存，也放大服务端 cursor 扫描成本。
- 固定条数上限只能降低「静默出错」的概率，不能证明完整性；真正的正确性应由「分页是否走到终点」保证，而不是靠一个大数字。
- 所以本轮先把边界抬高到足够覆盖真实账本、并把「触顶」变成显式结果；把上限彻底取消留给长期方案（§6）。

## 4. 不得静默截断（验收规则，最重要）

1. 某月超过上限时，**不得**只取前 50,000 笔就宣布同步完成，也不得把该月视作完整数据源。
2. 未取完的月份必须有持久状态；依赖该月的统计不得被标记为完整。
3. 用户必须能在下载管理/离线提示中看到「哪个月没取完、取回了多少、上限是多少」。
4. 允许重试或续读；重试不得把「再次触顶」当成成功。
5. 不得因本改动提高逐笔综合折算的 50,000，也不得让分析范围 100,000 守卫失效。
6. 测试必须覆盖「恰好等于上限」与「上限 +1」两种边界，证明后者不被当成完整。

## 5. 旧数据：此前被 4,000 截断的月份怎么办

- 旧实现的 query cache 最后一页 `nextCursor` 非空 → 新代码的 `alreadyComplete` 判定为 false → 下次联网自动重新读取（上限已提高，通常一次补齐）。
- 若缓存已被清理、本地账本里只有那 4,000 笔：系统无法自动识别它是截断产物（旧数据没有完整度元数据）。新代码不会把它标记为「未完整」；它仍会参与离线统计。**这意味着升级后第一次完整回填之前，旧截断月的历史少算无法自动修正**；建议在升级后手动「下载全部」一次，或等待自动填充重新覆盖（同月重复读取会按版本合并，不会重复计数）。
- 不伪造历史完整度、不回填假的覆盖回执。

## 6. 长期方向（待研究，本轮不实现）

| 方向 | 要解决的问题 |
|---|---|
| cursor 完整分页 | 去掉固定页数上限，用「是否还有 cursor」而不是「取了多少条」判定完成 |
| 断点续读 | partial 记录保存 `nextCursor`，重试从断点继续，减少重复请求 |
| 增量同步 / 月级版本 | 已完整月份只取变更，而不是整月重读 |
| 服务端聚合接口 | 统计改由服务端按日期/分类/账户聚合，客户端不再需要完整逐笔原件 |
| 逐笔汇率效率 | 降低大范围综合折算的内存与计算成本，减轻 50,000 投影压力 |
| 缓存与失效策略 | 更大本机缓存、冷热分层、清理与重建 |
| 覆盖完整性校验 | 把已设计但未接线的 `coverageGap`（服务器总量 vs 本机条数）接上，让「少算」可发现 |
| 明细页离线覆盖提示 | 明细列表离线读取本机数据时，明确说明只覆盖到哪个月 |
