## 0. 一句话结论

**今天的「导入」只认 Libevra 自己导出的 UTF-8 CSV 模板**：微信 XLSX、支付宝 CSV（GB18030）、BOA PDF 三份真实样本**没有一份能被现在的入口接受**。
建议把导入拆成「**服务端识别 → 统一候选 → 前端批量核对 → 一次性确认写入**」两阶段，**解析统一放在 API 端**（PDF 用一个成熟库，XLSX 用手写零依赖读取），
**复用现有 CSV 导入的事务/幂等/追溯机制**与**现有 OCR 概览的核对界面语言**，**不碰 S15-E2 判重核心**、**不需要数据库迁移**。

### 1.1 页面与两条入口

| 入口 | 路由 | 说明 |
|---|---|---|

组件是同一个 `apps/web/src/pages/ImportPage.tsx`，按有没有 `bookId` 分两种外壳。步骤机只有三态：`choose → confirm → report`。

### 1.2 服务端导入链路（`apps/api/src/routes/import.ts`，已完整读过）

单条路由 `POST /api/v1/import`，规则可以逐条列清：

| # | 规则 | 代码事实 | 对 V2 的含义 |
|---|---|---|---|
| 1 | 只接受 multipart | `request.isMultipart()` 否则 `expected_multipart` | 新预览接口沿用同一传输方式 |
| 2 | **文件读进内存** | `part.toBuffer().toString("utf8")`；注释明确「没有理由让它存在于服务器磁盘」 | **不落盘**是既有选择，V2 应保持 |
| 3 | **只按 UTF-8 解码** | 无编码检测、无 BOM 以外的处理（`parseCsv` 会剥 BOM） | 支付宝 GB18030 文件在这里就已经变成乱码 |
| 4 | 只认自己的列名 | `COLUMN_BY_HEADER` 由 `EXPORT_COLUMNS` 的中文表头生成（编号/日期/时间/时区/类型/金额/币种/分类/支付方式/备注/标签/录入时间/流水编号/来源编号/导出编号） | 外部文件的「交易时间/收/支/金额(元)」一个都对不上 |
| 5 | 必需列只有两个 | `occurredLocalDate`（日期）+ `amount`（金额） | 微信/支付宝都没有「日期」这一列名 |
| 6 | 行数上限 | `MAX_IMPORT_ROWS = 20000` | V2 可沿用 |
| 7 | **全批校验，一行错全批不写** | 先收集**所有**行错误 → `errors.length > 0` 直接返回 `ok:false` | 安全性质，V2 **必须保留** |
| 8 | 错误带行号与列名 | `ImportRowError{line, column, message}`，行号是文件里的真实行号 | 核对页的错误列表直接用 |
| 9 | 分类/支付方式必须已存在 | 不存在就报错，不自动创建（只有标签会自动创建） | 适配器只能「建议」，不能替用户造分类 |
| 10 | 类型只有收入/支出 | `kind` 空则用金额正负兜底 | **没有「不计收支」类型**（见 §4、§10-⑥） |
| 11 | 文件指纹幂等 | `sha256(fileText)` → 命中 `ImportLog` 直接返回**上次的结果** | 「同一份文件再导入」不会变成「全部重复」 |
| 12 | 行级身份去重 | `effectiveRefFor = 来源编号 ?? 流水编号`；命中 `Transaction.id` 或 `(bookId, sourceRef, sourceNamespace="")` 或**本次文件内已出现**的值 → 跳过并记录行号 | 「42 笔全部跳过」只可能出在这条规则上 |
| 13 | 身份不来自文件主键 | 文件里的 `流水编号` 只当参考，`id` 由服务端 `randomUUID()` 生成 | 外部文件不能指定我们的主键 |
| 14 | 单事务写入 | 标签创建 + 逐行 `allocateTransactionSeq` + `create` + `importLog` 全在一个 `$transaction` | 逐行分配编号**故意**不用块分配（失败会留号段空洞） |
| 15 | 追溯 | 每行写 `importRef`（`In-…`），`ImportLog` 记 `format/fileRef/exportedFileRef/sourceFingerprint/rowCount/importedCount/skippedCount` | V2 直接复用；`format` 是 `VarChar(8)`，**能写 xlsx/pdf，不需要迁移** |
| 16 | 来源命名空间 | 列存在（`sourceNamespace`，默认 `""`，`VarChar(80)`），但路由的查询与写入**都写死 `""`** | 想按平台隔离就得改查询；建议先不改（见 §8） |

### 1.3 前端上传与状态

- `accept=".csv,text/csv"`，一个 `sr-only` 的 `<input type="file">` + 一个主按钮「选择 CSV 文件」。
- **没有拖拽、没有文件名/大小/格式回显、没有清除/更换、没有格式识别、没有帮助展开**。
- 选完文件立刻弹 `ConfirmDialog`（「会先校验整个文件，通过后才写入这本账」），确认后 `useImportEntries` → `POST /import`（`timeoutMs: 120_000`）。
- 结果页两种：失败列出前 50 条错误（带行号）；成功显示「已导入 N 条 / 跳过 N 条 / 导入编号 / 来自这次导出」。
- 判重说明目前是一段静态文字：「文件里带的『流水编号』如果这个账本已经有了，那一行会被跳过」。

### 1.5 有没有微信/支付宝/BOA 适配器？

**没有。** 代码里不存在任何按平台解析账单文件的实现：

- OCR 那条线只处理**截图**（PNG/JPEG/WebP，`RECOGNIZE_MIME_TYPES`），产出的是「候选」而不是文件行；
- `/import` 只处理**自己导出的 CSV**；
- `/import-ledger` 处理的是**本系统游客账本 → 正式账本**，不认外部文件。

### 1.6 现有 CSV 导入的实测能力边界（三份真实样本都会失败）

我在本机用同一套逻辑复核过（不启动服务）：

- **微信 XLSX**：`part.toBuffer().toString("utf8")` 得到的是 ZIP 二进制乱码，`parseCsv` 找不到任何表头 → `missing_column`。
- **支付宝 CSV**：严格 UTF-8 解码在第 86 字节就失败；按 UTF-8 强制解码后出现 **2068 个替换字符**，`日期`/`金额`/`交易时间` 一个都匹配不到 → `missing_column`。
  即使解码正确，它**前 23 行是导出说明**，正式表头在第 24 行，现有解析把第 1 行当表头。
- **BOA PDF**：`toString("utf8")` 后是一堆二进制，同样在表头阶段失败。

> **结论**：V2 不是「优化导入」，而是**新增三种格式的识别能力**。现有 CSV 路径要保留（它承载「导出→改→导回」的往返，别把它改坏）。

## 2. 三份真实样本的实测结果（脱敏）

### 2.0 方法与边界

- 全部用 **Python 3.11 标准库**（`zipfile` + `xml.etree`、`gb18030` 解码、`zlib` + 自写 ToUnicode CMap 解析）完成，**没有安装任何库、没有联网、没有用云 OCR**。
- 脚本与中间输出在 `%TEMP%` 下的独立目录，跑完删除；本文只保留结构与计数。
- **凡是「实测」都在下表中标明获取方式；凡是我推断的，一律写「推断」。**

### 2.1 样本 A：微信支付账单 XLSX

| 项 | 实测结果 |
|---|---|
| 文件 | 7.7 KB；`PK` 头；ZIP 内 **10 个条目**（含 `xl/sharedStrings.xml`、`xl/styles.xml`、`sheet1.xml`） |
| 工作表 | **1 个**，名字是 `Sheet1`（不是「账单明细」之类；**不能靠表名识别**） |
| 使用区域 | `A1:K30`（30 行 × 11 列），**无 autoFilter、无冻结、无隐藏行列** |
| 合并单元格 | **17 个**：`A1:K1` … `A17:K17`，即**前 17 行整行合并**；**数据区（19–30）没有合并** |
| 前导说明 | 第 1–17 行：标题、昵称、起止时间、导出类型、导出时间、空行、`共N笔记录`、收入/支出/中性交易三行统计、`注：` 与 4 条说明、分隔线、空行 |
| **表头行** | **第 18 行**（1 基），11 列全部为共享字符串 |
| 列名 | `交易时间` `交易类型` `交易对方` `商品` `收/支` `金额(元)` `支付方式` `当前状态` `交易单号` `商户单号` `备注` |
| 数据行 | **12 行**（第 19–30 行），与声明「共 12 笔」一致 |
| **日期单元格类型** | **数值 serial**（`t` 缺省），全部套用自定义 `numFmt 164 = yyyy-mm-dd hh:mm:ss`；**没有一个是字符串** |
| 金额单元格类型 | **数值**（`numFmt 165 = ¥#,##0.00`）；原始小数位 **0/1/2 位**都有；**没有负号** |
| 单号保真 | `交易单号` 是**共享字符串**，长度 28/31/32/**39**，12 条全纯数字 → **不存在被 Excel 存成 float 的精度损失**（但 39 位远超 JS 安全整数，仍必须当字符串） |
| 占位符 | **`/` 表示「无值」**：`备注` 12/12 都是 `/`；`支付方式` 3 条 `/`；`交易对方` 1 条 `/`；`商户单号` 3 条 `/` + 1 条空 |
| 收/支 | **支出 8 / 收入 4 / 不计收支 0**（与声明 8/4/0 一致） |
| 当前状态 | 已存入零钱 3、支付成功 5、对方已收钱 2、已全额退款 1、对方已退还 1 |
| 交易类型 | 转账 6、商户消费 5、转账-退款 1 |
| 日期范围 | **2026-09-22 00:27 ~ 2026-10-16 10:04**，8 个不同日期；**秒不为 0**（不是整分钟） |
| 合计行 | 数据区之后**没有**合计行；合计信息只在前导说明里 |

**对适配器的含义（推断 → 需在实现时验证）**：必须**扫描表头**（找 `交易时间` + `金额` 同时出现的行），不能假设第 1 行；必须**按样式判断日期**（`numFmtId` 落在 Excel 内置日期区间，或自定义格式里含 `y/m/d/h/s`），不能只看是不是数字；`/` 必须当空；状态词表要按值处理而不是硬编码枚举。

| 收/付款方式 | 5 种：某银行储蓄卡(尾号\*\*\*\*)、另一银行储蓄卡(尾号\*\*\*\*)、以及 3 种带「&支付宝立减 / 随机立减 / 立减金」后缀的组合 |
| 页脚 | **没有**页脚/分隔行；最后一行就是最后一笔 |

**对适配器的含义**：①必须**先试 UTF-8（fatal）再退 GB18030**；②必须**扫描表头**；③必须容忍**尾部空列**与**混合行尾**；④**单号必须 strip 掉 `\t` 再当身份**（否则每次导入都会"看起来是新单号"）；⑤`/` 是占位符。

### 2.3 样本 C：Bank of America 结单 PDF

| 项 | 实测结果 |
|---|---|
| 文件 | 242.7 KB；`%PDF-1.5`；**未加密**（无 `/Encrypt`） |
| 页数 | **8 页**（`/Type /Page` 对象 8 个，`/Contents` 引用 8 个，`/Kids` 与之匹配） |
| **有无文本层** | ✅ **有**。可解压内容流 22 个，其中 **8 个含 `BT` + `Tj`**（共 39/51/78/107/100/98/5/3 个 `Tj`） |
| 文本层难点 | 6 个子集字体（`AAAAAB+ITC_Franklin_Gothic_Book` 等）+ **6 个 `/ToUnicode` CMap** + 自定义 `/Encoding`。**字面量字节不是 ASCII**：不按 CMap 映射就是乱码 |
| 我实际怎么解出来的 | 自写「对象定位 → 解 Flate → 解析 `beginbfchar/beginbfrange` → 按 `Tf/Td/Tm` 还原行列坐标」，**成功还原全部 8 页文字**（实测，非推断） |
| 页面结构 | 第 1 页：地址块 + **Account summary** 表（期初/存入/ATM 借记/其他扣款/服务费/期末）；第 2 页：IMPORTANT INFORMATION 法律段；第 3–6 页：交易表；第 7 页：Braille 申请说明；第 8 页：**intentionally left blank** |
| 每页交易行 | 第 3 页 18 行、第 4 页 33 行、第 5 页 30 行、第 6 页 27 行；第 1/2/7/8 页 **0 行** |
| 交易笔数 | **108 行**（首列为 `MM/DD/YY` 且行尾带两位小数金额） |
| 分区 | **Deposits and other additions 14 行**、**ATM and debit card subtractions 83 行**、**Other subtractions 11 行**；14+83+11 = 108 ✅ |
| 跨页延续 | 每个续表都重复 `Withdrawals and other subtractions - continued` / `ATM and debit card subtractions - continued` / `Date Description Amount`；**本样本没有「行被拆到两页」的情况**（见下"难点"） |
| 日期 | 只有一种格式 `MM/DD/YY`，**是过账日期**；范围 **2026-09-18 ~ 2026-10-19**（20 个不同日期），与结单周期 `September 18, 2026 – October 19, 2026` 一致 |
| 双日期 | **21 行**的描述里还有第二个 `MM/DD`（卡交易的交易日），**两套日期同时存在** |
| 金额 | 数字 + 两位小数，**无 `$`、无千分位**；**减项带 `-`**；存入 14 行全正、ATM/其他 94 行全负 |
| **对账** | ①三个分区的分组合计与结单里的 `Total …` **逐段完全一致**（差额 0 分）；②`期初 + 存入 − ATM − 其他 − 服务费 = 期末` **成立**（服务费为 0）；③第 3–6 页共 **111** 个「行尾金额」= 108 交易 + 3 个 `Total` 行 → **没有漏行、没有重复计** |
| 需排除项 | 97 行非交易文本（地址块、账户摘要表、法律段、页脚 `Page N of M`、页头"姓名｜账号｜周期"、`PULL/CYCLE/SPEC` 内部编码行、`intentionally left blank`） |
| 关键词（描述内，仅计数） | ZELLE 17、`purchase` 71、`check` 12（子串匹配，可能含 checking 等误计）、`transfer` 4、`deposit` 3、`apple` 3、`refund` 1 |
| 同日同金额 | **2 组**（各 2 行）→ 仅凭「日期 + 金额」无法区分同一笔，必须靠描述或行序 |
| 行序 | 基本按日期升序，但**有 2 处逆序**（同日内的先后） |

### 2.4 哪些是实测、哪些是推断

| 结论 | 依据 |
|---|---|
| 微信/支付宝/BOA 三种结构的全部计数、列名、类型、日期范围 | ✅ **实测**（stdlib 解析三份私有副本） |
| BOA 文本层可提取、且必须按 ToUnicode CMap 映射 | ✅ **实测**（自写 CMap 解码器还原全文，且三段对账全对） |
| 现有 `/import` 会拒绝这三种文件 | ✅ **代码事实 + 实测**（UTF-8 强制解码得到 2068 个替换字符；表头名不匹配） |
| 「微信单号不会被 Excel 存成 float」 | ✅ **本样本实测**（共享字符串）；⚠️ 但**不能**推断所有微信导出都这样，实现必须按单元格类型容错 |
| 「其他微信/支付宝导出可能多出状态值（支付失败/已关闭等）」 | ⚠️ **推断**（本样本没有这些值），词表必须宽松 |
| 「pdfjs / pdfminer 能还原这份 PDF」 | ⚠️ **未验证**（本轮不安装依赖）。我只能证明**文本层存在且可被 CMap 正确映射**，不能证明某个库开箱可用 |
| 「BOA 其他月份/其他账户格式相同」 | ⚠️ **推断**，只有一份样本 |
| 「行被拆到两页」的处理难度 | ⚠️ **推断**（本样本未出现；但 33/30/27 行/页说明表格可以很长，拆行风险真实存在） |

## 3. 推荐架构

### 3.1 管线

```
上传 → ①文件类型检测（magic bytes / 容器结构）
     → ②来源格式检测（XLSX 的工作表与表头 / CSV 的表头与编码 / PDF 的对象与 section）
     → ③适配器（微信 / 支付宝 / BOA / Libevra CSV）
     → ④统一候选模型（每行一个 candidate，带来源定位与警告）
     → ⑤批量核对（服务端判重 + 前端逐笔确认/编辑/排除）
     → ⑥确认保存（单事务 + importLog + importRef）
```

**①②都不看扩展名、不看文件名。** 判据是结构证据：

| 格式 | 判据（全部来自结构，不来自文件名） |
|---|---|
| Libevra CSV | UTF-8 可解 + 首行含 `编号`/`日期`/`金额` 等自有表头（≥3 个命中） |
| 微信 XLSX | ZIP 头 `PK\x03\x04` + 含 `xl/workbook.xml` + 某工作表里出现 `交易时间`/`交易单号`/`当前状态` |
| 支付宝 CSV | （UTF-8 或 GB18030 可解）+ 前 40 行内出现 `交易时间` 与 `交易订单号` 与 `收/支` |
| BOA PDF | `%PDF-` 头 + 可解出内容流且含 `Account summary` 或 `Deposits and other additions` + 行首 `MM/DD/YY` |
| 未知 | 明确说「不认识的账单格式」，并给出三种支持格式的导出路径；**不猜** |

### 3.2 解析放在前端还是后端？

**建议：后端（API 进程），两阶段接口。** 备选方案（前端解析 + 逐条本地写入）列在后面，作为需要所有者拍板的选项 A/B。

| 维度 | 后端解析（推荐） | 前端解析（备选） |
|---|---|---|
| 与现状一致性 | 现有 CSV 解析就在 API（`apps/api/src/routes/import.ts`），同一条脉络 | 会形成「CSV 在服务端、XLSX/PDF 在客户端」两套 |
| PDF 依赖 | 库只进服务端镜像（约 10–20 MB），**不上手机** | `pdfjs-dist` 进 PWA bundle；手机端每台都要下载、还要 worker |
| 文件去向 | 上传到**自己的服务器**（与今天 CSV 完全一致），处理完即弃、不落盘 | 文件不出设备（隐私更好），但需要客户端有能力解析 |
| 判重 | 服务端直接查账本 + 调 shared 核心，**不必把整本账拉到前端** | 需要先拉候选范围的历史记录；判重与唯一约束可能不一致 |
| 写入语义 | 复用**单事务 + 全部错误一次返回 + importLog + importRef 追溯 + S14-D 导入锁** | 逐条 `createEntry`（离线队列），**没有单一导入记录**，也不经过导入锁 |
| 离线 | 批量导入本来就要求在线（今天 CSV 也是） | 可离线解析、离线排队 |
| 限额/超时/日志 | 集中可控，日志可只记 `sha256 前 8 位 + 行号` | 分散在客户端，出错只能靠用户描述 |
| 失败降级 | 解析失败就是一次请求失败，不留半成品 | 解析成功但写入中断会留下「导了一半」的本地队列 |

> **我为什么推荐后端**：这份功能本质是**批量导入**（一次 48–108 行、需要可追溯的 `In-` 编号、需要复用「一行错全批不写」与导入锁），
> 而 OCR 那条线的「逐条本地写入」是**为几张截图设计的**，不是为一份结单设计的。
> 把 PDF 解析库塞进 PWA 是这次唯一会明显增加客户端体积的决定，收益（离线导入）与场景不匹配。

### 3.3 两阶段接口（建议新增，旧接口不动）

```
POST /api/v1/import/preview        multipart: file (+ x-libellum-book 头)
  → { previewId, format, source, encoding?, sheets?, pages?,
      candidates: [ …统一候选… ], totals: { rows, income, expense, excluded, unparsed },
      duplicates: [ { candidateId, matchedWith[], reason, evidence } ],
      warnings: [ … ], expiresAt }

POST /api/v1/import/commit         JSON: { previewId, decisions: [ { candidateId, keep, categoryId?, paymentMethodId?, kind?, amount?, date? } ] }
  → ImportReport（现有 schema，不变）
```

三条硬约束：

1. **提交只接受「决定」，不接受金额与日期**。金额/日期以服务端预览时解析出来的值为准；否则等于让客户端往账本里写任意金额（现有 CSV 路径没有这个口子）。
   用户在核对页改过的字段（例如把分类改掉）可以作为**受限的可编辑字段**（分类/支付方式/是否保留/方向），金额与日期**只允许在预览阶段就解析正确**，改不了就重新上传——这条可以在 Phase 2 先按「金额日期只读」实现，把「允许改金额」留作后续决策。
2. **preview 结果放在服务端内存里**（键 `previewId`，按 `userId + bookId` 隔离，TTL 10 分钟，进程重启即失效）。108 行 JSON 只有几十 KB，**不需要临时表、不需要落盘**。失效后让用户重新上传即可。
3. **旧 `POST /api/v1/import` 保留**（Libevra CSV 直写），V2 页面默认走 preview/commit；两者共用同一段「候选 → 写入」的实现，避免第二套落库逻辑。

> 备选（如果所有者不接受服务端内存缓存）：commit 携带**同一个文件**再上传一次 + 决定列表，服务端重新解析后按「文件指纹 + 行列定位」应用决定。**无状态、不可篡改**，代价是流量翻倍。

### 3.4 文件传输、大小上限、临时存储

| 项 | 建议 | 依据 |
|---|---|---|
| 传输 | multipart 上传，`part.toBuffer()` 读进内存 | 与现有 `/import`、`/recognize` 一致 |
| 单文件上限 | **10 MB**（不改全局 `multipart` 的 `fileSize`） | `apps/api/src/app.ts` 的全局上限就是 `MAX_RECOGNIZE_BYTES = 10MB`，改它会影响截图上传 |
| 数据行上限 | **20 000 行**（沿用 `MAX_IMPORT_ROWS`），超过就明确报「请分批」 | 现有规则 |
| PDF 页数上限 | **30 页**（本样本 8 页 / 242 KB） | 2 vCPU 上文本提取很轻，但页数上限是必要的防滥用闸门 |
| XLSX 解压上限 | **解压后 ≤ 50 MB、条目数 ≤ 512**（防 zip bomb） | 手写 ZIP 读取必须自带这道闸门 |
| 临时存储 | **不落盘**：内存 → 解析 → 丢弃；PDF 若走 Python sidecar 则按现有 OCR 协议**base64 进 stdin**，同样不落盘 | `apps/ocr/service.py` 的设计原则写得很明确 |
| 日志 | 只记 `请求 id / userId / bookId / format / sha256 前 8 位 / 行数 / 耗时 / 错误码`，**不记文件名、不记行内容** | 隐私红线 |
| 解析超时 | 单文件 **≤ 15 s**（XLSX/CSV）/**≤ 30 s**（PDF），超时返回可读错误 | 现有 OCR 单图 20 s、启动 60 s |

### 3.5 失败与降级

| 情况 | 表现 |
|---|---|
| 类型识别失败 | 「不认识的账单格式」，附支持列表与导出指引，**不猜** |
| 编码识别失败 | 明确说「这个文件的编码读不出来」，建议用 Excel 另存为 CSV（UTF-8） |
| 加密 PDF | 「这份 PDF 有密码保护，请先解除密码再上传」 |
| 扫描版 PDF（无文本层） | 「这是扫描件，目前不支持识别文字」+ 建议下载电子版账单（**明确写不支持**） |
| 部分行缺字段 | 该行标记「待核对」，不阻塞整批；**缺金额/缺日期的行在提交时逐条给原因**（与 OCR `validationBlocker` 同一套话术） |
| 行数超限 | 「文件有 N 行，超过一次导入上限 20000 行，请分批」 |

## 4. 统一候选模型

### 4.1 字段

```
candidateId         本次预览内稳定 ID（= sha256(fileSha256 + 行列定位) 前 16 位）
platform            WECHAT | ALIPAY | BANK | LIBEVRA_CSV | UNKNOWN
occurredLocalDate   YYYY-MM-DD（必填；PDF 的 MM/DD/YY 补全年份，年份取自结单周期）
occurredTime        HH:mm 或 HH:mm:ss（可空）
occurredPrecision   second | minute | day      ← 交给 S15-E2 核心时直接用
amountMinor         整数最小单位（wire 上用 string，避免 JSON 浮点）
currency            ISO 4217（默认取账本默认币种，可由来源覆盖）
kind                expense | income | transfer | unknown
merchant            对方/商户（可空）
description         原始描述/商品说明（原文，供追溯与分类建议）
rawFlow             收/支 / 不计收支（原文）
rawStatus           交易成功 / 已全额退款 / 交易关闭 …（原文）
rawCategory         来源分类（支付宝「交易分类」等，仅作建议）
rawPaymentMethod    来源支付方式原文（含「&立减」组合与卡尾号）
sourceRefKind       order | merchantOrder | synthetic
sourceRef           来源单号（已 strip 控制字符）；≤64 字符
sourceFile          { name, sha256, bytes, format }
sourceLocation      { kind:"xlsx", sheet, row } | { kind:"csv", line } | { kind:"pdf", page, rowIndex }
suggestedCategory   { categoryId|null, source: "rule"|"inferred"|null }
suggestedPayment    { paymentMethodId|null, source: "rule"|null }
excluded            boolean（用户或规则排除）
needsReview         boolean
warnings            [ { code, field, message } ]
```

### 4.2 与现有契约的映射

| 现有契约 | 怎么用 |
|---|---|
| `ImportReport` / `importReportSchema` | **作为 commit 的返回**，字段不变（`ok/fileRef/exportedFileRef/rowCount/importedCount/skippedCount/skippedLines/errors`） |
| `importRequestSchema`（只有 `fileId` uuid） | **保留给 legacy CSV**。preview 不需要它：身份来自文件指纹 + 行内容，客户端不该决定 |
| `ImportRowError` | 预览的 `warnings[]` 借用同样的 `{line, column, message}` 结构（`line` 直接用来源文件行号） |
| `EXPORT_COLUMNS` | **Libevra CSV 适配器**直接复用（15 列 → 候选），保证「导出→导回」这条往返不变 |
| `OcrCandidate`（shared） | 字段名刻意对齐（`amount/currency/direction/occurredLocalDate/occurredTime/merchant/sourcePlatform/status/isRefund/isTransfer/serial/rawText`）。**建议不合并成一个类型**：OCR 的 `serial` 是「防同一截图传两次」，账单的 `sourceRef` 是「账本内身份」，两者语义不同，混用会写出错误去重 |
| `DuplicateCandidateFields`（S15-E2） | 由候选**映射**得到（`bookId` = 目标账本、`kind`、`amountCents`、`currency`、`occurredAt` 带偏移的 ISO、`occurredLocalDate`、`categoryId`、`paymentMethodId`）。**不修改**核心 |
| `CreateTransactionInput` | commit 写入时的目标结构；`note` 由 `merchant + description` 组成（与 OCR 的 `composeNote` 同一思路） |

### 4.3 需要扩展什么

| 层 | 变更 | 说明 |
|---|---|---|
| `packages/shared` | **新增**一个导入候选模块（`billImportCandidateSchema` + 预览/提交请求响应 schema + 设置随请求传入的 schema） | 纯类型与校验，无副作用，web 与 api 共用；建议文件名带 `billImport` 前缀，避免与既有 `ledgerImport` 混淆 |
| `packages/shared` | **不改** `duplicateDetection.ts`、`export.ts`、`spreadsheet.ts`、`ocr.ts` | 兼容性边界 |
| `apps/api` | 新增 preview / commit 两条路由 + 三个适配器 + 格式检测 + XLSX 读取 + PDF 调用 | 主体工作量在这 |
| `apps/api` | `import.ts` 里「校验 → 去重 → 事务写入」**抽成可复用函数**，legacy 与 V2 共用 | 只搬不改语义；这是唯一会碰现有导入代码的地方，必须逐条对齐现有测试 |
| `apps/web` | `/import` 首屏改造 + 新核对路由 + 适配候选类型 | 不碰 OCR 批量页面 |
| 数据库 | **无** | 见 §4.4 |

### 4.4 是否需要 DB migration？**不需要。**

三条理由（都是查过 schema 的）：

1. `ImportLog.format` 是 `String @db.VarChar(8)`（不是 enum），`"xlsx"`/`"pdf"` 都能写；`fileRef`、`sourceFingerprint`、`exportedFileRef` 全都在。
2. `Transaction` 已有 `sourceRef`（`VarChar(64)`）、`sourceNamespace`（`VarChar(80)`，默认 `""`）、`importRef`（`VarChar(32)`），并有唯一约束 `(bookId, sourceNamespace, sourceRef)` —— 行级身份与追溯所需的一切都在。
3. 预览结果只在**服务端内存**里活 10 分钟，判重结果是**算出来的**，不需要表；判重设置**随请求传入**，不需要用户偏好列。

> **唯一需要注意的**：`sourceRef` 上限 64 字符。支付宝订单号 48 位 + 平台前缀仍在 64 以内；如果未来要拼更多信息，必须在适配层截断并保证唯一（建议 hash 化而不是截断）。

## 5. 三个适配器的解析策略与风险

### 5.1 微信 XLSX

**策略**

1. **ZIP 读取**：`PK\x03\x04` → 解析中央目录 → 只取 `xl/workbook.xml`、`xl/_rels/workbook.xml.rels`、`xl/sharedStrings.xml`、`xl/styles.xml`、`xl/worksheets/sheet*.xml`。用 `node:zlib.inflateRawSync`，**不安装库**（与现有 `apps/api/src/export/zip.ts` 的写入端正好对称）。
2. **表头定位**：不假设第 1 行；在**前 60 行**里找同时含 `交易时间` 与 `金额` 的行；找不到就报「这不是微信支付账单」。
3. **列映射**：`交易时间→日期+时间`、`收/支→方向`、`金额(元)→金额`、`交易对方→商户`、`商品→描述`、`当前状态→状态`、`交易单号→sourceRef`、`商户单号→备选 sourceRef`、`支付方式→paymentMethodRaw`、`备注→note`。
4. **日期**：cell `t` 缺省 + 样式 `numFmtId` 落在日期区间（14–22/45–47）或自定义格式含 `y/m/d/h/s` → 按 **Excel 1900 序列**换算（`1899-12-30 + days`），**保留秒**；否则按 `YYYY-MM-DD HH:MM:SS` 字符串解析；两者都不是 → 该行警告「日期读不出来」。
5. **金额**：cell 是数字就直接用（不经浮点元），按币种小数位转 `amountMinor`；如果 cell 是字符串（例如带 `¥`），先剥符号再解析。
6. **方向**：`收入→income`、`支出→expense`、`不计收支/中性交易→排除（默认）`（见 §10-⑥）。
7. **占位符**：`/` 与空串一律当「无值」，不写进备注、不当单号。
8. **身份**：`sourceRef = "WX-" + 交易单号`（strip 后 ≤ 64）；没有交易单号时退回商户单号；两者都没有 → `synthetic`（见 §8.3）。

**风险**

| 风险 | 说明 | 缓解 |
|---|---|---|
| Excel 把单号存成数字 | 本样本没有（全是共享字符串），但别的导出可能有 | 数字型 cell 直接取 `rawValue` 字符串（不经 `Number`），并在长度 > 15 时给警告 |
| 日期只有样式、没有值语义 | 判断依据是 `numFmt`，不是 `t` | 同时准备「字符串日期」分支，两条路都测 |
| 富文本 / 内联字符串 | `sharedStrings` 的 `si` 可能含多个 `r/t` | 拼接所有 `t`，样本已验证 |
| 合并单元格 | 前 17 行整行合并，容易把「A1 的值」当成 11 列的值 | 只按 `r`/`c` 实际存在的 cell 取，**不展开合并** |
| 工作表名不固定 | 本样本叫 `Sheet1` | 按内容找，不按名字 |
| zip bomb | 恶意 XLSX | 解压上限 + 条目数上限 |

### 5.2 支付宝 CSV

**策略**

1. **编码**：先 `new TextDecoder("utf-8", { fatal: true })`；失败 → `new TextDecoder("gb18030")`。**零依赖**（Node 24 自带完整 ICU，已实测 `gb18030` 可用）；BOM 手工剥。
2. **行尾**：混合 CRLF/LF，用现有 `parseCsv`（它逐字符处理 `\r`/`\n`，天然兼容）。
3. **表头定位**：在前 40 行里找含 `交易时间` + `交易订单号`（或 `收/支`）的行；**跳过前导 23 行说明**。
4. **尾部空列**：表头以逗号结尾 → 13 列里最后一列恒空。按**列名**取索引，不按位置硬编码。
5. **单号保真**：`sourceRef` = `交易订单号` **先 `trim()` 去掉尾部 `\t`/空白**，再 `"ALI-" + 单号`。**这是本适配器最容易错的一步**（48/48 行都带 `\t`）。
6. **方向**：`支出→expense`、`收入→income`、`不计收支→默认排除`（见 §10-⑥）。
7. **状态**：`交易成功/支付成功→正常`、`退款成功→标 isRefund`、`交易关闭→默认排除并提示`（钱没动）。
8. **分类建议**：`交易分类`（文化休闲/商业服务/教育培训/充值缴费/转账红包/退款）→ 用 `matchCategory`（已有 `packages/shared/src/categoryMatch.ts`）去匹配**本账本已有分类**，匹配不到就给 `null`，**不新建分类**。
9. **支付方式**：`收/付款方式`（含卡尾号与 `&立减`）→ 归一化：剥 `(...)` 尾号与 `&...` 后缀 → 映射到 `微信/支付宝/银行卡/现金/其他` 预设之一的**建议**；**原文只用于建议，不落库**。

**风险**

| 风险 | 说明 | 缓解 |
|---|---|---|
| 制表符 | 单号尾部 `\t`（48/48），不 strip 会导致「永远是新单号」→ 重复导入 | 统一走一个 `cleanCell()`：trim + 去零宽字符 |
| GB18030 兼容性 | 部署镜像若有 `small-icu` 会解码失败 | 构建时加一条自检（解码一段固定的 GB18030 字节）；失败就直接报错而不是静默乱码 |
| 前导行数变化 | 支付宝模板会随版本变动 | 扫表头，不数行数 |
| 用户改过文件 | 用户在 Excel 里编辑后再导出可能加引号、加千分位、改日期格式 | 解析器容忍引号/千分位/多种日期分隔符，并给「日期格式不认识」的可读错误 |
| 隐藏的 `_` 单号 | 1 条订单号含 `_` | 只做 trim，不做字符集校验 |

### 5.3 BOA PDF

**策略（文本层优先）**

1. **先判「有没有文本层」**：解析 `%PDF-` → 定位页面对象 → 解 `/FlateDecode` → 若**没有任何 `BT`/`Tj`** → 判定为**扫描件，直接拒收**并给明确提示（不 fallback 到 OCR，本轮不做）。
2. **文本提取**：用库（见 §6）而不是自己写。**必须显式配置 CMap/标准字体目录**——这份样本正是靠 `/ToUnicode` 才还原的，不配 CMap 就会得到乱码（我实测过：不用 CMap 是 `Ã¤¢£…` 这种）。
3. **按坐标重建行列**：`Tj` 的 x/y + `Td/Tm` 累积 → 按行分组、按列带切分（本样本三列：`Date` x≈左、`Description` 中间、`Amount` 右）。
4. **分区状态机**：用 section 标题驱动；`… - continued` 表示**续上一页的同一分区**；`Date Description Amount` 是表头，跳过。
5. **行识别**：首行为 `MM/DD/YY` 且行尾为带两位小数的金额 → 一行交易；不满足的行走「排除项」。
6. **排除项（必须显式列白名单）**：`Account summary` 表（期初/期末/四类合计）、`Total …` 行、页头（姓名｜账号｜周期）、页脚 `Page N of M`、法律段、地址块、`This page intentionally left blank`。
7. **方向与符号**：`Deposits and other additions → income`（金额为正）；`ATM and debit card subtractions` / `Other subtractions → expense`（金额为负）。**不按描述猜退款/转账**（见下）。
8. **年份**：`MM/DD/YY` 的 `YY` + 结单周期里的年份。跨年（12 月→1 月）时以周期为准，**不要**简单 +2000。
9. **身份**：BOA 行**没有单号**。`sourceRef = "BOA-" + sha256(文件指纹 + 页 + 行序) 前 16 位`（`synthetic`）。
10. **对账（保存前必须做）**：把三个分区的合计与结单 `Total` 行比对，并校验 `期初 + 存入 − 扣款 = 期末`。**不一致就不允许静默提交**，必须把差异作为警告显示出来。

**风险（这份样本教我的）**

| 风险 | 本样本证据 | 处理 |
|---|---|---|
| 字体子集 + CMap | 6 个子集字体、6 个 ToUnicode | 必须用库且配 CMap；不配就是乱码 |
| **双日期** | 21 行描述里有第二个 `MM/DD` | 只取**首列**为过账日期；描述内的日期不解析 |
| **跨页/续行** | 本样本没有，但 33 行/页说明会很长 | 分区状态机 + 「上一行没有金额则并入上一行」；**并要求对账兜底**：漏一行合计就对不上 |
| 同日同金额 | 2 组各 2 行 | 不能靠「日期+金额」去重；必须有 `synthetic sourceRef`（含行序） |
| 行序不完全单调 | 2 处逆序 | 不能假设升序；行序以文件为准 |
| 页内还有图片 | 7 个 `/Subtype/Image` | 只做文本提取，**不渲染**（也避免渲染类 CVE 面） |
| 扫描件 | 本样本不是 | **明确不支持**，提示下载电子版 |
| 其他银行 | 只有 BOA 一份 | 适配器按「结构」而不是「银行名」写，第一家只保证 BOA |

### 5.4 三个适配器共用的规则

| 规则 | 内容 |
|---|---|
| 金额 | 一律转**整数最小单位**（`decimalsFor(currency)`），不经过浮点元；显示时再格式化 |
| 日期 | 内部统一 `YYYY-MM-DD` + `HH:mm(:ss)` + `precision`；时区取账本/设备时区，**适配器不猜时区** |
| 方向 | 只认 `expense/income`；`不计收支/中性交易/交易关闭` 走「排除」而不是硬塞成支出 |
| 身份 | `平台前缀 + 单号`（≤64）；**没有单号的一律 synthetic**（文件指纹 + 行列定位），保证「同一文件两次导入 = 第二次全跳过」 |
| 定位 | 每个候选都带 `sourceLocation`，错误信息里直接说「第 N 行 / 第 N 页第 M 行」 |
| 不臆测 | 读不出来的字段给 `null` + 警告，**不填默认值**（这是 OCR 那条线已经确立的原则） |

## 6. 依赖推荐（**本轮不安装**）

### 6.1 今天仓库里有什么

查过 `package.json` / `pnpm-lock.yaml`：**没有任何** Excel、PDF、编码检测库（`xlsx`/`exceljs`/`pdf-parse`/`pdfjs-dist`/`iconv-lite`/`chardet`/`papaparse` 全都没有）。
现有 CSV 解析是**手写**的（`packages/shared/src/spreadsheet.ts`），现有 XLSX **写入**也是手写（`apps/api/src/export/xlsx.ts` + `zip.ts`）。

**架构事实（决定推荐的关键）**：`deploy/Dockerfile.api` 里 **API 与两个 Python sidecar 是同一个镜像、同一个 venv**，sidecar 由 API `spawn` 子进程、通过 **stdin/stdout 一行一个 JSON** 通信（无端口），**base64 传数据、永不落盘**。
所以「Python 侧解析」在运维上**不是新建服务**，只是新增一个入口脚本和几条依赖。

### 6.2 候选对比

| 库 | 用途 | 许可证 | 体积（量级） | 维护状态 | 风险 | 结论 |
|---|---|---|---|---|---|---|
| **手写 XLSX 读取** | XLSX | 本项目自有（AGPL） | **0** | 我们维护 | 需要自己处理 sharedStrings/styles/日期序列；~250 行 | ✅ **推荐** |
| `xlsx`（SheetJS CE，npm 上的） | XLSX | Apache-2.0 | ~7 MB 解包 | ⚠️ npm 上停在 **0.18.5（2022）**；新版只在其官方 CDN 发布 | ⚠️ npm 版本带**已知未修**的原型污染与 ReDoS 公告（CVE-2023-30533 / CVE-2024-22363，修复版本未发布到 npm）；从 CDN 安装会破坏 lockfile 与 CI 可复现性 | ❌ **不推荐**（引入前必须以 `npm audit` 与官方公告复核） |
| `exceljs` | XLSX | MIT | ~5 MB + 20 余个传递依赖 | 维护节奏慢（近年少更新） | 依赖树大、体积大；为了读一个 11 列的表不值 | ❌ 不推荐 |
| `fast-xml-parser` | 手写 XLSX 的替代（省掉 XML 词法） | MIT | ~40 KB | 活跃 | 又多一个依赖，收益仅省 ~80 行 | ⚪ 备选（若不想手写 XML） |
| **`pdfjs-dist`** | PDF 文本层 | **Apache-2.0**（Mozilla） | ~10–16 MB（含 `cmaps/` 与 `standard_fonts/`） | ✅ 活跃（Firefox 同源） | ①Node 下必须用 legacy 构建并**显式给 `cMapUrl` / `standardFontDataUrl`**，否则本样本这种子集字体解出乱码；②2024 年有过字体相关的任意代码执行公告（4.2.67 修复），**本项目只做文本提取、不渲染**，风险面小但仍须锁修复版本；③版本/公告以安装当日 `npm audit` 为准 | ✅ **推荐（若允许新 npm 依赖）** |
| `pdf-parse` | PDF 文本层 | MIT | 小 | ⚠️ 长期未更新，内部是很旧的 pdfjs | 对 CMap/新 PDF 支持弱，遇到本样本很可能乱码 | ❌ 不推荐 |
| `unpdf` | PDF（pdfjs 的服务端封装） | MIT | 中 | 较新、维护中 | 生态小、文档少；仍需验证 CMap | ⚪ 备选 |
| **Python `pdfminer.six`** | PDF 文本层 | MIT | ~5 MB（纯 Python） | ✅ 成熟稳定 | 需要自己按坐标排版（它给字符级坐标）；要在 sidecar 加一个**独立入口**（否则会连带加载 260 MB OCR 模型） | ✅ **推荐（若不允许新 npm 依赖）** |
| Python `pdfplumber` | PDF 文本 + 表格 | MIT | ~10 MB（含 `pypdfium2`） | ✅ 活跃 | 表格识别对这份「三列无表格线」的版式帮助有限；多一个较大的二进制依赖 | ⚪ 备选 |
| `iconv-lite` / `chardet` / `jschardet` | 编码检测 | MIT | 2.5 MB / 200 KB | 成熟 | **不需要**：Node 24 自带完整 ICU，`TextDecoder("gb18030")` 已实测可用；UTF-8 用 `{fatal:true}` 试解即可 | ❌ 不引入 |

> **关于 CVE 与体积的诚实说明**：上表的版本号、公告号与体积是**公开资料层面的判断**，本轮**没有联网复核、也没有安装**。
> 真正引入前必须做三件事：`npm audit` / `pip-audit` 跑一遍、锁到修复版本、用**三份真实样本 + 合成的恶意样本**各测一次。

### 6.3 推荐组合（按「允许新增什么」分档）

| 档 | 组合 | 新增依赖 | 适用 |
|---|---|---|---|
| **R1 零新增 npm 依赖** | 手写 XLSX + 内置 `TextDecoder` + **Python sidecar 装 `pdfminer.six`** | 0 个 npm 包；Python venv 多 ~5 MB | 最符合本项目「依赖要能审计」的口味；PDF 走已有的父子进程通道 |
| **R2 一个 npm 依赖** | 手写 XLSX + 内置 `TextDecoder` + `pdfjs-dist`（API 端） | 1 个 npm 包 | 实现最省事、调试最直观；镜像多 ~15 MB |
| **R3 不碰 PDF** | 先只做微信 + 支付宝 | 0 | 把 BOA 单独排期（见 §9 Phase 5） |

> 我倾向 **R1**：它与现有 OCR sidecar 的架构完全同构（同样的 stdin/stdout、同样的 base64、同样的不落盘），
> 而且**不给客户端 bundle 增加一个字节**。但 R2 的工程风险更低（不用动 Python 协议），
> **这条属于所有者决策（§10-③）**。

### 6.4 安全边界（无论选哪档都要守住）

1. **解析在服务端内存里完成**，不写临时文件、不缓存原始文件。
2. **不渲染 PDF**（只取文本）；不执行 XLSX 里的宏/公式（只读 `<v>`/`<t>` 文本）。
3. **zip bomb / XML 实体膨胀**：解压上限 + 条目数上限 + 禁用外部实体。
4. **超时**：单文件硬超时，避免 2 vCPU 被一份畸形文件拖死。
5. **错误信息不回显文件内容**（只回显行号与字段名）。
6. **不新增网络出口**：任何解析都不调用外部服务（这条与 OCR 的隐私理由一致）。

- **卡片视觉直接沿用 `/scan`**：`rounded-card border-2 border-dashed border-line bg-surface py-10`，选中态换成实线 + 品牌色边框。同一个 App 的「选择文件」应该长得一样。
- **拖拽只做桌面增强**：`onDragOver`（`preventDefault` + 高亮）、`onDrop`；移动端不显示拖拽文案。**拖拽不是唯一入口**（iOS Safari 对 `<input type=file>` 的 `display:none` 有坑，`/scan` 已经踩过，用 `sr-only` 而不是 `hidden`）。
- **文件名截断**：`min-w-0` + `truncate`，320 宽度下不换行、不撑破卡片。
- **「清除」与「更换」分开**：清除回到空卡片；更换重新打开选择器（同一个 `input`，选完 `event.target.value = ""` 才能重选同一文件——现有 `ImportPage` 已有这个处理）。
- **格式以检测结果为准**：如果扩展名是 `.xlsx` 但内容不是，显示「这个文件的格式认不出来」，并在选择阶段就拒绝，不等到上传后报错。

- **模板**：从「第二个主按钮」降级为轻链接（`text-link text-brand-dark`），点它仍然调 `fetchTemplate(bookId)`，文案说明「只有 Libevra 自己的模板，只填表头下的行」。

| 逐笔卡片 | 状态徽标（已识别/待核对/疑似重复/已排除）+ 日期时间 + 来源；金额 + 币种 + 方向；商户；分类/支付方式（带「系统建议」标记）；警告行 |

| 底部固定条 | `可导入 N 笔` + `确认导入`（`OcrImportBar` 的结构与安全区处理可以照搬）；`取消这次导入` |
| 对账提示（PDF） | 如果分区合计与结单合计不一致，顶部一条**常驻**警告，并在底部条上禁用「确认导入」直到用户确认差异 |

**完成页**：沿用 `ImportDoneView` 的三态（全部成功/部分成功/全失败）+ 现有 `Report` 的四个数字（文件行数/写入/跳过/导入编号）。**文案不要写「识别」**，写「导入」。

### 7.4 与 `/record`、`/scan` 的统一

三页共用一个骨架：`InnerPage`（标题 + 副标题 + 返回）→ **一个大卡片**→ 主按钮 → 次级文字链接。
标题句式统一为「动词 + 名词」：`语音记账` / `拍照记账`（现状 `/scan` 标题） / **`导入账单`**。

> ⚠️ 现状 `/import` 的标题是「导入历史账」，副标题是「用导出的文件或模板填写…」。V2 建议改成「导入账单」并把副标题换成
> 「微信、支付宝、银行结单都可以。先识别，核对后再写入。」——**这是文案变更，需所有者一句确认**（§10-⑩）。

### 7.6 返回 / 历史 / 不循环

现状（已读代码 + 测试）：

- `/import` 的头部「返回」是 `InnerPage` 的 `backMode = "history"`（默认），**深链/刷新**才回退到 `backTo`。
- `?from=nav` → `backTo = "/"`，并且**隐藏「← 返回导出」**。
- 账本设置来路 → `backTo = /books/:bookId/settings`，并显示目标横幅。

V2 必须保持的规则：

1. **核对页的「返回」= 回 `/import` 的上传态**（同一上下文），**不放「返回导出」**。
2. **`/export → /import` 的「← 返回导出」只在没有 `from=nav` 时出现**。否则 `/export → 导入 → 返回导出 → 导入` 形成环。
3. 完成页只留两个出口（`回到明细` / `再导入一个文件`），与 `ImportDoneView` 一致；**不加「返回」**。
4. 深链直接打开核对页（没有 `previewId`）→ 说「这次导入已经过期，请重新选择文件」，**不重定向**、不自动重放。

## 8. 重复检测与保存边界

### 8.1 现在的判重其实是两层，不要混

| 层 | 归属 | 作用 | V2 动不动 |
|---|---|---|---|
| **身份判重** | `/import` 路由 + 数据库唯一约束 `(bookId, sourceNamespace, sourceRef)` + 文件指纹 | 「这一行是不是已经在账本里」；**会跳过** | **不动**，只保证适配器给出**稳定且唯一**的 `sourceRef` |
| **内容判重** | S15-E2 核心（纯函数） | 「这两笔像不像同一笔」；**只提示，从不跳过** | **不改核心**，只新增一个服务端调用点 |

> 「42 笔全部重复跳过」只可能来自**第一层**。第二层永远只会「提示」，不会替你取消勾选（除非界面自己这么做）。

### 8.2 在 API 端复用 S15-E2 的兼容方案（不改核心）

**关键事实**：核心在 `packages/shared/src/duplicateDetection.ts`，是**纯函数**，`apps/api` 本来就依赖 `@libellum/shared`。
所以「服务端判重」**不需要新接口、不需要跨服务调用、不需要复制规则**，只要新增一个**适配层**：

```
候选（统一模型）                    ┐
                                 ├→ DuplicateCandidateFields → evaluateDuplicateCandidates(settings)
账本里时间窗口内的已有记录          ┘
```

四个对齐点（都必须显式处理，否则语义会悄悄变）：

1. **bookId**：两边统一取**目标账本**（这正是 E2 §1.4 对「账本导入」的既有约定）。
2. **时间**：候选要转成**带时区偏移的 ISO 8601**（`occurredAt` + `occurredAtPrecision`）。PDF 只有日期 → `precision: "day"`；支付宝/微信有秒 → `"second"`/`"minute"`。
   注意核心**拒绝**无偏移的时间戳（会把 `2026-10-21T18:03:00` 视为不可解析）。
3. **设置**：服务端没有用户偏好载体 → **由前端把 `DuplicateDetectionSettings` 随 preview 请求带上**，服务端用 `validateDuplicateDetectionSettings` 严格校验（不合法就 400，不静默回落），再用它调核心。
   这样「前端 OCR 看到的提示」与「服务端账单预览的提示」用的是**同一份设置、同一个函数**，语义一致，且**不需要迁移**。
4. **分类/支付方式**：核心只比 **ID**。候选在预览阶段的 `categoryId` 多数是 `null`（还没建议出来）→ 会落到「缺失不排除」，**这是核心的既定行为**，不要为了"看起来更严格"去填假 ID。

**性能**：不要全表比对。先用 SQL 粗筛（`bookId` + `kind` + `currency` + `occurredLocalDate` 在 `[最早-窗口, 最晚+窗口]` 内），把结果转成候选，再交给核心两两判断（核心自己还有「账本+方向+金额+币种」分桶）。108 行 × 一个月的记录，量级完全可控。

**红线**：不修改 `duplicateDetection.ts`、不改设置存储、不动 E2 已接入的两个前端入口、**不改唯一约束**。

### 8.3 「42 笔全部重复跳过」：只做诊断计划，不动去重保护

**这不是一个可以靠"放松去重"解决的问题**——去重保护是数据安全机制（AGENTS 明确禁止削弱）。建议按下面的顺序查，每步都有可判定的结果：

| # | 检查 | 结论指向 |
|---|---|---|
| 1 | 导入报告里 `rowCount / importedCount / skippedCount` 三者关系 | 全跳过 ⇔ `importedCount = 0 且 skippedCount = rowCount`。**先确认是"身份跳过"还是"解析出错被当成重复"** |
| 2 | 同一个文件的 sha256 是否已存在于 `ImportLog` | 若存在 → 这是**上次导入的幂等重放**，报告本应显示上次结果；如果显示「全部跳过」，说明是新文件但行身份命中 |
| 3 | 适配器写进 `sourceRef` 的值是否**互不相同** | 若 42 行拿到**同一个** `sourceRef`（例如把平台名/文件名当单号）→ 第 1 行写入、其余 41 行被"文件内已出现"跳过；若该值库里已有 → 42 行全跳过。**这是最可疑的一条** |
| 4 | `sourceRef` 是否带不可见字符 | 支付宝单号**每行都带尾部 `\t`**（实测 48/48）。若上次导入存了带 `\t` 的值、这次 strip 了（或反过来），身份就**不相等** → 表现为"重复导入"而不是"跳过"；反过来若两次都不 strip 则相等 → 正常跳过。**必须比对数据库里的原始值与这次解析值的字节** |
| 5 | 若 `sourceRef` 为空，是否 `fileId`（流水编号）命中 | 只有「Libevra 导出的文件再导回同一本账」才会这样，**这是正确行为**；此时应在报告里说清"这是你自己的导出" |
| 6 | 42 这个数字是不是"文件里的一段"（例如 48 行里的 42 行） | 若是 → 更像**行定位错位**（表头偏移一行，导致 42 行整体错配到另一批 ref）或**部分行的单号为空**（空 `sourceRef` 不参与判重，不会跳过 → 反过来排除这条） |
| 7 | 预览页的**默认勾选** | 如果预览把「疑似重复」默认设为不勾选，用户会看到"可导入 0 笔"——这是**界面语义**问题，不是去重问题。必须区分「服务端跳过」与「界面默认不选」 |
| 8 | 解析错误是否被归到「重复」类 | 检查 `warnings[]` 与 `errors[]` 的分类；**解析失败必须显示为"读不出来"，绝不能显示成"已存在"** |

> 诊断结论只能来自**数据库里的 `sourceRef` 实际值 + 这次的解析值 + `ImportLog` 记录**三者对比。
> 在这些证据拿到之前，**不改任何去重代码**。

### 8.4 保存边界（本轮明确不动）

- 不绕过 S14-D 的导入锁/撤销/最终确认（`apps/api/src/routes/ledgerImport.ts` 那套）；
- 不改 `Transaction` 唯一约束、不改 `idempotencyKey` 生成、不改逐行编号分配；
- 不做「自动删除/合并重复」；
- 关闭重复提醒仍然只是"不看提示"，不影响写入安全（E2 的既有语义）。
