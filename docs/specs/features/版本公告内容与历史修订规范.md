# 版本公告内容与历史修订规范

> 最后核对: `eb38be0` 上的公告整理工作区 / 2026-10-23。
> 本文定义公告写法与修订边界；页面与确认机制见 [S13-F](S13-F-软件更新与版本公告-设计决定.md)、[S13-G](S13-G-重大公告与协议确认-设计决定.md)。

## 1. 内容职责

公告记录一个正式版本具体增加、调整或修复了什么，不评价“更好用”“更省心”“更可靠”。使用用户能理解的产品名称及动作，必要时交代触发条件、改前行为和改后结果。小补丁可仅有两三项具体变化，不强行补栏目、问候或展望。

| 字段 | 要求 | 使用位置 |
|---|---|---|
| `version` | 原始版本号，独立保存，不从标题解析 | 运行版本判断、列表、详情 URL、相邻导航 |
| `title` | 简短、具体的功能主题；不机械重复品牌和版本 | 首页公告名称、列表标题、详情标题 |
| `summary` | 独立撰写的一句话概览，说明主要变化；不是正文首句截取 | 首页、近期、全部公告、详情导语 |
| `sections` | 完整正文，按真实内容使用“新增功能”“调整及优化”“问题修复”“注意事项”；无内容则省略 | 首页节选、详情全文 |
| `releasedAt` / `status` | 原始日期及发布状态独立保存；开发版本不能有正式日期 | 日期、排序、正式/开发筛选 |
| `major` | 保留历史分类，不能仅因整理文字而改为重大更新 | 历史分类；实际弹窗策略另由共享策略管理 |
| `revisedAt`（可选） | 历史内容整理日期，仅展示说明；不参与排序、更新判断或已读身份 | 详情页“按发布记录整理”说明 |

既有 `intro` / `closing` 仍兼容读取；不要求新公告增加与概览重复的导语、致谢或未来承诺。本轮不增数据库字段、接口、CMS 或迁移。

## 2. 事实核查

一项功能必须能关联到正式部署记录，并核对该次部署的源码或镜像来源。开发完成、本地验收、候选包、Git tag、提交日期都不能单独证明生产上线。证据不足时只保留可证实内容，在审阅报告中列出缺口。

核查顺序：正式部署报告与健康/资源记录 → 部署代码或标签指向的代码 → 阶段验收与版本日志。文档存在后补/矛盾时注明证据等级，不能把早期“未部署”或后续新增功能混入旧版。提交时间不是部署时间，部署时间也不是公告首次发表时间。

公告可能晚于功能上线：保留原版本、日期与 URL，在内部证据表分别记功能部署和公告补发。已部署但从未有独立公告的补丁，不伪造旧发表时间或为补齐号码自动新建一篇。

## 3. 安全及限制

- 明确识别草稿与真正入账、账本导入与账单文件导入、普通提醒与重大公告确认的区别。
- 对数据删除、撤销、恢复、权限、备份和账号安全，保留范围、条件、期限与失败后果。不能将“尝试撤销”改成“保证恢复”，不能以“安全处理”代替具体后果。
- 不将有限样本的识别准确率/延迟外推为普遍承诺，不将特定环境修复表述为“所有截图均可识别”。
- 若旧公告的重要承诺与能力冲突，保留原文和证据，列入所有者待确认清单；未经确认不悄悄改写为另一项承诺，也不自行发布更正公告。
- 不把法律确认机制当成正式法律文本已提供的证据。

## 4. 历史修订步骤

1. 保存整理前全文、日期、状态、重大标记和来源 commit；保留 Git 历史。
2. 逐条建立发布依据，再改标题、概览和正文；保留未证实事项清单。
3. 详情展示整理日期和说明；原版本号、原日期保持不变，不把旧公告重新列为“新发布”。
4. 保持普通历史与重大公告策略的事实一致，但不借普通文字整理改变已发表弹窗的身份或确认记录。已读公告不能因新标题/正文被当成未读。
5. 核对所有消费组件、开发构建区别、分页、相邻版本、直接刷新及返回；检查窄屏的标题换行、概览省略和点击范围。
6. 测试与审阅通过后交所有者决定是否发布。整理完成不等于已同步生产。

## 5. 本轮兼容决定

10 篇历史公告继续由 `apps/web/src/lib/updateAnnouncements.ts` 提供；不新增运行时数据源。原始快照只用于审阅和回归，不进入页面 bundle。普通历史没有单独的已读数据库标记，本轮不引入标记。

`packages/shared/src/consent.ts` 中已发表重大提示的标题、正文、`id`、`version`、`publishedAt` 及测试标记全部保留；服务端账号确认表、客户端旧版过滤规则也不改。阅读版与当时提示的措辞可以不同，但事实不能冲突。需要实质更正时，应单独决定更正说明与是否需要再次通知，不能挪用旧确认记录。
