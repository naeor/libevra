## 0. 一句话

**重复检测从此只有一套判定规则**：同账本、同方向、金额与币种完全相等、真实时间差在用户窗口内；
分类与支付方式默认在“双方都有值”时要求一致；结果只提示，不删除、不合并、不阻塞写入。
用户可以在**设置 → 记账偏好 → 重复交易检测**里开关提醒、调整窗口、关闭分类/支付方式匹配。

## 1. 权威规则（代码即规则）

### 1.1 判定顺序与结果含义

| # | 规则 | 通过条件 | 字段缺失时 | 字段不一致时 |
|---|---|---|---|---|
| 1 | `reminders` | 提醒开关为开 | — | 关闭 → 不检测（`suppressed`） |
| 2 | `book` | 双方 `bookId` 相同 | 缺账本 → 排除 `book_missing` | 排除 `book_mismatch` |
| 3 | `kind` | 收/支方向相同 | `unknown` → 排除 `kind_unknown` | 排除 `kind_mismatch` |
| 4 | `amount` | 整数最小单位完全相等 | `null` → 排除 `amount_missing`；非法 → `amount_invalid` | 排除 `amount_mismatch` |
| 5 | `currency` | 币种代码相同（去空白、转大写） | `null`/空 → 排除 `currency_missing` | 排除 `currency_mismatch` |
| 6 | `time` | 双方都有可解析时间 → 真实时间差 ≤ 窗口 | 双方同本地日期 → **缺失但不排除**；无任何日期/时间 → 排除 `time_missing` | 超窗 → `time_outside_window`；日期不同 → `date_mismatch` |
| 7 | `category` | 双方都有分类 ID 时相同 | 只有一方/双方都没有 → **缺失但不排除** | 排除 `category_mismatch` |
| 8 | `paymentMethod` | 双方都有支付方式 ID 时相同 | 同上 → **缺失但不排除** | 排除 `payment_method_mismatch` |

- **`matched`**：没有任何规则返回 `excluded`。字段缺失（`missing`）或设置关闭（`skipped`）都**不会**让 `matched` 变成 `false`。
- **`missing` 与 `mismatch` 分开**：`missingFields` 记录“没有证据”的字段；`mismatchedFields` 记录“有证据说明不是同一笔”的字段。
  `time_missing`、`amount_missing`、`currency_missing` 是“缺失导致的排除”，会同时出现在 `missingFields` 与 `exclusionCodes` 里。
- **`evidence` 不是概率**：`strong` = 没有缺失字段；`weak` = 有缺失字段但未被排除；`none` = 未命中。
  界面不得把它显示成“相似度/置信度”。

### 1.2 时间：真实时间差，不是 `HH:mm` 字符串

- 只接受**带显式时区偏移**的 ISO 8601 时间戳：`2026-10-21T18:03:00+08:00`、`2026-10-21T10:03:00.000Z`。
- 无偏移字符串（`2026-10-21T18:03:00`）在浏览器与 Node 里会被解释成不同时刻，因此**视为不可解析**，走本地日期的弱依据。
- 两个时间戳都有效时，比较 `|epoch 差| ≤ timeWindowSeconds`；因此跨分钟、跨日、跨时区都按同一基准计算。
  **23:59:30 与次日 00:00:20 在 60 秒窗口内会命中**（旧 OCR 实现要求日期字符串相同，这是有意的修正）。
- 时间精度 `"day"`（只有日期）**不**把中午 12:00 当真实时间；它只参与“同本地日期”的弱依据。
- 双方只有本地日期且相同 → `time` 记为 `missing`、不排除；日期不同 → `date_mismatch`；连日期都没有 → `time_missing`。
- 时区以**记录携带的偏移**为准；核心不读运行环境的时区。适配层负责把本地 `YYYY-MM-DD` + `HH:mm` 用设备时区换成带偏移的时间戳。

### 1.3 金额与币种

- 金额一律是**整数最小单位**（分；日元没有小数位）。核心不接受浮点元、不接受字符串金额、不做近似。
- 金额必须是**正的安全整数**；`null` 表示缺失，`NaN`/小数/0/负数/超大整数 → `amount_invalid`。
- 币种必须相同；只做 `trim().toUpperCase()` 规范化，**不做汇率折算**，也不引入汇率表。

### 1.4 分类与支付方式

- **只比较账本内 ID**，永远不比较显示名称。不同账本里碰巧同名（例如两边都叫“餐饮”）不会被视为相同。
- 账本导入是**跨账本**比较：适配层把来源分类/支付方式先翻译成目标账本的语义键
  （复用目标对象 → `target:<id>`；需要新建 → `new:<sourceId>`），再交给核心比较。这仍然是 ID 语义，不是名称。
- 默认开启；关闭后规则记为 `skipped`，不同分类/支付方式不再排除。
- “只有一方有值 → 不排除”是所有者明确要求：缺失不能被当成“不同”。

### 1.5 边界（硬约束）

- **只提示**：核心不写库、不删除、不合并、不覆盖，也不产生“是否允许写入”的结论。
- **不替代幂等**：关闭提醒后，同一次创建的 `idempotencyKey` 仍是固定 id，服务端唯一约束照常生效。
- **不替代来源身份去重**：CSV/账本导入的 `sourceRef` 去重、导入指纹、权限、离线同步都不经过本核心。
- **不跨账本**：不同 `bookId` 永不匹配。账本导入的“来源 vs 目标”是产品定义上的跨账本场景，
  适配层把双方 `bookId` 统一为目标账本——问的是“这笔来源记录写进目标账本后会不会重复”。
- **方向/业务类型**：普通收入与支出不互为重复；`unknown` 不猜。
  退款、转账、冲正目前没有可靠的结构化语义，本轮**不新增业务类型、不改数据模型**，
  只把“同方向同金额同时间”视为候选，复杂语义列为待决问题（见 §7）。

### 1.6 结果结构

`DuplicatePairResult` 包含：

| 字段 | 用途 |
|---|---|
| `pairKey` / `leftId` / `rightId` | 与左右顺序无关的稳定标识 |
| `matched` / `suppressed` | 是否命中；是否因总开关关闭而未检测 |
| `rules[]` | 每条规则的 `rule` / `outcome` / `code` / `fields` / `detail`，界面可展示依据 |
| `exclusionCodes[]` | 所有排除码；`matched` 为真时为空 |
| `missingFields[]` / `mismatchedFields[]` | 缺失 vs 不一致 |
| `timeDifferenceSeconds` | 真实时间差（秒，可能含小数）；无法计算为 `null` |
| `evidence` | `strong` / `weak` / `none`，**不是概率** |
| `reason` | 一句中文说明 |
| `settings` | 本次实际使用的设置副本 |
| `extensions` | **E3 预留**：`sourceTransactionIds`（本轮恒空）、`userConfirmedRelation`（本轮恒 `null`） |

批量函数 `evaluateDuplicateCandidates` 对每个组合调用同一个 `evaluateDuplicatePair`，只是先用
“账本 + 方向 + 金额 + 币种”分桶（这四项在任何设置下都必须相同），不会无条件 O(n²)。

## 2. 默认配置与校验

| 设置 | 默认 | 范围/规则 |
|---|---|---|
| `enabled` | `true` | 布尔；关闭只关闭业务层提示 |
| `timeWindowSeconds` | `60` | 整数，`1`–`2 592 000` 秒（30 天）；负数/0/小数/`NaN`/`Infinity` 全部拒绝 |
| `matchCategory` | `true` | 布尔 |
| `matchPaymentMethod` | `true` | 布尔 |

- **严格校验** `validateDuplicateDetectionSettings`：四个字段必须齐全且合法；**未知字段直接报错**
  （保存路径用它，避免“拼错键却以为保存成功”）。
- **宽松恢复** `recoverDuplicateDetectionSettings`：读取本地存储/旧数据时使用；合法字段保留，
  缺失/非法字段回落默认并记入 `usedDefaults`，未知字段忽略并报告；永不抛异常。
- 错误是结构化的 `{ field, code, message }`，`code` 包括 `not_object` / `unknown_field` / `missing` /
  `not_boolean` / `not_integer` / `below_minimum` / `above_maximum`。
- 恢复默认 = 四个字段全部取默认值，由设置页“恢复默认设置”按钮触发。

## 3. 用户设置与保存位置

### 3.1 入口与控件

**设置 → 记账偏好（`/settings/preferences`）→ 重复交易检测**。没有新增路由、没有改导航。
设置节复用现有设置页样式与 `InlineChoice`（内嵌选择，不用原生灰色下拉），新增一个与现有设计语言一致的
`SettingsToggle`（`role="switch"`、44px 触摸目标）。

- A. 重复交易提醒：默认开；关闭后规则区整体禁用但**保留原配置**，并明确写出“关闭重复提醒不影响数据安全保护”。
- B. 时间窗口：1 分钟 / 5 分钟 / 30 分钟 / 1 小时 / 1 天 / 自定义；自定义以**整数分钟**输入，
  范围 1–43200 分钟（30 天），非法输入给出具体中文错误，不静默回退。
- C. 分类匹配 / D. 支付方式匹配：默认开，说明“双方都有值时才要求一致”。
- E. 恢复默认设置：在提醒关闭时也可用。

### 3.2 存储（本轮为设备本地）

**服务端目前没有用户级偏好载体**：`PATCH /api/v1/auth/me` 只写 `User.defaultCurrency`，没有 JSON 偏好列；
本轮明确不做数据库迁移。因此第一轮采用 `localStorage`：

```
libellum.duplicate-detection.v1.account.<encodeURIComponent(userId)>
libellum.duplicate-detection.v1.guest
```

记录形状：`{ version: 1, settings: {...}, updatedAt: ISO }`。

- **按用户隔离**：键里带用户 ID；A 账号的设置不会被 B 账号读到。游客只有单独一个槽位。
- **版本**：`version` 不认识 → 使用默认值并提示，不猜测旧格式；未来改语义时必须升版本并写迁移。
- **损坏**：JSON 坏了/字段非法 → 默认值 + 结构化问题；合法字段仍保留，不抛异常。
- **账号切换/登出**：登出**不删除**账号设置（同账号重新登录仍保留）；切换账号读的是另一个键，不串值。
- **游客清理**：`clearGuestData()` 只删游客槽位，不碰正式账号；`clearAllDeviceData()` 的 `libellum` 前缀扫描
  会自动覆盖两类键。
- **局限（必须诚实）**：这是**设备本地设置，不跨设备同步**。换设备、清浏览器数据、换浏览器都会回到默认值。
- **未来迁移方式（E3+，需所有者批准迁移）**：在服务端增加用户偏好载体（例如 `User.preferences` JSON 或独立表），
  一次性读取本模块记录写回服务端，再以服务端为准；键名与 `version` 已为这一步预留。

## 7. 已知差异与待决问题（需要所有者确认）

### 7.1 本轮明确未做

无数据库迁移、无新表、无关系记忆、无全账本扫描、无自动删除/合并、无 AI 相似度、无后台任务、
无新业务类型、未改导航与设置结构、未重写 Python、未改 API 协议。

### 7.2 需要确认的规则变化

1. **标签不再作为账本导入的必要条件**（旧规则要求标签集合完全相同）。这是统一规则的直接结果，
   但会让导入核对页出现新的重复组（固定样本 3 → 5）。
2. **支付方式默认参与匹配**（旧规则完全不看）。映射到不同目标支付方式的两笔记录不再提示重复。
3. **缺失时间不排除**：双方只有同一天、没有可解析时间时，仍会以“弱证据”提示；
   完全没有时间依据（连本地日期都没有）才排除。是否改为“缺失时间一律不提示”需所有者确认。
4. **`transfer` 方向**：核心只按“同方向”比较，没有实现退款/冲正/转账的特殊语义。
   现有数据模型不能可靠表达这些关系，本轮只记录，不改模型。

### 7.3 API `POST /transactions/duplicates` 第一轮为何暂不迁移（历史）

- 请求只有 `occurredLocalDate` + `HH:mm`，**没有时区偏移、没有秒**；要计算真实时间差必须先扩协议
  （例如带 `utcOffsetMinutes` 或 ISO 时间戳），否则会把“服务器时区”混进用户账本。
- 现有语义是“空时间只与空时间匹配”，而统一核心对缺失时间的处理不同；直接替换会改变单笔拍照的提示行为。
- **2026-10-21 E4 后续**：请求 schema 已增加可选 `occurredAt` 与 `settings`；旧字段按每行 `occurredTz` 组成带偏移时刻、精度 `minute`，空时间保持 day 精度弱依据；路由已调用统一核心并读取 E3 关系抑制，旧响应 `{duplicates}` 保持兼容。相关回归见 `apps/api/test/ledger.test.ts` 与 `duplicateReview.test.ts`。

### 7.4 Python 旧去重实现（已删除）与统一规则的差异（历史）

Python 旧实现保持图内/跨图比较金额、币种、方向、日期、±60 秒、商户相似度与单号；不比较分类/支付方式；
对已有记录只比较金额/币种/方向/日期/±60 秒。**E4 已删除该实现及测试，不再参与产品路径。**
差异点（历史）：时间窗口不可配置、日期必须相同、没有分类/支付方式规则、时间窗口是常量。
当前所有入口只走 TS 统一核心；跨语言重复实现不再存在。
