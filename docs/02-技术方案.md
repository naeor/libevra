## 2. 数据流与一致性

本地负责快与可用；联网时服务器负责远端权威和备份。离线队列、缓存和业务数据库承担不同职责，不能以缓存缺失推断用户数据不存在。既有离线范围见[离线与同步](specs/product/离线与同步-设计决定.md)和[信息架构与共享离线范围](specs/product/S13-E-信息架构与共享离线范围-方案.md)。

### 交易写入与冲突

交易冲突按字段 base、wanted、服务器当前值与历史值判断；时间和简单版本大小不能作为自动覆盖依据。规则只定义在 [S8 冲突设计](specs/product/S8-冲突-设计决定.md)，执行入口为 `apps/api/src/lib/conflicts.ts` 和交易路由。幂等请求避免重复提交，软删除与相应事件避免旧设备复活已删除记录。冲突、权限与幂等属于独立判断，不互相替代。

### 工作台配置

分析工作台的个人配置不随共享账本同步，配置 CAS、离线待同步、导入导出及生命周期按[配置与分享 §11](specs/product/S17-工作台个人配置与布局分享-方案草案.md)。不要将交易字段冲突算法套用到配置文档。

### 财务分析与导入

金额以所属币种的最小单位整数存储和计算，不使用浮点累加，也不把所有币种都视为“分”（JPY 为零小数位）。解析、格式化与币种精度从 [money.ts](../packages/shared/src/money.ts)进入；Prisma 的 `amountCents` 名称不代表所有币种都乘以 100。

交易发生时刻、记账当地日期和系统创建/修改时间分别保存语义；不能用系统创建日期替代补记日期，也不能因界面语言或时区变化重新归属账目。字段以 [Transaction 模型](../prisma/schema.prisma)的 `occurredAt`、`occurredLocalDate`、`createdAt` 等为准。迁移历史金额、币种或日期须按对应契约与数据安全门禁处理，不从展示异常猜测并批量修正原始事实。

分析采用共享计算与展示分层，能力、筛选、折算口径从 [S17 总需求](specs/product/S17-模块化财务分析工作台-总需求规格.md)进入各权威专题。金额、币种、历史汇率和缺失数据标记不能仅在图表层修改。账单导入的解析、预览、确认、锁、分批任务及撤销分别按[导入 V2](specs/features/账单导入V2-实现说明.md)与[S14-D §13A–E](specs/features/S14-D-账本导入-设计草案.md)维护。

## 3. 界面、导航与设计系统

中央记账入口的原始目的，是让用户从主工作区方便地选择记账方式。它是记账工作模式入口，不是与明细/分析/账本/我的平级的普通 Tab；不能为页面腾空间，将它改成只直达手动记账而使截图、语音等入口失去可达性。具体入口数量、开合与导航呈现按现行页面和 [S19 设计系统](specs/design/S19-材质组件与动效设计系统.md)维护，不恢复早期“三张卡片”的数量约束。

`App.tsx` 定义路由入口；工作区由 `workspace/` 管理，S19 呈现层消费已接受的导航，不替代权限或导航语义。switchTab、objectExpand、enterMode、普通次级导航使用各自呈现器；规范及实验依赖见 [S19 设计系统](specs/design/S19-材质组件与动效设计系统.md)。

颜色由 CSS 语义 Token 和主题控制器提供；文字、布局与圆角由各设计规范维护。先查共享组件与 Gallery，不复制另一套材质系统。电脑端交互读取项目 desktop-ui skill；跨设备布局与所有者草图门禁从任务索引进入。

## 4. 安全、身份与生命周期

普通客户端只接收并展示当前用户有权看到且对其任务有用的数据。用户自己的操作历史可以有明确入口；不能把全站审计或他人的操作记录下发前端再靠隐藏控件保护。管理功能遵守独立权限范围，不因新增管理能力扩大普通接口的数据范围；具体授权仍以权限专题为准。

账号、账本、管理范围分别承担身份与授权职责；敏感权限表达式按 AGENTS 的修改边界处理。账号注销、归档、删除、恢复、关键事件与备份不能只看 UI 开关；从[权限决定](specs/product/管理员与权限边界-设计决定.md)及功能目录进入对应契约。密钥和真实数据留在本机或授权环境，不进入仓库。

## 5. 部署与恢复

服务器源码通过本地确认提交的 `git archive` 上传，不依赖服务器 Git 仓库。Web 为公网入口，API/数据库及 sidecar 按 Compose 隔离；relay 的身份与关键事件保护见运维专项。发布、备份和恢复均按[03 运维手册](03-运维手册.md)执行，不从早期部署研究复制命令。GitHub 推送不触发生产部署。

## 6. 多端与版本边界

Web、PWA、Android、iOS、自部署的阶段范围保留现行 S19–S26 路线。S23 目标具有真实 Android 原生能力，具体架构需评估，不预设简单套壳即可完成。免账号本地核心、原生本地存储与自部署发行是规划，不能写成已交付。

产品版本、Global Build ID、平台构建字段、发布和部署身份分别定义于[版本与兼容规范](specs/product/内部构建编号、产品版本与多端兼容规则.md)。协议、数据 schema 和能力协商独立判断兼容；文档提出的未来编号系统、支持范围和机器门禁尚未实施。正式上线后的版本形式尚待所有者决定。

## 7. 如何修改技术契约

先定位专题唯一来源，再核对代码与测试。接口或数据格式变化同步更新对应规格、迁移和兼容影响；版本记录只记录该次变更。修复实现偏差不重写正确规则；不能把未验收或未部署表述为已完成。维护流程见[文档维护规范](ops/文档维护规范.md)。


## 8. 原始目标与架构演进

早期目标是让家人跨设备方便记账，同时形成可开源、可学习和能解释工程取舍的项目。可用、离线可靠、金额正确、权限隔离、可备份恢复和可理解的工程结构，都是原目标的组成部分。后来扩展为长期多端产品，没有抹去这些起点；早期成本和工期估算不是今天的承诺。

| 决定 / 已形成的成果 | 当时要解决的问题与后续演进 |
|---|---|
| 2026-10-08 先做 Web / PWA | 用链接支持分居两地的家庭成员，减少早期安装与调试成本，也降低贡献者启动门槛。旧“原生只是备用壳”的选择已由 S23/S24 原生客户端规划取代；最初先交付 Web 的理由仍保留。 |
| 自建 API、共享领域层与关系型数据库 | 原来就希望掌握认证、财务规则、迁移和备份的完整链路，并能解释为什么这样设计；没有采用全部交给 BaaS 的路线。这一决定不是宣称其他技术不可用。 |
| S3 / S6 的金额、日期、幂等与可追溯性 | 真实账目不能因为币种精度、补记、超时重试或导入而改变事实；最小单位整数、日期语义、幂等键、来源编号与唯一约束共同承担不同职责。实现契约见 §2 和对应专题。 |
| S8 在上线前完成离线读写与冲突选择 | 离线涉及所有写路径，不能等功能都写完后再补。早期单会话限制不能满足手机与平板共同使用，改为多设备使用并完整处理字段冲突；离线拍照/录音排队方案被取消，不是尚待补齐的 S8 功能。 |
| S9 / S13 / S14 的账本与数据生命周期 | 从独立记账发展为共享角色、账号/账本职责分离、注销与恢复保护、游客本地记账及可撤销导入；“一个账号只用一本账”“永远不物理删除任何数据”等早期简化不覆盖后续专题契约。 |
| 品牌与多端方向 | Libellum 于 2026-10-14 更名为 Libevra，保留小账簿与开放记账的起点；品牌字符串迁移及有意保留的旧标识见[迁移记录](specs/product/Libevra品牌迁移记录.md)。S22–S25 扩展本地核心、原生端和自部署，不由旧 Web 选型否定。 |

原始命名候选、技术比较和取舍细节保留在下方历史原文；它们解释项目如何走到今天，不重新授权旧服务器操作、公开演示或公众发行。
