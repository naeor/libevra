## 1. 五分钟现状速查

```powershell
# 1) 站点活着吗（不需要 SSH）
curl.exe -s https://libevra.com/api/v1/health
# 期望：{"ok":true,...,"version":"<版本>","database":"up"}

# 2) 上服务器
ssh -i "$env:USERPROFILE\.ssh\libevra_server" ubuntu@43.161.227.152
```

在服务器上：

```bash
cd /srv/libevra/deploy
DC="sudo docker compose -f docker-compose.prod.yml"

$DC ps                                   # 基础容器是否 running/healthy
cat .last-deployed                       # 上一次成功发布的版本号
sudo systemctl list-timers 'libevra-*'   # 五个定时器的下次执行时间
sudo journalctl -u libevra-backup.service -n 30 --no-pager   # 最近一次备份日志
```

**判断顺序**：`/health` 的 `version` 与 `database=up` → 站点活着；`$DC ps` 正常 → 进程层没问题；`.last-deployed` 与 STATUS 一致 → 版本一致。

> ⚠️ 本手册**不写"现在是哪个版本"**，只写"怎么查"。现状永远以 [STATUS.md](STATUS.md) 与 `/health` 为准。

## 2. 生产架构（以 compose 文件为准）

```
                    Internet
                        │ 80 / 443 / 443-udp（唯一对外端口）
                ┌───────▼────────┐
                │ web (Caddy)    │  TLS、静态前端、反代 /api
                └───────┬────────┘
                        │ internal 网络（bridge）
        ┌───────────────┼────────────────────┐
  ┌─────▼─────┐   ┌─────▼─────┐      ┌───────▼────────┐
  │ api       │   │ db        │      │ critical-relay │ （可选 overlay）
  │ Fastify   │   │ postgres17│      │ 只写 COS 的旁路 │
  └───────────┘   └───────────┘      └────────────────┘
        ▲
  ┌─────┴─────┐
  │ migrate   │  跑完退出；api 等它成功才启动
  └───────────┘
```

| 服务 | 构建 | 端口 | 卷 | 说明 |
|---|---|---|---|---|
| **db** | `postgres:17` | **无端口**（仅 internal 网络可达） | `db-data` → `/var/lib/postgresql/data` | 健康检查 `pg_isready`；`POSTGRES_INITDB_ARGS` 固定 UTF8 + locale=C，保证恢复后排序一致 |
| **migrate** | `deploy/Dockerfile.api` | 无 | — | `pnpm db:deploy`，`restart: "no"`，跑完退出 |
| **api** | `deploy/Dockerfile.api` | **无端口**（只被 Caddy 反代） | `api-data` → `/data`（whisper 模型约 488 MB + 上传暂存） | `env_file: .env`；等 db healthy + migrate 成功才启动 |
| **web** | `deploy/Dockerfile.web`（Caddy） | **80 / 443 / 443·udp** | `caddy-data`（证书与 ACME 账户）、`caddy-config` | 启动时由 `web-entrypoint.sh` 渲染 Caddyfile 模板；域名来自 `LIBEVRA_DOMAIN` |
| **critical-relay** | `deploy/Dockerfile.api` | 无 | — | **独立 compose overlay**：`critical-events-relay.compose.yml`；`pnpm --filter @libellum/api critical:relay`；`no-new-privileges`；healthcheck 关闭（健康看数据库心跳） |

- 卷：`db-data`、`api-data`、`caddy-data`、`caddy-config`。`docker compose down` 不删卷；**`down -v` 会删掉全部账目**。
- 网络：只有一个 `internal`（bridge）。**数据库与 API 都不暴露公网端口**，因此项目里没有 CORS 配置。
- `critical-relay` 持有 **COS 写身份**；API 进程本身没有 COS 凭据。恢复用的**只读身份**在离线介质 `deploy/.critical-events-restore.env`，**不放在服务器**。

### relay 为什么要单独起

```bash
# 带 relay 的生产栈（S13-I 关键事件保护开启时）
sudo docker compose -f docker-compose.prod.yml -f critical-events-relay.compose.yml up -d
```

业务事务成功后 API 立即返回，relay 异步把**加密不可变**对象 PUT 到 COS 并重试。COS/relay 故障**不会**让已完成的业务返回 503；保护状态由 `critical:status` 与 `libevra-critical-health` 定时器观察。详见 [S13-I 异地关键状态登记簿](ops/S13-I-异地关键状态登记簿-设计决定.md) 与 [生产接入清单](ops/S13-I-生产接入清单与未来管理接口.md)。

## 3. 日常操作

| 想做什么 | 命令 |
|---|---|
| 看某服务日志 | `$DC logs -f --tail 200 api`（或 `web` / `db`）；查看 `critical-relay` 前须在 Compose 参数中加入实际使用的 relay/release overlay，只有 base 文件时没有该服务 |
| 重启 API | `$DC restart api`（**不要** `down` 整个栈） |
| 进数据库 shell | `$DC exec -T db psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"` |
| 看管理员名单 | `$DC exec -T api pnpm admin:list` |
| 生成邀请码 | 按[日常运维速查](ops/运维-02-日常速查.md)的步骤（**生产写操作，需授权**） |
| 看备份状态 | 查 `backup_logs` 表最近 5 行（见 §6.2） |
| 看保护状态 | `$DC exec -T api pnpm --filter @libellum/api critical:status` |
| 手动跑一次备份 | `cd /srv/libevra/deploy && ./backup-all.sh` |
| 看定时器 | `sudo systemctl list-timers 'libevra-*'` |

> ⚠️ `admin:grant` / `admin:allow` / `admin:revoke` / `admin:disallow`、建邀请码、开放注册，**都属于必须先问所有者的操作**（AGENTS §5）。

## 4. 发布一个新版本

> **GitHub 更新 ≠ 生产更新。** push 只到 GitHub；上线必须有人在服务器上执行（ADR-037）。

产品版本、构建编号、平台发布与实例部署的身份关系见[版本与多端兼容规格](specs/product/内部构建编号、产品版本与多端兼容规则.md)。全局编号登记与自动兼容门禁尚属规划；现阶段仍以源码 commit、归档/镜像摘要、现行 changelog 与实际部署记录追溯，不补造 Build ID。

### 4.1 前置

1. 目标产品版本已按现行规则确定（`packages/shared/src/version.ts` 的 `APP_VERSION`），[STATUS](STATUS.md) 指向的现行 changelog 有对应条目；发布记录固定完整源码 commit、源码归档校验值及实际镜像/资源身份，不能仅凭版本号认定产物一致。
2. 按 [AGENTS §6.1](../AGENTS.md)完成发布前验收检查及本次迁移/兼容专项，记录实际结果；不因已有同产品版本的测试而跳过不同构建输入的必要验证。
3. **所有者当次授权**发布。
4. 代码已按下述归档流程传到服务器；`/srv/libevra` 不是 Git clone。

### 4.1.1 归档准备与安装边界

在本机确认完整 commit 和验收结果，用 `git archive --format=tar -o <本机归档路径> <完整commit>` 生成源码包，计算 SHA-256；记录目标版本、源码 commit、归档摘要及拟部署环境。得到当次上传/部署授权后才传输，并在服务器暂存位置核对摘要。

安装前保留现有源码/镜像恢复入口、配置属主和权限；秘密配置、数据卷、备份及运行状态不能随源码覆盖。解包前后运行备份权限预检查；必要脚本与 helper 成套更新。具体维护窗口、暂存与切换方案随当次发布记录确认，不从历史记录继承批准。通过来源、配置与备份检查后才执行 §4.2。

### 4.2 执行

```bash
cd /srv/libevra/deploy
./deploy.sh --version X.Y.Z            # 完整流程
./deploy.sh --version X.Y.Z --no-build # 镜像已构建过
```

`deploy.sh` 依次做（顺序即 compose 的依赖顺序）：

| 步 | 动作 | 失败时 |
|---|---|---|
| 1 | 读 `.last-deployed` 记下上一版，供回滚 | — |
| 2 | 存在 Git 元数据时检查工作区；生产归档目录没有 `.git` 时该检查跳过，发布前须在来源工作区固定 commit 并核对归档摘要 | 来源/摘要未验证时由发布流程阻断，不能把跳过 Git 检查当作已验证 |
| 3 | **发布前自动备份** `./backup.sh --keep 7` | 中止（没备份不发布） |
| 4 | `compose build` | 中止 |
| 5 | `compose up -d --remove-orphans`：db → migrate（跑完退出）→ api → web | 中止 |
| 6 | API 健康检查（容器内 `fetch /api/v1/health`，30 次 ×2s） | 走回滚提示 |
| 7 | Web 健康检查（容器内 `curl --resolve $LIBEVRA_DOMAIN:443:127.0.0.1 /healthz`） | 走回滚提示 |
| 8 | 写 `.last-deployed`，打印两条**人工确认** | — |

> 第 7 步为什么绕：Caddy 会把 HTTP 308 跳到 HTTPS，而 `https://127.0.0.1` 的 SNI 是 IP、证书对不上，直接请求必然失败——旧检查曾因此把正常发布误判为失败。现在在容器内把真实域名 `--resolve` 到回环、只接受容器内 Caddy 的证书，不经过公网 DNS。

### 4.3 发布后必须人工确认（脚本不会替你做）

1. 浏览器打开 <https://libevra.com>，**登录并记一笔**。
2. 「账户 → 软件更新」显示的版本号 = 刚发布的版本。
3. `curl.exe -s https://libevra.com/api/v1/health` 的 `version` 正确、`database=up`。
4. 更新 [STATUS.md](STATUS.md) 的版本 / 部署 commit / 迁移数 / 最后核对时间。

## 5. 回滚与"迁移只向前"

**应用回滚不会回滚数据库。** 迁移只向前：如果新迁移删了列，退回旧镜像也换不回那列。

| 情况 | 做法 |
|---|---|
| **只改代码**（无 schema 变更） | 先验证旧产物与当前数据/协议兼容；经当次批准，在本地从已固定的上一 commit 生成并校验源码归档，再按原归档部署流程上传/发布，或使用已核验的旧镜像。生产目录不是 Git clone，不在服务器执行 `git checkout`；保留秘密配置与数据卷 |
| **改了 schema** | 先判定旧代码对新 schema 和关键状态的兼容性；不兼容时评审前向修复或备份恢复。整库恢复会丢失备份点后的写入，必须先保存故障现场、评估增量与离线操作、验证恢复备份并取得当次批准，不能自动恢复来配合应用降级 |
| **旧版本要连新库** | 必须先过 [S13-I 真实环境验收 §12](ops/S13-I-真实环境验收与生产接入计划.md) 的兼容性门槛（schema/迁移版本、权限、归档/弃置限制、关键事件写入）；**未通过不得启动** |

发布失败时 `deploy.sh` **不会自动回滚**——它打印回滚命令并保持当前状态，要求人工判断。

## 6. 备份、恢复与灾备

### 6.1 五层保护

| 层 | 脚本 | 做什么 |
|---|---|---|
| 1. 每日业务备份 | `backup-all.sh`（03:00） | 本地 dump → **隔离恢复演练**（`verify-dump.sh`）→ 加密 → 上传 COS → 远端元数据校验 → 写 `backup_logs` → 心跳 → 失败邮件告警 |
| 2. 可恢复性验证 | `verify-dump.sh` | 把 dump 导进**隔离临时库**验证，绝不碰现有库 |
| 3. 异地副本与演练 | `offsite-fetch.sh` / `monthly-offsite-drill.sh` | 取回并解密异地备份；**月度演练**验证"能取回、能解密、能恢复" |
| 4. 关键状态检查点 | `critical-events-backup-all.sh`（04:00，`CRITICAL_BACKUP_OFFSITE=cos`） | 精确检查点备份 + 独立异地副本（**不替代**第 1 层） |
| 5. 灾难恢复 | `restore.sh` / `emergency-raw-restore.sh` / `critical-events-fetch-backup.sh` | 整库恢复；应急 RAW 恢复；取回检查点备份对并校验 |

- 告警：`alert-mail.sh`（Resend HTTPS API，只用 curl/sed/awk，不依赖 python）。
- 外部心跳：`heartbeat.sh`（Dead Man's Switch）——"什么都没发生"和"一切都好"看起来一样，必须由外部定时器证明备份任务真的跑过。
- 保护层健康：`critical-events-health.sh`（每 5 分钟）；导入健康：`import-health.sh`（每 15 分钟，**只读**，不重试/不确认/不解锁）。

### 6.2 常用命令

```bash
cd /srv/libevra/deploy
./backup-all.sh                 # 完整备份（推荐，含异地与状态写入）
./backup.sh --keep 7            # 本地备份（发布流程内部调用）
./verify-dump.sh <dump文件>      # 只验证"能不能恢复"，不碰现有库
./restore.sh <备份文件>          # 整库恢复（**必须先获授权**）

# 备份状态（最近 5 次）
sudo docker compose -f docker-compose.prod.yml exec -T db \
  psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" \
  -c "select created_at, ok, file_ref, note from backup_logs order by created_at desc limit 5"
```

异地取回和月度演练在所有者电脑或隔离恢复机使用独立恢复身份，不能接着上面的生产终端命令直接执行；按脚本说明配置恢复环境后，使用 `./offsite-fetch.sh --latest`（或 `--ref <ref>`）和 `./monthly-offsite-drill.sh`。取回与上传同样遵守当次网络操作授权。

> ⚠️ `restore.sh` / `emergency-raw-restore.sh` 会**覆盖生产库**。执行前必须：所有者授权 + 当前库再备份一次 + 明确恢复到哪个时间点。

### 6.3 定时任务（服务器 systemd，时区 Asia/Hong_Kong）

| 定时器 | 时间 | 脚本 | 身份 |
|---|---|---|---|
| `libevra-backup.timer` | 每日 03:00 | `backup-all.sh` | ubuntu |
| `libevra-lifecycle.timer` | 每日 03:30 | `lifecycle:purge`（账本归档 365 天墓碑清理） | ubuntu |
| `libevra-critical-backup.timer` | 每日 04:00（随机 10 分钟） | `critical-events-backup-all.sh` | root |

## 7. 环境变量（`deploy/.env`，永不入库）

模板：`deploy/.env.production.example`（**没有任何真实口令**）。

| 变量 | 说明 |
|---|---|
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | 数据库；compose 用 `${VAR:?}` 强制要求设置 |
| `DATABASE_URL` | 主机名必须是 **`db`**（compose 服务名），口令与上面一致 |
| `SESSION_SECRET` | Compose 要求设置的兼容占位变量；API 会话使用随机 token（`auth/session.ts`），不把该变量描述为实际会话签名机制；配置仍按秘密保护 |
| `LIBEVRA_DOMAIN` / `WEB_ORIGIN` | 域名两处必须一致；Caddy 用它申请证书，API 用它做同源校验 |
| `ACME_EMAIL` | Let's Encrypt 通知邮箱；可空（`web-entrypoint.sh` 处理空值） |
| `REGISTRATION_MODE` | 生产必须是 **`invite`**；`open` 不要用 |
| `LIBELLUM_WHISPER_MODEL` / `_THREADS` | 镜像与配置示例默认 `base` / `2`，模型缓存到 `api-data`；实际生产配置与验收状态见 STATUS，切换模型需按维护授权执行 |
| `CRITICAL_EVENTS_MODE` / `CRITICAL_EVENTS_RELAY_TIMEOUT_MS` | relay 模式与超时 |
| `CRITICAL_BACKUP_OFFSITE` / `CRITICAL_BACKUP_DIR` / `CRITICAL_BACKUP_LOCAL_KEEP_DAYS` | 检查点备份的异地与保留 |
| `DEMO_USERNAME` / `DEMO_PASSWORD` | 配置模板的占位项，应用不读取；设置它们不会自动创建演示账号。演示功能是否启用仍待所有者决定 |

**另有三份不放在 `.env` 里的凭据文件**：

| 文件 | 位置 | 用途 |
|---|---|---|
| `deploy/.critical-events-key.env` | 服务器（mode 600） | 事件加密密钥 |
| `deploy/.critical-events-relay.env` | 服务器（mode 600） | relay 的 COS **写**身份 |
| `deploy/.critical-events-restore.env` | **离线介质，不放服务器** | 恢复用的 COS **只读**身份 |

## 8. 禁止清单（会造成不可逆损失）

1. `docker compose down -v` —— 删 `db-data`，**全部账目**
2. `prisma migrate reset` —— 删库重建
3. `docker volume rm` 任何项目卷；`docker system prune --volumes`
4. 手工 `DELETE` / `DROP` 生产表
5. 把 `.env`、口令、邀请码、私钥、恢复码提交进仓库 —— **仓库是公开的**
6. `force push` 或重写共享历史
7. 在服务器上直接改代码而不补回仓库 —— 会造成"服务器比仓库新"（已发生过）
8. 把未经验证的版本当生产发布
9. **未经所有者当次授权**做任何网络上传/发布/密钥变更（AGENTS §4 铁律）

## 9. 故障排查

| 症状 | 先查什么 | 常见原因 |
|---|---|---|
| 站点 502 / 打不开 | `$DC ps`、`$DC logs --tail 100 web api` | api 未 healthy；Caddy 证书问题（看 web 日志） |
| `/health` 的 `database` 不是 `up` | `$DC ps db`、`$DC logs db` | db 容器重启；磁盘满 |
| 发布后版本号没变 | `cat .last-deployed`、`apps/web` 构建产物、浏览器/PWA 缓存 | 镜像未重建；`--no-build` 用了旧镜像；PWA 缓存 |
| 备份没跑 / 心跳超时 | `journalctl -u libevra-backup.service`、`backup_logs` 表、心跳是否成功 | timer 未启用；脚本失败；告警邮件未配 |
| 语音很慢 | api 日志里的 whisper 计时、`LIBELLUM_WHISPER_MODEL` | CPU 争用；模型档位（small 明显慢于 base，见 S15-A 基线） |
| 导入卡住 / `undo_failed` 增长 | `./import-health.sh`（只读）、api 日志 | 见 S14 导入设计 §13；**不要手工解锁/重试**，先查明原因 |
| 保护链异常（critical events） | `critical:status`、`./critical-events-health.sh`、relay 日志 | relay 未启动；COS 凭据/网络；事件密钥不匹配 |

**不确定时**：先看 `deploy/README.md`（最详细）与对应 `ops/` 设计决定；仍不确定就**停下来问所有者**。

## 12. 部署脚本已知限制（需独立修正）

`deploy.sh` 只有检测到 Git 仓库才检查脏工作区；归档部署必须在本地提交、打包、传输与安装环节核对来源和哈希。脚本不会自动回滚；其旧提示中的服务器 `git checkout` 不适用于现有归档部署，也不能授权恢复整库。

必要脚本修正单独安排：统一脚本头部与失败提示；明确产物来源校验和归档回滚入口。未完成前按本文 §4–§5 操作，不执行脚本打印的旧 Git 命令。此限制登记不授权上传、生产恢复或脚本重构。
