> > 毕竟**他们要改所有的东西**，如果先做了，那后面做开发还得多一步改颜色。"
>
> **新排序的三条原则**：
> 1. **动数据的往前**——改表结构、改数据模型、加抓取任务的越早越好，越晚越要迁移真实数据；
> 2. **横切的往后**——i18n 与主题色要**重写已经写完的一切**，放最后一次性做完；
> 3. **需要所有者出钱/实名/真机的往前**——好让等待期与开发并行。
>
> 另外两处结构性变化：**离线优先从"第二批"提前到上线之前**（它动的是所有写路径，
> 之后每个新功能都要兼容离线），**协作也提前到上线之前**（所有者要求家人用上时就能一起记账）。

#### S15-A · 语音识别与记账字段解析

**目标**：把语音记账做到适合日常使用的速度与可靠性，同时保持金额、日期、币种、收支方向正确；语音转写与字段解析继续保持模块分离。

**已确认决定（所有者 2026-10-20）**

1. **multilingual base 作为下一生产版本的目标默认模型**，替代当前 small；small 保留为可回退方案。
2. 当前 2 vCPU 服务器实测 base 约 6.7 秒、small 约 25.5 秒（4.7 秒合成语音，2026-10-20 基线）；base 更接近当前交互需求，但**尚未证明达到最终 5 秒目标**。
3. 不要求生产同时常驻两个模型；切换方式、预热/懒加载、回退时的模型文件与内存占用在 S15-A 设计阶段确定。
4. **不引入“CPU 超过某百分比自动切 small”的机制**——small 更耗算力，高负载时自动切换通常适得其反。
5. **限制语音识别并发、合理排队与超时**，避免语音推理拖垮正常记账 API；不得在生产主机做高负载并发压测。
6. 保留 S14-V 已开发但未发布的保守 VAD、静音短路、子进程恢复、错误反馈和分段计时成果；这些成果只作为候选，不自动视为已验收。
7. 修复 `parseSpokenEntry` 把日期数字误当金额的问题；例如“10 月 8 日……42 元五角”应提取 `42.5`，而不是 `5`。修复必须有独立测试，且不改变无关解析语义。
8. 优先保证**金额、日期、币种、收支方向**正确；商户名称允许用户修正，但必须降低错误概率，不能因此放弃准确率验收。
9. 测试常见中文口语、数字歧义、背景噪声、短语音、长语音、静音，以及**适当英语语音**；不得只凭少量合成语音宣称生产准确率达标。
10. 保持语音转写与字段解析独立；不因识别不确定而猜测金额，不自动入账。
11. **暂不升级服务器**；如果后续性能确实无法满足要求，再评估更高规格的云服务器（所有者 2026-10-20）。

- 另需覆盖：收入、退款、跨币种、背景噪声、静音、超时

> 验收时比较：**识别时间、关键字段（金额／日期／币种／收支方向）正确性、CPU 与内存开销**。
> 5 秒以内的体验是**优化目标**，不是未经实测就必须实现的硬指标。

**验收标准（草案；数字阈值须所有者确认后写入正式验收）**

1. **功能**：语音转文字后金额/日期/币种/收支方向进入核对草稿；未经用户确认绝不写入正式账本；失败/静音/无权限/超时都有清楚反馈。
2. **延迟目标**：3–5 秒中文语音在目标生产环境（2 vCPU）端到端 p50 **争取 ≤5 秒**；base 当前隔离基线约 6.7 秒，未达标前不得宣称达到。必须分别报告首请求、warm、静音和不同长度；不得以本地机器数据代替服务器数据。
3. **准确率**：在经所有者确认的 held-out 语料上，金额、日期、币种、收支方向达到所有者确认的阈值；商户名称单独统计、可编辑、不得伪造；不得只用 1–2 条合成音频。
4. **字段解析**：日期中的数字不会被当成金额；缺失字段保持缺失/待确认；不猜测金额；关键字段测试覆盖数字歧义（如十四/四十、十五/五十）、小数、币种、退款/收入方向。
5. **安全与稳定**：并发有界、排队/超时有界；语音失败不拖垮正常 API；不向第三方 AI API 发送音频；音频不落盘；不自动入账；small 回退可执行。
6. **测试**：合成 + 经同意真人语音混合；噪声/静音/数字歧义/短句/长句；失败与重试；生产部署前在隔离环境验证。
7. **生产发布前**：完成候选镜像、回滚方案、数据/配置不变性说明，并取得所有者单独授权。

#### S15-B · OCR 多笔交易与批量整理

**目标**：让 OCR 能处理“一张图片一笔”“一张图片多笔”“多张图片多笔”以及跨图片重复，并提供统一的「概览页面」完成批量核对；不把图片数量当交易数量，不在用户确认前写入账本。

**正式设计方向**：见 [`S15-B-OCR多笔交易与概览页面-设计方向.md`](specs/features/S15-B-OCR%E5%A4%9A%E7%AC%94%E4%BA%A4%E6%98%93%E4%B8%8E%E6%A6%82%E8%A7%88%E9%A1%B5%E9%9D%A2-%E8%AE%BE%E8%AE%A1%E6%96%B9%E5%90%91.md)。本节只列阶段任务与验收边界；UI 细节、版式、阈值与技术路线以该设计方向和所有者拍板为准。

**核心原则**

- 先判断页面/版式类型，再切分交易；无法可靠判断时让用户选择，不擅自认定数量。
- 保留现有：单笔详情核对、多张凭证同一笔合并、多张分别识别的选择。
- 多张图片中的一张仍可包含多笔；跨图片/滚动截图重复必须提示。
- 「概览页面」是**展示、选择、核对**入口，不直接做字段编辑；点击进入详情修改，返回同步。
- 无问题交易不要求逐笔点击；有疑问/缺失/冲突/疑似重复才重点核对；最终统一确认。
- 没有识别出的字段显示“未填写/待确认”，不伪造默认值；来源平台、支付方式、账户、商户不能混成一个字段。
- 即使系统预选，最终写入仍由用户确认；不得直接入账。
- 复用概览的视觉/列表/选择/核对体验，但**不强行复用保存逻辑**；S14 导入任务、锁、撤销、最终确认机制不得绕过。
- 优先在 RapidOCR 上扩展；未经评估不引入大型云端 AI；真实付款截图默认不发第三方、默认不保存。

**验收标准**

- 每条关键路径有明确步骤、预期、实际、证据；失败项不写成通过；

### R1 · 局域网用户发现（候选研究 · **暂缓**）

**结论：暂缓，不排期，不作为上线硬阻塞。**

| 理由 | 说明 |
|---|---|
| **Web/PWA 没有可靠统一的发现能力** | 浏览器不暴露 mDNS/Bonjour，网页不能主动扫描局域网；WebRTC 需要信令与权限，且它不是"发现" |
| **权限限制** | 设备可见性、网络权限、企业/校园网隔离都会让"能看到"变成偶然 |
| **可见 ≠ 可信** | 同网段出现一个设备，不等于它是谁的、能不能共享账本；信任仍要一次明确邀请 |
| **复杂度高** | 发现、配对、信任、撤销、跨平台差异，每一层都是新面 |
| **S14 范围已经够大** | 游客 / 公开注册 / 邀请额度已经占满准入这一层，不能同时塞发现 |

**当前替代**：**二维码 / 邀请链接 / 短时配对码**——都是**显式、可撤销、可审计**的。
**未来方向**：如果 R2 的结论是"需要原生能力"，再研究原生 **mDNS/Bonjour**
（iOS 需要 `NSLocalNetworkUsageDescription` 与 Bonjour 服务声明；Android 用 `NsdManager`）——
**它是原生客户端的能力，不是 Web 的**。

**明确不做**：本轮不实现、不建表、不加权限、不改分享链接。

### R2 · 移动客户端与本地数据可靠性评估（研究 · **只评估，不迁移**）

**初步结论（待正式评估报告）**：**A 继续 Web/PWA 仍是基线**；
B Capacitor 是"要应用商店 / 本地通知 / 更强文件能力"时**成本最低的增量**；
C/D 只在"必须原生且愿意承担双端维护"时才考虑。**不要求原生客户端完成才能上线。**

| 方案 | 是什么 | 初判 |
|---|---|---|
| **A 继续 Web/PWA** | 现状：React SPA + Service Worker + IndexedDB | 零迁移；**iOS 通知 / 后台受限是真实短板** |
| **B Capacitor 打包** | 现有 Web 代码套原生壳 + 插件 | **改动最小**；**仍是 WebView，不等于完整原生能力** |
| **C React Native** | 重写 UI 与数据层（可复用 shared 逻辑 / API） | 成本高；**离线 / 同步逻辑要重做一遍** |
| **D 原生双端** | Swift / Kotlin 各写一套 | 成本最高；双端长期维护；与"一个人维护"冲突 |

**12 个评估维度**（详细对照在 S14 设计要点附录 B）：

1. 代码复用与要改的模块
2. **本地持久化**（IndexedDB / SQLite / 私有目录；**不把浏览器存储等同临时缓存**，**不承诺原生绝不丢数据**）
3. 离线与恢复同步
4. 后台限制与后台同步可靠性
5. 设备能力（文件 / 图片 / OCR / 语音 / 相机 / 通知）
6. iOS Safari/PWA 与 Android/打包的差异
7. 多设备协作与游客迁移
8. 安全与设备密钥 / 备份 / 隐私
9. 开发、测试、维护成本与长期债
10. APK 分发更新与 iOS 签名 / Apple Developer / TestFlight / App Store
11. 是否先 Android 再 iOS
12. **哪些限制是 Web 真无法解决，哪些只是当前实现不足**

**⚠️ 三条必须写进结论的**：

- **WebView 不等于完整原生能力**（Capacitor 也受 WKWebView / Chromium 的限制）；
- **不承诺"原生绝不会丢数据"**——任何本地存储都可能因卸载、系统清理、设备损坏而丢；
- **先分清"Web 真做不到"与"我们没做好"**：通知 / 后台执行 / 局域网发现是前者；
  相机、文件、语音、离线读写大多属于后者或已有可用方案。

**明确不做**：本轮**不迁移框架、不出 APK、不买 Apple Developer、不改存储层**。

### D1 · 版本公告与更新日志机制（已落地为静态公告；历史设计材料）

**⚠️ 先分清四件事**（现在经常被混成一件）：

| 层 | 是什么 | 要不要公告 |
|---|---|---|
| **代码提交** | 每次 `git commit` / PR | ❌ 不公告 |
| **开发版本** | 本地 / 测试构建、内部试用 | ❌ 不公告 |
| **生产部署** | `deploy.sh --version X.Y.Z` | ⚠️ 只在面向用户的发布时公告 |
| **正式发布** | 用户能感知的新功能 / 规则变化 | ✅ 写更新日志；重要改动一次性提示 |

**机制（初步设计，优先静态公告文件）**

- **技术记录 → 用户可读更新日志**：`版本记录` 继续做开发者记录；
  **另维护一份用户可读的静态公告文件**（随 Web 构建发布，**不新增 DB、不新增后台、不新增部署步骤**）。
- **流程**：**GitHub 技术版本记录 → 整理成用户可读条目 → 随构建发布 → 必要时应用内提示**。
- **展示入口**：**「关于」或「软件更新」页**里加"更新日志"入口；用户可随时查看历史。
- **提示分级**（不滥用）：
  - **信息级**：只写日志，不弹；
  - **通知级**：重要功能 / 影响使用的改动 → **应用内一次性提示**（按发布版本记一次，**不每次打开都弹**）；
  - **强提示级**：登录 / 注册 / 隐私 / 账号恢复 / 数据迁移规则的重要变化 → **必须清晰告知**，
    可要求用户确认后再继续（**按风险分级，不滥用**）。
- **普通修复与小 UI 可合并**成一条，不必逐次公告。
- **不写内部路线图 / 内部代号**；面向用户的措辞遵守既有产品语气纪律（ADR-020）。

**待定（见 S14 设计要点 §6）**：谁写、谁批、按设备还是按账号记"已读"、强提示是否要跨设备一致、
历史日志保留多久。

**明确不做**：本轮不建表、不做后台发布系统、**不把 `版本记录` 直接当用户公告**（它含内部细节）。

### 3B.1 产品定位

Libevra 最初是为自己、家人和朋友做的一款**隐私性强、自由度高、数据可自主控制**的记账软件；
它是开源项目，当前**没有商业化计划**。长期希望探索三种使用方式，而不是把同一个产品强行复制三套。

**共同目标（三种模式都适用）：**

- 记账、分类、统计、查询、导出、导入这些核心能力可靠可用；
- 用户能理解自己的数据存在哪里、如何备份、如何迁移；
- 不把 OCR、语音识别或云端服务设为“记一笔”的前置条件；
- 不把“自托管”或“本地存储”自动宣传成绝对隐私或端到端加密。

---

### 3B.2 三种候选模式

| 模式 | 数据位置 | 主要能力 | 代价/风险 | 研究重点 |
|---|---|---|---|---|
| **云端托管版**（当前路线） | 远程服务器 | 账号、多设备同步、协作、服务端 OCR/语音；网页/PWA 使用 | 依赖服务器与网络；服务器安全、备份、运维成本；家庭自托管的对照基线 | 保持现状、降低成本、完善备份和可迁移性 |
| **个人纯离线版** | 用户设备本地（IndexedDB / 桌面封装 / 移动端本地存储） | 记账、分类、统计、查询、导出/导入；不依赖远程服务器 | 浏览器存储不是永久可靠存储；换设备、清缓存、设备损坏都可能丢数据；本地备份和迁移必须是一等能力 | IndexedDB 持久性、桌面/移动封装、加密备份、导入导出、可选本地 OCR/语音 |
| **家庭自托管版** | 用户自己的电脑、NAS 或家庭服务器 | 家庭成员局域网使用；自行管理数据库和备份；可研究安全远程访问 | 需要自己升级、备份、处理证书/网络/身份安全；设备丢失和内部误操作风险仍在；不等于端到端加密 | 部署与升级、LAN 访问、远程访问安全、家庭成员身份、离线重连、备份恢复 |

**个人纯离线版的额外约束：**

- **浏览器离线存储不等于永久可靠存储。** 必须设计可验证的本地备份、导出和恢复；不能只依赖 IndexedDB。
- OCR、语音识别是可选能力，不能成为基本记账的必要依赖。
- 可以研究设备端小模型，但不能假设所有手机都能运行大型模型；不支持时必须有手动回退。

**家庭自托管版的额外约束：**

- 不应把“自己部署”直接等同于“绝对隐私”：仍需考虑身份认证、网络安全、设备丢失、备份和家庭成员误操作。
- 远程访问应优先研究成熟的安全方案（如 VPN/内网穿透/反向代理 + TLS），不自行发明加密协议。
- 家庭服务器可能长期无人值守，升级、磁盘空间、备份和故障恢复必须可操作。

---

### 3B.3 架构方向

**总原则：尽可能复用现有界面、业务逻辑和数据模型；通过合理的存储适配层或服务接口支持不同部署模式；避免长期维护三套完全独立的软件。**

当前可以复用的部分：

- React 页面、组件、设计系统和 PWA 外壳；
- `packages/shared` 的类型、Zod 校验、金额/统计等纯函数；
- 现有离线本地账本、幂等键、冲突检测与导入/导出逻辑；
- Fastify 业务路由与领域逻辑、Prisma 数据模型、备份/恢复工具；
- OCR/语音 sidecar 的“无端口、stdin/stdout”接口形态。

需要重新抽象或研究的边界：

- Web 端直接调用 HTTP API 的数据访问层，需要可替换的 local adapter；
- 身份、会话、账号/家庭成员/设备身份在不同模式下的语义；
- 多设备同步、离线写入、冲突合并和“服务器权威”是否仍成立；
- 本地持久化、备份格式、迁移与跨模式导入导出；
- 桌面/移动封装、自托管打包与升级；
- OCR/语音在本地、家庭服务器、云端三种位置的可用性与回退。

**不在本轮决定**：是否真的实现三种模式、是否新增客户端框架、是否支持跨模式实时同步、是否引入端到端加密。
这些都必须在原型、数据安全评估和所有者拍板后再立项。

---

### 3B.4 功能差异与迁移问题

需要先列出“三种模式各自能做什么、不能做什么”，再决定代码复用边界。至少需要回答：

- 纯离线版没有服务器时，协作、共享、管理员、云端备份是否明确关闭或只读？
- 从离线版迁移到云端/家庭服务器时，如何处理账号、账本 ID、成员关系、附件/OCR 结果和冲突历史？
- 从云端迁出时，导出格式是否能独立验证、重新导入？
- 家庭自托管版的局域网用户与远程用户是否有不同权限？
- 服务器端 OCR/语音与本地 OCR/语音的结果格式是否一致？

这些问题的详细拆分见 [`技术方案.md`](02-技术方案.md) §15；在得到可验证答案前，不对用户承诺功能或日期。

### 5.2 理解驱动开发（2026-10-19 起）

> **目标：减少“AI 写完、所有者只看结果”的被动验收，让所有者逐步真正理解技术体系，并积累可以独立运用的软件工程知识。**
> 这**不要求减少 AI 编码**，也不要求每个小改动都写长篇教材。

**协作流程（重要功能）**

1. 所有者提出需求；
2. AI 先用容易理解的语言解释：要解决的技术问题、可行方案、推荐方案及代价；
3. 所有者理解并参与决策；
4. AI 编码；
5. AI 解释关键实现：接口、数据流、失败处理和未采用方案；
6. 所有者验收、复述，并记录自己是否真正理解。

**讲解分三层，按需要展开：**

| 层次 | 要回答的问题 |
|---|---|
| **产品层** | 这个功能解决用户的什么问题？不做的代价是什么？ |
| **架构层** | 为什么放在这个模块？数据流和权限边界是什么？和其他模块如何解耦？ |
| **实现层** | 关键代码、接口、数据库字段、异常/重试/失败路径是什么？ |

**深度原则：**

- 数据库、数据安全、账号权限、备份恢复、同步机制、迁移等高风险模块，必须解释关键原理和失败风险；
- 普通 UI 文案、样式微调、简单 bug 修复可以简短说明，不机械生成教学长文；
- 紧急修复和生产安全操作优先处理，事后再解释；
- 讲解要区分**已实现的事实**、**设计意图**和**尚未验证的假设**，不能把 AI 的推断包装成事实。

**知识状态（只由所有者确认，AI 不代填“已掌握”）：**

| 状态 | 含义 | 证据 |
|---|---|---|
| **已理解** | 能用自己的话解释产品/架构/实现，并能独立完成一个小改动或测试 | 复述、练习题、独立修改、代码审查 |
| **听过** | 能描述概念，但还不能预测行为或独立实现 | 仅阅读/听讲 |
| **未掌握** | 只见过名词，尚不能解释或应用 | 尚无证据 |
| **AI 完成 ≠ 我掌握** | AI 写了代码或测试，不代表所有者已具备同等能力 | 不能作为“已理解”的证据 |

**知识记录表（初始教材：S13-I）**

> 维护位置就是本节；以后每学完一个主题，由所有者确认状态和证据，AI 只做建议和补充。
> 初始状态全部标为**待评估**，不假定所有者已经掌握。

| 主题 | 在 Libevra 中的用途 | 当前状态 | 证据/练习 | 下一步 |
|---|---|---|---|---|
| PostgreSQL 事务、MVCC、REPEATABLE READ、导出快照 | 检查点备份必须和业务链头属于同一一致性快照 | 待评估 | 画出“业务提交 / 检查点 / pg_dump”的时序 | 用两个并发事务观察可见性 |
| 行锁、advisory lock 与锁窗口 | 事件追加和检查点互斥；备份时业务仍可写 | 待评估 | 说明为什么锁只覆盖短窗口 | 写一个并发测试 |
| `pg_dump --snapshot` 与 sidecar | 精确备份边界，不用“备份完成时间”猜边界 | 待评估 | 对比普通 dump 与检查点 dump | 恢复后核对 chain head |
| 哈希、哈希链、HMAC 的区别 | 哈希链保证顺序/完整性；HMAC 带密钥认证；**都不等于加密** | 待评估 | 用一句话分别解释三者，指出哪一步不提供机密性 | 修改一个对象后观察验链失败 |
| AES-256-GCM、nonce、keyId/keyring | 事件对象机密性 + 完整性；密钥轮换兼容旧对象 | 待评估 | 说明为什么 nonce 不能复用 | 解密旧 keyId 对象 |
| outbox、LISTEN/NOTIFY、relay、重试退避、幂等 | 业务提交后异步上传；relay 故障不阻塞业务 | 待评估 | 画出 P0 请求 → DB → relay → COS 的路径 | 停 relay 后验证补传 |
| COS 对象版本控制、对象锁/WORM、客户端覆盖头 | 保护事件对象不被覆盖；客户端头不是服务端绝对保证 | 待评估 | 区分版本控制、对象锁、CAM 权限、请求头 | 在测试桶验证覆盖行为 |
| 数据库迁移前滚、应用回滚、数据库回滚 | 旧应用可连接新 schema 不代表可完整回滚 | 待评估 | 列出 34→45 迁移和应用回滚的差异 | 在隔离库做旧应用兼容测试 |
| 备份/恢复校验（SHA-256、HMAC、GPG） | 防止错误/损坏/伪造的备份被当成可恢复备份 | 待评估 | 说明每种校验防的是什么 | 篡改一个文件观察拒绝 |

**练习题建议（不做形式化考试）：**

- 不看文档，画出一次“删除账本”从请求到 COS 的完整数据流；
- 解释为什么“哈希链”不能替代加密，“HMAC”也不能替代加密；
- 写一个 relay 暂时失败后补传的测试，并说明幂等键的作用；
- 对比普通 S12-C dump 和 S13-I 检查点 dump，说明为什么后者才能安全重放删除；
- 在隔离库中把 34 个迁移前进到 45，再启动旧应用，记录哪些功能不可用。

**维护规则：**

- 知识记录只维护在这一节，不新建多个互相冲突的“学习笔记”；
- 每次重要功能验收后，补充“学了什么、证据是什么、还缺什么”；
- 没有实际证据（复述、练习、独立改动）时，状态不得写成“已理解”；
- 具体技术解释可以写在设计文档或验收记录里，但知识状态和索引在本节。

### 为什么它在 S12「可上线」之前

因为它改的是**所有界面共用的东西**（文字、颜色、层级风格）。
**上线后再做，意味着两个版本之间整站的观感会变一次**，而 S12 要做的是部署、演示账号与备案 ——
那些都需要界面已经稳定。

### 一、文字语义化

**现状**：*"部分的文字是标题，部分的文字是按钮，部分的文字是说明"* ——
同样的角色在不同页面由不同的人手写，于是同一类文字的字号、颜色、措辞不一致。

**目标**：
1. **同一功能的按钮，文案始终相同**（例如"保存"不会在某处叫"确定"、另一处叫"提交"）。
2. **所有说明性文字风格统一**（字号、颜色、行距一套）。
3. **有一个地方能看到全部文本** —— 便于通读与校对，
   而不是靠 grep 各个页面去猜哪些是用户可见的。

---

### 二、颜色语义化

**所有者给的真实例子**：

> *"现在账本空间开始页面最深的那个海浪颜色跟其他的页面导航栏是不一样的——
> 平时可能看不出什么，但是当用户从账本跳转到账本空间/开始时，
> 他就会明显的感觉到导航栏的颜色自然不一样。"*

**这一点已核实**：

| 位置 | 颜色 | 来源 |
|---|---|---|
| 品牌色令牌 `--color-brand` | `#55997a` | 一级页面标题区、导航高亮 |
| **海浪最深一层** | **`#3f7059`** | `OceanBackdrop.tsx` 里的**硬编码字面量**【2026-10-27 更正：现已改读 `--color-ocean-1…4` token，见 `OceanBackdrop.tsx`】 |

**根因**：`colors.test.ts` 有一条"颜色只能来自令牌"的规则，
而 `OceanBackdrop.tsx` 被列进了**豁免名单**【2026-10-27 更正：现已不在 `apps/web/src/lib/colors.test.ts` 的 EXEMPT 名单内】（理由是"它是一幅画，不是主题"）。
**这个豁免是错的** —— 海浪是整个应用里面积最大的一块颜色，
**它恰恰是最需要与品牌色一致的地方，而不是最不需要的地方。**

**目标**：
- 所有**导航**同一个颜色
- 所有**按钮**同一个颜色
- **危险操作**（删除等）同一个颜色
- 海浪的层次由**令牌的明度变化**导出，而不是四个独立的字面量

### 三、三类界面风格统一

所有者用了一个很清楚的类比：**"就像微信里面的通讯录和聊天一样"** ——
不用看标题，**一看就知道这两个是同级页面**。

| 类别 | 包含 | 应有的一致特征 |
|---|---|---|
| **一级界面** | 明细、分析、账本／协作、账户 | 品牌绿标题区 + 固定底部导航；四页美术与设计思路统一 |
| **设置／二级页** | 个人资料、软件更新等 | 左上角返回 → 功能名 → **灰色说明文字** → 内容 |
| **功能页** | 再往下的操作页 | **灰底** + **灰框圈出的白底内容块** |

**目标**：每类内部**结构、间距、字号层级、颜色用法**都一致；
**跨类之间要有可辨认的差异**（让人知道"我进到更深一层了"）。

#### F1 补充说明（**重要前提，先看清再决定**）

**技术上可行**，但**在 iPhone 上不保证有效**：

- **iOS 10 起，Safari 出于无障碍考虑会主动忽略 `user-scalable=no`**。也就是说，即使加了这个设置，**在你的 iPhone 上大概率不生效**。
- 真正能拦住 iOS 缩放的只有 **JS 拦截手势**（监听 `touchstart`，在双指时 `preventDefault`）。做法可行，但：
  - 会**连带破坏无障碍**——需要放大看的长辈将完全无法放大
  - 与浏览器默认行为对抗，未来系统更新可能失效
- 因此我的建议是：**这条待办值得记录，但优先级低**，而且**默认值必须是"允许缩放"**。

> **结论**：可以做，但**别指望它解决 iPhone 上的问题**。它更像"桌面浏览器/安卓上的可选优化"。

#### I8 详述：「浏览器其它」是什么 —— **✅ 已查清（2026-10-11）**

**所有者的问题（2026-10-11，原话）**：

> **"我一直想知道这个浏览器及其他到底是啥——一直占我空间还删不掉！"**

**要求**：**加一条待办，在正式上服务器之前查一下这是什么东西以及怎么删除，
希望前人有充分的经验。**

##### 结论：**它是浏览器的 HTTP 缓存**，而**网页无法用代码清除它**

| 问题 | 答案 |
|---|---|
| **它是什么** | **浏览器自己的 HTTP 缓存**（存原始响应），**不属于** IndexedDB，也**不属于** Cache Storage |
| **为什么删不掉** | **Web 平台没有任何 API 能清 HTTP 缓存。** `caches.delete()` 只清 **Cache Storage**（Service Worker 那一套）——**而我们已经在"清除本应用的全部本地数据"里清光了它**，所以那个按钮对这部分**天然无能为力** |
| **它为什么这么大** | **开发模式**：Vite 按需提供**未打包的模块**，每个模块一个请求、每个都进 HTTP 缓存；**而且没有关 sourcemap**，每个模块还带一份源码映射 |
| **它为什么涨** | 每次刷新都要重新拉一整套模块（开发服务器不复用浏览器缓存），旧的条目仍按源记账 |

**实测数字（2026-10-11，本机）**：

| 项 | 开发模式 | 生产构建 |
|---|---|---|
| **一次加载要拉的量** | 142 个源文件 + 约 309 个依赖包，**逐个请求** | **1 个 JS（610 KB）+ 1 个 CSS（37 KB）+ HTML/SW（9 KB）** |
| **产物总体积** | `node_modules/.vite` 预打包 **6.26 MB**（还会被 sourcemap 放大） | **655 KB** |

**⚠️ 所以那个 68.9 MB 里，真正"属于账本"的可能只有几百 KB**——
**其余是开发模式自己制造的，而且它在浏览器眼里是"页面缓存"，不是"我们的数据"。**

##### 怎么清除（**分两种，各有前提**）

| 场景 | 做法 |
|---|---|
| **只想清缓存，不动账本**（推荐先试这个） | **Chrome / Edge**：`F12` → **Network** → 勾 **Disable cache**（开发时）；或 **Application → Storage → Clear site data** 里**只勾"Cache storage / 缓存的图片和文件"**。<br>**Safari**（iOS）：**设置 → Safari → 清除历史记录与网站数据**——⚠️ **但这一个会连 IndexedDB 一起清掉，见下方警告。** |
| **彻底清（含账本）** | 用应用里的**「清除本应用的全部本地数据」**，或浏览器的"清除网站数据" |

> ### ⚠️ 动手之前必须先确认一件事
>
> **HTTP 缓存、IndexedDB、Cookie 是按"源"（origin）算的，很多浏览器把它们放在同一个"网站数据"里**——
> **"清除网站数据"会连我们的离线账本一起删掉。**
>
> **所以清除之前**：**确保账本已经全部同步到服务器**（明细页没有淡绿/淡红的行），
> **否则那些只在本机的改动会一起没掉。**
> **这与 `specs/product/离线与同步-设计决定.md` 的立场一致**：**"缓存是用户唯一的离线副本"——
> 所以任何"小心起见清掉缓存"的做法都是错的，除非用户明确知道自己要清什么。**

##### 根治办法：**日常用生产构建，而不是开发服务器**

**开发模式（`pnpm dev`）本来只是"我改代码时看的"，不是"给人用的"。**
**所有者日常在手机上用的时候，应该用的是生产构建**——那时每次加载只拉 **3 个小文件**，
HTTP 缓存自然几乎不增长。**这件事归到 S12（可上线）**：那时有真正的域名与 HTTPS，手机上用的是构建产物。

**⚠️ 顺带一条可以直接减负的**：`vite.config.ts` **没有关 sourcemap**，
开发模式下每个模块都带源码映射。**关掉它（或只在需要时打开）能立刻让开发模式的缓存占用小一大截**——
但**这属于代码改动**，要按规矩升版本 + 写版本记录，所以留到有明确需要时再做。

##### ✅ 已排期：**上线时关掉开发服务器**（所有者 2026-10-11 点名加的一项）

**所有者原话**：

> **"关于开发者缓存：现在还是开发状态，所以肯定没办法做。但是你可以在待办名单里加一项。
> 程序在上线前关掉开发服务器。这样一来，用户应该不会再出现这样的问题了吧。"**

**已写入 `开发计划.md` 的 S12（可上线）任务与验收标准**：域名指向 `apps/web/dist` 的静态产物，
`pnpm dev` 只留在开发机上；**顺手关掉开发模式的 sourcemap**。

**⚠️ 而"这样一来就不会再出现"这句话，要答得准确一点**：

| 问题 | 上线后会怎样 |
|---|---|
| **开发模式那几十万个模块请求** | ✅ **消失**——家人访问的是构建产物，一次加载只拉 3 个文件 |
| **sourcemap 放大** | ✅ **消失**（前提是关掉它） |
| **Service Worker 的外壳缓存** | ⚠️ **仍然会有，但它是有限的**：3 个文件、约 655 KB，而且**只在版本变化时才更新**——**不会再持续增长** |
| **`storage.estimate()` 报的数** | ⚠️ **仍然会略高于真实数据**——它包含浏览器还没落盘的部分。这是浏览器的记账方式，**不是我们的泄漏**，也**无法由程序消除** |

**结论**：**"每刷新一次就涨"这个现象会消失**，占用会稳定在一个小而固定的量级（预计**几百 KB 到 1–2 MB**，
不再是无上限增长）。**但 `estimate()` 那个数字本身永远会比真实数据大一点**——
**这不是 bug，是浏览器的记账口径**，所以我们**不承诺"这个数字会变成账本的真实大小"**。

**⚠️ 一条现在仍然成立的警告**（上线前后都一样）：**HTTP 缓存、IndexedDB、Cookie 同属"网站数据"**，
**很多浏览器"清除网站数据"会连离线账本一起删**——所以清之前必须确认**明细页没有淡绿/淡红的行**。

**⚠️ 还有一件事要分开看**：**开发服务器不能"完全删掉"**——真机调试仍然需要它
（手机通过局域网 https 访问，见 `docs/00-索引.md`；而且 **Service Worker 只在生产模式下注册**，
所以**离线功能只能在构建产物上测**，见 `worker.ts`）。
**要分的是"谁在用它"**：开发服务器给开发机，构建产物给家人。

**参考**：`docs/specs/product/离线与同步-设计决定.md` §4.5d（52.5MB 与 127KB 的差）。

**结论（2026-10-17 记录，不是实施决定）**

- **R1：暂缓。** 理由：**Web/PWA 没有可靠统一的发现能力**；权限限制；**可见 ≠ 可信**；复杂度高；
  S14 范围已经够大。**当前用二维码 / 邀请链接 / 短时配对码替代**；未来若要研究，方向是
  **原生 mDNS/Bonjour**，不是 Web。
- **R2：只评估。** **不要求原生客户端完成才能上线**；**WebView 不等于完整原生能力**；
  **不承诺原生绝不丢数据**；评估结论出来前**不迁移框架、不出 APK、不买 Apple Developer、不改存储层**。

## 12. 所有者点名、明确暂缓的项（**只记录，不实施**）

> 来源：`archive/design/待办清单历史.md` 的 §2.0.2 与 §2.0.4（2026-10-11 / 2026-10-16 所有者点名）。

### 12.1 P1 · 首次进入逻辑（2026-10-16）

**要什么**：

1. **首次进入** → 展示**展开的**账本空间；
2. **第二次及以后** → 直接进入该账号**上次使用的账本**的明细页；
3. **跨设备一致** —— "上次使用的账本"是**账号级**的，不是设备级；
4. **账本失效时安全回退**（被删/无权限/不存在 → 优雅退回可用状态，而不是报错或空白）；
5. **⚠️ 不重新制作海浪动画** —— 展开/收缩态已实现（规格见 [`specs/design/海浪效果要求.md`](specs/design/海浪效果要求.md)），本项只改"进哪个状态"的判断。

**为什么暂缓**：需要记住"某账号上次用哪本账"，**要动已存数据的含义**（账号字段或小表），属于高风险改动。

**动手前必须先定的两件事**：

- 这个"上次使用的账本"**存在哪**（账号字段 / 小表）——注意"一件事只留一份记录"（`lessons.md` §8.7）；
- **离线时怎么办**：跨设备一致意味着权威在服务器，但应用是离线优先——本地是否也缓存一份？本地那份用于离线即时判断？**这个取舍要先定**。

### 12.2 P2 · 全站中文文案优化（2026-10-16）

**范围**：全站用户可见的中文文案——按钮、提示、错误信息、权限说明、危险操作说明。
**要求**：简洁自然、清晰一致的产品语言。

**边界**：

- **不改变现有业务语义**（只改措辞，不改行为含义）；
- 不得违反既有纪律"应用内文案一律用产品语气"（ADR-020：面向用户的提示严谨、礼貌、中性，不夹带项目内部语境）；
- 危险操作（删除账本、撤销授权、恢复数据库等）的说明**要更清楚，不是更短**；
- 内部路线图信息**留在文档里，不进界面**。

**已有护栏**：`apps/web/src/lib/copy.test.ts` 会拦一些已退场文案；改文案前先读它，别把护栏拆了。
