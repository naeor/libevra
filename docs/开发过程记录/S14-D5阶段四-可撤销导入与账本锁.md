## 1. 产品语义变化

导入不再在最后一批写入后自动成为正式结果：

- 批次执行期间可撤销；
- 部分批次已提交后可撤销；
- 全部批次完成、等待确认时可撤销；
- `awaiting_confirmation` 连续 10 分钟无有效用户操作，由服务端自动安全撤销；
- 用户最终点击「确认完成」后才写正式回执、释放 A/B 业务锁、开放来源清理；
- 撤销不是“停止后续批次”，而是恢复已提交批次造成的业务变化。

### 1.1 状态机（与旧状态并存）

| 状态 | 含义 | 是否持锁 |
|---|---|---|
| `queued` / `running` / `finalizing` | 后台批次执行、对账 | 是 |
| `paused` | 异常或长时间无进展暂停，可继续或撤销；有独立超时 | 是 |
| `awaiting_confirmation` | 所有批次与业务写入完成，等待用户最终确认 | 是 |
| `confirming` | 最终确认事务执行中 | 是 |
| `confirmed` | 最终确认成功，正式回执已写，锁已释放 | 否 |
| `undoing` / `undone` | 正在/已经安全撤销全部已提交批次 | 是/否 |
| `undo_failed` | 撤销未完成，账本保持锁定并允许重试 | 是 |
| `completed` | 阶段一至阶段三的旧任务：已自动完成，不能撤销 | 否 |
| `cancelled` / `expired` | 旧任务的停止/快照过期状态；新 UI 不再使用 stop-only cancel | 否 |

旧 `completed` 任务保持历史事实，不伪装成可撤销任务；新任务使用 `confirmed`。

### 1.2 旧 cancel 接口

- 阶段四任务：`POST /jobs/:id/cancel` 作为安全撤销的兼容别名，不会保留半完成状态；
- 阶段三旧任务（无撤销日志）：仍保留旧 “停止后续批次” 行为，但错误码明确为 `job_cancelled_legacy`；
- Web UI 已移除 stop-only cancel 按钮，改用“撤销本次导入”。

## 2. 数据模型

### 2.1 批次反向日志（不是整库快照）

新增 `ledger_import_undo_batches`：

- 每个已提交批次同一事务写一行；
- `payload` 是该批次精确反向操作；
- 反向操作覆盖：
  - 本任务新增的目标交易 → 删除（硬删除；任务独占行，锁保证无外部编辑）；
  - 本任务更新的目标交易 → 恢复字段、标签、sourceRef/sourceNamespace；
  - 本任务写入/更新的来源状态 → 恢复旧状态或删除新建状态；
  - 本任务创建的分类/支付方式/标签 → 在无引用时删除；
- 撤销逆序处理批次；已撤销批次有 `undoneAt`，崩溃后从剩余批次继续；
- `confirm` 或 `undone` 后清空反向 payload，只保留批次行与不可变 job 事件，避免长期保留账目内容。

**没有采用**“导入前整库/整账本快照替换”：批量数据大、会覆盖其他并发或历史变化，不可接受。

### 2.2 目标 A 软删除延后

阶段四把“移除目标 A 记录”的最终软删除**延后到最终确认事务**。因此等待确认期间的撤销不需要复活已软删除的 A 行；确认事务整体成败，避免部分软删除。旧任务的 `removedTargets` 不进入新撤销路径；它们已确认，不能撤销。

### 2.3 最终确认事务

确认时同一事务：

1. 验证目标 A 指纹、数量和来源 B（正式来源）未变；
2. 应用最终 A 软删除并记录 TransactionEvent；
3. 再次对账；
4. 写 `ledger_imports` 正式回执；
5. 状态 `confirmed`，清空确认截止时间，释放业务锁；
6. 清空反向 payload。

确认失败回滚，回到 `awaiting_confirmation`，账本锁不释放，UI 显示错误并可重试/撤销。

### 2.4 审计

新增 `ledger_import_job_events`，记录 queued/paused/awaiting_confirmation/confirming/confirmed/undoing/undo_batch/undone/...，只含状态、计数和错误码，不复制账目正文。反向日志提供恢复能力；job events 提供最小审计。

## 3. 业务级账本锁

### 3.1 持久锁表

`ledger_write_locks`：

- 每本账本同一时刻最多一条 `released_at IS NULL` 的锁（partial unique index）；
- 从实际导入开始（任务创建并持锁）持续到 `confirmed` 或 `undone`；
- 服务器重启不丢失；
- 正式来源 B 与目标 A 同时锁定；游客来源没有服务端账本，只锁目标 A，来源快照指纹继续用于一致性；
- 其他账本的行和锁不受影响。

### 3.2 数据库写入触发器，而非仅前端禁用

`assert_ledger_write(book_id)` 在以下表的 INSERT/UPDATE/DELETE 触发器内执行：

- `transactions`、`transaction_tags`、`transaction_events`、`transaction_conflicts`；
- `categories`、`payment_methods`、`tags`；
- `book_members`、`notifications`（有 book_id 的邀请）、`book_share_links`、`book_messages`；
- `books`、`book_lifecycle_events`、`book_recovery_requests`、`book_tombstones`；
- `export_logs`、`import_logs`、`ledger_imports`、`ledger_import_source_states`。

**TOCTOU 处理**：

- 触发器先对父 `books` 行做 `FOR SHARE`；
- 获锁事务对同一 `books` 行做 `FOR UPDATE` 后再插入锁行；
- 写事务在触发器内检查锁；获锁事务与写事务因此按父行串行化；
- 没有长表锁，也不使用全站锁。

**锁 owner 自身写入**：导入/确认/撤销事务使用事务本地 `SET LOCAL libevra.ledger_lock_owner = 'import:<jobId>'`；触发器只放行匹配 owner。普通设备不设置 claim，收到 `409 ledger_locked`。

### 3.3 导出

- 普通 CSV/XLSX 导出是只读一致性查询，不获取长时间锁；
- 导入锁定期间普通导出直接 `409 ledger_locked`，避免导出到半完成导入状态；
- 没有新增“长时间特殊导出”；若未来需要，应使用短时业务锁并可靠释放，而不是本阶段伪造实现。

### 3.4 PWA 离线队列

离线同步收到 `409 ledger_locked` 时：

- 不当作内容冲突；
- 不清除 pending mark；
- 不把用户离线输入变成红色冲突；
- 解锁后的下一次同步重新验证并提交。

## 4. 10 分钟超时与恢复

- `IMPORT_CONFIRM_TIMEOUT_SECONDS` 默认 **600 秒**，安全范围 **60–3600**；
- 进入 `awaiting_confirmation` 写 `confirmationDeadline`；
- 只有显式用户动作（确认/撤销/继续任务/“我还在”）刷新期限；
- GET 轮询、页面心跳、鼠标移动**不**刷新；
- 页面关闭、断网、浏览器崩溃，服务端照常超时；
- 真正后台推进的批次不会被自动撤销；`queued/running/finalizing` 超过配置时间无进展才转为 `paused`；
- `paused` 同样有确认截止时间，超时自动撤销，避免异常任务永久锁账本；
- 超时自动撤销与用户主动撤销走同一条安全撤销路径；
- 超时**不会直接解锁**：必须先完成反日志撤销与校验，失败则保持 `undo_failed` 与锁；
- 服务端启动恢复 `queued/running/finalizing/confirming/undoing`，并定期扫描超时、卡住确认、卡住撤销；
- `undo_failed` 在尝试次数未超上限时可后台重试，但绝不绕过校验或被 UI 伪报成功。

旧的 7 天 `IMPORT_JOB_TTL_DAYS` 只保留给**阶段三旧任务**；阶段四任务持锁期间不能被 TTL 清空快照或直接 expiring。

## 5. 最终确认后的来源清理门槛

- 未 `confirmed`：不写正式回执，游客清理预览无回执，正式来源处置要求 `confirmed`/旧 `completed`；
- `confirmed` 后才显示来源安全与清理卡片；
- 默认仍完整保留来源；
- 正式来源弃置继续走 S13 lifecycle 与权限检查；
- 未全部导入时继续显示未迁入、恢复期限和额外确认；
- 确认不会绕过 S13 生命周期、协作者/邀请/分享链接检查。

## 7. 剩余风险与边界

1. **新建目标账本的导入仍走旧的同步路径**：不存在可锁的既有目标；本轮没有把它扩展成可撤销任务，需在后续版本决定是否先建空账本再走 phase 4。
2. **升级瞬间的旧阶段三活动任务没有反向日志**：worker 不会把旧任务推进到新确认流程，而会标记 `legacy_import_requires_repreview`，要求重新预览；旧任务中已提交的批次仍保留，升级前应尽量等待/清理活动任务。
3. **旧 `completed` 任务不能撤销**：它们没有反向日志，不能假装可撤销。
4. **硬删除新增目标行**：反向日志假定任务独占新增行；业务锁保证等待期间无外部编辑。若触发器被绕过或数据库被直接篡改，撤销会因校验失败进入 `undo_failed`，不会静默覆盖。
5. **目标 seq 计数器不回退**：撤销后删除新增行会留下编号空档；这是有意保护已发编号不被复用。
6. **反向日志在 confirmed/undone 后清空 payload**：保留 job events 审计，但不再保留账目正文；已确认/已撤销后不能再次重放反向操作。
7. **undo_failed 可能长期持锁**：只有校验恢复到可撤销状态才能解锁；系统会有限自动重试并显示明确状态，但极端数据损坏需要人工介入，不能强行解锁。
8. **10 分钟是默认值，暂未提供用户设置页面**。
9. **极端并发压力未做**：本轮的锁/确认/撤销测试覆盖串行化和重启，但未做数百任务同时竞争压测。
10. 未 push、未部署、未修改生产、未调用或修改 S13 服务/COS/CAM。
