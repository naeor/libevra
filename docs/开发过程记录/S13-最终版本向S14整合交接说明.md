## 0. 结论摘要

1. S13 的最终源码基线是 `s13-g` 的 **`cc14725`**，不是 1.13.09，也不是只到 `1e16a62`。
2. S14 `s14-a` 与 S13 的共同祖先是 **`547afa6`**。S13 从这个祖先之后新增了 **21 个提交**；S14 尚未继承这些提交。
3. 迁移差异没有想象中大：
   - 共同祖先已有 **43** 个 migration；
   - S13 最终有 **45** 个，新增 `20261018203000_critical_relay_retry_status`、`20261018204000_critical_operation_receipt_expiry`；
   - S14 分支当前有 **44** 个，已继承 43 个共同 migration，并新增自己的 `20261019020000_s14d_ledger_import`；
   - S14 缺的正是 S13 的上述 2 个 migration；
   - S14 工作区还有 **未提交** 的 `20261019050000_s14d_import_jobs`（D5 阶段一）。
4. Prisma schema 的两侧改动基本是**分区新增**，不是同一字段的平行改写：S13 增加 critical relay/checkpoint 字段和表；S14 增加 `LedgerImport`（以及未提交的 `LedgerImportJob`）。但是版本号文件、文档和部分 API 入口有真实 Git 冲突，不能盲目 `-X ours/theirs`。
5. **最需要优先处理的业务衔接是 S14-D 导入与 S13 生命周期/关键事件的关系**：
   - 导入到**已有目标 A** 时，A 的账目软删除只写 `TransactionEvent`，**不会进入 Critical Chain**；
   - 导入到**新建目标 A** 时，目标账本由 `createDefaultLedger` 创建，会记录 `book.created` 关键事件；
   - 未来 D5 清理来源 B 必须走 S13 生命周期，不得直接 SQL 删除账本；
   - D5 后台分批任务当前没有显式检查账号是否已注销/停用，合并后应补上；
   - 历史备份恢复可能复活 A 中被导入流程软删除的交易，这是当前 S13-I 的**已存在语义边界**，需要在 S14 验收中明确接受或另行扩展，不能假装已保护。
6. 推荐顺序：先给 S14 未提交的 D5 工作区做安全检查点，再在独立 integration 分支上合并 `s13-g`，解决文档/版本冲突，最后在**生产 45 migration 的隔离克隆**上验证 S14 migration 和导入流程。

## 3. 业务与安全规则

以下规则来自 S13-G/H/I 的实现与设计文档；S14 合并后必须**保留判断本身**，不能为了复用而移动/合并/改写敏感权限判断。

### 3.1 账号生命周期与关闭规则

- **注销不物理删除 `users` 行**：保留 UUID 作为共享交易/成员/历史外键锚点；
- 注销会：
  - `username` 改为 `closed_<uuid>`、`displayName` 改为已注销；
  - 设置不可用随机凭证、清空恢复码；
  - 写 `closedAt`、`disabledAt`，`isAdmin=false`，撤销管理授权；
  - 删除/撤销会话、通知配额、收件通知、未处理邀请、未用邀请码、分享链接；
  - 写 `account_tombstones`，保存账号 UUID/编号/时间/资源处理汇总/恢复凭证哈希；
- 旧会话先 `revoked_at`，旧设备下一次请求收到 `401 account_closed` 后清本地数据；
- **不能声称所有离线设备已即时物理清除**；只能在联网后拒绝并清理；
- “删除服务器数据”和“注销账号”是两个不同操作：
  - 删除数据：只处理账本数据，账号仍可登录；
  - 注销账号：结束账号，走上面的匿名化/吊销流程。

### 3.2 账本归档、删除与恢复规则

- **共享账本（仍有 ≥2 位有效成员）**：
  - 任意成员“删除/退出”只退出协作；
  - 写 `book_members.left_at`，会员行保留；
  - 其他成员、账目、留言、分享链接不受影响；
  - 当前管理者退出时，管理权在同一事务内交给最早加入的有效编辑者；没有编辑者则拒绝；
- **单人账本/最后一位有效成员**：
  - 归档：`archived_at`，`self_restore_until = archivedAt + 60 天`，`scheduled_purge_at = archivedAt + 365 天`；普通业务 API 不可访问；
  - 永久删除：写 `book_tombstones`，按依赖删除交易/账本；墓碑保存 UUID、编号、创建/删除者、时间、计数、结果；
  - 已删除账本 API 返回 `410 book_deleted`；ID 不再复用；
- 归档生命周期：
  - 0–60 天：原账号自助恢复；
  - 60–365 天：普通恢复关闭，可提交人工恢复申请，管理员核验批准/拒绝；
  - 满 365 天：每日清理任务在到期后 24 小时内执行；
  - 清理开始写 `purge_started_at`，恢复/清理互斥；失败回滚并记录 `purge_attempts/purge_last_error`；
  - 自动清理是独立脚本 + advisory lock，不是 API 进程内定时器；
- 已注销账号的归档保留需要一次性恢复凭证；只保存 SHA-256 哈希，响应中只显示一次；必须管理员核验，不凭账本编号自动恢复。

### 3.3 成员权限与邀请限制

- **`book_members` 是账本权限的唯一来源**；管理员不等于能看别人账本；
- 只有 `left_at IS NULL` 的成员有效；
- 角色只有 `editor` / `viewer`，没有旧的 `owner` 角色；管理者是单独字段/规则；
- 邀请：
  - 待接受且未过期的 `book_invite` 才有效；
  - 过期/已决定/已撤销邀请不永久阻止账本进入单人状态，但必须在资格判断时正确排除；
  - 注册邀请码和账本邀请是不同概念，不能混用；
- 分享链接：
  - 未撤销、未满员、未过期的分享链接仍可产生协作成员；
  - 因此“单人账本”导入资格必须把有效分享链接视为“尚可接受的协作邀请”；
- S14-D 正式导入首版只允许**本人创建、当前只有本人一个有效成员、无待接受账本邀请、无仍有效分享链接**的单人账本；服务端必须重新校验，客户端过滤不算权限；
- 并发加入/接受邀请/分享使用必须在事务锁内阻止；不能只靠预览时的检查。

### 3.4 关键事件的事务记录与异步 relay

- 事件类型（S13-I 实际覆盖）：
  - 账号：created / disabled / enabled / closed / data_deleted / recovery_requested / recovery_claimed；
  - 账本：created / archived / restored / deleted / disposed / undisposed / recovery_requested / approved / rejected；
  - 成员权限：joined / rejoined / left / removed / role_changed / manager_changed；
  - 认证：password_changed / password_reset / recovery_code_rotated / sessions_revoked；
  - 分享/其他 P0 操作按实际接点执行。
- **事件与业务状态变更必须在同一数据库事务中写入**；
- API 只写本地 `critical_events` 和哈希链，不持有 COS 凭据；
- API 不等待 relay ack；P0 业务成功与异地保护状态分离；
- relay 独立进程/容器持有 COS 写身份，异步上传加密事件和 manifest；
- P0 操作返回 `operationId` + 一次性 receipt token；不把 token 放 URL；24 小时过期；账号注销后仍可查询 receipt，但不恢复登录权限；
- `Idempotency-Key` 重复提交必须返回原结果，不重复写事件；
- 不允许在业务事务之外先写事件或先做保护动作，造成业务失败但事件已存在；
- 不允许用普通日志代替关键事件。

关键代码位置：

```text
apps/api/src/critical/store.ts
apps/api/src/critical/runtime.ts
apps/api/src/critical/checkpoint.ts
apps/api/src/critical/apply.ts
apps/api/src/scripts/critical-events-*.ts
apps/api/src/routes/p0-operation.ts
```

### 3.5 Critical Chain、Checkpoint 与恢复机制

- `critical_chain` 单行，追加时 `SELECT ... FOR UPDATE`；`eventHash = sha256(prevHash + canonical(core))`；
- relay 上传事件对象 + manifest；对象不可覆盖；出现 409 时 HEAD 比对哈希，不能盲目覆盖；
- checkpoint：
  - 在专用 advisory lock 下写 `critical_backup_checkpoints`；
  - 用 REPEATABLE READ snapshot，再 `pg_dump --snapshot` 生成同一快照；
  - sidecar 绑定 dump SHA-256；事件写入取共享锁，避免 checkpoint 与事件插入交错；
- safe restore：
  - `critical:preview` 只读差异；
  - `critical:apply-safe` 只对恢复快照中存在的对象重放安全状态；缺失目标进入 manualReview，不虚构账本/账号/交易；
  - 恢复库链头推进到远端最新；
  - 安全恢复只允许隔离数据库（库名含 test/restore/verify/isolated/rehearsal）；
- 原有 S12-C 备份/恢复通道不依赖 S13-I；旧 dump 没有 critical 表也能恢复，migrate 只做 additive 前滚；
- S13-I 不修改 S12-C 的 daily/monthly 生命周期、备份格式、GPG 或备份前缀。

### 3.6 关键操作如何接入事件记录

S14-D 的导入必须按以下方式接入，不能新增第二套“关键事件”：

1. **新建目标账本 A**：
   - 使用现有 `createDefaultLedger`（`apps/api/src/ledger/bootstrap.ts`）；
   - 它会在同一事务中记录 `book.created` 关键事件；
   - import 回执 `ledger_imports` 与 `book.created` 不能分属两个事务；
2. **已有目标 A 的账目软删除**：
   - 只写现有 `TransactionEvent`（`recordEvent`）；
   - 这不是 S13 的 `CriticalEvent`；S13 关键事件类型不覆盖单笔交易；
   - 不要为单笔交易创建新的 critical 事件类型；
3. **来源 B 保留**：
   - D4/D5 当前设计默认保留 B；
   - 不自动删除 B；不写 `book.deleted`；
4. **未来 D5 来源清理**：
   - 必须调用 S13 生命周期删除/归档入口（`lifecycle/book.ts` 对应的服务层/路由）；
   - 必须写 `book.deleted`（或对应生命周期事件）和 `book_tombstones`；
   - 必须保留 `ledger_imports`/`ledger_import_jobs`（无外键，不能因删账本清掉）；
   - 不能直接 `DELETE FROM books` 或直接删 `transactions`；
5. **账号注销/停用**：
   - D5 后台任务每批必须检查账号未注销/未停用，且目标/来源账本仍可写；
   - 不能因为“任务已经排队”就继续写；
6. **管理员/恢复操作**：
   - 不能绕过现有管理员五道校验和二次密码验证；
   - 不能把恢复凭证/操作 receipt 放进 URL 或日志。
