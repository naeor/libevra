# S13-I 灾难恢复操作手册（草案，尚未在生产启用）

> 本手册只在本地/隔离环境演练；不包含生产 COS 操作。生产启用前需要所有者批准 §4 的云权限。

## 1. 两套恢复路径，不能混用

### A. 安全恢复（默认，需要事件登记簿）

1. 把原始 S12-C dump 恢复到**隔离数据库**（不是生产库）。不要调用会重建生产库的 `restore.sh`。
2. 在隔离库上 `prisma migrate deploy`（旧 dump 会被前滚到当前 schema）。
3. 用**恢复只读身份**取回事件：
   ```bash
   cd deploy && ./critical-events-fetch.sh /tmp/libevra-critical-events
   ```
4. 验证加密对象、哈希链和 manifest；失败就保持隔离，不继续：
   ```bash
   CRITICAL_EVENT_KEY=... pnpm --filter @libellum/api critical:verify \
     --dir /tmp/libevra-critical-events
   ```
5. 指定备份时间边界（取 `backups/last-local.json` 的 `finishedAt` 或 dump 生成时间），应用安全恢复：
   ```bash
   DATABASE_URL=postgresql://.../libevra_restore_... \
   CRITICAL_EVENT_KEY=... pnpm --filter @libellum/api critical:apply-safe \
     --dir /tmp/libevra-critical-events \
     --backup-at 2026-10-18T00:00:00Z \
     --report /tmp/libevra-restore-report.json
   ```
   - 所有会话无条件撤销；
   - 删除/注销/权限撤销按事件重放，目标不存在时进入 `manualReview`，绝不凭事件凭空创建；
   - 密码/恢复码变更的账号被置为不可用凭据，需管理员重置；
   - 管理员**新增授权**不自动重放，必须人工核验。
6. 有 `manualReview` 或退出码非 0：继续隔离，人工逐项处理并留档。
7. 验收通过后，才由所有者批准切换生产流量。

### B. 原始备份直恢复（应急，不依赖 S13-I）

这是长期必须保留的通道；`deploy/restore.sh` 本身没有改动：

```bash
cd /srv/libevra/deploy
./offsite-fetch.sh --latest
./verify-dump.sh backups/restored/<name>.dump --expect backups/last-local.json
./restore.sh backups/restored/<name>.dump
```

> ⚠️ `restore.sh` 会覆盖生产库并自动 `up -d api`；它不依赖 `critical_events`、relay、事件密钥或任何 S13-I 表。失败时它没有自动回滚；`backups/pre-restore-*.dump` 是唯一回滚点。

如果目标是“恢复后默认保持隔离”，使用不自动启动 API/web 的独立包装（同样不依赖 S13-I）：

```bash
./emergency-raw-restore.sh backups/restored/<name>.dump
# 输入 yes；完成后 API/web 保持 stopped
```

> `emergency-raw-restore.sh` 只做原始数据恢复并保持隔离；`restore.sh` 是原自动重启路径。两者都不读 S13-I 表/密钥/服务，失败也都没有自动回滚。

应急直恢复后：
- **默认保持服务隔离**：不要立即把公网流量放回来；
- 如果要重新开放公网，必须单独进行人工风险确认（见 §3），且不能声称“删除/注销/权限撤销已经重新落实”；
- 可以人工运行旧的 `lifecycle:replay-tombstones`，但它只读取**恢复后的数据库**；若 dump 早于墓碑写入，它不会知道删除。

## 2. 关键限制

- 事件登记簿不会恢复备份之后新增的普通业务数据（新建账本、交易等）；缺失资源会进入 `manualReview`。
- 事件日志缺失、损坏、哈希链断裂、manifest 头不匹配时，安全恢复必须停止。
- 原始备份不因 S13-I 故障而不可用；S13-I 故障也不应阻止 S12-C 工作（本设计不修改 backup.sh / backup-all.sh）。
- **备份边界**目前由操作者通过 `--backup-at` 提供（取 `last-local.json` 的完成时间或 dump 时间），没有自动 backup checkpoint；这是上线前要补的工程点（见设计报告“剩余故障窗口”）。

## 3. 人工应急上线（与数据库恢复分开）

只有所有者可以决定。至少需要：
1. 确认恢复的是哪份备份、其时间边界；
2. 明确列出没有恢复的安全事件/人工核查项；
3. 决定是否接受旧密码/旧会话风险，并执行管理员密码重置；
4. 记录决定人、时间、范围和回滚点；
5. 重新开放流量。

**不要把“数据库已经恢复”当作“安全状态已经恢复”。**

## 4. 上线前必须批准的云配置（当前未操作）

- 新 COS 前缀 `critical-events/v1/` 独立生命周期（≥ 可恢复历史快照的最长保留期；建议不短于 365 天，且不与 daily/monthly 规则混用）。
- 写身份：仅 `PutObject/HeadObject`（建议加 `x-cos-forbid-overwrite`），无 `GetObject/ListBucket/DeleteObject`。
- 恢复身份：仅 `GetObject/ListBucket`，不常驻服务器。
- 新事件加密密钥：离线保险箱保存副本；丢失将导致历史事件不可解密。
- 是否采用独立桶（可选；第一版使用现有桶独立前缀）。
