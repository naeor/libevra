# S13-I 灾难恢复与全新服务器操作手册（草案，尚未在生产启用）

> 本地/隔离环境演练版。生产 COS、CAM、服务器、真实密钥、数据库在本轮均未被修改。
> 生产启用前需要所有者批准 §6 的云配置与 §5 的上线决定。

## 1. 两套恢复路径，不能混用

### A. 安全恢复（默认，需要事件登记簿 + 精确检查点）

1. 准备**带检查点的备份**（由 `deploy/critical-events-backup.sh` 生成；普通 S12-C dump 没有检查点，不能用于安全恢复）：
   ```bash
   cd /srv/libevra/deploy
   ./critical-events-backup.sh "pre-drill"
   # 产出 critical-backups/<name>.dump 与 <name>.dump.checkpoint.json
   ```
2. 把 dump 恢复到**隔离数据库**（不是生产库）。不要调用会重建生产库的 `restore.sh`。在隔离库上执行 `prisma migrate deploy`。
3. 用恢复只读身份取回事件：
   ```bash
   ./critical-events-fetch.sh /tmp/libevra-critical-events
   ```
4. 验证加密对象、哈希链、manifest；失败就保持隔离：
   ```bash
   CRITICAL_EVENT_KEY=... pnpm --filter @libellum/api critical:verify \
     --dir /tmp/libevra-critical-events
   ```
5. **只读预览**（不修改恢复库）：
   ```bash
   DATABASE_URL=postgresql://.../libevra_restore_... \
   CRITICAL_EVENT_KEY=... pnpm --filter @libellum/api critical:preview \
     --dir /tmp/libevra-critical-events \
     --dump /srv/libevra/deploy/critical-backups/<name>.dump \
     --checkpoint /srv/libevra/deploy/critical-backups/<name>.dump.checkpoint.json \
     --report /tmp/libevra-preview.json
   ```
   按事件组查看：自动处理、人工核验、目标缺失、可能倒退的风险。预览不删除会话、不写目标库。
6. **执行安全恢复**：
   ```bash
   DATABASE_URL=postgresql://.../libevra_restore_... \
   CRITICAL_EVENT_KEY=... pnpm --filter @libellum/api critical:apply-safe \
     --dir /tmp/libevra-critical-events \
     --dump /srv/libevra/deploy/critical-backups/<name>.dump \
     --checkpoint /srv/libevra/deploy/critical-backups/<name>.dump.checkpoint.json \
     --report /tmp/libevra-restore-report.json
   ```
   - 所有旧会话无条件撤销；
   - 删除/注销/权限撤销按事件重放；
   - 目标不存在→`manualReview`，绝不凭事件创建账号/账本/成员；
   - 密码/恢复码变更的账号旧凭据不可用，需管理员重置；
   - 管理员新增授权不自动重放；
   - 验证过的远端事件合并回恢复库，本地链头推进到远端最后一条。
7. 有 `manualReview` 或退出码非 0：保持隔离，人工逐项处理并留档。
8. 验收通过后，才由所有者批准重新开放流量（见 §5）。

### B. 原始备份直恢复（应急，不依赖 S13-I）

长期保留的独立通道；原 `restore.sh` 未被修改：

```bash
cd /srv/libevra/deploy
./offsite-fetch.sh --latest
./verify-dump.sh backups/restored/<name>.dump --expect backups/last-local.json
./restore.sh backups/restored/<name>.dump
```

> `restore.sh` 会覆盖生产库并自动 `up -d api`；不依赖 `critical_events`、relay、事件密钥或任何 S13-I 表。失败没有自动回滚；`backups/pre-restore-*.dump` 是唯一回滚点。

默认隔离的独立包装（同样不依赖 S13-I）：

```bash
./emergency-raw-restore.sh backups/restored/<name>.dump
# 输入 yes；完成后 API/web 保持 stopped
```

> `emergency-raw-restore.sh` 只做原始数据恢复并保持隔离；`restore.sh` 是原自动重启路径。两者都不读 S13-I 表/密钥/服务，失败也都没有自动回滚。

应急直恢复后：
- **默认保持服务隔离**：不要立即把公网流量放回来；
- 重新开放公网必须进行人工风险确认（§5）；
- 不能声称“删除/注销/权限撤销已经重新落实”；
- 可以人工运行旧的 `lifecycle:replay-tombstones`，但它只读取**恢复后的数据库**；若 dump 早于墓碑写入，它不会知道删除。

## 2. 精确备份检查点

- `critical-events-backup.sh` 持有专用 advisory lock，插入 `critical_backup_checkpoints` 行，然后导出 REPEATABLE READ snapshot；`pg_dump --snapshot` 使用同一快照。检查点行在 dump 内。
- 事件写入在 `recordCriticalEvent` 中取对应事务级共享锁；检查点期间不会有事件落在“检查点头之后但被包含进 dump”的缝隙。
- `<dump>.checkpoint.json` 绑定 dump SHA-256、大小、检查点 ID、链序号/哈希；安全恢复会把它与恢复库中的最新检查点行和链头比对。
- **不**用 pg_dump 完成时间或文件 mtime 近似边界。
- 检查点缺失、sidecar 不匹配、dump 哈希不符、恢复库链头不等于检查点 → 安全恢复停止；普通 S12-C dump 只能原始直恢复/人工核验。
- 检查点备份默认本地生成；`critical-events-backup-all.sh` 可按 schedule 自动上传 COS/独立介质。真实 COS 尚未验证；普通 S12-C dump 仍不能用于安全恢复，只有 dump+sidecar 可以。

## 3. 全新服务器场景

### 3.1 准备代码与运行环境

1. 新服务器安装 Docker Engine + compose plugin；准备基础安全（SSH key、防火墙、时区）。
2. 从 Git 取**已经所有者批准的生产版本**（本轮不 push；使用本地/备份中的 commit；不要把未验收开发版直接上线）。
3. 恢复生产环境配置（全部来自离线秘密保险箱，绝不从旧服务器唯一副本临时猜）：
   - `deploy/.env`（数据库口令、`SESSION_SECRET`、域名、邮件等）；
   - `deploy/.backup.env`、`deploy/.backup.key`、邮件/心跳配置（若启用备份）；
   - 若启用 S13-I：`deploy/.critical-events-relay.env`（写身份+事件密钥）和离线保管的 `deploy/.critical-events-restore.env`（恢复身份，不放在生产）；
   - 域名 DNS 指向新服务器；ACME 邮箱。
4. `./deploy.sh --version <version>`（或按部署文档构建/启动）；**在恢复数据前不要对外宣称可用**。
5. 检查 `docker compose ps`、`/api/v1/health`、`admin:list`、Caddy 证书。

### 3.2 取得并验证旧备份

- 普通备份：`./offsite-fetch.sh <ref>`（现有脚本 `--latest` 只找 daily；更老备份必须知道精确 `--ref`）。
- 若使用检查点备份：把 `*.dump` 和 `*.dump.checkpoint.json` **一起**从灾备介质取回，不能只取其中一个。自动流程默认本地保留 7 天（`CRITICAL_BACKUP_LOCAL_KEEP_DAYS`），异地成功后才清理更老本地副本。
- 校验：原 `verify-dump.sh`（临时库恢复 + 行数/关键表）或新 `critical:verify`（事件）。
- **永远保留原始备份文件只读副本**；不要覆盖/修改唯一可用备份。

### 3.3 恢复数据库

- **原始直恢复**：`./emergency-raw-restore.sh <dump>`（默认 API/web 停止），或原 `restore.sh`（自动启动 API）。
- **安全恢复**：先 `pg_restore` 到隔离库（例如 `libevra_restore_<ts>`），按 §1A 执行检查点/事件/预览/apply；验收后再切换生产。
- 恢复后按需恢复健康检查、备份 timer、域名/证书、监控告警；**这些是独立于数据库恢复的步骤**。

### 3.4 重新开放公网（必须单独批准）

见 §5；恢复数据库成功不等于可以开放。

## 4. 关键限制

- 事件登记簿不会恢复备份之后新增的普通业务数据（新建账本、交易等）；缺失资源进入 `manualReview`。
- 事件日志缺失、损坏、哈希链断裂、manifest 头不匹配时，安全恢复必须停止。
- 原始备份不因 S13-I 故障而不可用；S13-I 故障也不阻止 S12-C 工作（未修改 backup.sh / backup-all.sh）。
- 安全恢复不能自动重建备份之后新建的账号/账本；不会凭空创建。
- **剩余故障窗口**：数据库提交成功、relay 异地确认前整台服务器彻底损坏时，远端没有该事件，安全恢复无法得知这次操作。本设计没有消除这个窗口，只在 API 响应层面不谎报成功；原始直恢复仍可用。
- P0 之外的部分 P1 路径仍有非原子事件窗口（见设计报告 §3），不能声称全部事件“恰好一次”。
- 本地 `critical_events` 没有清理策略；远端前缀生命周期必须覆盖所有仍可恢复的历史备份，不能机械写 365 天。

## 5. 人工应急上线（与数据库恢复分开）

只有所有者可以决定。至少需要：
1. 确认恢复的是哪份备份、检查点 ID、适用时间/链边界；
2. 列出没有恢复的安全事件/人工核查项；
3. 决定是否接受旧密码/旧会话风险，并执行管理员密码重置；
4. 记录决定人、时间、范围和回滚点；
5. 重新开放流量。

**不要把“数据库已经恢复”当作“安全状态已经恢复”。**

## 6. 上线前必须批准的云配置（当前未操作）

- 新 COS 前缀 `critical-events/v1/` 独立生命周期，覆盖所有仍可恢复的历史备份；不与 daily/monthly 混用。
- relay 写身份：仅 `PutObject/HeadObject`，资源限该前缀；无 `GetObject/ListBucket/DeleteObject`。
- 恢复只读身份：`GetObject/ListBucket`，不常驻服务器。
- `CRITICAL_EVENT_KEY`：32 字节，离线保险箱保存副本；轮换使用 `CRITICAL_EVENT_KEY_ID` + `CRITICAL_EVENT_PREVIOUS_KEYS`，旧 v1/旧 keyId 事件仍可解密，不能直接丢弃旧密钥。
- 对象不可覆盖必须用测试前缀实测（见生产接入清单 §6.2），不能只相信“只给了 PutObject”。
- 是否采用独立桶（可选；第一版使用现有桶独立前缀）。
- 检查点备份的异地保存位置：安装 `libevra-critical-backup.timer`，配置 `CRITICAL_BACKUP_OFFSITE=cos` 或独立灾备介质；恢复机用 `critical-events-fetch-backup.sh` 取回。
- relay 心跳/保护状态接入告警：`critical:status` 或管理员保护状态接口 alarm。
- 是否接受 §4 的剩余故障窗口；若要消除，需要同步异地提交/共享日志服务。

## 7. 本地验证

- `test/criticalEvents.test.ts`：哈希链/加密对象、relay/COS 不可用时 P0 仍成功、pg_notify 立即唤醒、失败指数退避、receipt 业务/保护分离与过期、Idempotency-Key、对象缺失/损坏、删除/注销重放、角色变化、密码旧凭据失效、缺失目标不虚构。
- `test/criticalFullRestore.test.ts`：本机 PostgreSQL 真实 `pg_dump` + 精确检查点 + `pg_restore` 到独立库，验证只读预览与安全重放。
- `test/criticalCheckpointShell.test.ts`：实际执行 `critical-events-backup.sh`，在 pg_dump 慢速包装器睡眠期间删除账本，恢复后核对检查点行/链头/sidecar；并演练自动备份→异地复制→取回。
- `test/criticalRelayLatency.test.ts`：独立 relay 进程、10 秒轮询间隔，实测删除提交→远端 ack 约 **80–100ms**；relay 停止时注销成功，重启后积压自动补传。
- `test/criticalKeyring.test.ts`：v2 keyId、旧 v1 信封 previous key 解密、未来轮换兼容。
- 真实 COS 未测试；COS/CAM/生命周期/密钥演练需所有者单独授权（见 `S13-I-生产接入清单与未来管理接口.md`）。
