# S13-H 账号注销、服务器数据删除与账本生命周期

> 2026-10-18。**本地开发版本 `1.13.12`，仅本地隔离测试数据库验证；未 push、未部署、未修改生产。**
> 本轮按 L3 处理：涉及真实删除、共享账本、会话、离线同步、备份恢复与管理权限。

## 1. 实现边界

### 账号注销不物理删除 `users` 行

现有 schema 中 `books.created_by` 与 `transactions.user_id` 都是 `ON DELETE CASCADE`。物理删除用户会：

- 销毁他创建的整本共享账本，包括其他成员的账目；
- 销毁他在别人共享账本里记录的交易；
- 删除他发出的邀请、分享链接与历史关联。

因此注销采用**保留行 + 匿名化**：

- `users` 行保留，作为共享交易/成员/历史的外键锚点；
- `username` 改名为 `closed_<uuid>`，`displayName` 改为「已注销账号」；
- 密码改为不可用随机凭证，清空恢复码；
- `closedAt`、`disabledAt` 写入，`isAdmin=false`，撤销管理授权；
- 删除/撤销会话、通知配额、收件通知、未处理邀请、未用邀请码、分享链接；
- 写入 `account_tombstones`，保留账号 UUID、账号编号、创建/注销时间、处理汇总；
- 旧会话行先标记 `revoked_at`，旧设备下一次请求收到 `401 account_closed` 后删除该行。

**这是有意的安全边界，不是“假注销”**：账号不能再登录/同步，个人可删除数据按账本规则处理；但不会用危险级联破坏其他成员的数据。真正物理删除用户需要先完成共享账本所有权模型与历史归档模型，本轮未做。

## 2. 账本规则

### 共享账本（仍有 ≥2 位有效成员）

- 任意成员（包括创建者）选择「删除/退出」都只退出协作；
- 写 `book_members.left_at`，会员行保留；
- 其他成员、账目、留言、分享链接不受影响；
- 当前管理者退出时，管理权在同一事务内移交给最早加入的**有效编辑者**；没有编辑者则拒绝，避免账本失去管理者；
- 客户端清理该账号本账本本地数据。

### 单人账本 / 最后一位有效成员

- **归档**：写 `archived_at`（服务器 UTC），`self_restore_until = archivedAt + 60 天`，
  `scheduled_purge_at = archivedAt + 365 天`；数据保留，普通业务 API 不可访问。
- **永久删除**：写入 `book_tombstones` 后，先删 transactions（因 `category_id` 是 RESTRICT），
  再删账本；账本 UUID、编号、创建日期、创建者/删除者、时间、计数、结果保留在墓碑中。
- 已删除账本 ID 不再由 API 生成/复用；针对它的业务请求返回 `410 book_deleted`。

### 归档生命周期

| 时间 | 行为 |
|---|---|
| 0–60 天 | 原账号可自行恢复；重新归档时从新归档时间重新计算完整期限 |
| 60–365 天 | 普通恢复关闭；原账号可提交人工恢复申请，管理员核验后批准/拒绝 |
| 满 365 天 | 每日清理任务在到期后 **24 小时内**自动清理，留下墓碑 |
| 清理开始 | 设置 `purge_started_at`，恢复与清理都检查它，二者互斥 |
| 清理失败 | 回滚删除、记录 `purge_attempts/purge_last_error`，unit 失败并下次重试，不静默无限保留 |

- 自动清理是独立脚本 `lifecycle:purge`，不是 API 进程内定时器；使用 PostgreSQL advisory lock 防并发。
- 部署侧新增 `deploy/systemd/libevra-lifecycle.{service,timer}`：每天 **03:30 Asia/Hong_Kong**；
  所以界面写「预计自动清理日，到期后 24 小时内执行」，而不是承诺精确到秒。
- 恢复申请有 `deadline_at`；批准会立即恢复，不存在“已批准但等待清理”的状态；过期申请会变为过期并允许清理。

### 已注销账号保留的归档

- 注销时若保留归档账本，服务端生成**一次性恢复凭证**（32 位十六进制），只保存 SHA-256 哈希，
  响应中只显示一次；
- 之后通过 `/recover-archive` 提交：原账号编号 + 恢复凭证 + 原账本编号 + 接收账号编号；
- 必须由管理员核验资格并批准；不会仅凭账本编号恢复，也不会自动交给任意账号；
- 凭证丢失时系统无法还原；管理员只能按人工核验流程处理，这是现有账号体系下的身份验证边界。

## 3. 数据删除（“删除服务器数据”）

- 共享账本：退出协作，保留其他成员数据；
- 单人账本：永久删除；
- 已归档账本：永久删除；
- 撤销会话、邀请、分享链接、通知配额；账号停用并匿名化；
- 不生成归档保留与恢复凭证；
- 与注销相同：**不物理删除 `users` 行**，不破坏共享账本外键。

## 4. 离线与旧设备

- `book_deleted` / `book_deleting` / `book_archived` 是明确生命周期状态；同步队列遇到它们时停止该账本重试并清除本地该账本数据；
- 旧设备恢复联网后通过 `/auth/me` 的 `401 account_closed` 得知注销，清理当前账号本地数据并回到登录页；
- 完全离线设备无法立刻收到通知；服务端拒绝其后续同步，联网后退出。**不声称所有设备已即时物理清除。**

## 5. 墓碑与审计

- `book_tombstones`：书 UUID（主键，无外键，永不随删除消失）、编号、原创建时间、原创建者账号/ID、
  归档时间、自助恢复截止、原定清理时间、实际清理时间、删除方式/原因、操作者快照、成员/交易计数。
  不保存交易正文、备注、附件或账本名称。
- `account_tombstones`：用户 UUID、账号编号、创建/注销时间、方式、资源处理汇总、恢复凭证哈希。
- `book_lifecycle_events`：归档/恢复/退出/管理权移交/申请/批准/清理失败/清理完成，无外键故墓碑可读。
- 管理员恢复操作写 `AdminAuditLog`（`book.recovery.approve|reject`、`book.purge`），并检查管理员密码；
  管理员**看不到**账本名称、交易、备注或金额，恢复申请只含编号与生命周期元数据。

## 6. 备份与灾难恢复

调查结论（只读，未修改生产 COS）：

- 实际 COS 生命周期：`daily/` **70 天**（历史版本 42 天、分片 14 天），`monthly/` **365 天**（63/21 天）。
  仓库旧文档曾写 30/35 天，且 `baseline/` 400 天从未实现；已修正 `deploy/README.md` 与 `backup-all.sh` 注释。
- 主库 365 天是**主库归档清理期限**；历史加密备份仍按上述真实生命周期存在。不能对外宣称“删除后 365 天后任何副本都不存在”。
- 灾难恢复后旧 dump 会复活已删除账本/已注销账号；因此新增
  `lifecycle:replay-tombstones`，恢复流程要求先重放墓碑再启动 API。该脚本只删除墓碑已证明删除的账本，
  并重新匿名化已注销账号。
- 未改 COS 生命周期、未改生产恢复脚本、未安装 systemd timer；部署手册已增加操作步骤。

## 7. 页面

- **设置 → 账号与数据** `/settings/account-data`：账号导出、逐本归档/删除、已归档摘要与恢复/人工申请、删除服务器数据、注销账号；
- **账本设置 → 危险操作**：共享账本退出；单人账本归档/永久删除；
- **协议拒绝后的账户处理**：保留导出、退出登录，并打开同一「账号与数据」页面；该路径不受协议门禁阻塞；
- **公开恢复** `/recover-archive`：恢复凭证 + 编号提交申请；
- **管理员 → 账本恢复申请** `/admin/lifecycle`：列表、批准/拒绝、二次密码验证；无账本内容。
- 所有确认层沿用 S13-G 的统一弹窗/现有视觉。

## 9. 明确未完成 / 需要所有者决定

1. **物理删除 `users` 行**：因共享账本 CASCADE 风险未实现；当前是安全匿名化注销。若合规要求真正删除，
   必须先决定共享账本所有权、历史归属和备份重放规则。
2. **身份核验强度**：归档恢复由管理员人工核验恢复凭证；没有实名/身份证明体系，无法自动判断“申请人是不是本人”。
   凭证丢失时也没有自动找回路径。
3. **生产清理定时器尚未安装/部署**：代码、脚本和 unit 已本地就绪，但按任务要求未部署；生产仍为 1.13.09。
4. **正式 COS 生命周期/备份期限**：实际规则由腾讯云控制台维护，仓库只能记录和重放，不能从代码保证。
5. **旧版 `disposedAt` 弃置**仍保留为历史功能；新 UI 已改用 S13-H 归档/删除语义，旧数据不做自动迁移。
6. 完全离线设备的本地清除无法即时完成；只能在其联网时执行。
