# S13-I 生产接入清单、管理平台接口与 COS 演练计划

> 2026-10-18，**只读调查 + 本地代码/模板**；本文件不授权也不是执行记录。生产 COS、CAM、服务器、真实密钥、数据库均为未修改状态。

## 1. 现有事实（只读调查）

- 备份是整库 `pg_dump -Fc`；原 `restore.sh` 只依赖 `deploy/.env` + compose + 本地 dump，不读事件表/COS。
- API 容器**没有** COS SDK、rclone、gpg、COS 凭据或宿主 `deploy/` 挂载；COS 只在宿主机脚本中。
- 现有 COS：`daily/` 70 天（历史 42、分片 14），`monthly/` 365 天（历史 63、分片 21），无 `baseline/`；cam 文档旧策略列过未使用的 baseline，未列实际使用的 monthly，需要所有者按控制台实际核对。
- 现有上传身份无 Get/List/Delete；恢复身份不在服务器。
- `deploy/backups/` 覆盖原备份轮转、last-run/last-local、`.backup.lock`；新机制使用独立的 `deploy/critical-backups/`，不共用锁/前缀/状态文件。
- **触发方式**：事件与业务同事务写入；提交时 `pg_notify` 唤醒 relay，正常上传立即开始；轮询仅补偿。业务 API 不等待 ack，relay/COS 故障不会返回 503。
- **保护状态**：`critical:status`/管理员接口显示 pending、最老未确认、最近上传、连续失败、relay 心跳、链完整性；alarm 时 `critical-events-health.sh` 走现有邮件告警。
- `deploy/tests/run.sh` 是假 Docker/curl 的 64 项脚本测试，不能证明真实 COS 行为。
- 本轮当前开发机**没有 Docker/WSL**，`critical-events-backup.sh` 已用“本地 PostgreSQL 隔离模式”实际执行并验证（含备份生成中删除、恢复检查点/链头/sidecar）；Docker 分支共用同一脚本逻辑但**尚未在 Docker 环境实测**，上线前必须在 staging 的 compose 栈重跑一次。

## 2. 精确备份检查点（已实现）

- 新命令：`deploy/critical-events-backup.sh`（使用 db 容器内的 PostgreSQL 17 `psql`/`pg_dump`）。
- 机制：
  1. 在专用 advisory lock 下插入 `critical_backup_checkpoints` 行（记录当前 `critical_chain` 头）。
  2. 在同一 REPEATABLE READ 事务导出 PostgreSQL snapshot，随后让事件写入继续。
  3. `pg_dump --snapshot=<exported>` 使用该固定快照；检查点行本身在 dump 内。
  4. 写出 `<dump>.checkpoint.json`，包含 dump SHA-256、大小、检查点 ID、链序号/哈希。
- 不用 `pg_dump` 完成时间近似；安全恢复从**恢复后的数据库里的最新检查点行**取边界，并与 sidecar 的 ID/链头/哈希匹配。
- 普通 S12-C dump：没有 sidecar/检查点 → **安全恢复拒绝**，只能原始直恢复或人工核验；这是有意的 fail-closed。
- 检查点缺失、dump 哈希不符、sidecar 与恢复库检查点不符、恢复库链头不等于检查点 → 停止，不猜测。
- 自动流程：`deploy/critical-events-backup-all.sh` 可被 systemd timer 调度，并把 dump+sidecar 独立复制/上传到异地。本地 FS 演练已验证；真实 COS 未执行，需要所有者批准 `critical-backups/checkpoints/` 前缀/CAM。

## 3. P0 operation receipt（已实现）

- **业务成功与异地保护完全分离**：PostgreSQL 业务事务提交后立即返回成功；COS/relay 故障不会导致 503，也不会把删除/注销描述成失败。
- `critical_operations` 表；账号注销、删除服务器数据、永久删除账本、成员移除/角色变更/退出、分享链接撤销、管理员停用/恢复/邀请码撤销返回 `operationId`、`operationReceipt`、`operationStatusPath`。
- 查询：`GET /api/v1/operations/<id>`，请求头 `X-Operation-Receipt: <token>`；不需要会话，账号注销后仍可查询。token 24 小时过期，不接受 URL 查询参数（避免代理/访问日志长期泄露）。
- 返回两个独立状态：
  - `status/businessStatus = pending|completed|failed`：业务事务是否完成；
  - `protection.state = pending|partial|protected|failed`：事件是否已上传确认。
  - `completed + pending` 表示“操作已完成，备份增强尚未上传”，不是“删除未完成”。
- relay 补传后 `protection` 自动变化，不需要用户重试。
- 可选 `Idempotency-Key` 请求头（16–128 字符）：同一 P0 操作重复提交返回 `409 operation_already_started` 和原 operationId，不重复执行不可逆操作。客户端应使用原 receipt 查询状态。
- 安全边界：token 只存 SHA-256，24h 过期；只走请求头，不进 URL；不得把 `X-Operation-Receipt` 写入访问日志/前端埋点；它只返回业务+保护状态，不恢复会话、不提供数据内容。
- 204 删除成员响应在 `X-Operation-Id` / `X-Operation-Receipt` 响应头中携带回执；其他 P0 在 JSON body 中返回。

## 4. 恢复差异预览（已实现）

`critical:preview` 读取隔离库和远端事件，输出 JSON：

- checkpoint id/label/chain seq/hash；
- 事件组、逐条事件类型/时间/actor/target 可读标签；
- `decision = auto | manual | missing_target`；
- `rollbackRisk`；
- 自动/人工/缺失/风险计数；
- 明确提示“预览不修改数据库、不重放”。

该接口/命令不删除会话、不写任何表、不修改恢复库。

| 隔离恢复 | 人工 `pg_restore` 到新的隔离库；安全恢复前不要启动公网 API |
| 执行安全恢复 | `critical:apply-safe ... --report ...` |
| 查看恢复报告 | JSON 报告（checkpoint、applied、manualReview、notes） |

未来管理平台必须把**恢复数据库**、**使用解密密钥**、**开放公网**拆成三个独立权限动作；任何覆盖数据库/开公网/使用密钥的动作不能由同一个“继续”按钮完成。

## 6. 腾讯云配置清单（待所有者批准，本轮未改）

### 6.1 前缀与生命周期

- 建议前缀：`critical-events/v1/`（events/、manifests/）；检查点备份使用独立前缀 `critical-backups/checkpoints/`。
- 生命周期必须覆盖**所有仍可恢复的历史备份**；当前普通备份 daily 70 天、monthly 365 天。若保留任何超过 365 天的备份/手动归档，事件前缀必须相应延长；不能机械写 365。
- 与 daily/monthly 规则分开；不与原备份前缀共用；建议开启版本控制/对象锁只作为额外保护，但必须先实测与 `x-cos-forbid-overwrite` 的组合行为。
- 不在本前缀设置会删除“唯一远端事件副本”的规则；若设置过期，必须证明所有更老备份已不可恢复或已退役。检查点前缀同样不能被原 daily/monthly 规则误删，且必须覆盖最长可恢复备份期限。

### 6.2 CAM 写身份（relay + 检查点备份）

- relay 写身份资源：`critical-events/v1/*`。
- 检查点上传身份资源：`critical-backups/checkpoints/*`；可使用现有 S12-C 上传身份的额外前缀授权，或独立身份。
- 动作：`PutObject`、`HeadObject`；**不授予** `GetObject`、`ListBucket`、`DeleteObject`、`PutBucket*`（检查点上传还需要读本地文件，不涉及 COS Get）。
- **当前 checkpoint 写权限的最小增量（复用现有 S12-C 上传身份）：**
  - resource 增加：`qcs::cos:ap-hongkong:uid/1505362843:libevra-backup-1505362843/critical-backups/checkpoints/*`
  - 仅增加：`name/cos:PutObject`、`name/cos:HeadObject`
  - 不增加 Delete/Get/List；`daily/`、`monthly/`、`baseline/` 规则不变。
  - 当前 dump 约 100KB，rclone 单次 PUT 足够；若未来 dump 超过 rclone 分块阈值，才需要评估 `InitiateMultipartUpload`/`UploadPart`/`CompleteMultipartUpload`/`AbortMultipartUpload`，不要预先授予。
- 恢复只读身份（离线）需要增加同一 checkpoint 前缀的 `GetObject`、`HeadObject`、`GetBucket`（用于 `critical-events-fetch-backup.sh` 的列表）；不得给写权限。`GetBucket` 必须使用桶级资源 `.../libevra-backup-1505362843/*`，并加 `condition.string_equal.cos:prefix`（`critical-backups%2Fcheckpoints%2F`）；checkpoint fetch 已使用 `rclone lsf --fast-list`，一次只请求该精确前缀，避免探测 year/month 子前缀。
- 检查点测试步骤（隔离或经批准的非生产前缀）：1) 用现有 S12-C 上传身份向 `critical-backups/checkpoints/test/` 上传一个临时 dump+sidecar；2) HEAD 大小一致；3) 用恢复只读身份列出/下载并校验；4) 用 `critical-events-fetch-backup.sh --latest` 验证路径；5) 测试对象暂不删除，待所有者另行批准（不增加 Delete 权限）。
- 不能把“只有 PutObject 就不可覆盖”当作结论：2026-10-18 真实测试在测试前缀上发现**同 key 第二次 PUT 返回 200 并覆盖当前内容**，即使桶已返回 `x-cos-version-id`。必须用独立测试桶/对象锁再验证；生产不能依赖客户端 header。
验证项：
  1. 首次 PUT 成功；
  2. 相同 key 再次 PUT（带 `x-cos-forbid-overwrite: true`）收到冲突/拒绝，原对象字节不变；
  3. HEAD 返回原 ETag/元数据；
  4. 写身份执行 GET/LIST/DELETE 均被拒绝。
- 若控制台/API 对同名覆盖的限制不满足，则需开启**版本控制 + 拒绝覆盖策略/对象锁**或改用独立桶；不能降级为“相信客户端”。

### 6.3 CAM 恢复只读身份

- 资源：`critical-events/v1/*` 和 `critical-backups/checkpoints/*`。
- 动作：`GetObject`、`HeadObject`、`GetBucket`；无写/删。
- **`cos:prefix` 条件在 2026-10-18 的测试中未生效**：读身份列测试前缀也 403。不要因此改为整桶 GetBucket；改用独立测试桶（整桶读安全）或证明桶策略/临时密钥能严格限制 List。
- 不常驻生产服务器，只在管理员本机/离线恢复机使用。
- 与写身份分离；不得复用 S12-C 上传身份。

### 6.4 事件密钥

- `CRITICAL_EVENT_KEY`：32 字节随机值（base64/64 hex）。
- 生成：`node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`。
- 保存：离线灾难恢复保险箱 + 管理平台本机安全存储；**不能只放在同一台生产服务器**。
- 轮换：代码已支持 `CRITICAL_EVENT_KEY_ID` + `CRITICAL_EVENT_PREVIOUS_KEYS`。新事件写入 v2 信封并记录 keyId；旧 v1（无 keyId）和旧 keyId 事件用 previous key 解密。轮换时**所有 API/relay/verify/apply 进程**必须同时带旧密钥；不要删除旧密钥直到旧对象过期。尚无自动重加密，旧事件保持旧密钥。
- 丢失：历史事件不可解密；原始备份直恢复仍可工作。
- 与 `.backup.key`（GPG 备份口令）分开保管，互不复用。

### 6.5 relay 部署/回滚（待批准后执行）

- 新增 sidecar：`deploy/critical-events-relay.compose.yml`，无端口，共享数据库，仅 relay env 有写身份。
- 正常触发：事件事务内 `pg_notify` 唤醒 relay；轮询仅补偿。relay 心跳/状态供管理员保护状态接口和 `critical:status` 告警。
- 首次上线前先跑测试前缀；生产启用前先手动 `critical:relay --once`（在测试 DB/测试前缀）并核对对象/ack。
- 回滚：停 relay——业务**不会** 503，只会让 `protection` 停在 pending/failed 并触发告警；普通备份不受影响。不要删 COS 事件对象。恢复原 API 版本若不含 S13-I，则 P0 不再写事件——上线前必须明确这是否可接受。

### 6.6 自动检查点备份（待批准后安装）

- `critical-events-backup-all.sh` + `systemd/libevra-critical-backup.service/.timer`（每日 04:00 HKT，`Persistent=true`）。
- `CRITICAL_BACKUP_OFFSITE=cos` 时用 `COS_UPLOAD_*` 身份把 GPG 加密 dump 与 sidecar 上传到 `critical-backups/checkpoints/<YYYY>/`；恢复机用 `critical-events-fetch-backup.sh` 和**只读** `COS_RESTORE_*` 身份取回/解密/校验。
- 生命周期必须覆盖所有仍可恢复的历史备份；该前缀与 daily/monthly 分开，不能被原规则误删。
- 只能使用**测试前缀**先演练；本轮未修改真实 COS/CAM。

### 6.7 保护状态告警（待批准后安装）

- `critical:status` 读取 pending/failed、最老未确认时间、最近上传、连续失败、relay 心跳、链完整性；alarm 时退出码 1。
- `systemd/libevra-critical-health.service/.timer` 每 5 分钟运行 `critical-events-health.sh`；异常调用现有 `alert-mail.sh` 的 `critical-protection` 阶段，不会影响业务/S12-C 备份。
- 管理员接口：`GET /api/v1/admin/lifecycle/critical-events/status`。

### 9.10 旧应用回滚边界（通用规则）

1. 先停新 API/relay/所有 S13-I timer；保留数据库、COS 事件对象和检查点。
2. 若只是代码问题且数据库可保留，**优先前滚修复或使用新版本整 API 停机方案**；不要直接启动未验证的旧应用。
3. **任何旧应用版本在连接已经升级的生产数据库前，都必须完成兼容性和权限安全验证；未通过不得启动。** 这不是对某个版本号的永久禁令，而是针对“旧应用 + 新数据库”运行条件的门槛。
4. 已知不兼容：原始 `1.13.09`（commit `814d797`）实测会重新访问已归档/已弃置账本，且没有 critical 事件记录机制；**当前不得直接将其作为生产回滚版本**，除非另行修补并重新通过同一套验证。
5. 验证至少覆盖：迁移版本/schema、已注销账号、成员/管理员撤销、归档/弃置/删除可见性、critical 事件写入或危险写操作禁用、会话与普通记账数据完整性。
6. 启动任何旧应用前查询：
   - `books.archived_at` / `books.disposed_at` 是否非空；
   - `critical_events.delivery_state <> 'acked'` 是否存在；
   - 是否有新生命周期/恢复申请状态。
   任一非空且旧应用未通过验证：**不得启动**。
7. 若必须恢复数据，使用 S12-C 原始备份直恢复（不依赖 S13-I），并接受回退到备份时点；恢复库隔离验证后才开放。
8. 不允许通过删除 `critical_*` 表或 COS 对象来“修复”回滚；这会破坏保护证据。

### 9.11 API 停机保护流程（已隔离演练）

> 适用于“高风险业务模块故障、无法安全继续服务”且不启动旧版回滚的情况。
> 原则：**数据完整性和权限安全优先于可用性；允许临时停止 API。**

1. 停止对外 API：
   ```bash
   cd /srv/libevra/deploy
   docker compose -f docker-compose.prod.yml stop api
   ```
   **不要** `down -v`、不要删除 db/api 卷、不要执行 down migration、不要删除 `critical_*` 表。
2. 保留数据库、relay、S12-C 与检查点 timer；relay 正常时继续补传 pending。若 relay 本身故障，再单独停 relay。
3. 保护状态检查使用**一次性容器**，不依赖运行中的 API：
   ```bash
   docker compose -f docker-compose.prod.yml run --rm --no-deps -T api \
     pnpm --filter @libellum/api critical:status
   ```
   该命令只读，不监听端口，退出码直接反映保护状态。
4. 停机期间 S12-C 原备份和 S13-I 检查点备份照常运行；检查数据库容器健康。
5. 修复后按 **relay → API** 顺序启动：
   ```bash
   docker compose -f docker-compose.prod.yml \
     -f critical-events-relay.compose.yml up -d critical-relay
   docker compose -f docker-compose.prod.yml up -d api
   ```
6. 验证：`/api/v1/health`、登录/普通记账、账本/统计、归档/弃置限制、`critical:status` pending/chain、S12-C 与检查点备份日志。
7. 恢复告警：确认 health timer 的下一次正常检查与恢复通知；不要把“API 已恢复”误当成“保护层已恢复”。
8. 本流程的局限：无零停机、无维护页；API 停止期间用户无法进行服务器写入；relay/事件密钥/COS 同时故障时 pending 无法补传；数据库/宿主机丢失不在本流程范围。

### 9.12 维护窗口首次启用顺序（生产，待授权）

> 目标：**在 API 接受任何新的关键业务写入之前，保护链、relay、首个有效 checkpoint 和告警都已就绪。**
> 不能假定“迁移完成后先起 API、再补 checkpoint”是安全的；首次 checkpoint 必须是空链基线。

1. **前置 gate**
   - 测试对象已按精确清单清理，Reader 复列返回 0；
   - 事件桶/CAM/密钥/relay env/timer 配置已由所有者批准；
   - 当日 S12-C 备份窗口避开维护窗口。

2. **冻结对外写入**
   - `docker compose -f docker-compose.prod.yml stop web api`；
   - 保留 `db` 运行；DB/API 无公网端口；
   - 不执行 `down -v`，不删除卷/表/COS/备份。

3. **迁移前备份与隔离验证**
   - 运行 S12-C 完整备份（本地+异地+恢复演练）；
   - 另做独立 `pg_dump`，记录 34 个迁移、数据基线、sha256；
   - 在隔离库恢复并核对 baseline；不把恢复库开公网。

4. **迁移 34→45**
   - 只运行 migrate 容器；API 保持停止；
   - 校验迁移数 45、`critical_chain`/`critical_events` 等表存在、数据基线未变；
   - 不执行 down migration。

5. **配置事件密钥与保护工具 / 首个 checkpoint**
   - 把事件密钥/keyId 写入 `.critical-events-relay.env`（600）与备份工具环境；
   - 此时 API 停止，`critical_chain.last_seq=0`；
   - 用候选 `critical-events-backup.sh` 生成 **空链 checkpoint**；
   - 校验 sidecar、chain=0、dump hash；
   - 这是首个合法安全恢复基线；**必须在 API 接受写入前完成**。

6. **先启动 relay，不启动业务**
   - 启动 `critical-relay`（只读 DB、COS 写）；事件表为空，relay 只写心跳；
   - 用一次性容器执行 `critical:status`：`runtime=relay`、relay running、chain complete；确认没有 pending。

7. **API 内部冒烟**
   - 启动 API，但 **web/Caddy 仍停止**，公网无入口；
   - 通过内部网络/exec 检查 `/api/v1/health`、登录、只读账本/统计；
   - 不做会生成关键事件的新增/删除/归档/注销操作（除非使用隔离测试账户并明确记录）；
   - 再查 `critical:status`：链仍为 0，relay running，无 pending。

8. **开放用户访问**
   - 启动 web/Caddy；
   - 检查公网 health、版本 1.13.15、普通读取；
   - 观察首批业务操作：P0 返回成功后 relay 异步补传，pending 最终归零。

9. **安装并启用 timer/告警**
   - 安装 `libevra-critical-backup.timer`、`libevra-critical-health.timer`；
   - 先手动触发一次检查点备份/健康检查，确认 S12-C 原 timer 不受影响；
   - 确认告警收件人和恢复通知；进入 24h 观察。

**一致性关系：**

- checkpoint 通过独占 advisory lock + REPEATABLE READ 快照 + `pg_dump --snapshot` 获取；事件写入使用对应共享锁，因此 checkpoint 链头与 dump 属于同一一致性快照。
- **首个 checkpoint 是 chain seq=0**；API 在它之后才开始产生 seq=1、2… 的事件。顺序错误（先 API 写入、后补空链 checkpoint）会让首个“基线”不是真正的空链基线。
- relay 只负责上传，不追加事件序号；API 的事务提交才追加。
- 若 API 在 checkpoint 完成后写入，事件序号从 1 开始；checkpoint 之后的远端事件可由 preview/apply 处理；S12-C 备份不提供这条链边界。
- 发生并发写入时，checkpoint 锁会让事件追加等待或进入快照之后，但生产维护窗口仍必须停 API，避免把“可恢复”误当成“首个基线已正确”。

**失败停机：** 任一步失败则停止 API/relay/timer，保留 DB/COS/备份；不执行 down migration；恢复/前滚需另行批准。
