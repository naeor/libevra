# S13-I 生产接入清单、管理平台接口与 COS 演练计划

> 2026-10-18，**只读调查 + 本地代码/模板**；本文件不授权也不是执行记录。生产 COS、CAM、服务器、真实密钥、数据库均为未修改状态。

## 1. 现有事实（只读调查）

- 备份是整库 `pg_dump -Fc`；原 `restore.sh` 只依赖 `deploy/.env` + compose + 本地 dump，不读事件表/COS。
- API 容器**没有** COS SDK、rclone、gpg、COS 凭据或宿主 `deploy/` 挂载；COS 只在宿主机脚本中。
- 现有 COS：`daily/` 70 天（历史 42、分片 14），`monthly/` 365 天（历史 63、分片 21），无 `baseline/`；cam 文档旧策略列过未使用的 baseline，未列实际使用的 monthly，需要所有者按控制台实际核对。
- 现有上传身份无 Get/List/Delete；恢复身份不在服务器。
- `deploy/backups/` 覆盖原备份轮转、last-run/last-local、`.backup.lock`；新机制使用独立的 `deploy/critical-backups/`，不共用锁/前缀/状态文件。
- `deploy/tests/run.sh` 是假 Docker/curl 的 61 项脚本测试，不能证明真实 COS 行为。

## 2. 精确备份检查点（已实现）

- 新命令：`deploy/critical-events-backup.sh`（使用 db 容器内的 PostgreSQL 17 `psql`/`pg_dump`）。
- 机制：
  1. 在专用 advisory lock 下插入 `critical_backup_checkpoints` 行（记录当前 `critical_chain` 头）。
  2. 在同一 REPEATABLE READ 事务导出 PostgreSQL snapshot，随后让事件写入继续。
  3. `pg_dump --snapshot=<exported>` 使用该固定快照；检查点行本身在 dump 内。
  4. 写出 `<dump>.checkpoint.json`，包含 dump SHA-256、大小、检查点 ID、链序号/哈希。
- 不用 `pg_dump` 完成时间近似；安全恢复从**恢复后的数据库里的最新检查点行**取边界，并与 sidecar 的 ID/链头/哈希匹配。
- 普通 S12-C dump：没有 sidecar/检查点 → **安全恢复拒绝**，只能原始直恢复或人工核验；这是有意的 fail-closed。
- 检查点缺失、dump 哈希不符、sidecar 与恢复库检查点不符、恢复库链头不等于检查点 → 停止，不猜测。
- 限制：检查点备份目前是 **opt-in 独立备份**，不是修改 S12-C 格式；它不会自动上传 COS。上线前需要决定其异地保存方式（建议与加密备份一起放入灾备介质/COS 新前缀，并由管理平台列出）。

## 3. P0 operation receipt（已实现）

- `critical_operations` 表；`POST /api/v1/account/close`、`/account/delete-data`、`/books/:id/lifecycle` 的永久删除返回 `operationId`、`operationReceipt`、`operationStatusPath`。
- P0 503 也携带三者；该状态**不恢复账号登录/会话**。
- 查询：`GET /api/v1/operations/<id>?token=<operationReceipt>`，不需要会话；status 为：
  - `pending`：处理中；
  - `committed_unconfirmed`：数据库可能已提交、异地未确认；
  - `confirmed`：完全确认；
  - `failed`：未完成或拒绝；
  - `manual_review`：需要人工核验。
- relay 以后补传时会根据事件行的 `batchId` 自动把 receipt 推导为 `confirmed`；不会恢复已注销账号访问。
- 可选 `Idempotency-Key` 请求头（16–128 字符）：同一 P0 操作重复提交会返回 `409 operation_already_started` 和原 operationId，不重复执行不可逆操作。客户端应使用原 receipt 查询状态。
- **未覆盖**：其他 P0 路由（管理员暂停/撤销、成员移除/角色等）仍返回 503 但暂未生成 operation receipt；它们通常有管理员会话可重试/核对，后续管理平台可统一套用同一 helper。

## 4. 恢复差异预览（已实现）

`critical:preview` 读取隔离库和远端事件，输出 JSON：

- checkpoint id/label/chain seq/hash；
- 事件组、逐条事件类型/时间/actor/target 可读标签；
- `decision = auto | manual | missing_target`；
- `rollbackRisk`；
- 自动/人工/缺失/风险计数；
- 明确提示“预览不修改数据库、不重放”。

该接口/命令不删除会话、不写任何表、不修改恢复库。

## 5. 未来本地管理平台可直接复用的命令/接口

| 能力 | 命令/接口 |
|---|---|
| 列出普通备份 | `deploy/offsite-fetch.sh --list`（现有，只列 daily）、`deploy/backups/*.dump` |
| 列出检查点备份 | `deploy/critical-backups/*.dump` 及其 `.checkpoint.json` |
| 验证普通 dump | `deploy/verify-dump.sh <dump>` |
| 验证事件登记簿 | `pnpm --filter @libellum/api critical:verify --dir <fetched>` |
| 创建检查点备份 | `deploy/critical-events-backup.sh [label]` |
| 预览差异 | `pnpm --filter @libellum/api critical:preview --dir ... --dump ... --checkpoint ... --report ...` |
| 隔离恢复 | 人工 `pg_restore` 到新的隔离库；安全恢复前不要启动公网 API |
| 执行安全恢复 | `critical:apply-safe ... --report ...` |
| 查看恢复报告 | JSON 报告（checkpoint、applied、manualReview、notes） |
| 查询 P0 操作状态 | `GET /api/v1/operations/:id?token=...` |
| 原始直恢复 | `deploy/emergency-raw-restore.sh <dump>` 或原 `restore.sh` |

未来管理平台必须把**恢复数据库**、**使用解密密钥**、**开放公网**拆成三个独立权限动作；任何覆盖数据库/开公网/使用密钥的动作不能由同一个“继续”按钮完成。

## 6. 腾讯云配置清单（待所有者批准，本轮未改）

### 6.1 前缀与生命周期

- 建议前缀：`critical-events/v1/`（events/、manifests/、可选 checkpoints/）。
- 生命周期必须覆盖**所有仍可恢复的历史备份**；当前普通备份 daily 70 天、monthly 365 天。若保留任何超过 365 天的备份/手动归档，事件前缀必须相应延长；不能机械写 365。
- 与 daily/monthly 规则分开；不与原备份前缀共用；建议开启版本控制/对象锁只作为额外保护，但必须先实测与 `x-cos-forbid-overwrite` 的组合行为。
- 不在本前缀设置会删除“唯一远端事件副本”的规则；若设置过期，必须证明所有更老备份已不可恢复或已退役。

### 6.2 CAM 写身份（relay）

- 资源：`critical-events/v1/*`。
- 动作：`PutObject`、`HeadObject`（如使用 multipart 则仅所需分片动作）；**不授予** `GetObject`、`ListBucket`、`DeleteObject`、`PutBucket*`。
- 不能把“只有 PutObject 就不可覆盖”当作结论：必须用测试前缀验证：
  1. 首次 PUT 成功；
  2. 相同 key 再次 PUT（带 `x-cos-forbid-overwrite: true`）收到冲突/拒绝，原对象字节不变；
  3. HEAD 返回原 ETag/元数据；
  4. 写身份执行 GET/LIST/DELETE 均被拒绝。
- 若控制台/API 对同名覆盖的限制不满足，则需开启**版本控制 + 拒绝覆盖策略/对象锁**或改用独立桶；不能降级为“相信客户端”。

### 6.3 CAM 恢复只读身份

- 资源：`critical-events/v1/*`。
- 动作：`GetObject`、`ListBucket`；无写/删。
- 不常驻生产服务器，只在管理员本机/离线恢复机使用。
- 与写身份分离；不得复用 S12-C 上传身份。

### 6.4 事件密钥

- `CRITICAL_EVENT_KEY`：32 字节随机值（base64/64 hex）。
- 生成：`node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`。
- 保存：离线灾难恢复保险箱 + 管理平台本机安全存储；**不能只放在同一台生产服务器**。
- 轮换：当前对象未带 keyId，不能直接换密钥；轮换前需设计多密钥版本/重加密，或保留旧密钥直到旧对象寿命结束。本轮不实现轮换。
- 丢失：历史事件不可解密；原始备份直恢复仍可工作。
- 与 `.backup.key`（GPG 备份口令）分开保管，互不复用。

### 6.5 relay 部署/回滚（待批准后执行）

- 新增 sidecar：`deploy/critical-events-relay.compose.yml`，无端口，共享数据库，仅 relay env 有写身份。
- 首次上线前先跑测试前缀；生产启用前先手动 `critical:relay --once`（在测试 DB/测试前缀）并核对对象/ack。
- 回滚：停 relay（P0 会 503，不谎报成功；普通备份不受影响）；不要删 COS 事件对象。恢复原 API 版本若不含 S13-I，则 P0 不再写事件——上线前必须明确这是否可接受。

## 7. 测试前缀演练计划（等待所有者明确授权后才执行）

1. 在**非生产测试桶/前缀**创建 `critical-events-test/`，使用独立 CAM 写/读身份。
2. 验证不可覆盖：PUT → 重复 PUT → HEAD/字节比较 → 写身份 GET/LIST/DELETE 拒绝。
3. 用测试数据库运行 `critical:relay --once`，上传若干事件；用只读身份取回并 `critical:verify`。
4. 删除/损坏一个对象，确认 verify/安全恢复停止；不可用日志时确认原始备份直恢复仍可完成。
5. 用测试检查点备份 + 隔离库跑 `critical:preview` 与 `critical:apply-safe`。
6. 演练完成后删除测试前缀对象需所有者单独批准；本轮不执行任何云端操作。

## 8. 新服务器上线前的明确批准点

- 新建/修改 COS 前缀、CAM 策略、生命周期；
- 生成并保存真实 `CRITICAL_EVENT_KEY`；
- 部署 relay sidecar、修改生产 compose/env；
- 启用检查点备份并决定异地保存位置；
- 用生产备份做一次隔离恢复演练；
- 任何覆盖生产数据库或开放公网流量的动作。
