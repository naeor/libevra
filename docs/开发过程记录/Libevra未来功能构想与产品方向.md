# Libevra 未来功能构想与产品方向

> **状态：产品方向讨论整理 / 未批准开发 / 不构成产品承诺。**
> 本文记录所有者讨论后的长期产品目标，不启动 S15，也不代表任何技术方案、时间表或第三方合作已经确定。
> 文中“已实现”只指截至 1.14.19 的真实能力；其余均为**正在研究**或**未来构想**，需要逐项验证后才能进入设计或开发。
> 技术可行性、费用、第三方资格、合规条件和运营模式均**待调查**；不改变“离线优先、数据属于用户、操作可解释、可撤回”的前提。

## 0. 当前实际状态（截至 1.14.19）

**已经实现：**

- 官方云端模式的 Web/PWA + API + PostgreSQL 生产环境；
- 邀请制账号、登录、账本协作和多设备在线使用；
- S14 账本导入、来源身份、冲突处理、可撤销确认、业务锁和 CSV 导入原子性；
- 现有 PWA 离线缓存和离线队列（服务端数据仍以官方云端为主）。

**尚未实现：**

- 真正无须官方服务器的本地单机模式；
- 官方 Android/iOS 原生客户端；
- 自托管部署包和完整的私人服务器运行体系；
- 本地、私人服务器、官方云端之间的用户主动迁移或持续同步；
- 本文列出的 OCR、语音、智能整理、主动财务分析、银行正式授权接口等新能力。

**正在研究：**

- 目前没有启动 S15 或任何上述新功能的开发；本轮仅整理方向和识别待研究问题。

> 后文的“目标产品体验”描述的是希望达到的状态，不能读成已实现、已排期或已承诺。

## 1. 长期产品定位

Libevra 希望发展为一款**开放源代码、可自主部署、同时提供便捷官方云服务**的财务管理软件。

核心理念是：

> 用户可以自行决定使用哪一种客户端、把财务数据保存在哪里，以及是否需要联机和多人协作。

因此：

- Libevra 不应要求所有用户必须注册官方账号；
- 不应要求所有用户必须把财务数据上传到官方服务器；
- 官方云服务、私人自托管服务器和本地单机使用应当是同一产品的不同运行方式，而不是三个需要分别开发、长期维护的独立产品。

可以参考传统游戏客户端与服务器的关系：

- 用户可以直接连接官方服务器使用；
- 用户可以自行部署私人服务器，与家人或朋友协作；
- 用户也可以完全不连接服务器，仅使用本地单机功能。

这三种方式共享同一套产品理念、数据模型和客户端体验；具体技术实现可以不同，但不能把它们做成三个互不相干的产品。

## 2. 三种运行模式

### 2.1 本地单机模式（Local-only）——未来构想

这是未来的重要方向，但不是当前 PWA 离线缓存的简单延伸。

**目标产品体验：**

- Android/iOS 客户端安装后，无须注册账号即可开始使用；
- 无须连接 Libevra 官方服务器；
- 无须部署 NAS、数据库服务器或其他独立服务端；
- 账本和交易数据保存在设备本地；
- 支持基本记账、分类、查询、分析、导入和导出；
- 没有互联网连接时仍可使用核心功能；
- 用户以后可以主动选择把本地账本迁移到官方云端或自托管服务器。

**需要研究：**

- 设备本地数据库、持久化、升级和迁移；
- 设备丢失、损坏、误删后的备份与恢复；
- 数据加密、密钥管理和安全存储；
- 本地单机与现有 PWA 离线缓存、离线队列的边界；
- 未来向官方云或私人服务器的安全迁移与可选同步；
- iOS/Android 对本地数据库、后台任务和系统集成的限制。

**明确不宣称：** 单机模式尚未实现，也不是现有 PWA 离线缓存的升级版承诺。

### 2.2 官方云端模式（Official Cloud）——当前已有，继续保留

继续保留目前 Libevra 的主要使用方式。

**目标产品体验：**

- 用户直接访问官网即可使用网页版；
- 未来也可以通过 Android/iOS 客户端连接官方服务器；
- 官方服务器承担账户认证、账本协作、数据存储和多设备同步；
- 用户不需要自行购买、配置或维护服务器；
- 适合希望开箱即用、由官方托管数据的用户。

现有的 Web/PWA + API + PostgreSQL 架构是这一模式的基础，应尽可能保留已有投资、数据模型和实现成果；不应为了未来模式而重写一套无关的记账系统。

### 2.3 私人自托管模式（Self-hosted）——未来构想

用户可以在自己的 NAS、家庭服务器、小型计算机或其他受支持设备上部署 Libevra 服务端。

这个模式的初衷不是把用户限制在局域网，而是：

> 让不希望把私人财务数据交给第三方云服务器的用户，也能使用多人协作、共享账本和多设备同步等需要服务器的功能。

**主要原则：**

- 官方提供安装包、部署工具和清晰的安装教学；
- 由用户自己的设备承担服务端职责；
- 财务数据默认保存在用户自己的服务器上；
- 官方不需要知道私人服务器的存在；
- 自托管服务器可以不连接官方服务，仍正常使用核心功能；
- 用户可以通过局域网访问；
- 如用户自行配置安全的远程访问，也可以从外部网络连接；
- 外网连接能力主要取决于用户自己的网络配置，不应成为自托管版的人为功能限制；
- 自托管模式应尽量保留官方云端版的核心记账、多人协作和同步功能。

**明确区分：** 自托管不是功能缩水的单机版，也不是简单复制一个静态网页；但具体部署、升级、备份、远程访问和安全责任仍需研究，不能写成已经可用。

## 3. 客户端与服务端解耦

未来客户端和服务器部署位置应当是**两个相对独立的维度**，而不是把“Web/PWA + 官方云”作为唯一组合。

**客户端形态：**

- Web/PWA；
- Android 原生或采用原生 UI 的跨平台客户端；
- iOS 原生或采用原生 UI 的跨平台客户端。

**服务端形态：**

- 官方 Libevra 云服务器；
- 用户自行部署的私人服务器；
- 本地单机模式下的设备本地存储（不依赖远程服务端）。

**目标体验：** 理想情况下，同一个 Android/iOS 客户端可以选择：

1. 本地使用；
2. 连接官方云端；
3. 连接私人服务器。

**边界与约束：**

- 不同服务器的账号和数据默认独立；
- 不应为了家庭版重新开发一套完全无关的记账系统；
- 但也不能直接假定目前的账号认证、数据库、离线队列和 API 可以无修改实现这套架构；
- 连接哪个服务器、哪些数据同步，必须由用户明确选择。

> 因此本文分别标注：**目标产品体验**、**可复用的现有技术**、**尚需研究的架构问题**，不把三者混为一谈。

### 3.1 可复用的现有技术（候选，不是结论）

- TypeScript 业务逻辑、共享校验规则和 API schema；
- 现有 Web/PWA 页面与交互基础；
- 现有数据模型、导入/导出、账本协作和业务锁思路；
- 现有离线队列、PWA 缓存和版本公告机制（需验证其在新模式下是否适用）。

### 3.2 尚需研究的架构问题

- 账号身份如何在不同服务器间隔离，是否需要统一身份；
- 官方云、自托管和本地单机之间的数据模型是否完全一致；
- 本地数据库与 PostgreSQL 的映射、迁移和冲突处理；
- 现有 API 是否适合被原生客户端长期使用，是否需要稳定的客户端 API 边界；
- 离线队列、业务锁、Critical Chain 在本地/私人服务器模式下如何工作；
- 升级、备份、恢复和跨设备同步的兼容性；
- 是否以及如何复用现有 Web 前端而不强行使用 WebView。

## 4. 原生移动客户端——未来构想

未来的 Android/iOS App 不应只是把现有网页放入 WebView。开发原生应用的目的，是获得更自然的移动端体验和真正有价值的系统集成能力。

**值得研究：**

- 原生导航、页面切换、手势和系统交互；
- 更好的本地数据持久化；
- 推送通知；
- 后台任务与有限的后台同步；
- 相机、相册和文件选择；
- 系统分享菜单及账单文件导入；
- 生物识别与安全存储；
- 桌面小组件、快捷操作；
- iOS FinanceKit 等符合资格的官方能力。

**技术路线：**

- 可以研究 React Native 等跨平台技术；
- 尽量复用现有 TypeScript 业务逻辑、校验规则和 API 定义；
- **此时不决定最终技术栈**，也不要求重写现有 Web 前端；
- 原生 UI 与 Web/PWA 可以长期并存，不能假定一方立即取代另一方。

**移动平台限制必须写清：**

- 移动操作系统仍然限制后台任务；
- 原生 App 并不意味着可以无限制地在后台运行或同步；
- 推送、后台刷新、系统权限和审核要求需要分别验证；
- 原生客户端的安全存储、生物识别和通知能力需要与数据所有权原则一起设计。

## 5. 自托管与官方云端的可选关联——未来构想

私人服务器默认应独立运行，**不应自动向 Libevra 官方报告其存在、设备信息或用户账目**。

未来可以向用户提供**主动选择**的官方云端关联能力。基本思路：

1. 用户可以先在自己的私人服务器创建完全独立的本地账号；
2. 该账号不依赖官方注册；
3. 如果用户希望启用云端迁移或同步，再创建或关联官方云端账号；
4. 用户自行决定哪些账本或数据允许传输；
5. 没有明确授权时，不应向官方云端同步财务数据。

**必须区分两项能力：**

### 5.1 一次性迁移（较容易理解，仍需研究）

将某一本账本从私人服务器或单机设备迁移到官方云端，之后不一定继续保持同步。

需要研究：导出/导入身份映射、迁移完整性、重复导入、原始账本保留、失败回滚和用户确认。

### 5.2 持续同步（远期研究方向，不得宣传为即将实现）

私人服务器与官方服务器长期交换账本更新，涉及：

- 双向写入和冲突解决；
- 网络中断、重试和幂等；
- 权限管理和访问撤销；
- 数据恢复与审计；
- 多设备在线/离线状态。

持续同步明显更复杂，**目前仅作为远期研究方向**，不是已批准功能。

**多人账本额外约束：**

- 多人账本涉及其他协作者的隐私和授权；
- 不应由管理员一个人随意把所有人的私人数据上传到云端；
- 应研究按账本授权、取消授权、停止同步、云端副本处理和审计机制；
- 同步必须是每个参与者知情、可选择退出的行为。

## 6. 数据所有权与隐私原则

Libevra 应尊重用户对自己财务数据的控制权。

**长期原则：**

- 本地单机数据默认留在设备内；
- 自托管数据默认留在私人服务器内；
- 官方云端只处理用户选择存储或明确授权传输的数据；
- 用户应当有合理的数据导出、迁移和恢复方式；
- 跨服务端同步必须是明确选择，不能是隐藏行为；
- 不同运行模式的账号身份应当明确隔离；
- 数据迁移不能擅自删除原始账本；
- 不把隐私保护宣传成绝对安全，必须说明各运行模式的责任与风险。

**对于 OCR、语音识别和未来的 AI 财务分析：**

- 优先探索本地执行的可能性；
- 自托管用户可以选择使用自己的计算资源；
- 如果使用官方或第三方云端智能服务，必须明确告知哪些数据会被发送；
- 未经授权不得把私人账单、截图、语音或账目上传到外部 AI 服务；
- 核心手动记账功能不应强制依赖 AI；
- AI 输出的准确性和不确定性必须向用户说明。

## 7. 智能输入与整理（保留原有构想）

> 以下均为未来构想/待验证方向；不因为本文档更新而视为已批准或已实现。

### 7.1 智能 OCR：支付账单列表截图

- **用户问题**：用户已有微信支付/支付宝账单列表截图，但逐笔打开详情再手工录入成本高。
- **可验证范围**：从一张列表截图识别多笔交易（日期、金额、收/支方向、商户/用途），先显示预览和逐条置信度，由用户确认后写入；不要求逐笔打开详情。
- **先验证什么**：截图版式覆盖、金额/日期准确率、重复识别、无法识别时的退出手动路径。
- **可行性/费用/第三方**：待调查；未选定服务商，不默认上传原始截图。
- **风险**：误读金额、把退款识别成支出、截图中包含敏感信息。

### 7.2 自然语言语音记账

- **用户问题**：用户希望“说一句话”完成记录，例如“昨天午餐 35 块，用微信”。
- **可验证范围**：理解日期、金额、账户/支付方式、用途；对不确定的日期、金额或分类先追问确认，不直接写入。
- **先验证什么**：中文口语、相对日期、金额单位、否定/退款表达、无网/低置信度处理。
- **可行性/费用/第三方**：待调查；语音原文是否离开设备必须先明确。
- **风险**：误解金额或日期造成账目错误；语音数据隐私。

### 7.3 智能账单整理

- **用户问题**：不同来源导入后出现重复、冲突、退款、内部转账和分类不一致。
- **可验证范围**：在现有 S14 导入预览/去重/冲突解决基础上，增加重复交易建议、退款匹配、内部转账识别和分类建议；所有建议先展示，不静默改账。
- **先验证什么**：与现有 S14 来源身份、增量导入和业务锁兼容；误匹配率和撤销路径。
- **可行性/费用/第三方**：待调查；先做规则与可解释特征，再评估模型。
- **风险**：把两笔真实交易误判为重复；退款/转账匹配错误；跨账本数据泄露。

### 7.4 可配置的自动整理

- **用户问题**：用户希望自主决定自动化程度，而不是被迫接受“全手动”或“全自动”。
- **可验证范围**：提供手动、辅助、高可信度自动三档；高可信度记录可自动处理，低可信度必须确认；自动变更保留操作记录、来源和撤销能力。
- **先验证什么**：默认档位、自动处理阈值、操作日志、撤销窗口和失败恢复。
- **可行性/费用/第三方**：待调查；需要先有稳定的来源身份、置信度和撤销模型。
- **风险**：自动化放大错误；用户不理解哪一步被自动处理；撤销不完整。

### 7.5 BOA 银行账单

- **用户问题**：BOA 账单需要整理进 Libevra，但逐笔手工输入不现实。
- **可验证范围**：优先研究 CSV/官方导出文件导入和字段映射；长期再评估 Plaid 等正规用户授权接口。
- **先验证什么**：CSV 字段、日期/金额/正负号、重复导入、跨月边界和原始文件保留策略。
- **可行性/费用/第三方**：CSV 待调查；Plaid 资格/费用/地区支持**待调查**；不默认接入或购买付费接口。
- **风险**：银行文件格式变化、账户信息敏感、第三方接口条款和用户授权。

### 7.6 微信 / 支付宝账单

- **用户问题**：用户的主要流水在微信支付/支付宝，希望减少手工录入。
- **可验证范围**：优先改善**用户主动提供的截图**和**官方账单文件**导入；不采用密码收集、模拟登录或会话抓取。
- **先验证什么**：官方账单文件格式、截图列表识别、退款/转账表达和重复检测。
- **可行性/费用/第三方**：待调查；官方文件格式与平台条款需要核对。
- **风险**：平台条款、截图敏感信息、识别错误；任何“代替用户登录”的方案都不在范围内。

### 7.7 统一数据整理

- 跨来源去重、Pending 到正式交易的状态更新、退款、内部转账、多币种处理。
- **待调查**：统一交易身份、币种换算来源与时间点、退款关联规则、跨来源合并的审计与撤销。
- **前置条件**：S14 导入的来源身份、锁、确认和撤销模型必须保持稳定。

### 7.8 银行/支付账单文件解析框架

- 为 BOA、微信、支付宝等文件建立可配置字段映射、文件保留和导入历史。
- **待调查**：格式版本、字段缺失、金额正负号、退款/转账标记、用户自定义映射的安全边界。
- **不采用**：收集网银/支付密码、模拟登录、抓取会话。

### 7.9 Apple Pay / FinanceKit

- 长期研究 Apple 官方支持的金融账户读取能力；评估 iOS 原生应用与现有 PWA 的关系。
- **待调查**：资格申请、地区限制、能力边界、审核要求、维护成本、与离线优先/隐私原则的兼容性。
- **不采用**：非官方私有接口或绕过系统授权。

### 7.10 产品方向：周期导入，而不是每天手动记账

- **用户问题**：用户不一定能坚持每天记账，但希望通过周期性导入了解收支。
- **可验证范围**：先验证“导入—预览—确认—整理”的周期流程，让用户在周末或月末一次完成，而不是要求每日手动输入。
- **先验证什么**：导入频率、提醒节奏、未确认任务保留、跨周期去重和离线可用性。
- **可行性/费用/第三方**：产品方向已明确为候选；具体交互待验证。
- **风险**：周期导入延迟反馈；用户忘记确认；提醒造成打扰。

## 8. 智能财务分析与主动提醒——未来构想

除了被动显示收入、支出和图表，未来 Libevra 可以主动分析用户财务状况。

**可能的分析：**

- 本月消费与历史平均值对比；
- 游戏、餐饮、娱乐等分类支出异常增加；
- 固定订阅费用变化；
- 预算接近或超过上限；
- 重复扣费或可疑的重复交易；
- 长期消费趋势；
- 账户余额和现金流变化；
- 用户可理解的财务总结与建议。

**目标：** 让喜欢分析数据的用户获得更丰富的信息，同时让不愿意研究图表的用户也能轻松了解重要变化。

**设计原则：**

- 用户可以开启、关闭或调整提醒类型；
- 控制通知频率，避免无意义打扰；
- 对推测性结论标注不确定性；
- 提醒应解释判断依据，而不是只给模糊警告；
- 不把消费建议设计成道德评价或责备；
- 涉及敏感财务信息的通知内容，应考虑锁屏隐私；
- 初期优先研究规则型分析，复杂 AI 分析留到后续探索；
- 原生 Android/iOS 客户端可以提供更完整的通知集成，但 Web/PWA 在支持的平台上也有一定通知能力，不必完全放弃网页提醒；
- 未授权不得把私人账单或账目上传到外部分析服务。

## 9. AGPLv3 与项目运营

Libevra 当前计划采用 **AGPL-3.0** 开源许可证，项目目前不以盈利为目标。

需要明确记录：

- AGPL-3.0 属于自由及开源软件许可证；
- 许可证本身允许商业使用，并不强制非营利；
- 项目是否收费、是否商业化，是独立于许可证的运营决定；
- 自托管、源代码开放和官方云服务可以同时存在，不互相否定；
- 此时**不决定未来收费模式**，也**不修改现有 LICENSE**。

## 10. 官网与版本分发——未来构想

长期希望将官网发展成兼具产品展示、下载和使用指引的平台。

用户可以在官网了解并选择：

- 直接使用网页版；
- 下载 Android/iOS 客户端；
- 下载或获取自托管服务器部署包；
- 阅读 NAS、Linux、Docker 等适用环境的安装说明；
- 查看不同运行模式的功能与适用场景；
- 阅读备份、升级、数据恢复及远程访问指导。

**原则：**

- 不同平台不代表需要完全分叉的产品代码；
- 官网必须清楚说明哪些功能已经可用、哪些仍在规划；
- 不得把未来运行模式、原生客户端或自托管能力写成已经可下载或已支持；
- 下载来源、签名、版本校验和安全公告需要单独设计。

## 13. 仍然没有答案的架构问题

1. **身份模型**：本地账号、私人服务器账号和官方云账号如何隔离、迁移和关联？是否需要统一身份？
2. **数据模型**：设备本地数据库、私人服务器数据库和官方 PostgreSQL 是否使用同一套 schema？如何升级和兼容？
3. **离线与同步**：现有离线队列、业务锁和 Critical Chain 在本地/私人服务器模式中如何保证一致性？
4. **API 边界**：现有 API 是否适合原生客户端长期使用？是否需要独立的客户端 API/版本策略？
5. **自托管运维**：安装、升级、备份、恢复、远程访问和安全责任如何交付？官方支持边界是什么？
6. **多人隐私**：按账本授权、参与者和云端副本的处理如何设计？谁能上传、谁能停止同步？
7. **一次性迁移 vs 持续同步**：两者的数据模型和审计要求是否不同？是否需要分别设计？
8. **原生客户端技术路线**：React Native、原生 UI 或混合方案如何取舍？如何复用 TypeScript 业务逻辑？
9. **第三方数据能力**：Plaid、FinanceKit 等资格、地区、费用、条款和用户退出机制均未确定。
10. **智能服务**：本地 OCR/语音是否足够？何时需要云端服务？如何取得明确授权并避免敏感数据外泄？

## 14. 评估顺序建议

1. **先验证输入质量**：截图 OCR、语音解析、CSV/官方文件导入各自的可验证窄场景。
2. **再验证整理正确性**：重复、退款、转账、分类建议在 S14 导入系统上是否可解释、可撤销。
3. **验证官方云端现有价值**：不为了未来模式牺牲当前稳定性、备份、安全和邀请制注册。
4. **再研究客户端/服务端解耦**：身份、数据模型、API、离线和权限问题必须先有答案。
5. **最后才讨论本地单机、自托管、原生客户端和跨服务器同步**：这些都需要独立立项、资源评估和安全设计。

> 本文所有“待调查”项都没有技术结论、费用结论或第三方资格结论。需要所有者逐项确认后才进入设计或开发；不得据此启动 S15。
