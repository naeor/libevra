# Libevra 未来功能构想与产品方向

> **状态：长期构想 / 未批准开发 / 不构成产品承诺。**
> 本文只整理未来可能方向，不代表 S15 或任何后续里程碑已经启动；技术可行性、费用、第三方资格与合规条件均**待调查**。
> 在不改变“离线优先、数据属于用户、操作可解释、可撤回”的前提下，才考虑以下方向。

## 0. 共同原则

1. **离线优先不后退**：任何自动识别或云端能力都不能让“没网就不能记账”重新出现。
2. **不收集银行/支付密码，不模拟登录，不抓取会话**：第三方数据只能通过用户明确授权的官方接口或用户主动提供的文件/截图。
3. **先预览、再确认、可撤销**：自动化程度越高，越需要可解释的来源、置信度和操作记录。
4. **渐进发布**：先做可验证的窄场景，再扩大来源和自动化；不以“全自动”作为卖点。
5. **不擅自新增付费云资源或第三方数据处理者**：费用、数据处理协议、用户授权和退出方式必须先由所有者确认。

## 1. 短期可验证（先做小范围验证，不代表已排期）

### 1.1 智能 OCR：支付账单列表截图

- **用户问题**：用户已有微信支付/支付宝的账单列表截图，但逐笔打开详情再手工录入成本高。
- **可验证范围**：从一张列表截图识别多笔交易（日期、金额、收/支方向、商户/用途），先显示预览和逐条置信度，由用户确认后写入；不要求逐笔打开详情。
- **先验证什么**：截图版式覆盖、金额/日期准确率、重复识别、无法识别时的退出手动路径。
- **可行性**：待调查（本地 OCR、上传 OCR、模型成本、微信/支付宝界面变化）。
- **费用/第三方**：待调查；未选定服务商，不默认上传原始截图。
- **风险**：误读金额、把退款识别成支出、截图中包含敏感信息。

### 1.2 自然语言语音记账

- **用户问题**：用户希望“说一句话”完成记录，例如“昨天午餐 35 块，用微信”。
- **可验证范围**：理解日期、金额、账户/支付方式、用途；对不确定的日期、金额或分类先追问确认，不直接写入。
- **先验证什么**：中文口语、相对日期、金额单位、否定/退款表达、无网/低置信度处理。
- **可行性**：待调查（现有语音入口、端侧识别、语音服务成本、隐私）。
- **费用/第三方**：待调查；语音原文是否离开设备必须先明确。
- **风险**：误解金额或日期造成账目错误；语音数据隐私。

### 1.3 智能账单整理

- **用户问题**：不同来源导入后出现重复、冲突、退款、内部转账和分类不一致。
- **可验证范围**：在现有 S14 导入预览/去重/冲突解决基础上，增加重复交易建议、退款匹配、内部转账识别和分类建议；所有建议先展示，不静默改账。
- **先验证什么**：与现有 S14 来源身份、增量导入和业务锁兼容；误匹配率和撤销路径。
- **可行性**：待调查；先做规则与可解释特征，再评估模型。
- **费用/第三方**：待调查。
- **风险**：把两笔真实交易误判为重复；退款/转账匹配错误；跨账本数据泄露。

### 1.4 可配置的自动整理

- **用户问题**：用户希望自主决定自动化程度，而不是被迫接受“全手动”或“全自动”。
- **可验证范围**：提供手动、辅助、高可信度自动三档；高可信度记录可自动处理，低可信度必须确认；自动变更保留操作记录、来源和撤销能力。
- **先验证什么**：默认档位、自动处理阈值、操作日志、撤销窗口和失败恢复。
- **可行性**：待调查；需要先有稳定的来源身份、置信度和撤销模型。
- **费用/第三方**：待调查。
- **风险**：自动化放大错误；用户不理解哪一步被自动处理；撤销不完整。

### 1.5 BOA 银行账单

- **用户问题**：BOA 账单需要整理进 Libevra，但逐笔手工输入不现实。
- **可验证范围**：优先研究 CSV/官方导出文件导入和字段映射；长期再评估 Plaid 等正规用户授权接口。
- **先验证什么**：CSV 字段、日期/金额/正负号、重复导入、跨月边界和原始文件保留策略。
- **可行性**：CSV 待调查；Plaid 资格/费用/地区支持**待调查**。
- **费用/第三方**：待调查；不默认接入 Plaid 或购买付费接口。
- **风险**：银行文件格式变化、账户信息敏感、第三方接口条款和用户授权。

### 1.6 微信 / 支付宝账单

- **用户问题**：用户的主要流水在微信支付/支付宝，希望减少手工录入。
- **可验证范围**：优先改善**用户主动提供的截图**和**官方账单文件**导入；不采用密码收集、模拟登录或会话抓取。
- **先验证什么**：官方账单文件格式、截图列表识别、退款/转账表达和重复检测。
- **可行性**：待调查；官方文件格式与平台条款需要核对。
- **费用/第三方**：待调查。
- **风险**：平台条款、截图敏感信息、识别错误；任何“代替用户登录”的方案都不在范围内。

### 1.7 产品方向：周期导入，而不是每天手动记账

- **用户问题**：用户不一定能坚持每天记账，但希望通过周期性导入了解收支。
- **可验证范围**：先验证“导入—预览—确认—整理”的周期流程，让用户在周末或月末一次完成，而不是要求每日手动输入。
- **先验证什么**：导入频率、提醒节奏、未确认任务保留、跨周期去重和离线可用性。
- **可行性**：产品方向已明确为候选；具体交互待验证。
- **费用/第三方**：不适用/待调查。
- **风险**：周期导入延迟反馈；用户忘记确认；提醒造成打扰。

## 2. 中期研究（需要专项调查/决策）

### 2.1 统一数据整理层

- 跨来源去重、Pending 到正式交易的状态更新、退款、内部转账、多币种处理。
- **待调查**：统一交易身份、币种换算来源与时间点、退款关联规则、跨来源合并的审计与撤销。
- **前置条件**：S14 导入的来源身份、锁、确认和撤销模型必须保持稳定。

### 2.2 银行/支付账单文件解析框架

- 为 BOA、微信、支付宝等文件建立可配置字段映射、文件保留和导入历史。
- **待调查**：格式版本、字段缺失、金额正负号、退款/转账标记、用户自定义映射的安全边界。
- **不采用**：收集网银/支付密码、模拟登录、抓取会话。

### 2.3 自动化整理的可解释性与审计

- 自动变更必须保留来源、规则/模型版本、置信度、操作记录和撤销能力。
- **待调查**：记录保留时长、跨设备一致性、用户界面如何解释自动变化。

### 2.4 周期性财务回顾

- 依托周期导入和统一整理，提供“本月收支概览”“待确认记录”等低风险回顾能力。
- **待调查**：是否需要新统计口径；避免把预测当成事实。

## 3. 长期探索（不承诺）

### 3.1 Apple Pay / FinanceKit

- 长期研究 Apple 官方支持的金融账户读取能力；评估 iOS 原生应用与现有 PWA 的关系。
- **待调查**：资格申请、地区限制、能力边界、审核要求、维护成本、与离线优先/隐私原则的兼容性。
- **不采用**：非官方私有接口或绕过系统授权。

### 3.2 Plaid 等正规银行数据接口

- 在 CSV/文件导入成熟后，评估 Plaid 或其他具备用户授权、可退出、可解释的数据接口。
- **待调查**：地区/银行覆盖、费用、用户授权流程、数据处理协议、失败与撤销路径。

### 3.3 更广的账户/资产视图

- 多账户、多币种、账户间转账、待结算/Pending 状态和周期性账单的统一视图。
- **待调查**：数据准确性、币种来源、用户授权、不同账户的数据归属与隐私边界。

### 3.4 更强的整理自动化

- 在可解释、可撤销的自动化基础上，逐步扩大高可信度场景。
- **前置条件**：短期验证和审计机制稳定；任何扩大都必须重新评估费用、隐私和失败模式。

## 4. 明确不做 / 暂不启动

- 不启动 S15 功能开发；本文只是构想整理。
- 不收集银行/支付密码，不模拟登录，不抓取第三方会话。
- 不因自动化而削弱离线优先、用户确认、业务锁（S14）或 Critical Chain。
- 不在未确认费用、第三方资质和数据处理条款前新增付费云资源或外部数据处理者。
- 不把“愿景”写成“已实现”或“已排期”。

## 5. 评估顺序建议

1. **先验证输入质量**：截图 OCR、语音解析、CSV/官方文件导入各自的可验证窄场景。
2. **再验证整理正确性**：重复、退款、转账、分类建议在 S14 导入系统上是否可解释、可撤销。
3. **最后才讨论自动化程度**：高可信度自动处理必须有操作记录和撤销；低可信度永不静默写入。
4. **第三方接口放在最后**：先完成用户主动文件/截图路径，再评估 Plaid/FinanceKit 等资格与成本。

> 本文所有“待调查”项都没有技术结论、费用结论或第三方资格结论。需要所有者逐项确认后才进入设计或开发。
