## 5. 成本、磁盘与任务竞争估算（粗略，按当前 98KB dump）

- S12-C 现每天 1 份 GPG（~41KB）+ 每月 1 份 monthly；本地 34 份共 2.4MB。
- S13-I 检查点若每天 1 份：本地 plain dump ~98KB + sidecar ~0.5KB；异地上传 GPG ~42KB。保留 70 天约 3MB；365 天约 15MB。
- 事件对象：每个加密事件+manifest 约 1–2KB；假设每天 100 个 P0/P1，约 0.2MB/天、73MB/年。总量远小于 1GB 量级；实际按事件量增长。
- 请求成本：每天备份约 3–6 次 PUT/HEAD；事件每天数百次 PUT/HEAD；对 COS 计费通常可忽略，但需按真实地域/计费单确认。
- 本地磁盘：当前 52G 可用；建议检查点本地保留 7 天并加清理，否则长期每天 dump 会缓慢累积。新 API 镜像约 2.5GB，生产当前 images 5.9GB/build cache 12.58GB，空间足够但发布前可清理旧 build cache。
- 数据库：300 次事件插入本地测试 792ms（平均 2.64ms/次），表 925KB；备份期间 20 次写入 67.5ms。当前生产 5 账本/164 交易，负载很小。
- 定时任务竞争：S12-C 03:00；S13-I 建议 04:00，避免同时 pg_dump/恢复演练；健康检查每 5 分钟只读查询。两套脚本锁文件、目录、COS 前缀均独立；当前磁盘/CPU/DB 规模下无显著竞争，但应监控备份窗口。

## 6. 本地可靠性验证（本轮新增）

- LISTEN 断线：终止 relay 的 listener backend 后，事件仍能在 8 秒内（实际约 0.3–1 秒重连）被上传。
- 事务回滚不通知；提交后才通知。
- 3 个连续事件遇到模拟 429：首事件失败并写入 nextAttemptAt；强制到期后按 seq 1→2→3 上传。
- relay 完全停止：注销仍 200；重启后积压自动清空（实测 1–2ms）。
- 单次瞬时失败不会触发 health alarm；relay stale/最老积压/连续失败会 alarm。
- receipt 24h 过期后查询 404，不影响业务 completed。
- 容量：300 事件 792ms（2.64ms/次，表 925KB）。
- 备份期间 20 条事件写入 67.5ms；检查点/sidecar/恢复库匹配。
- S12-C 原脚本测试 65 项通过。
- 真实 COS 未测；不能把这些本地数字当作云上延迟/计费。

## 7. 生产启用阶段（所有者逐项批准）

### 阶段 0：准备（不触碰业务）
1. 建测试前缀/测试 CAM/测试密钥，完成第 3 节演练。
2. 准备生产事件密钥及离线副本（32 字节，base64/hex）。
3. 准备 relay env（写身份 + 事件密钥）；恢复只读身份不常驻服务器。
4. 检查生产磁盘、备份窗口、systemd 可用。

### 阶段 1：只读/隔离接入（不改变业务写路径）
1. 部署 relay 代码但不启用 API 的 S13-I 事件写入？当前 API 1.13.09 无事件表，需先发布含 schema 的新版本；部署 schema migration 会新增空表，不改现有业务。
2. 先运行 relay 对测试 DB/测试前缀的 `--once`，验证对象/ack。
3. 在 staging 完整演练后才进生产。

### 阶段 2：生产启用
1. 发布包含 45 个 migration 的版本；migration 只增表/列，不改原备份。
2. 启动 relay sidecar（无端口、写身份）。
3. 启用 S13-I 后观察 P0 业务响应：应为原语义成功；protection 状态变 protected。
4. 安装 `libevra-critical-backup.timer`（04:00）和 `libevra-critical-health.timer`（5 分钟）。
5. 配置 COS 生命周期（事件/检查点独立前缀）和告警路由。
6. 24 小时内观察：pending/最老未确认、连续失败、relay heartbeat、链完整性、备份产物、业务错误率。

### 阶段 3：观察与扩量
- 先只观察，不把 protection alarm 当成业务故障；若持续积压/失败，按暂停/回退处理。
- 检查点备份先本地/异地并存，确认可从 COS 取回后再依赖。

## 8. 暂停、回退与重新启动

**暂停（保留代码/schema/数据）：**
- 停 relay：业务继续成功，事件转 pending/failed，保护告警应触发；
- 停 critical-backup/health timers：不影响 S12-C；
- 不删除 COS 事件对象、不删除 `critical_events` 表。

**回退到无 S13-I 的旧版本（必须显式保护降级）：**
- 旧版本不再写 `critical_events`/不设置 operation receipt，也**不会**自动补记停机期间的关键事件；
- 回退前必须：停 relay、保留事件对象、记录回退时点、把保护告警改为“S13-I 已停用”；
- **不能默默把旧版本当作“保护正常”**；需运维看板/邮件显式标注降级，直到重新启用；
- 原始 S12-C 备份/恢复仍独立可用。

**重新启动：**
1. 部署含 S13-I 的新版本（migration 已有，可前滚）；
2. 启动 relay，等待 pending 全部 ack；
3. 检查链完整性/事件对象/checkpoint；
4. 重新启用 timers 和告警；
5. 记录恢复时点。

## 9. 故障时原始备份独立恢复

- 使用原 `offsite-fetch.sh` + `verify-dump.sh` + `restore.sh`，或默认隔离的 `emergency-raw-restore.sh`。
- 不依赖 `critical_events`、relay、COS 事件密钥、checkpoint/sidecar。
- 如果 S13-I 完全不可用，S12-C 备份任务和原始恢复仍照常；这是最高原则。
- 恢复后的数据库/开放公网仍分开批准。

## 10. 需要所有者打开腾讯云控制台完成的操作

1. 创建/确认测试 COS 前缀 `critical-events-test/v1/`、`critical-backups-test/checkpoints/`。
2. 创建测试 CAM 写身份（仅 Put/Head）和测试只读身份（仅 Get/List）。
3. 用测试身份验证：相同 object key 带 `x-cos-forbid-overwrite` 的第二次 PUT 被拒绝且原对象不变；写身份 GET/LIST/DELETE 被拒绝。
4. 配置测试前缀生命周期并验证不影响原 daily/monthly。
5. 批准测试桶对象删除/清理（演练后）。
6. 批准生产前缀/CAM/生命周期/生产事件密钥/relay/定时器/告警的实际创建。

## 11. 当前结论

- **本地可靠性验证已通过**：业务与保护解耦、NOTIFY 立即唤醒、断线重连、链序、429/5xx 退避、积压恢复、心跳阈值、receipt 过期、备份期间写入、容量、S12-C 独立回归。
- **真实 COS/Docker 验证尚未开始**：缺 Docker/WSL、缺所有者授权的测试 CAM/前缀/密钥。不能在报告中声称已通过真实云验收。
- **距离正式上线还差**：测试前缀/CAM/密钥演练、Docker compose relay 实测、生产部署与 24h 观察、回退操作人/告警接收人确认。
- 成本量级很小，但必须用真实计费单确认；磁盘充足，检查点本地需加保留清理。

## 12. 1.13.09 旧版回滚安全边界（2026-10-19 实测）

> **测试环境：** 隔离 staging DB（45 个 migration）、正式旧版 API 镜像（health 返回 `1.13.09`）、测试账号与账本。  
> **结论先行：旧版可以启动、登录和记普通账，但存在回滚阻塞项；不能简单宣称“旧版可回滚”。**

| 场景 | 旧版 1.13.09 实测行为 | 结论 |
|---|---|---|
| 账号已注销（新 schema 的 `closed_at`/`disabled_at`） | 旧版登录返回 **401 `account_disabled`** | 通过：已注销账号不会重新开放 |
| 成员权限已撤销/成员已移出（`left_at`） | 旧版 `/books` 返回空列表，账本不可见 | 通过：已撤销成员关系不会被旧版重新打开 |
| 管理员授权已撤销（`admin_grants` 撤销、`is_admin=false`） | 旧版 `/admin/self` 返回 **403 `admin_forbidden`** | 通过：已撤销管理员权限不会重新生效 |
| 永久删除账本（`book.deleted`，物理删除） | 旧版列表无该行，不能访问 | 通过：删除后的行不存在，旧版无对象可复活 |
| **账本已归档（`archived_at`）** | 旧版 `/books` 仍返回该账本，`/ledger` 返回 **200**，还能继续访问/修改 | **回滚阻塞项**：旧版不识别归档语义 |
| **账本已弃置（`disposed_at`）** | 旧版 `/books` 把它显示在 `disposed` 列表，`/ledger` 仍返回 **200** | **回滚阻塞项**：旧版不识别弃置语义 |
| 有未上传的 critical pending 事件 | 旧版没有 critical event 写入/relay 处理；旧版继续运行时不会补记关键事件 | **回滚限制项**：旧版写入会落在保护簿记之外，后续新版本恢复时可能丢失关键事件 |
| 恢复/归档/处置的新路由 | 旧版返回 **404**（S13-G/H 功能不存在） | 功能缺失本身可接受，但不能作为“安全回滚” |

**因此：**

- **通用门槛：任何旧应用版本在连接已经升级的生产数据库前，都必须完成兼容性和权限安全验证；未通过不得启动。** 这不是对 `1.13.09` 版本号的永久禁令，而是对“旧应用 + 新数据库”这一运行条件的限制。
- 原始 `1.13.09`（commit `814d797`）已实测未通过：会重新访问已归档/已弃置账本，且没有 critical 事件记录机制；因此**当前不得直接把它作为生产回滚版本**。未来如有重新验证或修补过的构建，必须重新走同一套验证门槛。
- 兼容性验证至少覆盖：schema/迁移版本、账号关闭、成员/管理员撤销、归档/弃置/删除可见性、关键事件写入或危险写操作禁用、会话与普通记账数据完整性。
- 回滚前必须查询并记录：
  ```sql
  select count(*) from books where archived_at is not null or disposed_at is not null;
  select count(*) from critical_events where delivery_state <> 'acked';
  ```
  任一计数不为 0，不得直接启动未通过验证的旧应用。
- 回滚期间必须停止 relay 和 S13-I timers；旧版应急版本若没有 critical 事件写入能力，其任何写入都不能被当作“保护仍正常”。
- 若必须回滚且存在归档/弃置账本，**候选的补救方向**是先将这些账本隔离（例如保存成员关系到隔离表、暂时移除成员的可见关系），让旧版无法通过成员关系访问；但该方案会改变权限数据，必须在隔离环境完整验证并取得所有者批准，**不能作为未经演练的自动步骤**。
- 更安全的发布策略是：**优先前滚修复，或采用新版本的整 API 停机方案**；只有经过兼容性验证的旧应用才允许启动。
