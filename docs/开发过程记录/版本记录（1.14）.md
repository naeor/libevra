### 1.14.03 —— **S14-B：游客身份、持久化与启动流程；游客工作台基础框架**（2026-10-18，本地）

**背景**：S14-A 留下的 `/guest` 还只是一页"尚未开放"的诚实占位。这一版让游客成为**真正可持续使用的本地身份**：
打开 Libevra 时能直接回到自己的游客环境，刷新/重新打开不会重播开场，也**绝不**与正式账号的数据、缓存、离线队列混在一起。

**改了什么**

1. **游客身份（localStorage，同步可读）**：新增 `lib/guest/identity.ts`。
   - 键 `libellum-guest-identity`（新键，**有意沿用历史品牌前缀**；改名会丢失已有游客身份，见品牌迁移记录 §5.1）；
   - 字段：`id`（本地 UUID，**不是服务器 userId**，不进入任何请求头/账号 scope）、`schemaVersion`、`createdAt`、
     `welcomePending`、`noticeAcknowledged`、`lastPath`；
   - `createGuestIdentity()` **幂等**：第二次进入复用原身份，不会反复创建新游客；写入失败返回 `null`，工作台如实报错，
     不假装身份已持久化；损坏/未知版本的数据按"无身份"处理，不猜测修复。
2. **启动状态判断**（不改服务器认证逻辑）：
   - `RequireAuth`：正式会话优先（由既有 `AuthProvider` 判定）；无正式会话时若有游客身份 → 直接 `/guest`；
     两者都没有 → `/login`；`/join/:token` 仍按既有规则带 `?next=` 去登录；
   - 会话验证仍在 `Splash`（"载入中…"）之后才决定路由，**不会先闪登录页**再跳转；
   - 网络失败沿用既有规则（只有 401 才算退出；网络错误继续用本机记住的账号），游客身份与游客数据不受网络影响；
   - 记住 `lastPath`，重新打开游客模式回到上次游客页面（当前只有 `/guest`，S14-C 的子页面可直接复用）。
3. **一次性开场**：新增 `.guest-welcome` 品牌过渡，由身份字段 `welcomePending` 控制；首次进入播一次，
   随后在第一次挂载时**立即持久化清除**——刷新、关闭浏览器重开、从正式账号返回游客都**不会重播**；
   `prefers-reduced-motion` 下不渲染该过渡。**没有复用/重播账本空间的海浪展示态**，也没有改海浪代码。
4. **游客数据独立存储**：新增 `lib/guest/storage.ts`，独立 IndexedDB 数据库 **`libellum-guest`**（store `kv`）。
   - ⚠️ **故意不放进 `libellum`**：正式账号的 `resetEverything()` 会删除整个 `libellum` 数据库、查询缓存与同步队列
     也在其中；游客数据若同库，一次正式账号清理就能误删游客账本。独立库让隔离成为结构而不是约定；
   - 键命名空间 `guest:<guestId>:...`（永不与 `<userId>:<bookId>` 形式混淆）；`lib/guest/ledger.ts` 实现最小本地账本注册表
     （`ledgers`、`current-ledger`），首次进入创建**一个空的**默认账本（名称、币种、创建时间），**没有任何交易/假数据**。
5. **游客工作台**（替换 S14-A 占位页）：沿用正式应用视觉体系（品牌头、绿头、20px 卡片、既有字号/颜色令牌），
   明确显示"游客模式 / 本机游客身份"，展示本地账本卡片（"这里还没有任何账目"、禁用的"记一笔（即将开放）"），
   提供登录/创建正式账号入口、一次性数据提示（「游客数据仅保存在当前设备。清除浏览器数据或更换设备后，可能无法找回。」
   确认后持久化，不再重复）、以及**需要明确确认的"清理游客数据"**。
6. **正式账号与游客切换的边界**：
   - 登录/退出正式账号**不读取、不上传、不覆盖、不删除游客数据**；游客数据也不写入正式账号的查询缓存与同步队列；
   - `me` 页与"注销账号"完成页的退出目的地从 `/login` 改为 `/`：由启动判断决定去游客工作台（有游客身份时）
     还是登录页（无游客身份时）；这样"退出正式账号后回到此前游客身份"是确定的，不会经过登录页竞态；
   - **同步触发器只在有正式账号时启动**（`AppRoutes` 改为依赖 `status/user`），游客不触发任何业务 API/同步；
   - 清理游客数据只删除 `libellum-guest` 数据库与游客身份键，**不调用任何正式账号清理函数**；按钮在确认弹窗之后执行，
     并在版本记录/代码注释中写明"清理游客不得影响正式账号离线数据"。
7. **测试与文案防退化**：新增身份/账本注册表单元测试、游客工作台文案测试；S14-A 的账号入口测试保持通过。

**为什么这么设计**：S14-B 的核心不是"多一个页面"，而是**两个身份在同一浏览器里共存**。
身份必须同步可读（否则启动会闪错页面）；游客数据必须独立存储（否则正式账号的清理路径会碰到它）；
开场必须由持久化状态决定（否则刷新就会重播）；游客必须不触发正式账号的 API 与同步（否则隔离只在界面上成立）。

**怎么验证的**

- 静态检查：`pnpm typecheck` ✅；`pnpm check:build`（真实生产构建）✅；`pnpm check:docs` ✅。
- 自动化测试：`pnpm -r test` ✅ —— **API 383 条（30 文件）**、**Web 480 条（54 文件）**。
  新增：游客身份解析/幂等创建/标志更新/路径安全/清理隔离；游客账本注册表形状与容错；工作台文案（含"没有假数据"与
  "不影响正式账号"）。
- **真实浏览器（孤立栈：独立库 `ledger_s14a_test`、API 3200、Web 5176、headless Edge/CDP）S14-B 18 项通过**：
  - 首次进入：无身份→账号入口；点击游客入口→游客工作台，**一次性品牌过渡出现后消失**；身份/本地账本写入独立 IndexedDB；
  - 持久化：刷新直接回游客工作台且**不重播开场**；模拟关闭浏览器（清 sessionStorage 后重开）直接进游客工作台、
    **没有闪现登录页**（`Page.addScriptToEvaluateOnNewDocument` 观察器记录）；

  - 改路由无法获取正式账号页面（`/settings`→`/guest`，`/join/*`→`/login?next=`）；
  - 正式账号登录成功后游客身份/账本原样保留、正式账号存储中**没有 guest 键**；退出后**回到同一游客身份与账本**；

- 没有云端游客身份、受限游客协作、公开注册名额、邀请额度新规（S14-D/E/F，均待所有者拍板）；
- **决策记录**：正式账号设置里的"清除本应用的全部本地数据"目前只清理正式账号的 `libellum`/缓存/SW，**不会清理游客库**
  （游客清理必须走游客工作台的明确确认）。S14-C/D 若要把它扩展成"两者都清"，必须同时修改文案与确认项，不能静默合并。

**S14-C 接入本地记账时的架构约束（给下一版）**：

1. 游客账本/交易只能写 `libellum-guest`（`guest:<guestId>:...`），**不得**写 `libellum`、TanStack `query-cache`、
   `ledger-marks`/`ledger-months` 或离线同步队列；
2. 游客身份 id **不是 userId**，不要传给 `setOfflineAccount`/`x-libellum-book`/任何服务端请求；游客不调用业务 API；
3. 可复用的是**纯函数层**（本地筛选/统计/合并/格式化等），不是账号的持久化缓存与同步管线；
4. 游客数据模型应继续带 `schemaVersion`，迁移/导出/升级都先读版本再决定；账本注册表已允许未来多账本（`ledgers` 数组 +
   `current-ledger`），S14-C 只需追加交易命名空间（如 `guest:<id>:book:<bookId>:...`）；
5. 游客→正式账号的迁移应是**可重入、幂等、失败不删本地**的独立模块；迁移成功前后都要保留原数据，直到用户明确确认；
6. 任何"清除全部本地数据"类操作若要包含游客，必须单独调整文案与确认（见上方决策记录）。

### 1.14.02 —— **S14-A：注册与登录页面重设计、注册模式自适应、游客入口占位**（2026-10-18，本地）

**背景**：S14 的第一小步。目标是让第一次接触 Libevra 的人能自然地**注册 / 登录 / 发现游客入口**，
同时**不放松任何认证规则**，并为 S14-B 的游客模式留一个真实、不撒谎的入口。

**改了什么**

1. **统一账号入口的视觉与结构**（`AuthLayout`、新增 `AuthSwitcher` / `PasswordField` /
   `GuestEntry`；重写 `LoginPage` / `RegisterPage`）：
   - 一个品牌头（绿色圆角标记 + `Libevra` + 副标语）、一个登录/注册分段切换、一个内容卡片、
     一个安静页脚；三块都用 `--radius-card`（20px）、`canvas/surface/line/ink/muted/brand` 既有令牌；
   - 手机单列、最大宽度 26rem、桌面居中；390 / 320 / 1280 三档实测无横向溢出；
   - 进入动效：6px + 淡入 / 260ms（`.auth-enter`，延迟 60ms），**尊重 `prefers-reduced-motion`**；
     它只用于账号页，**没有碰账本空间的海浪动画**；
   - 密码显示/隐藏是无障碍按钮（`aria-label`、`aria-pressed`、44px 命中区），登录与注册的所有密码框共用。
2. **普通注册只要求三个字段**：用户名、密码、确认密码。
   - 两次密码不一致 → 字段内 `role="alert"` 提示，**不发送请求**；
   - 昵称：服务端仍要求 `displayName`（应用内展示名），**本阶段用用户名作为新账号的初始昵称**；
     已有账号的昵称不受影响。给昵称做编辑入口不在 S14-A 内，已记入遗留。
3. **受限注册（邀请码）自动出现**：
   - 新增公开接口 `GET /api/v1/auth/registration-config` → `{ mode: "invite" | "open", inviteRequired }`，
     **只回答模式，不暴露额度/名额/配额**；
   - 注册页进入时读取该接口；权限要求时增加**唯一一个**邀请码输入项，并显示一句持续可见的说明：
     「为了保持稳定的使用体验，目前新账号通过邀请开放。」（不使用"额度耗尽 / 资源不足 / 名额用完"等措辞）。
   - **规则由服务端强制**：邀请模式下不带邀请码的注册返回 `400 invite_required`；
     前端隐藏字段不能放宽规则。
   - **规则变化会更新**：页面在获得焦点/重新可见时静默重读配置（实测：服务端从 `open` 切回 `invite`
     后，已打开的页面**无需刷新**自动出现邀请码与说明）。
   - 新增环境变量 **`REGISTRATION_MODE`**（`invite` 默认 / `open`）；`open` 仅用于本地验证，
     **生产仍是 `invite`**（需所有者批准且 S14-D 名额/风控完成后才考虑）。
4. **登录页保留全部既有能力**：用户名、密码、忘记密码、恢复已注销账号的归档账本、前往注册、
   提交中禁用、重复提交防护、网络错误提示、账号停用/注销提示、登录后 `?next=` 同日站跳转、
   已登录访问 `/login` 直接回到应用。
   - ⚠️ **顺带修正一个既有缺陷**：首次访问（从未登录、没有本机记住的账号）时，`/auth/me` 的 401
     曾被当成"会话失效"，登录页会错误显示「登录状态已失效，请重新登录」。
     现在只有**本机确实记得某个账号**时才会显示该提示；首次访问与密码错误不再冒充会话过期。
5. **登录/注册两页的字段与提示全部保留安全语义**：登录失败仍是「用户名或密码不正确。」（不透露账号是否存在）；
   停用「该账户目前已停用或不存在。」；注销「这个账号已经注销。」。
6. **游客入口**：登录 / 普通注册 / 受限注册三处都出现同一位置、同一权重的
   「以游客身份继续」文字入口；指向真实路由 **`/guest`**。
   `/guest` 是**诚实占位页**（"游客模式还在准备中，尚未开放" + 创建账号 / 返回登录），
   **不伪装游客记账已可用**；S14-B 会把该页替换为游客工作台，入口与路由保持不变。
7. **注册成功后的恢复码不再可能被跳过**：浏览器验收发现注册成功的一瞬间存在一个渲染窗口，
   旧的 `if (user && !recoveryCode) Navigate` 可能在恢复码显示前跳走；现在注册提交期间与
   成功之后都阻止该跳转（恢复码是账号唯一的自助找回凭据）。
8. **文档与工具**：
   - 新建本文件并更新 `docs/README.md` 索引与份数；旧版本记录的当前状态指向本文件；
   - `.env.example` 增加 `REGISTRATION_MODE` 说明；
   - 开发用 Vite 端口支持 `LIBELLUM_WEB_PORT` 覆盖（默认仍是 5173），用于**不打断所有者现有 dev server**
     的隔离验证。

**没有改什么（边界）**：没有数据库迁移；没有改账号编号分配、默认账本初始化、邀请码次数/状态、
管理员判定、会话/Cookie、协议政策、离线同步与冲突逻辑；没有改 `deploy/`、CI、生产环境；
没有 push、没有部署。

**为什么这么设计**：账号入口是三块（登录 / 普通注册 / 受限注册）却只应像一个产品：
- 用**一个外壳 + 一个切换**表达"同一决定的两面"，而不是两个互不认识的表单；
- 邀请说明是**规则陈述**而不是稀缺营销——这是所有者对这一页的明确要求；
- "是否需要邀请码"必须**由服务端回答**，前端只是镜像；模式可热更新，避免规则变化后页面撒谎；
- 游客入口必须**存在且真实**：S14-B 之前它只承诺"尚未开放"，不承诺任何一个还没做的能力。

**怎么验证的**

- 静态检查：`pnpm typecheck` ✅；`pnpm check:build`（真实生产构建）✅；`pnpm check:docs` ✅。
- 自动化测试：`pnpm -r test` ✅ —— **API 383 条（30 文件）**、**Web 459 条（52 文件）**。
  新增覆盖：
