### 1.14.13 —— **S14-D D5 阶段二：增量导入（状态历史、变化核对、并发与恢复加固）**（2026-10-19，本地开发版，未发布）

**背景**：阶段一解决了大账本可靠写入，但再次导入时不能把所有来源记录当新记录。用户需要看到“哪些已导入、哪些变了、哪些曾跳过”，并且不能因为重复导入而覆盖、复制或删除数据。

**改了什么**

1. **持久来源状态**：新增 `ledger_import_source_states`（migration `20261019110000_s14d_import_source_states`），以 `(targetBookId, sourceBookKey, sourceTransactionId)` 唯一保存内容指纹、决策、目标 id/version；不复制整份游客来源快照。
2. **增量预览**：新增只读接口 `/api/v1/ledger-imports/incremental-preview`（正式来源服务端读取；游客快照上传），返回 `new / unchanged / modified / target_changed / target_deleted / previously_skipped / previously_skipped_modified / needs_review`。
3. **显式处理**：
   - 未变化默认跳过，不重复创建；
   - 来源变化默认保留目标，只有用户明确选择“用来源更新目标”才更新已有 A；
   - 目标 version 已变化时禁止覆盖；
   - 此前跳过/keep-a 可明确选择本次导入，否则保持跳过；
   - keep-both 视为已导入，未变化时不再提示；
   - 来源已删除不自动删除目标。
4. **分批任务**：增量导入始终走服务端持久化任务；每批为 `create/update/skip` 操作，skip 也记录状态；目标 version 校验失败暂停；已有暂停/运行任务优先返回旧任务。
5. **数据最小化**：任务完成后在同一最终事务清空 payload 中的游客来源快照，只保留计数、批次回执和结果。
6. **故障加固**：新增部分批次已提交后的真实 SIGKILL/restart 测试（400 笔已提交时杀进程，重启后完成 3000 笔，重复 sourceRef=0）；新增暂停后恢复不重复、目标并发变化、最终 A 删除失败、账号停用、账本归档等测试。
7. **UI**：核对页新增「此前导入的核对」，显示未变化/新增/修改/目标变化/目标已删/此前跳过；修改记录并排显示来源和目标，支持保留目标或用来源更新；320/390/桌面。

**验证**：Shared 167 / API 435 / Web 518；typecheck、build、docs、check:db 通过；D5 API 8 条 + 增量 API 5 条；真实浏览器增量核对/更新/来源保留 2 项；部分批次 SIGKILL/restart 通过。详见 [`S14-D5阶段二-增量导入`](S14-D5阶段二-增量导入.md)。

**边界**：未实现正式来源清理（阶段三）；未 push、未部署、未修改生产；游客任务暂停/失败期间的快照清理与 TTL 仍未实现。

### 1.14.12 —— **S14-D D5 阶段一：持久化分批任务、断点恢复与最终统一软删除 A**（2026-10-19，本地开发版，未发布）

**背景**：500 笔只是 D2–D4 的临时上限。D5 阶段一先解决大账本可靠执行：一次确认后服务端分批写入、每批幂等、刷新/重启可恢复、全局对账后才显示成功；涉及 A 的软删除延后到最后统一处理。

**改了什么**

1. **任务持久化**：新增 `ledger_import_jobs` 表（向前迁移 `20261019050000_s14d_import_jobs`），保存来源快照、taxonomy、逐条决定、导入计划、批次回执、目标基线与预期指纹。
2. **分批执行**：
   - 超过 200 笔的导入通过 `POST /api/v1/ledger-imports/jobs` 创建任务；服务端后台逐批执行，稳定 `importId`；
   - 每批是独立事务；批成功后在同一事务推进任务进度、目标指纹/数量和批次回执；
   - 逐批提交不宣称整体原子性；已提交批次保留，失败只暂停后续。
3. **断点恢复**：
   - `GET /jobs/:id` 返回服务端真实进度；页面刷新/关闭后可用 job id 重新接上；
   - 服务启动扫描 `queued/running/finalizing` 任务并恢复；
   - 页面显示运行/暂停/失败/最终对账状态，提供刷新和继续任务。
4. **A 删除最终阶段**：
   - 所有 B 批次完成、目标数量/指纹对账后，才在最终事务中逐条校验 A 身份/version 并统一软删除；
   - 最终事务失败时任务不完成，已导入 B 保留、A 不删除；
   - 最终对账通过才写 `ledger_imports` 回执并标记 `completed`。
5. **资格与锁**：正式来源仍按 D4 每批校验单人/邀请/分享/指纹；每批使用短表锁+账本行/交易行锁，不把 D4 宽锁覆盖整个长任务。游客来源目标同样要求单人正常账本。
6. **本轮明确只做阶段一**：增量导入、来源清理、批量导入到新建目标账本尚未实现；新目标大账本会提示先创建目标。
7. **测试**：D5 API 3 条（450 笔游客跨 3 批、最终 A 删除、正式来源分批）；真实浏览器 2 项（真实进度、刷新恢复/最终对账）；D1–D4 回归。截图在 `docs/开发过程记录/截图/2026-10-19-S14-D-D5分批导入/`。

**边界**：未 push、未部署、未合并 S13-I；未修改生产数据。D5 尚未完整验收，后续必须补增量导入、来源清理和恢复失败场景测试。

**1.14.12 整合补充（2026-10-19）**：S13 1.13.15 最终源码基线 `cc14725` 已通过真实双父 merge（`5fa7100`）进入 `s14-integration`。合并后 S13 的 critical relay/checkpoint、P0 回执、生命周期、账号注销/停用、部署配置和 2 个 migration 全部继承；D1–D5 阶段一代码与迁移保留。新增 D5 故障注入 4 条（目标并发变化、最终 A 删除失败后重试、账号停用、归档账本生命周期）和真实 API kill/restart（5000 笔，0 重复 sourceRef）验证。45→47 隔离升级、`check:db`、typecheck/build/docs、Shared 167/API 429/Web 518 通过。详见 [`S14-S13整合-预检与验收记录`](S14-S13整合-预检与验收记录.md)。

### 1.14.11 —— **S14-D D4：正式单人账本 B → A（服务端读取、权限锁与安全草稿恢复）**（2026-10-19，本地开发版，未发布）

**背景**：D4 允许把同一账号下的另一本正式单人账本作为来源 B 导入目标 A。D4 的安全要求比游客导入更高：B/A 都必须是当前账号独立拥有的单人账本，成员、待接受邀请、分享链接和账本状态必须在预览和提交时由服务端真实查询；来源账本不能被旧浏览器快照或 TOCTOU 权限变化欺骗。

**改了什么**

1. **共享契约**：
   - 导入请求支持 `guest` 游客快照或正式 `sourceBookId + sourceFingerprint` 两种来源；
   - 正式来源不再上传来源快照；新增 `POST /api/v1/ledger-imports/preview` 返回服务器读取的 canonical 来源/目标快照与指纹；
   - 结果回执增加可选的 `sourceBookId`，游客回执保持兼容。
2. **服务端资格与并发**：
   - 新增正式单人账本资格检查：`createdBy`、当前有效成员只有本人、无待接受邀请、无可用分享链接、未归档/弃置/永久删除；历史上已退出的成员和过期邀请不阻止；
   - 预览/提交都重新真实查询；提交事务内用 `LOCK TABLE book_members/notifications/book_share_links` + 两本 `books` 行锁 + 两本账本现有交易行锁封住成员/邀请/账目变化；
   - 来源/目标 id 相同、正式来源新建目标、跨账号越权均拒绝；
   - 复用同一导入事务、幂等回执、taxonomy 映射、逐条决定、A 软删除/审计/恢复；**不修改、不删除、不关闭来源 B**。
3. **UI**：
   - 来源选择支持「本机游客账本」或另一本正式单人账本；正式来源只能导入另一本现有正式账本（不新建目标、不选自己）；
   - 预览/确认沿用 D1–D3 页面；来源范围提示“不会删除或关闭来源 B”；
   - 来源/目标预览后变化时，服务端拒绝，客户端自动重新从服务器预览并恢复安全草稿。
4. **安全草稿恢复**：
   - 先恢复完全相同的 taxonomy 冲突选择，再用恢复后的映射重建预览；
   - 按「记录 id + 内容 + 映射键 + 冲突组成员」签名逐组恢复；目标 A 的 id/version/内容变化、映射或组结构变化都会清空该组；
   - 页面提示「部分选择已恢复，变化的记录需要重新核对」，核对页高亮受影响组；
   - 不按金额/日期/列表位置恢复；最终确认页和服务器指纹仍再次校验。
5. **测试**：D4 API 11 条、D4 真实浏览器 4 项、D3 guest 浏览器 4 项回归；全量 Shared/API/Web、构建、文档检查。截图在 `docs/开发过程记录/截图/2026-10-19-S14-D-D4正式来源导入/`。

**明确不做**：D5 来源删除/清空、增量导入、大账本分批与断点恢复；共享/多人账本导入；发布。

**边界**：未 push、未部署、未合并 S13-I；未修改生产数据库或真实用户账本。

### 1.14.10 —— **D3 一对一核对 UI 统一、导入删除审计与 D4/D5 方向落纸**（2026-10-19，本地开发版，未发布）

**背景**：所有者验收 D3 后要求简化一对一四张大卡片，统一为“逐条决定去留”；删除 A 的最终确认与安全逻辑不能降低。

**改了什么**

1. **一对一 UI 统一**：来源 B 使用「导入 / 跳过」分段控件，目标 A 使用「保留 / 移除（软删除）」分段控件；两笔记录上下排列，四种组合自然产生，不再显示四张重复统计的大卡片。
2. **多对多快捷建议保留**：快捷建议只填入逐条草稿，页面逐条显示每笔 B/A 选择与当前数量；不会因组级建议直接删除整组 A。
3. **当前结果摘要**：核对区域底部用一句简短说明当前选择；被移除的 A 记录有克制的 danger 背景提示，不再每条选项下重复四项统计。
4. **删除审计**：`GET /transactions/:id` 对被导入移除的记录返回 `deletedByImportId`；账目详情删除状态显示「通过账本导入移除」，可展开查看导入任务编号；仍然只使用现有 `/transactions/:id/restore`，不新增独立导入恢复中心。
5. **D4/D5 产品决定落纸**：D4 来源变化必须重新预览/核对，可暂存草稿但必须验证记录身份、映射与冲突组兼容；D5 一次确认、全局预览后分批、约 200 笔测试起步、逐批幂等/断点恢复、优先 B 全部写入并对账后再统一软删除 A、完成前不得显示成功。
6. **测试**：D3 API 11 条导入测试（含删除审计）继续通过；浏览器 4 项更新为逐条控件，并新增导入任务编号审计截图；全量测试同一基线。
7. **视觉**：保留 D1/D2/D3 现有卡片、颜色和间距；320/390/桌面布局通过；箭头布局保持上一轮的两列网格对齐。

**明确不做**：D4 正式来源、D5 分批实现；D2/D3 核心数据机制不重写。

**边界**：未 push、未部署、未合并 S13-I；未修改生产数据。

### 1.14.09 —— **S14-D D3：完整重复处理、A 软删除与现有恢复入口**（2026-10-19，本地开发版，未发布）

**背景**：D2 只支持「保留 A / 两边都保留」，不允许删除目标记录。D3 补齐四种处理，并且必须让多对多组逐条确认、不能默认删除整组 A；删除后的记录必须走现有账目软删除/恢复机制。

**改了什么**

1. **一对一四选择**：保留 A、保留 B、两边都保留、两边都不保留；后两种会软删除目标 A 的这 1 条记录。
2. **一对多/多对多逐条核对**：
   - B 逐条「导入 / 跳过」，A 逐条「保留 / 移除（软删除）」；
   - 四种快捷建议可一键填入草稿，但页面立即显示具体数量，最终仍需确认；
   - 多记录组使用未附逐条 `targetActions` 的组级删除快捷方式时，服务端返回 `group_removal_not_explicit`。
3. **最终确认**：摘要列出导入、跳过、软删除 A 数量；可展开查看所有被删除 A；有删除时弹出现有 `ConfirmDialog` 风格的二次确认；未在清单中的 A 不会被删除。
4. **服务端**：
   - 扩展导入请求为显式 `sourceActions/targetActions`；
   - 校验每个 A ID 属于目标账本、有效、属于当前组，并受来源/目标指纹约束；
   - A 软删除与 B 写入、taxonomy、序号、回执、对账仍在同一事务；失败整体回滚；
   - 软删除保留 id/seq/sourceRef/importRef，写 `deleted` 历史事件，changes 保存 `importId/importSource/importGroupId`；
   - `importId` 幂等，重试不会重复删除/导入。
5. **现有恢复入口**：
   - `GET /transactions/:id` 可返回已删除记录及 `deletedAt`；
   - 账目详情页识别已删除状态，展示删除时间与「恢复这笔记账」；
   - 恢复调用现有 `/transactions/:id/restore`，不新增独立导入恢复系统，恢复后编号不变。
6. **UI 小修**：预览「导入方向」改为两列网格，箭头与左侧「来源 B」「目标 A」标签列自然居中对齐，不再依赖固定像素偏移。
7. **测试**：D3 API 4 条 + D2 既有 7 条共 11 条导入集成测试；D3 浏览器 4 项；全量 Shared/API/Web 测试、构建、文档检查；截图在 `docs/开发过程记录/截图/2026-10-19-S14-D-D3导入/`。

**验证覆盖**

- 一对一四种选择；一对多/多对多逐条；未选择的 A 不删除；
- A 软删除后可通过现有详情/恢复入口恢复；
- 失败整体回滚；重试与幂等不重复删除/导入；
- 来源/目标变化拒绝；
- 原始交易编号及无关账目不变；
- 320/390/桌面布局与箭头几何对齐。

**明确未实现（D4/D5，已写入设计草案 §14.1）**

   `ledger-marks`/`ledger-months`、离线队列或同步触发器。**同步触发器只在有正式账号时启动**（S14-B 已定，本轮保持）。

**改了什么**

1. **启动与路由**：新增 `RequireSession`（正式账号 **或** 游客身份都放行）与 `RequireAccount`（仅正式账号）。
   - `/`、`/add`、`/stats`、`/me`、`/transactions/:id`、`/start`、分类/支付方式/标签管理使用 `RequireSession`；
   - 协作、邀请、账号安全、管理员、导入导出、更新中心等**必须服务器**的页面使用 `RequireAccount`，
     游客直达时会自然回到登录入口（登录页仍有「以游客身份继续」，可回到原游客环境）；
   - **正式账号优先**的判断不变：浏览器同时有正式会话与游客身份时，全部页面走正式账号数据源。
2. **统一数据访问层（本轮核心）**：
   - `lib/guest/data.ts`：单个带 `schemaVersion` 的游客数据块（账本元数据、分类、支付方式、标签、交易、已删除交易、下一个流水号），
     自动迁移 S14-B 已有的游客账本（保留原账本 id 与名称，不清空）；首次进入用**共享的预设常量** seed 分类/支付方式
     （`packages/shared/src/presets.ts`，服务端改为从 shared 再导出，避免两份预设漂移）。
   - `queries.ts` 的 `useLedger / useBooks / useBookMembers / useTransactions / useSummary / useTransaction /
     useStats / useQuickAmounts / useCurrentBookId / useLedgerMeta / useClassificationUsage` 以及交易、分类、支付方式、
     标签的写入 hooks 增加游客分支：读本地数据，写本地数据库后使游客查询失效；**游客分支不发任何业务 API 请求**。
   - `offline/write.ts` 的 `createEntry / updateEntry / deleteEntry / resolveConflict / refreshPending / pendingIds`
     增加游客分支：创建/编辑/删除直接落 `libellum-guest`，不写 sync marks；`/add`、`/`、`/transactions/:id`
     因此**不需要为游客复制一份页面逻辑**。
   - `sync.ts` / `syncController.ts` 在游客模式是安全的 no-op（刷新按钮改为“重新读取本地游客数据”，不是假同步）。
3. **页面复用与必要的游客分支（只改数据/可用性，不改布局）**：
   - **明细**：同一个月/支出收入/币种视图；本地新增、修改、删除后实时更新且持久化；隐藏服务器同步横幅、冲突页、
     下载/离线提示与导出/更多入口（这些在游客模式下没有意义或必须服务器）。**游客模式下“游客模式”标签出现在原品牌头部。**
   - **记账**：同一张表单、同样默认分类/支付方式/快捷金额/时间规则；写入本地数据库；`/add` 顶部增加同一枚小标签。
   - **分析**：同一批图表组件；`useStats` 用本地交易 `computeStats` 计算，刷新/离线都可用。
   - **账本空间**：原海浪界面原样复用（同一动画、同一过渡、同一手势）；游客显示自己的本地账本一行，
     “仅本机 · 游客本地账本”，隐藏齿轮（服务器管理）、新建账本与编号/邀请说明；**没有第二套海浪或第二套首页**。
   - **「我的」**：`MePage` 新增游客变体，同帧、同列表节奏、同确认弹窗；含游客身份（本机 id）、创建/登录正式账号、
     分类/支付方式/标签入口、清除游客数据、清除设备全部本地数据；**没有在每页堆积“请先注册”提示**。
   - **分类/支付方式/标签管理**：直接复用正式 `ManagePages`；游客用本地数据与本地 mutations，
     `useBookMembers` 游客分支返回唯一成员（owner），因此新增/改名/归档/永久删除等本地能力可用。
4. **底部导航与服务器专属动作**：游客的「语音 / 拍照」为禁用并标注“需要正式账号”（转录、识图是服务器能力），
   「手动」正常；第四项「账本」在游客模式指向**本地账本空间**，而不是只有正式账号能用的协作页。
5. **开场与恢复**：保留一次性的游客品牌过渡（现在覆盖在**正式界面**之上，显示一次后持久化清除）；
   刷新/关闭重开/从正式账号返回都不重播；**不强制进入海浪展示态**——海浪的初始状态仍由按身份记忆的
   “已看过展示态”标记决定（游客用 guest id 作为该标记的 key）。
6. **账号切换与清理**：
   - 登录正式账号：不读取、不上传、不合并游客数据；游客身份/本地账本原样保留；正式账号页面看不到游客账目。
   - 退出正式账号：本机有游客身份时回到**原游客环境**（同一身份、同一账本、同一记录）；没有则登录页。
   - 清理分三级且互不误伤：① 正式账号设置里的“清除本应用本地数据”仍只清正式账号（既有行为不动）；
     ② 游客「我的」→“清除游客数据”只删游客身份与 `libellum-guest`（需确认）；③ “清除此设备全部 Libevra 本地数据”
     需**两次确认**，范围文案写明同时包含游客与正式账号本地副本、不删服务器数据。
   - **游客转正入口**：游客「我的」提供“创建正式账号”，并说明不会自动上传/合并、迁移将在后续版本单独提供且可预览。
     **本轮不做迁移**（S14-D）。
7. **测试与防退化**：
   - 新增 `lib/guest/data.test.ts`（排序、LedgerMeta 形状、删除标记），更新游客文案测试（`copy.test.ts`）、
     `authSurfaces.test.tsx`、`tabHeader.test.ts`；`GuestModeBadge` 使用 `useAuthOptional`，组件测试无需挂载完整 AuthProvider。
   - 新增浏览器验收脚本（`libevra-study/s14a/verify-phase8a.mjs`、`phase8b.mjs`）覆盖首次进入、增删改持久化、
     刷新/重开、无业务 API、不与正式存储串号、分析、账本空间、游客「我的」、320/桌面、正式账号对照、登录/退出切换、
     分类新增、两级清理确认与清理隔离。

**为什么这么设计**：S14-B 的独立工作台证明了“游客要有一个地方”，但那个地方与正式应用越走越远，最终会需要两套
导航、两套视觉和两套行为。**本版把差异压缩到数据层的一个分支上**：页面不知道自己在为谁显示，只知道数据从哪里来；
身份差异只出现在查询键、写路径、启动判断、少量“此功能需要服务器”的入口，以及一枚小标签。这样后续维护只有一套 UI，
S14-D 的迁移也只需要搬数据，不需要搬页面。

**给 S14-D（迁移）的约束**

4. 迁移完成前后都要保留游客数据，直到用户明确确认；**绝不自动覆盖正式账号已存在的账本或交易**。
5. 若未来扩展“清除设备全部数据”，继续沿本轮的两级确认与范围文案，不得与“退出登录”“清除游客数据”合并。

### 1.14.03 —— **S14-B：游客身份、持久化与启动流程；游客工作台基础框架**（2026-10-18，本地）

**背景**：S14-A 留下的 `/guest` 还只是一页"尚未开放"的诚实占位。这一版让游客成为**真正可持续使用的本地身份**：
打开 Libevra 时能直接回到自己的游客环境，刷新/重新打开不会重播开场，也**绝不**与正式账号的数据、缓存、离线队列混在一起。

**改了什么**

1. **游客身份（localStorage，同步可读）**：新增 `lib/guest/identity.ts`。
   - 键 `libellum-guest-identity`（新键，**有意沿用历史品牌前缀**；改名会丢失已有游客身份，见品牌迁移记录 §5.1）；
   - 字段：`id`（本地 UUID，**不是服务器 userId**，不进入任何请求头/账号 scope）、`schemaVersion`、`createdAt`、
     `welcomePending`、`noticeAcknowledged`、`lastPath`；
   - `createGuestIdentity()` **幂等**：第二次进入复用原身份，不会反复创建新游客；写入失败返回 `null`，工作台如实报错，
     不假装身份已持久化；损坏/未知版本的数据按"无身份"处理，不猜测修复。
2. **启动状态判断**（不改服务器认证逻辑）：
   - `RequireAuth`：正式会话优先（由既有 `AuthProvider` 判定）；无正式会话时若有游客身份 → 直接 `/guest`；
     两者都没有 → `/login`；`/join/:token` 仍按既有规则带 `?next=` 去登录；
   - 会话验证仍在 `Splash`（"载入中…"）之后才决定路由，**不会先闪登录页**再跳转；
   - 网络失败沿用既有规则（只有 401 才算退出；网络错误继续用本机记住的账号），游客身份与游客数据不受网络影响；
   - 记住 `lastPath`，重新打开游客模式回到上次游客页面（当前只有 `/guest`，S14-C 的子页面可直接复用）。
3. **一次性开场**：新增 `.guest-welcome` 品牌过渡，由身份字段 `welcomePending` 控制；首次进入播一次，
   随后在第一次挂载时**立即持久化清除**——刷新、关闭浏览器重开、从正式账号返回游客都**不会重播**；
   `prefers-reduced-motion` 下不渲染该过渡。**没有复用/重播账本空间的海浪展示态**，也没有改海浪代码。
4. **游客数据独立存储**：新增 `lib/guest/storage.ts`，独立 IndexedDB 数据库 **`libellum-guest`**（store `kv`）。
   - ⚠️ **故意不放进 `libellum`**：正式账号的 `resetEverything()` 会删除整个 `libellum` 数据库、查询缓存与同步队列
     也在其中；游客数据若同库，一次正式账号清理就能误删游客账本。独立库让隔离成为结构而不是约定；
   - 键命名空间 `guest:<guestId>:...`（永不与 `<userId>:<bookId>` 形式混淆）；`lib/guest/ledger.ts` 实现最小本地账本注册表
     （`ledgers`、`current-ledger`），首次进入创建**一个空的**默认账本（名称、币种、创建时间），**没有任何交易/假数据**。
5. **游客工作台**（替换 S14-A 占位页）：沿用正式应用视觉体系（品牌头、绿头、20px 卡片、既有字号/颜色令牌），
   明确显示"游客模式 / 本机游客身份"，展示本地账本卡片（"这里还没有任何账目"、禁用的"记一笔（即将开放）"），
   提供登录/创建正式账号入口、一次性数据提示（「游客数据仅保存在当前设备。清除浏览器数据或更换设备后，可能无法找回。」
   确认后持久化，不再重复）、以及**需要明确确认的"清理游客数据"**。
6. **正式账号与游客切换的边界**：
   - 登录/退出正式账号**不读取、不上传、不覆盖、不删除游客数据**；游客数据也不写入正式账号的查询缓存与同步队列；
   - `me` 页与"注销账号"完成页的退出目的地从 `/login` 改为 `/`：由启动判断决定去游客工作台（有游客身份时）
     还是登录页（无游客身份时）；这样"退出正式账号后回到此前游客身份"是确定的，不会经过登录页竞态；
   - **同步触发器只在有正式账号时启动**（`AppRoutes` 改为依赖 `status/user`），游客不触发任何业务 API/同步；
   - 清理游客数据只删除 `libellum-guest` 数据库与游客身份键，**不调用任何正式账号清理函数**；按钮在确认弹窗之后执行，
     并在版本记录/代码注释中写明"清理游客不得影响正式账号离线数据"。
7. **测试与文案防退化**：新增身份/账本注册表单元测试、游客工作台文案测试；S14-A 的账号入口测试保持通过。

**为什么这么设计**：S14-B 的核心不是"多一个页面"，而是**两个身份在同一浏览器里共存**。
身份必须同步可读（否则启动会闪错页面）；游客数据必须独立存储（否则正式账号的清理路径会碰到它）；
开场必须由持久化状态决定（否则刷新就会重播）；游客必须不触发正式账号的 API 与同步（否则隔离只在界面上成立）。

**怎么验证的**

- 静态检查：`pnpm typecheck` ✅；`pnpm check:build`（真实生产构建）✅；`pnpm check:docs` ✅。
- 自动化测试：`pnpm -r test` ✅ —— **API 383 条（30 文件）**、**Web 480 条（54 文件）**。
  新增：游客身份解析/幂等创建/标志更新/路径安全/清理隔离；游客账本注册表形状与容错；工作台文案（含"没有假数据"与
  "不影响正式账号"）。

1. 游客账本/交易只能写 `libellum-guest`（`guest:<guestId>:...`），**不得**写 `libellum`、TanStack `query-cache`、

3. 可复用的是**纯函数层**（本地筛选/统计/合并/格式化等），不是账号的持久化缓存与同步管线；
4. 游客数据模型应继续带 `schemaVersion`，迁移/导出/升级都先读版本再决定；账本注册表已允许未来多账本（`ledgers` 数组 +

5. 游客→正式账号的迁移应是**可重入、幂等、失败不删本地**的独立模块；迁移成功前后都要保留原数据，直到用户明确确认；
6. 任何"清除全部本地数据"类操作若要包含游客，必须单独调整文案与确认（见上方决策记录）。

### 1.14.02 —— **S14-A：注册与登录页面重设计、注册模式自适应、游客入口占位**（2026-10-18，本地）

**背景**：S14 的第一小步。目标是让第一次接触 Libevra 的人能自然地**注册 / 登录 / 发现游客入口**，
同时**不放松任何认证规则**，并为 S14-B 的游客模式留一个真实、不撒谎的入口。

**改了什么**

1. **统一账号入口的视觉与结构**（`AuthLayout`、新增 `AuthSwitcher` / `PasswordField` /
   `GuestEntry`；重写 `LoginPage` / `RegisterPage`）：
   - 一个品牌头（绿色圆角标记 + `Libevra` + 副标语）、一个登录/注册分段切换、一个内容卡片、
     一个安静页脚；三块都用 `--radius-card`（20px）、`canvas/surface/line/ink/muted/brand` 既有令牌；
   - 手机单列、最大宽度 26rem、桌面居中；390 / 320 / 1280 三档实测无横向溢出；
   - 进入动效：6px + 淡入 / 260ms（`.auth-enter`，延迟 60ms），**尊重 `prefers-reduced-motion`**；
     它只用于账号页，**没有碰账本空间的海浪动画**；
   - 密码显示/隐藏是无障碍按钮（`aria-label`、`aria-pressed`、44px 命中区），登录与注册的所有密码框共用。
2. **普通注册只要求三个字段**：用户名、密码、确认密码。
   - 两次密码不一致 → 字段内 `role="alert"` 提示，**不发送请求**；
   - 昵称：服务端仍要求 `displayName`（应用内展示名），**本阶段用用户名作为新账号的初始昵称**；
     已有账号的昵称不受影响。给昵称做编辑入口不在 S14-A 内，已记入遗留。
3. **受限注册（邀请码）自动出现**：
   - 新增公开接口 `GET /api/v1/auth/registration-config` → `{ mode: "invite" | "open", inviteRequired }`，
     **只回答模式，不暴露额度/名额/配额**；
   - 注册页进入时读取该接口；权限要求时增加**唯一一个**邀请码输入项，并显示一句持续可见的说明：
     「为了保持稳定的使用体验，目前新账号通过邀请开放。」（不使用"额度耗尽 / 资源不足 / 名额用完"等措辞）。
   - **规则由服务端强制**：邀请模式下不带邀请码的注册返回 `400 invite_required`；
     前端隐藏字段不能放宽规则。
   - **规则变化会更新**：页面在获得焦点/重新可见时静默重读配置（实测：服务端从 `open` 切回 `invite`
     后，已打开的页面**无需刷新**自动出现邀请码与说明）。
   - 新增环境变量 **`REGISTRATION_MODE`**（`invite` 默认 / `open`）；`open` 仅用于本地验证，
     **生产仍是 `invite`**（需所有者批准且 S14-D 名额/风控完成后才考虑）。
4. **登录页保留全部既有能力**：用户名、密码、忘记密码、恢复已注销账号的归档账本、前往注册、
   提交中禁用、重复提交防护、网络错误提示、账号停用/注销提示、登录后 `?next=` 同日站跳转、
   已登录访问 `/login` 直接回到应用。
   - ⚠️ **顺带修正一个既有缺陷**：首次访问（从未登录、没有本机记住的账号）时，`/auth/me` 的 401
     曾被当成"会话失效"，登录页会错误显示「登录状态已失效，请重新登录」。
     现在只有**本机确实记得某个账号**时才会显示该提示；首次访问与密码错误不再冒充会话过期。
5. **登录/注册两页的字段与提示全部保留安全语义**：登录失败仍是「用户名或密码不正确。」（不透露账号是否存在）；
   停用「该账户目前已停用或不存在。」；注销「这个账号已经注销。」。
6. **游客入口**：登录 / 普通注册 / 受限注册三处都出现同一位置、同一权重的
   「以游客身份继续」文字入口；指向真实路由 **`/guest`**。
   `/guest` 是**诚实占位页**（"游客模式还在准备中，尚未开放" + 创建账号 / 返回登录），
   **不伪装游客记账已可用**；S14-B 会把该页替换为游客工作台，入口与路由保持不变。
7. **注册成功后的恢复码不再可能被跳过**：浏览器验收发现注册成功的一瞬间存在一个渲染窗口，
   旧的 `if (user && !recoveryCode) Navigate` 可能在恢复码显示前跳走；现在注册提交期间与
   成功之后都阻止该跳转（恢复码是账号唯一的自助找回凭据）。
8. **文档与工具**：
   - 新建本文件并更新 `docs/README.md` 索引与份数；旧版本记录的当前状态指向本文件；
   - `.env.example` 增加 `REGISTRATION_MODE` 说明；
   - 开发用 Vite 端口支持 `LIBELLUM_WEB_PORT` 覆盖（默认仍是 5173），用于**不打断所有者现有 dev server**
     的隔离验证。

**没有改什么（边界）**：没有数据库迁移；没有改账号编号分配、默认账本初始化、邀请码次数/状态、
管理员判定、会话/Cookie、协议政策、离线同步与冲突逻辑；没有改 `deploy/`、CI、生产环境；
没有 push、没有部署。

**为什么这么设计**：账号入口是三块（登录 / 普通注册 / 受限注册）却只应像一个产品：
- 用**一个外壳 + 一个切换**表达"同一决定的两面"，而不是两个互不认识的表单；
- 邀请说明是**规则陈述**而不是稀缺营销——这是所有者对这一页的明确要求；
- "是否需要邀请码"必须**由服务端回答**，前端只是镜像；模式可热更新，避免规则变化后页面撒谎；
- 游客入口必须**存在且真实**：S14-B 之前它只承诺"尚未开放"，不承诺任何一个还没做的能力。
