旧版镜像的 32 迁移目录对新数据库执行 `prisma migrate deploy`：**成功，输出 "No pending migrations to apply."**

两个新迁移是纯加法，旧 Prisma Client 查询现有表时忽略多出的表和列。因此：

- **应用回滚到 1.10.23 不需要回滚数据库**（结构兼容）。
- 数据库回滚（`restore.sh`）只用于发布后确认数据损坏/迁移半途失败等场景，是**整库覆盖**，会丢失发布后数据。

## 4. deploy / backup / systemd 协同与风险

### 4.1 已修复：deploy.sh Web 健康检查在生产恒失败

生产旧 `deploy.sh`：

```bash
wget -q --spider http://127.0.0.1/healthz
```

实测：Caddy 返回 `308 https://127.0.0.1/healthz`，容器内对 IP 的 TLS SNI 证书不匹配 → **wget 返回 1**。
即使 API 健康、Web 正常，deploy.sh 会判定 `WEB_OK=0` 并走失败分支。

已本地修复为：

```bash
curl -ksS -o /dev/null -w "%{http_code}" \
  --resolve "$LIBEVRA_DOMAIN:443:127.0.0.1" \
  "https://$LIBEVRA_DOMAIN/healthz"
```

并断言返回 200。该命令已在**当前生产 web 容器**内只读验证返回 `200`；`deploy/tests/run.sh` 增加静态回归（46/46 通过）。

### 4.2 双重 flock

- `/etc` service 已是直接执行 `backup-all.sh`，脚本内部 `flock -n 9` 保留；
- 仓库 `deploy/systemd/libevra-backup.service` 也已是修复版；
- 发布包会覆盖源码目录的 unit（修正），**不会自动覆盖 `/etc`**；
- 发布前/后不得再手工用 `flock` 包 service；备份与发布不可并发。

## 7. 回滚方案

### 7.1 应用回滚（首选，不需要数据库回滚）

- 新迁移纯加法 → **旧应用可运行在新数据库上**；旧迁移 deploy 已实测不报错。
- 使用发布前保留的旧 source 目录和旧镜像：

```bash
cd /srv/libevra.pre-1.13.07/deploy
docker image tag libevra-api:pre-1.13.07 deploy-api:latest
docker image tag libevra-web:pre-1.13.07 deploy-web:latest
docker compose -f docker-compose.prod.yml up -d --no-build
```

- 旧 compose/Caddyfile/镜像一起恢复，避免新 compose 的 `web-entrypoint.sh` 与新镜像不匹配。
- 回滚后验证旧 API `/health`、Web、登录、数据行数；旧 app 读新库只多两个空表/可空列，兼容。
- **不要执行 `prisma migrate reset`/`down -v`。**

### 7.2 数据库回滚（只用于数据损坏/迁移失败）

- 用 §5.1 的 pre-release dump，`restore.sh <dump> --yes`；会覆盖整库并丢失发布后写入。
- 恢复后先恢复旧 source/镜像，再跑 `backup.sh`；检查管理员名单和账目数。
- **不能假设迁移可自动回滚**；不存在 down migration，迁移只向前。

### 7.3 部分失败

- migrate 失败：API 不会启动（depends_on 条件），旧 api 可能仍在；先查 migrate 日志，决定修复/回滚；不要手工改 `_prisma_migrations`。
- 健康检查失败：按 deploy.sh 输出人工判断；回滚应用或恢复数据库。
- Caddy/web 失败：回滚 web 镜像/compose；检查证书卷仍在。

## 12. 发布建议与待所有者确认

**建议：有条件 Go。**

必须满足的条件：

1. 本报告 §11 的全量测试/构建在最终 release commit 上全绿；
2. 按 §4.4 生成并核对 release archive（SHA、无密钥、34 迁移、可执行位、unit 直接执行）；
3. 按 §5.1 完成发布前独立完整备份并验证；
4. 生产保留旧 source + 旧镜像 tag；
5. 发布时按 §6，先通过 Caddy validate 和生产构建，再执行 deploy.sh；
6. 发布后按 §8 验收，尤其检查旧账号/数据、PWA 老缓存、备份和 timer。

需要所有者明确确认：

- 接受“源码通过发布包覆盖、而不是服务器 git checkout”的方式；
- 允许发布期间执行一次真实完整备份、构建镜像和重启 API/Web 容器；
- 允许发布后重启/重建 web 容器以应用 Caddy 配置（会短暂中断 HTTPS）；
- 接受首次由新代码执行的发布/备份仍需人工验收（真机 Safari/iPhone 仍未验证）；
- 发布后是否立即跑一次新脚本完整备份，以生成 `backup_logs` 并验证新备份链路。
