## 1. 本轮发现并修复的问题

### 1.1 `conflict_resolutions` 漏出业务锁触发器

阶段四触发器覆盖了交易、交易事件、冲突记录、分类、标签、成员、邀请、分享、生命周期等，但**遗漏 `conflict_resolutions`**。该表带 `book_id`，是离线冲突解决的实际写入路径；锁定账本期间仍可能写入。

修复：新增 migration `20261019170000_s14d_phase4_lock_coverage`，给 `conflict_resolutions` 挂同一个 `trg_guard_book_id()` 触发器。真实数据库直接写入验证已补。

### 1.2 撤销缺少交易级审计事件

阶段四撤销更新目标交易时只恢复字段，没有写 `TransactionEvent`；对新增临时交易的硬删除也没有历史行。结果是业务数据正确，但交易历史可能看起来“导入更新仍在”，撤销不可见。

修复：

- 恢复更新行时写 `kind=updated` 事件，带恢复前后金额/分类/支付方式/时间/备注及 `importUndo` 标记；
- 删除新增临时交易前写 `kind=deleted` 事件，`transaction_id=null`、保留不可变 `seq` 快照和 `importUndo`；
- 新增 `importUndo` 历史字段标签；事件与撤销在同一事务，崩溃回滚后不重复。

### 1.3 备份恢复后的锁状态可能孤儿/缺失

阶段四的 `ledger_write_locks` 是持久锁。若备份包含活动锁、或恢复后缺少锁：

- 孤儿锁可能永久锁账本；
- 活动任务缺锁会在下一次批次校验失败，卡在异常状态。

修复：

- 新增 `reconcileLedgerLocks()`，在 API 启动时：
  - 释放无对应任务、旧任务、已终态任务、无权 owner 的孤儿锁；
  - 为仍活动的 phase-4 任务重新获取缺失的锁；
  - lock 归属冲突时把任务转 paused 并保留可恢复状态。
- 本地数据库测试：模拟恢复后锁丢失 → 重新取得；模拟孤儿锁 → 释放。
- `deploy/backup.sh` 的 `pg_dump` 排除 `ledger_write_locks` 数据（保留表结构），恢复演练把该表按 0 行比较；恢复后由启动协调器重建活动锁。
- `deploy/restore.sh` 对旧备份也做恢复列表过滤：只去掉 `TABLE DATA public ledger_write_locks`，保留表结构；本地用等价 `pg_restore -L` 对含旧锁数据的 3000 交易 dump 恢复成功（51 migrations、0 锁）。

### 1.4 旧同步导入入口的绕过（已按所有者方案 B 修复）

原来 `POST /api/v1/ledger-imports` 仍支持新建目标的同步导入和已有目标的直接同步导入，可以绕过最终确认、锁和撤销。所有者 2026-10-19 确认方案 B：

- 不引入 draft/temporary 账本生命周期；
- 取消“导入过程中一步新建目标账本”；
- 用户先在账本空间正常创建空账本，再将其作为导入目标；
- 撤销导入后不删除事先创建的空账本。

实现：

1. 生产构建的旧 `POST /api/v1/ledger-imports` 对 target-new 和 target-existing 的写请求均返回 `409 legacy_import_disabled`；只有测试构造显式打开测试兼容开关才可执行旧路径；
2. 同一 `importId` 已有历史回执时，旧端点只做只读 replay，保持历史回执查询兼容；
3. Web 移除目标“新建正式账本”选项和新建名称输入，显示“导入不会新建目标账本，请先在账本空间创建空账本”，旧 `target=new` URL 被安全归零；
4. Web 所有导入统一走 phase-4 job；测试验证空账本在撤销后仍存在、不被删除；
5. 旧 PWA 缓存请求得到 409 与清晰提示，不产生任何目标写入。

### 1.5 新建空目标的行为边界

方案 B 下，空账本由用户正常创建并立即存在于账本空间；导入撤销只撤销本次任务造成的交易、taxonomy 和来源状态，不删除该空账本。已用 API 测试验证：撤销后空账本仍存在，`archivedAt/disposedAt` 为空，目标账目 0 行，锁释放。

### 1.5 D4 小导入切到 job 后的草稿恢复回归

阶段四把已有目标的导入统一到 job 后，`handleSubmit` 的 job 分支捕获 `source_changed` 时走通用错误页，绕过了 D4 的“部分选择已恢复”路径。

修复：job 分支复用 D4 的 `<source_changed/target_changed>` 重载与草稿恢复；真实浏览器 D4 恢复路径已重新通过。

## 2. 撤销一致性审计结论

### 2.1 硬删除临时交易的影响范围

逐项核对并通过测试：

- 交易行本身：仅本任务创建行，删除后目标 live count 回到导入前；
- `transaction_tags`：随交易硬删除级联；
- `transaction_conflicts`：随交易级联；
- `TransactionEvent`：删除前写审计事件，`transaction_id` 变空、seq 快照保留；
- 分类/支付方式/标签：导入创建的 taxonomy 只有在全部相关交易被撤销后、仍无引用时才删除；有引用会进入 `undo_failed`，不会强行删除；
- 来源状态：按批次前快照恢复（新建→删除，旧→恢复）；
- 导入回执：`ledger_imports` 只在 confirmed 事务写，撤销不会产生回执；
- 账户：交易归属 `user_id` 不变；账户余额不是物化字段，统计由交易重新计算；账号本身不由导入撤销修改；
- 编号 `seq`：接受空档，不回退、不复用；这是所有者明确允许的；
- 来源 B：撤销只恢复 A，不修改 B；
- 统计/分类使用数：由剩余交易派生，撤销后回到导入前；
- `books.nextTransactionSeq`：不回退，保留已发编号空档。

### 2.2 中途崩溃与幂等

- 每个批次的业务写入 + 反向日志在同一事务；
- 撤销逐批逆序，`undoneAt` 标记；崩溃重启从剩余批次继续；
- 失败保持 `undo_failed` + 锁；修复后重试从未完成批次继续；
- 实际 SIGKILL 测试（见 §4）确认中断撤销可继续并最终 `undone`；
- 没有发现“成功撤销但残留目标交易/来源状态/taxonomy 引用”的路径。

### 2.3 仍保留的限制

- `undo_failed` 若由数据库被直接篡改造成，可能一直保持锁，需要人工恢复；
- 反向日志在 confirmed/undone 后清空 payload，只保留 job events 审计；
- 硬删除不可通过交易详情恢复；这是任务独占临时行的设计选择，需在发布说明中向用户表达。

## 3. 账本锁与触发器审计

### 3.1 覆盖范围

已覆盖写表：

`transactions`、`transaction_tags`、`transaction_events`、`transaction_conflicts`、`conflict_resolutions`、`categories`、`payment_methods`、`tags`、`book_members`、`notifications`（book_id 非空）、`book_share_links`、`book_messages`、`books`、`book_lifecycle_events`、`book_recovery_requests`、`book_tombstones`、`export_logs`、`import_logs`、`ledger_imports`、`ledger_import_source_states`。

未加触发器：

- `ledger_import_jobs` / `ledger_import_job_events` / `ledger_import_undo_batches`：仅导入 owner 内部状态，不是用户业务数据；owner 事务带 claim；
- `critical_*`、`users`、`sessions`、`notification_quota` 等全局/安全表：不属于单本账业务锁，导入 worker 每批重新检查账号状态；
- 分类/标签都是账本内资源，没有跨账本共享 taxonomy；不存在通过共享 taxonomy 间接改锁定账本的路径。

### 3.2 TOCTOU 与锁顺序

- 写触发器先对父 `books` 行 `FOR SHARE`；
- 获锁事务对同一行 `FOR UPDATE` 再插入锁行；
- 写事务与获锁事务通过父行串行化，消除“检查无锁→获锁→写入”窗口；
- 锁行 partial unique 保证同账本最多一个 active owner；
- 所有获锁按 book id 排序，单账本写入不阻塞其他账本；
- 本地真实数据库并发写入 8 路（直接 Prisma，不只 API）全部被 `ledger_locked` 拒绝；其他账本 API 写入成功；
- 真实 SIGKILL/重启、并发 confirm/undo/timeout 测试未见两个终态同时生效。

### 3.3 系统内部写入与导出

- 批次、确认、撤销事务均设置事务本地 `libevra.ledger_lock_owner` claim，可写被锁账本；
- 旧 phase-3 任务不会进入新流程，worker 会标记 `legacy_import_requires_repreview`，避免无锁执行；
- 普通导出在锁存在时返回 409 `ledger_locked`；新建/其他账本不受影响；未引入长时锁；
- PWA 离线队列遇到 409 `ledger_locked` 不清 pending、不当作内容冲突，解锁后重试。

### 3.4 备份恢复兼容

- 本地用 `pg_dump --exclude-table-data=ledger_write_locks` 对含 1 用户/1 账本/3000 交易/3 任务/31 撤销批次的数据库做 dump，`pg_restore --exit-on-error` 恢复成功，行数保留，锁表 0 行；
- API 启动协调器为仍活动的任务重建锁、释放孤儿锁；
- **旧备份格式**包含活动锁数据时，恢复数据的触发器仍可能拒绝；恢复旧备份前必须先采用新备份流程/清理锁表；
- 本轮没有生产恢复副本可用，**未做生产 1.13.15 备份副本的实际升级恢复演练**。

## 4. 确认/撤销竞争与崩溃结果

测试方式：真实 Fastify API 子进程 + 真实 PostgreSQL；`SIGKILL` 通过终止进程子树完成。

| 场景 | 结果 |
|---|---|
| API 并发确认 + timeout sweep | 3 轮均为唯一终态 confirmed/undone；confirmed 有回执，undone 无回执；锁释放 |
| 两设备同时确认/撤销 | 唯一终态，不出现 confirmed 与 undone 同时生效 |
| SIGKILL during undo（3000 条） | 重启后继续完成 undo；目标 0 行；锁 0；状态 undone |
| SIGKILL during confirm（3000 条） | 重启后恢复并 confirmed；目标 3000 行；正式回执存在；锁 0 |
| 服务重启后过期 awaiting | 自动 undo；目标回基线；锁释放 |
| 中断 undo 持久状态恢复 | 通过 |
| `undo_failed` 恢复后重试 | 通过（先保持锁，修正版本后重试 undone） |

日志/脚本：`libevra-study/s14a/verify-phase4-kill.mts`（工作区外验证脚本，不进入应用代码）。

### 9.3 主要风险

- 真实财务数据泄露：只允许在所有者指定的隔离机器和磁盘加密环境处理；
- 误连生产：恢复脚本必须显式指向隔离库，不使用生产 compose/.env；
- 解密密钥保管：只在内存/临时文件最小化使用，不提交、不截图、不发送；
- 备份本身不完整或过旧：先做归档解析和行数/摘要核对，失败就停止；
- 恢复后触发器/锁：必须走新 restore 过滤与启动协调器，不能强解不安全的锁；
- 演练写操作污染真实数据：隔离库内使用专用测试账号，不恢复后连接生产服务。
