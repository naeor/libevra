# S14 1.14.20 OCR 生产修复技术报告

> 状态：**候选修复，尚未部署生产**。生产仍为 1.14.19；所有生产发布/重启需所有者再次授权。
> 本轮不新增 migration，不修改数据库结构、账本数据、Critical Chain 或备份配置。

## 1. 根因

生产 API 容器中的 OCR 子进程在启动时执行：

```text
from rapidocr_onnxruntime import RapidOCR
```

该包导入 `cv2`，而运行时镜像缺少 OpenCV 所需的系统共享库，导致：

```text
ImportError: libxcb.so.1: cannot open shared object file: No such file or directory
```

`ldd` 在 1.14.18 和 1.14.19 两个 API 镜像中都报告缺少：

- `libxcb.so.1`
- `libGL.so.1`
- `libglib-2.0.so.0`
- `libgthread-2.0.so.0`

Python 包和 OCR 模型本身存在；问题发生在图片解码和模型初始化之前。

## 2. 为什么用户等约 60 秒

`OcrService` 启动子进程后会等待 `{"ready":true}`。旧逻辑在子进程提前退出时没有立即 reject 启动 Promise，而是一直等到 `STARTUP_TIMEOUT_MS = 60_000`。因此用户看到长时间“处理中”后失败，而真正的 ImportError 只出现在服务端日志。

## 3. 修复内容

### 3.1 运行时系统库

`deploy/Dockerfile.api` 的运行时 apt 安装增加：

```text
libxcb1
libgl1
libglib2.0-0
```

选择最小系统库而不是升级 OCR/Python 框架，也暂不更换 `opencv-python` 为 headless 版本。

### 3.2 OcrService 启动失败处理

修改 `apps/api/src/ocr/client.ts`：

- 子进程在 ready 前退出时立即 reject，不再等待 60 秒；
- 子进程 error 立即 reject；
- 启动超时仍保留，并清理子进程、定时器和启动 Promise；
- 每次失败后重置启动状态，后续请求可以重新启动服务；
- 识别超时可配置（测试使用），生产默认不变；
- 技术错误写入服务端日志，不进入用户响应。

### 3.3 API 错误反馈

`apps/api/src/routes/recognize.ts` 捕获 OCR 服务级异常，返回：

- HTTP 503
- `code: "ocr_unavailable"`
- 简短中文提示；不包含 Python traceback、共享库名或其他技术细节。
