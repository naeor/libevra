# S13-I 异地关键状态登记簿与灾难恢复安全补强（设计决定）

> 2026-10-18。**本地开发版本 `1.14.00`；未 push、未部署、未修改生产 COS/数据库，未执行生产恢复。**
> 本文记录实际实现、故障窗口、测试证据和上线前仍需所有者批准的云配置。

## 1. 最高原则：不削弱原有备份

- **未改** `deploy/backup.sh`、`backup-all.sh`、`restore.sh`、`offsite-fetch.sh`、GPG、备份格式、daily/monthly 生命周期。
- 新表会随整库 `pg_dump` 自然进入备份，但**原备份的读取/恢复不依赖 S13-I**：旧 dump 没有 `critical_*` 表也能被 `restore.sh` 恢复，`migrate` 只做 additive 前滚。
- 新机制不写 `deploy/backups/`、不碰 `.backup.lock`/`last-local.json`/`last-run.json`、不使用 `daily/`、`monthly/` 前缀。
- **原始直恢复**仍是独立通道：见 [`S13-I-灾难恢复操作手册.md`](S13-I-灾难恢复操作手册.md) §1B。
- 安全恢复失败不会自动覆盖生产库；所有安全恢复工具只接受隔离数据库（库名必须含 test/restore/verify/isolated/rehearsal）。

## 2. 架构

```
业务事务 ──> critical_events（本地哈希链 outbox） ──commit──> API
                                                          │ P0 业务提交即成功（不等待 ack）
                                                          ▼
                                    独立 relay 进程（唯一持有 COS 写身份）
                                                          │
                                          加密不可覆盖对象 + manifest
                                                          ▼
                                             COS 独立前缀 critical-events/v1/
                                                          │
                                       恢复只读身份（不常驻服务器）取回
                                                          ▼
                                     critical:verify → critical:apply-safe
```

- **API 不持有任何 COS 凭据**；API 只写 DB 并在事务提交时 `pg_notify` 唤醒 relay，**不等待** `delivery_state=acked`；业务成功与保护状态分离。实际边界调查见 `apps/api` 无 COS SDK、API 镜像无 rclone/gpg、无 `deploy/` 挂载。
- **本地链**：`critical_chain` 单行，追加时 `SELECT … FOR UPDATE`；`eventHash = sha256(prevHash + canonical(core))`。事件与其描述的状态变更在**同一事务**写入。
- **远端对象**：每事件一个 `events/<seq>-<eventId>.json.enc`，另有 `manifests/<seq>-<hash>.json.enc` 记录链头；AES-256-GCM；文件系统 sink 用 `wx`，COS 用 `x-cos-forbid-overwrite: true`；接口没有 delete 方法。
- **重试/响应丢失**：对象 PUT 带 `x-cos-meta-event-hash`；若收到 409（已存在），relay 用 HEAD（写身份允许 HeadObject）比较哈希，不读取全部历史；因此“上传成功但确认响应丢失”可以安全恢复。
- **精确备份检查点**：`critical-events-backup.sh` 在专用 advisory lock 下写 `critical_backup_checkpoints` 行，导出 REPEATABLE READ snapshot，再用 `pg_dump --snapshot` 产生同一快照的 dump；事件写入取对应事务共享锁。检查点行在 dump 内，sidecar 绑定 dump SHA-256；恢复不再用完成时间近似。
- **relay 侧车**：`deploy/critical-events-relay.compose.yml` + `.critical-events-relay.env`；无端口；`restart: unless-stopped`；写身份只对独立前缀有 PutObject/HeadObject。
- **safe restore**：`critical:preview` 生成只读差异；`critical:apply-safe` 只对恢复快照中已存在的对象重放安全状态，缺失目标进入 `manualReview`，不虚构账本/账号/交易；恢复库链头推进到远端最新。
- **P0 operation receipt**：关闭/删除数据/永久删除账本、成员移除/角色变更/退出、分享链接撤销、管理员停用/恢复/邀请码撤销返回 `operationId` + 一次性 receipt token；`GET /api/v1/operations/:id` 用 `X-Operation-Receipt` 请求头查询（24 小时过期，不放进 URL），账号已注销后仍可查询，不恢复任何登录权限。`status/businessStatus` 与 `protection` 分离。可选 `Idempotency-Key` 重复提交返回 409 原操作。

## 3. P0/P1 事件覆盖（实际接点）

| 组 | 事件 | 接点 |
|---|---|---|
| 账号 | created / disabled / enabled / closed / data_deleted / recovery_requested / recovery_claimed | `routes/auth.ts` 注册；`routes/admin.ts` suspend/restore；`lifecycle/account.ts` close/delete-data/closed claim；`lifecycle/book.ts` 认领批准 |
| 账本 | created / archived / restored / deleted / disposed / undisposed / recovery_requested / approved / rejected | `ledger/bootstrap.ts`；`lifecycle/book.ts`；`routes/books.ts` dispose/restore；`lifecycle/account.ts` 关号逐本 |
| 成员权限 | joined / rejoined / left / removed / role_changed / manager_changed | `collab/respond.ts`、`collab/share.ts`、`collab/members.ts`、`lifecycle/book.ts`、`lifecycle/account.ts` |
| 认证 | password_changed / password_reset / recovery_code_rotated / sessions_revoked | `routes/auth.ts`（改密/恢复/换码）；`lifecycle/account.ts` 关号 |
| 邀请/分享/管理 | invite.created/revoked/used；share_link.created/revoked；admin.granted/revoked/allowlist_changed | `routes/admin.ts`；`routes/books.ts`；`routes/notifications.ts`；`routes/share.ts`；`scripts/{grant,revoke,allow,disallow}-admin.ts` |
| 协议 | agreement.accepted | `routes/auth.ts` 注册；`routes/consent.ts` 登录后接受 |

**未凭空实现**：MFA、设备管理、邮箱恢复、认证安全版本、协议撤回、保留政策版本在现有系统不存在；仅预留类型/扩展位，未新增业务。

### 已知未完全接入 / P1 非原子点

- **分享链接创建/撤销**已与事件同一事务写入；`invite.created`（账本邀请）仍是在通知/配额写入后写事件，`notifications` 撤回也是先删除后写事件——这两个 P1 变化只操作 pending 通知，不产生实际成员访问；实际加入/重新加入在事务内原子写事件。P0 的永久删除、关号、密码、成员角色/移除/退出、管理员暂停/恢复/授权撤销、分享链接撤销、邀请码撤销等均已接入；业务成功不等异地确认。
- **P0 operation receipt** 覆盖账号注销、删除服务器数据、永久删除账本、成员移除/角色变更/退出、分享链接撤销、管理员停用/恢复/邀请码撤销；其他 P0 可复用同一 helper。新增 CLI 管理员脚本不再因异地确认失败而失败。
- 分享链接使用的 `share_link.used` 未单独记录（`member.joined` 已记录访问关系；链接 `use_count` 是普通计数）。
- 邀请码“过期”是计算状态，没有写入事件；协议撤回/保留政策版本尚无业务。
- 管理员在 web 上没有授权入口（有意），CLI 授权/撤权/名单脚本写事件并异步保护；结果不等待异地 ack。

## 4. 异步事务外盒与真实故障窗口

**最高原则：S13-I 是 S12-C 备份的增强，不是业务操作前置条件。** 只要 PostgreSQL 业务事务提交成功，接口就按原业务语义返回成功；COS/relay/事件上传失败**不得**返回 503。

实际保证：

1. **事件与业务同事务**：`recordCriticalEvent` 与业务变更在同一 PostgreSQL 事务；事件行、哈希链和业务状态一起提交或一起回滚。事件写入失败会回滚业务事务（这是数据一致性错误，不是可吞掉的补丁错误）。
2. **提交即成功**：事务提交后接口立即返回；P0 不再调用 `waitForRelayAcks`，`confirmP0` 为空操作。异地保护状态通过 operation receipt 单独展示。
3. **提交后立即唤醒 relay**：事件事务内执行 `pg_notify('critical_events_new', ...)`；独立 relay 持有 `LISTEN` 连接，提交时被唤醒并立即上传。1 秒轮询仅作为漏通知/重启补偿，不是正常路径。本地实测（轮询故意调成 10 秒）删除请求到 `acked` 约 **80ms**。
4. **失败持久化与退避**：失败事件保留 `failed`、`lastError`、`attempts`、`lastAttemptAt`、`nextAttemptAt`；指数退避 1s→2s→…→5min，且严格按 seq 顺序，不允许后序事件越过失败的前序事件。
5. **重启续传**：relay 启动先补传所有 `pending/failed` 且已到重试时间的积压；远端对象不可覆盖 + 已存在对象按 hash 校验，重复上传幂等。
6. **数据库事务失败**：事件和业务状态同事务回滚；不会出现“业务没有、远端有”。
7. **relay 完全不可用 / COS 不可用**：业务仍成功；事件留在 pending/failed，管理员保护状态告警；relay 恢复后自动补传。S12-C 备份完全不受影响（独立进程/锁/文件/前缀）。
8. **整台服务器在 DB 提交后、事件上传前丢失**：本地 outbox 和业务库一起丢失，远端没有该事件；安全恢复无法得知这次操作。这是当前架构**无法消除**的窗口，不声称已解决。
9. **COS 对象缺失/损坏/覆盖**：`critical:verify` 拒绝；安全恢复保持隔离；原备份直恢复仍可独立完成。

**业务成功与保护成功分离**：operation receipt 的 `status/businessStatus` 只表示业务事务是否完成；`protection.state = pending|partial|protected|failed` 表示异地事件保护状态。`completed + pending` 的含义是“删除已完成，备份增强尚未上传”，绝不是“删除未完成”。

**备份边界**：由 `critical-events-backup.sh` 生成的精确检查点决定：检查点行与 `critical_chain` 头在同一 REPEATABLE READ snapshot 内，`pg_dump --snapshot` 使用同一 snapshot；sidecar 绑定 dump 哈希。**不是** backup 完成时间。普通 S12-C dump 无检查点/sidecar 时安全恢复拒绝猜测；原始直恢复不受影响。`critical-events-backup-all.sh` 可自动调度并把 dump+sidecar 独立上传到 `critical-backups/checkpoints/` 前缀（本地 FS 演练已验证，真实 COS 未执行）。

## 5. 安全恢复与人工核查

安全恢复自动处理：
- 账号注销/停用/启用；
- 账本删除/归档/恢复/废弃；
- 成员退出/移除/角色变更/管理权移交；
- 认证会话撤销；密码/恢复码变更的旧凭据被置为不可用，需管理员重置；
- 邀请码/分享链接撤销；
- 管理员撤销；**管理员新增授权不自动恢复**，进入人工核查；
- 缺失目标（备份中不存在的账号/账本/成员关系）一律 `manualReview`，不虚构资源。
- **把验证过的远端事件元数据合并回恢复库，并把本地哈希链头推进到远端最后一条**；否则恢复后的第一个新事件会复用已在 COS 存在的序号/事件哈希。

流程、命令和原始直恢复步骤见操作手册。安全恢复验收前保持隔离；人工应急上线和数据库恢复是两件事，必须单独确认。
恢复前可运行 `critical:preview`：它按事件组输出检查点、逐事件类型/时间/actor/target、自动/人工/缺失目标/倒退风险，**不写目标库**。P0 receipt 可公开查询，且不恢复已注销账号的访问权限。

## 7. 上线前需要所有者批准（本轮未操作）

1. 为现有 COS 桶新增独立前缀 `critical-events/v1/` 及生命周期：**不得被 daily 70 天/monthly 365 天规则误删**；保留期至少覆盖可恢复历史快照的最长保留期（建议 ≥365 天）。
2. 新增 relay 写身份：仅 `PutObject` + `HeadObject`（含 `x-cos-forbid-overwrite`），资源限于该前缀；无 Get/List/Delete。
3. 新增恢复只读身份（不常驻服务器）：`GetObject` + `ListBucket`，资源限于该前缀；无写/删。
4. 事件加密密钥：`CRITICAL_EVENT_KEY` + `CRITICAL_EVENT_KEY_ID`（当前 `v1`）；轮换时把旧密钥放入 `CRITICAL_EVENT_PREVIOUS_KEYS=v1:<old>`，新事件用新 keyId，旧 v1 信封仍可解密。密钥离线保险箱保存。
5. 是否使用独立桶（可选；第一版不强制）；检查点备份额外需要 `critical-backups/checkpoints/` 前缀写权限或独立灾备介质。
6. 是否接受 §4 的“进程/服务器在 DB 提交后、远端确认前丢失”窗口；若要消除，需要进一步设计同步异地提交或共享日志服务。
7. 安装 `libevra-critical-backup.timer` 自动执行带检查点备份并异地保存；需要决定 COS 检查点前缀/独立介质、GPG 口令和保留期。
8. 部署 relay 心跳/告警：`critical:status` 或管理员保护状态接口的 alarm 字段接入现有邮件/Healthchecks/监控。
