# S13-I 异地关键状态登记簿与灾难恢复安全补强（设计决定）

> 2026-10-18。**本地开发版本 `1.14.00`；未 push、未部署、未修改生产 COS/数据库，未执行生产恢复。**
> 本文记录实际实现、故障窗口、测试证据和上线前仍需所有者批准的云配置。

## 1. 最高原则：不削弱原有备份

- **未改** `deploy/backup.sh`、`backup-all.sh`、`restore.sh`、`offsite-fetch.sh`、GPG、备份格式、daily/monthly 生命周期。
- 新表会随整库 `pg_dump` 自然进入备份，但**原备份的读取/恢复不依赖 S13-I**：旧 dump 没有 `critical_*` 表也能被 `restore.sh` 恢复，`migrate` 只做 additive 前滚。
- 新机制不写 `deploy/backups/`、不碰 `.backup.lock`/`last-local.json`/`last-run.json`、不使用 `daily/`、`monthly/` 前缀。
- **原始直恢复**仍是独立通道：见 [`S13-I-灾难恢复操作手册.md`](S13-I-灾难恢复操作手册.md) §1B。
- 安全恢复失败不会自动覆盖生产库；所有安全恢复工具只接受隔离数据库（库名必须含 test/restore/verify/isolated/rehearsal）。

## 2. 架构

```
业务事务 ──> critical_events（本地哈希链 outbox） ──commit──> API
                                                          │ P0 等待 ack
                                                          ▼
                                    独立 relay 进程（唯一持有 COS 写身份）
                                                          │
                                          加密不可覆盖对象 + manifest
                                                          ▼
                                             COS 独立前缀 critical-events/v1/
                                                          │
                                       恢复只读身份（不常驻服务器）取回
                                                          ▼
                                     critical:verify → critical:apply-safe
```

- **API 不持有任何 COS 凭据**；API 只写 DB 并等待 `delivery_state=acked`。实际边界调查见 `apps/api` 无 COS SDK、API 镜像无 rclone/gpg、无 `deploy/` 挂载。
- **本地链**：`critical_chain` 单行，追加时 `SELECT … FOR UPDATE`；`eventHash = sha256(prevHash + canonical(core))`。事件与其描述的状态变更在**同一事务**写入。
- **远端对象**：每事件一个 `events/<seq>-<eventId>.json.enc`，另有 `manifests/<seq>-<hash>.json.enc` 记录链头；AES-256-GCM；文件系统 sink 用 `wx`，COS 用 `x-cos-forbid-overwrite: true`；接口没有 delete 方法。
- **重试/响应丢失**：对象 PUT 带 `x-cos-meta-event-hash`；若收到 409（已存在），relay 用 HEAD（写身份允许 HeadObject）比较哈希，不读取全部历史；因此“上传成功但确认响应丢失”可以安全恢复。
- **relay 侧车**：`deploy/critical-events-relay.compose.yml` + `.critical-events-relay.env`；无端口；`restart: unless-stopped`；写身份只对独立前缀有 PutObject/HeadObject。
- **safe restore**：`critical:verify` 做只读校验；`critical:apply-safe` 只对恢复快照中已存在的对象重放安全状态，缺失目标进入 `manualReview`，不虚构账本/账号/交易。

## 3. P0/P1 事件覆盖（实际接点）

| 组 | 事件 | 接点 |
|---|---|---|
| 账号 | created / disabled / enabled / closed / data_deleted / recovery_requested / recovery_claimed | `routes/auth.ts` 注册；`routes/admin.ts` suspend/restore；`lifecycle/account.ts` close/delete-data/closed claim；`lifecycle/book.ts` 认领批准 |
| 账本 | created / archived / restored / deleted / disposed / undisposed / recovery_requested / approved / rejected | `ledger/bootstrap.ts`；`lifecycle/book.ts`；`routes/books.ts` dispose/restore；`lifecycle/account.ts` 关号逐本 |
| 成员权限 | joined / rejoined / left / removed / role_changed / manager_changed | `collab/respond.ts`、`collab/share.ts`、`collab/members.ts`、`lifecycle/book.ts`、`lifecycle/account.ts` |
| 认证 | password_changed / password_reset / recovery_code_rotated / sessions_revoked | `routes/auth.ts`（改密/恢复/换码）；`lifecycle/account.ts` 关号 |
| 邀请/分享/管理 | invite.created/revoked/used；share_link.created/revoked；admin.granted/revoked/allowlist_changed | `routes/admin.ts`；`routes/books.ts`；`routes/notifications.ts`；`routes/share.ts`；`scripts/{grant,revoke,allow,disallow}-admin.ts` |
| 协议 | agreement.accepted | `routes/auth.ts` 注册；`routes/consent.ts` 登录后接受 |

**未凭空实现**：MFA、设备管理、邮箱恢复、认证安全版本、协议撤回、保留政策版本在现有系统不存在；仅预留类型/扩展位，未新增业务。

### 已知未完全接入 / P1 非原子点

- `share_link.created` 在链接已创建后写事件（不在同一事务）；`invite.created`（账本邀请）和 `notifications` 撤回也在状态变更后写事件。P0 的永久删除、关号、密码、成员角色/移除、管理员授权/撤销、分享链接撤销、邀请码撤销等已走 P0 等待或脚本确认。
- 分享链接使用的 `share_link.used` 未单独记录（`member.joined` 已记录访问关系；链接 `use_count` 是普通计数）。
- 邀请码“过期”是计算状态，没有写入事件；协议撤回/保留政策版本尚无业务。
- 管理员在 web 上没有授权入口（有意），CLI 授权/撤权/名单脚本写事件并等待异地确认；成功脚本若异地确认失败会提示人工核验。

## 4. 事务外盒与真实故障窗口

不是“普通 Outbox 自动跨库原子”。实际保证：

1. **DB 提交成功、远端失败**：P0 路由 `confirmP0` 抛 503 `critical_event_unconfirmed`，不返回最终成功；事件留 `failed/pending` + `lastError`，relay 重试。操作可能已提交，客户端需要按错误提示核对/重试。
2. **远端成功、DB ack 更新失败**：对象和 manifest 已写入；重试用 HEAD metadata 校验后补 ack，不会重复删除或重复注销。
3. **上传成功但确认响应丢失**：同上，HEAD 校验。
4. **事件写入成功、进程在 flush 前崩溃**：事件为 pending；客户端通常未收到成功；relay 启动后补传。这是**剩余窗口**，在 relay 补传前，旧备份恢复无法看到该事件；对 P0 操作客户端没有收到成功。
5. **数据库事务失败**：事件与状态同事务回滚；不会出现“远端有事件、DB 无状态”（上传只在 commit 后发起）。
6. **整台服务器在 DB 提交后、异地确认前丢失**：与第 4 点相同；本地 DB 与 outbox 一起丢失，远端没有该事件，安全恢复无法得知这次操作。这是本轮架构**无法消除的故障窗口**，除非引入同地/异地同步提交或远程事务协调器；本轮没有伪装成已解决。
7. **relay 整体不可用**：P0 全部 503，不会静默成功；P1 排队。S12-C 备份完全不受影响（不共用进程/锁/前缀）。
8. **COS 对象缺失/损坏/覆盖**：`critical:verify` 拒绝；安全恢复保持隔离；原备份直恢复仍可独立完成。

**备份边界**：安全恢复必须由操作者给 `--backup-at`（`backups/last-local.json` 的完成时间或 dump 时间）。当前没有自动 backup checkpoint/manifest，因此“备份之后的事件尾部整体缺失”只能依赖 relay 的 P0 同步确认与人工核查；上线前建议增加备份完成时的独立 checkpoint（本轮不擅自改备份系统）。

## 5. 安全恢复与人工核查

安全恢复自动处理：
- 账号注销/停用/启用；
- 账本删除/归档/恢复/废弃；
- 成员退出/移除/角色变更/管理权移交；
- 认证会话撤销；密码/恢复码变更的旧凭据被置为不可用，需管理员重置；
- 邀请码/分享链接撤销；
- 管理员撤销；**管理员新增授权不自动恢复**，进入人工核查；
- 缺失目标（备份中不存在的账号/账本/成员关系）一律 `manualReview`，不虚构资源。
- **把验证过的远端事件元数据合并回恢复库，并把本地哈希链头推进到远端最后一条**；否则恢复后的第一个新事件会复用已在 COS 存在的序号/事件哈希。

流程、命令和原始直恢复步骤见操作手册。安全恢复验收前保持隔离；人工应急上线和数据库恢复是两件事，必须单独确认。

## 7. 上线前需要所有者批准（本轮未操作）

1. 为现有 COS 桶新增独立前缀 `critical-events/v1/` 及生命周期：**不得被 daily 70 天/monthly 365 天规则误删**；保留期至少覆盖可恢复历史快照的最长保留期（建议 ≥365 天）。
2. 新增 relay 写身份：仅 `PutObject` + `HeadObject`（含 `x-cos-forbid-overwrite`），资源限于该前缀；无 Get/List/Delete。
3. 新增恢复只读身份（不常驻服务器）：`GetObject` + `ListBucket`，资源限于该前缀；无写/删。
4. 事件加密密钥 `CRITICAL_EVENT_KEY`：32 字节，离线保险箱保存副本；丢失后历史事件不可解密。
5. 是否使用独立桶（可选；第一版不强制）。
6. 是否接受 §4 的“进程/服务器在 DB 提交后、远端确认前丢失”窗口；若要消除，需要进一步设计同步异地提交或共享日志服务。
7. 备份完成时是否增加自动 checkpoint（当前由操作者给 `--backup-at`）。
