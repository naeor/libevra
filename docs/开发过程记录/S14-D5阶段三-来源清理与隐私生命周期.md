## 1. 先修复：游客来源身份不是“guest”一个桶

### 1.1 核查结论

游客账本的稳定 id 由 `createDefaultGuestLedger()` 生成：

```text
guest-book-<uuid>
```

它随游客账本数据一起保存在本机；游客身份本身另有 `guestId`。此前 D5 阶段二把状态键固定为 `"guest"`，并且目标交易的唯一性只约束 `(bookId, sourceRef)`：

- 独立设备随机生成的交易 UUID 碰撞概率极低；
- 但复制/恢复游客数据会保留原交易 UUID，不同游客账本可能出现同一个 `sourceTransactionId`；
- 仅使用 `"guest"` 会导致不同游客账本共用状态命名空间，甚至目标 `sourceRef` 冲突。

### 1.2 修复

1. `GuestImportSource` 新增可选稳定字段 `guestBookId`（游客账本 id）；游客预览/提交自动携带；
2. 状态键改为：
   - 游客：`guest:<guestBookId>`
   - 正式：来源 bookId
3. `transactions` 新增 `source_namespace`：
   - 正式来源：来源 bookId
   - 游客：`guest:<guestBookId>`
   - 历史/手工记录：空字符串（legacy）
4. 唯一约束从 `(bookId, sourceRef)` 改为 `(bookId, sourceNamespace, sourceRef)`；
5. 本机清理要求 `guestBookId` 与来源快照一致。

### 1.3 兼容旧数据

- 旧目标记录的 `source_namespace` 默认空字符串；
- 旧状态键 `"guest"` 仍可读取，但只作为 legacy 信息；
- **不会**把无稳定身份的旧记录静默归到当前游客账本：
  - 变化记录默认保留目标；
  - 旧记录禁止直接覆盖；
  - 清理预览只接受新命名空间下、目标 version 和来源指纹都匹配的状态；
- 旧游客数据不会自动迁移/合并；首次重新预览会显示“旧导入记录身份未确认”的提示。

专项测试覆盖：两个不同 `guestBookId` 使用同一 `sourceTransactionId` 导入同一目标，生成两条独立目标记录和两个状态键；旧 namespace 目标不会被静默覆盖。

## 2. 本机游客来源清理

### 2.1 原则

- 导入成功和来源清理是两个独立动作；
- 默认保留；
- 只清理服务端确认“具体记录已安全迁入且目标仍校验通过”的记录；
- 未迁移、已跳过、已变化、旧身份、目标修改/删除的记录保留；
- 不清理整个 IndexedDB，不影响分类、标签、设置、其他游客数据。

### 2.2 服务端校验

新增只读接口：

`POST /api/v1/ledger-imports/guest-cleanup-preview`

校验：

- 目标账本仍为当前账号可用的单人正常账本；
- 导入回执属于当前账号且目标一致；
- `guestBookId` 与快照一致；
- 状态决策为 `imported`；
- 目标交易存在且未删除；
- 目标 `sourceNamespace`、`sourceRef` 与状态一致；
- 目标 version 等于上次确认 version；
- 来源当前指纹等于状态指纹。

返回 `cleanableSourceIds`、`cleanableCount`、`retainedCount`；服务端不执行删除。

### 2.3 本机执行

- 仅移除这些指定的游客交易记录；
- 移入本机 `GuestData.cleanup` 归档，可恢复；
- 一次 IndexedDB 写入完成归档+移除；中断不会半删除；
- 重复调用幂等，已不存在记录不重复处理；
- 页面显示“将清理 X 笔、保留 Y 笔”，并在完成后显示“已清理 X 笔、来源仍保留 Y 笔”和恢复按钮。

## 3. 正式来源 B

- 默认完整保留；
- 导入结果页新增“来源安全与清理”卡片，必须手动点击检查；
- 服务端只读接口返回：
  - 来源当前总账目；
  - 能在目标账本找到的已迁入数量；
  - 未确认迁入数量；
  - S13 lifecycle 的 `canArchive`、归档时间、自动恢复截止、计划永久删除时间、待恢复请求；
- 弃置按钮调用 S13 既有 `POST /books/:bookId/lifecycle {action:"archive"}`，**不是 SQL 删除**；
- 未迁入记录 >0 时显示额外警告并要求再次确认；
- 弃置后可用 S13 归档恢复入口恢复；
- 不提供一步永久删除，不自动执行弃置。

## 4. 任务取消与 TTL

### 4.1 取消

新增 `POST /api/v1/ledger-imports/jobs/:id/cancel`：

- 行锁与批次事务串行；取消先获锁则后续批次不会再执行；批次先提交则保留已提交记录；
- 取消不等于撤销：已导入/更新/跳过的部分保留；
- 状态改为 `cancelled`，清空游客来源快照和操作列表，保留计数、批次和最小错误信息；
- 不允许再 resume；
- UI 进度卡显示“已取消”、已提交批次和 **保留已提交部分** 的明确说明。

### 4.2 TTL

- `IMPORT_JOB_TTL_DAYS` 默认 **7 天**；
- 后台定期扫描 `paused/failed` 且超期的任务，改为 `expired`；
- 清空 `payload.source` 和操作列表；
- 已导入账目和回执不删除，不标记为整体成功；
- UI 明确显示“已过期，来源快照已清理，无法继续该任务；已导入账目保留”。

## 7. 仍存在的风险

1. **旧游客状态/目标记录的来源身份无法凭空还原**；本轮采取保守策略：不自动关联、不覆盖、不清理。
2. **游客清理归档只在本机**；清除浏览器数据会同时失去归档和来源，不能声称服务器可恢复游客本机数据。
3. **取消与 worker 的极端并发**由数据库行锁和状态检查保护，但尚未做大量并发压力测试。
4. **TTL 清理后无法继续旧任务**；已导入账目保留，但用户需要重新预览并可能产生新的任务。
5. **正式来源弃置后按 S13 生命周期存在恢复期限**；超过期限的计划永久删除由 S13 负责，本功能不绕过。
6. 来源清理不会清理分类、标签或其他本机数据；不清理整个 IndexedDB。
7. 生产、部署、push 均未执行。
