## 发现的问题 1：同 key 第二次 PUT 仍然覆盖（严重）

测试写身份对同一个测试对象连续两次 PUT：

- 两次都返回 **200**；
- 读身份 GET 看到的内容已变成第二次上传的内容；
- 测试桶对 PUT 返回了 `x-cos-version-id`，说明**版本控制已启用**，但 `x-cos-forbid-overwrite: true` 没有阻止当前版本被替换。

腾讯云 PUT Object 文档也明确：同名对象默认覆盖；要保留旧版本需要版本控制，而严格不可覆盖还需要对象锁/合规保留等机制。**不能继续把 `x-cos-forbid-overwrite` 当成不可覆盖保证。**

代码已增加最低限度防护：`CosCriticalRemote.putIfAbsent` 在上传前先 HEAD；如果同名对象已存在则抛 `RemoteObjectExistsError`，让上层按 hash/元数据核对，不再盲目 PUT 覆盖。实测该客户端路径第二次上传被阻止且原内容保留。但这仍不能替代服务端版本控制/对象锁（HEAD 与 PUT 之间仍有竞态，人工/其他身份仍可覆盖）。

生产上线前必须由所有者选择：

- 使用**独立不可变桶 + 对象锁/WORM**（需确认腾讯云账号资格、地域、最短保留期）；或
- 明确接受“版本控制保留旧版本、但当前 key 可被覆盖”的残余风险，并增加监控；或
- 改变对象键/恢复协议（随机不可复用 key、索引/manifest），这会扩大改动，不能偷偷做。

## 发现的问题 2：读身份无法按测试前缀 List

读身份 GET/HEAD 测试对象成功，但 `GetBucket` 带上 `cos:prefix` 条件后，**列测试前缀也返回 403**。已尝试的 policy 条件形式（`string_equal` + `cos:prefix`）在该 CAM 用户策略中没有生效。

因此：

- 读身份目前只能按**已知对象 key** GET，不能安全按前缀列举；
- 生产安全恢复依赖读取事件列表，**当前读身份配置不足以做真实恢复演练**；
- 不能为了让 List 成功而给读身份整桶 GetBucket（那会允许读取/枚举生产对象）。

建议改为**独立测试桶**：读身份只对测试桶有整桶 GetBucket，测试桶不存在任何生产对象；生产事件也建议使用独立桶或先证明桶策略/临时密钥能严格限制 List 前缀。

### 覆盖行为（与旧桶不同）

- 新桶**版本控制关闭**；
- 同 key 第二次 PUT **带** `x-cos-forbid-overwrite: true`：**409，原内容保留**；
- 同 key 第二次 PUT **不带** 该头：**200，当前内容被覆盖**；
- 因此新桶策略下客户端保护有效；生产接入必须选择同样行为的专用桶，不能沿用“旧桶上该头无效”的假设；
- 客户端仍在 PUT 前 HEAD，不能把客户端保护当服务端绝对不可篡改保证。
