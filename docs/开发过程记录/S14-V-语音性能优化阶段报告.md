# S14-V 语音识别性能优化阶段报告

> 状态：**研究/实现阶段，未发布，未部署生产**。生产仍为 1.14.20，语音默认模型仍为 small，线程仍为 2。
> 所有测试音频均为合成 TTS、噪声或静音，不含真实用户录音或财务数据；未向任何第三方 AI API 发送音频。

## 1. 结论摘要

- 生产实际配置已确认：`LIBELLUM_WHISPER_MODEL=small`、`LIBELLUM_WHISPER_THREADS=2`；不存在额外错误线程配置。
- 正常 4.7 秒中文语音：生产服务器 warm 约 **24.4–24.8 秒**，本地 Ryzen 机器约 **4.4–4.9 秒**；服务器推理在噪声中仍约 **25.5 秒**。
- 服务器隔离测试 base：4.7 秒音频推理约 **6.7 秒**，比 small 快约 3.8 倍，但仍高于 5 秒目标，且本地合成集上出现 1 个商户名错误。
- 已实现保守 VAD：5 秒静音从完整推理降到约 **13 毫秒**；正常语音仍交给 Whisper，不降低识别范围。
- 已实现可配置模型路径、线程数上限保护、子进程提前退出/启动失败处理、超时收敛和分段计时。
- **未达到“3–5 秒中文语音端到端接近 5 秒”的目标**；普通语音 small 的延迟基本不变。当前不准备生产发布版本，也不修改生产默认模型。

### 2.4 准确率结果

**转写文本层面的关键字段**（9 条有语音样本）：

| 模型 | 金额 | 日期 | 渠道 | 商户 | 收支方向 |
|---|---:|---:|---:|---:|---:|
| small | 9/9 | 7/7 | 9/9 | 3/3 | 9/9 |
| base | 9/9 | 7/7 | 9/9 | **2/3** | 9/9 |

- small 的商户名全部正确（含“星巴克”“全家便利店”）。
- base 把“星巴克”听成“新八课”；金额/日期/渠道仍正确。
- 两者都能识别美元/银行卡/信用卡等样本。

**重要发现（既有字段解析问题）**：当前 `parseSpokenEntry` 在含日期的文本中会把日期汉字误当金额。例如：

- “10月8号……42元五角”→ API 解析金额为 `5` 而不是 `42.5`；
- “9月21号……88元”→ API 解析金额为 `9` 而不是 `88`。

这不是 small/base 的识别错误，也不是 S14-V 新引入的问题；是**既有字段提取器**的行为。它意味着当前语音 API 在“日期 + 金额”同句场景下不能可靠地给出金额，不能为了发布而隐藏。本轮没有修改字段解析器，避免把性能阶段扩大成计费字段语义重构；建议作为独立修复项。

### 2.5 短音频、静音和 VAD

- 4.7 秒音频解码仅 5–24 ms；没有额外文件写入或二次转换。
- 原实现没有 VAD：5 秒静音仍会执行完整 Whisper 推理，服务器约 50–57 秒，且可能产生幻觉文字。
- 新 VAD 是保守能量门：只跳过几乎没有能量的片段。正常语音仍完整送入 Whisper。
- 服务器隔离测试：5 秒静音从完整推理降到 **约 13 毫秒**，`speechless=true`，没有幻觉文本。

### 3.3 错误与恢复

- 子进程在 ready 前退出：立即失败，不再等旧的 300/600 秒。
- 启动/转写超时：默认启动 120 秒、单次转写 120 秒；清理子进程和启动 Promise。
- 失败后下一次请求可以重新启动子进程。
- 技术错误只写服务端日志；用户收到简短 503 提示。
- 录音从未写入磁盘；仍为 base64 内存传输。
- 语音转写与字段提取仍然分离；未修改账本和自动入账逻辑。

## 5. 最终回答

1. **原来语音为什么慢？**
   CPU-only Whisper small 在 2 vCPU 老 Xeon 上执行固定约 30 秒窗口推理；耗时的 95% 以上在推理，不是上传、解码或字段解析。生产 warm 约 24.4 秒；本地 Ryzen 约 4.4 秒。模型只加载一次，不是重复加载；线程已正确设为 2。

2. **small 和 base 哪个更适合 Libevra？**
   当前仍推荐 **small 作为默认**：合成集上 small 商户名 3/3，base 2/3；base 虽快约 3.8 倍，但在服务器仍约 6.7 秒，并且中文细节有可见损失。base 可作为隔离环境中的可选配置继续评估，不应直接替换生产。

3. **优化后实际快了多少？**
   - 静音：从整段推理（服务器约 50–57 秒）降到约 **13 毫秒**，这是本轮最大且确定的收益。
   - 正常语音：small 基本没有变快（25.5 秒 vs 24.4 秒，在噪声范围内）；base 可选时约 6.7 秒，但仍然超过 5 秒目标。
   - 目标“3–5 秒接近 5 秒”**未达到**。

4. **准确率是否有可观察下降？**
   small 的识别文本与旧参数下一致；VAD 只影响静音，正常语音没有观察到下降。base 出现 1 个商户名错误。另有**既有的“日期汉字被字段解析器误当金额”**问题，不是本次改动造成，但在发布语音前必须独立修复。

5. **需要增加多少常驻内存？**
   默认 small 没有增加；VAD/计时/配置代码可忽略。若切换到 base，模型内存会从 small 的约 0.7–0.86 GB 降到 base 的约 0.31 GB（本地/既有测量），是减少而不是增加。

6. **现有服务器能否稳定运行？**
   可以稳定运行，未发现 OOM、内存不足或进程崩溃；但 small 的正常语音等待约 25 秒，交互体验仍不达标。建议先不升级服务器，优先解决模型/字段解析和明确产品取舍。

7. **哪些优化已经实现，哪些仍属于后续研究？**
   已实现：保守 VAD/静音短路、模型路径和线程可配置、线程上限保护、子进程提前退出/恢复、超时收敛、分段计时、用户友好 503、自动化测试。
   后续：base 真实中文 A/B 和产品选择、字段解析器日期/金额修复、更完整 VAD（人声检测）、更快的 CPU 推理方案、medium/large 评估、原生端/家庭服务器本地识别。

8. **是否已经达到可发布候选标准？**
   **没有。** 主要原因是普通 3–5 秒语音仍远高于 5 秒目标，且既有字段解析器会对“日期 + 金额”误解析。当前不准备 1.14.21 发布公告，也不修改生产模型/线程/服务器。若所有者愿意先发布一个低风险可靠性补丁，本轮 VAD/错误处理代码可作为候选，但它不应被宣传为“语音提速”。
